# Change Execution Rationale

This intent document preserves observations behind `docs/change-execution.md`. It states no execution rule and cannot authorize a product or workflow decision by itself.

## The Delegation Problem

Agents omit details, misread instructions, trust reports, and follow locally reasonable paths that do not move the requested outcome. A long-running primary agent also loses semantic resolution through repeated context compression, excessive contradictory input, and accumulated procedural residue. The engineering problem is therefore not to assume a perfect coordinator; it is to preserve direction and reality contact while allowing the method to adapt.

The repository previously responded to each observed failure by adding another universal gate, matrix field, role transition, event, counter, or breaker. Many additions addressed a real incident. Together they made work locally compliant and globally slow: a simple NanoHost correction could take hours, tens of role events, and repeated independent reviews while the product boundary remained untouched. The failed premise was that enough prescribed procedure would remove model fallibility.

The current direction preserves the protected concerns and removes the universal mechanisms. User intent, strict safety, actual artifact inspection, independent judgment where risk warrants it, oracle honesty, and concurrent write ownership remain hard. Decomposition, role order, test order, correction count, and intermediate document shape remain methods.

## Observations That Survive The Cutover

**Direct artifacts beat completion reports.** Several expensive escapes occurred when a producer described a compliant change while the actual diff changed an immutable test or wrote beyond the assigned surface. Reading the artifact would have settled the discrepancy immediately. This is why acceptance requires the diff, bytes, or named execution output rather than the report alone.

**Prediction exposes empty motion.** An orchestrator can explain after any action why the output was useful. Recording before a material action which artifact, belief, or decision should change makes a repeated no-yield method visible without a universal event budget. It extends the same logic as naming a test's expected failure before running it.

**Recovery needs a different context.** In the observed long programs, the same context that had converged on an unproductive route could reread its checkpoint and reproduce the route. External clean-context readings found the drift. A fresh-context direction check preserves that useful intervention without installing a permanent review pipeline.

**The trigger measures drift, not tokens.** The first version of that check fired after every compaction. One measured pilot then compacted 107 times in 58 hours while spawning 28 subagents in total, and left no record of the check having run or of having been skipped; whether the obligation was too costly or merely ignored cannot be told from that, which is itself the problem. Compaction frequency is set by tool-output volume, so it tracks token consumption rather than accumulated drift. The same pilot showed where drift is actually expensive: a retracted host-noninterference belief was acted on three times, removing the system Docker bridge each time, before evidence caught it. A belief that is never spent costs nothing; the price is paid at the point of commitment. Its owner therefore keys the check to commitment rather than to compaction, and asks for a recorded line where no check runs so that the remaining gap is visible rather than silent.

**Intent and working state have different lifecycles.** A checkpoint must be cheap to rewrite as facts and methods change. User intent cannot be equally mutable, because a compressed or resumed context could silently lose a non-negotiable. Append-only intent epochs make a real change visible while leaving the route plastic.

**One writer is enough concurrency machinery.** The repository paid heavily for artifact inventories, expected magnitudes, expansion counts, and lease identities. Their durable purpose was preventing agents from overwriting each other. Declaring one writer per path at a time protects that purpose directly.

**Reality contact is cheaper than source inference when the environment is reachable.** The NanoHost program repeatedly derived an executable environment from prose and source, then learned on the real host that the inferred transition did not exist. The product's own errors named missing facts more cheaply. This supports probe-before-commitment and does not relax authorization, credential, cleanup, or irreversible-effect boundaries.

**An instrument can be green and blind.** A host assertion suite reported all mismatch cases green while mutation showed that its real comparison path executed zero times. The suite had tested fixture bytes, not the remote assertion it claimed. Oracle classification, deliberate failure, positive observation, and effect-domain ownership remain necessary because workflow simplification does not make evidence trustworthy by itself.

**Findings need a queryable lifecycle; route history does not.** Two existing findings reports accumulated 124 items under two heading levels, two ID forms, sixteen field labels, and dozens of free-form status phrasings; a field named Closure evidence appeared beside both resolved and still-pending work, so a reader could not answer what remained without reinterpreting the whole file. Findings are curated items whose status changes and whose unresolved set is queried after plan close, so a small structural check intercepts an observed retrieval and retention failure. A route log instead appends independent causal lines and derives no current state; imposing a validator there would rebuild the coordination machinery this model removed without intercepting the findings failure.

## Why No Replacement Framework Is Installed Yet

The proposed replacement vocabulary contained many one-use capitalized concepts. In always-loaded governance, descriptive vocabulary tends to become a checklist and then a mandatory lifecycle. Installing that framework before the pilots would repeat the same pattern under new names.

The first cutover is therefore subtractive. It keeps a small safety and reliability kernel, then uses the three unfinished plans as different experiments: strict real-host effects, architecture-heavy work, and recovery from a blocked boundary. Only repeated evidence of a missing capability justifies a later binding addition.

Raw pilot transcripts, checkpoints, artifacts, timings, and human decisions remain outside the active execution context and are reviewed after the work. Rates do not flow back into executing roles, no live threshold stops a task, and one pilot result does not become a universal rule.

## What Would Falsify The Direction

The subtractive direction should be reconsidered if the pilots show repeated escaped defects traceable to a removed protection, silent loss of user intent despite append-only epochs, concurrent write loss despite path ownership, repeated inability to resume after fresh-context review, or strict safety incidents. The response is to add the smallest mechanism that directly intercepts the repeated failure, not to restore an entire historical pipeline.

Faster completion alone is not success. The relevant comparison includes time to a usable artifact, time to first reality contact, human interruptions, wrong-premise rework, recovery latency, escaped defects, and strict incidents. These are task-external observations for engineers and auditors, not execution targets.
