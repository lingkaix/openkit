# NanoHost Runtime And Transport

This specification is the single entry owner of the NanoHost execution-host topology, identity and placement definitions, component boundaries, shared-Sandbox and AgentSession lifecycle, placement compatibility, on-demand idle Sandbox retirement, operator distribution/installation/replacement/inspection/image-store surface, and Runtime Epoch fail-stop recovery and forensic reporting.

## Scope

### Owns

- The container provider realization of the [environment provider contract](20261020-compute_neutrality_target.md#environment-provider-contract) for one configured NanoHost. This includes the Host epoch, Sandbox incarnation map, physical readiness, absence proof, Worker Shim carrier, and provider-side recovery.

- Scope execution intent and outcome transactions, global reservation commit gaps, and deadline progression inside NanoCore in [Durable Execution And Control Store](20261019-durable_execution_and_control_store.md) ([decision](../decisions/20261019-durable_execution_and_control_store.md)), and scheduler admission, claim selection, execution-attempt grants, and capacity accounting in [Durable Scheduler Design](20260703-durable_scheduler_design.md) and [Runtime Scheduling Scale](20260703-durable_scheduler_design.md#scale-limits).

## Definitions

- **`Execution Host` and `NanoHost`**: `Execution Host` is the generic deployment role; `NanoHost` is OpenKit's sole concrete product and implementation of that role. One deployment NanoHost owns one current private Runtime Epoch containing the NanoHost service, one stock OpenShell Gateway, the effect-capable members of one configured container backend, and zero or more Sandboxes. NanoHost is the sole local OpenShell lifecycle authority, replacing per-AgentSession disposable Cells.
- **`NanoHost service`**: the trusted execution-host process (`apps/nanohost`) that owns local OpenShell lifecycle effects, the Runtime Epoch, transport projection, package materialization, Sandbox creation and deletion, Sandbox Integration attachment, evidence transfer, and cleanup reporting. It applies only already-authorized work selected by NanoCore's scheduler and policy owners and never selects product work, broadens permission, creates product state, settles uncertain external effects, applies Workspace changes, or infers Turn completion.
- **Runtime Epoch.** The private enclosing lifecycle and failure boundary for the Host's execution infrastructure. At each start NanoHost issues a new Host epoch ID and admits it with its enrolled Host, deployment and current connection generation. The same Host epoch ID survives a reconnect of the same runtime. NanoCore retains the origin Host epoch ID on claims and follows it when recovering original effects. The Core connection generation fences a carrier and identifies no physical lifetime.
- **`Effect-capable member`**: any process or service in the epoch that can accept, retain, forward, complete, or materialize an OpenShell or container-backend effect, comprising the NanoHost service, the stock Gateway, every member of the configured container backend (`dockerd`, `containerd`, and their helpers and proxies, plus the epoch `slirp4netns` helper), and the Sandbox incarnations they operate. Monitoring, logging, or read-only diagnostic processes may remain outside the failure group only when they cannot signal, forward, mutate, authenticate to, or complete a runtime effect. The OS service manager's control-group termination supplies the fail-stop guarantee rather than any implementation language; this specification makes no claim that other languages cannot express the required transport or process mechanisms.
- **Worker Shim.** The in-Sandbox supervisor in `packages/worker-shim`, with one lifetime per Sandbox incarnation. It pulls over NanoHost's relay and supervises native adapter processes. The [Worker Runtime Communication Model](20260629-worker_runtime_communication_model.md) owns its contract.
- **Residency and measured image evidence.** Core retains Sandbox, Sandbox incarnation and origin Host epoch lineage with the deciding claims. Inventory and live readiness are views. If a decision uses an observation as proof, keep it with that decision. The backend keeps the measured image identity for the exact binding and preserves its existing work and evidence references after cleanup.

## Components And Placement

```text
Runtime Epoch
├── NanoHost service (apps/nanohost)
├── stock OpenShell Gateway (foreground process)
├── configured container backend (V1: dedicated dockerd, containerd, and slirp4netns)
└── zero or more Sandboxes and AgentSession executions

outside every epoch, durable and inert
├── NanoHost Image Store (/var/lib/openkit/nanohost-images)
├── Persistent Worker Volumes (/var/lib/openkit/nanohost-work)
└── NanoHost Token slots and forensic evidence
```

- **Technical role matrix and single binary boundary**: the NanoHost service is one deployable Rust binary crate at `apps/nanohost` (`@openkit/nanohost`, not a shared `packages/` library, with no parallel Go or TypeScript service implementation, no in-process Gateway server, no normal-operation OpenShell CLI subprocess wrapper, and no vendored protobuf or generated-client fallback). It compiles the official `openshell-sdk` from the Cargo-locked release commit and runs the checksum-verified stock Gateway as a separate foreground process. The same one-NanoHost topology operates when NanoCore is co-located, containerized, or on another host without changing ownership or authentication. NanoCore neither prepares, creates, deletes, inspects, nor recycles OpenShell resources and holds no Cell, SSH lifecycle, remote Gateway, or Docker endpoint handle.

| Role | V1 realization | Owns | Excludes |
| --- | --- | --- | --- |
| NanoHost service | One Rust binary crate under `apps/nanohost` | Runtime Epoch coordination, one NanoCore session, one Gateway client channel, local OpenShell effects, sandbox bridges, readiness, and bounded evidence. | Product authority, scheduler policy, durable operation recovery, alternate language implementation, and arbitrary proxying. |
| OpenShell client boundary | Official `openshell-sdk` source fixed to the supported release commit by Cargo and `Cargo.lock` | Typed lifecycle and forwarding RPC access over one authenticated loopback gRPC/HTTP/2 channel. | Vendored protobuf copies, generated-client fallback, Gateway server code, CLI output parsing, filesystem discovery, floating `main`, and OpenShell protocol extensions. |
| stock OpenShell Gateway | Official unmodified checksum-verified executable at the qualified pin | Stock Gateway state, authentication, sandbox lifecycle coordination, `ForwardTcp`, Supervisor pairing, and byte relay. | OpenKit route semantics, NanoCore connectivity, in-process linking, OpenKit patches, and independent restart. |
| configured container backend | One dedicated `dockerd` and its dedicated `containerd` with NanoHost-private roots, sockets, and networks, as foreground service-cgroup members | Container and sandbox execution state for the current epoch only. | Backend selection, image acquisition, product authority, membership in more than one epoch, independent restart, and any effect domain outside the NanoHost service cgroup. |
| NanoHost Image Store | One durable epoch-external digest-addressed content directory plus a bounded index, owned by the NanoHost service account | Verified inert image content and its local index. | Registry service behavior, published artifacts, product records, canonical storage, mutable runtime state, credentials, listeners, and epoch membership. |
| OS supervisor | Linux service manager and cgroup boundary | Complete group kill, host-to-Sandbox process containment, fresh-epoch restart, and proof that no effect-capable member survives NanoHost failure. | Member-local recovery, a repository-owned supervisor framework, and readiness adjudication. |
| Worker Shim | Existing TypeScript `packages/worker-shim` evolved in place | Sandbox-local standard HTTP/2 client, fixed local binding, governed runtime-context injection, and Worker Agent process supervision. | Gateway credentials, `ForwardTcp`, direct NanoCore connectivity, route authority, and a second shim package. |
| NanoCore | Existing TypeScript `apps/nanocore` application | Durable work, scheduler, identity, permission, route semantics, lineage, sequence, usage, audit, product state, and authorized build definitions supplied as backend build input. | Gateway, container-backend, sandbox, process, image-store, or Runtime Epoch lifecycle effects, and any host instruction. |

- **Internal roles, Rust stack, and reversion condition**: `apps/nanohost` has four logical internal responsibility roles (epoch coordinator, NanoCore-session owner, OpenShell-client owner, and per-Sandbox bridge owner) inside one binary crate rather than public interfaces, separate crates, plugins, services, databases, or durable state machines; source module count is not contractual. It uses a small pinned async stack (Tokio for process and I/O ownership, the official exact-release OpenShell SDK for Gateway gRPC, `h2` for the server side of the nested sandbox HTTP/2 session, and Rustls for non-loopback NanoCore TLS) under the app-local Cargo lock and toolchain owner (`docs/toolchain.md`, `docs/cookbooks/rust-setup.md`), with no application Web framework or copied Rust protocol schema family. Rust (`apps/nanohost`) is the sole selectable NanoHost implementation for self-contained execution-host deployment, predictable low resident footprint beside the container backend, direct reuse of the upstream Rust OpenShell SDK, and explicit HTTP/2 flow-control management; the decision reverts to a TypeScript implementation (keeping the stock Gateway as a separate checksum-verified foreground process and without weakening the contract, forking OpenShell, or splitting NanoHost across two languages) only if the official SDK client boundary cannot invoke required stock operations, the transport envelope cannot be met in the Rust stack, or delegated implementation and review throughput proves materially worse than the equivalent TypeScript path on comparable work.
- **Scale, authority, backend, and retired-topology boundaries**: under the substrate doctrine in [Runtime Model](../core/runtime-model.md) (NanoHost collects execution facts while NanoCore accepts product facts, work descends while authority does not, bytes move while truth does not, and NanoHost buffers only what it produces without caching what it was granted) and [Durable Execution And Control Store](20261019-durable_execution_and_control_store.md) (which lives inside NanoCore without adding a NanoHost operation journal, Worker inbox, or recovery service, while existing physical placement, Epoch, attachment, identity, command-receipt, current-authority, and cleanup proofs remain binding until individually proved ablations remove them), NanoCore retains all decision authority and NanoHost applies only already-authorized work. The current implementation stays inside the small-deployment profile in [Runtime Scheduling Scale](20260703-durable_scheduler_design.md#scale-limits) with one configured NanoHost and one configured host-local container backend; no product-visible NanoHost, Runtime Epoch, Gateway, container, network, process, or backend-native record exists, and dynamic discovery, fleet scheduling, multi-NanoHost placement, live AgentSession migration, active-active execution, high availability, warm pools, and remote attestation are excluded unless a separate accepted scale/attestation architecture is adopted. The legacy NanoCore-owned per-Session OpenShell Cell lifecycle and configuration are removed and are never a selectable fallback or second lifecycle owner. Configuration and execution exclude any Cell owner, Cell epoch, Cell helper, NanoCore-to-SSH lifecycle target, NanoCore-to-Gateway URL, operator-managed Gateway forward, direct Sandbox-to-NanoCore endpoint, custom OpenShell binary, or TLS-verification bypass; SSH may be used only for installation-time stdin secret-sink delivery, diagnostics, evidence collection, or human-authorized break-glass response (aside from the pinned opaque Gateway-internal single-file helper relay in [NanoHost OpenShell Gateway](20261116-nanohost_openshell_gateway.md)), never for normal execution or recovery. NanoHost introduces no durable operation journal, settlement coordinator, recovery state machine, database, actor framework, plugin framework, multi-crate workspace, in-process Gateway server, or normal-operation OpenShell CLI wrapper.
- **Epoch boundary and foreground cgroup supervision**: the Runtime Epoch includes every mutable root, socket, network, cgroup, process, authentication material, and backend handle that could complete an accepted OpenShell effect. On the V1 Linux execution host, NanoHost starts the fixed stock Gateway and dedicated container-backend executables once as foreground children inside its OS service cgroup using direct argument vectors and fixed NanoHost-owned paths without a shell or wrapper script, under mandatory control-group termination semantics equivalent to systemd `KillMode=control-group` and with no OpenKit supervisor framework.
- **Configured container backend and effect-domain classification**: NanoHost instantiates, provisions private roots for, proves empty, and rebuilds only the single configured container backend; supporting additional backends is a configuration-time selection concern only (with no backend abstraction layer, driver framework, capability negotiation, or live runtime switch), changing the configured backend replaces the epoch through full invalidation and fresh creation, and an epoch that starts an unconfigured backend is invalid. Every candidate backend is classified by its effect domain before configuration:

| Class | Meaning | Fence | V1 status |
| --- | --- | --- | --- |
| Host-local effect domain | Every process able to accept, retain, forward, complete, or materialize an accepted sandbox effect is a descendant member of the NanoHost service cgroup on the execution host. | Complete control-group termination proves the prior effect domain impossible. | Docker authorized (`dockerd` + `containerd`); Podman requires its own accepted realization contract. |
| External effect domain | An accepted effect can be completed by a control plane, scheduler, kubelet, or node agent outside the NanoHost process tree and cgroup. | Cgroup termination is **not** a fence; a generation-scoped external fencing contract is required. | Kubernetes and every other remote orchestrator are **not authorized**. |

- **Epoch-external Image Store and Persistent Worker Volumes**: the NanoHost Image Store (`/var/lib/openkit/nanohost-images`) and the NanoHost Token sink remain outside every Runtime Epoch and MUST NOT contain mutable runtime state, live sockets, process identity, Gateway data, container records, or epoch authentication authority. The Image Store is inert local supply (never a registry, published artifact, product record, canonical storage, or network service) holding only verified digest-addressed OCI manifests, configs, and layer blobs plus a bounded local index readable and writable only by the NanoHost service account, without certifying user-authored blobs as credential-free; the configured container backend receives images only through explicit NanoHost-driven import, never by sharing or mounting the store. Published worker images are never a prerequisite for NanoHost startup or readiness: fresh Epoch creation starts the private backend and Gateway without acquiring, building, or importing Worker images and without `OPENKIT_NANOHOST_REQUIRED_IMAGE_DIGESTS`, a startup image list/count, or a pre-ready effect lane (while stock OpenShell Supervisor bootstrap may access GHCR before Gateway health). Under [Persistent Worker Volumes](20260910-persistent_worker_volumes.md), NanoHost alone derives root-validated fixed mounts through stock `SandboxTemplate.driver_config` and the private Docker driver's explicit mount support (callers never supply backend paths or arbitrary driver config), and `/var/lib/openkit/nanohost-work` is a durable execution-host root outside epoch roots, the Image Store, credentials, and forensic evidence that is never removed by recursive epoch cleanup, explicit image removal, or normal Sandbox deletion.

## Sandbox And Session Lifecycle

### Sandbox Incarnation Map

NanoHost realizes Core's desired set by Sandbox incarnation ID. The [OpenShell adapter](20261116-nanohost_openshell_gateway.md) owns the private physical address mapping. The incarnation map retains the original Gateway, provider workspace, origin Host epoch and mapping version. The full inventory reports readiness, attachment, envelope and shim carrier against that incarnation. Core derives occupancy from its claims. V0.2.0 has one Host slot and one Worker per Sandbox incarnation. A compatibility check admits placement within the exact storage association and authorized envelope.

Before create, Core records the original intent, target incarnation, payload binding and exclusions. Check current authority and required predecessor release. The incarnation row may enforce exclusive ownership of the derived address across overlapping and still-actionable calls in the original provider namespace.

After a possible create, inspect, reconcile and delete only under the original binding. Verify the native object ID when known. A collision or lineage mismatch returns a typed conflict and issues zero destructive calls. A missing observation leaves the original binding and claim held.

Recheck the existing static Sandbox envelope and native continuation compatibility on placement. The Sandbox check covers Workspace, trust class, admitted image and template, layout and mounts, OS identity, network, provider and credential visibility, resource class, required capability and containment. Reuse of a native conversation requires the exact authorized reference under [AgentSession](../core/agent-session.md) and current compatibility with the prepared package. Changes in child-only public environment or static Skill and MCP supply require an authorized successor with exact native resume. A wider envelope change requires Sandbox replacement. Credential revocation fences work immediately.

NanoHost starts the image-owned Worker Shim once for a Sandbox incarnation ID and refuses a second start for that ID. An authenticated reconnect within the existing budget can restore the carrier to the same shim and incarnation. A shim exit requires Sandbox recycle. A new Host agent starts a new epoch and adopts no Sandbox from its predecessor.

- **Epoch creation, immutable membership, and readiness order**: on first start or recovery, the supervisor establishes a new group and NanoHost creates fresh private roots, sockets, networks, namespace state, authentication material, container-runtime state, and Gateway state, validating identity, stock component identities, Supervisor ownership, private root ownership, loopback Gateway binding, host-to-Sandbox isolation, and absence of stale effect-capable processes before accepting work (failed creation keeps NanoHost non-ready, exports one `epoch-creation-failure` report, terminates the partial group, and retries only through a fresh epoch). Epoch identity, component identities, configured backend, mutable roots, sockets, networks, namespaces, supervision membership, and epoch-local authentication generation are immutable; any change replaces the epoch through full invalidation and fresh creation, while NanoHost Token slot updates remain outside epoch identity and only Sandbox incarnation create/delete and point-of-use image import mutate membership inside a healthy epoch. `EpochCoordinator::start` proves the epoch's inventory fresh and empty before any effect; if NanoCore is unavailable, NanoHost stays locally healthy without advertising capacity until `EpochCoordinator::start`, physical admission, and durable empty `204` readiness acknowledgement complete in order before the first effect poll, and a healthy reconnect repeats admission and readiness without rebuilding the still-live epoch while `RuntimeTarget` preserves any occupied or cleanup-held slot.

### Persistent Worker Storage Amendment

- **Storage attachment and materialization.** NanoCore records current authority and the placement claims before contact. NanoHost verifies the exact Volume writer generation, incarnation and local root identity, and uses the validated mounts. Initialize a Volume only when the authorized attachment identifies it as new. Verify that `workspace.collect` names the same live incarnation and attachment before scanning. Collection does not change the writer generation or release it. Image builds use no retained work mounts. Keep-present readiness includes the shim carrier. A keyed Turn input still requires the fresh immutable AEP, Context Package and attempt authority, with the existing route and supply checks. Verified AEP import precedes Worker supply and Context Package import. Initial work-slot materialization and accepted baseline precede the first Turn input. Retained slots keep their admitted baseline. See [Persistent Worker Volumes](20260910-persistent_worker_volumes.md) and [Workspace Synchronization](20260703-workspace_synchronization.md).
- **Close, drain and idle retirement.** Each AgentSession keeps its own authority, terminal handoff, capture and cleanup evidence. Revoke route bindings and dispose of temporary control and request state after required collection. Preserve native and working bytes. Terminal export can start after accepted `final_status`, while Workspace collection still gates the next Turn. Sandbox retirement closes admission, settles or truthfully interrupts admitted work, revokes routes, collects required outputs and keeps the incarnation absent. Follow [Durable Scheduler Design](20260703-durable_scheduler_design.md#replacement-and-drain) for an unproved Worker stop. An incompatible idle Sandbox may retire on demand when its exact old owner, binding, collection and settled state are proved, with no live attempts, unrecorded receipts or pending operations. Unknown or dirty residency refuses capacity. Recheck unchanged storage selection and settle old obligations against their original lineage. Release the attachment only after provider proof. This rule adds no inactivity timer.

### Physical Epoch Identity And Recovery

On the authoritative connection, NanoHost carries the enrolled Host, deployment, current connection generation and Host epoch ID in the readiness association. Keep-present readiness correlates the actual Sandbox incarnation, Volume writer generation, realized envelope and admitted shim carrier with that association. Inventory and absence evidence carry their epoch and incarnation scope on the current connection. Core rejects stale or mismatched association evidence and stamps the original Host epoch on the deciding claim. Reconnect can change the connection generation while preserving the same Host epoch. The proof that releases a predecessor claim must cover that original epoch.

**Provider absence proof.** The [environment provider contract](20261020-compute_neutrality_target.md#environment-provider-contract) allows exact absence proof inside the epoch or proof by epoch renewal only. The final NanoHost guarantee is decided by S2 qualification. Same-epoch release requires durable closed ingress for the incarnation ID, a definite join of every accepted operation for that ID, and independent exact physical absence including writer detachment. Get and complete List read the same Gateway inventory. They leave physical absence unproved on their own. A deletion or mutation receipt settles only what it proves about the original operation. A request ID supplies no fresh retry or release authority. A Delete acknowledgement during accepted provisioning supplies no join receipt for an accepted create or an already-issued runtime operation. A deadline starts escalation and leaves the claim charged. If accepted create or delete stays unresolved at its original deadline, close Host admission and order epoch renewal under [Replacement And Drain](20260703-durable_scheduler_design.md#replacement-and-drain). Release follows proved predecessor termination and fresh-empty readiness, including the one-slot case.

### Sandbox Credential Carrier

Under [Worker Credential Access Declarations](20260703-vault_secret_injection.md#runtime-file-visibility), private Sandbox creation input may include transient `credentialBindings` (`declarationId`, `planId`, `receiptId`, material reference/version/UTF-8 format, normalized non-overlapping read-only file target, and required ephemeral/retained-storage/capture/export protection). NanoHost validates the closed shape, unique identities, and non-overlapping targets before creating any carrier, after image seeding completes and before empty no-follow mount-point admission, with no caller-selected host path or arbitrary driver configuration. Each Sandbox owns one `0700` `tmpfs` carrier (`nodev`, `nosuid`, `noexec`) outside retained roots inside the pinned private backend mount namespace; source files are Worker read-only while NanoHost retains the writable descriptor for same-inode replacement without rename or remount, proving memory inode identity and actual mounted source, destination, and access through the installed helper before settling the receipt.

## Operator Surface

- **Distribution archive and deterministic packaging**: the NanoHost Distribution composed by [Release Management](20260829-release_management.md) supports only `linux/amd64` and `linux/arm64` archives named `openkit-nanohost-<tag>-linux-<architecture>.tar.gz`. Each archive has one tag-and-target-prefixed root containing 10 files (`nanohost`, `openshell-gateway`, `openkit-nanohost.service`, `install.sh`, `host-manifest.json`, `MANIFEST.json`, `SHA256SUMS`, `licenses/openkit-LICENSE`, `licenses/openshell-LICENSE`, `licenses/openshell-THIRD-PARTY-NOTICES`) and 2 directories (`0755` for directories and `nanohost`/`openshell-gateway`/`install.sh`, `0644` for the unit, manifests, checksums, and licenses, `uid/gid 0/0`, `mtime 0`, fixed member order, two tar zero end blocks and zero-byte padding, and exact 10-byte gzip header `1f 8b 08 00 00 00 00 00 02 03`). Both binaries MUST be little-endian ELF64 x86-64 or AArch64 (`ET_EXEC` or `ET_DYN`) with complete valid ELF headers, bounded ELF64 program-header tables, and at least one executable file-backed `PT_LOAD` segment containing the entry point (entry point and virtual address `< 2^63`, file offset/filesz/memsz/alignment `< 2^32`, memory size covering file size, valid alignment, and full memory interval `< 2^63`; header-only ELF is rejected across packaging, shared verifier, and installer). Gateway and OpenShell license bytes match `apps/nanohost/openshell/release.json`; `install.sh`, `openkit-nanohost.service`, `host-manifest.json`, and `LICENSE` match exact checkout bytes; `MANIFEST.json` projects tag, product commit, target, file set, fixed destinations, target architecture, host-profile id and digest, and OpenShell release facts without duplicating host-profile fields; and no configuration, credential, Token hash, deployment identity, environment file, OpenShell CLI, Supervisor image, Image Store content, runtime evidence, or source tree is bundled.
- **Installer modes, locking, and CLI entry**: the installer writes only `/usr/lib/openkit/nanohost` (`0755`), `/usr/lib/openkit/openshell-gateway` (`0755`), and `/etc/systemd/system/openkit-nanohost.service` (`0644`), verifying all inner checksums, both ELF identities, and the bundled host-profile digest before any write. Live installation requires `requirements-met` from the bundled schema-v2 host profile checker under [Deployment Host Requirements](20260909-deployment_host_requirements.md#machine-readable-requirement-sources) (including Git admission for the private-store scan under [NanoHost Workspace Data Boundary](20260801-nanohost_workspace_data_boundary.md)) with no repository or network fallback. `install.sh --check-host` emits that single profile-check JSON with no mutation or lifecycle effect; `--check` and default live installation reuse the same probe without printing a second host-check JSON object. Live preflight requires existing destination ancestors to be real non-symlink directories and existing destinations to be regular non-symlink files, holds one exclusive advisory lock on `/etc/systemd/system` throughout observation and mutation without lockfiles or durable state, and uses the three adjacent reserved temporary paths (`/usr/lib/openkit/.nanohost.openkit-install`, `/usr/lib/openkit/.openshell-gateway.openkit-install`, `/etc/systemd/system/.openkit-nanohost.service.openkit-install`). `--check` writes nothing, invokes no `systemctl`, reports `host-prerequisites=pass` when met, and reports `installable`, `already-installed`, `resumable`, or `destination-conflict` (`destination-conflict` exits nonzero while preserving truthful host-prerequisite output; the other three exit zero without claiming readiness). Staging accepts only an absolute non-root `DESTDIR` whose canonical normalized form is textually identical, does not exist, and has real non-symlink existing ancestors, creates private staging directories, verifies package and target ELF identities, skips host probes, writes beneath `DESTDIR`, and reports `staged-only`. Live installation prepares all missing payloads at reserved temp paths before atomic no-overwrite publication and revalidation, cleans only invocation-owned regular temps and empty parent directories on caught failure/signal (reusing exact interrupted regular temps while never removing or adopting changed/non-regular/symlink paths), and reports `installation=incomplete` on publication-set failure or `installation=complete` / `installation=already-installed` plus `remaining=configuration,enrollment,service-start` on success; it owns no automatic update, downgrade, rollback, uninstall, repair, configuration, enrollment, image pull, or `systemctl` start/stop/restart. `nanohost --version` runs before configuration, storage, network, enrollment, Epoch, or child effects, prints the Cargo version, and exits zero; unknown arguments select no lifecycle or installer operation.

### Filesystem Capacity Observations

Existing byte limits and free-byte reserves apply on every filesystem, and inode reserves apply where inode accounting is available. When total, free, and available inode counts all report zero, NanoHost treats inode accounting as unavailable rather than exhausted; other observations with zero available inodes retain their ordinary refusal, observation errors and allocation failures retain their owner semantics, and missing inode accounting never weakens a byte-space check or permits retained-data eviction.

### Host-Observed Sandbox Resource Summary

Under the [resource and preflight diagnostic decision](../decisions/20261019-sandbox_resource_and_preflight_diagnostics.md), NanoHost observes the exact Sandbox container through its private V1 Docker and cgroup before removal where possible and carries the result only as optional `resourceSummary` on `sandbox.delete` (carrier close, Worker inventory, `final_status`, and storage-only inspection carry no Host resource facts, and an absent container supplies no fields). The fixed optional fields are `memoryPeakBytes`, `oomKillCount`, `backendOomKilled`, `cpuUsageSeconds`, `cpuThrottledSeconds`, `pidsPeak`, and `exitState` (`created`, `running`, `paused`, `restarting`, `removing`, `exited`, or `dead`), with integer/finite-second values in `0..2^53-1`, boolean `backendOomKilled`, and no paths, process text, logs, environment strings, or arbitrary keys. Current defaults bound the summary to `1 KiB` (with `8 KiB` command-output and `4 KiB` kernel-file limits) and collection to `min(1 s, remaining delete allowance currently 120 s)` before the SDK delete RPC. Invalid or oversized summaries are dropped whole without changing the delete result, receipt identity, or cleanup/fence semantics; unavailable or timed-out fields are omitted as unknown (never `0` or `false`), counters describe container lifetime rather than per-Turn deltas, and validated facts are destined only for the existing teardown stage span when an observer is available, with no retained diagnostic record, cache, metric, or outcome authority.

### Installed Release Replacement

- **Stopped operator replacement and retained state**: explicit operator replacement ([decision](../decisions/20261006-nanohost_installed_release_replacement.md)) replaces an installed NanoHost distribution through the unchanged verified target installer while preserving deployment identity, enrollment, both Token slots and companion metadata, configuration, Image Store, Worker volumes, private Workspace scan content, and forensic evidence (recreating only Epoch state, with no update journal, service, or cross-domain transaction). A retained-format change requires its accepted one-way migration or a disclosed pre-`v0.1.0` deployment reset under [Release Management](20260829-release_management.md#pre-stable-deployment-reset-and-protected-accounts) before replacement; missing or incompatible state blocks readiness without empty reinitialization, reenrollment, or automatic repair.
- **Predecessor fence, payload publication, rollback, and App sequencing**: replacement requires a verified target archive and host check, verified old payload identities, a non-overwriting recovery location, exclusive maintenance ownership, proved complete predecessor fencing (main process absent, service cgroup empty/absent, and all relevant slice descendants unpopulated), and persistent start inhibition across interruption or reboot until the complete target destination set, reloaded effective unit, and retained inputs are verified. Only differing installer-owned destinations are vacated after durable old-payload backup. Partial replacement stays stopped and inhibited; rollback restores only verified old payloads while stopped and inhibited after a full fence and positive proof that old code can read current retained data and configuration, never restoring old Epoch state, rolling back Tokens, replaying unknown operations, or overwriting retained data. App/Web update ([App Update Delivery](20260910-app_update_delivery.md)) assesses NanoHost-first versus App-first transitional compatibility and isolates Worker work during the mixed interval. The external replacement helper in `scripts/host-worker-update/` enforces canonical Linux systemd posture (verified manager search path, no foreign drop-in overrides, pending jobs, or external triggers, a durable attempted-start marker before publishing the volatile `/run` permit consumed before `exec`, and temporary `Restart=no` until the same ready incarnation is measured and stock supervision is restored with a fresh native effective-unit baseline, without repeating an unknown start).
- **Failed-state retirement and decommission**: after a bounded startup failure, an operator with recovery authorization may stop activation, prove the prior effect domain empty, and retire both complete private epoch roots and the unresolved timestamp marker outside their live names while preserving Image Store, Worker volumes, scan store, forensic evidence, identity, and credentials; old volume attachment hints release only after the fresh startup barrier proves all prior writers absent. NanoHost decommission fences the authoritative connection, revokes all Tokens for the configured identity, stops admission, finishes or terminates work under operator lifecycle, invalidates and removes the complete supervised group, and removes raw slot files, Image Store content/index, and forensic reports/notes (while Worker volumes require separate purge authority and Core retains redacted history); later re-enrollment of the exact retained identity/deployment pair issues a fresh first Token and requires all ordinary readiness gates.

A Host refused for a release mismatch must obtain a compatible payload through authorized installed-release replacement before epoch renewal. A refused peer grants no teardown authority. If authorized replacement is unavailable or the mismatch persists, stop retries and show a maintenance hold under [Fault Tolerance](../core/fault-tolerance.md#exit-of-every-hold).

## Failure Scope And Recovery

### Core-Outage Restart Backoff

NanoHost uses one stock service unit with defaults `RestartSec=5s`, `RestartSteps=5`, and `RestartMaxDelaySec=5min`. On systemd 254 or later, stock systemd grows the restart delay geometrically up to the 5-minute cap; older supported managers ignore those two directives and retain the existing 5-second restart behavior as a documented degradation, with no version probing, alternate unit selection, or fixed 5-minute fallback. `RestartPreventExitStatus=78` preserves non-restartable exit when credentials are unavailable or admission returns HTTP `401`, keeping service-cgroup stop ordering, whole-Epoch fencing, and the `30 s` stop bound. A delayed restart proves neither cleanup nor a Turn outcome, adds no custom retry controller, timer file, or durable backoff counter, and continues automatic recoverable failures at the cap. Outside an explicit service-manager stop or prevented credential exit, the service manager terminates the complete failure group after NanoHost exit or kill and starts a fresh generation only after the complete previous group is observed gone ([decision](../decisions/20261002-nanohost_automatic_restart.md)); first start after installation remains an explicit operator action.

- **Host infrastructure failure.** NanoHost is the sole caller of its runtime and answers for its own accepted local operations. A failure of the epoch's own effect infrastructure or containment invalidates the complete supervised epoch. In particular, loss of Host containment calls for immediate invalidation. Failed Worker stop and shim loss use the Sandbox incarnation's outside stop unit. Settling an original operation and proving its incarnation absent are separate obligations.
- **Fresh-empty readiness and carrier cleanup.** Fresh-empty readiness proves the predecessor epoch's effect domain ended and the new one is empty. Volumes remain retained. NanoCore retains the original epoch and evidence for claims settled by that proof. A successor connection fences the predecessor carrier before carrying routes, and carrier closure alone supplies no physical release.
- **Core restart and short network outage.** A healthy Host epoch and Sandbox can continue through Core restart or a temporary outage. Reconnect the same surviving shim and Worker only under exact authenticated lineage, sequence and unexpired authority. When a Host restarts, its fresh epoch proves predecessor absence before admitting capacity. Core settles affected work independently and keeps the original unknown outcomes when evidence is missing.
- **Unknown Sandbox create or delete.** Follow the provider absence rule. Where qualified, repeat delete of the exact incarnation and observe within the original deadline. A proved local absence leaves unrelated Sandboxes in place. Escalate unresolved operations to the Host epoch at the original deadline. Keep the original claim and receipt obligations.

- **Summary of failure boundaries across local and session surfaces**: local preparation-image persistence failure returns empty `503` and retries identical result delivery every `1 s` on the same connection without interrupting resident Workers or replaying commands ([NanoHost Transport](20261116-nanohost_transport.md)); an authoritative successor with no eligible retained mutating result leaves the original effect `unknown` and holds its claim under the provider absence rule; a later qualified exact Worker stop can preserve siblings, while an unproved stop uses Sandbox recycle; failed off-peak freshness rebuild leaves the old or partial Sandbox non-admitting with zero advertised capacity; an unconfigured or external-domain container backend fails before readiness; NanoHost Token slot installation, rotation, abort, or clear does not disturb a live Epoch (re-reading slots only on the next connection attempt); and reaching the produced-fact buffer size (`8 MiB`) or age bound fails affected records truthfully without dropping, summarizing, or reordering.

### Epoch Invalidation Report

The Epoch Invalidation Report is NanoHost-private, non-product, non-authorizing forensic evidence exported to an append-only host location owned by the NanoHost service account before fail-stop termination; it is never a product `EvidenceBundle` ([Audit, Usage, And Evidence Records](20260703-audit_usage_evidence_records.md)), Core protocol field, durable operation journal, recovery/adoption/settlement input, or scheduling/readiness input (Audit receives only a redacted reference).
- **NanoHost-initiated versus NanoHost-absent triggers**: when NanoHost is alive and invalidates an epoch, it uses one of the nine closed triggers — `uncertain-create`, `uncertain-delete`, `member-exit`, `member-identity-change`, `member-local-restart`, `containment-loss`, `epoch-creation-failure`, `operator-action`, or `terminal-session-failure` (used when closed outer-session failure rules require terminal exit of a ready Epoch and no more specific trigger applies, preserving the first unresolved fence timestamp) — and exports one report before group termination and process exit. When NanoHost is already absent (`nanohost-crash`, `nanohost-killed`, `nanohost-identity-loss`, `execution-server-restart`, or `host-loss`), no report is synthesized; instead, the next epoch's recovery records one bounded **prior-epoch disposition note** (`nanohost-absent`, prior epoch identity/generation if recoverable, observed residual processes/roots/networks/sockets/sandboxes, and fencing outcome) in the same location without delaying or weakening the fence.
- **Redacted contents and bounds**: a report contains only epoch identity/generation, creation and invalidation timestamps, configured NanoHost identity id, trigger, uncertain operation kind/lineage/loss point/elapsed time, effect-capable member inventory with PIDs/resolved binary identities/cgroup/observed exit code, signal, or task-finished reason (or unavailable proof, never unverified exit codes or raw exception text), configured backend identity/version and imported image digests, readiness proof results, current connection generation/fence/bridge state, and a bounded redacted tail of member diagnostics. It MUST NOT contain raw or hashed NanoHost Tokens, sink contents, Gateway/backend/provider/Vault credentials, TLS private material, prompts, transcripts, or Workspace/Artifact bytes. Each report or note is bounded to at most `8 MiB` and `2 s` of export time (truncated and marked incomplete if reached, never delaying the fence), and at most the `20` most recent reports or notes are retained before pruning the oldest.

## Acceptance

### Epoch Rebuild Cost Budget

| Budget | V1 target | Hard bound |
| --- | --- | --- |
| Fence proved to readiness advertised, total, including an empty Image Store | at most `90 s` | at most `300 s`; report a violation, then permit a fresh bounded rebuild at the next proved process start |
| Fresh roots, backend start, Gateway health, and all remaining readiness proofs, inside the total above | at most `30 s` | at most `120 s` |
| Point-of-use cold image load from the store, outside readiness | at most `15 s` | one absolute `300 s` bound, capped by any earlier caller deadline, then fail the dependent operation |
| Bounded image metadata commands, including post-load manifest inspection, outside readiness | outside readiness | at most `45 s` per command, capped by any earlier caller deadline |
| Registry retrieval into the store, off the readiness path | not budgeted for readiness | at most `15 min` per image, then fail the attempt |
| Authorized build into the store, off the readiness path | not budgeted for readiness | at most `30 min`, at most `20 GiB` OCI output, and at most `128` manifest layers, then fail the build |

The shared-epoch premise is falsified if, measured over at least `200` completed AgentSessions on the declared topology, either the uncertain-outcome rate exceeds `1` per `100` completed AgentSessions or the observed rebuild time exceeds the `300 s` hard bound; sustained violation reopens the epoch-granularity decision rather than returning silently to per-AgentSession runtimes or grace-based cleanup.

- **Service backoff, readiness gates, and Host epoch identity**: verify the single bundled systemd unit, modern stepped restart backoff (`RestartSec=5s`, `RestartSteps=5`, `RestartMaxDelaySec=5min`), older-manager 5-second degradation (tolerating only exact stock ignored-key warnings for those two directives in `[Service]`), prevented exit `78`, and stock systemd counter resets (requiring restored Core connectivity and an authenticated ready Host for deliberate operator reset). Verify all readiness preconditions (current identity and authoritative session, active transport Token, exact qualified Rust/SDK/Gateway/Supervisor identities, foreground cgroup membership, fresh private network/mount namespaces and DNS, single declared host-local backend, healthy loopback Gateway, empty container/Sandbox inventory, private external Image Store with no Worker image preload, prior-epoch fence, and `EpochCoordinator::start` fresh-slot proof) and the authenticated `nanohost.runtime-target` readiness observation (`identityId` and `deploymentId` match, `predecessorFenced`, `ready`, and `freshEmpty` all `true`, and post-start current generation). Verify Host epoch identity continuity across same-Epoch reconnect versus different-Epoch retirement and storage reattachment, pre-effect backend anchor cleanup without a Sandbox, and original-volume readback.
- **Incarnation placement and persistence.** Verify that a repeated keep-present order converges on the named incarnation with one shim start and that equal compatible settings do not alias different incarnations. Verify original Volume bytes across deletion and cold wake, and placement refusal while the predecessor claim remains unknown. Race duplicate admissions and prove one exclusive address in the original provider namespace. Withhold a Create reply and verify reconciliation uses the original mapping and scope across reopen. Exercise Delete during an accepted Create and show that the acknowledgement and inventory alone leave the claim held. Verify fenced fresh-empty readiness before release on the renewal path.
- **Image Store, retained-parent build, distribution, replacement, and live inspection**: verify no-readiness Worker image preload, bounded-memory streaming archive verification/admission and rewound-descriptor backend import (exercising a layer larger than buffering limits so memory stays independent of archive size), retained-parent Buildx builds under strict policy in a fresh backend with registries unavailable (covering alias reuse, conflicting alias, conflicting archive annotation, wrong resolved checksum, broader-rule bypass, duplicate references, bounded import timeout, Epoch recreation, and manifest-versus-configuration inspection), and strict `build-context://empty/v1` + inline Dockerfile (`1..268,435,456` bytes) + `layerLimit` (`1..128`) + `{docker.io:443, ghcr.io:443}` / AEP `{host, port}` egress enforcement before any `RUN` instruction. Verify byte-reproducible `linux/amd64` and `linux/arm64` archives, `nanohost --version` before effects, verifier rejection of corruption/mismatch/conflict/staging escape, isolated fixed-path `--check-host` and all four `--check`/install dispositions, stopped Installed Release Replacement across payload subsets with complete cgroup fencing, persistent inhibition, exact byte recovery, and forward/reset compatibility, and `nanohost inspect` positive and negative cases (unauthorized peer, malformed request, wrong nonce, inaccessible files, live-image versus pathname replacement, process exit/replacement, unit change, and same-Epoch reconnect race).
- **Required fault scenarios and blocking preconditions**:
  1. **NanoCore restart during active work**: start a real AgentSession, observe a post-launch durable worker sequence, restart only NanoCore while NanoHost, the Runtime Epoch, Sandbox, Integration, and worker continue, establish a fenced successor transport session, and complete through one accepted `final_status` with exact attempt/AgentSession/backend-session/package/process-key/sequence continuity and zero duplicate Sandbox creates, launches, output publications, inference/capability replays, or capacity claims.
  2. **NanoHost `SIGKILL` during blocked Sandbox create**: hold an accepted `sandbox.create` below the NanoHost operation boundary (observed via the value-free pre-dispatch journal record carrying only the closed operation name), deliver `SIGKILL` to NanoHost without manual cleanup, prove the OS supervisor terminates the Gateway, backend members, Sandboxes, cgroups, and helpers with no late effect after fault release, and recover through a fresh-empty Epoch before advertising capacity.
  3. **Execution-server restart**: restart the execution server during a live or in-flight operation, prove NanoCore marks affected AgentSessions `interrupted` or `unknown` without inferring cancellation or completion, keep NanoHost non-ready while any old effect or state remains possible, and prove the fresh Gateway and backend healthy and empty before accepting work.
  4. **Effect-capable member failure**: kill the stock Gateway or a configured backend member during an accepted operation without first killing NanoHost, prove the coordinator monitor invalidates and terminates the entire supervised group without member-local restart, interrupt hosted AgentSessions independently with zero usable capacity, and recover only through a fresh empty Epoch that blocks old member identities from re-entering.
  5. **Cutover and blocking preconditions**: NanoHost is the sole selectable runtime path without legacy Cell, SSH lifecycle, Gateway-forward, or direct-endpoint fallback; stock integration qualification ([NanoHost OpenShell Gateway](20261116-nanohost_openshell_gateway.md)), saturating-load transport envelope ([NanoHost Transport](20261116-nanohost_transport.md)), and the rebuild-budget premise are measured blocking preconditions with no alternate authority or open design waivers, and local source/regression evidence does not substitute for fresh exact-candidate live-host qualification.
