# Web Product Surface Projection

# Web Product Surface Projection

This specification owns the Web product projection over NanoCore. Superseded Web slice specs are historical reference. They do not define active requirements.

## Scope

Owns inclusion, the `live`, `workflow`, and `roadmap` dispositions, workflow grouping, the account gate, and the bounded settings projections.

Does not own:
- Operation declarations and the access catalog. [Operation Definition](20261002-operation_definition.md) owns them.
- Release readiness. The owning specification defines the readiness criteria.
- Authentication, membership, and invitations. Identity and the multi-user Workspace own them.
- Conversation-target resolution and submission. [Unified Conversation Composer](20260831-unified_conversation_composer.md) owns them.
- The broader deployment-admin surface. [Deployment administration](https://github.com/lingkaix/openkit/issues/954) tracks it.

Core: [Architecture](../core/architecture.md), [Work Model](../core/work-model.md), [Identity](../core/identity.md), [Policy](../core/policy.md).

## Personal Assistant, Memory And Shared Work

Thread lists, search, notification and Artifact/widget access obey `20260909-thread_visibility_and_sharing.md`, including project-private Assistant/admin Threads and Workspace-shared Task/Goal work. Personal Memory lives under the current User surface, Workspace Knowledge under the selected Workspace, and Server Knowledge under administration. Memory inspection/edit/forget and pending candidates use `20260909-personal_memory_and_knowledge_learning.md`; notebook edit/history/diff/restore and delegated-maintenance outcomes use `20260909-knowledge_notebook_editing.md`, with current disclosure, active-only defaults and explicit retained-history labels; ordinary Workspace navigation never enumerates another user's Memory. A shared snapshot labels its cutoff and subsequent conversation audience. Management conversation and validated forms invoke the same configuration commands and exact preview/confirmation contract owned by the Assistant spec.

## Decision

Web is the product projection for every currently supported canonical-user or Workspace-authorized NanoCore operation. The [operation definitions](20261002-operation_definition.md) supply operation identity, scope and credential admission. Their access catalog is a projection, alongside separately owned transport entries; page names and mockups are not the inventory authority. The included universe is every `PUBLIC_OPERATION_ACCESS` entry whose scope is `user` or `workspace`, excluding Gateway-actor authentication and the Worker-only operation. A recount is not a permanent limit.

Workspace Knowledge Manager answers show the returned citation titles and excerpts. A citation links to current full content only when its qualified owner and page identity match an available current page; a missing or foreign reference never aliases a local page. The link labels current content because it may differ from the cited answer. The direct Add knowledge form offers explicit registered-Source selection and submits that exact Source identity and captured digest as a page source reference. Equal content alone creates no relationship, and switching Workspaces never carries a selected Source into another Workspace's command.

One product workflow MAY project several operations. Web MUST consume existing Core and App API contracts through `@openkit/core-client` and MUST NOT invent runtime, Policy, Knowledge, Workspace Sync, portability, scheduling, or recovery semantics.

The five `automation.list`, `automation.create`, `automation.update`, `automation.delete`, and `automation.history` operations project the durable fixed-interval and monthly UTC recurring owner through the live selected-Workspace Automations surface. `knowledge.proposal.draft` and `knowledge.proposal.reverse` also remain unpublished under [Knowledge Manager drafting and generated-Knowledge lineage](https://github.com/lingkaix/openkit/issues/954) because ordinary-user reads cannot recover their exact candidate, accepted-review, and applied-page lineage after refresh or restart. The bounded Configuration editor implements only the runtime-config slice of [deployment administration](https://github.com/lingkaix/openkit/issues/954); the issue tracks the remaining deployment administration surfaces.

`workspace.archive-download` belongs to the existing Web export workflow under [Streaming Archives Use Web And Administrator CLI](../decisions/20261003-streaming_archives_use_web_and_admin_cli.md). The later [snapshot decision](../decisions/20261027-online_workspace_snapshots_and_recovery.md) removes ordinary portable import and selects backup, restore and MOVE. It does not retire analytical export or authorize future Web import. The initial [Native Knowledge package transport](20261018-file_storage_and_knowledge_packages.md#export-and-import) supplies Workspace package interchange without a Web workflow. The [Workspace backup and export specification](20260704-workspace_backup_export_import.md) defines the supported portability operations. `workspace.delete` and `workspace.deleted-recover` remain unpublished under [multi-user Web membership](https://github.com/lingkaix/openkit/issues/160) because that owner defers those controls to its remaining Web projection. These roadmap dispositions add no UI feature and do not reopen the completed non-Web capability slices.

The first shared-Thread resource Policy slice exposes `workspace.resource-access-request` and `workspace.resource-access-apply` through the Core Client, CLI and MCP. Their ordinary-user Web request and distinct confirmation controls remain unpublished under [exact Workspace resource access](https://github.com/lingkaix/openkit/issues/954). The existing Pending Request and Workspace configuration owners retain authority for the supported entry points.

## Contract / Expected Behavior

### Inclusion and exclusions

An ordinary-user Web operation is included when it is a `PUBLIC_OPERATION_ACCESS` key whose `scope` is `user` or `workspace` and whose `authentication` is not `gateway-actor`, and whose operation definition does not admit only `worker-package` credentials. The count follows the current catalog. Inventory derivation MUST follow the operation definitions and their access projection, including explicitly owned transport entries, together with generated App API OpenAPI and `@openkit/core-client`. It MUST NOT use screen titles as the source list. `PUBLIC_OPERATION_ACCESS` is the current access projection, not a separate definition owner.

The following are excluded from ordinary-user Web and MUST NOT appear on a published ordinary-user route:

- Server-scoped catalog operations, including deployment-admin and bootstrap-secret authentication: every access-projection entry whose scope is server. [Deployment administration](https://github.com/lingkaix/openkit/issues/954) tracks their future separate admin surface.
- Gateway-actor operations `POST /v1/chat/completions` and `POST /v1/responses`.
- Worker-only catalog operations whose definitions admit only `worker-package` credentials, currently `automation.event-admit`, and Worker-private routes outside the public catalog, including `/api/worker-control/*`.

Better Auth sign-in, sign-up, and sign-out plus `GET /api/meta` are already-live admission and connection plumbing. They remain acceptance prerequisites and MAY be called from ordinary Web, but they are not catalog operations and do not receive `live` / `workflow` / `roadmap` dispositions.

### Authority and projection boundary

This specification owns Web inclusion, disposition vocabulary, workflow grouping, and ordinary-user publication rules. NanoCore owns the catalog and route behavior. `@openkit/core-client` owns typed client methods. Owning Core documents and specifications own product semantics. GitHub issues track the work required for unpublished outcomes. Web routes, local component state, UI-only filters, and browser storage remain presentation projections, not canonical product records. Web does not present backend-private runtime state, raw secrets, raw OpenShell internals, or hidden agent-private task graphs as ordinary product concepts.

Live and workflow dispositions MUST consume the composed Core Client. A missing typed client method is a Core Client gap that blocks `live` or `workflow` until that package owns the method. Web MUST NOT bypass the composed client with a parallel HTTP helper.

The shell-level Search capability is opened from an accessible icon-only command at the right of the brand row and MUST NOT reserve a persistent strip above every routed main view. The selected Workspace switcher is always visible immediately below the brand row, shows the authoritative selected Workspace name, and owns the UI-only selection that rebinds every selected-Workspace query. Its choices are the Workspaces the signed-in user belongs to through an active membership. A Workspace admitted only because the caller holds current administrator eligibility is omitted from that switcher.

Administration lists those other Workspaces and opens one into the same selected-Workspace state. Chat starter, Thread, and every other routed main view MUST NOT render a Workspace selector. The canonical Chat Thread route is `/chat/:workspaceId/:threadId`; link producers and route consumers use that exact lineage and MUST NOT encode the Workspace as a query parameter or preserve a compatibility route.

The Agents surface is a selected-Workspace projection. It MUST read the selected Workspace's Agent resource set and bind health operations to that same Workspace; it MUST NOT display the deduplicated cross-Workspace Agent catalog as though every listed Agent belonged to the current Workspace.

The same surface separately presents current Workers through one NanoCore-owned selected-Workspace read projection shared by the composed Core Client and remote MCP. Configured Agent supply and observed Worker state MUST have distinct labels. A Worker row represents product-safe availability for the current AgentSession of an authorized visible Thread, not a new durable Worker entity or an AgentSession selection surface. Internal roles, terminal predecessors, hidden Threads and catalog-only supply do not become Worker rows. The row is keyed by Thread, so concurrent Workers using one Agent remain distinct and a current Worker remains visible after its Agent leaves the configured catalog; AgentSession, native conversation, Sandbox and credential identifiers MUST NOT appear in ordinary output. Core retains all lifecycle authority; reading or refreshing this projection creates, resumes, retries, replaces or terminates no work.

Current work affiliation comes only from an exact matching uncleared Worker checkpoint and its existing Turn, Thread and AgentSession lineage. A Goal-dispatched Task is an ordinary Task. `goalId` may name the Goal that authorized it and may be absent. `taskId` stays absent because a Task has no separate task record. Current affiliation MUST NOT be inferred from the latest Goal, a navigation category, or a later projection. A checkpoint with a null recorded worker session is pre-launch and supplies no current assignment; a non-null session must equal the row's current AgentSession. No current checkpoint means no recorded current assignment. Conflicting or incomplete lineage is reported as unavailable, not repaired or guessed. A row may link to its authorized Thread through the existing conversation route; this navigation does not assert that an unsupported runtime can accept input while busy. Runtime status is labeled as the last recorded state with its record update timestamp, not fresh process-liveness proof. Fetch failures retain an explicit unavailable or stale indication and never become an empty successful inventory.

Model and configuration details derive from existing records, not the configured catalog entry. The exact current package snapshot, after matching its Workspace, Thread and AgentSession scope, supplies a separately labeled preferred logical model and package-selected MCP policy. The read requires existing `workspace.read` access, and last-used usage fields additionally retain existing `audit.read` authorization; an unauthorized viewer receives an explicit restricted indication without those values. The most recent `category=llm` usage attributed to the row's current AgentSession, joined by capability-call id to a `family=llm` call and its exact existing Turn with matching Workspace, Thread and current AgentSession lineage, supplies a separately labeled last-used logical model and timestamp even when that Worker is now idle; this historical usage does not imply a current assignment. Usage from a retired predecessor on the same Thread is excluded. A difference between package preference and last-used model is not itself a configuration-drift signal. Mismatched or absent attribution stays unavailable and provider references are not native model identities. Progressive disclosure uses an explicit field allowlist: package-selected Workspace MCP server ids with allowed/denied/approval-required tool names, and filesystem/network/process defaults, enforcement labels and rule counts. Unknown keys and raw values are never copied through. These are the Workspace-owned servers selected by this package, not a new editable Agent policy tier. It MUST NOT expose raw policy rules, local paths, commands, environment values, endpoints, credentials or native runtime metadata. These are package intent and recorded usage, not proof of actual runtime loading or permission to change a running Worker. Replacement, restart or configuration change is reflected only through current authoritative records; this read projection has no retry, cache-repair or durable migration lifecycle of its own.

Acceptance requires configured supply without a current Worker to remain catalog-only; two Workers of one Agent to remain distinct; Workers absent from the latest catalog to remain visible; null-session pre-launch checkpoints to supply no assignment; idle Workers to have no current assignment without historical backfill; last-used usage to retain the audit access boundary; a Goal-dispatched Task attributed only by an optional Goal id, not by a separate task record or a later Goal; private Thread omission before dependent data reads, producing viewer-relative counts rather than a capacity inventory; distinct package preference and last-used model values; explicit missing/conflicting evidence; no hidden runtime identity or secret-bearing configuration in the payload; and matching Web/Skill results from the same typed read. Model switching and busy Worker input retain their separately owned command and runtime contracts.

Archived threads are a selected-Workspace projection reached from the compact sidebar shortcut grid. The active **Conversations** sidebar list excludes `status=archived`; the Archived threads surface lists only archived rows and restores a row through the existing authoritative Thread update with `status=active` before refreshing both projections. `ThreadSchema` does not own a Chat or Task discriminator and Task Mode deliberately has no separate durable Task record, so Web MUST NOT infer a Thread kind from its route, Turns, or transient browser state. The selected-Workspace **Assistant** action opens its backend-owned private Timeline as defined under Workflow-level projection; a Task-mode route may enter Task Mode on the same Thread without reclassifying it. Web adds no separate archive store or recovery API.

NanoCore's selected-Workspace `conversation.navigation` operation projection supplies visible active Threads, current/latest activity (`chat`, `task`, `goal`, or `unknown`), viewer-relative state (`needs-you`, `working`, or `idle`), and `lastActivityAt`. It is derived from existing records, not a durable Thread kind. Active Goal context takes precedence, then latest Goal context when newer than the selected Turn; otherwise the current or latest Turn's configured Worker assignment/session or established internal Chat Agent assignment identifies activity. The Chat producer records quick-chat for Assistant commands and knowledge-manager for direct Knowledge Manager commands in the existing Turn.agentId field. Missing or unrecognized assignments remain unknown, including historical unassigned Chat Turns; opaque Item IDs and expiring command receipts do not determine activity. Web consumes this projection without classification heuristics.

`needs-you` takes precedence over `working` and requires an exact viewer-eligible Turn approval/question or existing actionable Goal plan/result review. `working` requires a pending/running Turn or running Goal. A completed Turn is not an unread reply. Working and actionable rows sort before idle rows, then by newest actual Item/Turn/Goal activity and stable Thread id. Thread creation is the baseline activity for an empty conversation; later name or archive metadata changes do not count as conversation activity.

Navigation `unreadCount` is an exact nonnegative integer or null. Exactness requires exhaustive current message selection within 64 candidates and 64 KiB of combined canonical body and receipt bytes. A metadata-only receipt byte-size preflight and its decode share one User snapshot; selected message heads and canonical bodies share one Workspace snapshot. Candidate or byte overflow yields null, never a partial count, empty-set substitute or full-history fallback. Only exact zero permits “All replies read”; null has no count claim and keeps Mark read available. Mark read acknowledgement cannot certify a later navigation zero. Indexed receipt rows and new retained fields are not introduced.

The projection creates, updates, and removes no durable record; each read is recomputed from authorized current owners, including after restart. Missing activity evidence is explicit unknown, and archived or invisible Threads are omitted. A failed refresh must be exposed as stale or unavailable in Web and must not manufacture an idle state. Retry refetches the same read model. Foreground refresh keeps other conversations current without starting work. While this browser is awaiting its own conversation submission response, the existing mutation state may temporarily promote that exact Workspace/Thread row and show a blue Waiting for response indicator; this is explicitly client request progress, ends when the request settles, and neither claims an accepted Turn nor persists a server lifecycle state. Goal child navigation follows the Goal Navigation Groups contract below; the activity read does not infer a hierarchy. Read receipts follow the User-owned contract below. Acceptance requires one mixed Workspace to preserve visibility, exact gate authority, unknown unassigned work, and newest-reply ordering on an older Thread.


The Thread title bar prioritizes the Thread name and future compact status. Rename and Archive are accessible icon-only actions immediately beside the name; the accessible icon-only **Side panel** toggle is aligned to the far right. The panel currently mirrors the Thread's Artifact and file-change index and MUST NOT be labeled or described as the global Artifact inventory.

### Goal Navigation Groups

The accepted D03 choice groups a visible Coordinator Thread, its actual work-intent cards and their linked Task Threads. Goal records, card identities and GoalTaskLink citations remain the unique authority for membership. The Web joins the existing Goal view and current visible Thread list; names, creation order and activity labels never establish a parent or card association. It adds no work entity, execution lifecycle or durable grouping record.

Every retained link to a visible Task keeps all of that Task's recorded Turn attempts, including completed, failed, interrupted and cancelled attempts. A linked archived Thread remains available as archived history; archive is not deletion or audience revocation. An explicit missing Task remains unresolved and offers no action to create a replacement. Unrelated Threads remain in ordinary conversation navigation. A linked Task opens its existing Task Thread route; grouping starts no work and resolves no request.

Group expansion is local presentation state and resets when its Workspace changes. Source reads and expansion never advance read receipts. Current Workspace and Thread admission stay with the existing operations. A missing Goal, stale source or failed dependency has an unavailable state and a read retry; cached child facts are hidden after a failed read. No client reconstruction or mutation retry is added. Restart rereads the existing owners. Acceptance shows real card associations, multiple retained attempts, archived and missing history, collapse and expansion, unrelated work, and failed reads without stale child facts.

### User-owned Read Receipts

The accepted D02 choice persists one logical read receipt per authenticated User, Workspace and Thread. It records the identities of completed message bodies actually displayed to that User, and every current eligible message when the User explicitly selects Mark read. It does not infer reading from a Turn completing, prefetch, navigation, a cached response, hidden rendering, a timestamp or identifier order. A visible message body in a foreground document is sufficient display; this is a display receipt, not proof of human attention. Completed non-empty assistant messages and completed messages from another actor are eligible; the viewer's own User messages, in-progress messages and non-message Items do not create unread replies.

The canonical receipt is User-owned SQLite metadata in the existing user database, keyed by Workspace and Thread. Its message identity set grows by union, so different devices, duplicate updates and delayed updates cannot make a read message unread or mark an unobserved earlier message read. This reuses canonical Item identities and creates no Thread ordinal, Item revision ledger, work entity or second message store. An absent receipt means no eligible message is recorded read. Reads never advance the receipt. Navigation derives exact-or-null unread counts from current visible eligible messages and the current User's receipt under its fixed proof allowance above; a failed read is unavailable, never a fabricated zero.

The server derives the User from the authenticated actor and requires current Workspace and exact Thread access before reading or advancing a receipt. A caller cannot select another User. A read requires a nonempty selection of 1 to 200 Item identities before deduplication; omitted or empty selections are refused. Its explicit window scope returns only selected currently eligible read/unread identities, deduplicated in first-request-occurrence order; valid ineligible Items are omitted. Missing or cross-Thread selected sources reject the entire read. Selected canonical sources and current admission are checked again after native User opening. No complete-Thread read or Thread-scope read response exists. Callers with more loaded identities partition them into bounded windows; their combined knowledge covers only those selected identities, never unrelated history.

Display updates name at most 200 completed eligible Items in that exact Thread; an unknown, missing, cross-Thread or ineligible target rejects the whole update and leaves the receipt unchanged. Eligibility and current authority are rechecked after native opening and immediately before publication, without traversing unrelated Item history. Concurrent updates still union identities in the existing User database transaction. Only after its FULL acknowledgement does the server return the bounded deduplicated selected identities, not the stored union. Empty display selections never publish membership. Explicit bulk Mark read selects current eligible Items on the server, retains current revalidation and cooperative yields, and returns only the count of acknowledged selected identities, including already-recorded identities. This count is not a newly-read count or a claim that later-arriving messages are read. A failed or unknown acknowledgement reports an error, never fabricated success; retrying the same display is idempotent and does not start a Turn, answer a question or resolve a gate. Restart retains the same metadata. Unknown additive database columns do not change its meaning; invalid required receipt content fails with an ordinary storage error. The retained union and its internal native reply remain unchanged; bounded window responses and selected Item reads do not certify constant-time retained-membership I/O or the separate navigation path.

A receipt has no independent termination or recovery command. Deleted or inaccessible Workspaces and Threads are unavailable under their current owners, and their retained User metadata grants no access or resurrection. User deletion removes its User-owned state. Whole Data Root backup retains that state under existing ownership; portable Workspace export and import do not transfer another User's read state or remint it into a new Workspace. No conversion reader or predecessor migration is introduced. Acceptance proves actual display and explicit read, prefetch without advancement, cross-device union and restart, current actor and audience isolation, and truthful failed reads and writes.

### Recorded Interruption Identity

Usage and audit projects the existing AuditEvent actor and exact Workspace/Thread/Turn/request lineage alongside each event's action, summary, outcome and recorded time. A recorded `turn.interrupt` identifies the admitted requester of an accepted Stop command; it does not substitute for terminal status or prove completed backend cleanup. The visible actor uses its recorded kind and stable identity, with an explicit Actor not recorded label when absent. No identity is inferred from triggerActor, the current viewer, permission admission or optional telemetry. An exact Thread link uses only the event's currently authorized Workspace and Thread coordinates; no identifier is reformatted or guessed. The existing Audit owner defines producer, replay, missing-history and audience semantics. Failed reads retain the existing unavailable and retry behavior. Acceptance preserves a different initiator and interrupter, exact lineage, absent historical identity, and current audience filtering.

### Workspace Tool Rules And Recorded Skill Lineage

The selected-Workspace Catalog edits an existing local MCP binding's allowed, approval-required and denied tool names through `catalog.mcp-binding`, using the displayed catalog and binding revisions. Saving preserves enablement, schema policy, timeout and omitted credential bindings. Shared Server supply remains separately administered. A deliberate save is the human configuration decision; it creates no proposal queue and grants no captured invocation approval. Pending, disconnected or failed current reads disable writes. A failed or uncertain save preserves the draft and requires explicit current-state inspection before another save; no automatic mutation retry occurs. A successful refresh retains unsaved rule text and shows the freshly read binding lists for comparison. Failed enablement has a read-only binding refresh; another effect is not required to recover editing.

Diagnostics lazily reads the selected Workspace's existing package snapshot and shows its exact Thread, Turn and recorded Skill IDs, content digests and selection sources. It uses only these allowlisted public fields, never the raw package, private paths or current catalog values. Missing Skill supply is unavailable; an empty recorded array means no Skills recorded; an absent or unknown selection source is not recorded. The existing snapshot owner's authorization, retention and failure semantics apply. These are recorded package selections, not proof of native consumption or current pins. Selection changes no catalog, Turn or package state. Acceptance proves exact rule submission with unchanged binding properties and a lazy snapshot read that preserves lineage while excluding other package content.

### Workflow-level projection

Web MUST project included operations through product workflows such as account and sharing, conversation, Goal, Material, Action Center, Knowledge, Workspace Sync review-to-apply, portability, agents and recovery, and Workspace-authorized settings.

A workflow MAY satisfy several operations when each operation's user-visible behavior, authoritative state, or named supporting read is reachable through that workflow. The coverage check records that mapping. Web MUST NOT add a generic operation runner, an operation-id index as a product destination, or a dedicated published page whose only purpose is to expose one catalog key.

Ordinary Assistant navigation opens the backend-owned private User/Workspace Timeline through thread.create and follows the exact returned Thread identity. Opening creates no Turn and submits no message. It does not offer another private conversation, choose a Timeline by date or identifier, rename an existing Timeline, or implicitly restore an archived one. An archived result opens its retained history with the existing archive status and explicit restoration path. Pending or failed opening is visible, with explicit retry of the same frozen request. A result for a departed selected Workspace must not redirect the current Workspace. This binding ships only with the accepted private Timeline backend.

The Members navigation entry uses the existing selected-project-Workspace Account surface at /settings/account. It creates no member route or membership authority. Personal Workspace selection offers no member-management entry. Current account and membership reads continue to govern visible facts and effects.

AgentSession is a hidden runtime-continuity item and MUST NOT appear in Web or ordinary App API as a picker, creation or restart action, navigation object, identifier, history, active-session object, or native handle.

### Disposition lifecycle

Every included operation MUST have exactly one of the following dispositions:

- `live`: a published Tier-A product control or exact Core Client call on a reachable ordinary-user surface.
- `workflow`: no dedicated control, but a named published workflow already projects the operation's user-visible behavior or authoritative state.
- `roadmap`: the endpoint is callable and in-scope, but the owning capability is not release-ready as a truthful product feature. The gap stays unpublished and MUST link to an open issue that tracks the exact gap.

The disposition guard is inventory and admission evidence. It MUST prove inclusion of that current set, uniqueness of each key's disposition, closed disposition shape, and that a `live` or `workflow` disposition names a surface that is currently Tier A. It cannot by itself detect a false workflow behavior claim.

Creation: when the included catalog gains a key, the disposition guard MUST fail until exactly one disposition is recorded. Update: shipping a truthful published projection moves `roadmap` to `live` or `workflow`. Termination: when a key leaves the included set, its disposition MUST be removed; leftover dispositions MUST fail the guard. Retry of a Core operation follows that operation's existing Core and client error contract. Dispositions are repository artifacts and have no session retry of their own. Recovery of a false `live` or `workflow` behavior claim is not a guard verdict: focused UI tests plus independent review of the actual diff decide whether the named workflow is reachable and truthful, and a false claim MUST NOT become silent repair or a browser-owned success.

Conflict: two dispositions for one included key MUST fail the guard. Missing: an included key with no disposition MUST fail the guard. Stale admission: a `live` or `workflow` disposition whose named surface is not currently Tier A MUST fail the guard. Restart: UI restart MUST reread Core truth and MUST NOT reconstruct workflow state from browser storage. Dependency failure: a not-release-ready owning capability MUST use `roadmap` rather than a fake working UI; Knowledge proposal drafting and reversal use [Knowledge Manager drafting and generated-Knowledge lineage](https://github.com/lingkaix/openkit/issues/954), and deferred Workspace deletion and recovery controls use [multi-user Web membership](https://github.com/lingkaix/openkit/issues/160), for this reason. An unresolved delivery gap requires an open issue.

A `roadmap` disposition MUST link to the open GitHub issue for that operation's remaining Web work.

The Knowledge package owner excludes an initial Web workflow. Channels projects current-user Discord binding and notification observations through status, pair, `notification.list`, and `notification.send`. `channel.discord.revoke` is retired. A typed authorization denial remains visible with an explicit retry and MUST NOT render a Token-entry fallback.

### Recurring Workflow Projection

The Automations surface uses the [Recurring Trigger contract](20260711-scheduler_recurring_event_triggers.md). The surface configures either a fixed interval or monthly UTC cadence on an existing target Thread. Monthly controls select a day from 1 through 28 and an explicit UTC hour, minute and second. The surface supports create/edit/pause/resume/delete with current authority and expected revision, and reads persisted definition status, trigger history, and linked scheduler/Turn status separately after refresh or restart. Accepted-but-queued, admission failure, expiry and later execution failure must remain distinguishable. Admission history shows the typed failure code, including `queue_backlog_full`, so a busy schedule is distinguishable from denied authority or invalid input. Exact expired ranges display their fixed interval or monthly UTC cadence, covered time span and count without unbounded expansion. The UI cannot replay a source/imported occurrence or retry execution by changing its trigger state. The live Automations surface projects these durable controls through the five definition-derived automation operations and selected-Workspace navigation. Create always saves paused. Resume requires an explicit UTC nominal instant, and edits remain paused-only. Deletion confirms that accepted work continues and retained history remains. Reads use current `workspace.read`; mutations use current `workspace.configure`, without creator-private privilege. The immutable responsible user remains visible. Accepted occurrences with a missing or contradictory Turn show their read-only `recovery_required` publication cause; a still-queued damaged admission offers only the existing scheduler cancellation, with pending and unknown outcomes and an explicit history refresh. This action releases the existing waiting slot and never repairs, resumes or re-admits the damaged occurrence. Turn links require both an actual retained Turn identity and no publication issue. A `?turnId=` link locates only a matching Turn in the current authorized Thread read; an unknown or unavailable target shows safe unavailable copy. Opening the link does not reconstruct a Turn, repair publication, retry work or invoke a mutation. Deleted definitions remain discoverable as retained history; their rows offer only history and Thread links, without edit, resume, pause or delete actions. Pending actions are protected against duplicate submissions. Workspace switches unmount drafts and action outcomes and separate query keys; a late response cannot populate the new Workspace. Denied reads do not render stale protected rows as an empty success. Unknown writes are not replayed; the user must refresh and inspect. Conflict, loading, empty, safe error, disconnected, pending and refetch states use DESIGN.md §9.12–9.14.

### Deployment Configuration Projection

The published Tier-A **Configuration** screen is a separately authorized deployment-admin workflow inside the Settings shell. It lists the existing runtime-config documents as one relative-path tree, reads one exact JSONC source at a time, preserves comments and formatting while editing, validates the complete draft through `client.operations['runtime.validate']`, and writes the complete source through `client.operations['runtime.file-update']` with the exact last-read revision. A conflict keeps the local draft and requires an explicit reload; Web MUST NOT overwrite, merge, or claim success.

Saving changes only the authored file.
