# Generative UI Interaction

## Owns

This specification owns agent-native declarative presentation and interaction across temporary and reusable surfaces: admission, source binding, action dispatch, persistence, reopen, failure, and observable behavior. It is independent of [Generative Kernel Data And Operations](20260908-generative_kernel_data_operations.md). Kernel-backed UI is one composed acceptance scenario, not the scope of Generative UI.

## Does Not Own

[Web UI Rebuild Stack](20260710-web_ui_rebuild_stack.md) owns React, the official A2UI renderer, Spectrum mapping, the browser isolation host, and dependency choices. [Web Product Surface Projection](20260628-web_product_surface_projection.md) owns publication and supported product surfaces; `DESIGN.md` owns visual composition. Existing owners retain Item history, Artifact content, work execution, Human Attention, Policy, Vault, and business data. This specification does not introduce a frontend app builder, unmediated JavaScript/HTML execution in the host DOM, new work runtime, or independent permission system.

## Summary

Generative UI presents information and available interactions using a host-controlled component catalog. It may display ordinary OpenKit records, external results, task output, or Kernel records. Neither Kernel storage nor a Worker agent is mandatory. An admitted agent may select a registered widget or generate a declaration when its task benefits from presentation; a user may also request one explicitly. NanoCore may deterministically construct a view from a known schema or result. NanoCore admits declarations and binds operations; Web renders them. No extra UI-generation agent is required.

The data source remains authoritative for business facts. A saved presentation owns its declaration and bindings, not the records displayed through those bindings. Headless operations remain usable without a UI, and a useful temporary view need not create durable business data.

## Decision

Use a shared Core admission and action boundary for declarative UI, with optional admitted agent generation or deterministic construction rather than a mandatory UI agent. Adopt standard Apps SDK/MCP tool and UI-resource interface semantics, with A2UI organizing the whole surface, native components by default, and an isolated MCP Apps HTML delegate for specialized Plugin interactions. This is the engineer-selected mixed-rendering scope; exact host conformance still requires the acceptance proof below. Retain business data with its existing owner and add only the saved-definition authority needed for explicit reuse; the initial native contract below fixes concrete persistence and public bindings while deferred profiles remain unavailable.

## Protocol And Version Direction

Start implementation on A2UI protocol v0.9 using the official React renderer and Web Core. Inspect v1.0 candidate changes now and target eventual v1.0 compatibility. Work is not gated on the upstream stable release, its announcement date, or official renderer v1.0 availability. Pin compatible package versions when implementing; package versions are not protocol versions. Do not retain v0.8 or build a speculative multi-version compatibility framework.

The wire content is upstream A2UI messages under the selected protocol and a host-approved catalog, not OpenKit's current recursive `type/props/children` fixture format. OpenKit action authorization and source binding remain outside the renderer's authority. Protocol validation alone never authorizes an operation.

| v1.0 candidate change to account for | OpenKit design consequence |
| --- | --- |
| Bidirectional function calls and correlated responses | Map admitted calls to exact Core operations; the protocol's agent endpoint is logical and does not require an LLM or Worker. No renderer-to-Worker bypass. |
| Catalog function caller/return constraints and user activation | Enforce supported caller, argument/result schema, and activation rules. User activation is not current Policy authorization or a substitute for an owned Approval Gate. |
| Mixed catalogs and explicit catalog identity | Resolve each component/function against host-admitted catalogs; a declaration cannot load code, dependencies, or a new catalog. |
| Host-owned styling and richer validation/accessibility | Keep Spectrum styling and accessibility with Web; reject or safely degrade unsupported composition rather than interpreting arbitrary CSS or code. |
| Initial surface data/components and explicit data-model deletion | Separate UI model deltas from business commands. In particular, a protocol null/delete delta never implicitly deletes a business record or writes a database null. |

Candidate details are provisional upstream facts, not additional OpenKit product authorities. Upgrade the protocol at its boundary with conformance checks when supported. Final v1.0 interoperability is the compatibility target; the current v0.9 implementation can deliver useful work before that upgrade.

## Apps SDK Tool And Widget Interface

Adopt the standard MCP tool/resource concepts used by the [OpenAI Apps SDK UI contract](https://developers.openai.com/plugins/build/chatgpt-ui): named tools with input schemas and structured results, registered URI-addressed UI resources, and a render tool's `_meta.ui.resourceUri` association. Reuse the [A2UI over MCP](https://a2ui.org/guides/a2ui_over_mcp/) resource profile `application/a2ui+json` for A2UI templates and data-model messages; use the MCP Apps HTML profile for delegated resources. Use standard fields where their meaning is the same; do not invent a parallel OpenKit widget-function registry or require ChatGPT-only `window.openai` APIs. The existing Agent Plugin and MCP catalog owns tool/resource distribution, while this specification owns the accepted presentation and action binding.

Separate headless data tools from render tools. Data retrieval, updates, and agent reasoning do not automatically render a widget. A render request selects an admitted reusable resource/version or proposes a new A2UI declaration; dynamic creation uses the same validation as registered content and cannot load new executable components. Structured tool results supply declared source data; optional text remains useful to agents and nonvisual clients. UI-only metadata is neither a secret store nor authorization.

| Standard interaction | OpenKit first projection |
| --- | --- |
| Tool schema and `structuredContent` result | Exact governed command input/output and source provenance; ordinary data calls work headlessly. |
| Render tool `_meta.ui.resourceUri` | An admitted, version-bound A2UI resource or MCP Apps HTML resource, resolved through Core under the current actor and audience. |
| Resource retrieval and tool-result delivery | Existing Core transport supplies the accepted A2UI declaration and validated data to the official renderer. |
| Widget tool invocation | Core resolves the accepted action to its exact tool/command and reauthorizes; no direct browser-to-MCP or renderer-to-Worker bypass. |
| Conversation message or model-context update | Existing user-input/context-selection paths, visibly distinct from executing a data operation; metadata cannot manufacture user authorization. |

Native resources use `application/a2ui+json`; HTML delegates use `text/html;profile=mcp-app`. These are different resource kinds, not interchangeable MIME labels. A2UI templates and their data updates follow the upstream resource/message profile; their actions retain Core admission. The delegate uses the standard MCP Apps host handshake and bridge rather than a new Plugin messaging protocol. Negotiate and advertise only implemented protocol versions and capabilities; unsupported requests return the standard unsupported/error result. A2UI v1.0 and MCP Apps host conformance remain separate dimensions.

Registration controls resource availability; explicit saved-view identity controls reusable presentation lifecycle. A registered template is not a saved instance or a copy of source data. A dynamically produced temporary declaration need not create a globally discoverable widget registration. Reusing an exact registered template requires no model generation; saving a composed instance follows the saved-view contract below.

### PluginWidget Delegate

Use one host catalog component, provisionally `PluginWidget`, for specialized maps, timeline editors, and canvases. Follow the [A2UI MCP Apps integration direction](https://a2ui.org/guides/mcp-apps-in-a2ui/) and [MCP Apps host contract](https://modelcontextprotocol.io/extensions/apps/overview), using the official bridge SDK where suitable. The upstream guide supplies Lit/Angular examples; React integration is work to implement and verify, not an existing OpenKit capability.

The three admissions are distinct:

1. An agent or user publishes/selects a Plugin through the existing catalog owner. Its MCP server exposes UI resources, related tools, schemas, and requested host capabilities. Registration identifies the exact component version, server/resource identity, accepted HTML/assets digest, and declared capability envelope. Remote URI text alone is insufficient immutable identity. Executable dependencies must be bundled in those pinned bytes or fetched with verified immutable digests before admission; allowing a mutable remote script origin does not satisfy version pinning.
2. The agent references that admitted resource in an A2UI declaration with bounded initial data or authorized source references and display parameters. Core validates the exact Plugin/resource revision and action bindings; a declaration cannot inject arbitrary HTML or acquire capabilities by supplying a URL.
3. Web mounts the exact accepted resource in an isolated iframe host and establishes the standard MCP Apps bridge. NanoCore resolves any governed resource read or tool effect under current authority and returns the owned result. Loading a widget grants no direct NanoCore API credentials, Worker channel, or unrestricted MCP forwarding.

Publishing a new executable resource revision to a shared audience is a materially consequential, recoverable commitment under Core Permissions. Before commitment, expose the exact resource/content digest, selected version, requested host/network/tool capabilities, and destination audience as the existing operation preview. Current delegated catalog authority and Policy decide commitment and whether the existing Human Attention owner requires an additional approval. An irreversible, credential-bearing, authorization-changing, externally visible, or cost-material effect retains the stronger distinct confirmation and owning gate required by Permissions. This creates no widget-specific approval record or blanket human review of every render. Loading an already admitted exact revision rechecks current resource identity, audience, and capabilities; it does not by itself require new approval. Later tool calls retain their own effect checks.

The browser host MUST isolate Plugin DOM, scripts, styles, storage, and cookies from OpenKit and other widgets. Use the upstream sandbox-proxy/inner-frame pattern as the initial implementation direction; the untrusted inner frame has no same-origin or top-navigation privilege. Bind the bridge to the exact frame source and current instance/handshake; an opaque origin is not authenticated by an origin string alone. Reject messages from other frames and stale instances, validate schemas and bounded payloads, and dispose the bridge on unload/replacement. Enforce host-approved CSP/resource/network origins and requested browser permissions; declarations request capabilities but cannot grant them. Navigation and external resource access follow host admission, not arbitrary widget URLs. No direct network capability is granted by default; any allowed browser resource loading must name its origins and data-disclosure envelope. Kernel writes and credentialed/external business actions always use the governed server tool path, never browser-held credentials. A CSP origin allowance does not authorize a business effect. Do not copy the sample's optional security-test bypass or a permissive sandbox flag list into the production contract.

Standard `ui/initialize`, tool input/result notifications, `tools/call`, conversation messages, model-context updates, and resize/lifecycle behavior keep their upstream meaning. An app-originated tool request is checked against the admitted resource's supported app-callable tools and routed through NanoCore's existing governed MCP/capability owner. It cannot dispatch another Plugin's tool, change actor/scope, or bypass Policy. Model-context updates are context data, not an instruction to execute a tool or counterfeit a human message/approval. Unsupported optional capabilities are denied explicitly. Expired or uncertain effect outcomes use the command/capability owner's inspection semantics; reloading the iframe cannot replay them.

For native/delegate linkage, define bounded domain data in the admitted interaction binding, such as a selected set of customer IDs. Use the standard bridge's supported messages/tool results to convey it and the A2UI data model to update native siblings; any extra local selection event must be an explicit schema-bound host extension, not a claim that MCP Apps standardizes arbitrary cross-widget events. The host validates IDs, source scope, size, and freshness. Selection/filter state is ephemeral; it cannot patch authoritative Kernel data. Saving a selection invokes an explicit current-authority data command, while further reasoning invokes the existing Agent work owner. No DOM access or mandatory LLM round trip is needed for local selection feedback.

Each delegate has an accessible name, focus boundary, loading/failure state, and a local retry control. Native siblings continue operating if their sources are independent. A missing, revoked, changed, or corrupt resource disables that region and dependent actions; it cannot silently fetch replacement code at the same URI. Retry may repeat safe loading/initialization, never a business operation. Agents can build, validate, register, and later reuse a new widget through existing development and Plugin owners; that path does not execute generated code inside NanoCore or the host document.

## Contract

### Producer, Admission, And Rendering

Any producer submits an untrusted declaration and bounded data. During UI admission, the producer may request a known presentation or supported action, but cannot register tools, scripts, network targets, or new executable components. Agent-authored Plugin resources follow their separate governed catalog admission; embedding them in a UI declaration cannot install them. NanoCore validates syntax, selected protocol/catalog, size and composition bounds, source references, current audience, and exact allowed bindings before publication. Invalid output receives a safe plain-content fallback when one can be produced without disclosing restricted data.

The first component set should cover the motivating read view and edit form using existing accessible primitives. Text, labeled inputs, selection, bounded lists/tables, and explicit action buttons cover the initial native slice; the single PluginWidget delegate extends it for specialized interactions; no customer-specific native component or custom widget marketplace is needed. Catalog expansion requires an actual supported interaction and its fallback behavior. Web handles focus, keyboard navigation, accessible names, validation messages, and host styling; a model cannot override these responsibilities.

An in-thread surface is represented through existing Item history. Its exact accepted declaration or immutable content reference, protocol/catalog identity, source mode, and action bindings must be recoverable; browser memory is not its durable owner. Streaming is a projection while generation is incomplete. No interaction can execute from an unadmitted partial declaration, and incomplete output must not be persisted as a completed reusable view. Restart renders the last accepted content or an explicit incomplete/fallback state, without launching a new generation or replaying an action.

### Temporary And Reusable Surfaces

Temporary means there is no independent saved-view identity or automatic live refresh. It does not mean that an already published Thread Item vanishes. A temporary result can remain inspectable as historical content under existing Item/Artifact retention. Saving a reusable view is an explicit authorized operation, separate from generating a reply, editing a field, or running a business command.

The bounded new durable need is a saved view: stable Workspace identity and current immutable definition revision, title, author/request lineage, protocol/catalog identity, presentation declaration, exact source binding, and supported action references. It owns no business-data rows, credentials, active grants, independent execution state, or copied permission decision. The persistence proposal below assigns these bytes and links explicitly; the initial contract below fixes its presentation subset; independent saved-view schemas remain a deferred extension. The Markdown/plain-text Material contract is not generalized to store it.

| Source mode | Meaning on display/reopen | Mutation boundary |
| --- | --- | --- |
| Historical result | Render the accepted result bytes or exact immutable reference with observation time and provenance; do not label it current. | An action must re-resolve current authority and target state, or explicitly require refresh. History is not permission. |
| Live bound view | Resolve a named bounded query against its owning source under the current actor's authority; show freshness and failures. | Explicit typed actions carry exact target and expected revisions. Refresh itself cannot mutate business data. |

Unsaved client input is an orthogonal browser-local draft overlay on either source mode, not a third saved source mode. It remains visibly distinct from current server values and historical content. Only explicit submission through an owning command can persist business data; saving or reopening the view definition does not save or restore this draft overlay.

Saving or updating a reusable view validates the whole definition and requires the expected saved-view revision. Conflicts preserve the existing definition and user draft for an explicit refresh/review. Reopen uses the saved revision and its declared source mode, without asking a model to regenerate the UI. Unsupported protocol/catalog revisions, missing content, missing records, or denied sources yield an explicit unavailable/fallback view; they cannot cause automatic schema creation or target substitution.

Retiring a saved view removes it from ordinary active discovery and disables its actions while preserving authorized historical inspection and portability. Reactivation revalidates the definition, sources, and current authority. Physical saved-view purge is outside the initial scope; Thread/Workspace deletion and retention retain their existing owners. Definition versions and business record versions are distinct, and editing one never silently changes the other.

### Persistence Ownership And Standard State Reuse

A2UI supplies declaration/data-model messages, MCP supplies resources and tool results, and AG-UI supplies snapshot/delta synchronization. None defines OpenKit's authoritative Item links, saved-view identity, access scope, retention, or portable record graph. Use their wire models instead of inventing a component language or browser bridge; keep storage ownership explicit:

| Content | Proposed persistence owner | Reopen behavior |
| --- | --- | --- |
| Accepted presentation revision | Immutable Workspace SQLite presentation revision containing exact A2UI declaration, source mode/bindings, pinned resource identities/digests, and necessary accepted historical payload | Read that exact revision; do not regenerate or substitute current Plugin bytes. |
| Temporary conversation presentation | Existing Item history references the accepted revision and retains a safe text fallback | Display as historical content; no separate saved-view identity or automatic live query. |
| Explicitly saved view | Small Workspace SQLite saved-view record with identity, title, current revision, lifecycle, actor/request lineage | Resolve its exact revision and current-authority sources. Saving is separate from publishing a Thread Item. |
| Plugin executable UI resource | Existing Plugin/component source plus exact admitted resource bytes/digest retained with the presentation when upstream cannot provide immutable retrieval | Mount only the pinned bytes with currently allowed capabilities; missing bytes remain unavailable. This retention is not another Plugin version catalog. |
| User deliverable Artifact | Existing Artifact owner, only when the user saves/exports a deliverable or introduces an existing Artifact as a source | Use explicit Artifact ID/version/digest; do not assume an ordinary Artifact version counter retains all prior content. |
| Widget selection, focus, draft input | Ephemeral host/widget state | Reset on reopen unless explicitly saved as presentation parameters or written through a business command. |

This contract needs no mandatory Artifact for every widget, no Material expansion, and no second business-data store. The accepted presentation revision is the sole retained declaration owner for both temporary and saved views. Historical source bytes are labeled observations with audience and provenance, never a live business authority. The initial record families and reference/retention coverage are fixed in [Storage Layout And Record Ownership](20260703-storage_layout_record_ownership.md) and [Workspace Backup, Export, And Import](20260704-workspace_backup_export_import.md); saved-view coverage remains deferred.

Create immutable presentation content before publishing its Item reference or saved-view pointer. The SQLite saved-view pointer/revision update and metadata-only receipt commit locally together. Appending an Item is a separate existing history effect: interrupted publication leaves either an unreferenced revision or explicit incomplete/recovery-required publication, never a fabricated successful reference or automatic effect replay. Retention must preserve every revision and pinned resource still referenced by a retained Item or saved view; purge cannot leave a dangling reference. Reopen checks current audience and capabilities before rendering even retained HTML. A stale pinned Plugin version is not automatically upgraded by registration changes.

[AG-UI state synchronization](https://docs.ag-ui.com/concepts/state) offers full `STATE_SNAPSHOT` and ordered JSON Patch `STATE_DELTA` events. If an AG-UI consumer is integrated, reuse these at the existing transport adapter boundary; a missing base or inconsistent delta requires a fresh snapshot. Inside A2UI, use its native data-model messages and bindings. Do not maintain two authoritative session states or add an AG-UI server solely for widget/native linkage. Neither kind of state patch is a database command, a saved-view edit, or a human approval. Persist only through the named owners above.

### Action Binding And Current Authority

The renderer sends a bounded interaction request referencing the accepted surface/definition revision, action ID, schema-admitted arguments, relevant expected source revisions, and request ID. Core derives actor, Workspace, audience, targets, implementation binding, and required authority from authenticated context and the accepted definition. Client-supplied labels, hidden fields, metadata, source IDs, or approval flags cannot widen that binding.

Expected source preconditions follow the owning command: immutable results use exact content identity, while mutable targets use its supported revision or conditional-write mechanism. The renderer cannot invent a revision for a revisionless external source. If a requested safe edit requires a precondition that the owner cannot enforce, that edit remains unavailable rather than claiming lost-update protection. Source bindings preserve and recheck external instance identity independently of mutable connection handles, including for non-Kernel sources.

Each action maps to one exact existing or accepted typed command. Deterministic reads and writes do not start an agent. An explicit request for reasoning or extended work invokes existing Task/Goal semantics. An external operation uses its existing capability/effect owner. Kernel commands use the Kernel specification when available; ordinary record operations do not depend on it. A2UI agent-callable functions are admitted only if a concrete existing entry path permits that exact call; neither a protocol caller label nor a published view registers model-visible Tools.

[Policy Enforcement Mapping](20260703-policy_enforcement_mapping.md) retains the unique product-operation/access-right registry. UI proposal, save, read, retirement, and action projections need explicit mappings and catalog coverage before publication; the initial operation projection and the Policy owner define these mappings; component names never grant authority.

Current authorization applies when reading the view, fetching data, publishing to an audience, and submitting an action. Approval-dependent effects reuse the existing [Human Attention](20260531-human_attention_intervention_model.md) contract and remain bound to the exact target, arguments, and revisions approved. A changed request requires renewed admission. Generated confirmation buttons cannot manufacture approval, and the UI creates no second Approval/Elicitation record family.

The owning command returns the authoritative result. A local validation error or conflict keeps the unsaved input and identifies what must be corrected or refreshed. Stale operation/definition identity cannot execute a newer binding silently. Duplicate delivery uses the command owner's request identity/receipt semantics; an expired or unknown receipt is not permission for automatic replay. User-visible effects retain existing attributed Item/work/capability lineage. No separate UI action runner, action log authority, or settlement loop is introduced.

### Failures, Recovery, And Disclosure

Web distinguishes loading/streaming, usable rendered content, unavailable interaction, and safe plain-content fallback. Unknown components degrade to safe content; they never load remote code or substitute an unadmitted iframe. An explicitly admitted PluginWidget is the sole delegated HTML path. A failed source read must not turn stale data into current data. An invalid action result must not be treated as success merely because a button completed its animation.

If the browser disconnects after submission, Core's owning command or execution record decides the outcome. Reconnect may inspect that outcome but cannot resubmit the effect automatically. An unknown external result stays unknown under the capability owner; the view offers inspection or a fresh authorized attempt rather than claiming rollback. A restart must not regenerate a saved view, rerun an operation, or recover business authority from the UI data model.

Only audience-authorized data reaches the browser or an agent. Renderer-only metadata is not a place for secrets; hidden controls and model-invisible payloads are not access control. Passing a view back to an agent requires the existing context-selection and disclosure rules, with only the needed fields and provenance; do not automatically inject the entire UI data model. A surface containing a PluginWidget MUST keep A2UI `sendDataModel` disabled; only schema-admitted necessary fields may reach agent context through the explicit interaction/context boundary. Revoking access prevents subsequent reads and effects, without pretending already delivered bytes can be recalled from a client.

`OutputAudience` and source-to-destination disclosure remain owned by `docs/core/permissions.md`; human reader identity and Workspace membership remain owned by [Multi-User Workspace System](20260715-multi_user_workspace_system.md). Permission to read a private result does not imply permission to save it into a shared view or Thread. Saving and publishing recheck the exact destination audience, including retained historical result content.

Saved definitions and any canonical accepted UI payloads require explicit portability coverage under [Workspace Backup, Export, And Import](20260704-workspace_backup_export_import.md). Import preserves immutable declaration content and rewrites internal references consistently, while external bindings remain unbound where access cannot be proven. It does not import credentials, grants, host-renderer executable code, or cached authority. Digest-pinned Plugin UI resource bytes may be transported only as explicitly classified inert presentation content; import verifies them but does not install a Plugin, register a capability, or enable execution. Re-admit the resource and bind its tools under current target authority before mounting it. Unavailable catalogs or bindings disable interaction while retaining safe inspectable content. Export success must be verified with real saved and reopened views, not inferred from generic Item export.

## Relationship To Community Protocols

[A2UI](https://github.com/a2ui-project/a2ui) supplies the declarative rendering protocol and catalog model. [AG-UI](https://github.com/ag-ui-protocol/ag-ui) informs event, interaction, and state-stream boundaries; OpenKit need not replace its existing Item/API transport to render A2UI. Add an AG-UI adapter only for a concrete interoperability consumer.

[OpenAI Apps/Plugins UI architecture](https://developers.openai.com/plugins/build/chatgpt-ui) supplies the tool/resource association and structured-result interface direction adopted above. OpenKit uses native A2UI rendering by default and the standard MCP Apps host bridge for explicitly admitted HTML delegates. Business state, widget state, and conversation context remain separate. The [community catalog](https://github.com/narrowin/awesome-generative-ui) is a discovery index, not a normative specification.

Chat renders those Items through official `@a2ui/react@0.11.0` / `@a2ui/web_core@0.10.7` v0.9 imports and the native catalog mapping in `apps/web/src/generative/native-catalog.tsx`. ## Rollout And Acceptance

The first native slice renders one ordinary existing result through A2UI v0.9, with safe fallback and one exact existing action. A headless Kernel slice proves data durability; a Kernel-backed native view composes the two without requiring independently saved views. Saved-view and HTML-delegate slices subsequently prove their own lifecycle and interaction contracts. These are separable probes, not a fixed delivery order or a requirement to defer useful UI until Kernel lands.

The predicates below cover the full design. The initial-delivery boundary selects the native subset; predicates for deferred features apply before those features are enabled, not as prerequisites for the native MVP. Partial implementation must not be reported as full conformance.

- A registered widget and a dynamically generated declaration use the same admission path. Headless data tools do not force UI; render tools resolve exact A2UI resources, and the specialized HTML region uses the standard isolated delegate with only its negotiated capabilities.
- A Worker-produced and a deterministically constructed view share admission/rendering semantics; an ordinary action works without a model call.
- A UI over an existing non-Kernel result works without Kernel records or module creation; a Kernel module remains usable without Web.
- Upstream v0.9 messages render through the official renderer/catalog mapping. Candidate v1.0 changes have an explicit boundary migration path without an upstream release wait.
- A partial/invalid declaration, unknown component, unavailable catalog, or disallowed function cannot execute an effect or load unadmitted code and has a safe accessible fallback.
- A saved historical view reopens with exact historical provenance; a live view re-queries current data; an unsaved input remains visibly unsaved. No reopen regenerates content or executes an old action.
- Stale targets, revoked permissions, changed operation revisions, and forged bindings fail before effect; required human approval covers the exact submitted operation.
- Double submission and reconnect do not duplicate a local mutation or silently repeat an unknown external effect. The authoritative outcome or explicit unknown state can be inspected after restart.
- One map-selection scenario exchanges validated customer IDs with a native list, then saves them through a Kernel command; forged cross-frame messages, undeclared tools, stale resource versions, denied CSP origins, and context-update-as-approval attempts produce no unauthorized effect. Delegate load failure leaves independent native controls usable, and reload does not replay writes.
- Keyboard-only operation, meaningful accessible labels, validation errors, and fallback content work in the motivating read/edit flow.
- Saved definitions and accepted payloads survive export/import with valid references and current authorization; missing external bindings remain explicit and non-executable.

## Initial Contract: Native A2UI Presentation And Actions

The initial contract reuses upstream [A2UI v0.9 messages and actions](https://a2ui.org/specification/v0.9-a2ui/) and the [A2UI over MCP resource profile](https://a2ui.org/guides/a2ui_over_mcp/). OpenKit adds only authenticated source/action binding, immutable retention and Item publication, and transport request identity. AG-UI's snapshot/delta vocabulary remains an optional interoperability projection; it does not supply a persistent Item or database schema and is not a required second state store.

### Catalog And Retained Content

The initial catalog ID is `urn:openkit:a2ui:catalog:native:v1`. Its definition projects upstream v0.9 basic-catalog `Text`, `Row`, `Column`, `List`, `Card`, `Button`, `TextField`, and `CheckBox` schemas onto existing accessible host primitives. It is an explicitly smaller catalog, not an assertion that OpenKit implements the entire upstream basic catalog. Keep standard component IDs, property names, literal/path bindings, child references and list templates. Function calls, arbitrary validation regex/check expressions, media/network components, inline catalogs, supplied themes/styles, and PluginWidget are unavailable initially. A static reachable `root` component is required; dangling references, cycles, duplicate IDs and actions inside repeating templates are rejected. Native repeated read-only rows remain supported. Initial editing binds a static form to one exact record; a later interaction contract can extend repeated-row action binding without changing A2UI itself.

A publish input is `{threadId,turnId,title,fallbackText,messages,source,actions}`. The generated-answer admission shorthand below normalizes to the same retained item source; it adds no retained source kind. `messages` contains one v0.9 `createSurface`, one `updateComponents` with the complete component set, and no producer-supplied business `updateDataModel`. Core reads the authorized source and appends its root `updateDataModel`, so source values cannot be counterfeited by producer-supplied data. All three accepted messages have the same surface ID; `createSurface.sendDataModel` is false. The publisher may choose a bounded surface ID; the host namespaces each renderer instance by presentation ID rather than allowing equal surface IDs in separate Items to share state. A2UI `deleteSurface` disposes a browser instance only; it never retires a presentation or deletes Kernel data.

Core retains the exact accepted three-message JSON array and its SHA-256 digest in one immutable presentation record. It does not retain every keystroke or invent a new serialized component-tree language. Changes to the declaration/source/action binding require a new presentation and explicit publication; there is no mutable current-view pointer in the MVP. Protocol wire `version` remains `v0.9`, not a package version or an invented `v0.9.1` message discriminator. Eventual v1.0 migration is at the rendering boundary; retained v0.9 bytes are not relabeled as v1.0 bytes.

The presentation row contains exactly `id`, `workspaceId`, `threadId`, `turnId`, `itemId`, `createdAt`, trusted `actor`, nullable `requestId`, nullable `originRequestId`, `semanticInputHash`, `title`, `fallbackText`, `protocolVersion`, `catalogId`, `messages`, `contentDigest`, `source`, `actions`, and `observedAt`. IDs are Core-assigned UUIDs; `id` identifies this immutable presentation revision, so no second revision counter/identity is needed. `itemId` is allocated before retaining the row. Actor/request lineage is attributed through existing owners; saved authority, credentials, executable code and copied permission decisions are absent. ### Source Preconditions And Actions

`query` uses the Kernel's ordinary request/limit semantics and is not a permission expression. All returned source content must be disclosable to the destination Thread audience at publication and to the current reader on reopen/refresh. Reads recheck source authorization even when the bytes are historical; no retained content is a bypass for revoked access. Missing content, wrong digest, retired/unavailable app, unsupported catalog or schema drift yields an explicit unavailable action or safe fallback, never target substitution.

`actions` contains at most eight unique static bindings `{name,componentId,kind,...}`. Each named component must be an admitted Button whose `action.event.name` agrees with the binding. Initial kinds are `refresh` and `kernel-record-update` only. A refresh binding has no extra fields and expects empty event context. A record-update binding adds `{recordId,writableFieldIds}`; it requires a kernel-records source with page 1, perPage 1, and a top-level conjoined `id = recordId` equality matching the bound record ID. Core verifies the normalized filter and exactly one result; zero results make the form unavailable, and a paged/reorderable multi-record source cannot carry a write binding. It permits 1–16 unique text/bool field IDs whose schema has `required:true`. Nullable fields remain read-only in this initial form profile: empty text means an empty string, false means false, and neither may be invented from null. An explicit nullable control adapter is a later extension. The first form does not accept arbitrary record IDs, fields, collection selectors, operations, URLs or credentials from action context. Other data types remain fully available to the Agent data API but are read-only in the initial form catalog until their typed input adapter is added.

For a writable form, `query.fields` must equal the bound writable field names, with no additional fields. Each bound field has exactly one admitted TextField (text) or CheckBox (bool) whose value binds `/records/0/data/<fieldName>`; other editable controls are rejected. The Button event context must bind `expectedRecordRevision` to `/records/0/revision` and `values` to `/records/0/data` using upstream path objects, with no literal overrides or extra keys. Admission validates this wiring as well as the server-side action binding; the native binding engine therefore submits exactly the displayed record and permitted values without a second form-data language.

A record-update event context is exactly `{expectedRecordRevision,values:{fieldName:value,...}}`; `values` is a nonempty subset of the bound fields. The revision is an untrusted compare-and-set value, not authorization. Field names resolve under the accepted schema revision. At execution, Core checks the source remains constrained to the same exact record ID, its current query membership and its expected revision in the same app transaction as the write; a record that no longer matches cannot be changed through this stale binding. Extra context keys, wrong types, omitted required preconditions, stale schema, different source component/surface, or unavailable bindings fail before effect. The ordinary Kernel update remains the executor and result owner. No UI action runner or new execution record exists.

### Standard Messages And Transport Projection

The browser sends the unchanged native client message `{version:"v0.9",action:{name,surfaceId,sourceComponentId,timestamp,context}}`. The admitted presentation ID is in the API path and the client-generated UUID request ID is in `x-openkit-request-id`, outside the A2UI message. Timestamps are untrusted display metadata, never identity or authority. The browser allocates one request ID per deliberate submission, reuses it for the same in-flight submission/double click, and never derives identity from data values. A fresh intentional submission gets a fresh ID. An uncertain result is inspected rather than automatically resubmitted, including after reload.

Record-update execution passes that request ID to `kernel.records.update`; the semantic fingerprint includes the presentation and action binding lineage as well as the admitted mutation. A valid duplicate resolves the owning Kernel receipt and current record before checking stale data preconditions, while rechecking current access and binding availability; it cannot mutate again. A changed submitted value under the same ID produces `idempotency_key_conflict`. No separate UI receipt duplicates the Kernel mutation receipt. The action response contains the authoritative current record and standard `updateDataModel` messages; a failure preserves the browser draft and reports the Core error. Refresh is a read, not a business mutation or publication. Its separate POST refresh route accepts only a binding of kind `refresh`, so the operation catalog has a fixed read-only posture rather than guessing it from client arguments.

For a successful update, Core re-queries the bounded source and returns a root `updateDataModel`; if the post-commit source read fails or no longer includes the edited row, report the committed record result and explicit refresh-unavailable condition. Do not return a failure that implies the write rolled back or retry the write to repair the view. Temporary browser draft values are overlaid separately from refreshed server values; refresh/reopen never silently submits or preserves them as saved business data. A client error message, including upstream `VALIDATION_FAILED`, is a rendering diagnostic and cannot dispatch an action or alter presentation history.

| Operation ID | App API path relative to `/api/app/workspaces/:workspaceId` | Supported result |
| --- | --- | --- |
| `generative-ui.publish` | `POST /generative-presentations` | Retained presentation plus exact Item publication reference or explicit recovery condition. |
| `generative-ui.get` | `GET /generative-presentations/:presentationId` | Exact authorized presentation and derived Item-publication condition. |
| `generative-ui.resource` | `GET /generative-presentations/:presentationId/resource` | Standard text resource content for the retained native template. |
| `generative-ui.refresh` | `POST /generative-presentations/:presentationId/refresh` with the native refresh event | Current source read and standard data-model messages; read-only mutation posture. |
| `generative-ui.action` | `POST /generative-presentations/:presentationId/actions` with the native update event | Current owning record result plus standard data-model messages; mutating posture, never a new Agent run. |

Publish uses its request ID header. The static form's mutating action requires that header; refresh accepts it only as transport correlation and refuses every mutating binding. The action route refuses refresh bindings. Actions are not appended to a completed source Turn as new work. They use existing request/Audit lineage to the originating Item; a new agent task or UI generation follows ordinary work admission separately.

The selected built-in Worker tool names use the same operation IDs with dots and hyphens normalized to underscores and strict operation-specific schemas. Native render results use fallback `TextContent`, an `EmbeddedResource` containing `application/a2ui+json` data-model messages, and `_meta.ui.resourceUri` identifying `ui://openkit/generative/{presentationId}`. That URI resolves only the exact retained `createSurface`/`updateComponents` template through Core and has no independent template-installation lifecycle. A dynamic publish cannot know its resource URI before execution; the exact association is returned on the tool result. Reusable predeclared render-tool/template registrations are deferred. This is the native A2UI-over-MCP profile, not a claim of full ChatGPT Apps SDK or HTML MCP Apps host conformance.

The Web host uses the authenticated Core resource endpoint to resolve the same URI; it never opens an arbitrary MCP server or URL. The Worker tool result already includes its necessary data and declaration reference, so this slice does not require adding a Worker `resources/read` capability family. Public Skill/CLI projections expose the same operations through the existing catalog; the read-only resource route may be a cataloged read rather than another process/runtime. Headless Kernel calls carry no UI metadata and never force a widget to render.

### Publication, Recovery, Retention, And Bounds

Publish requires the exact current writable Thread/Turn and producer authority. A selected Worker is bound to its authenticated current session/Turn; a deterministic producer uses existing trusted Turn admission. Core validates the whole input, fetches current source data, resolves static actions and audience, allocates presentation/Item IDs, then commits the immutable presentation and an attributed admission AuditEvent in Workspace SQLite. It next appends the exact referencing Item through the existing file-backed Item owner and finally records the existing Workspace completed receipt referencing the presentation. File-backed Item append and SQLite commit are separate effects, not one transaction.

A valid publish receipt returns the exact existing presentation and derives publication from the named Item. If the receipt is missing/expired but a request-owned presentation or Item exists, return `recovery_required` with that resource reference; do not append again, synthesize a receipt, or introduce a pending-publication state machine. `get` derives `published`, `unpublished`, or `inconsistent` by comparing the reserved Item ID and exact reference in retained Item history. Missing/contradictory references are inspectable, not automatically repaired. A caller may inspect and make a fresh deliberate publish request under current writable-Turn authority; this creates a new presentation, not a silent repair. Before a receipt exists, a unique `(workspaceId,requestId)` constraint on presentation admission prevents a concurrent duplicate from allocating another effect. Different semantic input for the same key is rejected.

Retain every admitted immutable presentation and its exact historical payload while its owning Thread history is retained, including unreferenced presentations from interrupted publication. No independent view purge, reactivation, or background collection is added. Thread/Workspace deletion uses the existing lifecycle and portable closure owner; it cannot delete content still referenced by retained history or report complete backup/export without the presentation graph. On reopen, replay the retained accepted messages as historical content with `observedAt`; no model regeneration, automatic live read, or action replay occurs. Explicit refresh labels the returned current observation and does not overwrite historical bytes.

Fixed initial bounds are one surface/source, 200 declared components, 500 expanded component instances, graph depth 20, eight static actions, 256 KiB/declaration, 2 MiB/accepted messages including source data, 64 KiB/action message, and 8 KiB/fallback text. All identifiers/strings also satisfy upstream and owning Core schemas. Exceeding a bound fails before publication/effect, with safe authorized fallback. No source/data-model auto-forwarding is enabled. Keyboard focus, accessible labels and unsaved-input/error behavior use the existing Web primitives; renderer package versions are selected and tested during implementation. Missing base or invalid sequence requires a fresh full accepted message set, not applying an uncertain delta. If an AG-UI consumer is later added, its `STATE_SNAPSHOT`/`STATE_DELTA` remain adapter projections of that same state, with no second durable authority.

## Initial Delivery Boundary

The first delivery admits and renders native A2UI v0.9 content in an existing Thread, retains the exact accepted presentation revision and Item reference, and dispatches an explicit typed action through Core. It must work for an existing non-Kernel source and compose with a headless Kernel. Historical reopen and an explicit current-data refresh are sufficient initially; neither an independent saved-view identity nor automatic live refresh is required to prove this loop. The declaration and action admission boundary remains common to deterministic and agent producers.

The accepted mixed-rendering direction remains A2UI native composition plus a single isolated MCP Apps HTML delegate. The delegate, reusable template management, independent saved-view lifecycle, and an AG-UI interoperability adapter are later implementation slices. Their detailed contracts and conformance checks are prerequisites for those features, not for native rendering. No browser-only persistence, custom recursive fixture language, or unmediated effect path is an acceptable MVP shortcut. Every introduced canonical presentation/Item reference still needs the existing storage and portability owners' explicit coverage.
