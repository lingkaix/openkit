# Persistent Worker Volumes And Environment Replacement

## Owns

This specification owns the user-selectable Sandbox as the existing retained Worker environment association, administrator templates, exact worker Thread selection, retained working files and native runtime data on the execution host, scoped attachment/removal, initialization without overwrite, and authorized compatible environment replacement. It also owns the bounded durable image-result settlement used only by environment preparation; the transport owner supplies authenticated carriage and correlation. It owns the concrete first Docker/OpenShell realization of the Core storage principle, not another runtime, general filesystem service, public Computer entity, general volume catalog or scheduler. The bounded Sandbox resource projection uses the existing association and operation owners.

## Does Not Own

NanoCore owns Workspace/Thread/AgentSession, permissions, scheduling, Items, Artifacts and acceptance. The runtime and transport owner owns the Runtime Epoch and process fencing. Agent supply owns image declarations and desired setup; image acquisition/build execution and the Image Store retain their existing owner. Native adapters own runtime file schemas and exact conversation continuity. Git and object stores keep their authority. VM/microVM backends, process-memory checkpointing, live migration, multi-host replication, generic snapshots and automatic rollback are not implemented by this contract.

## Retained Bytes And Boundaries

Preserve complete admitted volumes, regardless of whether OpenKit recognizes their contents. Untracked/ignored files, project `temp/`, partial work, native conversation history, memory and configuration are illustrative, never an exhaustive set or file-type filter. No Gitignore, extension, Artifact registration or last-Turn filter defines retention. Disposable scratch and generated credentials/control/context live in separately declared locations. An ordinary Turn or AgentSession close releases execution and request-private material only; it cannot purge these roots.

Retention is not product publication. A dirty worktree owns its uncommitted work bytes, while Git owns committed versions, and Core owns accepted changes and evidence. Native files admitted into a Workspace-shared Sandbox have that shared destination audience; protected sources require explicit source-owner authorization before delivery. Existing private associations retain their restrictions and exact continuation as specified below. Native memory is not automatically Core User Memory or Workspace Knowledge. Admitted native configuration may influence local execution and define local instructions, Skills and tools under its adapter's qualified native conventions. It does not select a conversation, grant platform credentials, or change externally admitted model, Gateway, managed MCP, filesystem or network authority; the current AEP and protected adapter bindings remain controlling. Unsupported native features remain explicit limitations, not reasons to erase or silently rewrite retained configuration.

Persisted directories do not contain OpenKit-injected route credentials, live control endpoints, lease material or regenerated AEP packages. The launcher refreshes current bindings separately before every process launch. No file's existence authorizes a future effect. The system does not inspect or extract hidden reasoning to manufacture continuity evidence.

## Selectable Resource And Administrator Templates

The product name is Sandbox; the Core resource is the retained Worker environment association. A physical Sandbox runtime instance realizes it and may be replaced without changing its public identity. `storageRef` is immutable identity. The bounded editable name is metadata, not a hostname or uniqueness key; duplicate names are allowed and product lists show a short identity disambiguator. A Sandbox may exist stopped and before its first execution. Public running, stopped, unavailable and recovery-required descriptions derive from the association and backend residency/cleanup owners, never a second stored lifecycle enum. The execution host owns bytes, not product identity.

A Sandbox template is a named administrator-authored environment-supply definition in existing Server configuration. Its immutable revision identifies the governed reference/build declaration, admitted exact image digest, verified runtime capabilities, storage layout and image-default evidence. Dockerfile-like inputs, public build arguments and bounded build-egress/resource declarations use existing preparation. Build authority applies only to the administrator's admitted preparation, never to runtime network grants. Successful acquisition/build, exact inspection and administrator activation of non-secret image-default evidence are prerequisites for publication. Only currently enabled published revisions are offered. Editing a definition neither publishes it nor mutates an existing Sandbox's pin. Configuration revision/CAS and authored/resolved candidates extend to a template target; no new build service, image store or job lifecycle is introduced.

A template exposes a deliberately published secret-free supply summary, not its private candidate Thread, raw diagnostics or private Artifact content. It contains no permission/Vault grants, raw credentials, Provider routing, host selector, arbitrary host mounts, other-user storage refs, Thread/AgentSession state, native handles or control endpoints. Image-declared targets remain layout requests under mount admission. Native defaults remain ordinary image supply, with protected platform bindings and no populated-home reseeding.

The selected AgentManifest remains the runtime authority source: adapter, binaries, requirements, grants, credentials and other governed setup. Resolve the resource's admitted image pin instead of the manifest default and prove it supports that exact launch contract. Copy no template grants and union no co-resident policies. Missing runtime, binary, layout or required capability proof returns a bounded incompatibility reason. Installed tools remain usable inside the admitted Sandbox with unchanged external AEP reach. The manifest image declaration remains active default supply, normalized with template selection into the one existing setup/AEP path; no cloned Agent, per-provider resolver or backend-specific public field is required.

Persist only the selected name, creation attribution, exact template revision when selected, verified image/default evidence reference and existing scope/layout/target/attachment facts. Do not copy the full AEP, image blobs, configuration contents, occupancy, health or grants into the resource. Template provenance differs from selected image identity: later publication never rewrites an established pin. Resource and template updates use their existing separate revision owners.

Extend existing associations additively or through a one-way migration under [Storage Layout](20260703-storage_layout_record_ownership.md#retained-sandbox-association-storage). Keep every existing ref, target, byte, contributor, generation, state, receipt and historical AEP usable. Use neutral names and enrich image pins only from exact retained verified provenance, never tags, latest Agent config, directory proximity or matching layout. Insufficient provenance requires explicit current revision-bound compatible image/template adoption while retaining the fence; no fabricated readiness, data-root discard, permanent legacy reader or dual write is permitted. Existing private conversation associations keep their exact authorized continuation and metadata audience; enrichment cannot make them visible or attachable to other members.

The decision and its reason are recorded in [User-Selected Workspace-Shared Sandboxes](../decisions/20261008-user_selected_workspace_shared_sandboxes.md). These amendments govern implementation after `v0.1.0-rc.1`; that release does not wait for this feature.

## Workspace Sharing And Protected Sources

A newly created Sandbox belongs to its Workspace and is shared from creation, including with no contributors. Every active member may list/inspect it, create from admitted templates, select/execute, rename with association CAS, idle-stop and request administrator deletion, regardless of creator or contributor. Bounded compatible image adoption uses the same eligibility. Current credential scope, policy and lifecycle remain required. Current administrators retain their separate eligibility without Workspace membership and with truthful actor attribution; they never impersonate a contributor or bypass holds, mount compatibility, protected-source admission, credential visibility or cleanup.

A Workspace-shared Sandbox admits its retained working and native data to current and future Workspace members; creator identity and work-slot names provide no confidentiality boundary. Private or otherwise narrower source data may enter only through its source owner's explicit authorization to that destination audience. Membership loss blocks future governed access but cannot retract previously disclosed bytes. Shared contributions survive departure of their contributor. Contributor history remains for attribution, restrictive-source evidence and independent-review separation, not a same-user lock or universal per-caller contributor intersection.

Task and Goal execution Threads already have the Workspace-shared audience under [Thread Visibility](20260909-thread_visibility_and_sharing.md). Before context, working data, native history or other governed sources enter a shared volume or its co-resident execution, their owner must permit disclosure to that destination audience. Source read permission and the Sandbox notice are insufficient. For new shared work, refuse still-private conversation content or private native continuity. An existing authorized private-to-shared handoff or publication supplies exactly its confirmed selected payload, never the rest of a private native home or transcript. Use a fresh shared worker Thread when continuity requires it. No classifier, scrubber, per-file ACL, implicit share-all-history or new declassification action is introduced.

Existing private retained volumes cannot be published by a migration or by removing a user-id comparison. Preserve their bytes, metadata restrictions and exact private continuation; withhold shared attachment until existing source authority explicitly permits the complete retained-content audience, or select a new shared Sandbox. Missing/unknown audience evidence fails closed. Private-derived names and metadata cannot leak through lists or errors, including resource existence. Administrator recovery inspection does not admit ordinary-member execution. This is a restricted-data disposition in the existing association, not a private Sandbox product tier or permanent old-format reader.

Otherwise eligible shared name/status remains member-visible even when detailed contributor history is inaccessible; project that history through its own record audience. Blocked shared resources may show a safe unavailable reason. Lists, direct refs, previews and status exclude private titles, prompts, native handles, secrets and restricted lineage before disclosure, using existing non-disclosing refusal for inaccessible/missing references. A Task history may name its admitted resource only within that history's audience and does not publish the whole inventory or native files.

Before creation or selection is submitted, Web and remote MCP discovery/description plus selection preview convey this exact product meaning: “This Sandbox is shared with current and future members of this Workspace. Members can read and change its working files, native session data and files you add, including secrets you place there. It contains other members' work when shown below. Your Task uses its own work slot and conversation; this does not make its files private. Stopping affects the shared runtime; only an administrator can purge its retained data.” Name the Workspace and selected Sandbox, show authorized contributor/work summaries and current occupancy, and disclose stop/rebuild impact without restricted source records. The creator and every later selector receive this meaning, including through their personal agent's operation guidance. Skipping preview never skips server checks. This notice creates no approval record, invitation, contributor consent or bearer grant and cannot authorize private-source disclosure.

Removed, disabled or nonmember ordinary actors lose list/read/name/select/start/stop/rebuild and resource-specific deletion-request access even with an old ref, selection or unexpired credential. Reauthorize at every effect boundary, including queued dispatch and exact replay disclosure. Close/fence the removed actor's active binding and revoke its mediated authority; widen cleanup only when local cleanup and sibling safety cannot be proved. Retain admitted shared contributions and exact remaining actors' authority. Previously copied bytes cannot be recalled.

## Worker Thread Choice

Initial Task input carries either an exact selected `storageRef`/expected revision or create-from-template id/exact revision and bounded name. Choice and actor enter existing immutable command/admission lineage and canonical replay hashing before Coordinator decisions are recomputed, for direct, conversational and Goal handoffs alike. Creation uses the existing request-receipt owner: identical scope/input yields the same association, changed input conflicts, and a receipt gap with incomplete owners requires inspection rather than another allocation. Initial Thread intent may persist before the first Turn through that same owner, never a parallel preference table.

Assignment belongs to the worker Thread because its mutable slot and native conversation survive sequential Turns. Before first admitted execution, an unconsumed selection may change through ordinary revision-checked intent editing; it cannot retarget queued/active work. After native continuity, omission means the exact prior association/slot/pair; a different choice conflicts even when stopped. Offer a new Thread for a different Sandbox. Compatible rebuilding preserves the association and exact resume without migration, reset or empty-session fallback. Existing private continuation remains restricted. An internal Assistant/Coordinator Thread has no worker selection. Goal cards express choice as intent copied to ordinary Task admission through existing Plan/card checks, never a Goal pin or automatic inherited affinity.

A new worker Thread without choice gets fresh retained shared storage from the Agent's administrator-authored default supply and a neutral name. The personal agent or Coordinator may explicitly reuse another member's eligible resource under authorized related-work intent; deterministic admission never guesses relatedness or chooses an unspecified warm environment. Missing/unavailable explicit choices never fall back. A fresh Thread gets its own slot and native conversation; reading shared native files grants no conversation binding.

Remote MCP projects the same `worker-environment.*` operations through existing search, describe, guide and call, authenticated as the Token's user. It discovers published templates/resources, creates when requested, previews selection and starts ordinary Task work without an admin credential or direct NanoHost command. The semantic sequence is `worker-environment.templates`, `worker-environment.create`, `worker-environment.list`, read-only `worker-environment.select`, then `task.start` with the exact `workerStorageChoice`. The create choice uses the same creation owner at Task admission; no secondary create path or nested receipt owner is introduced. Template details use the bounded template read rather than another registry API. Selection preview reserves nothing and mutates no Thread; actual admission/reservation decides races.

## Generic Image Storage Contract

An image declares persistent mount targets through standard OCI image configuration `Volumes`. OpenKit retains the entire contents of each admitted volume, not a list of supported data kinds. Derived images inherit that declaration through `FROM`; installing a browser, upgrading Codex or adding another program requires no OpenKit storage handler. The selected immutable image and current AEP/image-supply admission pin the storage-layout expectation: family/version, target paths, numeric UID/GID and platform. An inherited image label may describe family/version, but neither that label nor matching ancestry chooses a storage association or grants access. Core supplies the association independently under current user authority.

Equal admitted layout permits reattachment of the same targets to their existing bytes. It does not certify arbitrary application file-format compatibility. A software downgrade can mount successfully and fail in the application; report that failure without deleting, reseeding, migrating or claiming rollback of the data. A changed required mount path, platform, numeric ownership or storage family is a layout conflict requiring explicit migration/new environment rather than automatic reuse. Added targets may initialize new volumes; removed targets remain retained and are not silently purged. The exact before/after volume set is part of the environment-change preview.

The current base declares `/workspace` and `/sandbox` as persistent targets and pins the sandbox UID/GID and numeric OCI `User` to `1000:1000`. Its OCI `WorkingDir` becomes `/tmp/openkit-bootstrap`, outside those targets, because pinned stock OpenShell refuses a volume masking OCI WorkingDir. The image creates that nonpersistent bootstrap directory owned by the sandbox identity with mode `0700`, because stock OpenShell performs an actual write probe on OCI WorkingDir. The compiled filesystem policy explicitly grants it read/write and uses `include_workdir: false`; immutable `/opt` remains read-only. The unary shim launch still explicitly uses `/workspace`. The existing fixed Worker bootstrap remains an image-owned executable; no label selects executable code. `/openkit` becomes a real nonpersistent directory rather than a symlink into `/sandbox`. The base-provided Python environment lives under immutable `/opt`, so retaining `/sandbox` cannot mask updated base software; user-created environments inside declared data targets remain opaque retained data. Additional derived targets must pass the same canonical absolute-path, duplicate/overlap, control-root, policy and ownership validation; no caller may bind a host path or mask `/`, immutable runtime supply, sockets, `/proc`, `/sys`, `/dev`, credential or control roots. Retained roots may contain unknown subdirectories and formats without schema checks.

Runtime adapters select their ordinary state directories inside the declared durable home rather than generated control/input roots. Integration may give each Thread a stable private working/home subtree to preserve the existing Workspace-write isolation; these subtrees are separate assigned write slots, not confidentiality boundaries within a Workspace-shared volume. That is placement of an opaque directory, not a per-runtime inventory or content migration. Live execution and sequence authority stay with the current AgentSession binding. The restricted native resume reference is retained data outside the disposable control root, stored under the proving AgentSession's `agentSessionId`; its non-secret locator and accepted digest remain on that AgentSession's durable record after close, as [AgentSession Continuity](20260704-agent_session_continuity.md) and [Worker Control Protocol](20260703-worker_control_protocol.md#harness-control-operations) define. Neither the retained reference nor its resume pair grants live execution authority. Distinct concurrently resident Threads use separate mutable worktrees. A sequential successor may reuse a predecessor worktree through an explicit selection or the same-Thread continuation selection defined under Association And Lifecycle, only after its writer is fenced and source-to-destination admission for the whole volume succeeds; compatible placement alone never makes that selection. A close invalidates that authority and stops its writers; it does not recursively delete the data directory. Native configuration is preserved while current launch policy continues to govern executable behavior. Persistence itself does not enable previously unsupported native hooks, plugins or discovery.

### Native Defaults And Private Home Placement

Each adapter places its mutable native home/state in its admitted stable Thread/runtime-private retained scope and places generated control and credential-bearing launch material in the separate ephemeral scope. Sharing an immutable default tree does not authorize assigning the same mutable native home to two Threads, sibling-session discovery or a new storage attachment. Members may read admitted shared native files, but file access does not establish a Core conversation binding or exact native resume authority.

Image-authored native defaults are ordinary runtime-native files at an image-designated source proved by that adapter's selected pin. Prefer the runtime's own separate configuration/resource layering when it supports that source and protected precedence. Otherwise initialize only a genuinely fresh native home from that source before native resource loading; the initializer creates native files, not an OpenKit profile format, package manager, migration or synchronization service.

An existing native home is never overwritten, reset, reseeded or synchronized by image-default initialization, including after image replacement or a failed open. Native layering may read the selected image's defaults without copying them into that home; authored native precedence and overrides remain effective. Absence of a source is valid when no source was designated. A designated missing, unreadable, invalid or incompatible source is a visible setup failure, not an empty-success fallback.

Initialization requires sole write ownership, no writes outside the admitted destination and validated source traversal. Freshness must be established, not inferred merely from an empty directory or missing remembered filename. Initialization must be complete before use; interrupted or partial initialization remains unadmitted and is inspected before retry without deleting or replacing existing bytes. Ordinary directory creation, staging and no-overwrite publication may implement this rule; no new durable profile registry or per-native-file retention inventory is introduced.

Image defaults supply configuration/resources, not authority to import another live home, select a saved conversation or restore platform credentials. Ordinary close retains the entire native home. A successor resumes only its exact recorded native reference after the existing predecessor fence. Missing/incompatible native data, uncertain initialization or unproved writer absence prevents the dependent start and preserves retained data for explicit correction.

The decision and its reason are recorded in [a decision record](../decisions/20260930-adapters_honor_native_configuration.md).

The [Codex](20260716-codex_worker_adapter.md), [Pi](20260716-pi_worker_adapter.md), [OpenCode](20260716-opencode_worker_adapter.md) and [DeepSeek](20260930-deepseek_worker_adapter.md) owners define their per-pin native source selection, parsing, precedence and loading boundaries. A benign native preference shadowed by an actual higher-precedence protected binding works without editing the file; an effective authority conflict refuses. Invalid required native configuration fails where the native pin parses it, while unknown additive settings retain native format semantics rather than being stripped into a reduced OpenKit format. Native loading/reloading follows proved runtime mechanics and any required successor follows existing exact-resume lifecycle; full local permission does not promise interactive UI parity or unsupported native features. Native prompt refusal/cancellation, managed-token secrecy, exact conversation selection, fixed adapter operations, cleanup and writer-fencing requirements remain unchanged.

## Association And Lifecycle

A read-only workspace collection uses the same admitted attachment as execution. NanoCore selects the storage association and work slot under current scope and audience authority. NanoHost's root-owned association metadata proves the local ref, scope, attachment generation, Sandbox identity, initialized target mapping, and local root identity only when they agree with the current live attachment. Stored metadata alone cannot prove a live attachment after restart. Collection cannot attach, initialize, repair, or select retained storage through directory discovery. Missing or conflicting proof preserves the files and refuses collection through the [data-boundary failure contract](20260801-nanohost_workspace_data_boundary.md#read-only-private-store-scan).

One durable `WorkerStorageBinding` associates an opaque `storageRef` with one admitted Sandbox sharing group. It outlives physical Sandbox/Harness/epoch/image replacement and is not a public Computer, general volume catalog or workflow. Core owns the record: storageRef, configured NanoHost/deployment, Workspace, bounded editable display name, creation attribution, exact selected template revision when applicable, verified immutable image/default evidence reference, sharing-group membership and required protected-source destination-admission evidence, admitted storage-layout identity, target-to-volume identities, revision, monotonic attachment generation with contributor Task/Goal/Thread lineage, at-most-one current attachment and a terminal purge marker. Existing Thread/AgentSession bindings reference it; exact scope and caller authorization are rechecked before use. No image digest, native container ID, filesystem discovery or `(Workspace,user)` derivation can substitute for this record. The first realization stores these associations in the existing server SQLite database and records references in current Sandbox/Thread runtime bindings. Transactional revision compare-and-set admission reserves attachment and advances its generation before dispatch; release requires exact ordinary runtime cleanup evidence. Contributor lineage and attachment generations remain available while the storageRef exists; ordinary Task/Thread cleanup cannot erase the historical audience needed for future eligibility. Association membership is not an authorization cache: current Workspace membership, credential scope, policy and protected-source destination admission must agree on every attachment. Creator and contributor identities remain attribution/provenance and independent-review inputs, never same-user eligibility locks. An uncertain external result retains the reservation until inspection or the existing wider fence supplies evidence; no second attachment is issued on timeout.

The existing AgentSession record retains the exact association and work slot admitted for that binding, as defined by AgentSession Continuity. This historical attachment fact survives physical binding deletion and identifies data without granting attachment or execution authority. WorkerStorageBinding remains the unique authority for target identities, current revision, source-admission evidence and attachment lifecycle; an AgentSession does not copy those authorities.

Image changes and successor AgentSessions retain the same association when authorized and compatible. Cross-Workspace reuse and sharing are excluded from this realization; image reuse does not imply data reuse. Within one Workspace, the Operator/Coordinator Agent SHOULD prefer suitable idle environments for related Tasks/Goals, using authorized Core Task, Goal, Thread and Artifact lineage to decide usefulness. The deterministic admission path filters current Workspace eligibility, protected-source admission, image layout, occupancy, contributor lineage and independent-adjudication separation; it does not score semantic relatedness. An independent reviewer receives separate storage from contributors whose work it adjudicates, even after those contributors close. Historical private content cannot be made public by selecting a new Thread or replacing the image.

For a same-Thread successor with an expected native resume pair, ordinary Worker admission MUST select the association and work slot recorded by the AgentSession that supplies that pair. This applies after routine capacity eviction as well as compatible environment replacement. Admission derives the selection before slot-dependent package planning and replacement effects, captures the association's current revision, and carries the exact selection through the existing selected-storage path. Omission automatically selects that exact continuation. A user may supply that same exact association and slot with its expected revision; selecting another resource does not override continuity. A failed intervening AgentSession without a native pair does not change the selected source of the retained conversation.

Continuation selection rechecks the current principal, shared-resource eligibility or the existing private association's exact source restrictions, protected-source admission, Workspace and deployment scope, RuntimeTarget, layout, independent-adjudication separation, work-slot ownership and attachment certainty. It grants no exception to predecessor fencing or the single-attachment rule. An exact compatible surviving attachment uses ordinary shared-Sandbox admission; any required replacement first proves the complete writer fence and release. Attachment elsewhere remains occupied until an authorized existing lifecycle operation proves its release.

An absent or contradictory predecessor attachment fact, missing association or retained target, revoked or unproved audience, incompatible layout, uncertain cleanup or stale expected revision refuses dependent continuation and preserves retained data. A native resume failure after valid attachment remains an explicit resume failure. No failure permits another association, an empty retained target, native-directory discovery or a fresh-conversation fallback. A known release by the same authorized replacement may supply its exact resulting revision; other revision changes require a new request. An uncertain external result retains the existing reservation or fence until the existing inspection or complete effect-domain proof resolves it, without automatic effect replay.

An explicit fresh-storage choice, a different association or a different work slot conflicts with an expected native resume pair and is refused before replacement or new storage creation. An explicit selection of the same association and slot still uses its supplied expected revision and all current admission checks. New-Thread creation and an explicitly admitted runtime switch keep their separately owned semantics; storage choice alone does not reset a Thread's native conversation.

Existing admission accepts an explicit new-environment or selected-storageRef choice, with expected association revision. A Goal card may express an exact environment preference as work intent passed to ordinary Task admission through existing Plan/card revision checks; it owns no inherited storage field, Goal pin or second selection lifecycle. Same-Thread native continuation supplies the exact predecessor selection defined above; each attachment rechecks current eligibility. When no explicit selection exists and no native resume pair is expected, admission creates a new Workspace-shared retained storageRef from manifest default supply, not an anonymous disposable volume. This can accumulate idle storage; status exposes the authorized retained associations and capacity refusal, and explicit whole-ref purge handles unreferenced data. Task completion alone never grants automatic purge. The Agent may select an eligible idle association for a new related Thread/Task/Goal even after its old Sandbox is gone. Selection intentionally makes all shared retained bytes accessible to admitted current and future members. Current resource eligibility and source-to-shared-destination admission must permit reuse; matching image or one candidate alone never grants it. Unknown, narrower or revoked required private-source admission blocks reuse rather than relying on a per-file classifier. A departed contributor or deleted shared Thread alone neither withdraws an independently admitted shared contribution nor purges its bytes. Candidate summaries expose only authorized Core identities/lineage, admitted layout, occupancy and observed availability, never host paths, raw handles, credentials or an unadmitted peek into volume contents. After admission, authorized file inspection remains ordinary Worker behavior.

Portable Workspace or Goal export clears operational retained-storage and work-slot selection rather than carrying an opaque association reference into another deployment. Import does not import execution-host attachment authority. An imported or reminted Goal starts with no operational retained-storage selection; selecting storage requires a fresh admission in its destination Workspace. Copying a historical opaque reference cannot copy its files, remap its association or authorize cross-Workspace reuse.

Replacement fences every resident writer, not only the requesting Thread. Shared concurrent placement retains separate mutable slots under existing Workspace-write isolation; explicit sequential handoff can reuse a selected prior slot. There is no new intra-Sandbox security claim, similarity service, volume browser or scheduling engine.

Creation establishes an exact scoped association before first materialization. Initialization is exclusive and no-overwrite: an empty new work slot may receive its initial exact source; a populated slot is inspected and reused under current source/access checks. Never run automatic reset/clean/clone-over-existing on a retained worktree. A different requested source or incompatible baseline returns a conflict, retaining all bytes for an explicit agent/user reconciliation. A partial first initialization remains visibly incomplete and retained; it is never admitted as a complete checkout or erased as a retry convenience.

Only one current Sandbox attachment may own a retained storage group; per-Thread writer admission within it remains governed by the existing scheduler and shared-Sandbox rules. Replacement quiesces the old writer or proves the complete previous effect domain terminated before admitting a new one. Core records admission and outcomes through existing runtime/configuration/command owners; NanoHost verifies exact local root identity and attachment, without a new operation journal. After crash, a stored attachment hint does not prove writer absence. The transport owner's explicit physical Epoch witness binds both the Sandbox incarnation and pre-effect backend attempt; normal reconnect preserves equal-Epoch state, while replacement and uncertain cleanup require a different authenticated fresh Epoch with the existing complete predecessor fence. Connection generations and readiness timestamps are not physical-absence evidence. Missing storage for an existing association, symlink/identity mismatch, conflicting scope, unproved detach and incompatible mount layout fail closed while retaining the existing files. Creation and attach must remain distinguishable so a missing mount cannot be disguised as empty successful recovery.

An authorized Worker may still modify or delete files through its ordinary granted filesystem access; lifecycle retention does not provide application undo or snapshots. Default retention has no implicit time-to-live. Admission checks available host headroom and existing resource-limit policy; a configured limit or insufficient capacity refuses admission, without an invented automatic eviction policy. Status distinguishes capacity refusal from authorization, compatibility and readiness failures. Explicit resource purge follows current deletion authority, writer fencing, restricted data/hold checks and an auditable exact target. Resource retirement, lost transport, service stop, epoch cleanup, image pruning and disk pressure cannot silently remove retained work. Resource deletion reports incomplete while unavailable execution-host storage cannot be inspected or erased. A bounded operator export includes ignored/untracked files and native data, quiesces writers for a consistent copy and preserves identity metadata separately from public reports. Deleting a Thread does not purge group volumes or another Thread's files; purge granularity is the whole storageRef and must respect every surviving reference and audience. When a private source is narrowed, deleted or revoked and its owner requires access withdrawal, fence affected shared attachment and withhold reuse unless whole-volume retention can prove protected bytes absent. An explicitly published copy follows its publication owner's retention rules rather than an inferred retroactive cascade. Do not infer safe removal by scanning filenames or hiding a Core Thread. A still-authorized existing private association continues only under its exact source restrictions; no migration broadens them. A Core-only backup declares execution-host roots absent; it cannot claim full work-environment recovery. Host loss remains unavailable unless an actual backup has been restored and re-admitted.

## Resource Lifecycle And Observable Refusals

User workload-resource mutations consume admitted supply under current resource and affected-work authority. Administrator template publication, policy changes, arbitrary builds and retained-storage purge remain technical administration. Creation and stopped metadata reserve no physical capacity; image equality never merges resources.

| Condition or operation | Required result |
| --- | --- |
| Create | Recheck current Workspace eligibility, exact enabled published template revision and admitted supply. Commit one association and receipt; return stable identity, selected supply, revision and idle/uninitialized facts. Launch no worker and require no idle host. Lost response replays that receipt. Initialization/readiness is a later observed result. |
| List/status/rename | Authorize before metadata disclosure. Rename uses current association CAS and changes no identity, requires no creator consent and derives no name from private content. Distinguish selected supply, observed attachment and readiness; stored choice is not a live probe. |
| First use | Recheck live membership, scope, source-to-shared-destination admission, exact supply, layout and current AEP. Reserve association CAS before effects. Initialize only genuinely fresh targets exactly once. Failure keeps identity, bytes and truthful reserved/unknown state. |
| Concurrent members | One retained association has at most one current writable physical attachment; concurrent members share that attachment only through an admitted group with separately owned mutable work slots. No second attachment, competing assigned writer for the same slot, or transfer from an unfenced predecessor is authorized. Full shared-volume access is not protection against deliberate sibling modification. |
| Busy or attached elsewhere | Compatible eligible Threads may join only a proved existing sharing group with distinct slots and bounded capacity. Otherwise keep accepted work queued or refuse ineligibility. First reservation CAS wins; a second Thread joins that same generation through contributor admission rather than another mount. Stale explicit revision conflicts without silent rebase. Unknown ownership cannot be replaced by timeout/preference. |
| Stop | Any active eligible member may idle-stop another member's shared realization through ordinary drain/close. Preview every affected resident binding safely. Active Turns return busy/affected-work conflict; separately authorized ordinary cancellation precedes another stop request. Retain bytes, do not cancel queued work, interrupt implicitly or add suspension. Queued work may later start it again, which the product shows. |
| Template update | Preserve established revision and image digest; show newer availability without treating freshness as revocation. A moved tag changes no pin. An older still-enabled published revision remains usable. |
| Rebuild/image adoption | Choose an exact currently published revision and preview image/layout delta plus the full affected group. Verify supply before drain. At an idle boundary, fence every old writer, advance association revision and replace/reattach compatible targets with fresh authority. Report selection/configuration separately from actual physical outcome. Start no successor Turn without separate ordinary admission. |
| Incompatible layout/native format | Keep all old targets. Added targets may initialize; removed targets remain retained. Changed family/path/ownership/platform requires separately authorized migration or a new Sandbox. Compatibility covers image, runtime, layout, network, credential exposure, sensitivity, capacity and containment independently of current membership. Actor identity remains exact execution/audit lineage rather than a cross-member compatibility veto. A membership-snapshot hash is no access cache. A2 still admits only one physical Sandbox: another selected association waits for the existing demand-driven eligible-idle retirement path, with no inactivity timer, eviction policy or completion-time promise. Match resource identity plus full compatibility in residency lookup, preview, restoration, creation and cleanup, never compatibility alone.

Deliberate writes to another member's retained tree require coordinated current write ownership, an idle/fenced slot or existing explicit handoff. A new Thread cannot steal an active slot or conversation. Slot separation prevents ordinary scheduling collisions under full Sandbox permission; it is no OS barrier to intentional sibling writes. Do not promise prevention, infer malicious intent from checksum/resume failures or repair continuity silently. Independent adjudication needs separate producer storage and suitable containment. A backend unable to prove the shared-group/slot contract serializes or refuses dependent work.

Selection/list/preview dispatch no retirement or runtime effects. Persist incoming admission/attempt ownership before effectful replacement; cleanup names the old resident and originating physical Epoch. Idle retirement requires zero active occupancy, exact clean bindings, no competing nonclosed attempts, settled operations and deletion lineage. Exact settled `session.close` refusal with `cleanup_required` may use wider retirement; unknown/queued/dispatched cleanup holds exclusion and is not replayed. Bridge close, Sandbox deletion, native-proof handoff, output/evidence/collection barriers and route revocation keep their existing order; storage release/runtime-row removal and attempt closure wait for their required proof. Same-Epoch readiness, timestamps or empty probes prove no old-writer absence, and contradictory fresh-Epoch proof refuses on cold recovery too. Incoming preparation failure cannot contaminate a healthy resident. Actual retirement failure preserves the correct resident/storage fence and the incoming Turn's truthful result rather than endless capacity deferral.

Templates have no worker-process lifecycle; publication/update/disable/recovery use configuration, candidates and settlement. Thread selection has no independent execution/retry lifecycle; commands, Thread bindings and ordinary attempts own those. ### Durable Image Settlement

An environment-preparation `image.acquire` or `image.build` result must be durable before NanoCore acknowledges it: NanoHost discards an acknowledged result, and fresh `image.inspect` cannot run while that result's response occupies its single effect-control request. Use one immutable private image-settlement row in the existing Server SQLite database. Its fields are the deterministic effect request id, the closed operation (`image.acquire` or `image.build`), authored Artifact id/version/content digest, canonical input digest, the closed success-or-failure outcome, validated image digest or exact `effect_failed` code, and creation time. Success requires the image digest and excludes the failure code; failure requires that code and excludes a digest. The request id is unique. Creation time is written once on first insert and is excluded from duplicate equality; compare request id, operation, authored lineage, input digest, outcome and image digest or failure code. The row carries no command, Dockerfile, log, credential, scheduling state, retry count or dispatch authority; it is not a pending-effect journal or second candidate registry.

The exact authenticated pending effect supplies settlement lineage. After normal transport correlation and result validation, persist that row before acknowledgment, pending-effect removal or resolution to its caller. An identical existing row is idempotent; a conflicting identity or outcome refuses acknowledgment. This small local write does not invoke image inspection, Artifact creation, audit fan-out or another external effect. It depends on neither a live source Workspace/Thread nor current administrator authority, so deletion or revocation cannot prevent settlement of an already accepted effect. A local settlement storage failure is delivery deferral, not result rejection: return the transport owner's exact empty `503`, retain the existing single pending correlation, and report `recovery_required` to the preparation caller without creating a resolved candidate. NanoHost retains and redelivers the exact already completed result on the same connection once per second until it can be durably acknowledged; it never repeats acquisition/build. During this explicit degraded state, subsequent lifecycle effects on that NanoHost wait, including new Sandbox creation, close and file-output collection. This storage failure alone must not terminate the epoch or existing Workers, even after prolonged deferral. Other worker-control, inference and capability streams retain their normal independent carriage, without a guarantee that unrelated database-dependent operations remain available. No new queue, durable retry state or command replay is introduced. Existing connection loss, identity conflicts, member failure and containment rules remain applicable; this exception does not waive those independent failures. Emit one bounded value-free deferred observation and a recovered observation through existing logs, not one event per retry; these diagnostics grant no readiness or effect authority. An administrator may separately request existing restart or decommission operations with their normal consequences; no automated timeout substitutes for that decision. Status and product responses cannot claim preparation success while persistence is deferred.

Recovery first reads the exact durable settlement. A known success permits a new authorized inspection and creation of the separately resolved Artifact; a known failure remains failed. A retained identical NanoHost result after a lost acknowledgment must be accepted against that row even after Core restart and without repeating an effect or requiring a live candidate. A contradictory result is rejected. Where neither settlement nor result exists, immutable authored lineage permits only the existing result-only recovery; it never authorizes redispatch. Surviving settlement bytes grant no access to a deleted or inaccessible candidate and cannot authorize activation. A successful configuration write, image acquisition or settlement alone establishes no mounted-environment readiness.

These minimal non-authorizing operation facts use the existing `workspace-audit` retention class at their Server responsibility home, remain outside Workspace portability, and are covered by the Server SQLite backup. The first implementation retains them without automatic collection. Future deletion requires that no live result-redelivery, replay or recovery path can reference the request id after its product owner terminalizes, and must respect any legal hold; no garbage collector is introduced here. Acceptance exercises a crash after persistence but before acknowledgment, a crash after acknowledgment but before inspection, identical and conflicting reconnect results, source deletion and token revocation during an accepted build, and local settlement-write failure with repeated delivery deferral and recovery on the same live epoch, no lifecycle poll between deferred deliveries, continued independent Worker traffic, no false success and no blind rebuild.

## Implementation Status

User-selected Workspace-shared Sandboxes and administrator template publication are accepted post-`v0.1.0-rc.1` targets awaiting implementation. The observations below qualify the pre-existing retained-environment mechanisms, not the new sharing/selection surface.

Retained whole-volume mounts, inherited layout admission, scoped storage associations and Agent-selected reuse, portable selection clearing, exact Server Agent preparation/activation CAS, private candidate recovery and durable pre-acknowledgment image settlement are implemented. NanoHost starts without Worker-image preload, supports local digest-verified import and retained-parent builds, and retains verified images under configurable capacity without automatic eviction. The physical-Epoch owner separates durable storage from live execution and supports bounded same-Epoch Worker reconnect after NanoCore restart. Focused regressions cover authorization, incompatible or missing storage, competing writers, recovery, replay and failure semantics. A1 acceptance exercises original tracked/ignored files and native runtime history across Host recovery, a completed Worker through an App-only restart, and Web/private-Agent preparation plus compatible replacement followed by successful successor tool execution and full data readback. Packaged administrator CLI replay returns the original activation result without another configuration, attachment or Task transition. These observations qualify this retained-environment chain; they do not certify every NanoHost platform, unrelated release qualification, or arbitrary native-format rollback.
