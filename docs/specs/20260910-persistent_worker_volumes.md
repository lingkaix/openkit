# Persistent Worker Volumes And Environment Replacement

## Owns

This specification owns retained Worker working files and native runtime data on the execution host, their exact scoped association, attachment and removal, initialization without overwrite, and the use of those bytes during an authorized compatible environment replacement. It also owns the bounded durable image-result settlement used only by environment preparation; the transport owner supplies authenticated carriage and correlation. It owns the concrete first Docker/OpenShell realization of the Core storage principle, not another runtime, filesystem service, public Computer entity, volume catalog or scheduler.

## Does Not Own

NanoCore owns Workspace/Thread/AgentSession, permissions, scheduling, Items, Artifacts and acceptance. The runtime and transport owner owns the Runtime Epoch and process fencing. Agent supply owns image declarations and desired setup; image acquisition/build execution and the Image Store retain their existing owner. Native adapters own runtime file schemas and exact conversation continuity. Git and object stores keep their authority. VM/microVM backends, process-memory checkpointing, live migration, multi-host replication, generic snapshots and automatic rollback are not implemented by this contract.

## Retained Bytes And Boundaries

Preserve complete admitted volumes, regardless of whether OpenKit recognizes their contents. Untracked/ignored files, project `temp/`, partial work, native conversation history, memory and configuration are illustrative, never an exhaustive set or file-type filter. No Gitignore, extension, Artifact registration or last-Turn filter defines retention. Disposable scratch and generated credentials/control/context live in separately declared locations. An ordinary Turn or AgentSession close releases execution and request-private material only; it cannot purge these roots.

Retention is not product publication. A dirty worktree owns its uncommitted work bytes, while Git owns committed versions, and Core owns accepted changes and evidence. Native files retain their cumulative Workspace/Thread/responsible-user audience; explicit related-work reuse admits the whole volume only when every source audience permits the new work to read it; native memory is not automatically Core User Memory or Workspace Knowledge. Saved runtime configuration cannot change allowed model/provider/tool/credential/network authority; adapter-generated invocation values remain governed by the current AEP. Unsupported native features remain unsupported even if their configuration files are preserved.

Persisted directories do not contain OpenKit-injected route credentials, live control endpoints, lease material or regenerated AEP packages. The launcher refreshes current bindings separately before every process launch. No file's existence authorizes a future effect. The system does not inspect or extract hidden reasoning to manufacture continuity evidence.

## Generic Image Storage Contract

An image declares persistent mount targets through standard OCI image configuration `Volumes`. OpenKit retains the entire contents of each admitted volume, not a list of supported data kinds. Derived images inherit that declaration through `FROM`; installing a browser, upgrading Codex or adding another program requires no OpenKit storage handler. The selected immutable image and current AEP/image-supply admission pin the storage-layout expectation: family/version, target paths, numeric UID/GID and platform. An inherited image label may describe family/version, but neither that label nor matching ancestry chooses a storage association or grants access. Core supplies the association independently under current user authority.

Equal admitted layout permits reattachment of the same targets to their existing bytes. It does not certify arbitrary application file-format compatibility. A software downgrade can mount successfully and fail in the application; report that failure without deleting, reseeding, migrating or claiming rollback of the data. A changed required mount path, platform, numeric ownership or storage family is a layout conflict requiring explicit migration/new environment rather than automatic reuse. Added targets may initialize new volumes; removed targets remain retained and are not silently purged. The exact before/after volume set is part of the environment-change preview.

The current base declares `/workspace` and `/sandbox` as persistent targets and pins the sandbox UID/GID and numeric OCI `User` to `1000:1000`. Its OCI `WorkingDir` becomes `/tmp/openkit-bootstrap`, outside those targets, because pinned stock OpenShell refuses a volume masking OCI WorkingDir. The image creates that nonpersistent bootstrap directory owned by the sandbox identity with mode `0700`, because stock OpenShell performs an actual write probe on OCI WorkingDir. The compiled filesystem policy explicitly grants it read/write and uses `include_workdir: false`; immutable `/opt` remains read-only. The unary shim launch still explicitly uses `/workspace`. The existing fixed Worker bootstrap remains an image-owned executable; no label selects executable code. `/openkit` becomes a real nonpersistent directory rather than a symlink into `/sandbox`. The base-provided Python environment lives under immutable `/opt`, so retaining `/sandbox` cannot mask updated base software; user-created environments inside declared data targets remain opaque retained data. Additional derived targets must pass the same canonical absolute-path, duplicate/overlap, control-root, policy and ownership validation; no caller may bind a host path or mask `/`, immutable runtime supply, sockets, `/proc`, `/sys`, `/dev`, credential or control roots. Retained roots may contain unknown subdirectories and formats without schema checks.

Runtime adapters select their ordinary state directories inside the declared durable home rather than generated control/input roots. Integration may give each Thread a stable private working/home subtree to preserve the existing Workspace-write isolation. That is placement of an opaque directory, not a per-runtime inventory or content migration. Exact handle/sequence authority stays in the current AgentSession binding outside the generic persisted tree. Distinct concurrently resident Threads use separate mutable worktrees. An explicitly selected sequential successor may reuse a predecessor worktree only after its writer is fenced and whole-volume audience admission succeeds; compatible placement alone never makes that selection. A close invalidates that authority and stops its writers; it does not recursively delete the data directory. Native configuration is preserved while current launch policy continues to govern executable behavior. Persistence itself does not enable previously unsupported native hooks, plugins or discovery.

## Association And Lifecycle

One private durable `WorkerStorageBinding` associates an opaque `storageRef` with one admitted Sandbox sharing group. It outlives Sandbox/Harness/epoch/image replacement and is not a public Computer, volume catalog or workflow. Core owns the record: storageRef, configured NanoHost/deployment, Workspace, responsible-user/audience and sharing-group membership, admitted storage-layout identity, target-to-volume identities, revision, monotonic attachment generation with contributor Task/Goal/Thread lineage, at-most-one current attachment and a terminal purge marker. Existing Thread/AgentSession bindings reference it; exact scope and caller authorization are rechecked before use. No image digest, native container ID, filesystem discovery or `(Workspace,user)` derivation can substitute for this record. The first realization stores these private associations in the existing server SQLite database and records references in current Sandbox/Thread runtime bindings. Transactional revision compare-and-set admission reserves attachment and advances its generation before dispatch; release requires exact ordinary runtime cleanup evidence. Contributor lineage and attachment generations remain available while the storageRef exists; ordinary Task/Thread cleanup cannot erase the historical audience needed for future eligibility. Association membership is not an authorization cache: current Thread visibility, membership and responsible-user trust must agree on every attachment. An uncertain external result retains the reservation until inspection or the existing wider fence supplies evidence; no second attachment is issued on timeout.

Image changes and successor AgentSessions retain the same association when authorized and compatible. Cross-Workspace reuse and sharing are excluded from this realization; image reuse does not imply data reuse. Within one Workspace, the Operator/Orchestrator Agent SHOULD prefer suitable idle environments for related Tasks/Goals, using authorized Core Task, Goal, Thread and Artifact lineage to decide usefulness. The deterministic admission path filters current Workspace/audience authorization, image layout, occupancy, contributor lineage and independent-adjudication separation; it does not score semantic relatedness. An independent reviewer receives separate storage from contributors whose work it adjudicates, even after those contributors close. Historical private content cannot be made public by selecting a new Thread or replacing the image.

Existing admission accepts an explicit new-environment or selected-storageRef choice, with expected association revision. Goal-level choices may be inherited by their child work, but each attachment rechecks current eligibility; absent an explicit choice or inherited selection, create a new retained storageRef, not an anonymous disposable volume. This can accumulate idle storage; status exposes the authorized retained associations and capacity refusal, and explicit whole-ref purge handles unreferenced data. Task completion alone never grants automatic purge. The Agent may select an eligible idle association for a new related Thread/Task/Goal even after its old Sandbox is gone. Selection intentionally makes all retained bytes accessible to that admitted work, so every contributing source audience must permit it; matching Workspace, user, image or one eligible candidate alone never grants reuse. Revoked, deleted, unknown or narrower private audience blocks reuse rather than relying on a per-file classifier. Candidate summaries expose only authorized Core identities/lineage, admitted layout, occupancy and observed availability, never host paths, raw handles, credentials or an unadmitted peek into volume contents. After admission, authorized file inspection remains ordinary Worker behavior.

Portable Workspace or Goal export clears operational retained-storage and work-slot selection rather than carrying an opaque association reference into another deployment. Import does not import execution-host attachment authority. An imported or reminted Goal starts with no operational retained-storage selection; selecting storage requires a fresh admission in its destination Workspace. Copying a historical opaque reference cannot copy its files, remap its association or authorize cross-Workspace reuse.

Replacement fences every resident writer, not only the requesting Thread. Shared concurrent placement retains separate mutable slots under existing Workspace-write isolation; explicit sequential handoff can reuse a selected prior slot. There is no new intra-Sandbox security claim, similarity service, volume browser or scheduling engine.

Creation establishes an exact scoped association before first materialization. Initialization is exclusive and no-overwrite: an empty new work slot may receive its initial exact source; a populated slot is inspected and reused under current source/access checks. Never run automatic reset/clean/clone-over-existing on a retained worktree. A different requested source or incompatible baseline returns a conflict, retaining all bytes for an explicit agent/user reconciliation. A partial first initialization remains visibly incomplete and retained; it is never admitted as a complete checkout or erased as a retry convenience.

Only one current Sandbox attachment may own a retained storage group; per-Thread writer admission within it remains governed by the existing scheduler and shared-Sandbox rules. Replacement quiesces the old writer or proves the complete previous effect domain terminated before admitting a new one. Core records admission and outcomes through existing runtime/configuration/command owners; NanoHost verifies exact local root identity and attachment, without a new operation journal. After crash, a stored attachment hint does not prove writer absence. Missing storage for an existing association, symlink/identity mismatch, conflicting scope, unproved detach and incompatible mount layout fail closed while retaining the existing files. Creation and attach must remain distinguishable so a missing mount cannot be disguised as empty successful recovery.

An authorized Worker may still modify or delete files through its ordinary granted filesystem access; lifecycle retention does not provide application undo or snapshots. Default retention has no implicit time-to-live. Admission checks available host headroom and existing resource-limit policy; a configured limit or insufficient capacity refuses admission, without an invented automatic eviction policy. Status distinguishes capacity refusal from authorization, compatibility and readiness failures. Explicit resource purge follows current deletion authority, writer fencing, restricted data/hold checks and an auditable exact target. Resource retirement, lost transport, service stop, epoch cleanup, image pruning and disk pressure cannot silently remove retained work. Resource deletion reports incomplete while unavailable execution-host storage cannot be inspected or erased. A bounded operator export includes ignored/untracked files and native data, quiesces writers for a consistent copy and preserves identity metadata separately from public reports. Deleting a Thread does not purge group volumes or another Thread's files; purge granularity is the whole storageRef and must respect every surviving reference and audience. A deleted/revoked private Thread cannot remain readable through an old attachment: fence the group and withhold reattachment pending an authorized whole-group disposition when selective erasure is unavailable. A Core-only backup declares execution-host roots absent; it cannot claim full work-environment recovery. Host loss remains unavailable unless an actual backup has been restored and re-admitted.

## First Execution-Host Realization

Use a root-owned persistent directory outside `/var/lib/openkit/nanohost` and `/run/openkit/nanohost`, which remain disposable epoch roots. The service derives all path components from validated opaque Core association identities; callers never supply host paths or arbitrary mount definitions. Store scope identity outside the worker-writable subtree and validate it on reopen. No-follow traversal, fixed roots and root-owned parent directories prevent a worker from replacing the attachment's parent or redirecting a later mount. The physical store is `/var/lib/openkit/nanohost-work`, with one root-owned association directory per opaque ref, mode-0700 root-owned parents and private identity metadata outside its worker-writable volume children, and no relation to Docker daemon metadata. Volume children use the admitted numeric ownership; callers never supply `chown` targets. Stop/fence all old writers before any detach/replacement validation.

Pinned stock OpenShell `0.0.99` supports `SandboxTemplate.driver_config.docker.mounts` and `type=bind` with its Docker driver's `enable_bind_mounts=true`. NanoHost supplies only its derived retained directory and a fixed sandbox target, with explicit read/write mode and the existing filesystem policy. The Gateway remains private and receives no arbitrary caller driver config. Do not preserve Docker daemon metadata, containers or old gateway state to retain data; fresh backend epochs remount separately retained bytes only after ordinary empty/containment readiness. Do not mount Docker sockets, NanoCore DATA_ROOT, NanoHost credentials or the image store into a Worker.

First attachment seeds each new volume from that target's contents in the exact admitted image, then atomically admits the initialized directory. Use a stopped, never-executed private-Docker seed container and bounded extraction into a new owned staging directory; no image process executes and no registry or network fallback occurs. Preserve ordinary file/directory bytes, modes and safe symlinks; reject escaping archive paths, external hardlinks, special devices and unsupported metadata before publication. A crash or incomplete extraction leaves an unavailable/incomplete association, never an apparently initialized empty volume. Initialization is tracked per target: an explicitly added target may seed once from the prepared image, while an already initialized target is never seeded again. A missing previously initialized target is an error. Seed container and staging cleanup remain under the current epoch's effect fence, separately from durable volume cleanup.

Mounting a retained work root does not overlay `/usr`, the immutable shim or the full root filesystem. Software installed into writable user/work locations remains with those locations; system software is reproduced by an exact immutable image. Runtime homes are routed by native adapters, separated by Thread and runtime family so an image update does not silently hand one runtime another runtime's state. Mount layout, ownership and OS/architecture compatibility are checked before reuse; native-format compatibility is not inferred and any runtime failure preserves bytes for a corrected image or explicitly authorized data migration.

## Credential And Control Separation

Generated AEP, Context, route secrets, process-control state and temporary Vault injection targets remain outside persistent targets. Injection planning rejects a persistent target unless its actual secret sink is a separately declared nonpersistent mount/file binding whose lifetime and cleanup are proved. It must not hide an entire runtime home behind tmpfs just to exclude one credential file. Supported adapters continue to use current Gateway-mediated/environment bindings or their existing ephemeral secret-file mechanism; unsupported persistent-file injection is rejected before the volume is mounted or any secret written. User configuration, memory and history are not discarded to achieve credential cleanup. Secret values never enter storage metadata, operation previews, audit or receipts.

## Owned Operation Surface

Reuse configuration and Task/Goal owners for execution, without a replacement daemon or parallel job lifecycle. Technical environment preparation/activation and execution-storage maintenance require the initiating user's current usable administrator authority under Permissions Core (a valid admin Token in server mode), plus current access to every target and source audience. Ordinary Workspace membership or confirmation cannot substitute; the model receives no Token secret. Routine scheduling within an already approved resource envelope retains its ordinary workload authority. The existing private administration Tools and public Skill-facing operation layer must expose the same bounded environment preparation, activation/status and whole-storageRef purge semantics. Preparation receives the exact Server Agent target and authored image declaration, returns its resolved digest/layout and impact without mounting or interrupting work, and delegates image effects to the existing NanoHost owner. Activation receives that exact prepared candidate, expected storage/configuration revision, affected group and payload-bound confirmation; current actor, Policy and effect/consumption grants are rechecked before dispatch. Status returns only owner-observed image, storage association, attachment and readiness/unknown facts, never inferred completion from a successful config write. Purge names one exact unreferenced storageRef/revision and explicit confirmation and returns definite deletion or a truthful retained/unknown result. No operation takes a caller-selected host path, raw driver config, executable command or credential. Request ids use existing command receipts and different input under one id conflicts; unknown external effects require inspection rather than blind replay. The administration entry calls those same owners in process; Desktop Skill calls their public schema projection.

The image remains `runtime.image` in the existing Server Agent manifest. The target is `{kind: 'agent', agentId}`; neither an Agent profile nor a Thread acquires a separate image override. Updating a shared Agent affects all later admissions using that Agent, across its profiles and Workspaces, and the preview must state that scope. For a task-specific environment the administrator creates or selects a distinct Agent configuration through existing configuration ownership, then selects that Agent for the work while explicitly reusing eligible storage. This operation does not automatically clone an Agent or change unrelated Agent configurations.

Expose preparation and activation at global `POST /api/app/worker-environments/prepare` and `/api/app/worker-environments/activate`; their private candidate home is not their configuration target scope. Their `configuration` names the existing configuration service's file id and exact SHA-256 `expectedRevision`; verify that the admitted file is the targeted Server Agent manifest and never accept a host path or numeric runtime-snapshot version as that CAS. Optional `replaceNow: {workspaceId, threadId, prompt}` selects current resident work for immediate replacement. Its nonempty prompt is the actual successor Turn input, displayed for the administrator to author or explicitly adopt during confirmation and bound into the candidate; the operation must not synthesize hidden user speech. Preparation derives the complete affected sharing group and exact `affectedStorage` refs/revisions from current authority, verifies every audience, and binds them into the immutable candidate and confirmation. Without `replaceNow`, the operation changes only the Agent's later admissions and its affected storage list is empty. List, select, status and purge remain Workspace-scoped operations.

Activation uses the existing configuration compare-and-swap/reload, drain/fence and ordinary Turn paths. The selected ordinary successor Turn uses the targeted Agent and rechecks compatible storage and current authority; it never resumes through a hidden Thread image setting. Configuration and host replacement are separate effect domains: a later failure does not imply that an already written manifest was rolled back. Return the exact observed configuration file revision when written, otherwise no configuration result, together with each affected storage ref, its expected revision and closed disposition `fenced`, `reattached`, `unchanged` or `unknown`. Do not return one invented environment or infer ready status from the manifest write. Every failed or uncertain stage preserves the existing records and reports its actual partial result without blind activation replay.

Preparation also returns the canonical payload-bound activation confirmation as a non-authoritative preview. Web and packaged Skill callers use the same preview after review; possession of its text grants no authority and does not bypass current candidate, configuration, audience or storage checks.

An activation request uses an ordinary private administration Turn and an initial status Item before effects. One immutable version-1 turn-output JSON Artifact retains exactly the closed activation response observed by that request; the existing command receipt points to that Artifact. Identical replay rechecks current private access and returns those historical observations, never repeats activation. A missing or inconsistent Turn, request status, result Artifact or receipt remains `recovery_required`; deletion of this evidence does not erase configuration or runtime authority. The result Artifact introduces no job lifecycle, retry authority or alternative storage owner. Activation reuses the ordinary interrupt and scheduler owners for active members and the ordinary scheduler's materialization-capacity admission and runtime drain checks before admitting the confirmed successor Turn. If those checks cannot prove replacement is currently admissible, report the observed configuration revision when written, otherwise no configuration result, together with `unchanged` or `unknown` storage disposition as supported by actual observations, without starting a speculative successor or automatically repeating the request.

The existing NanoHost transport adds three fixed single-subject operations: `image.inspect` for exact verified local image-layout facts, `storage.inspect` for exact association/attachment/capacity facts, and `storage.purge` for one fenced exact association. Their command/result carriage and unknown-result rules are owned by `docs/specs/20260802-nanohost_runtime_and_transport.md`. None lists user files, accepts a host path or creates an execution environment to inspect idle storage. Build/acquire remain the existing image operations; `sandbox.create` initializes or attaches the selected volumes and `sandbox.delete` only ends execution. Partial purge fences that ref and reports unknown rather than a definite failure or an unrelated epoch restart.

Both environment preparation and ordinary Worker materialization first make the exact image available through `image.acquire` or `image.build`, then perform read-only `image.inspect` before storage reservation or Sandbox creation. An exact local digest with `pullPolicy: never` still uses `image.acquire` to verify and import already retained Image Store content into the current backend, with no registry request or build fallback. This is necessary after a fresh empty-backend epoch; readiness alone does not establish image availability. Missing or corrupt content fails the dependent operation, preserves volumes and resident Workers, and never substitutes another digest. An activated candidate remains pinned to the resolved Artifact digest.

Environment preparation creates an immutable authored Artifact for the exact declaration, target, expected revision and bounded impact, followed by a separate immutable resolved Artifact that references the authored id/version/digest and verified outcome. Both use version 1 under the existing create-only Artifact owner and `turn-output` provenance on the administrator's private conversation Turn; no Artifact editing or version-history API is required. An artifact-reference Item presents review in that private Thread; the private administration Turn needs no Worker execution lease. Preparation may build and inspect an image while the old Worker remains active, but cannot mount its storage or apply the candidate. The resolved candidate binds the verified digest/layout and affected associations; an authored or unresolved candidate is not activatable. The human-issued activation command binds confirmation to the exact resolved Artifact id/version/digest, target and storage revisions, and affected group. Purge confirmation binds its exact storageRef and revision. The model cannot invoke these commands or supply the human decision. Reuse existing command receipt and audit semantics; there is no paused model execution to resume and no new ApprovalRequest action. No new job registry, operation Turn class or command-receipt metadata owner is introduced.

An internal preparation Tool uses its actual current administration Turn. Direct Web/Skill preparation creates one ordinary administration Turn in the selected private administration Thread, with its id derived from the exact command request id; identical input reuses that request lineage and changed input conflicts. A genuinely user-authored rationale may produce a user-message Item; a structured image declaration alone produces an ordinary status Item recording receipt, never invented user speech. The producing Turn is checked by the operation owner rather than accepted as an arbitrary caller-selected past Turn. A terminal Turn is never rewritten to append a late Artifact. If the selected administration Thread has a non-terminal Turn, direct preparation, recovery or activation returns `thread_busy` before creating a Turn or dispatching effects; the caller may use another authorized private administration Thread, or terminalize interrupted work through its existing owner before retrying. Recovery retains the original candidate source and audience checks even when its new Turn uses another private administration Thread. Recovery after terminalization requires a new ordinary administration Turn with explicit causation to the original authored candidate and request; the resolved Artifact still references that exact original authored candidate and settlement. If the original Thread or source authority is missing, candidate publication is refused while the private settlement fact remains preserved. Partial durable tuples return recovery-required rather than claimed success, and request replay does not repeat image effects. The prepare endpoint uses an explicit `mode` discriminator: `prepare` accepts the declaration and target, while `recover` accepts `recoverFrom`, the exact authored Artifact id/version/content digest, and a fresh request id distinct from the original preparation request. Repeating that recovery request with identical input reuses its lineage; changed input conflicts, and an incomplete durable tuple remains recovery-required without dispatching image effects. Recovery takes the declaration, target, original configuration SHA and affected-storage revisions from that immutable Artifact rather than rebasing them. It checks current administrator and source audience authority, resolves only an existing settlement or retained result, and never dispatches acquire/build. Its new ordinary administration Turn records the proven original request id in the initial status Item's existing `causationId`; a caller-provided causation string is not proof. The resolved Artifact's origin and mutation request id identify this recovery request while its content links the original authored Artifact. There is at most one resolved Artifact per authored Artifact, with identity derived from the authored reference: an authorized recovery returns an already existing valid resolved Artifact without creating another Turn or Artifact. A stale configuration or storage baseline remains stale and cannot activate; a different baseline requires a newly authored and reviewed candidate.

Build request identity derives from the immutable authored Artifact id/version and exact canonical input under the NanoHost transport owner. On restart, recovery reads the exact durable settlement first. Without it, authored lineage permits result-only registration, never redispatch; if no result can be recovered, the outcome remains unknown. Image inspection requires a known success digest and cannot discover a lost build or acquisition result. Administrator revocation blocks new preparation dispatch and activation, but does not prevent authenticated settlement of the already dispatched result. Candidate visibility follows the existing private Thread owner, independently of access to its target Workspace. A referrer cannot receive the administrator's candidate bytes or technical observations through an ordinary shared Item.

### Durable Image Settlement

An environment-preparation `image.acquire` or `image.build` result must be durable before NanoCore acknowledges it: NanoHost discards an acknowledged result, and fresh `image.inspect` cannot run while that result's response occupies its single effect-control request. Use one immutable private image-settlement row in the existing Server SQLite database. Its fields are the deterministic effect request id, the closed operation (`image.acquire` or `image.build`), authored Artifact id/version/content digest, canonical input digest, the closed success-or-failure outcome, validated image digest or exact `effect_failed` code, and creation time. Success requires the image digest and excludes the failure code; failure requires that code and excludes a digest. The request id is unique. Creation time is written once on first insert and is excluded from duplicate equality; compare request id, operation, authored lineage, input digest, outcome and image digest or failure code. The row carries no command, Dockerfile, log, credential, scheduling state, retry count or dispatch authority; it is not a pending-effect journal or second candidate registry.

The exact authenticated pending effect supplies settlement lineage. After normal transport correlation and result validation, persist that row before acknowledgment, pending-effect removal or resolution to its caller. An identical existing row is idempotent; a conflicting identity or outcome refuses acknowledgment. This small local write does not invoke image inspection, Artifact creation, audit fan-out or another external effect. It depends on neither a live source Workspace/Thread nor current administrator authority, so deletion or revocation cannot prevent settlement of an already accepted effect. A local settlement storage failure is delivery deferral, not result rejection: return the transport owner's exact empty `503`, retain the existing single pending correlation, and report `recovery_required` to the preparation caller without creating a resolved candidate. NanoHost retains and redelivers the exact already completed result on the same connection once per second until it can be durably acknowledged; it never repeats acquisition/build. During this explicit degraded state, subsequent lifecycle effects on that NanoHost wait, including new Sandbox creation, close and file-output collection. This storage failure alone must not terminate the epoch or existing Workers, even after prolonged deferral. Other worker-control, inference and capability streams retain their normal independent carriage, without a guarantee that unrelated database-dependent operations remain available. No new queue, durable retry state or command replay is introduced. Existing connection loss, identity conflicts, member failure and containment rules remain applicable; this exception does not waive those independent failures. Emit one bounded value-free deferred observation and a recovered observation through existing logs, not one event per retry; these diagnostics grant no readiness or effect authority. An administrator may separately request existing restart or decommission operations with their normal consequences; no automated timeout substitutes for that decision. Status and product responses cannot claim preparation success while persistence is deferred.

Recovery first reads the exact durable settlement. A known success permits a new authorized inspection and creation of the separately resolved Artifact; a known failure remains failed. A retained identical NanoHost result after a lost acknowledgment must be accepted against that row even after Core restart and without repeating an effect or requiring a live candidate. A contradictory result is rejected. Where neither settlement nor result exists, immutable authored lineage permits only the existing result-only recovery; it never authorizes redispatch. Surviving settlement bytes grant no access to a deleted or inaccessible candidate and cannot authorize activation. A successful configuration write, image acquisition or settlement alone establishes no mounted-environment readiness.

These minimal non-authorizing operation facts use the existing `workspace-audit` retention class at their Server responsibility home, remain outside Workspace portability, and are covered by the Server SQLite backup. The first implementation retains them without automatic collection. Future deletion requires that no live result-redelivery, replay or recovery path can reference the request id after its product owner terminalizes, and must respect any legal hold; no garbage collector is introduced here. Acceptance exercises a crash after persistence but before acknowledgment, a crash after acknowledgment but before inspection, identical and conflicting reconnect results, source deletion and token revocation during an accepted build, and local settlement-write failure with repeated delivery deferral and recovery on the same live epoch, no lifecycle poll between deferred deliveries, continued independent Worker traffic, no false success and no blind rebuild.

## Planned Environment Replacement

The Desktop Skill and the private administration entry use the same owned image/setup and replacement operations. Internal agents may author a candidate Dockerfile and requested environment; builds execute through existing NanoHost image operations, not an internal shell or arbitrary Docker access. Preparation and actual activation are separate observable results.

1. Resolve current actor, target Workspace/Thread scope, image/AEP candidate, current revision, retained storage association and affected resident work. Build/acquire and validate the exact candidate image using existing policy-bounded image ownership before interrupting anything.
2. Preview affected work and the exact change. Use the existing payload-bound confirmation and command identity; a changed candidate or affected-work set invalidates stale approval. No normal build request implicitly interrupts another user's work.
3. Drain affected admissions and let active work finish, or truthfully interrupt it when that consequence is explicitly authorized. Collect what can be collected and prove all old writers gone through existing Harness/Sandbox cleanup. An unknown effect is preserved as unknown, not retried by changing an image.
4. Replace the Sandbox while retaining data. Create a fresh compatible runtime with fresh control/credentials, bind the same retained storage and check exact image, files, runtime homes and execution readiness. Failure leaves data retained and no false ready/completed result.
5. Resume the logical task through an ordinary newly admitted Turn. A proven idle native conversation may be reused only through the adapter's explicit exact continuity contract. Otherwise create fresh native execution with current Core context and retained files available as data; never choose an arbitrary last session or reassign an active Turn. Old native conversations remain retained even when automatic native resume is unavailable.

An image rollback changes software only; it does not reverse changes the new image or worker already made to the volume. Automatic data migration/rollback is excluded. A migration required by a particular runtime is a separately authorized task with a quiescent backup and explicit success/failure semantics.

## NanoCore Updates And Failure

Routine NanoCore/Web updates do not restart NanoHost or erase retained roots. A healthy epoch survives bounded Core disconnects under the existing lease/reconnect owner. A local process may continue; inference, tool and control requests needing Core may pause or fail. Exact live continuation requires actual lease/identity/sequence proof. Longer outage or failed proof preserves interrupted/unknown outcomes without inventing completion or replay. Retained files survive independently of whether an active process can resume. NanoHost upgrade/failure may replace the whole epoch but cannot delete retained work as part of that effect fence.

## Observable Acceptance

- Preparation targets only the exact Server Agent manifest and binds its configuration-file SHA; a mismatched file, stale SHA or changed affected storage group cannot activate. The preview discloses all later admissions using a shared Agent; task-specific use selects a distinct Agent configuration and creates no Thread image override.
- Global preparation and activation return private authored/resolved candidates and observed configuration/per-storage dispositions through both clients. Config-only activation leaves resident work unchanged; immediate replacement uses the confirmed actual successor prompt, existing drain/fence and ordinary Turn admission. A partial host failure does not hide an already successful configuration write.
- Recovery on a terminal preparation uses a fresh ordinary Turn and proven causation, never mutates terminal history, repeats image effects or rebases the immutable baseline. Busy Threads refuse before effects; same-request retries and an already published resolved Artifact do not create duplicates.
- Activation replay returns the original immutable response without configuration, interrupt or replacement effects; changed input conflicts and missing evidence requires inspection. A busy private administration Thread refuses activation before effects. Removing the evidence Artifact leaves configuration and runtime authority intact. Possession of the canonical confirmation preview without current administrator authority cannot activate anything.
- Portable Goal export and import clear operational storage selections, so importing into a new Workspace cannot retain or remap a source Workspace storage association.

- Write tracked, untracked and ignored `temp/` files plus native conversation, memory and non-secret config bytes; prove exact contents survive normal close, same-image container replacement, compatible image replacement and a real NanoHost epoch restart.
- Prove candidate image adds an actually usable tool and reuses the same work/native data, while immutable system supply changes and no old writer remains.
- Sequential Turns and successor AgentSessions preserve required files without reset/clean; source mismatch and missing retained root produce explicit conflict/unavailable without empty replacement.
- Prove Agent-selected reuse by a new related Task/Goal after the old Sandbox is gone; no selection creates fresh storage, and an inherited Goal selection still rechecks eligibility. Current authorization and fresh credentials govern every attachment; cross-Workspace, unauthorized source audience, independent-review contamination, path traversal, symlink and competing writer attempts cannot attach the root.
- Keep separate controls for process survival, native conversation continuity and byte persistence. A file checksum does not certify live execution recovery, and a healthy service does not certify all work survived.
- Test failure before build, after drain and during replacement; preserve old bytes and truthful result/cleanup state. Disk pressure and epoch cleanup never evict retained work.
- Exercise both Web/private administration and packaged Desktop Skill entry paths against the same owned operations, with independent evidence and all original Core policies.
