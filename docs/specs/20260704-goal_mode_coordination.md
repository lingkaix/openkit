# Goal Mode Coordination

## Goal Development Freeze

Further Goal Mode development, including its storage, execution flow, and associated export structures, is frozen by the engineer pending complete product Redesign. The existing clauses preserve the prior design baseline, not authorization to complete pending Goal amendments or acceptance of the checkpoint implementation. The planning-authority and completedOutcome proposals remain deferred. Non-Goal responsibilities are unaffected. See [the engineer's decision](../decisions/20260928-goal_freeze_and_export_backup_boundary.md).

## Availability During The Agent Communication Redesign

The agent communication redesign removes the mechanisms that Goal execution depends on: the `awaiting_human` Turn status, `Turn.humanGate`, the `human-gate` worker stop, the worker `blocked/ask_user` final status, the suspended source AgentSession, and the single worker Turn per step with lower-level `remainingWorkerIterations=0`. It does not carry Goal onto pending requests or resident AgentSessions, as [the engineer decided](../decisions/20260930-goal_entry_unavailable_until_redesign.md). Until the Goal redesign:
- **Unavailable.** Goal entry (`startThreadGoal`), planning, including its planning question Gate (`createThreadGoalPlan`, `reviseThreadGoalIntent`, and `reviseThreadGoalPlan`), step (`runThreadGoalStep` and the local test supervise step), and steering submission (`submitThreadGoalSteering`) return `409 goal_mode_unavailable` before any write. They create no Turn, AgentSession, Gate, pending request, checkpoint, or scheduler admission.
- **Available.** Goal reads (`getThreadGoalSummary` and `getThreadGoalPlan`), pause, resume, plan approval, and the terminal handling of existing steering (`convertGoalSteeringToFollowUp` and `cancelGoalSteering`) stay, because they reach no removed mechanism. An operation found in implementation to reach one joins the unavailable set, and this section is amended with it.
- **Stored records.** Goal, Goal Task, Goal Review, checkpoint, and Gate records keep their current owners and read operations. This version starts from a new data root and carries no earlier-version data, as [the engineer decided](../decisions/20260930-earlier_version_data_not_carried.md). Contradictory checkpoints stay `recovery_required` and are not repaired by launching a worker.
- **Reading this specification.** The clauses below that describe worker Gates, `awaiting_human`, `Turn.humanGate`, the `human-gate` stop, `blocked/ask_user`, `waiting_for_user`, the suspended source AgentSession, and `remainingWorkerIterations=0` are the frozen design baseline for the Goal redesign. They describe no live execution path, and they are not retargeted onto pending requests.

Acceptance: each unavailable operation returns `409 goal_mode_unavailable` with no write, a read of an existing Goal returns its stored record, and pause and resume keep their receipt behavior.

## Summary

Goal Mode is the V1 mode for long-running, ambiguous, high-risk, multi-step, or multi-agent objectives. One Goal continuously incorporates authorized user intent, planning, bounded worker steps, evidence, review, and replanning until an independently verified completion proposal closes it or another owning transition blocks, aborts, fails, or pauses it. Its initial Plan and material revisions are immutable proposals approved before the affected work proceeds. This continuous process uses deterministic Goal control and bounded Goal-scoped Orchestrator Turns, not a separate Planning workflow. [Continuous Goal Intent And Plan Approval](../decisions/20260924-continuous_goal_intent_and_plan_approval.md) records the decision.

Goal Mode must not become an invisible autonomous loop. It advances through explicit plans, bounded steps, visible progress, human attention gates, evidence, and stop decisions.

## Goals / Non-goals

### Goals

- Make long-running objectives first-class and durable.
- Require an approved immutable Plan to authorize every V1 Goal worker step, while allowing a one-Task lightweight Plan when sufficient.
- Support multiple bounded worker steps, with exactly one worker per V1 step and different workers allowed across different steps.
- Keep user steering and human decisions visible and auditable.
- Preserve enough evidence to review and resume a goal after interruption.
- Permit bounded unattended progression only inside the Goal's inspectable autonomy class, budget, and completion-verification boundary.

### Non-goals

- Do not create unattended recursive self-improvement.
- Do not bypass Action Center, plan approval, permission gates, artifact review, repository readiness, or Git approval gates.
- Do not require every Goal Mode step to be planned in maximal detail upfront.
- Do not make Goal Mode a separate runtime or worker agent.
- Do not put raw adapter state, raw worker checkpoints, or backend-native task graphs into the public contract.
- Do not introduce a Goal Supervisor, ambient global Orchestrator, cross-Goal mutation owner, second scheduler, second Goal lifecycle, GoalSandbox, new isolation class, or public Goal pin field.

## Background

Goal Mode is already referenced by the AI Interface, Human Attention, worker reliability, and development loop specs. Those documents define channel projections and lower-level mechanisms, but Goal Mode itself needs a V1 contract that ties objective, plan, bounded execution, review, and recovery together.

## Decision

- Goal Mode is the built-in V1 workflow mode for objectives that exceed Chat Mode or Task Mode.
- The Goal Mode service owns durable progression and calls Workflow Coordinator for bounded routing, worker-selection, semantic worker-context, plan, and stop decisions.
- Goal Mode state is durable NanoCore state projected through thread items, App API, AI Interface, Action Center, artifacts, and evidence bundles.
- A goal may run one or more bounded worker steps; each step has an explicit stop decision before the next step starts.
- Every V1 Goal worker step requires one approved immutable Goal Plan. A low-risk single-step Goal uses the same contract with one lightweight Task rather than bypassing planning.
- Deterministic Goal control owns mechanically decidable progression, while one Goal-scoped Orchestrator Turn may make bounded semantic judgements through the role and Tool contract in `docs/specs/20260704-workflow_coordinator_internal_agent.md`.
- An Orchestrator may propose completion but cannot verify or close its own Goal; only the Goal owner may close after accepting the proposal and its independent verifier result.

## Contract / Expected Behavior

### Goal records

A `GoalRecord` must carry:

- `goalId`
- `workspaceId`
- `threadId`
- `title`
- `objective`
- `autonomyClass`
- `budget`
- `completionVerification`
- `status`
- nullable `createdByItemId`
- `currentIntentItemId`
- nullable `currentAffectedTaskIds`
- nullable `planItemId`
- nullable `pendingPlanItemId`
- nullable `currentTaskId`
- nullable `terminalStopReason`
- nullable `pendingRevision`
- nullable `nextTurnAt`
- `createdAt` and `updatedAt`

`threadId` is the Goal Main Thread addressed to the Goal-scoped Orchestrator. `currentIntentItemId` names the latest immutable objective or intent-revision Item; initially it equals `createdByItemId`. `currentAffectedTaskIds` is the Goal-owned current hold scope: null means the user did not identify unaffected work and all remaining Tasks are held, `[]` means no Task is held, and named ids hold those Tasks and their transitive dependents. It starts as `[]` and is effective only when an active approved Plan exists and that Plan's `sourceIntentItemId` differs from `GoalRecord.currentIntentItemId`; approval of a Plan bound to the current intent clears it to `[]`. No timestamp orders these authorities. `planItemId` names the active approved Plan and is null before first approval; `pendingPlanItemId` names at most one immutable candidate awaiting exact approval and is null otherwise. The two pointers may coexist after first approval so unaffected work can continue under the active Plan. `autonomyClass`, `budget`, and `completionVerification` are Goal-owned delegation fields resolved at Goal creation from the accepted handoff package. `nextTurnAt` is only the optional deterministic due-time for the next Orchestrator admission. Other Plan, human-attention, evidence, Coordinator, wake-reason, worker-execution, and terminal-time summaries are derived from their owning records; they are not duplicate `GoalRecord` fields.

Goal status values are exactly:

- `planning`
- `awaiting_plan_approval`
- `running`
- `paused`
- `awaiting_user`
- `reviewing`
- `blocked`
- `completed`
- `aborted`
- `failed`

`terminalStopReason` MUST be null in every non-terminal status. `completed`, `blocked`, `aborted`, and `failed` are terminal; they require `currentTaskId=null` and do not exit automatically or through `resume`. Outside terminal state, `currentTaskId` is null unless it names the exact Task currently `running` or `reviewing`; a `ready` Task is never current.

| Current Goal status | Permitted next status | Owning predicate |
| --- | --- | --- |
| `planning` | `awaiting_plan_approval` or `awaiting_user` | The initial immutable Goal Plan plus plan Item, or an exact planning question gate, is durable. A recoverable planner failure retains its failed Turn and leaves the Goal in `planning`. |
| `awaiting_plan_approval` | `running` | Approval of the exact pending initial Plan creates the complete Goal Task set and makes that Plan active. A pre-approval revision request or recoverable planner failure keeps the pending pointer and this status; a successful approvable revision replaces only the pending pointer. |
| `running` | `running`, `paused`, `awaiting_user`, `reviewing`, `completed`, `blocked`, `aborted`, or `failed` | The exact bounded-step, pause, gate, review, or terminal predicate in this specification is durable; `completed` additionally requires an accepted completion proposal and its independent verifier result. |
| `paused` | `running` | The exact resume command succeeds while no worker Turn is active. |
| `awaiting_user` | `planning` or `running` | The exact initial planning or worker gate owner accepts its response under the fixed destination below; no current read-model inference may choose the destination. Revision questions retain their prior Goal status and gate ownership as specified below. |
| `reviewing` | `running` or `aborted` | The Goal Task Review resolution snapshot below is durable and has been applied exactly once; completing the last Task returns the Goal to `running` for completion proposal and independent verification rather than closing it. |
| terminal | none | A new attempt requires a new Goal and request id; history is preserved. |

### Goal autonomy boundary

The Goal is the unique durable owner of `autonomyClass`, `budget`, and `completionVerification`; there is no `GoalDelegationEnvelope` or second revisioned delegation record. Objective, scope, non-goals, constraints, expected outputs, success criteria, effect permissions, capability and Vault restrictions, deployment ceilings, Plan revisions, gates, reviews, scheduling, failure, recovery, and Goal lifecycle remain with their existing owners and are not copied into these fields.

`autonomyClass` is the Goal's policy-owned class identifier naming which otherwise admitted effects may proceed unattended; the policy owner defines the closed class vocabulary, while this Goal field records the resolved choice. It can only narrow current actor, permission, capability, data, credential, approval, and effect authority and can never create, restore, or widen any permission. `budget` is the Goal's resolved ceiling tuple bounded by deployment policy; the usage and metering owners define units and record consumption, while this field owns only the ceilings and the exhaustion boundary. Budget exhaustion pauses unattended progression and requests human attention rather than granting more capacity or rewriting the work as failed. `completionVerification` is the Goal's resolved independent-verification policy naming the required verifier posture, evidence class, and any model-family, context, Harness, or Sandbox independence requirement; it never treats model confidence or Orchestrator output as verification.

The three fields are resolved when the Goal is created from the authenticated handoff package and current owners. They change only through an explicit authorized Goal command with ordinary audit lineage. `autonomyClass` may preserve or narrow existing permissions but never widen them; a `budget` change remains within deployment ceilings and grants no new effect permission; and `completionVerification` may preserve or strengthen required independence but cannot weaken it on the current Goal. Authorized objective or scope changes remain on the same Goal with retained intent history and classified Plan revision; a new Goal requires a deliberate split or independently managed outcome. These fields have no independent entity, revision log, retry queue, or recovery lifecycle beyond the Goal and command owners.

Every Plan proposal, Task dispatch or cancellation, attention request, blocked report, and completion proposal binds the exact current fields and is reauthorized by the current effect owners; neither a Tool closure nor a warm provider context is an authorization cache. A missing, stale, malformed, contradictory, over-budget, or permission-widening field tuple rejects admission before mutation. An unknown external effect remains unknown until its effect owner reconciles it, and retry uses a new command or Turn from current durable truth rather than replaying the effect blindly. Restart rereads the Goal fields and current owners and never reconstructs authority from Orchestrator memory.

Observable acceptance requires that one ordinary multi-step Goal can progress without further input only while every effect remains inside all three fields and current authority; an out-of-class effect stops at its exact Approval; budget exhaustion pauses and requests attention; missing or stale fields fail closed; a requested permission widening is rejected by its current owner; and Goal closure identifies an accepted completion proposal, an independent verifier satisfying `completionVerification`, and the evidence that the Goal owner accepted.

### Orchestrator lifecycle, wake control, and repeated-work protection

The Goal Orchestrator is one independent logical role scoped to one exact Goal per Turn. The Goal and Goal Main Thread carry its long lifetime, while each Orchestrator Turn is short and reconstructible through `docs/specs/20260813-internal_agent_runtime.md`. There is no ambient global Orchestrator, Goal Supervisor, cross-Goal owner, continuously resident model loop, or provider conversation that owns progression.

Goal creation or accepted Plan state, Task material milestones or terminal transitions, pending Worker requests, Review or human-attention decisions, accepted user commands, relevant budget or dependency changes, recovery-required or unknown outcomes, and owned due-time checks are wake conditions. Ordinary heartbeats, token streams, unchanged progress, and raw logs are not wake conditions. The Goal controller rereads current durable state after every wake and never treats an event payload as Goal truth.

Compatible wake reasons coalesce behind one nullable Goal-owned `pendingRevision`; it is a monotonically advancing marker that records another durable pass is required, not an event log or payload store. `nextTurnAt` records only an optional owned due time. The Goal Main Thread's ordinary one-active-Turn rule provides single-flight admission, so no claim record or Orchestrator lock exists. A wake arriving during an active Turn advances `pendingRevision`; settlement clears only the revision that Turn observed, and a later revision causes another safe pass rather than injection into the active model Turn. Consequential Goal and Worker commands retain their own idempotency and are never coalesced merely because their wake reasons are.

On restart, deterministic Goal control scans non-terminal Goals for a pending revision or overdue `nextTurnAt`, validates current authority, and invokes the same exact Turn-admission operation with deterministic request identity. Duplicate wake delivery is safe. Missing, stale, or contradictory wake state produces `recovery_required` or human attention and remains inspectable; it does not create a replacement Goal, infer a lost event, or activate a model from raw logs.

A deterministic watcher is the default: it inspects Task revision, expected completion, deadline, dependency, restart, pending-request, terminal, unknown, recovery, command, Review, and attention facts and admits a Turn only after a material condition exists. A fixed ten-minute model poll is permitted only as a bounded fallback when the watcher cannot supply timely activation; it may do no more than re-evaluate non-terminal Goals from the same durable fields at that interval and may activate the model only when a material wake condition remains. If the fallback cannot read or validate those owners, it leaves the Goal pending and reports typed recovery or attention instead of guessing. This fallback authorizes no generic event bus, workflow engine, fire ledger, second scheduler, recovery coordinator, or durable internal-execution transcript.

The Goal owns one repeated-work circuit breaker across Orchestrator Turns, separate from the shared loop's per-Turn fuses. It trips from inspectable durable facts in exactly four trigger classes: successive Turns consuming the same wake condition without a new Goal, Plan, Task, evidence reference, attention request, or later due time; repeated fuse outcomes at the same Goal revision; duplicate dispatch attempts; and a trigger storm with no eligible action. The breaker trips on the second occurrence of any one of those classes within the current Goal revision since the last material durable-state change or explicit authorized recovery. Neither the breaker nor the loop asks a model to judge hidden reasoning progress.

A tripped breaker leaves the Goal truthful and non-completed, stops automatic admission, and routes to the applicable pause, blocked, diagnostic, recovery-required, or human-attention owner with its observed evidence. It resets only after an explicit authorized action or a material durable-state change makes a new pass eligible. Restart preserves the tripped condition from its durable evidence; missing or contradictory breaker evidence fails closed rather than clearing it. Observable acceptance proves that fresh bounded Turns cannot bypass repeated-work detection, a breaker trip creates no Goal success or new lifecycle owner, and new material state or an authorized recovery action can resume through ordinary admission. The Goal's `pendingRevision` in this wake contract is only a wake marker; it is distinct from a pending immutable Plan candidate or an intent revision.

### Worker execution Threads and Goal Main Thread lineage

The Goal Main Thread is the conversation addressed to the Goal-scoped Orchestrator. Every concurrently scheduled Goal worker execution receives its own execution Thread in the same Workspace and its own AgentSession, even when executions share an Agent, Harness, or Sandbox. The execution Thread records the Goal-worker source and `parentThreadId` equal to the Goal Main Thread id; its Turn, AgentSession, Items, evidence, cancellation, and terminal outcome remain independent owners.

For each dispatched execution, the Goal Main Thread retains exactly one reference Item naming the execution Thread, Goal Task, and worker Turn; current status and evidence are resolved from those referenced owners. The reference Item never copies, mirrors, summarizes as authority, or reconstructs worker history inside the Goal Main Thread, and worker Items are never appended to the Main Thread. The Orchestrator inspects bounded results and evidence on demand through its Goal-scoped Tools.

The execution Thread and reference Item are created as part of the exact admitted dispatch lineage before worker execution can be acknowledged. A duplicate dispatch reuses only its already accepted lineage, while a new attempt receives a new Turn and, when it may execute independently or concurrently, a new execution Thread and AgentSession. Missing, stale, duplicated, cross-Workspace, or contradictory parent lineage, reference Item, Thread, Turn, AgentSession, Task, or command state returns `recovery_required` and starts no replacement execution. Restart follows the reference to the durable execution owners; it never rebuilds a missing worker transcript in the Goal Main Thread.

Observable acceptance proves that two concurrent Goal worker executions have different Threads and AgentSessions, both execution Threads point to the one Goal Main Thread, the Main Thread has one reference Item per execution and no worker transcript Items, and inspection or recovery reaches worker history only through the referenced execution Thread.

### Goal worker ordinary-Sandbox pin

The Goal-scoped Orchestrator remains NanoCore-hosted and MUST NOT dispatch Goal worker work through the default standby-worker selection. On the first worker-bearing admission for one Goal, NanoCore pins one compatible ordinary Sandbox to that Goal by writing the unique durable scheduling authority, the nullable `pinnedGoalId` on the existing durable NanoCore-private Sandbox placement and lifecycle projection (`SandboxRuntimeRecord`), whose semantics and lifecycle are owned by `docs/specs/20260703-runtime_scheduling_scale.md` and whose physical home is owned by `docs/specs/20260703-durable_scheduler_design.md`, and retains that Sandbox warm so later compatible Goal worker AgentSessions prefer it, reducing transfer and synchronization and avoiding repeated work caused by lost temporary state. NanoCore resolves that field before placement and then issues the existing NanoHost `session.open` and `turn.start` wires unchanged. This is a NanoCore scheduling strategy only: there is no GoalSandbox entity, no new isolation class, no NanoHost verb, no AEP or worker-control field, no user or App API field, no GoalRecord pin field, and no pin record, table, or second scheduler.

The pin names one ordinary Sandbox already owned by existing Sandbox and runtime-scheduling contracts. Goal Mode owns this pin policy and does not own Sandbox lifecycle. Warm retained state is never durable authority, permission, recovery truth, completion proof, or unique required progress. Another Goal MUST NOT co-reside on the Sandbox whose `SandboxRuntimeRecord.pinnedGoalId` names the first Goal. The second Goal MAY use another ordinary compatible Sandbox; if the one-Sandbox profile has no remaining compatible capacity, its existing scheduler admission entry stays queued for normal dispatch retry and the Goal remains non-terminal. This creates no new denial, queue, or attention state.

Creation occurs at the first worker-bearing admission, not at `goal.start`. An absent `pinnedGoalId` before that first admission, or an ordinarily released pin with no conflicting live binding or occupancy, creates a new pin on a freshly admitted compatible ordinary Sandbox through ordinary scheduling. The pin remains while the Goal is non-terminal unless ordinary lifecycle or failure forces drain or replacement. A terminal Goal releases the pin through ordinary cleanup by clearing `SandboxRuntimeRecord.pinnedGoalId`. Retry is a newly admitted worker Turn under current owners. Restart reconstructs the pin only from `SandboxRuntimeRecord.pinnedGoalId` and other NanoCore-private scheduling and binding truth, never from warm Sandbox contents, Orchestrator memory, or a public Goal field. Lost warm state costs latency only and is not a recovery dependency.

Fresh authority, AEP, context, and lease checks occur for every Turn. Strict-risk separation and `completionVerification` or adjudication independence MUST use another ordinary Sandbox when shared retained state could undermine them. Incompatibility, revocation, and cleanup uncertainty remain ordinary lifecycle selection or drain cases and MAY replace the pin through ordinary cleanup and a newly admitted compatible ordinary Sandbox. Only stale or contradictory `pinnedGoalId` that conflicts with live binding or occupancy fails closed through the existing recovery owner and remains inspectable. NanoCore MUST NOT use default standby-worker selection.

Observable acceptance proves that later compatible worker AgentSessions of the same Goal reuse the ordinary Sandbox named by `SandboxRuntimeRecord.pinnedGoalId` when it remains admissible; that another Goal is excluded from that Sandbox and either uses another ordinary compatible Sandbox or remains non-terminal with its existing scheduler admission entry queued for normal dispatch retry; that every Turn still performs fresh authority, AEP, context, and lease checks; that an absent or ordinarily released pin creates a new pin through ordinary scheduling; that only conflicting stale or contradictory pin state fails closed; that lost warm state is latency rather than recovery truth; that NanoHost `session.open` and `turn.start` stay unchanged; and that no GoalSandbox, public pin field, or new denial, queue, or attention state is introduced.

### Completion proposal and independent closure

Task completion, a Coordinator `complete` outcome, reviewer approval, Orchestrator quiescence, a local loop outcome, elapsed time, and model confidence are never Goal completion. They may establish that bounded work is ready for a completion proposal, but the Goal remains non-terminal until the closure predicate below is durable.

The primary Orchestrator submits `goal.completion.propose` with acceptance claims, exact outputs, unresolved risks, current Goal and Plan revision, and evidence references. The accepted command and its referenced owners are the completion proposal authority; no private model summary or new parallel Goal state machine is introduced. The Goal's `completionVerification` selects an independently admitted verifier that did not plan, dispatch, or produce the proposal and that satisfies every required context, objective, model-family, Harness, and Sandbox independence constraint.

The Goal owner alone may transition to `completed`, and only after it validates the accepted proposal, verifier identity and independence, verifier result, current Goal and Plan revision, autonomy and budget state, required evidence, resolved attention and recovery facts, and terminal predicate. A stale proposal, changed Plan, missing evidence, failed or unavailable verifier, independence mismatch, unresolved risk, unknown effect, or rejected claim leaves the Goal non-completed and returns typed findings to bounded Plan revision, new Task dispatch, attention, blocked reporting, retry, or a non-success terminal owner. No fallback may weaken verification or let the proposing Orchestrator verify itself.

Retry after rejection or dependency recovery is a new completion proposal and verifier attempt from current durable truth, linked to the earlier findings; it never overwrites the rejected proposal or reuses a stale verdict. Restart resumes from accepted proposal and verifier records when complete, or reports the incomplete tuple as pending or `recovery_required`; it does not ask the model whether the Goal was probably complete. Observable acceptance requires one accepted proposal and one qualifying independent verifier result for every `completed` Goal, preserves rejected and stale attempts, and proves that no other outcome can terminalize the Goal as completed.

There are exactly three `awaiting_user` producers: an initial-planning `user-input` gate, a Goal worker `user-input` gate, and a Goal worker approval gate. A revision planning question uses that same `user-input` gate owner without changing the Goal's prior status or either Plan pointer; affected work stays held by the revision fence. `turn.input.submit` owns user-input responses, while `approval.respond` owns the worker approval decision; both attach their response or decision Item to the same active Turn as required by Core protocol and briefly resume that Turn only to close its existing gate. An initial planning-question response completes the planning Turn, returns the Goal to `planning`, and requires a new `goal.plan` command with a new request id. A revision-question response completes its planning Turn, leaves the prior active and pending Plan pointers intact, and requires a new request-bound planning Turn using that exact response and predecessor; it neither approves a Plan nor releases affected work. A stale answer to a closed or superseded question gate is rejected by the gate owner. A worker user-input response completes the original worker envelope, changes the addressed Goal Task from `running` to `ready`, sets that Task's `latestGateContextItemId` to the exact response Item, leaves the Goal `running` with `currentTaskId=null`, and requires a new `goal.step` command and Turn. A granted worker approval uses the same Task and Goal destination, points to its decision Item, terminalizes the source AgentSession as `closed`, and uses the same completed Turn and checkpoint mapping. A denied worker approval instead terminalizes the Product Turn and source AgentSession as `interrupted`, aborts its checkpoint, returns the Task to `ready`, points to the denial Item, leaves the Goal `running` with `currentTaskId=null`, and requires a new `goal.step`. Protocol-level `expired`, `withdrawn`, and `superseded` statuses have no accepted producer, command, or decision Item and therefore cannot close a Goal worker gate; encountering one there is `recovery_required` until a separate contract defines its transition. None resumes the prior worker AgentSession or enters `reviewing`; later execution requires a new command, Turn, lease, and successor AgentSession.

Only an exact Core Gate may produce `awaiting_user` or write `latestGateContextItemId`. An AEP accepted raw `blocked/ask_user` final status without such a Gate is not a fourth producer and uses S05's bounded unavailable-transport fallback: NanoCore preserves the raw accepted status, finishes backend cleanup, interrupts the Product Turn with `worker_human_gate_unavailable` and its AgentSession with the same bounded message, leaves the request checkpoint at `preparing` with null stop reason and worker AgentSession id, releases only the exact matching lease as `released + needs-evidence`, and returns `409 recovery_required`. The already reserved Goal remains `running` with the addressed Task as `currentTaskId`, that Task remains `running`, and its existing nullable Gate-context pointer is unchanged. NanoCore MUST NOT create a Gate, change the Goal to `awaiting_user`, write Goal Gate context, publish a successful step receipt, offer a Gate response or retry action, resume the AgentSession, or add a recovery state from this tuple; boot preserves the checkpoint as `recovery_required` after scheduler fencing.

An acknowledged planning-gate response is the response Item, terminal planning Turn, resulting Goal state, and completed input-command receipt. An acknowledged Goal worker-gate response is the response or decision Item, its matching request Item, terminal old Turn, terminal checkpoint, resulting Goal Task with `latestGateContextItemId` naming that response or decision, resulting Goal state, and completed input or approval-command receipt. The receipt is published only after that exact tuple is durable. Exact replay under the original gate and command identity may complete only deterministic missing writes whose inputs and destination are fixed by that identity; a changed response conflicts, a competing response is `stale`, and any partial or contradictory owner tuple returns `recovery_required`. This bounded logical commit reuses the existing owners and does not authorize a gate settlement or recovery workflow.

A gate request Item is `completed` once its immutable question or approval payload is durable; waiting state belongs only to the referenced `Turn.humanGate`, the pending `ApprovalRequest` when applicable, and the absence of the matching response or decision Item. `turn.input.submit` has two strict request shapes rather than an optional mixed payload: ordinary input is `{ workspaceId, threadId, requestId, input, modelId? }`, while an exact gate response is `{ workspaceId, threadId, turnId, requestId, answers }`. A request producer rejects duplicate question ids as `400 invalid_request` before writing the request Item. `answers` is exactly `{ [questionId]: [string] }`; its keys equal every and only request Item question id, and the one array member is non-empty. V1 has no multi-select mode, so zero or multiple values, missing or extra answer keys are `400 invalid_request`, while duplicate ids or contradictory lineage already present in durable gate authority are `409 recovery_required`. A request containing any `isSecret=true` question returns `400 secret_input_not_supported` before a response Item or command write because no safe secret-answer owner exists. The response Item preserves that exact structured map. It is never flattened into one string or delegated to a runtime callback as business authority.

### Goal plan authority

One immutable app-local `GoalPlanRecord` is the complete Plan version authority before and after approval. It is keyed by the deterministic `planItemId` and carries exactly `workspaceId`, `threadId`, `goalId`, `planItemId`, nullable `predecessorPlanItemId`, `sourceIntentItemId`, nullable `sourceTaskEvidenceDigest`, `schemaVersion=1`, `planDigest`, `goalSummary`, `assumptions`, `tasks`, `taskDispositions`, `risks`, `questions`, `verificationApproach`, `createdByRequestId`, and `createdAt`. `predecessorPlanItemId` is null only for the initial Plan; `sourceTaskEvidenceDigest` is null until an approved active Plan has Task and evidence owners to snapshot. A post-approval revision's `sourceTaskEvidenceDigest` fixes the exact ordered snapshot of active-Plan Task identities and statuses, their resolved Review outcomes, and the identifiers and content digests of accepted evidence referenced at proposal time; timestamps alone cannot satisfy this fence. Approval recomputes it from those owners and rejects a mismatch. The corresponding proposal Item records reason, proposer, evidence references, current Goal autonomy fields, and exact diff against the predecessor; those are provenance and inspection facts, not a second Plan payload. Its task entries carry exactly `taskId`, `title`, `objective`, `acceptanceCriteria`, `contextBudgetTokens`, `resources`, `expectedArtifacts`, `verificationChecks`, `reviewPolicy`, `dependsOnTaskIds`, and `escalationConditions` using the bounds and value sets of the current `GoalPlanOutputSchema`. V1 `reviewPolicy.reviewers` is exactly `['human']`; `internal` and `worker` reviewers have no accepted producer or completion predicate and are rejected during Plan validation. An approvable record requires `questions=[]`; a non-empty question list creates the exact planning gate instead of an approvable record on initial planning or revision. A question result does not replace either Plan pointer. Every new immutable Plan version, including a material post-approval revision, requires approval of its exact identity and digest before affected work uses it. Routine authorized execution refinements are recorded against the active Plan and do not create a new Plan version.

`taskDispositions` is an ordered array of exactly `{ taskId, successorTaskId, reason }`, with `successorTaskId` a new Task id or null and `reason` non-empty. Before first Plan approval, including pre-approval candidate revisions, it is `[]`. For a post-approval successor, it contains exactly one entry for each non-completed Task of the active approved Plan at proposal time in that Plan's Task order, with no duplicate `taskId`; no completed Task receives an entry. Each `taskId` resolves to that active Plan, and each non-null `successorTaskId` resolves to a Task in the proposed Plan. Null explicitly ends that predecessor work; a non-null target carries it into the named new Task, and several predecessor Tasks may converge on one successor. The proposed Plan's Task ids remain unique against approved Goal Task rows. The full Plan read and approval projection show these entries alongside the new Task list, so a user approves the exact remaining-work disposition. Missing, extra, stale, foreign, duplicate, empty-reason, or invalid-target entries reject the proposal before it becomes approvable; approval rechecks the exact source Task snapshot and disposition set.

`planDigest` is `sha256:` plus 64 lowercase hexadecimal digits over the UTF-8 JSON of only `schemaVersion`, `goalSummary`, `assumptions`, `tasks`, `taskDispositions`, `risks`, `questions`, and `verificationApproach`, with object keys recursively sorted lexicographically, array order preserved, and no insignificant whitespace or Unicode normalization. Workspace, Thread, Goal, Item, request, and timestamp lineage is verified separately and does not enter the digest.

Workspace export reads Goal, active and historical Goal Plan, and Goal Task rows from one SQLite snapshot and carries every Goal Plan record before its Goal Task rows. Import first validates each source Plan digest, builds the canonical Task-id map from the ordered union of Plan Task ids and Goal Task and dependency ids so Plan-only Tasks are not lost, and remints Workspace, Thread, Goal, Plan Item, predecessor Plan Item, source intent Item, current intent Item, affected Task, Task, dependency, Item-resource, and Artifact-resource identities through the same canonical maps used by their owning records; Knowledge and repository resource ids, file references, external references, reasons, request lineage, array order, and timestamps remain unchanged. It preserves null versus empty `currentAffectedTaskIds`, remints both `taskDispositions.taskId` and non-null `successorTaskId` through the canonical Task map, and validates every named affected or disposition Task against the imported Goal. Imported `createdByRequestId` is historical provenance and is validated only as a stored non-empty identifier because the source command ledger is intentionally not portable; it need not resolve to a local command row. Import then recomputes `planDigest` only after the exact reminted payload is complete and applies the same Plan validation before inserting the new immutable record. It preserves a post-approval candidate's original `sourceTaskEvidenceDigest` as historical proposal evidence rather than recomputing it from possibly changed Task truth. Because import remints source identities, that candidate is not approval-eligible in the imported Workspace: approval returns `stale`, and an explicit new request redrafts from imported current truth. A candidate drafted before first approval has a null source Task snapshot and remains eligible subject to its other exact approval predicates. Goal Task import remints its `planItemId`, Task and dependency ids, Item or Artifact resource references, and nullable `latestGateContextItemId` under the same rule, then verifies the immutable Task payload against that exact Plan and verifies that a non-null Gate pointer resolves to one valid matching request/response pair in the Task's Workspace and Thread. Duplicate rows, Plan and Task incoherence, missing mappings, malformed records, or a digest that did not match the exported pre-remint payload fail import rather than dropping the Plan, repairing a Task, or falling back to its lightweight Item.

The protocol `plan` Item with the same `planItemId` remains a lightweight user-visible proposal snapshot containing title, summary, and step ids and titles with proposal-time `pending` status; it is not the full Plan payload, approval authority, or live Goal Task projection. Current Task status is read only from `GoalTaskRecord`. For a successor, the Item summary signals changed predecessor work and the approval surface renders the exact digest-bound `taskDispositions` from the full Plan read, not from that summary. A revision request retains the active approved Plan and any prior candidate until an exact successor is durably proposed or the candidate is approved. One pending candidate at a time uses the Goal's `pendingPlanItemId`; successful planning replaces that pointer and preserves prior immutable Plan records and Items. A revision planner Turn is admitted by its request-bound instruction Item against the exact predecessor, not by changing the Goal to `planning`. The instruction Item has `type: 'user-message'`, `parentItemId` naming the predecessor Plan Item when present, and `causationId` naming the request. A missing instruction Item is a silent drop and is forbidden. A concurrent revision against a different predecessor is `stale`; a second unresolved revision request against the same candidate fails closed until the first reaches a terminal result or its question gate is answered. No separate Plan status machine or settlement record is added.

A recoverable planner failure or rejected planner output retains the exact failed planning Turn and its admitted input and output, leaves the Goal non-terminal, and keeps both Plan pointers unchanged. This applies to initial planning and revision; a failed attempt is neither an approvable Plan nor proof that the Goal itself failed. With no initial Plan, the Goal remains `planning`; with a pending initial Plan, it remains `awaiting_plan_approval`; after first approval, the Goal retains its prior non-terminal status. [A Failed Plan Revision Keeps The Goal Alive](../decisions/20260921-plan_revision_failure_keeps_goal.md) remains the narrower revision precedent. A failed revision does not revoke the previous approvable candidate or active approved Plan. A distinct new request may retry planning from current durable truth. The same request finds the request-derived terminal failed Turn and returns `recovery_required` before another model call. An incomplete, contradictory, or ambiguous Turn, Item, Plan, pointer, or request tuple also returns `recovery_required`; a successful-result reader returning no new Plan for an exact terminal failure does not authorize rerunning that request. Restart retains these facts and never infers a Plan from an orphan Item or model memory.

For a revision, the immutable instruction Item on its completed request Turn and the separate failed planner Turn with retained model input and output form the complete failed-attempt lineage; no copied instruction Item or invented failure Item on the planner Turn is required. The Plan read surface derives one exact `planningAction` from durable Goal, Plan, Turn, Item, and Gate owners: `create` only for pristine initial planning, `draft_revision` for an admitted instruction still awaiting its first planner attempt, `retry` after a terminal failed planner Turn, `answer_question` for the exact open planning Gate, `continue_planning` when the latest planning-question Turn has completed with its exact response Item and no successor planning Turn has consumed that response, `await_approval` for an approvable pending candidate, `in_progress` when the latest request-derived planning Turn after the current instruction is non-terminal and has no human Gate, and `none` when an active approved Plan has no pending candidate, instruction, question, or failed attempt, or the Goal is terminal. A revision draft action names the exact instruction Item and request lineage. `continue_planning` names the exact response Item and requires a new planning request id; it takes precedence over an older approvable candidate until that answer is consumed by a successor Turn. A client may automatically create only the pristine initial draft; it offers an explicit new-request retry after failure and never treats absence of a successful Plan as proof that no attempt occurred. A missing or contradictory source tuple projects `recovery_required`, not an eligible action.

Plan creation uses one bounded cross-store compromise: it completes the visible plan Item first, then atomically inserts the immutable Goal Plan record and updates `pendingPlanItemId` in one Workspace transaction. If that Workspace transaction fails, the request fails and both Plan pointers retain their prior values; the orphan Item is a non-authoritative projection and neither approval nor recovery may treat it as Plan authority. No compensation record or settlement workflow is added.

Plan approval accepts only the exact `pendingPlanItemId`, loads that immutable record server-side, verifies its digest and current predecessor, and rejects duplicate or Goal-historical task ids, missing or self dependencies, and dependency cycles as `goal_plan_invalid` before Goal, Goal Task, or command mutation. The Task id namespace spans approved Goal Task rows, not unapproved candidate drafts, so a post-approval successor cannot overwrite or impersonate historical Task evidence; pre-approval candidate revisions may retain local Task ids because no Goal Task rows exist yet. A post-approval successor explicitly lists the remaining work it will authorize as new Task ids. Its digest-bound `taskDispositions` identifies each unfinished predecessor Task whose work is carried into a new Task or deliberately ended, with the reason; the proposal diff names completed predecessor results as authorized resources or evidence where they remain relevant, or explicitly explains their exclusion. If the successor intentionally repeats a completed predecessor's work, the proposal diff says so and the user approves that repetition as part of the exact new work; no automatic semantic comparison of Task text is approval authority. A successor Task may depend only on Tasks in its own Plan graph; completed predecessor results enter through resource and evidence references, not cross-Plan dependency edges. The user approves this exact successor work and disposition, so activation cannot silently discard unfinished or newly completed work.

When a successor Task relies on a completed predecessor result, Goal Mode resolves the named authorized Item or Artifact evidence into that Task's prepared context and requires the Context Package owner's exact materialization and delivery proof before worker execution. A Plan resource declaration or proposal diff alone does not supply those bytes. Missing, denied, stale, or undeliverable evidence blocks that dispatch through its existing context or attention owner; no automatic semantic duplicate-work classifier is inferred from the Plan text.

At a safe point, one Workspace transaction creates the complete ordered Goal Task snapshots for the approved Plan, changes `planItemId` to that exact Plan, clears `pendingPlanItemId`, and changes the initial Goal to `running` with `currentTaskId=null`; post-approval activation preserves the Goal's valid non-terminal lifecycle. Tasks from superseded Plans remain historical with their last truthful statuses and cannot be selected for new dispatch. Active Task counts, dependency progression, stop decisions, and completion claims use only Tasks of the active approved Plan; read models distinguish superseded history from remaining active work.

Each new Task receives `orderIndex` from its zero-based position in the immutable plan array; a Task with no dependencies starts `ready`, while every other Task starts `pending`. A `GoalTaskRecord` is the sole post-approval task-graph and execution-snapshot owner and carries exactly `taskId`, `workspaceId`, `threadId`, `goalId`, `planItemId`, `status`, `title`, `objective`, `orderIndex`, `dependsOnTaskIds`, `acceptanceCriteria`, `contextBudgetTokens`, `resources`, `expectedArtifacts`, `verificationChecks`, `reviewPolicy`, `escalationConditions`, nullable `latestGateContextItemId`, `createdAt`, and `updatedAt`. Planned facts remain immutable; only status, `latestGateContextItemId`, and `updatedAt` may change. The Gate pointer starts null, changes only in the exact worker-gate closeout transaction above, remains sticky across later attempts and interruption, is replaced only by a newer valid Gate response for the same Task, and returns to null when the Task becomes terminal. It is owner and recovery lineage, not a public Goal Task response field; clients read the referenced Items from Thread history. Task status is exactly `pending`, `ready`, `running`, `reviewing`, `completed`, `blocked`, or `failed`; `skipped` and `needs_revision` are not V1 states because neither has a complete producer, successor, and completion predicate.

Before reserving a ready Task, `goal.step` resolves a non-null `latestGateContextItemId` to exactly one completed `user-input-response` or `approval-decision` Item and its unique completed matching request Item on the same prior worker Turn. The Task pointer is the durable Task-to-Gate association written only by the validated closeout transaction; the two Items must share the Task's Workspace and Thread, share one Turn, and agree on their user-input or Approval request identity and accepted decision owner. Absence, ambiguity, inconsistent Item lineage, or a protocol-only Approval status is `recovery_required` before mutation. The Goal service passes the request and response Item refs in canonical Thread Item order immediately after the mandatory Workspace and Thread refs and before other prepared context refs. Both refs appear in the structured worker request and the accepted S39 trace. V1 deliberately keeps only the latest Gate pair as a bounded sticky compromise; older Items remain immutable Thread history but are not guaranteed automatic reinjection after a newer Gate response.

Approval copies every Plan task field exactly once into its Goal Task snapshot. A Goal worker request then uses the following lossless mapping; no other Goal Task field enters the semantic request:

| Immutable Goal Task fact | Exact worker-request use |
| --- | --- |
| `objective` | `objective` |
| `acceptanceCriteria` | `acceptanceCriteria` |
| `resources` | `resources`, preserving every declaration and its order; these declarations do not grant access or prove material delivery |
| `expectedArtifacts` | `expectedArtifacts` |
| `contextBudgetTokens` | `constraints.maxContextTokens` |
| mode boundary | `constraints.maxWorkerIterations=1` |
| `verificationChecks` | `verification` |
| `reviewPolicy` | `reviewPolicy` |
| `escalationConditions` | `escalationConditions`, preserving all entries without renaming, truncation, or conversion to stop conditions |
| valid `latestGateContextItemId` pair | the matching request and response or decision Items as the first prepared Item `contextRefs` after Workspace and Thread |
| latest eligible resolved Review | nullable `reviewContext` under the exact Review rule below |
| `planItemId`, `taskId`, `title`, `orderIndex`, `dependsOnTaskIds`, `status`, the Gate pointer itself, and timestamps | excluded as lineage, display, graph, lifecycle, or audit fields |

`contextRefs` remain separately authorized and delivered Workspace, Thread, Item, Artifact, or Knowledge owners; Plan resource declarations neither replace those references nor claim that their material was delivered. The exact approved-Plan lineage predicate is `task.planItemId === goal.planItemId` with both values non-null; the step does not reread Plan content after approval because the Goal Task is then authority. A selected Goal Task with missing, malformed, mismatched lineage, otherwise incomplete immutable request facts, or an invalid latest Gate Item pair returns `recovery_required` before Goal, Task, checkpoint, Turn, Item, or scheduler mutation. The service must not repair that state with defaults, the immutable Plan, the lightweight Plan Item, a caller payload, or a current projection. Before first delivery, deterministic recomposition requires the same immutable Goal Task, latest Gate pair when present, eligible Review, and exact owning Context Package trace; while that Worker Context Package trace is absent, a crash before the Turn-owned Item returns `recovery_required` rather than repeating mutable context selection. After delivery, replay reads the existing Turn-owned `user-message` bytes and never recomposes them from current context.

The immutable Goal Task review policy owns post-step review. `required=true` creates the existing human Goal Review and `required=false` skips it while still applying the accepted stop and dependency transition. `goal.step` has no review-policy override; changing review policy before approval requires Plan revision, while changing an approved Task policy requires a new classified Plan revision activated at a safe point. A change that weakens Goal completion verification or expands the mandate cannot be disguised as a Task-policy revision.

| Current Goal Task status | Permitted next status | Owning predicate |
| --- | --- | --- |
| `pending` | `ready` | Every named dependency is durably `completed`. |
| `ready` | `running` | One exact worker Turn and checkpoint reservation for the Task are durable under the accepted `goal.step` command. |
| `running` | `reviewing`, `completed`, `blocked`, `failed`, or bounded-continuation `ready` | The exact worker Turn, evidence, Coordinator outcome, and review policy satisfy the matching bounded-step predicate below. `ready` is permitted only when the exact worker user-input response or approval decision closes the original envelope, or after scheduler and worker-control authority terminalizes the original execution as interrupted, the reconnect window ends, and an explicit retry command is accepted. Both paths preserve the old Turn, evidence, gate decision when applicable, and checkpoint history; the next attempt uses a new Turn and request id. |
| `reviewing` | `completed`, `ready`, or `failed` | The resolved Goal Review snapshot maps `accept` to `completed`, `refine` or `retry` to `ready`, and `abort` to `failed`. A refined or retried step uses a new Turn and request id and retains the prior Turn, evidence, and Review. |
| terminal | none | `completed`, `blocked`, and `failed` remain historical facts; retry or refinement creates a new attempt from the explicit review transition rather than rewriting the old Turn. |

The V1 Goal Review verdict set is exactly `accept`, `refine`, `retry`, and `abort`. `ask_user` belongs to the worker or Coordinator gate path before review resolution, `decompose` is a Plan revision or deliberate Goal split rather than a Review verdict, and a human `block` has no truthful worker `StopReason`. A reviewer who wants corrections uses `refine`, while an explicit terminal rejection uses `abort`. `refine` and `retry` keep the Task identity, use a new Turn and request id, and require the next Coordinator worker request to carry the resolved Review id, reason, original Turn id, and evidence references. Retry reuses the original objective, acceptance criteria, and constraints plus that failure context; refinement additionally carries the Review's explicit revision instruction. Neither overwrites the prior attempt.

The interrupted-worker branch of `running -> ready` uses only the eligibility and `worker.recovery.retry` command contract in `docs/specs/20260531-worker_turn_reliability_envelope.md`. Timeout ownership, checkpoint presence, or a failed reconnect request is insufficient. The accepted command leaves the already interrupted Turn unchanged, atomically changes this exact Task to `ready`, changes its Goal to `running` with `currentTaskId=null`, writes its bounded receipt, and starts no replacement; the next `goal.step` owns the new Turn, admission, lease, and worker attempt.

For a selected ready Task, the Goal service reads the Task's Reviews in their existing deterministic `createdAt, reviewId` order and inspects only the latest record. No Review means an initial or non-Review continuation and produces `reviewContext=null`. A latest coherently resolved `refine` or `retry` Review is eligible only when its immutable snapshot has the same Task in `ready`, the same Goal in `running` with `currentTaskId=null` and no terminal reason, `nextReadyTaskId` equal to the selected Task, and `outcome` equal to the verdict. The exact nested request context is `{ reviewId, verdict, reason, revisionInstruction, priorTurnId, evidence: { itemIds, artifactIds } }`; it copies no mutable Goal or Task projection and no verification-evidence text. An unresolved, partially resolved, mismatched, accepted, or aborted latest Review beside a selected ready Task is contradictory and returns `recovery_required` before Task, Goal, checkpoint, Turn, or scheduler mutation.

V1 deliberately uses a sticky latest-Review compromise instead of adding a consumed marker or attempt-lineage record. The eligible `refine` or `retry` context remains on later attempts of the same Task until a newer Review supersedes it or the Task becomes terminal. This preserves the human correction across an interrupted or explicitly retried continuation and accepts that the context may be repeated; a future one-shot rule requires a separately accepted owner and is not authorized by this contract.

### Planning and intent revision

Planning is an activity throughout one Goal, not a separate workflow or lifecycle. Goal creation, new evidence, user input, Task results, Gate and Review outcomes, and changed dependencies may lead to clarification, research, an initial Plan, an execution refinement, or a revised Plan. The initial `planning` status means that no Plan has yet been approved; planning can continue while the Goal is `running`. Before the first Plan, research may use admitted internal Tools or an explicitly approved lightweight research Plan; Goal creation alone authorizes no worker-level research. A bounded low-risk objective may use a one-Task lightweight Plan. Planning needs enough detail for the next approval and safe execution, not a complete prediction of all later work.

`goal.intent.revise` accepts the exact new `objective`, the user's `revision` instruction, and optional `affectedTaskIds`. It records the change as one immutable readable `user-message` Item with exact actor, request, predecessor, and revision identity; the Item text explains the new objective, instruction, and affected-work scope for historical inspection. Its `parentItemId` names the preceding `currentIntentItemId`, while `causationId` names the command request. The same accepted logical command updates `GoalRecord.objective`, `currentIntentItemId`, and `currentAffectedTaskIds`; those Goal fields are current objective and hold authority, and the Item is immutable user-intent history. Every proposed Plan binds the exact intent Item it addresses. A Task remains bound through its immutable approved Plan to the intent under which it was admitted. The user's explicit instruction authorizes that requested intent change itself; derived method, cost, time, data, permission, risk, or external effects still require their owning decisions. A new Goal is created only when the user deliberately splits or independently manages the outcome.

The revision command accepts optional `affectedTaskIds`. An explicit empty list states that all remaining approved work still satisfies the revised intent; omitted scope conservatively holds all remaining work; named Task ids hold those Tasks and their transitive dependents. A stale, foreign, terminal, or contradictory Task scope fails before mutation. A held Task cannot receive a new Turn under the old Plan. A running affected Turn remains pinned to its admitted Plan and Context Package while its existing cancellation or interruption owner brings it to a safe point; stop, revocation, and narrowed authorization take effect immediately through those owners rather than waiting for Plan approval. Unaffected work that remains valid and authorized may continue, and may complete, while a candidate Plan is pending. The Goal owner reassesses the affected set after each material state change and before every dispatch; uncertainty holds the affected work and requests clarification. No new queued-intent owner or in-flight context rewrite is admitted.

Every V1 worker step requires the active approved immutable Plan and current authorization. Plan assumptions, bounded Task snapshots, expected Artifacts, verification checks, per-Task review policy, escalation conditions, risks, and verification approach make the executable Plan explicit without hiding additional scope, non-goals, approval points, or stop conditions in prose. An optional editorial review may improve Plan wording or presentation, but it is not execution authority. Every new immutable Plan version, initial or revised, requires explicit approval of its exact version before affected worker execution. An authorized execution refinement within the current Plan is recorded with reason and evidence but creates no new Plan version or approval gate.

An approvable `pendingPlanItemId` creates the existing exact Plan approval attention request. Goal readback and Action Center show the pending Plan identity, predecessor, diff, affected-work hold, and approval action separately from the active approved Plan, including when the Goal remains `running` and unaffected work continues. `awaiting_plan_approval` remains the initial pre-approval Goal status; a post-approval candidate does not change `running` into an unowned lifecycle status. A pending candidate with unresolved questions is not approvable, and an unanswered question remains visible through its exact user-input Gate. When all remaining work is held, the Goal and attention read models explain that execution waits for the pending Plan decision or a new user instruction rather than displaying an idle running Goal.

### Plan revision classification

Every accepted Plan remains immutable. A proposed new version links to its predecessor, source intent Item, reason, proposer, evidence, exact diff, current Goal autonomy fields, and the exact Task and evidence source snapshot used to prepare it. Those revision facts are retained with the existing Plan proposal and Thread Item owners; they are not a second Plan authority. The Goal owner selects at most one pending candidate and one active approved version. A model Turn, provider-native conversation, current Task projection, or mutable Plan Item cannot replace that authority.

An **execution refinement** changes only a worker choice, retry, ordering, decomposition detail, or implementation technique already permitted by the exact approved Plan and current owners. It cannot change a Plan-bound Task fact or a previously approved commitment. The Orchestrator may record its reason, evidence, and current Plan identity and proceed when every current owner and autonomy field admits it. A change to the objective, included scope, deliverables, non-goals, constraints, effect or permission boundary, budget or time commitment, success or acceptance criteria, output audience, important architecture or method, risk posture, or verification rule is material and requires a new exact Plan proposal and approval. Materiality can arise without a textual change to budget or acceptance fields. A known authorized intent change does not grant its derived effects. Uncertainty is gated for approval rather than classified as a refinement; no automatic importance score or separate policy engine is required.

An applied execution refinement is recorded in an existing Goal Main Thread `status` Item. Its `summary` names the active Plan, selected Task, reason, evidence Item and Artifact ids, and exact bounded changed action in readable text; this Item projects the accepted step command and is not separate authority. The existing `goal.step` input may carry optional `refinement` with exactly `activePlanItemId`, `taskId`, `reason`, `evidenceItemIds`, `evidenceArtifactIds`, and `changedAction`. Goal control validates that the Plan and selected ready Task still match, each evidence reference is current and visible to the permitted audience, and the action stays within the approved Plan, Task facts, autonomy fields, and effect owners. It writes the Item after exact Task reservation and before worker launch is acknowledged; an incomplete cross-store tuple remains `recovery_required` and the Item alone cannot authorize execution. A Review retry or refine uses its existing immutable Review reason and evidence and the next dispatch path, without a duplicate refinement payload. If no existing action can record and apply the refinement, it remains a proposal. No ninth Orchestrator Tool, parallel refinement record, or permission grant is added.

Plan activation occurs only at a safe point. A running Worker Turn remains bound to the Plan revision and Context Package admitted at its start; a replacement affects only later Turns unless the existing Task is explicitly cancelled through its owner and a new attempt is admitted. Approval compares the proposed predecessor, source intent revision, Goal autonomy fields, and exact source Task and evidence snapshot against current durable truth. If unaffected work completed or its evidence changed after the proposal, the candidate is stale and must be redrafted from the new facts; approval cannot silently discard that progress. Approval also rejects an incompatible active Turn and any held Task whose cancellation has not reached its safe point. Superseded Plan revisions, Tasks, Turns, evidence, and cancellation outcomes remain visible and causally linked.

A stale predecessor or source snapshot, concurrent accepted revision, missing exact diff, absent evidence, incompatible active Turn, policy conflict, permission widening, or unavailable dependency rejects or gates the proposal before activation. Retry creates another immutable proposal from current Goal truth. Restart resolves the active revision, pending candidate, affected-work hold, and source snapshot from durable Goal, Plan, Item, Task, and evidence owners, never from Orchestrator memory. Observable acceptance requires that a dependency failure can yield a visible execution refinement; changed objective, scope, deliverables, budget, audience, important method, risk, or weaker verification cannot masquerade as refinement; every Task names its authorizing Plan and source intent; and historical inspection reconstructs why each version became active.

### Bounded steps

- Each Goal Mode step is a bounded work unit selected by Workflow Coordinator.
- Each V1 step calls exactly one worker agent. A later step may select a different worker, but multiple workers inside one step require a separately accepted graph or recipe contract and are not authorized here.
- Each step must produce exactly one Coordinator stop outcome: `continue`, `review`, `ask_user`, `block`, `abort`, or `complete`, with the matching `shouldStop` and protocol `StopReason` defined by S15.
- Approval, retry, handoff, and pause are separate Goal service gates or commands after that decision; they are not additional Coordinator stop outcomes. Worker failure maps through the typed StopReason and the six-value Coordinator decision rather than adding a `fail` outcome.
- A new step must not start while a required human gate is unresolved.

No separate durable stop-decision row is permitted. The accepted Coordinator response is a projection over the exact worker Turn, checkpoint or terminal evidence, Goal Task, Goal, and Goal Review owners below:

| Outcome | Durable acceptance predicate |
| --- | --- |
| `continue` | The addressed worker Turn and evidence are complete, the addressed Goal Task is `completed`, at least one other Task of the active approved Plan remains incomplete, and the Goal is `running` with `currentTaskId=null` and no terminal StopReason. Every pending Task whose dependencies are now completed is `ready`, but the next command has not selected one. |
| `review` | The worker Turn is complete, the Goal Task and Goal are `reviewing`, and one unresolved Goal Review names the same Goal, task, Turn, Item evidence, and Artifact evidence. |
| `ask_user` | The worker Turn is `awaiting_human` on its exact user-input or approval gate, the Goal Task remains `running`, and the Goal is `awaiting_user` with `terminalStopReason=null`; the worker Turn and Coordinator response retain the non-terminal `ask_user` reason. |
| `block` | The Goal Task is `failed` and the Goal is `failed` when `stopReason=error`; otherwise the Goal Task and Goal are `blocked`. `currentTaskId=null` and `terminalStopReason` equals the exact worker StopReason. |
| `abort` | The Goal Task is `failed`, the Goal is `aborted` with `currentTaskId=null`, and `terminalStopReason=aborted`. |
| `complete` | Every Task of the active approved Plan, including the addressed Goal Task, is `completed`, while the Goal remains `running` with `currentTaskId=null` and `terminalStopReason=null` until an accepted `goal.completion.propose` and its independent verifier satisfy the closure predicate. |

The Goal service MUST run one worker Turn per V1 step with lower-level `remainingWorkerIterations=0`. It computes `hasOtherIncompleteTasksAfterAddressedTaskCompletion` only from Tasks of the active approved Plan by excluding the addressed Task and treating its accepted completion as completed, then obtains the Coordinator decision from that pre-mutation summary. The worker Turn, terminal evidence, and checkpoint are already-durable preconditions; the Workspace database applies the matching Goal, addressed Goal Task, Goal Review, current-task, and terminal-reason tuple and unlocks every pending Task whose dependencies are completed in one transaction. A Coordinator `complete` outcome completes only the bounded Task set and leaves the Goal eligible for a later completion proposal; it cannot write Goal `completed`. Together those writes form one acknowledged logical commit, not a cross-store transaction or settlement protocol. Physical crash consistency between storage owners remains C09's responsibility.

A lower-level `continue` is invalid for this V1 path and returns `goal_stop_decision_invalid` before the Workspace transaction, command receipt, checkpoint clear, or next-step mutation; the already durable worker Turn, checkpoint, and evidence remain unchanged. Restart and exact-request replay derive the same response from those owners and MUST NOT create another Review, Task transition, or stop-decision record. A partial or contradictory owner tuple returns `recovery_required` and leaves the checkpoint uncleared; it MUST NOT be repaired from the latest read model or Coordinator process memory. A projection, response-serialization, checkpoint-cleanup, or post-worker owner-commit failure also returns `recovery_required` without rewriting the Goal to `failed`; only an authoritative worker `stopReason=error` may apply the `failed` outcome above.

### Goal command identity and replay

Every Goal mutation requires `requestId`. Command identity is the command name, authenticated actor id, Workspace id, Thread id, and request id. NanoCore hashes only the canonical caller-supplied path and body shown below; a current Goal, selected Task, default title, generated plan, Coordinator decision, or read projection resolved during execution is an output and MUST NOT enter the input hash.

| Command | Canonical caller input after path scope | Successful replay owner |
| --- | --- | --- |
| `goal.start` | `objective` and optional `title` | Original `goalId`, objective Turn, objective Item, and Goal read resource. |
| `goal.plan` | No semantic body | Original `goalId` and Goal read resource with either the completed planning Turn, immutable approvable Goal Plan, and completed plan Item, or the request-derived planning Turn, exact question request Item, and its `user-input` Gate. |
| `goal.plan.approve` | `planItemId` only | Original `goalId`, immutable Goal Plan, plan Item, exact Goal Task set, and Goal read resource. |
| `goal.plan.revise` | `revision` | Original `goalId`, revision Turn and Item, and Goal read resource. |
| `goal.intent.revise` | `objective`, `revision`, and optional `affectedTaskIds`, preserving omitted versus empty | Original `goalId`, immutable revision Item, current Goal objective and hold scope, and Goal read resource. |
| `goal.pause` | No semantic body | Original `goalId`, accepted `paused` command outcome, and current read projection of that exact Goal. |
| `goal.resume` | No semantic body | Original `goalId`, accepted `resumed` command outcome, and current read projection of that exact Goal. |
| `goal.step` | Optional exact `refinement` with `activePlanItemId`, `taskId`, `reason`, `evidenceItemIds`, `evidenceArtifactIds`, and `changedAction`; absent means no caller refinement | Original Goal, Task, Turn, stop outcome, evidence, nullable Review, and any refinement status Item lineage. |
| `goal.review.decide` | `verdict`, optional `reason`, and `revisionInstruction` required only for `refine` | Resolved Goal Review with the exact decision and resolution snapshot, addressed Goal Task, and Goal read resource. |

The ledger lookup occurs before resolving the current Goal or ready Task. A completed matching record replays its original resource lineage even when a newer Goal or Task is current; changed caller input returns `409 idempotency_key_conflict` before effects. Only after an absent ledger and absent deterministic request-owned effect may the first execution resolve the active Goal, ready Task, defaults, plan, Coordinator result, or worker candidate.

`goal.start` derives its Goal, objective Turn, and objective Item identities from the immutable command scope and request id. `goal.plan` and `goal.plan.revise` likewise derive their Turn and Item identities from that scope, and `goal.plan` derives the Plan record and plan Item from the same planning Turn. These identities distinguish no effect from a request-owned effect and expose a crash half-state without a reservation record or mutable current-Goal lookup; for a cross-store mutation, they do not by themselves prove that the same request won the Workspace mutation. Workspace-database-only mutations apply their Goal, Plan, Task, Review, and command writes in the existing database transaction where possible. Cross-store commands acknowledge only after every named owner is durable. The exact request-derived terminal failed planning Turn is a complete handled-failure exception: it retains its admitted input and output with no Plan or Question, is never a successful replay owner, and forbids another model call under the same request. Every other unprovable or incomplete tuple returns `recovery_required` and MUST NOT be repaired by inference.

Direct public `goal.start` requires a request id and derives the Goal, completed objective Turn, and completed objective `user-message` Item from command, actor, Workspace, addressed Goal Main Thread, and request identity. The Item stores the exact objective and request causation, and the Goal points back through `createdByItemId`. Fresh execution checks that the Thread has no active Goal before creating Core-store owners, then one Workspace transaction rechecks that predicate before inserting the deterministic Goal. The schema-valid Goal response is built before the command receipt is published; a matching receipt replays only after validating the exact original Goal, Turn, and Item lineage, and changed canonical input conflicts before effects. V1 deliberately fails closed for every missing-receipt owner tuple, including one that looks complete: Goal and Item authority preserve the objective and resolved title but do not preserve whether the optional caller title was absent or explicitly equal to the derived default, and the default title is forbidden from entering the caller-input hash. Retry therefore returns `recovery_required` without synthesizing a receipt, inferring canonical input, creating a replacement Goal or Turn, or adding another request record. Chat-to-Goal and Task-to-Goal handoffs derive one new receiving Goal Main Thread plus the same downstream owners from their initiating outer command identity and retain only that outer receipt; a missing outer receipt likewise fails closed until the outer command's own recovery contract can prove its complete response.

`goal.pause` and `goal.resume` use the Core single-resource replay rule rather than a response snapshot. Their Workspace-scoped command receipt stores only response kind `goal` and the original `goalId`; a receipt carrying a payload snapshot is invalid. The pause response is exactly `{ outcome: "paused", goal }`, the resume response is exactly `{ outcome: "resumed", goal }`, and `goal` is the current schema-valid projection of the exact original Goal named by the receipt. The literal outcome states what the accepted command did, while `goal.status` states the resource's current truth; after a later opposite transition, replay therefore preserves the historical outcome and truthfully returns the current status without resolving the latest Goal, copying a mutable Goal projection into the ledger, or adding transition history.

Fresh pause accepts only the exact latest active Goal in `running` with `currentTaskId=null`, `terminalStopReason=null`, and no non-terminal `pending`, `running`, or `awaiting_human` worker Turn. Fresh resume accepts only that exact Goal in `paused` under the same safe-boundary predicate. One Workspace SQLite transaction looks up the receipt before current-Goal selection, rechecks the exact Goal identity and Workspace-owned predicate, changes the status, builds the schema-valid response, and inserts the metadata-only receipt; a transaction failure leaves neither transition nor receipt. The separate Thread Turn owner is rechecked immediately inside that synchronous transaction callback but is not represented as a fictitious distributed transaction; exclusion against a concurrent worker launch depends on `goal.step` rechecking the same Goal status when it reserves the Task and Turn. A matching completed receipt bypasses current-target selection and never repeats either transition.

With no retained receipt, pause and resume are fresh commands and may execute only from their exact source-state predicate; target or other states return the typed transition conflict and never synthesize a receipt. A receipt that names a missing Goal, carries a snapshot, or contradicts its command scope or input hash returns `recovery_required`. A caller intentionally retrying after the seven-day receipt window uses a new request id. Tests must prove transaction rollback, ordinary replay across later transitions, exact original-Goal projection, metadata-only receipt shape, and no duplicate status mutation when a receipt exists.

The public V1 `goal.plan` command acknowledges exactly one of two successful planning outcomes: an approvable Plan or an exact planning question requiring user input. It has no semantic caller input, so a schema-valid request cannot produce a changed-input conflict; unknown body fields remain `invalid_request`. Initial planning rechecks the exact Goal and absence of an approved or pending Plan; revision planning instead uses the recorded request, predecessor, and current intent against intact Plan pointers. For a Plan outcome, the acknowledged tuple is the request-derived completed planning Turn and completed plan Item, digest-valid immutable Plan with matching `createdByRequestId`, applicable pending Plan pointer, original Goal identity, and completed command receipt. For a question outcome, it is the request-derived planning Turn in its exact `user-input` Gate, completed question request Item on that Turn, applicable resulting Goal status and unchanged Plan pointers, original Goal identity, and completed command receipt; the response exposes that question and Gate, not an approvable Plan. The receipt is published only after the matching full tuple is durable. A matching receipt replays its original Plan or question outcome after validating its request-owned lineage, even if the question was subsequently answered; it never calls the planner again. If receipt publication fails after a complete Plan tuple commits, retry reconstructs that same outcome from the original Goal and Plan lineage and publishes the missing receipt. A missing receipt after a question outcome permits the same reconstruction only while the exact question Gate is still open and every named owner and resulting Goal predicate remain provable; an answered, missing, partial, or contradictory Gate tuple returns `recovery_required` without a second model call or invented receipt. A terminal failed planning Turn remains durable failure evidence, not a successful `goal.plan` replay owner; the same request returns `recovery_required` before another model call, while a distinct new request may retry from current truth. NanoCore does not infer success, resolve the latest Goal, or create replacement owners inside recovery. A read projection distinguishes an untouched initial `planning` Goal from one with a retained failed attempt so a client offers explicit retry after failure rather than automatically creating another Plan on reload.

When Chat-to-Goal or Task-to-Goal handoff invokes the Goal service, the initiating outer command remains the only ledger owner. Goal Mode derives one receiving Goal Main Thread in the same Workspace with `parentThreadId` equal to the originating Thread, creates the downstream Goal, objective Turn, and objective Item in that receiving Thread, and leaves one handoff reference Item in the originating Thread. It does not publish a nested `goal.start` record, copy originating history, or reconstruct it inside the Goal Main Thread. Missing or contradictory parent, reference, receiving Thread, Goal, Turn, Item, or receipt lineage returns `recovery_required` and creates no replacement. Direct public Goal entry uses the `goal.start` identity above. This rule prevents two receipts from claiming the same handoff.

`goal.plan.approve` never accepts a full Plan from the caller. It loads the exact pending immutable Goal Plan, verifies its digest, graph, predecessor, source intent, and source Task and evidence snapshot, then commits the exact Task snapshots and pointer transition in one Workspace transaction at a safe point. A missing Plan record, mismatched Goal or Item lineage, changed digest, or partial Task set returns `recovery_required`; a non-pending `planItemId`, changed predecessor or source snapshot, or `plan.sourceIntentItemId !== goal.currentIntentItemId` returns `stale`; graph invalidity returns `goal_plan_invalid`. It neither trusts Plan content from the client or Item summary nor discards unaffected work completed since the candidate was drafted.

V1 accepts one bounded cross-store idempotency compromise for `goal.plan.approve`: the existing app-local command receipt is persisted immediately after the Workspace approval transaction because the current command-ledger owner opens its scoped database independently. Normal exact replay and changed-input conflict use that receipt. If a crash leaves the complete approved Goal and Task tuple without the matching receipt, the next attempt returns `recovery_required`; it does not infer the winning request, synthesize a receipt, roll back Tasks, or introduce an approval settlement workflow.

`goal.plan.revise` uses the same bounded fail-closed compromise without a recovery workflow. First execution verifies the exact non-terminal Goal, its active or pending predecessor Plan when one exists, and visible completed Plan Item before writing; its deterministic revision Turn and `user-message` Item derive from actor, Workspace, Thread, command, and request identity, and the Item uses `parentItemId` for the predecessor Plan and `causationId` for the request. The Workspace transaction rechecks that predecessor and MUST NOT clear the active pointer or move the Goal to `planning`. The schema-valid public response is built before the command receipt is published. A matching receipt replays original Goal lineage after validating those owners, and changed canonical input returns `idempotency_key_conflict`. A competing unresolved revision against the same predecessor returns `recovery_required`. If a deterministic revision Turn or Item exists without the receipt, retry returns `recovery_required` even when the tuple looks complete; NanoCore does not synthesize a receipt, infer a winner, create a settlement record, or launch a replacement Turn.

`goal.intent.revise` accepts only an authenticated user instruction for the exact non-terminal Goal, with non-empty `objective` and `revision` and optional distinct Goal-owned `affectedTaskIds`; omission, `[]`, and a named array are different canonical inputs. It derives one completed intent Turn and one readable revision Item from the command, actor, Workspace, Thread, and request identity before the Workspace mutation. One Workspace transaction rechecks the exact predecessor `currentIntentItemId`, validates the affected scope, changes `objective`, `currentIntentItemId`, and `currentAffectedTaskIds`, and writes a receipt naming the original Goal and revision Item. A competing intent revision against an older predecessor is `stale`; a changed input under the same request id is `idempotency_key_conflict`. A matching receipt replays the original Item and current projection of that same Goal without applying the revision again, even after a later accepted revision. The receipt is published only after the complete owner tuple is durable. A deterministic Item without a matching receipt, a missing Item named by a receipt, or a contradictory Goal and Item lineage returns `recovery_required` without inferring the winner, repeating the mutation, or deleting the Item. Restart reads the same owners and command receipt; a new request may revise current truth, but the same unresolved request cannot be rerun. Immediate stop, revocation, and permission narrowing remain with their existing owners even when this command cannot acknowledge a complete tuple.

Before one `goal.step` worker launch, the Goal Main Thread is the command's addressed Thread, while the worker execution receives a separate execution Thread in the same Workspace with `parentThreadId` equal to that Main Thread. The execution Thread and reserved Turn id derive from command, actor, Workspace, Goal Main Thread, Task, and request identity, and the worker Turn derives only inside that execution Thread. One Workspace database transaction reselects the first `ready` Task of the active approved Plan by stable plan order, rechecks the exact Goal is `running` with `currentTaskId=null` and `terminalStopReason=null`, CAS-transitions that Task to `running`, sets the Goal's `currentTaskId` to that Task, records the existing allowed worker-launch PermissionDecision, and writes the existing `preparing` Worker Checkpoint with the request id, non-secret canonical input hash, execution Thread id, reserved Turn id, Goal id, Task id, and prepared context digest. The Goal Main Thread receives one reference Item naming the execution Thread, Task, and Turn and receives no worker history. When `refinement` is present, its exact fields enter the canonical caller-input hash and the Goal service derives one status Item identity from the same request; replay validates that Item against the accepted Task and Plan before returning, and a changed refinement conflicts before effects. Only the complete parent lineage, reference Item, checkpoint, permission, Task, Thread, Turn, and first scheduler-admission tuple authorizes execution and its own AgentSession. A missing member, different Thread or Turn, duplicate effect, contradictory admission, or request-bound checkpoint without an immutable matching worker-request trace returns `recovery_required` and never reruns Coordinator, reconstructs worker history in the Main Thread, reselects current context, or launches a replacement. The accepted S16/S39 Context Package trace supplies that immutable worker-request proof; exact replay may continue a not-yet-started first launch only by proving the same bytes and identities. This uses the checkpoint as the existing launch fence and adds no reservation record.

After the terminal Turn and evidence preconditions are durable and the Workspace transaction reaches one accepted outcome, the command ledger stores only response kind `goal` and the exact original `goalId`. It stores no Task, Turn, outcome, stop, evidence, Review, Gate, Coordinator, AgentSession, Context Assembly, checkpoint, or HTTP response snapshot. A worker gate is the sole nonterminal successful step boundary: its receipt still names only the Goal while the exact `awaiting_human` Turn, Gate Items, `waiting_for_user` checkpoint, running Goal Task, and `awaiting_user` Goal remain with their existing owners.

The successful public response is exactly `{ goal }`, where `goal` is the current projection of the exact original Goal named by the receipt. A fresh caller that needs the worker Turn, evidence, Review, or Gate re-queries the Thread, Turn, Action Center, and Review surfaces that own those facts. A replay returns the same current-Goal shape and does not attempt to reconstruct the historical HTTP result. This intentionally gives up byte-exact or field-exact replay rather than copying mutable or historical business data into the command ledger.

Within the ledger retention window, the same identity and input projects the receipt-named Goal without rerunning Coordinator, launching a worker, advancing another Task, duplicating a gate, or duplicating a Review. Changed semantic input returns `idempotency_key_conflict`. If any request-owned checkpoint, deterministic reserved Turn, or other step effect exists without the receipt, the live command returns `recovery_required` and performs no reconstruction, inferred closeout, receipt publication, or replacement launch. The receipt is durable before a terminal checkpoint may be cleared; replay may finish only that already-receipted terminal checkpoint cleanup, while a worker-gate checkpoint remains at `waiting_for_user` until its Gate response closes the old envelope. Any uncleared checkpoint blocks a competing `goal.step`, and every uncleared terminal checkpoint remains discoverable after restart. A caller that intentionally retries after the idempotency window uses a new request id. No pending command state, settlement row, or Goal recovery workflow is added.

A terminal checkpoint with complete request identity, canonical StopReason, evidence, and immutable Goal Task input but no Goal owner transaction remains a boot-recovery input under the separate owner-derived checkpoint classification contract. The live `goal.step` command does not use that checkpoint to reconstruct a response or publish a missing receipt. Boot classification must either apply the already-defined mode owner transaction from a complete tuple or leave the checkpoint discoverable as `recovery_required`; it must not guess from the current Goal read model or create another recovery owner. The exact metadata-only receipt and cleanup order for that boot path are defined with the boot classifier rather than by HTTP replay.

### Steering and user input

- Goal steering is accepted only when S16 can atomically ground the input Item and `PendingUserTurnRecord` under the exact active Goal and worker Turn; every other busy input fails before writes.
- Accepted input remains `queued` until the exact winning claim and immutable Context Package trace prove delivery to one specific accepted worker Turn under the original Goal. That Turn may be the originally active Turn or a later claimed Turn under the same non-terminal Goal; a UI or Coordinator summary is not delivery proof.
- `applied` means delivery only. `goal.steering.send` does not mutate the Goal objective, approved Plan, Task graph, non-goals, risk policy, or authorization state. A user intent change uses `goal.intent.revise`; a new immutable Plan version then follows the classified revision and exact approval rules above. Message content may inform a later Coordinator decision, but it does not itself revise intent or Plan authority.

### Evidence and review

- Goal Mode must attach evidence references to worker steps and terminal summaries.
- Evidence may include artifacts, command summaries, test results, workspace sync reviews, Git push records, Action Center decisions, and restricted diagnostics by reference.
- Review state must be visible enough for the user or an external coordinator to understand what happened without reading raw backend internals.

A Goal Review is created unresolved with immutable Goal, Task, worker Turn, Item and Artifact evidence, prompt, and creation lineage, but with nullable verdict, reason, revision instruction, resolution request id, resolution actor id, resolved timestamp, and `resolutionSnapshot`. A producer MUST NOT preselect a human verdict. `goal.review.decide` is a separate human command scoped by authenticated actor, Workspace, Thread, Goal, Review, and required request id. Its canonical input contains the exact `accept`, `refine`, `retry`, or `abort` verdict, an optional reason that is required for `retry` and `abort`, and a non-empty revision instruction required only for `refine`. The first writer MUST compare-and-set the Review only while every nullable decision field is null; that Workspace transaction stores the input decision, applies the verdict-to-Task-and-Goal mapping, and stores the resulting immutable snapshot. Identical replay by the winning request returns that snapshot; reuse of its request id with changed decision input returns `idempotency_key_conflict`, a different command that loses the unresolved compare-and-set returns `stale`, and a contradictory owner tuple returns `recovery_required` before mutation. No later writer may overwrite the resolution.

The exact `GoalReviewRecord` fields are `reviewId`, `workspaceId`, `threadId`, `goalId`, `taskId`, non-null worker `turnId`, `itemIds`, `artifactIds`, `verificationEvidence`, `prompt`, `createdByRequestId`, `createdAt`, `updatedAt`, nullable `verdict`, nullable `reason`, nullable `revisionInstruction`, nullable `resolutionRequestId`, nullable `resolvedByActorId`, nullable `resolvedAt`, and nullable `resolutionSnapshot`. Before resolution, every nullable decision field is null. After resolution, `verdict`, `resolutionRequestId`, `resolvedByActorId`, `resolvedAt`, and `resolutionSnapshot` are non-null; `reason` is non-null for `retry` and `abort` and otherwise optional; `revisionInstruction` is non-null only for `refine`. Any other combination is contradictory state and cannot be imported, projected as actionable, or repaired by inference.

The exact immutable `resolutionSnapshot` carries `outcome`, `task`, `goal`, and `nextReadyTaskId`. `task` is exactly `{ taskId, status }`; `goal` is exactly `{ goalId, status, currentTaskId, terminalStopReason }`; and `nextReadyTaskId` is a nullable stable projection, never launch authority. `outcome` is exactly `complete_next_task`, `tasks_complete`, `refine`, `retry`, or `aborted`. Every snapshot has `goal.currentTaskId=null`; `accept` produces a completed Task and either `complete_next_task` or `tasks_complete`, but `tasks_complete` leaves the Goal `running` and only makes it eligible for a completion proposal; `refine` or `retry` produces the same ready Task and matching outcome; and `abort` produces a failed Task plus an aborted Goal with `terminalStopReason=aborted`. The decision response exposes this bounded snapshot rather than a mutable full Goal or Goal Task record.

The resolved Review and its snapshot are the semantic authority for post-review Task progression. In the same Workspace transaction, `accept` makes the reviewed Task `completed`, unlocks dependency-satisfied Tasks, and leaves the Goal `running` with `currentTaskId=null` whether more Tasks remain or all Tasks are complete; `refine` or `retry` makes the reviewed Task `ready` and leaves the Goal `running` with `currentTaskId=null`; `abort` makes the reviewed Task `failed` and the Goal `aborted` with `currentTaskId=null` and `terminalStopReason=aborted`. When all Tasks are complete, a later Orchestrator Turn may submit the separate completion proposal; the Review cannot stand in for its independent verifier. A response may project the first ready Task by stable plan order as `nextReadyTaskId`, but only the next `goal.step` transaction may make that Task current. The service MUST NOT call Workflow Coordinator again to reinterpret the human decision, create another stop-decision record, overwrite the reviewed Turn or evidence, or use the projection as authority.

### Recovery

- Explicit `goal.resume` is only the fenced `paused -> running` Goal lifecycle transition. It does not resume a Turn, AgentSession, Sandbox, scheduler lease, worker process, or backend session, and it reads only the exact Goal plus the Thread's non-terminal-Turn safety predicate; a later `goal.step` or restart-recovery path owns reconstruction from Plan, Task, checkpoint, evidence, and AgentSession records.
- Restart recovery and later worker continuation must read durable Goal, Thread, Action Center, worker step, Artifact, evidence, and AgentSession records.
- It must not rely on coordinator conversation memory as the source of truth.
- Pending worker checkpoints, stale leases, failed worker steps, or interrupted sessions must surface as typed recovery choices.

### Relationship to other modes

- Chat Mode may hand off to Goal Mode when the Assistant identifies a large objective.
- Task Mode may escalate to Goal Mode when a bounded task becomes multi-step, risky, or long-running.
- Goal Mode V1 starts worker execution only from an approved immutable Goal Plan. A simple objective may use a one-task plan, but it does not bypass plan authority or approval.

## Accepted Design

Goal Mode is a NanoCore workflow service that calls Workflow Coordinator for deterministic decisions and admits one Goal-scoped Orchestrator Turn only for bounded semantic judgement. Coordinator owns semantic worker-context composition and the Goal-level bounded-step stop decision; the Goal Mode service owns autonomy-field binding, deterministic wake and single-flight control, repeated-work protection, worker-execution Thread lineage, Goal worker ordinary-Sandbox pin policy, completion-proposal admission, and persistence of the existing Goal, Goal Task, Goal Review, Turn, evidence, and accepted context owners that prove progression. It requests context delivery, scheduler, worker-control, attention, and independent-verification effects through their existing owners and composes the role-agnostic runtime in `docs/specs/20260813-internal_agent_runtime.md` rather than inventing a separate runtime, scheduler, GoalSandbox, or Goal lifecycle.

The removed `@openkit/mcp` kernel-test facade must not be restored through compatibility or replacement work. Current Goal product operations belong to the transport-neutral operation catalog exposed through the unified `openkit` Skill and its bundled CLI.

NanoCore exposes the current V1 Goal Mode operations for start, read, planning, approval, revision, pause, resume, bounded steps, Action Center reads, Artifacts, evidence, and interrupted worker recovery. The unified `openkit` Skill projects that supported surface through its bundled CLI and does not preserve former MCP tool names or resources. Chat Mode goal handoff and Task Mode escalation create durable Goal Mode objectives through the same service and keep worker execution deferred until planning and bounded steps. Public `goal.plan` now uses the existing internal-role profile and a bounded model Turn with only `goal.plan.propose` for initial and revision drafts. Its request-owned Turn and Items yield an immutable pending Plan, an exact planning question Gate, or a retained failed attempt without terminalizing the Goal; the same failed request does not call the model again. `goal.intent.revise` persists a readable intent Item and updates the exact current objective and affected-Task hold; `goal.plan.revise` retains an active approved Plan while a candidate is drafted. Goal Plan readback distinguishes active and pending Plans and derives `create`, `draft_revision`, `retry`, `answer_question`, `continue_planning`, `await_approval`, `in_progress`, or `none` from durable owners. Post-approval successor proposals carry new Task ids, predecessor dispositions, and a source Task and evidence digest; approval rechecks current intent, predecessor, Task and resource evidence, and the safe point before activating the candidate. Action Center exposes a pending Plan even while the Goal remains running, and Web shows the intent-scope choice, explicit draft, retry, question-continuation and approval actions, and the proposed Task dispositions. `goal.step` now accepts the bounded optional execution-refinement input, validates its active Plan, selected Task, and evidence refs, and writes a linked Goal Main Thread status Item before worker launch. Pause and resume now require request identity, store only the original Goal id in the existing Workspace command ledger, and commit that receipt with the exact status transition in one Workspace transaction. They reject an unsafe current Task, terminal reason, or non-terminal `pending`, `running`, or `awaiting_human` Turn; replay returns the historical outcome plus the current projection of the exact original Goal without repeating the transition. Goal step now derives the reserved Turn from request identity, consults the command receipt and exact request-bound checkpoint before mutable workflow selection, and co-transacts Goal and Task reservation, the allowed worker-launch PermissionDecision, and the `preparing` checkpoint. Its public response is the current `{ goal }` projection, its receipt stores only that Goal id, and any request-owned effect without the receipt fails closed as `recovery_required` rather than rebuilding a historical result. Interrupted-worker recovery now requires the exact interrupted Turn and recorded AgentSession, the matching terminal restart-cleanup lease, and the request-bound checkpoint before it exposes a row. Its strict request-id command atomically changes the exact running Goal Task to `ready`, leaves the Goal `running` with `currentTaskId=null`, records a bounded Turn receipt, and starts no replacement worker; contradictory Goal lineage remains inspection and guidance only. Caller-selected `record_terminal`, its App API route, Core Client method, former MCP tool, Action Center action, schemas, tests, and OpenAPI projection remain removed. Runtime configuration projects only product-safe availability; stale AgentSession retirement and successor creation are internal continuity behavior, and no Goal, App API, Core Client, Action Center, or bundled-CLI operation selects or restarts AgentSession. Historical deterministic L6 evidence covered the former Goal MCP path from status and diagnostics through repository linking, plan approval, one bounded step, Action Center handling, read-only inspection of NanoCore-produced evidence bundles, and Artifact read when present; the retired MCP-only story is not an active release gate.

Goal, historical and active Plan, and Goal Task export now uses one SQLite read snapshot. Import validates every source digest and Plan/Task relationship before reminting, builds one canonical identity map that includes Plan-only Tasks, remints identity-bearing references, recomputes each Plan digest only after its exact reminted payload is complete, and inserts the coherent result in the existing import transaction; malformed, duplicate, incomplete, or incoherent authority fails instead of being omitted or repaired.

For a post-approval successor, current source capture records ordered active-Plan Task status and Review facts, completed no-Review worker output when its owning Turn can be identified, and the IDs and content digests or versions of Item and Artifact resources named by the candidate. Proposal persists that combined source digest, and approval recomputes it against current owners before activating new Task rows. Completed predecessor results used by the successor appear as exact resource references; the proposal Item summary also shows the predecessor diff, Task dispositions, and model-authored exclusion explanations taken from the Plan assumptions.

Plan approval exact replay and changed-input conflict use the existing app-local command receipt. The current bounded two-store compromise writes that receipt immediately after the Workspace approval transaction; a crash that leaves the complete approved Goal and Task tuple without its matching receipt returns `recovery_required` on retry and does not infer the winning request, synthesize a receipt, revert Tasks, or create an approval settlement workflow.

Each real Goal step reserves its Turn identity before checkpointing and then starts that same Turn through the durable scheduler. Scheduler admission owns the AgentSession, lease, and `lease-binding:` worker-control token lineage, and terminal Goal handling releases the lease. The objective user Item id derives from the created Turn id rather than a Workspace-local counter, so independent Workspaces and Threads cannot collide in shared Core storage; cross-Workspace and cross-Thread regression coverage protects this invariant.

The current real-worker launch reads the complete immutable approved Goal Task, verifies its non-null active Plan lineage, asks Coordinator to compose the one exact request from its objective, acceptance criteria, ordered resources, expected Artifacts, context budget, verification checks, review policy, escalation conditions, and eligible Review context, schema-parses that request, and sends its compact JSON through the scheduler, AEP, worker input, Turn input, and Turn-owned `user-message` Item. Missing, malformed, or mismatched immutable request facts return `recovery_required` before launch instead of using defaults, caller input, Plan content, or the lightweight Plan Item. The checkpoint stores the Goal-step request id, canonical input hash, deterministic Turn, Goal, Task, context digest, and product-safe context assembly diagnostics as launch-fence evidence, while S39 persists and verifies the separate immutable Context Package delivery trace; the checkpoint is not delivery proof. A missing or contradictory trace or otherwise unprovable post-fence state returns `recovery_required` without repeating mutable preparation. Goal step fixes lower-level `remainingWorkerIterations=0`, rejects lower-level `continue`, supplies the pre-mutation incomplete-Task predicate, consumes the Coordinator decision before owner mutation, and keeps `ask_user` non-terminal only when an exact Core Gate owns that wait.

`goal.start`, `goal.plan`, `goal.plan.approve`, `goal.plan.revise`, `goal.pause`, `goal.resume`, and `goal.step` now require a request id, and their public schemas reject caller Plan content, `reviewPolicyOverride`, `followUpDrainMode`, and generic queue fields. Every command uses the existing ledger under its documented replay and bounded receipt-gap rules. Goal step performs receipt lookup before active Turn, current Goal, ready Task, Coordinator, or context resolution; exact replay validates the original owner tuple, while a receipt gap consults only the deterministic request-owned checkpoint and accepted business owners. `GoalRecordStatus`, Goal read schemas, and workspace import reject the unowned `verifying` lifecycle value; verification evidence and checkpoint stages retain their separate owners. Goal Task App API schemas, NanoCore storage and import contracts, and generated OpenAPI reject both unowned `skipped` and `needs_revision` states, while task counts and terminal summaries project neither. Goal Review schemas accept only `accept`, `refine`, `retry`, and `abort`; worker or Coordinator `ask_user` and `block` outcomes remain separate gate and stop paths rather than Review verdicts.

The step route now reserves the stable-order Task, runnable Goal, deterministic Turn, allowed launch PermissionDecision, request identity, input hash, and `preparing` checkpoint in one Workspace transaction. Any uncleared checkpoint for that Goal rejects a competing reservation; the original request either replays its receipt, reconstructs the same bounded result from a complete accepted terminal tuple during boot, or returns `recovery_required` without mutation. An exact worker Gate tuple is replayable only through its already durable `goal.step` receipt; a missing Gate receipt preserves the `waiting_for_user` checkpoint as `recovery_required`. After an accepted worker stop, one Workspace transaction commits the addressed Goal Task, Goal Review when required, Goal status, `currentTaskId`, terminal reason, and dependency unlocks; block and abort clear the current Task, and only an authoritative worker `error` marks the Goal failed. The command receipt is published before terminal checkpoint cleanup. A failed owner commit rolls back that tuple, while checkpoint cleanup, projection, response-shape, startup, admission, or other post-fence failure returns `recovery_required` without rewriting Goal or Task authority or launching replacement work. Boot now fences scheduler and worker-control state before scanning every Goal checkpoint through this same owner classifier; it closes only a complete deterministic tuple, preserves live or reconnecting work, and retains every incomplete or contradictory checkpoint while readiness reports `recovery_required`.

Goal worker structured user-input and approval Gates now use the exact shared closeout. Gate creation immediately changes the Product Turn to `awaiting_human`, but an AEP-backed Worker Gate changes the Goal projection to `awaiting_user` and becomes acknowledged and actionable only when its accepted `blocked/ask_user` final status, backend cleanup, Workspace handoff, full Gate lineage, `waiting_for_user` checkpoint, and suspended source AgentSession agree; the delivered Codex MCP path obtains that outcome through the typed session-continuity `human-gate` stop. An enqueue-unproved or contradictory Gate is inspect-only `recovery_required`, keeps its checkpoint and Goal at their prior non-waiting states, and accepts no response. The response or decision Item then closes the old Turn and AgentSession without runtime continuation, records `latestGateContextItemId`, returns the Task to `ready`, leaves the Goal `running` with no current Task, releases scheduler ownership, publishes the response receipt, and only then permits checkpoint deletion. Grant closes the Product Turn and source AgentSession as `completed` and `closed`; denial closes them as `interrupted` and `interrupted` with checkpoint `aborted`. A raw AEP `blocked/ask_user` without an exact Gate instead takes the bounded S05 interruption fallback and writes no Goal Gate context. S16/S39 now provide exact Context Package delivery proof and bounded steering over the existing Goal owners; broader recovery discovery and the remaining explicitly partial Goal projection stay open without a settlement workflow or second Goal state owner.

The current step route reads only the immutable Goal Task review policy. The human-reviewed path persists the exact unresolved Review tuple with matching Task and Goal reviewing state and no preselected verdict; `required=false` takes the same accepted closeout path without a Review. The decision request carries one of the four canonical verdicts; one Workspace transaction applies the verdict, claims the all-null decision tuple, stores the authenticated actor and bounded immutable snapshot, and leaves `currentTaskId=null` without another Coordinator call. Exact replay uses that snapshot when the command ledger is absent, changed input conflicts, competing requests are stale, contradictory tuples require recovery, Action Center projects four verdict-free actions, and first-party clients collect required instruction or reason text. A later `refine` or `retry` step reads only the deterministic latest Review, validates its complete resolution snapshot before mutation, and includes its exact verdict-specific context and prior Item and Artifact evidence in a new Coordinator request and new Turn; the previous Turn, Review, and evidence remain unchanged. The eligible context remains sticky under the bounded fallback until a newer Review supersedes it or the Task terminates.

NanoCore persists task-scoped verification evidence and projects it in goal and terminal summaries. The bounded propose-only Goal Orchestrator planning Turn, same-Goal intent revision and affected-Task hold, pending-versus-active Plan read and approval, post-approval successor drafting, source Task and evidence snapshot fence, Task dispositions, and execution-refinement status Item are now present. The Goal's accepted durable `autonomyClass`, `budget`, and `completionVerification` fields remain unimplemented; a separate three-field owner amendment has been discussed but is pending and is not accepted design authority. The full eight-Tool Goal Orchestrator progression, autonomous wake state, repeated-work breaker, receiving Goal Main Threads for handoffs, worker execution Threads and Main Thread reference Items, and independent completion-proposal verifier remain unimplemented. The accepted Goal worker ordinary-Sandbox pin is not implemented: today `SandboxRuntimeRecord` carries placement, cleanup, sandbox binding ref, and a nullable NanoCore-private `pinnedGoalId` column with an idle-eviction safety reader but no production writer or Goal-aware selector; `AgentSessionRuntimeBinding` carries Workspace and Thread and has no Goal discriminator; current admission lacks Goal, so no Goal pin lifecycle is enforced, another Goal can co-reside, and Goal work can use ordinary selection, including default standby-worker selection. The current routes still place handoff and Goal worker Turns in their originating Threads and can project Goal completion from the bounded-step or human Goal Review path alone; those behaviors diverge from this accepted contract and cannot be treated as conforming handoff, execution lineage, pin, or closure.

## Alternatives Considered

- Treat Goal Mode as an Agent Skill Interface-only flow. Rejected: Goal Mode must be NanoCore state, with the bundled CLI and Web as projections.
- Let the Coordinator run until completion without bounded steps. Rejected: bounded steps are required for review, recovery, cost control, and human attention.
- Require maximal-detail plans for every goal before any action. Rejected: every V1 Goal worker step still requires approval, but a low-risk goal uses one lightweight Task and only the detail needed for its executable objective, evidence, and stop conditions.

## Consequences

- Goal Mode becomes the central V1 mode for serious delegated work.
- Existing end-user Agent Skill and Web flows gain a clearer owning contract.
- Implementation must harden durable goal state and recovery before claiming release readiness.

## Testing Strategy / Acceptance Criteria

- L1: exhaustive tests for the exact Goal and Goal Task transition tables, immutable Goal Plan shape, digest and graph validation, plan approval requirements, steering classification, review-resolution mapping, and stop decisions; removed states and verdicts are rejected.
- L2: contract tests require `requestId` on every Goal mutation, reject `followUpDrainMode` and `reviewPolicyOverride`, reject non-human V1 Plan reviewers, and prove the exact GoalRecord, GoalTaskRecord, plan, step, worker-request, evidence, and Action Center projection shapes.
- L3: NanoCore black-box tests for start, draft plan, approve plan, run one step, handle pending attention, resume after restart, and complete.
- L3: prove that the real worker launch receives the complete accepted delegation and immutable Context Package trace rather than only its objective or a mutable checkpoint summary.
- L3: prove lower-level worker iterations are fixed to zero, another incomplete Goal Task turns accepted lower-level `complete` into Goal-level `continue`, and lower-level `continue` returns `goal_stop_decision_invalid` before mutation.
- L3: prove every concurrent Goal worker execution receives a distinct execution Thread and AgentSession, every execution Thread names the Goal Main Thread as parent, and the Main Thread retains one reference Item without copied worker Items or reconstructed worker history.
- L3: prove that later compatible worker AgentSessions of the same Goal reuse the ordinary Sandbox named by `SandboxRuntimeRecord.pinnedGoalId` when it remains admissible, that another Goal is excluded from that Sandbox and either uses another ordinary compatible Sandbox or remains non-terminal with its existing scheduler admission queued for normal dispatch retry, that every Turn still performs fresh authority, AEP, context, and lease checks, that an absent or ordinarily released pin creates a new pin through ordinary scheduling, that only stale or contradictory pin state conflicting with live binding or occupancy fails closed, and that default standby-worker selection is never used; the nullable `SandboxRuntimeRecord.pinnedGoalId` column now exists, but its only production reader protects idle eviction, with no Goal-aware selector or writer; current admission lacks Goal, and this criterion remains unmet.
- L3: prove wake reasons coalesce through one pending revision, ordinary Main Thread Turn admission enforces single-flight, restart admits overdue work through the deterministic watcher, and the ten-minute fallback never polls a model without a material durable wake condition.
- L3: prove repeated no-progress Turns trip the Goal-owned breaker without completing the Goal and resume only after material durable change or an authorized recovery action.
- L3: prove that an explicit same-Goal intent revision updates the current objective and retains its immutable Item, holds exactly the affected Tasks and their transitive dependents, promptly cancels affected active work through existing owners, and allows unaffected valid work to finish under its pinned Plan and Context Package.
- L3: prove pristine initial planning, iterative questions, exact answers and stale-answer rejection, recoverable initial and revision planner failures with retained Turn input and output, same-request no-rerun, distinct-request retry, and a read action that never automatically restarts a failed attempt.
- L3: `goal.plan` acknowledges and replays an exact Plan or question outcome from its request-owned Turn, Item, Goal, and receipt tuple; a receipt-less complete open question Gate can recover without another model call, while an answered or partial receipt-less tuple is `recovery_required`.
- L3: after an initial or revision planning question is answered, readback returns `continue_planning` with the exact response Item until a new request-bound planning Turn consumes it, even if an older candidate remains approvable.
- L3: prove exact-version approval of initial and post-approval pending Plans, Goal-wide uniqueness against approved Task rows while pre-approval drafts may reuse local ids, explicit new Task ids for remaining successor work, exact completed-result resource or evidence references, no cross-Plan dependency edge, safe-point activation, rejection of changed predecessor, source intent, Task or evidence snapshot, retention of prior Plan and Task evidence, and selection only from the active approved Plan.
- L3: initial and pre-approval Plan candidates carry `taskDispositions=[]`; a post-approval successor carries one ordered digest-bound disposition per non-completed active predecessor Task, each ending it with a reason or naming an exact new Task, and approval rejects missing, extra, stale, duplicate, or invalid mappings before Task mutation.
- L3: prove accepted intent revisions use exact request identity and predecessor, distinguish omitted from empty affected scope, reject stale or conflicting input, replay only the original Item and Goal without applying twice, and preserve an orphan Item as `recovery_required` after a cross-store failure.
- L3: prove an approvable pending successor is visible in Goal readback and Action Center while Goal status stays `running`, and a fully held Goal explains its pending approval or question Gate.
- L3: import preserves the original source snapshot digest on a pending post-approval candidate, rejects its approval as stale after identity remint, and allows an explicit new-request redraft from imported current truth; a candidate drafted before first approval with no source Task snapshot remains eligible under its exact other predicates.
- L3: prove an authorized execution refinement is recorded through its existing Goal Main Thread Item and dispatch or Review path without another Plan, gate, or Tool, while objective, scope, deliverables, acceptance, budget, time, effect, permission, important method or architecture, risk, and verification changes cannot masquerade as refinement even when unchanged fields make an exact diff look small.
- L3: prove Goal `completed` requires one accepted completion proposal and a qualifying independent verifier result, while Worker completion, Goal Task Review acceptance, Coordinator `complete`, Orchestrator quiescence, model confidence, stale evidence, and weakened independence cannot close it.
- L3: prove every non-terminal Goal status keeps `terminalStopReason=null`, including `awaiting_user`, while the addressed Turn and Coordinator response preserve the immediate stop reason.
- L3: prove the terminal Turn, evidence, and checkpoint preconditions are durable before the pre-mutation Coordinator decision is consumed; the Goal, Goal Task, Goal Review, current-task, and terminal-reason tuple commits in one Workspace transaction, while contradictory cross-store state returns `recovery_required` and same-request replay creates no duplicate Review or transition.
- L3: kill after worker terminal persistence but before the Goal-step command receipt, then replay the same id and prove it returns `recovery_required` with the original checkpoint and owner state unchanged; separately prove that an already-receipted replay projects the current exact Goal, can finish terminal checkpoint cleanup, rejects conflicting input before effects, and creates no second worker, task advance, or Review.
- L3: prove the request-derived Turn, first-ready Task and runnable Goal reservation, allowed worker-launch PermissionDecision, and `preparing` checkpoint commit or roll back together; while that checkpoint remains uncleared, a competing request returns `recovery_required` without another Task reservation, Turn, permission decision, or worker launch.
- L3: kill each Goal mutation before its first write, between cross-store owner writes, after its complete owner tuple, and after receipt publication; prove exact replay, conflict, or `recovery_required` according to the command table without a pending command row.
- L3: mutate a caller-retained plan after drafting and prove approval ignores that payload, loads the immutable server-owned Plan, rejects stale ids, digest mismatch, missing dependencies, self-dependencies, and cycles, and creates complete immutable Goal Task execution snapshots exactly once.
- L3: inject Goal, Task, Review, checkpoint-cleanup, projection, and response failures after worker termination; prove none rewrites the Goal to failed unless the authoritative worker StopReason is `error`.
- L3: resolve each accepted Goal Review verdict twice and after restart; prove its immutable snapshot applies once without another Coordinator call and retains every prior Turn and evidence reference.
- L3: reject every partially resolved Goal Review tuple and every portable Review or snapshot containing an unsupported verdict, Task state, outcome, non-null current Task, or inconsistent reason and revision instruction.
- L3: step and Review closeout unlock every dependency-satisfied Task but leave `currentTaskId=null`; only the next step transaction selects the first ready Task, and every terminal Goal also has `currentTaskId=null`.
- L3: an `ask_user` Gate answer or Approval decision closes the original waiting envelope, returns its Task to `ready`, writes the exact `latestGateContextItemId`, leaves the Goal running with no current Task, and requires a new step request and Turn whose Coordinator request and S39 trace include the matching request/response Item pair; corrupt pointers and unsupported Approval statuses fail before launch, and no worker AgentSession resumes implicitly.
- L6: story acceptance where a user works out a plan with the system, approves it, runs multiple bounded worker steps, reviews evidence, and completes the objective.

Acceptance: Goal Mode can be resumed from durable state, never runs past unresolved human gates or its autonomy and budget boundary, gives concurrent worker executions independent Thread and AgentSession lineage, coalesces deterministic wake conditions under Main Thread single-flight, trips repeated-work safely, pins Goal worker work through `SandboxRuntimeRecord.pinnedGoalId` on an ordinary Sandbox without a GoalSandbox or public pin field, makes each worker step and terminal decision visible with evidence, and closes only from an accepted completion proposal plus its qualifying independent verifier.

## Risks & Mitigations

- Risk: Goal Mode becomes too broad to implement. Mitigation: keep deterministic control primary, admit semantic Orchestrator Turns only for demonstrated judgement, and add no Supervisor, global coordinator, second scheduler, or second Goal lifecycle.
- Risk: users cannot tell whether work is ongoing or waiting. Mitigation: explicit status and Action Center projection.
- Risk: coordinator context loss breaks long goals. Mitigation: durable goal and evidence state are the source of truth.

## Resolved Decisions

Previously open questions are resolved by accepted V1 defaults: a Thread may have only one active Goal at a time; every V1 worker step belongs to one explicit approved immutable Plan revision; a low-risk Goal may use a one-task plan but has no planless or implicit-plan execution path; autonomy is carried only by the three Goal fields; single-flight is ordinary Goal Main Thread Turn admission; and model confidence never closes a Goal.
