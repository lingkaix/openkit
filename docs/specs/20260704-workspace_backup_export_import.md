# Workspace Backup, Export, Import, And Data-Root Migration

This specification is the single owner of the analytical Workspace export format and `.openkit-workspace.tar.zst` archive transport, per-Workspace operational backup capture, verification, completion sealing, same-deployment restore, deleted Workspace recovery, and cross-deployment MOVE, whole-data-root cold and hot backup and stopped-server restore, and configuration-repoint data-root migration.

## Scope

Owns:
- Analytical Workspace export with the [registered baseline marker](20261017-retained_format_register.md#v020-version-tag-inventory): inspectable directory tree layout, root manifest, exact content inventory, offline verification, inclusion/exclusion/redaction rules, portable Material and version-keyed Artifact Review representations, and export-time item-log snapshot compaction elision declarations. Database files are not the analytical representation, and outward verification remains supported independently of operational backup.
- The canonical `.openkit-workspace.tar.zst` archive transport (`application/vnd.openkit.workspace-export+tar.zstd`), binary App API streaming boundary, request staging, and local-mode bundled CLI projection.
- Operational per-Workspace local backup capture, verification, completion sealing, same-deployment restore, deleted Workspace recovery, and identity-preserving cross-deployment MOVE, plus the interaction between Workspace deletion, retention classes, and the sealed audit-closure export.
- Whole-data-root cold and hot backup procedures, stopped-server restore, and configuration-repoint data-root migration with deployment predecessor lineage, kept separate from per-Workspace operations.
- Product boundary exclusions: analytical Workspace export serves external analysis, evaluation, and audit only; ordinary OpenKit portable import and its import/dry-run engine are absent and are not a deferred COPY. Operational COPY is deferred and MUST NOT be used to bypass a MOVE collision or mutate sealed original evidence. User-scope, Server-scope, and whole-deployment analytical export units, deeper item-log compaction, remote backup destinations, incremental remote synchronization, page-level SQLite or WAL shipping, live multi-deployment replication, and whole-server hot-backup redesign are outside supported operations. Only local backup destinations are supported; Workspace archive uses this snapshot and freeze contract while Thread archive keeps its Thread-scoped rules. Future evaluation mechanisms do not automatically authorize a new portable record family. The retired Workspace host repository (`localPath` and Turn `workspaceCwd` or `workspaceRoots` repository bindings) is excluded from validation, import, and preservation. No extra hold manager, state machine, or Main lock-retry service is introduced.

Does not own:
- Control commits, execution settlement, snapshot-root mapping, and garbage collection ([Durable Execution And Control Store](20261019-durable_execution_and_control_store.md)), physical storage placement ([Storage Layout And Record Ownership](20260703-storage_layout_record_ownership.md)), or boot-time layout verification, index rebuild, and recovery sequencing ([NanoCore Bootstrap Readiness](20260704-nanocore_bootstrap_readiness.md)).
- Record envelope and required-feature registry mechanics ([Schema Evolution And Record Envelope](20260703-schema_evolution_record_envelope.md)) or sibling ownership scopes, retention classes, legal holds, and Audit or sealed deletion-closure schemas ([Audit, Usage, And Evidence Records](20260703-audit_usage_evidence_records.md), [Storage](../core/storage.md)).
- Standalone Knowledge Base package interchange ([File Storage And Knowledge Packages](20261018-file_storage_and_knowledge_packages.md)), which creates no Workspace-export round-trip obligation, or standalone Light App definition catalog interchange, snapshot restore, and one-way format migration ([Generative Kernel Data And Operations](20260908-generative_kernel_data_operations.md), [Skill Catalog Versioning And Pinning](20260711-skill_catalog_versioning_pinning.md)).
- Workspace membership, invitation, owner transfer, and actor lifecycle ([Multi-User Workspace System](20260715-multi_user_workspace_system.md)), Vault backend and rebinding mechanics ([Vault Backend Implementation](20260704-vault_backend_implementation.md)), or Better Auth session authentication and Administrator Eligibility ([Policy](../core/policy.md), [Remote Auth Credential Bootstrap](20260704-remote_auth_credential_bootstrap.md)).
- Generic retained execution-host volumes ([Persistent Worker Volumes](20260910-persistent_worker_volumes.md)).

Core: [Storage](../core/storage.md), [Identity](../core/identity.md), [Architecture](../core/architecture.md), [Evidence](../core/evidence.md), [Vault](../core/vault.md), [Policy](../core/policy.md).

## Operations

### Backup

#### Current Product Boundary

Every Workspace MUST support online local backup capture and verified same-deployment restore before `v0.1.0`, freezing only the affected Workspace. Nondestructive busy capture while work runs is permitted only behind a fence covering every physical SQL and mutable-file writer across the common cut; native ACK drain alone is insufficient, and until that all-writer fence lands, capture enforces the idle scoped freeze and blocker checks.

The lifecycle owner (`tryFreezeWorkspace`) MUST atomically close new target publishers before checking authoritative blockers. If a publisher is already admitted, another freeze exists, or required facts are unreadable, freeze refuses immediately; if blocker inspection refuses, admission reopens. Successful admission returns one idempotent release. No SQL transaction may span an `await`, and a lifecycle operation's own ordinary mutation admission MUST NOT count as target running work. Every mutable publisher — including late terminal publication, dispatch, Pending claim, filesystem apply, and maintenance — shares that exclusion; durable execution, physical cleanup, claim, and recovery facts (never gate counters alone) prove inactivity, while unrelated Workspaces remain usable. A fresh manual capture of the same Workspace MAY borrow an active caller's exact lifecycle freeze after checking current authority, blockers, and native ACK drain; borrowing never releases the caller's freeze on success or refusal, and foreign, released, or replaced freeze owners are refused.

#### Online Snapshot Policy

One snapshot owner serves capture, restore, MOVE, deletion, and deleted recovery. Scheduled idle capture runs on the maintenance tick, skips blocked Workspaces without recording an accepted failed request, and considers at most one eligible Workspace per pass (current default). The current default policy is one successful sealed capture per UTC day and seven finished automatic daily generations. Eligibility derives from the last sealed manifest; legal holds and active readers or recovery pins independently protect required generations.

Idle backup reuses independently owned immutable digest objects in the local pool; page-level SQLite incrementality is not used. SQLite databases and mutable files are copied under the same target fence using the native online SQLite backup primitive for committed database snapshots; WAL and SHM files are never standalone snapshot authority, and captured Core account/membership provenance uses one short read transaction without pausing the whole server. Before database copy, the native hold owner atomically refuses a competing database or global hold without queueing, drains only finite already-posted acknowledgements for that database, releases the hold before posting native finish or close and in `finally` on every exit, and never awaits a native command whose post is held.

Capture releases the Workspace pause early only after mutable snapshots are independent and immutable content protection is proved; otherwise it holds the fence through copy and seal. Ordinary backup ends its Light App read generation after native resume and logical freeze release, whereas MOVE and borrowed freezes retain it until cleanup. Retention retires generation exposure before garbage-collecting unreachable digest objects; sealed or pinned closures survive live deletion, and clock expiry never releases content protection.

Public snapshot operations (`packages/app-api-schemas/src/workspace-snapshot-operations.ts`) address owned backup and request identities, never server paths. Capture, verify, restore, MOVE-out, inspect, finish, abandon, and reactivation use JSON; sealed-bundle download and MOVE-in use streaming `application/octet-stream`. Manual calls require current Administrator Eligibility rechecked after `await` boundaries; maintenance uses its trusted owner rather than a synthetic administrator. Capture takes `workspaceId` and purpose (`backup` or `move`) and returns the backup identity and disposition. Inspect, finish, and abandon select that exact capture identity under current authority and operation fences; abandon closes publication rights before releasing content protection. Reports (`WorkspaceSnapshotOperationReportSchema`) return disposition, verified identities/digests/counts, lineage, coverage/exclusions, dropped members, unresolved dependencies, any unprovable safety window, and the next permitted action.

Every mutable authority inside the Workspace directory MUST be captured consistently at the common cut: Notebook heads and history (copying canonical Knowledge files and Git history unchanged with no interchange conversion or identity remapping), Light App databases and sealed local recovery copies, authored configuration revisions, and mutable catalog/MCP process data (while whole-data-root backup retains canonical catalogs, Skill snapshots, restricted original Plugin roots, and mutable MCP data). For cold Light App capture, the held cut MUST prove that no WAL/SHM or open native App handle exists, or the native owner MUST admit the App as a participant with writable final-close ownership before the hold. The bundle closure includes retained Threads, Turns, Items, Materials, Artifacts, Knowledge/Sources, local Light Apps, catalog payloads, work observations, restricted bodies, Pending Requests, and immutable model-I/O message/part blobs and native transcripts. It excludes Vault material/keys, authentication credentials, User Memory, live Server Knowledge/configuration, and physical execution bindings; captured server excerpts and pinned AEP/configuration snapshots remain historical evidence, user content is not secret-sanitized, and external/remote bytes and retained Worker volumes are reported omitted or unavailable unless explicitly covered (never substituted by Git or Artifacts).

Each capture allocates one independent `wsbak` UUIDv7 ([Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md#ids)) before copying or staging; exact retry retains that identity and fingerprint, while a new capture allocates a new ID. Capture performs only effect-free authority and capacity preflight before freezing and rechecking blockers, protects complete transitive snapshot roots (histories, manifests, definitions, prompts, message parts, and blobs) before selection, keeps the same fence across control SQL, Light Apps, and opaque roots while copying immutable bytes through Storage, validates the manifest file set, inventory digest, SQLite integrity, identities, required features, complete reference closure, and Light App/presentation digests before sealing, and for `purpose: 'backup'` synchronizes the bundle and manifest before publishing the durable seal and releasing content protection (`purpose: 'move'` stops at `verified` without publishing a backup seal).

Cold Workspace capture from a verified data-root backup directory (`backup.create`) is strictly read-only: it takes no parent kernel lock, verifies the parent manifest before reading, checks copied bytes against parent digests, and reverifies the parent inventory digest afterward, refusing any change with `parent-backup-invalid`. Workspace deletion captures a recoverable operational snapshot and separately produces the sealed audit-closure export under [Audit, Usage, And Evidence Records](20260703-audit_usage_evidence_records.md) before removing live Workspace state.

#### Common Root Cut

A whole-root hot backup requires every active writer, migration, file creator or replacer, and content publisher to join the global pause, including kernel, service, extension, Workspace, User and App owners. Drain acknowledgements and hold the pause through sequential snapshots and verified inventory. Refuse if a required owner cannot join. Closed files behind the creation gate need no writer. Copy immutable Light App snapshots byte-exactly. Cold archive includes committed WAL. Before admitting ingress after restore, validate the source deployment, manifest, file inventory and each owning ledger under exclusion.

#### External Trigger Admission History

Same-deployment backup and restore preserve the immutable external-event admission schedule, opaque event key, source Turn, and scheduler entry links owned by [Scheduler Recurring Event Triggers](20260711-scheduler_recurring_event_triggers.md); missing historical references remain explicit and are never synthesized, queued, or replayed.

Whole-data-root backup (`backup.create` and `backup.verify` in `packages/app-api-schemas/src/data-root-admin-operations.ts` under deployment-administrator admission and local handles) is separate from per-Workspace backup. Every newly initialized data root mints and persists an independent `dep` UUIDv7 deployment ID before producing scoped records (preserving it across boots). Each new data-root backup or storage conversion allocates an independent `drb` UUIDv7 before copy or staging and retains it in the manifest, verification result, and migration report. Cold backup with NanoCore stopped produces a `consistency: clean` copy as the baseline bootable whole-server recovery input, preserving Core users, owners, memberships, invitations, token metadata, Light App directories, and presentation stores. Hot whole-server backup holds one continuous Core capture pause across tree copy, SQLite snapshots (including Light Apps created after startup and their referenced immutable definition bytes read from the captured DB), and manifest verification, recording `consistency: crash-consistent` without cross-store transaction atomicity or a bootability guarantee.

### Export

#### Personal Data And Audience Coverage

Analytical Workspace export creation (`workspace.export`) and archive download (`workspace.archive-download`, `GET /api/app/workspaces/:workspaceId/exports/:exportId/archive`) require the creating actor's current usable deployment-administrator `workspace.export` decision through the common Policy Kernel authorizer ([Policy](../core/policy.md)). Workspace membership, ownership, or `workspace.read` grants no export or download authority. Every server-managed export handle remains private to its recorded creator; another administrator cannot substitute, and handle lineage admits only the current deployment or its recorded predecessor. Authorized export collects the complete Workspace closure, including private Threads, Items, Artifacts, Materials, observations, and private-derived content, with no caller-selected audience; User Memory and live Server Knowledge remain excluded under [Personal Memory And Knowledge Learning](20260909-personal_memory_and_knowledge_learning.md). Retrieval trace reads and export apply containing-record audience and current Source access without leaking restricted metadata; retention, suppression, legal holds, and private-origin restrictions govern payloads, previews, counts, and diagnostics without widening raw-evidence visibility.

Export creation exclusively owns a previously absent export root, writes `openkit-workspace-export.json` last, verifies the completed tree before returning, and removes only its owned root on failure. Snapshot and body digests describe the exact exported bytes. Public analytical surfaces are `workspace.export`, `workspace.archive-download`, and Vault-reference rebind. `@openkit/core-client`, Web, and the administrator CLI use the streaming archive binding without base64-encoding archives or exposing server paths, while remote MCP omits `workspace.archive-download` from discovery and refuses calls before file processing ([Operation Definition](20261002-operation_definition.md#remote-mcp-projection)). The bundled CLI in local mode creates the caller's destination as an exclusive non-link regular file (`O_CREAT|O_EXCL`, mode `0600`), refuses overwrite, and leaves an exclusively created partial file in place on transfer failure rather than racing pathname cleanup.

Export accounting derives its `cap` UUIDv5 identifier from exact JSON input `["storage_export", exportId]` at the accounting trigger ([Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md#ids)). Files and bytes measurements allocate independent `use` UUIDv7 rows with category `storage`, unit `files` or `bytes`, exact quantity, model/provider, source `workspace-export-inventory`, and normalized `sourceIds`. Verification and replay reuse the existing call and full stored-equivalent measurement linkage without duplicate rows or synthetic success.

Analytical Workspace export includes complete canonical Workspace, Thread, Turn, Item-revision, and Turn-event history (including completed request/response Items whose responsible-user IDs remain non-authorizing lineage), exact Artifact original bodies/metadata and version-keyed Reviews, Material rows/inline revisions/Thread Material bindings (including unbound history) and worker Context Package trace coverage (retaining distinct original, representation, and delivered digests without current-source reconstruction, plus derivative provenance when included and explicit declaration of omitted rebuildable caches), AgentSession records, current Goal records/cards/immutable Plan bytes and digests/Goal Task links/Task terminal facts (where a missing Task target stays unresolved evidence rather than dangling lineage, and retired predecessor Goal/steering tables are absent), retained Turn input files (excluding client drafts, private staging, and live transfer authority), and accepted Knowledge pages and Sources materialized from one published Notebook revision (never raw `notebook.git` or actionable Knowledge Proposal/Review owners). Optional complete published-history export MUST admit the complete historical source/audience/suppression closure and exclude candidates, reflogs, config, hooks, and credentials. Only completed-Item snapshot compaction permitted by [Storage](../core/storage.md) may elide superseded segments when replay equivalence is preserved and the manifest declares the compaction and elided segments.

#### Work Observation Portability

Every Workspace SQLite table and durable file/state family MUST be classified as portable or explicitly nonportable in the same change that introduces its storage ownership, enforced by the Workspace SQLite coverage guard (`workspace-export.ts`) and explicit Core-family and app-local tests. Under current administrator authority and the restricted-evidence export exception ([Audit, Usage, And Evidence Records](20260703-audit_usage_evidence_records.md)), admitted restricted original work bodies travel intact in the analytical Workspace export while unpublished chunk staging remains nonportable runtime state. When `env.bound.payload.assistantSkillAdmission` is present in an exported work observation, its `{catalogRevision, skillId, versionId, contentDigest}` tuple travels as unchanged historical source metadata without resolving against a target catalog or granting capability.

Recurring Workspace families in Core SQLite are captured under the Workspace mutation fence into the three recurring JSONL files, excluding resolved deployment-local Workspace root and `cwd` paths from admission payloads and retaining compact expired ranges without expansion; all exported recurrence and external-event keys, actors, requests, and queue IDs are inert historical provenance. Portable catalog export (`records/agent-resource-catalog.json`) carries Workspace Skill metadata/history and retained tree payloads (`skill-payloads/<skillId>/<digestHex>.json`), Plugin and MCP non-secret metadata/unavailable-content lineage, and non-secret Server catalog references, while excluding `catalog/plugin-snapshots/`, raw `plugin.json`/`mcp.json`, `catalog/mcp-data/`, source receipts, runtime materializations, and launch authority. Export never contacts an MCP server, fetches a source, starts a process, or acquires original Plugin bytes. `assistant.resources` references and normalized UI answer-source Item references travel as non-executable lineage under private-Thread audience rules. User-authored Skill, Artifact, Knowledge, Source, and config bytes are unsanitized user content and MUST NOT be described as DLP- or secret-sanitized. Exported `config/workspace.jsonc` carries `workspace.policy.mediation` assignments, prohibitions, and managed-boundary facts with `openkit.workspace-resource-policy.v1` even after the last positive association is revoked; audience filtering never strips a managed Thread restriction, and source principal IDs grant no target membership. Generative export holds the Workspace mutation fence across Light App inventory, per-app SQLite databases, and presentations, serializing captured bytes directly (never paging the public API), projecting app-local AuditEvents into the portable Audit family, omitting app command receipts, credentials, grants, and local migration recovery snapshots, and exporting reusable Light App template definitions in the resource catalog (`lightApps`) without business rows or execution bindings.

#### Non-Portable And Redacted State

System-managed Vault material, provider/runtime credentials, session cookies, and access tokens MUST NOT appear in an export. Resolved agent setup exports only a strict non-secret redacted whitelist (`setup-ledger.ts`). Active/removed memberships, invitations, auth sessions, personal preferences, user-local notifications, deployment-local command receipts, Pending Request lifecycle tables, snapshot coordination, execution journals (`control_executions`, `control_execution_steps`), derived SQLite databases/indexes, staging roots, caches, scheduler queues, execution attempts, backend residency, and native AgentSession handles/host paths/compatibility keys/policy-snapshot bindings/storage-slot references are excluded or reduced to redacted summaries.

The analytical export excludes `workspace_work_inputs`, which holds original scheduler input bytes for admission and replay. Operational backup and MOVE retain those rows as Workspace database state.

### Restore

#### Backup And Restore

Core `core-workspace-recovery/v1` execution-journal records own restore and MOVE decisions and results across crash restart; original admission identity and revision remain distinct from journal revision and stage order, binding the original command, source, candidate, purpose, backup, account map, and durable Core proof bytes (`workspace-recovery-journal.ts`), while keeping preparation open until a terminal decision and recording any later revocation or inspection as a separate linked entry.

Same-deployment restore selects a sealed backup and matching Workspace and source-deployment identity under current administrator authority (which confers no ordinary content access) and proved absence of affected writers; a moved-out Workspace refuses restore (reactivation is separate). Restore verifies the completion seal, release/features, confined regular-file paths, inventory digests, SQLite integrity, Light App schemas/data/definition digests, and presentation/Item references before effects, without executing packaged content or contacting external mounts. It stages privately on the destination filesystem while preserving the predecessor, opens staged databases in existing-only mode without exposing staged data to discovery/indexes/execution, preserves current server users/ownership/membership/grants and provable safety constraints (applying current retention expiry without extending retention or restoring suppressed content), marks captured in-flight Turns and executions as interrupted with unknown effects preserved and no replay or automatic queue/timer/schedule restart, and publishes the complete Workspace through staged placement before admitting traffic and rebuilding disposable projections.

When the current Workspace database is lost, restricted recovery from verified backup `B` requires explicit administrator acknowledgement disclosing that post-`B` Workspace-owned suppression, restrictions, and holds cannot be proven and may be lost, records the unprovable window from `B` capture start to detected loss in Audit and the recovery report, and opens the Workspace with automation, channels, schedules, and executable catalog bindings disabled until explicit administrator readmission.

#### Skewed Owner Histories

A valid ledger validates format and identity. Only exact continuity, reauthorization or reconciliation can restore a current binding, challenge, credential, enable generation or notice. When the kernel is ahead, settle an exact original intent from its receipt and recover missing published bytes or recipient claims only with matching evidence. An enqueued or possibly sent notice beside older communication state stays unknown. When a service or extension is ahead, inspect missing kernel grants or receipts. Historical absence cannot authorize dispatch. Validate trigger cursors against event identity at the saved append position. Rescan with deduplication or expose the gap. When both are behind, fence the predecessor and remote writers, restrict ingress to recovery, and fence or reauthorize superseded AuthSessions, Tokens and bindings before ordinary effects. Hold possible duplicate delivery and preserve an independently provable path for administrator re-enrolment. Missing audience proof refuses attach, purge and disclosure. Keep imposed Policy restrictions when security trigger state is lost.

#### Deleted Workspace Recovery

Deleted Workspace recovery restores the original Workspace identity and reactivates its deleted registry row from the final fenced operational snapshot captured at deletion, preserving original `privateOwnerUserId` values, current server authority, legal holds, and eligibility of the original active owner or a current administrator. It returns the common snapshot report (`command: 'restore'`) with `restored`/`none` after registry and serving activation (or `pending`/`finish` only for a proved sealed unfinished continuation), omitting the full capture inventory and repeated closure lineage while retaining required request proof. The report uses the original admission request selection. The caller explicitly repeats that same deleted-recovery request under current owner-or-administrator Kernel authority; required request, closure and admission lineage remains retained even when omitted from the response.

Whole-data-root restore is a stopped-server operation that verifies the backup manifest and files before same-filesystem staging and rename replacement, preserving active recurring definitions, cursors, pending occurrences, and scheduler rows together, and then runs boot-time layout verification, SQLite integrity checks, migrations, derived-index rebuild, and runtime restart recovery ([NanoCore Bootstrap Readiness](20260704-nanocore_bootstrap_readiness.md)). Moving a data root by repointing server configuration is supported because product records embed no absolute data-root paths; when a move changes the deployment ID, the new deployment records the predecessor ID so later exports retain truthful lineage.

### MOVE

Cross-deployment MOVE transfers one Workspace between deployments with an admitted matching bundle release and database format, preserving the Workspace, Knowledge Base, and all in-Workspace history identities; the operator MUST choose at most one destination per move bundle, and the target MUST refuse unrelated identity collisions in its registry, final paths, staged candidates, retained tombstones, or global IDs without reminting or falling back to COPY.

Source MOVE freezes the Workspace nonwaitingly (keeping passive Pending history inert under the claim/delivery fence), captures and synchronizes a verified `quiescent` bundle without transferring processes/queues/capacity/attachments/sessions, and in one source-local control transaction commits the move seal fact and `moved-out` disposition bound to the backup ID and manifest digest. Finalization, abandonment, and reactivation share one source-local operation fence requiring the current matching `moved-out` revision, backup ID, manifest digest, and open publication right; the durable marker publishes only after the source transaction commits, releasing capture protection while keeping the source as an inspectable read-only tombstone with its bytes and holds intact. Explicit source reactivation under that same fence requires current authority, the expected `moved-out` revision, target absence/fencing, and retirement of transferable copies, durably closing the capture's publication right and retiring candidate/seal exposure before reopening admission and recording Audit lineage.

Target MOVE admission takes a request identity, sealed move bundle, target owner (defaulting to the importing administrator), and explicit source-to-target member map (`workspace-move-mapping.ts`). The complete resolved map including the owner MUST be injective and reference existing active target accounts; unmapped members are dropped and listed in the report, never inferred from names, emails, or matching local IDs, and invalid raw account values are reported by position only without echoing raw account strings. Historical `ActorRef` values remain source-qualified non-authorizing attribution; private Thread audiences rebind only through explicit member mappings (reserving the owner target for injectivity does not automatically map unmapped private audiences to the importing owner), while unmapped private audiences remain unavailable except to separately owned administrator inspection. Source roles, Policy decisions, grants, invitations, tokens, and administrator eligibility never travel.

On the MOVE target: pinned AEP/configuration bytes remain historical while new work resolves current target Agent/configuration supply; Vault references export non-secret metadata only and arrive unbound until secret material is re-provided to the target Vault (accepting secret input only, returning redacted metadata, and retaining no secret material in rendered Web state) with fresh target grants; Worker volumes and native session continuity are omitted/unavailable; Server Knowledge and external Sources remain source-qualified unavailable provenance until separate target admission; local Light App data, schemas, definitions, recovery copies, and presentations are validated and preserved (never reconstructed from rendered views); retained Skill payloads and catalog history travel with executable Plugin/MCP bindings disabled until fresh target configuration, source reimport, credentials, and administrator stdio activation; and schedules, external triggers, channels, Pending Requests, and unfinished executions remain inert history without automatic reconnect, catch-up, signal enqueue, approval reissuance, source-receipt reuse, or execution replay.

The administrator move-admission request identity and input fingerprint (source deployment, backup ID, manifest digest, resolved target owner, and canonical source-sorted member map) bind candidate ownership before placement. Target admission checks any committed same-request result first (returning it on matching fingerprint or conflicting on changed input), verifies the sealed move bundle and account map, stages privately through ordinary target control transactions while preserving original immutable digests and recording import provenance, synchronizes and places the unpublished stage before registering the Workspace, owner, and members in one target server transaction (never fabricating registration from directory discovery), and activates the Workspace with imported automation and executable bindings disabled.

Before MOVE, deletion or same-ID restore, freeze submissions, fence affected writers and sends, and drain acknowledgements. Export native content and permitted inert history. Leave routes, credentials, grants, live queue and outbox at their source owners. Recheck registry revision at use and target identity, current account and local grant at admission. Unavailable-owner cleanup stays on the original lifecycle step. Invalidate stale refs before reactivation and report incomplete deletion until every required purge is proved. Discord history stays retained under its own policy, with inert links to departed work.

### Import

No crash-recovery reader exists for a portable-import publication window. Imported pages or historical records never import another user's review authority, automatic capture settings, or source grants. In any retained or migrated history, Approval, `PermissionDecision`, and `VaultGrant` rows are historical evidence only: `apr_imported_` is a reserved non-authorizing namespace rejected by target Approval creation, canonical imported VaultGrants carry immutable `issuance: 'imported-history'` under [Vault Secret Injection](20260703-vault_secret_injection.md), and effect consumers MUST reject any authority tuple carrying `apr_imported_` or a grant without `issuance: 'target'` even after Vault-reference rebinding.

## Archive Format

The primary analytical export unit is one Workspace directory tree transported as one Zstandard-compressed POSIX USTAR archive (`.openkit-workspace.tar.zst`, media type `application/vnd.openkit.workspace-export+tar.zstd`) with no wrapper directory, second manifest, or transport record. Archive download reverifies the tree, orders paths canonically, and streams tar then Zstandard without buffering the whole archive, using directory mode `0755`, file mode `0644`, zero `uid`/`gid`/`mtime`, and empty `uname`/`gname`. Archive production and verification admit PAX path records for valid paths exceeding USTAR field lengths; short paths retain unchanged USTAR bytes, while longer canonical file and derived-directory paths use standard per-entry PAX `path` records. Root `openkit-workspace-export.json` uses the common record envelope (`recordType: 'workspace-export'`, `exportFormatVersion: 1`), validated with `requiredFeatures` before family processing. Admit only the supported baseline form. Each `contentInventory` entry (`packages/config-schema/src/workspace-export.ts`) admits only `{path, bytes, digest}` for every non-manifest file once (rejecting unknown entry fields), and manifest `contentDigest` is the SHA-256 of the exact original validated JSON serialization of that inventory (a named retained exception to JCS re-serialization). The verifier reads each inventoried file once and returns those verified bytes. Unknown descriptive fields on the manifest or portable records are ignored and never forwarded into effects or public views, while unknown core or required semantics fail closed.

Portable Workspace database rows serialize as strict JSONL or JSON records rather than SQLite files (excluding `control_executions`, `control_execution_steps`, Pending Request tables, and snapshot coordination):
- System-owned `records/workspace-record.json` (identity and lifecycle only, no `name` or `defaults`), editable `config/workspace.jsonc` (owning `name`, `defaultAgentId`, and `workspace.policy.mediation` restrictions with `openkit.workspace-resource-policy.v1` without membership), custom Knowledge schema, and native OKF pages (`openkit.knowledge-git-notebook.v1` and `openkit.knowledge-owner-scope.v1`); incompatible internal exports are regenerated rather than upgraded.
- Mandatory Material and Review JSONL files (present even when empty): `records/workspace-materials.jsonl`, `records/workspace-material-revisions.jsonl` (exact inline canonical UTF-8 `content`, never a payload directory, `contentRef`, or duplicate byte file), `records/thread-material-bindings.jsonl`, and `records/artifact-reviews.jsonl` keyed by `(workspaceId, artifactId, artifactVersion)`.
- Mandatory Vault injection files (present even when empty): `records/vault-injection-plans.jsonl` and `records/vault-injection-receipts.jsonl`.
- Mandatory recurring files with `workspace.recurring-triggers.v1` (present even when empty): `records/recurring-schedules.jsonl`, `records/recurring-occurrences.jsonl`, and `records/recurring-expired-ranges.jsonl`.
- Mandatory resource catalog projection with `agent.resource-catalog.v1` (present even when empty): `records/agent-resource-catalog.json` (strict whitelist, never raw `catalog/catalog.json`) and retained Skill trees at `skill-payloads/<skillId>/<digestHex>.json` using the bounded `openkit-tree-v1` directory/file/base64/executable envelope.

Operational Workspace backup (`apps/nanocore/src/storage/workspace-backup-bundle.ts`) is an offline-verifiable static SQLite snapshot and local content closure directory with root `manifest.json` (`format: 'openkit-workspace-backup'`, `schemaVersion: 1`, `purpose: 'backup' | 'move'`) and `seal.json` (`format: 'openkit-workspace-backup-seal'`, `schemaVersion: 1`), distinct from analytical export and Knowledge packages. Streamed operational bundles use bounded Zstandard-compressed POSIX USTAR (`application/octet-stream`) with no wrapper directory and the identical manifest, seal, and inventory (metadata mode `0600` and integer inventory modes `<= 0777`). Current default operational bundle bounds are `2,147,483,648` bytes per file, `34,359,738,368` total bytes, `200,000` inventory entries, and `16,777,216` bytes for manifest/seal metadata. The local digest-object pool is separate from a standalone bundle and never accepted as a flat bundle root; both owned local snapshots and standalone bundles supply independently acquired verified copies through the same callback-scoped manifest/file interface, applying path, link, size, original-byte-digest, and reader-lifetime checks to both, and recovery proof bytes are persisted through the Core immutable content owner before SQL references. The manifest binds backup, Workspace, source-deployment, and established Knowledge Base IDs (never allocating an absent KB on read), prior MOVE lineage, captured Workspace revision, start/end timestamps, consistency (`workspace-consistent` for hot local capture or `quiescent` for MOVE), every snapshot/content file once with confined relative path, byte length, raw SHA-256, and integer mode (including database snapshots and transitive manifests while excluding root `manifest.json` and `seal.json`), `inventoryDigest` as the SHA-256 of the exact serialized original inventory (a named retained exception to JCS re-serialization), coverage (authorities, roots, omitted projections/volumes, and typed external dependencies with closed availability `available | unavailable | omitted`), and account provenance (source owner, members, and private-audience references without credentials or grants). `seal.json` binds backup ID, purpose, and exact manifest digest as a completion marker (not a cryptographic signature). It is not source-authentication proof; transfer confidentiality and authenticity remain the administrator's responsibility. Unsealed directories MUST NOT restore or import. Unknown descriptive manifest fields confer no authority; unknown core fields or required features refuse admission.

Whole-data-root backup (`openkit-data-root-backup.json`, `schemaVersion: 1`, `backupFormatVersion: 1` in `apps/nanocore/src/storage/data-root-backup.ts`) records capture timestamps, source deployment, mode/consistency (`clean` or `crash-consistent`), required features, and per-file inventory digests; its verifier checks every file's path, link absence, size, and SHA-256 digest and rejects extra/missing files or unknown required features, but does not independently recompute the manifest `contentDigest` or authenticate the manifest.

## Errors And Failure

#### Scoped Freeze And Blockers

Destructive restore, MOVE, deletion, and Workspace archive never wait for or interrupt active work; authoritative blockers refuse immediately, and borrowing a freeze never admits an older sealed generation or alters automatic capture/MOVE rules. Cold Light App reads have no normal-at-rest waiver, though ordinary non-capture cold reads do not require a capture freeze.

| Family | Blocker versus inert history |
| --- | --- |
| Turns and Goal/Task work | Nonsealed Turns and unacknowledged terminal publication block. Ready Goals, cards, and closed history alone are inert. |
| Worker attempts and residency | Open/closing attempts, handoff, unproved cleanup, and unresolved physical bindings block. Cleanup-proved idle storage is inert for capture; replacement still requires physical exclusion. |
| Pending Requests | Claimed execution without disposition and active raising/delivery block. Passive unclaimed or final undelivered records are inert only under the claim/delivery fence. |
| Recurrence and scheduler admission | Active preparation, uncertain publication, and nonterminal Turns block. Future timers and merely queued/denied entries are inert under the dispatch fence. |
| Synchronization and materialization | Active preparation/apply and an approved Plan without proved Result block. Undecided Review, finished Result, and immutable snapshots are inert. |
| Snapshot and export | Generation, original-byte acquisition, candidate placement, and unfinished recovery block. A stream holding only independent verified sealed bytes is inert. |
| Knowledge, Source, catalog, Light App, and retention | Mutable head, reference, namespace, Git, and GC publication block. Immutable finished versions and read-only derived indexes are inert. |
| Capability calls and callbacks | Unsettled calls, owed receipts/accounting, and possible later writes block. Historical unknown contact is inert only with proved closed execution and writer exclusion. |
| Holds and unavailable facts | Legal holds follow their nondestructive/destructive rules. Unclassified writers, unreadable evidence, and ambiguous rows block. |

Public lifecycle refusals return HTTP `409` with `workspace_blocked` (`retryable: false`) or `workspace_frozen` (`retryable: true`, with no retry-time promise), carrying `workspaceId`, lifecycle `operation`, `retryable`, and `blockers` (`WorkspaceLifecycleBlockersDetailsSchema` in `packages/app-api-schemas/src/workspace-freeze.ts`, which defines the closed operation, blocker-kind, reason, and quick-action sets). Authorized blockers expose only typed identities and existing quick actions; all hidden private blockers and unreadable enumerations collapse into a single identity-free `unavailable` row without leaking counts, paths, commands, credentials, or previews. Quick actions recheck current authority, request identity, and revision, do not prove physical cleanup, leave blockers without an executable stop inspect-only (`#537`), and require explicit user retry after resolution.

Export preflight and offline verification fail closed before publication or admission on: any unresolved `user-input-request` Item (reporting blocking Item IDs safely); missing, mismatched, or contradictory creator `workspace.export` authority or `cap`/`use` accounting rows; duplicate, noncanonical, or unsafe paths, symbolic/hard links, special files, missing or extra files, or byte-length/digest mismatches; retired `records/knowledge-observations.jsonl`, `records/knowledge-claims.jsonl`, `records/knowledge-conflicts.jsonl`, `records/knowledge-proposals.jsonl`, `records/knowledge-proposal-reviews.jsonl`, `records/injection-plans.jsonl`, or `records/injection-receipts.jsonl` paths (refused rather than translated, merged, ignored, or dual-read); removed `workspace.json`, record-owned `name`/`defaults`, missing config `name`, or duplicate moved-field ownership; unknown observation types or unsupported `requiredFeatures` (while cold whole-root backup copies bytes without interpreting observation features); missing or tampered retained Skill payloads (while legitimately purged versions keep explicit unavailable history without creating an executable entry); unknown Light App native tables/columns, missing definitions, unresolved app authority, or inconsistent Generative UI presentation/Item closures (where a presentation with an absent reserved Item is valid `unpublished` history, but an Item referencing a missing/wrong presentation, a mismatched reference, or duplicate publication is `inconsistent` and never repaired); any UTF-8/base64 conversion or current-source reconstruction of binary originals or absent historical Context Package bytes; missing, extra, duplicate, corrupt, or contradictory Turn input payloads; or a native accepted recurring occurrence whose canonical Turn is missing or contradictory. Validation and refusal MUST occur before any row, catalog, scheduler, session, or effect mutation.

Logical journal completion never proves physical close, serving readmission, or unknown-effect success. Failed copy or verification publishes no seal, preserves source authority, and reports the failing authority; after restart, a crashed automatic unsealed capture abandons its publication right and releases its pins, while manual capture retains explicit inspect/finish/abandon. Missing required local bytes fail capture/restore (while valid reference-only external Sources may be unavailable), and a new app or unavailable authority during hot whole-root capture fails that attempt. Pre-publication restore or MOVE failure leaves prior readable authority unchanged, and late copy/sync failure during private candidate preparation refuses canonical replacement; an unavailable close seal proves close only. Interrupted or uncertain publication quarantines only the affected Workspace with its candidate/predecessor evidence intact (one successful verification never clears an unrelated layout or database refusal), while healthy siblings boot and corrupt shared server authority refuses whole-server boot. Before source MOVE seal commit, failure keeps admission closed pending fenced retry/cancel; after commit, only explicit reactivation reopens admission, a crash during reactivation keeps admission closed, and later finalizer retries return the abandoned/reactivated disposition without publishing a seal or bundle. On the MOVE target, an unregistered placed candidate remains quarantined until exact same-key/fingerprint retry finishes it or fenced administrator discard durably closes its finish right and retires it (respecting legal holds and never discarding registered authority). Legal holds block Workspace deletion until released; deleted recovery never acknowledges lost safety on the caller's behalf, and legacy completed deletion requests holding only analytical export bytes refuse with `unavailable`. Whole-root crash-consistent restore may be rejected at boot if a ledger is torn (Item/event readers may discard an incomplete final fragment, while other authoritative ledgers fail closed).
