# Workspace Backup, Export, Import, And Data-Root Migration
Workspace export format: V3

## Current Product Boundary

Workspace export serves external analysis, evaluation, audit, and other external use. Lossless re-import into OpenKit is not its acceptance requirement. Existing analytical import behavior and regression obligations remain; they do not define operational recovery.

Before `v0.1.0`, each Workspace MUST support local hot backup, verified same-deployment restore, and an operator-driven offline move. [The operational decision](../decisions/20261019-workspace_backup_restore_move.md) activates the previously deferred detailed design. Copy/remint, remote synchronization, optional native-volume continuity, and whole-server hot-backup changes remain deferred. Backup And Restore and Workspace Move below own these operations.

The predecessor Goal tables and the two Goal steering tables leave both the portable inventory and the excluded inventory with the one-way Goal removal. The current records of [Goal](20261002-goal.md), its cards, its immutable Plan versions with their bytes and digests, its Goal Task links and the Task terminal facts that wake it are portable work data ([decision](../decisions/20261003-current_goal_records_are_portable.md)); import restores no approval authority, and a Goal Task link or Task terminal fact whose Task is missing from the archive stays unresolved evidence, not dangling required lineage. S3-compatible storage, cloud drives, and Litestream remain later options, not selected backends. Local Workspace recovery now has the snapshot and restore contract below. See [the engineer's decision](../decisions/20260928-goal_freeze_and_export_backup_boundary.md). The export-versus-backup separation in that decision stays.

## Knowledge Packages And File-Preserving Backup

[File Storage And Knowledge Packages](20261018-file_storage_and_knowledge_packages.md) owns standalone Knowledge Base interchange. Its package shares canonical `raw/`, OKF page, schema, index and log paths; its published `sources/` pointer pages preserve Source authority and its manifest carries derivative metadata. Export packs admitted files plus a manifest; import validates, remints owned identities and verifies digests. That contract gives Workspace export no new round-trip obligation.

Backup copies the same canonical Knowledge Base files unchanged within its declared consistent snapshot, including local Notebook history. Backup performs no interchange conversion or identity remapping. Remote references remain metadata unless backup explicitly covers their external bytes. The package specification names each necessary layout difference; backup/restore retains its existing integrity, security and restore-performance owner.

## Execution-Host Volume Coverage

[Persistent Worker Volumes](20260910-persistent_worker_volumes.md) owns generic retained execution-host volumes. A backup/export that covers only NanoCore files must explicitly report those volumes omitted or unavailable; Git and accepted Artifacts are not substitutes for their untracked, ignored or native data. Consistent whole-volume export requires quiescent writers and preserves the source access audience. Restore imports data into a new checked storage association and grants no live process, credential, attachment or native-session authority.

## Summary

The primary export unit is one workspace. Workspace export format V3 is a self-describing, offline-verifiable directory tree whose manifest commits to the exact portable file set and bytes consumed by import. Imports consume only those verified bytes, enforce required features fail-closed, preserve or remint the workspace id with recorded lineage, remint collision-prone target identities and references, and coordinate staged files with transactional Core replay and synchronous compensation on failure. A portable Workspace export carries product truth and actor lineage but no deployment-local access grants. Ordinary portable import records the authenticated importing user as the new canonical owner and only active member. Deleted-Workspace recovery follows the owner distinction in Verification And Import. Operational backup captures one Workspace's consistent static databases and reachable immutable content. Restore preserves its identity; move uses the same bundle and leaves a moved-out source tombstone. Whole-server recovery retains its separate boundary. Data-root migration is a config repoint validated at boot. System-managed Vault, provider, and runtime secrets never enter workspace exports; exports carry only non-secret vault reference metadata that lands `unbound`. User-authored portable content is not a sanitized or DLP-scanned channel.

## Goals

- Keep analytical Workspace export independent of a binary database format.
- Recover or move one Workspace without restoring the source server.
- Make every export verifiable offline against its own manifest.
- Preserve complete authoritative workspace history and file-backed knowledge state.
- Keep imports safe: fail closed on unknown semantics or incomplete lineage, leave no partial state after a caught synchronous failure, and document the remaining process-crash window explicitly.
- Keep system-managed Vault, provider, and runtime secret material, backend-native handles, derived indexes, and server operational state out of workspace exports.
- Define backup and restore procedures that lean on rebuildable derived state instead of exporting it.
- Keep lineage truthful across export, import, and data-root moves.

## Non-goals

- Do not design incremental, differential, or continuous backup.
- Do not design live replication or multi-deployment sync.
- Do not define a deep compaction model beyond the item-log snapshot allowance in `docs/core/storage.md`.
- Do not redefine ownership scopes, envelope fields, retention classes, or vault semantics owned by sibling specs.

## Background

`docs/core/storage.md` establishes file-system-first storage with rebuildable SQLite indexes and lists the backup, export, import, and compaction model as an open point. `docs/specs/20260703-storage_layout_record_ownership.md` fixes the ownership tree, and `docs/specs/20260703-audit_usage_evidence_records.md` places workspace-lineage audit rows in workspace scope so exports are self-contained. This spec defines the portable format and the validation, backup, restore, and migration contract.

## Personal Data And Audience Coverage

Ordinary Workspace export carries shared eligible Threads, Items, Artifacts, Workspace Knowledge and sources. An ordinary caller MUST exclude User Memory, Server Knowledge and other users' private project Threads, including their raw bytes, previews and derived files. Directory membership is not an export permission. A currently usable administrator credential's export of a Workspace includes that Workspace's private project Threads and private-derived content under the administrator eligibility rule in [Core Permissions](../core/permissions.md). User Memory and Server Knowledge remain non-portable record families for this Workspace bundle. `20260909-thread_visibility_and_sharing.md` owns explicit current-user private-history export and reminted private import; `20260909-personal_memory_and_knowledge_learning.md` owns separate Memory/Server Knowledge OKF export. Workspace backup and restore require current deployment-administrator authority. They cover all retained Workspace audiences, including private Threads, without conferring ordinary content access. User Memory and live Server Knowledge remain outside this operational bundle. Existing portable coverage guards must classify these exclusions when implementation adds the records. Imported pages do not import another user's review authority, automatic capture settings or source grants.

## Decision

The export unit is one workspace, serialized as a plain V3 directory tree with an envelope-wrapped manifest and per-file digests. The canonical transported form is that exact tree streamed as `.openkit-workspace.tar.zst`; transport introduces no second manifest or server archive registry. SQLite never travels inside an export: portable source-of-truth rows are dumped as line-oriented records, and derived indexes are omitted so their existing owner can rebuild them at boot or on demand. Import is manifest-verified, fail-closed on unknown required features or incomplete lineage, and coordinated through same-filesystem staging, one Core transaction, and synchronous compensating rollback. This does not create a transaction spanning the filesystem and SQLite across a process crash. V1 and V2 are intentionally incompatible and rejected rather than migrated. Operational Workspace backup instead uses the control-store snapshot and immutable-content closure. Offline move preserves identities, closes the source, and requires fresh target authority. The existing whole-server procedures remain distinct. Data-root migration is supported by repointing server config and letting boot verification validate the moved tree.

## Contract / Expected Behavior

### Export Unit And V3 Manifest

- The primary export unit MUST be one workspace. Exports of other scopes are not defined by this spec.
- An export MUST be a directory tree. Its canonical transported form MUST be one Zstandard-compressed POSIX tar archive with extension `.openkit-workspace.tar.zst` and media type `application/vnd.openkit.workspace-export+tar.zstd`; the archived form contains the identical tree and no wrapping directory, second manifest, or transport record.
- The export root MUST contain `openkit-workspace-export.json`, carrying the common record envelope with `recordType: workspace-export`, workspace ownership and lineage, source deployment id, workspace id, export timestamp, `requiredFeatures`, and the content inventory.
- The manifest MUST declare `exportFormatVersion: 3`. Importers MUST reject V1, V2 and every other version; no compatibility adapter or in-place upgrade is defined.
- The content inventory MUST list every non-manifest file exactly once with its relative path, byte length, and SHA-256 digest. The manifest `contentDigest` MUST be the SHA-256 digest of the exact JSON serialization of that inventory.
- The verifier MUST reject duplicate inventory paths, links, unsafe paths, unsupported file types, digest or byte-length mismatches, absent listed files, and non-manifest files absent from the inventory.
- Export creation MUST own a previously absent export root, write the manifest last, verify the completed tree before returning it, and remove that owned root if any step fails.
- Export preflight MUST reject a Workspace containing any unresolved `user-input-request` before creating the export root. The V3 verifier and importer MUST independently reject any input containing one, including input produced by another implementation or deployment. Product-safe diagnostics MUST identify the blocking Item ids. Completed historical request and response Items remain portable lineage, but no portable import may reactivate a source responsible-user identifier as target authority.

Inventory entries admit exactly path, byte length and SHA-256 digest; unknown entry fields refuse whether or not the inventory digest covers them. Verification hashes the validated original serialized inventory, preserving supported original field ordering. Descriptive manifest and portable record readers ignore unknown descriptive fields without forwarding them into target effects or public views. Source snapshot digests are verified before normalization; only the accepted import remint rewrites owned references and recomputes package, trace and snapshot digests over the exact target representations written.

### Export Accounting Identity

The Workspace export accounting CapabilityCall derives `cap` UUIDv5 from exact JSON name `["storage_export", exportId]`. `exportId` is the exact recorded Workspace export identity; the literal retains the export-accounting purpose. Allocate only at the existing accounting trigger ([accepted allocation decision](../decisions/20261016-identifier_derivation_and_import_allocations.md)). Permitted inventory verification and replay reuse the same call. They validate its immutable attribution and the exact export inventory, without repeating publication or inferring success from identity.

Files and bytes measurements use independent `use` UUIDv7 and the [Capability Usage recorder](20260704-capability_usage_gateway_foundation.md#call-and-usage-identity)'s full stored-equivalence lookup. Match the same `capabilityCallId`, category `storage`, unit `files` or `bytes`, exact quantity, existing model/provider, source `workspace-export-inventory` and normalized `sourceIds`. An equivalent row retains its ID through reopen. Different measurements cannot collapse by ID shape or unit alone. Neither measurement derives identity from `exportId`. Inventory verification resolves the call and measurement linkage. Existing publication order, private-handle authorization, scoped portability, retention and unknown/partial-effect failures remain unchanged. Acceptance requires exact call/measurement joins, unchanged inventory and repeated verification without extra rows or effects. Incomplete publication fails closed.

### Required Portable Contents

V3 MUST include the complete canonical workspace history, not only current projections:

- the workspace record, thread records, turn records, every item revision, and the complete turn-event history
- artifacts with their canonical bodies and metadata, version-keyed Artifact Review history, and AgentSession records
- knowledge entries, knowledge sources, and registered source material

Generated Knowledge Proposal and Knowledge Review owners are actionable source-Workspace authority and MUST NOT enter the clone/remint export. Accepted Knowledge Pages remain portable as ordinary authoritative page bytes. Complete data-root backup and restore preserve Proposal and Review files without changing their Workspace identity; that operational backup path is not portable Workspace import. Export MUST omit, and import MUST reject, the legacy `records/knowledge-proposals.jsonl` and `records/knowledge-proposal-reviews.jsonl` paths rather than reminting, weakening, or silently ignoring them.

Import MUST reject the retired `records/knowledge-observations.jsonl`, `records/knowledge-claims.jsonl`, and `records/knowledge-conflicts.jsonl` paths before publication; it MUST NOT silently discard their content or convert it into canonical Notebook pages.

The Git notebook extension in `20260909-knowledge_notebook_editing.md` changes the content reader, not Workspace disclosure or actionable-authority exclusions. Ordinary export materializes selected authorized pages from one published commit; it never packages raw `notebook.git`. Optional notebook history export admits the complete requested published-history/source closure under current permissions and suppression, excluding candidates, reflogs, config, hooks and credentials. An inadmissible historical closure fails that optional export rather than leaking hidden objects. Complete same-owner backup retains Git plus its independently owned records under the operational recovery boundary.

When optional history is included, scope/ID reminting rebuilds affected notebook commits and page digests before rewriting dependent S61/S39 references. Without history, imported historical S39 selections retain the original notebook commit as source provenance only; their reminted delivered bytes/digests remain proved by the retained package, not a target Git lookup. Imported attribution and original commit IDs are provenance only; no maintenance setting or Review grant becomes actionable. A current-page-only import creates one initial target commit. Exact Observation subject pins use the same bounded current-tree closure as exact supporting page pins. If the archive omits the historical target bytes named by a subject pin, import refuses before publication. It does not retarget the assessment, drop it, or substitute current bytes. Ordinary later edits in the source Notebook can leave that assessment historical and inactive; current-tree export does not promise the omitted Git history. Historical S39 packages keep their exact independent delivery ownership and cannot be reconstructed from current notebook pages. Suppressed content cannot return through restoration/import. The Git notebook required-feature marker prevents older importers from treating history as ordinary files; implementation updates portability coverage guards with this contract.

V3 MUST include the complete Phase 1 Material and Artifact Review row graph under these exact record paths:

- `records/workspace-materials.jsonl` for every `WorkspaceMaterial`
- `records/workspace-material-revisions.jsonl` for every immutable `WorkspaceMaterialRevision`, including its exact inline canonical UTF-8 `content`
- `records/thread-material-bindings.jsonl` for every `ThreadMaterialBinding`, including unbound history retained by the source Workspace
- `records/artifact-reviews.jsonl` for every version-keyed `ArtifactReview`

All four paths are present even when their family is empty. The three Material paths are the only portable Material content representation: V3 MUST NOT invent a Material content directory, export a `contentRef`, or duplicate revision bytes as files. `artifact-reviews.jsonl` carries one row per `(workspaceId, artifactId, artifactVersion)` rather than the current Artifact-id-only file projection.

V3 MUST include all existing records from these three authoritative file-backed ledger families:

- knowledge observations
- knowledge claims
- complete knowledge conflict append history, not only the latest conflict projection

V3 carries immutable retrieval-trace files only within their owning Thread or Turn at the paths in Storage Layout. A trace read, ordinary export and direct record projection apply both the containing-record audience and the reader's current source access. A failed source check exposes no content or restricted identity metadata; the stored trace stays immutable. There is no separate Workspace Knowledge retrieval-trace ledger.

V3 MUST also include the exact portable workspace file state:

- the system-owned `workspace-record.json`, Workspace `config/workspace.jsonc`, and the custom workspace knowledge schema
- native OKF knowledge pages

The exported `workspace-record.json` carries no editable `name` or execution defaults. `config/workspace.jsonc` carries the Workspace name, shared `defaultAgentId`, and the other accepted portable Workspace composition. Export and import MUST reject the removed `workspace.json` path, a record containing `name` or `defaults`, a config missing its required name, or duplicate ownership of one moved field; they never translate the old shape.

Portable workspace-scope database rows MUST be emitted as strict line-oriented records rather than as a database file. This includes the accepted Material and Artifact Review families plus the implemented audit, capability and usage, repository and Git, permission and checkpoint, resolved setup and redacted Agent Environment Package, workspace synchronization and apply, worker-side MCP schema, vault-reference and grant, injection, and vault-use families. The workspace SQLite coverage guard MUST classify every table in `workspace.sqlite` as portable or explicitly non-portable. Core-owned vault and injection families remain explicit exporter, importer, and focused-test responsibilities; the workspace SQLite guard does not claim to inventory Core tables.

Workspace Export V3 MUST serialize the complete non-secret plan and receipt families at exactly `records/vault-injection-plans.jsonl` and `records/vault-injection-receipts.jsonl`. Both paths are present even when empty. The verifier and importer MUST reject `records/injection-plans.jsonl` and `records/injection-receipts.jsonl` as unsupported old paths; they MUST NOT translate, merge, ignore, or dual-read them.

The accepted Skill, MCP, and Agent Plugin catalog owners introduce the bounded portable projection below. Evaluation mechanisms remain outside export scope. Any later accepted design creating Workspace-owned durable records MUST classify them here, and the change implementing those records MUST update the existing file/state and SQLite coverage guards together with export/import; no implemented record family may be silently omitted.

### Work Observation Portability

Exports containing Turn work observations declare `openkit.work-observations.v1`. Each included Turn retains its `observations.jsonl` beside its Item file, with the directory-level required-feature marker and immutable capture binding preserved. This is distinct from Knowledge observations. Export/import classify the file in existing exact inventory and coverage guards; an unknown observation type or unsupported required feature cannot be silently processed or dropped. Cold whole-root backup retains the file without interpreting its feature.

Current Thread audience policy and body-read authorization apply before collecting portable bytes, and the restricted-evidence export exception of docs/specs/20260703-audit_usage_evidence_records.md governs restricted originals. Other users' private Threads and their observations/content remain excluded for an ordinary caller. A currently usable administrator credential's export includes them under the administrator eligibility rule in [Core Permissions](../core/permissions.md). Admitted original bodies of retained work data, including restricted originals, travel intact in the portable export and import restores them intact, so that a re-imported Workspace keeps the complete information it was exported with, rather than being exported as expired, reference-free records; existing evidence policy still governs held, unavailable, and already expired content, and an observation reference never grants content access ([decision](../decisions/20260924-restricted_bodies_travel_in_export.md)). Unpublished restricted chunk staging is non-portable runtime state, while complete committed content follows its EvidenceBundle owner.

Import remints observation IDs, their observation/Item parent anchors and owning Thread/Turn, and rewrites in-package reference scope/locators through exact existing maps. Existing AEP and origin-reference remapping stays consistent with the imported package; source-native identities are restricted provenance only. A body content digest continues to describe the unchanged body bytes. Digests of legitimately reminted owner records cannot substitute for identity maps. `corr` remains scoped to the reminted logical group, never a cross-import join. Server and excluded-owner references remain explicitly unresolved under source identity, never rebound by bare ID. Same-identity replay cannot resurrect lawfully expired bytes.

The canonical `env.bound.payload.assistantSkillAdmission`, when present, travels with the observation through authorized export and import. Its `catalogRevision`, `skillId`, `versionId`, and `contentDigest` values remain unchanged historical source metadata. They are not destination catalog references, must not be reminted through catalog maps, and must not be resolved against a target catalog by bare ID. This rule also applies after re-export and a later import. Observation, Thread, Turn, parent and owned reference identities still follow their existing remint rules, and `env.bound.payload.workspaceId` identifies the reminted owning Workspace. Import does not turn the historical Skill tuple into a target selection, admission, executable capability, or access grant. It does not require a live target catalog entry to interpret the historical tuple. Live Workspace `assistant.resources.skillIds` retain their separate catalog-map rewriting and unavailable-until-fresh-selection rules.

### Recurring Work Portability

The [Recurring Trigger contract](20260711-scheduler_recurring_event_triggers.md) selects required feature `workspace.recurring-triggers.v1`. Its implementation must include `records/recurring-schedules.jsonl`, `records/recurring-occurrences.jsonl`, and `records/recurring-expired-ranges.jsonl` even when empty, plus the associated Workspace AuditEvent rows through the existing audit representation. These Workspace-owned families reside in Core SQLite, so the exporter and coverage checks must explicitly include them; generic exclusion of Server operational records must not omit them. Export captures definition, immutable authored occurrence/range snapshots, attempt history and terminal outcomes under the existing Workspace mutation fence. The portable whitelist excludes resolved Workspace roots and working-directory paths from the admission payload: those deployment-local values are retained only by complete same-deployment backup, never imported as a target admission payload. Compact ranges retain their exact interval/count/coverage rather than expanding into unbounded files.

Portable import retains this graph only as inert imported history under existing imported-history provenance. Preserve source definition status, cursor, actor, request and queue identity as non-authorizing historical facts; no imported row may enter active scanner selection, admission retry, command replay or the AutomationIdentity resolver. Workspace and Thread/Turn references follow existing import maps. Remint every schedule ID through a target import map, rewrite every occurrence/range and audit reference, and recompute deterministic occurrence identities under the reminted schedule ID; preserve `originScheduleId` and the source automation ActorRef only as non-authorizing provenance. Revalidate the same exact covered nominal instants after remapping, and never register the imported schedule as a target AutomationIdentity. Source queue/request identifiers remain labeled origin references because live scheduler rows are excluded. A Turn reference may identify an unmaterialized source Turn only when the linked admission history explicitly says no Turn existed; a reference claiming an existing portable Turn must resolve. Source Agent/profile/model IDs remain historical selectors, never target supply or grants. Validate exact range arithmetic, non-overlap with individual rows, attempt bounds and all required reference relationships before mutation; reject contradictions rather than dropping history.

Starting recurring work in the target requires creating a new schedule through current target authority; import cannot resume the source schedule. Complete same-deployment data-root restore instead preserves canonical active definitions, cursors, pending occurrences and scheduler rows together, after which ordinary boot recovery and the current-time/current-authority scan apply. No import starts a worker, resolves credentials or creates queue capacity. User-authored prompt content follows existing portable-content rules; system credentials and runtime/provider payloads remain excluded.

### Agent Resource Catalog Portability

The catalog implementation MUST extend V3 using required feature `agent.resource-catalog.v1` and the existing manifest, exact-file inventory, staged publication, and coverage mechanisms. An export from that implementation includes `records/agent-resource-catalog.json` even when empty. It is a strict whitelist projection, never a copy of `catalog/catalog.json`, and does not define a second live catalog or an export service.

| Source family | Portable representation | Target behavior |
| --- | --- | --- |
| Workspace Skill entries, immutable versions, candidate content and decision history | Stable scoped ids, display/availability history, exact digests and format, inventories, producer and source lineage, exact base-version and authorized work/evidence references in the portable catalog; retained Skill trees at `skill-payloads/<skillId>/<digestHex>.json` | Preserve version content and history; import entries disabled, with no active default or pin. Source candidate state and actor ids are historical, not target review or submitter-only authority. |
| Plugin entries, source versions, membership and selection history | Only scoped ids, source/publisher labels, digests, exact member references, and redacted non-secret origin lineage in the portable catalog | Original package content is unavailable; no live installation or activation is reconstructed. Independently imported Skill content remains usable after fresh target selection. |
| MCP entries, configuration-version and binding history | Only scoped ids, version/configuration digests, display labels, source membership, and unavailable-content lineage in the portable catalog | No runnable configuration, active selection, binding, grant, or package-data key is imported; target reimport and rebinding are explicit. |
| Original PluginVersion roots and raw MCP declarations | Excluded; neither `catalog/plugin-snapshots/` nor raw `plugin.json`/`mcp.json` package/configuration copies are portable catalog paths | Import rejects these paths and any endpoint, command, arguments, environment, headers, or source-acquisition authority in the portable catalog. A matching name or recorded digest cannot synthesize missing source bytes. |
| Mutable `catalog/mcp-data/`, source receipts, runtime materializations and indexes | Excluded | No process data, current receipt, discovered root, native handle, or target runtime authority is reconstructed. |
| Server-owned catalog resources | Non-secret exact source references only | No Server bytes or ownership are copied; required supply remains unavailable until explicitly resolved under target authority. |

Each retained Skill tree uses the complete bounded tree representation already accepted for candidate Artifact submission by `docs/specs/20260711-skill_catalog_versioning_pinning.md`: normalized relative directory/file entries, executable flags, and base64 file bytes. This preserves empty directories and executable identity without trusting tar permission bits or making deep source paths into archive entry paths. The verifier enforces both the existing archive bounds and Skill bounds, checks every payload against its exact `openkit-tree-v1` identity and metadata inventory, and rejects extra/missing payloads or digest disagreement. Reconstruction uses the same catalog admission owner and creates read-only immutable content, not a directly executable import. Versions whose content was legitimately purged retain explicit unavailable-content history; missing bytes claimed as retained fail export/import. User-authored Skill bytes are subject to current content-read authority and remain unsanitized user content, like other portable artifacts; an export must not widen a restricted content read.

Import rewrites Workspace ownership and all owned Workspace/Thread/Turn/Artifact/evidence references through the existing id maps, while original publisher/source identities remain provenance. Entry, version, and candidate ids scoped only to the imported Workspace can remain stable; any reminted id must rewrite every member, base-version, candidate, setup, AEP, and history reference before graph validation. Skill content digests remain unchanged; dependent rewritten package/history digests follow their existing owners. Source defaults, pins, installation selections, binding state, and candidate decisions remain only explicitly marked imported history in the catalog provenance, not current target state. Reviewing imported candidate content requires a fresh target candidate submission with an explicit current base and current permission; an imported decision or actor id grants no action. Imported AEP/materialization observations remain historical under the existing imported-history verifier and never claim target delivery.

Workspace configuration may retain the exact `assistant.resources` references defined by `20260909-internal_agent_resource_integration.md`. Rewrite the first slice's Skill identities through the same catalog maps. A later accepted capability-to-MCP binding extension must map its server identity through that existing catalog without importing an upstream schema as a model Tool. Imported references are non-executable until their independent resource owners receive fresh target selection/binding; a matching name cannot activate missing resources. The same private-Thread audience decision also covers internal Tool Items and generated-answer source Items, including the administrator eligibility exception. UI presentations normalize answer shorthand to ordinary Item references before persistence, so existing Item/presentation graph rewriting and source/digest validation cover them; no new portable inline-data or internal-run record is introduced.

A later target action may select verified independent Skill versions through current `workspace.configure`. Restoring a Plugin or MCP requires exact source reimport through the ordinary catalog owner, current configuration authority, fresh bindings and data keys, and deployment-admin stdio activation where applicable; absent or changed source returns unavailable/conflict rather than matching by display name or inferring an upstream latest version. No import contacts an MCP server, fetches a source, starts a process, or activates a worker. These exclusions apply to ordinary Workspace export even if its caller also has deployment-admin authority; separately authorized original-plugin export remains with the Plugin owner.

Complete data-root backup and same-deployment restore retain canonical catalogs, Skill snapshots, restricted original Plugin roots, and mutable MCP data under the existing backup rules. Portable export is not a replacement for that complete backup. The catalog owners retain all resource mutation, removal, and retention authority; this projection adds no candidate lifecycle, registry, background reconciliation, or cross-deployment activation mechanism.

### Named Resource Privacy Restrictions

Workspace `config/workspace.jsonc` carries the current `workspace.policy.mediation` assignments, prohibitions and managed-boundary facts defined by [Named Workspace Resource Access](20260703-policy_enforcement_mapping.md#named-workspace-resource-access-r033). These portable Workspace privacy restrictions are distinct from the deployment-local membership, credential and historical approval records excluded below. Each exported managed Thread retains its applicable boundary and restrictions; export audience filtering must not convert it into an unmanaged Thread.

Import validates the authority-bearing configuration and its required feature before target publication, uses the existing identity maps to rewrite Workspace-local resource family/id references, and retains the boundary even after the last positive association was revoked. Source principal references do not grant target membership or bind a target User or Agent merely because an identifier matches. Mandatory restrictions and target principal bindings must validate under current target authority; otherwise import rejects before publication through its existing failure path, with the boundary still present in the source archive. It must not drop unsupported Policy or publish content under the full-member baseline. Successful import keeps the restrictions effective before the first content read. Current Workspace or deployment administrators use the existing Pending Request, confirmation and configuration contract for later changes; no import-specific grant store or workflow is introduced.

- System-managed Vault material, provider credentials, session cookies, access tokens, runtime credentials, and backend secrets MUST NOT appear in an export.

Export and import both apply that projection rather than trusting stored or supplied `setup` JSON, so open manifest extensions, workspace environment payloads, provider secret references, and other unowned pass-through fields cannot cross the portability boundary.
- Active memberships, removed membership tombstones, invitations, auth sessions, personal preferences, and user-local notification state MUST NOT appear in a portable Workspace export.
- Stable actor references in product history and audit MUST remain as non-authority lineage. Import MUST NOT interpret a source owner, member, approver, reviewer, or actor id as a target-deployment access grant.
- Imported Approval, `PermissionDecision`, and `VaultGrant` rows are readable historical evidence only. `apr_imported_` remains a reserved non-authorizing import namespace. Target-side Approval creation MUST reject it, and the importer MUST retain the target-owned `apr_imported_<targetWorkspaceId>_*` identity on every rewritten reference. Imported VaultGrants use canonical `grant` identifiers and required immutable `issuance=imported-history` under [Vault Secret Injection](20260703-vault_secret_injection.md#grant-shape). An effect consumer MUST reject an authority tuple carrying the imported Approval identity or a canonical grant without `issuance=target`, even after repository or Vault-reference rebinding. An imported allow decision without its required linked target-issuance authority remains non-authorizing; consumers MUST NOT infer origin. A target effect requires a fresh target-issued Approval and permission decision, or a fresh target-issued VaultGrant, as applicable. Rebinding restores a resource location or secret reference, never source-deployment authority.
- Material and Review request fields travel only as historical mutation lineage. Deployment-local idempotency or command-receipt rows remain non-portable unless their owning specification explicitly classifies them otherwise, and import MUST NOT make a source actor or receipt an authorization edge on the target. Cross-deployment replay of a pre-export Material or Artifact Review command is intentionally unsupported.
- User-authored artifacts, knowledge, source material, and workspace configuration are portable content and are not generically secret-scanned. Operators and product surfaces MUST NOT describe an export as sanitized user content.
- Vault references MUST export only non-secret reference metadata. On import they MUST enter the `unbound` state and require explicit re-binding before use.
- Backend-native handles, host paths, active Sandbox details, runtime compatibility keys, AgentSession policy-snapshot bindings, and similar source-host state MUST be excluded or reduced to an explicitly redacted portable summary. AgentSession retainedStorage association and work-slot references are source-deployment operational state: portable export omits or clears them, and portable import clears them and cannot remap them into attachment authority. Complete same-deployment backup retains them with the existing AgentSession records and storage associations, while runtime recovery still requires current attachment proof.
- Workspace execution-journal tables `control_executions` and `control_execution_steps` are non-portable control state and MUST NOT appear in analytical Workspace export. Full operational backup and MOVE retain them only within the Workspace database bytes; they introduce no analytical export family or new export format. This classification follows the [execution control-state decision](../decisions/20261019-durable_execution_and_control_store.md#workspace-journal-control-state-clarification).
- Derived indexes, SQLite database files, host-local filesystem staging roots, caches, scheduler queues, execution attempts, and backend-private residency MUST NOT export. They are rebuilt or re-established on the target deployment. Historical leases, capacity records, and target health remain non-portable and grant no target authority.
- The Goal steering table is removed with the Goal implementation. Export does not keep a portable family or an excluded family for it, and it does not invent a steering replay. After that removal, export does not conflict on that table. Original Items that are not Goal-owned remain portable.
- Restricted raw evidence follows its retention class; export MUST NOT widen its visibility.

The source and reminted reference graphs must validate; no separate Knowledge trace ledger, old-contract reader or second trace path is retained.

Foreign imported evidence remains unavailable even if a target page path or User identity matches. Source-manifest Server equality remains required for Workspace selections and fresh source acts. A different query Server is valid only for a retained User or Server selection when the verified source Workspace already has `importedFrom`; its immediate source deployment need not equal the original query Server across multiple imports. This history grants no current authority. Provenance remains in existing Workspace `importedFrom` and query context; no provenance field, second Server field, ledger or reader path is added. Same-deployment history and reminted Workspace-page references retain their ordinary current-access checks. Reading never rewrites stored evidence.

The [Server Knowledge decision](../decisions/20261017-server_knowledge_is_shared_knowledge.md) records this distinction and its rationale.
- An imported trace's request digest is immutable source evidence, is not reminted, and is not checked against the target context; query text is neither stored nor exported.
- The Material importer MUST first validate each Material as one complete linear parent graph. A Material with `currentRevisionId=null` has no revisions. A decided historical Review retains its version and digest without requiring a historical Artifact body; import validates its existing result owners instead, including the exact applied Material revision for an accepted proposal or the exact follow-up Turn for refinement or redo, and MUST NOT synthesize Artifact version history. For a non-null `materialProposal`, source validation and the reminted target graph MUST each prove that the tuple exactly matches the source Turn's unique accepted S39 `materialSelections` entry; the importer also rewrites `materialId` and `baseRevisionId`, requires that base revision to belong to the target Material with the unchanged verified `baseContentDigest`, and rewrites nullable `appliedMaterialRevisionId`. A duplicate pair, unresolved-version mismatch, digest disagreement, dangling source, proposal, S39, base, applied-revision, or follow-up lineage, invalid decision/result combination, or contradictory Workspace Sync exclusion MUST fail import. Portable Workspace import preserves the Artifact's original product origin; it is not the workspace-only Artifact import command that creates an `origin=imported` Artifact without Review authority.

The verifier requires every portable owner and exact package byte but intentionally omits the non-portable runtime authorities above. Retained Turn-owned traces and package bytes remain usable as historical evidence. The existing staged importer uses one exact map entry per source owner, shared by every consumer of the same verified snapshot. The map is invocation-local. ### Portable Archive Transport

- Archive download MUST reverify the existing server-managed export tree before sending a response, traverse the verified inventory in canonical path order, and stream tar then Zstandard output without buffering the complete archive or creating a second server-side archive. Tar directories use mode `0755`; regular files use mode `0644`; uid, gid, uname, gname, and mtime are zero or empty canonical values. Import treats tar metadata as non-authorizing and always creates private target staging with the fixed modes below.
- Every archive file and derived directory path MUST be representable without an extension entry by the POSIX USTAR `name` and `prefix` fields: the exact UTF-8 name is at most 100 bytes, an optional prefix is at most 155 bytes, and their split occurs only at an existing slash. Export creation and offline verification MUST reject a noncanonical or unrepresentable path before accepting the export tree; archive production MUST NOT emit PAX, GNU long-name, or another extension entry.
- A non-administrator caller retains the existing current source Workspace owner and `workspace.export` requirements for archive download. A currently usable administrator credential is eligible under the administrator eligibility rule in [Core Permissions](../core/permissions.md). Download also requires the creating actor's current authority, so an export collected under administrator authority is never released to a caller who does not hold it. `workspace.read` alone is insufficient. A foreign-deployment export handle is never a readable or enumerable public server object.
- Archive dry-run and mutating import MUST accept one streamed request body and MUST NOT publish it as a durable export handle, archive registry row, reusable upload, or server content address. The authenticated importer is target authority; foreign deployment and source actor identifiers remain lineage only.
- The current archive ceilings are exactly 8,589,934,592 compressed request bytes, 34,359,738,368 expanded tar bytes, 200,000 total tar entries including directories, and 2,147,483,648 bytes for one regular-file entry. A declared content length above the compressed ceiling fails before body consumption; missing or legal chunked length remains allowed, but observed bytes enforce every ceiling during streaming. These are fixed Phase 1 trust-boundary constants, not operator configuration.
- Request staging lives only under the dedicated server archive-request staging namespace. Each request owns one newly created `0700` directory and `0600` regular files created with exclusive no-link semantics. Extraction rejects absolute, empty, non-UTF-8, backslash, dot, dot-dot, noncanonical, duplicate, case-colliding, or NUL/control paths and every symlink, hard link, device, FIFO, socket, sparse entry, unsupported extension entry, extra file, missing file, size mismatch, and verifier failure.
- Dry-run parses only the verified staged bytes, returns the existing collision and verification report, and removes its staging in request `finally`. Mutating import consumes the same verified bytes through the existing coordinated import owner and removes its staging after success or caught failure. A running request removes only its own directory; listener-preflight boot cleanup may remove the complete dedicated request-staging namespace because no request can then be active. No ordinary operation scans or removes another request's staging.
- For a non-administrator caller, a same-deployment archive still requires the current source Workspace owner with `workspace.export` authority before dry-run or import. A currently usable administrator credential is eligible beside that owner under the administrator eligibility rule in [Core Permissions](../core/permissions.md). A foreign archive has no target source membership to check. Both preserve the source Workspace ID when the accepted collision predicate reports it available and use the existing deterministic remint rule otherwise.
- A process crash may leave non-authorizing request staging, and a process crash inside the existing filesystem-to-Core import publication window retains that owner's explicit recovery gap. Staging presence never authorizes import, repair, replay, or Workspace publication.

### Public Portability Surfaces

- NanoCore retains the server-managed JSON export, dry-run import, and mutating import handles and adds `GET /api/app/workspaces/:workspaceId/exports/:exportId/archive`, `POST /api/app/workspace-archives/import-dry-run`, and `POST /api/app/workspace-archives/import`. The two POST routes require the exact archive media type; mutating import additionally requires one non-empty `x-openkit-request-id` header and returns the existing JSON import result only after the body is fully verified and consumed.
- `@openkit/core-client` exposes stream-oriented archive download, dry-run, and import methods. The operation definitions, Web and administrator CLI project the three archive operations through these streaming bindings ([decision](../decisions/20261003-streaming_archives_use_web_and_admin_cli.md)); remote MCP disposition follows [Operation Definition](20261002-operation_definition.md#remote-mcp-projection). No projection base64-encodes archive bytes or exposes a server filesystem path.
- The supported bundled CLI archive path remains local mode with its implicit canonical user for an ordinary caller. Download creates the caller's exact destination as a non-link regular file with `O_CREAT|O_EXCL` and mode `0600`; it refuses overwrite and leaves an exclusively created partial destination in place after transfer failure rather than using a pathname cleanup race. Dry-run and import open the caller's exact source as one regular non-link file and verify that identity remains stable through stream acquisition. Server-mode ordinary users retain Better Auth session surfaces. This change adds no cookie jar, ordinary-user login command, or canonical-user bearer token. A currently usable administrator credential is eligible for these archive operations under the administrator eligibility rule in [Core Permissions](../core/permissions.md).
- Workspace vault-reference discovery and re-binding accept secret material only as input, store it in the active target vault backend, and return only redacted reference metadata.
- The Web portability surface supports repository and vault-reference re-binding after import or migration without retaining secret material in rendered state.

### Backup And Restore

#### Operator Contract

- Capture takes purpose `backup`/`move` and the Workspace selector; return its capture identity (the backup identity) and disposition.
- Inspect, finish, and abandon select that capture identity and use current authority and operation fences. Abandon closes publication rights before releasing protection.
- Restore selects a sealed backup and the same-deployment Workspace; restricted recovery additionally requires the acknowledgement below.
- Move admission takes a target request identity, sealed move bundle, owner selection, and explicit member map. Target finish/discard selects its owning request key/fingerprint. Reactivation takes the source Workspace, capture identity, and expected moved-out revision.
- Reports identify disposition, verified identities/digests/counts, lineage, coverage/exclusions, dropped members, unresolved dependencies, any unprovable safety window, and the next permitted action.

The operator MUST choose ONE destination per move bundle.

#### Workspace Bundle And Authority

A Workspace backup is an offline-verifiable local directory of consistent static database snapshots and their complete local content closure. An archive transports the identical inventory. Neither analytical V3 nor Knowledge interchange defines this format.

The [control-store snapshot map](20261019-durable_execution_and_control_store.md#portability-snapshot-closure-and-garbage-collection) owns placement and snapshot roots. Every mutable authority inside the Workspace directory MUST be captured consistently under quiescence or its owner's snapshot rule. This includes Notebook heads/history, Light App databases and recovery copies, authored configuration revisions, and mutable catalog process data. No live WAL file copy qualifies as a snapshot. Unknown or uncovered canonical families refuse complete backup rather than disappear from its inventory.

Include retained Threads, Turns, Items, Materials, Artifacts, Knowledge/Sources, local Light Apps, catalog payloads, work observations, restricted bodies, Pending Requests, and their existing history/coverage. Retained model I/O message/part blobs and native transcripts belong to the Workspace's immutable content store and MUST enter the bundle closure under the retention owner. Preserve exact bytes, identities, restrictions, suppression, and holds. A valid reference-only external Source may remain unavailable; required local bytes may not. Omit disposable projections and indexes explicitly.

Exclude Vault material/keys, authentication credentials, User Memory, live Server Knowledge/configuration, and physical execution bindings. Workspace-owned captured server excerpts and pinned AEP/configuration snapshots remain evidence, not imported server authority. Worker volumes are excluded by default and listed separately. This backup does not inspect or sanitize user-authored content for secrets.

Creation, verification, restore, move, and reactivation require a current deployment-administrator credential and the existing per-effect authority checks. Backup possession grants no product access. Use private staging, confined regular-file paths, existing capacity limits, and no overwrite of an unrelated destination. Backup deletion uses existing retention and legal-hold rules; no new retention class is introduced.

Allocate one backup identity through the existing generator before copy/staging, never from timestamps or deployment IDs. A retry keeps its capture identity and input fingerprint; changed inputs conflict. A new capture gets a new identity. Allocation/validation failure leaves source authority unchanged.

The versioned manifest has the following closed core. Unknown descriptive additions are ignored; unknown core values and unsupported required semantics refuse admission.

| Manifest fact | Required meaning |
| --- | --- |
| Format and purpose | Workspace-backup format version 1, distinct from export V3; purpose `backup` or `move`. |
| Identity and lineage | Backup, Workspace, source deployment, and established Knowledge Base identities; prior move lineage and captured Workspace revision. Reading never allocates an absent Knowledge Base. |
| Release and features | Exact release/build identity, database format markers, and all required features. Source and restore/import target MUST run the same exact release. |
| Capture and consistency | Start/end times; `workspace-consistent` for a hot local cut, or `quiescent` for a move. Neither class proves an external effect completed. |
| Inventory | Every admitted snapshot/content file exactly once, with confined relative path, byte length, raw SHA-256, and file modes required by its owner. Include database snapshots and transitive manifests; exclude the root manifest and completion seal to avoid a digest cycle. |
| Inventory digest | SHA-256 over the exact serialized inventory; verify this digest independently of individual file digests. |
| Coverage | Included authorities, snapshot roots, omitted projections/volumes, and typed external dependencies with availability. Capture absence remains distinct from non-occurrence. |
| Account provenance | Source owner/member account IDs and private-audience references for explicit target mapping; no credentials, invitations, or transferable grants. |

A versioned seal binds the backup identity, purpose, and exact manifest digest. It is a completion marker, not a signature or source-authentication proof. Transfer confidentiality and authenticity remain the administrator's responsibility. A directory without a valid seal is incomplete and MUST NOT restore or import.

#### Local Hot Capture

1. Admit the request and protect the selected Workspace's complete snapshot roots from garbage collection before snapshot selection. Protection covers transitive manifests, Notebook history, definitions, prompts, message parts, and other required blobs.
2. Hold the layout's common-cut gate across control SQL, Light Apps, and opaque roots. Block mutations, stabilize in-flight app effects, and obtain each owner's freeze/flush or stopped-writer proof before selecting heads and taking SQLite backup-API snapshots. Unrelated Workspaces remain usable. Never independently copy a live database and WAL.
3. Once snapshots and immutable roots are fixed, release the capture pause, not the content protection. Copy the referenced immutable bytes through the Storage owner. Concurrent new content is outside this cut; later deletion cannot remove protected members.
4. Write the manifest, verify its inventory digest and exact file set, and validate database integrity, identities, required features, and complete reference closure. Light App schema/native-table inventories and definition/presentation digests retain their existing checks.
5. For purpose `backup`, synchronize the completed bundle and manifest before publishing its seal. Report success only after the seal is durable. Release content protection only after verified independent copies exist. Purpose `move` stops after verification and uses Source Seal And Moved-Out State below; it MUST NOT publish a backup seal first.

Failed copy/verification publishes no seal; preserve source data and report the failing authority. Process exit or clock expiry cannot release protection. After restart, inspect the same capture identity; finish its verified capture or explicitly abandon before releasing protection. No automatic repair/retry service is added.

#### Same-Deployment Restore

Restore requires the same source deployment and Workspace identity, current administrator authority, and proved absence of affected writers. Fence dependent execution hosts through their existing owner. Refuse an identity mismatch or a moved-out Workspace; reactivation is a separate operation. Keep current server users, ownership, membership, and physical registry authority, not a historical server database from the bundle.

1. Verify the seal, exact release/features, paths, inventory/digests, SQLite integrity, and complete owned graphs before changing live authority. Reject duplicate, missing, unlisted, linked, or unsafe entries; only the root manifest and seal are exempt from the content inventory. Parse or copy only verified bytes. Never execute packaged content or contact an external mount during verification.
2. Stage on the destination filesystem. Preserve the predecessor separately. Reverify staged bytes and open staged databases without creating replacements. Do not expose staged data through discovery, indexes, or execution.
3. Preserve provable current safety constraints and apply current retention expiry; restored bytes do not extend retention. Server-scoped membership and grants MUST come from the current server database. If Workspace safety authority is lost, only the explicit restricted-recovery procedure below permits admission; otherwise unresolved authority keeps the Workspace quarantined.
4. Treat captured nonterminal executions and unknown effects under the control-store interruption rules. Do not replay a Turn, claimed external effect, or old request merely because its snapshot precedes completion. Do not automatically restart captured queues, timers, or schedule catch-up. Later work requires fresh admission under its owner. Revalidate Pending Requests and current authorization before any later decision or delivery.
5. Publish the complete verified Workspace through the existing staged-placement boundary, then admit it only after its authoritative open succeeds. Retain the predecessor until publication and required integrity checks finish. Rebuild only disposable projections.

When the current Workspace database is lost, a deployment administrator may explicitly acknowledge restricted recovery from verified backup B. The acknowledgement states that Workspace-owned suppression, restrictions, and holds after B's capture cannot be proven and may be lost. Existing Audit and the recovery report record B and the unprovable window from B's capture start to detected loss. No global safety ledger is introduced; [the recovery decision](../decisions/20261019-restricted_recovery_and_local_move_recovery.md) owns the accepted limitation.

Restricted recovery opens with automation, channels, schedules, and executable catalog bindings disabled, as on MOVE import, until explicit administrator re-admission under current checks. It preserves provable safety facts and current server authority; it does not claim to recover missing post-capture facts.

A failure before publication leaves prior readable authority unchanged. An interrupted or uncertain publication fences and quarantines only the affected Workspace, preserving candidate/predecessor bytes. Restart never serves a partial candidate, fabricates empty authority, or automatically rolls back an external effect. Healthy Workspaces can boot. Corrupt server authority refuses server boot; uncertain shared writers block their actual effect domain.

#### Existing Whole-Server Recovery Boundary

The rules in this subsection apply only to whole-data-root recovery. They do not limit the new per-Workspace guarantee.

Each new data-root backup uses one independent `drb` UUIDv7 from the shared [Protocol Identifiers And Enums generator](20261021-protocol_identifiers_and_enums.md#ids). Allocate it before backup copy, snapshot or staging publication, including backups for the physical Epoch and Workspace storage conversions. Retain that same ID in the manifest, verification result and migration report. Deployment identity and capture times remain separate manifest facts; they do not derive backup identity. If allocation fails, preserve the predecessor and publish no backup or migration staging. Backup writers validate supplied backup and deployment IDs against their named kinds before copy, snapshot or manifest publication. Malformed or wrong-kind values fail before target mutation. Existing locks, fences, inventory verification, conversion transactions and repeat-conversion refusal remain unchanged.

- Cold backup is the baseline for whole-server recovery. With NanoCore stopped, a complete data-root byte copy has `consistency: clean` and is the supported bootable recovery input.
- Full data-root backup includes canonical users, Workspace owners, memberships, invitations, and token metadata through the Core database. Workspace bundles do not replace that server authority.
- Existing whole-server hot backup holds one continuous Core capture pause across tree copy, all SQLite backup snapshots, definition checks, and manifest verification. Pending writers then resume with their later changes. It retains `consistency: crash-consistent`, excludes cross-system atomicity and automatic reconciliation, and does not promise a bootable restored root.
- Its manifest retains capture times, source deployment, mode/consistency, exact inventory, and per-file digests. Verification rejects links, extra/missing files, unsafe paths, digest mismatch, and unsupported features. Unlike the new Workspace bundle, its current verifier does not independently recompute the inventory digest or authenticate the manifest.
- Whole-server restore verifies first, replaces the root through same-filesystem staging/rename, and invokes existing boot-time SQLite integrity recovery, migrations, derived-index rebuild, and runtime restart recovery. It remains a stopped-server operation, not a live App API mutation. Whole-server hot-backup changes are deferred.

### Workspace Move

Move transfers one Workspace between two deployments of the same exact release. It preserves the Workspace, Knowledge Base, and all in-Workspace history identities. The target MUST refuse unrelated Workspace identity collisions in its registry, final paths, staged imports, or retained tombstones. Only the exact owned-candidate recovery below is exempt. Other owner-defined global identity collisions also refuse admission. It MUST NOT silently remint. Analytical import's existing preserve-or-remint policy remains separate; operational COPY is deferred.

#### Source Seal And Moved-Out State

1. Close Workspace admission. Through the execution owner, settle product executions or truthfully interrupt them, inspect unknown effects, and fence all writers. Withdraw outstanding Pending Requests through their owner before capture; retain requests, decisions, and withdrawal history. No source request becomes live target authority.
2. Capture and verify a `quiescent` bundle through steps 1-4 of Local Hot Capture. Synchronize the complete bundle and manifest before the source seal transaction. Keep admission closed throughout. No Worker process, queue, capacity reservation, physical attachment, or live session authority travels.
3. In one source-local control transaction, commit the successful move seal fact and the Workspace's `moved-out` lifecycle disposition. Bind both to the same backup identity and manifest digest. Record source deployment and lineage under the existing Workspace lifecycle/Audit owners.
4. Finalization, including marker publication and bundle return, shares one source-local operation fence with abandonment and reactivation. Under that fence, require the CURRENT matching moved-out revision, backup identity, manifest digest, and open publication right. A historical seal fact is insufficient. Publish the durable marker only after the source transaction commits. Before commit, no transferable seal exists; afterward, marker failure leaves the source read-only. After durable sealing, release capture protection, not ordinary retention or holds.
5. Return the sealed bundle for operator transfer. Keep the source as an inspectable, read-only tombstone with its backup identity and lineage. Runtime callbacks, schedules, triggers, and ordinary mutations cannot reopen it. Retain source bytes and holds; moving is not deletion.

Before the seal transaction commits, failure keeps admission closed pending fenced cancellation/retry. Afterward, only explicit reactivation may reopen it. Reactivation requires current authority, the expected moved-out revision, target absence/fencing, and retirement of transferable copies. Under the SAME operation fence, durably close the capture's right to publish or return a bundle, retire its local candidate/seal from transferable exposure, then reopen admission and record Audit/lineage. A crash between those steps keeps admission closed; later finalization retries return the abandoned/reactivated disposition, never a seal or bundle. Preserve held bytes. [The offline decision](../decisions/20261019-workspace_backup_restore_move.md) retains the no-acknowledgement boundary; [local recovery](../decisions/20261019-restricted_recovery_and_local_move_recovery.md) records this correction.

#### Target Admission And Rebinding

The importing administrator supplies the target owner, defaulting to themself, and may supply an exact source-account-to-target-account member map. Every supplied target account MUST exist and be active. A missing owner refuses import before publication. Unmapped members are dropped and listed in the report; never infer accounts from names, contact addresses, or matching deployment-local IDs. The owner receives active membership under the existing identity owner. Mapped members receive only target-admitted membership, not source roles or Policy decisions. Source grants, invitations, tokens, and administrator eligibility never travel.

Preserve historical ActorRef values as source-qualified attribution. Rebind private audience access only through explicit admitted mappings. Unmapped private audiences remain unavailable, not shared with the Workspace. Current administrator eligibility retains its separately owned inspection authority. Removed memberships and historical request responsibility cannot create a target grant.

| Dependency | Target disposition |
| --- | --- |
| Agent and configuration references | Preserve pinned AEP/configuration bytes as history. New execution resolves the target's current Agent/configuration; absent supply blocks that execution, not local history inspection. |
| Vault | Preserve redacted reference/history only; mark references unbound. Re-provide material through the target Vault and obtain fresh grants. No old plan or receipt authorizes injection. |
| Worker volumes and native sessions | Report excluded volumes and unavailable native continuity. Allocate target resources normally for new work; a session ID is not resume proof. |
| Server Knowledge and external Sources | Keep source-qualified provenance and explicit unavailable outcomes. Separate current target admission may establish a new authorized reference; equal names/IDs do not rebind history. |
| Light Apps | Preserve complete local business data, schema/definition history, recovery copies, and immutable presentations. Validate all app-local authorities before publication; rendered views are never recovery inputs. |
| Skills/catalog and mutable process data | Preserve retained Workspace payloads and historical references. Disable executable catalog bindings, including Plugin/MCP launch bindings, until target-authorized configuration and credentials exist. Opaque process data grants no authority. |
| Schedules, external triggers, and channel bindings | Import disabled, with no catch-up, queued dispatch, or automatic reconnection. Re-enable explicitly under current target authority; preserve historical event keys without replay. |
| Pending Requests and execution records | Import historical decisions/withdrawals and ended work only. Do not enqueue old signals, reissue approvals, reuse source receipts as target effect authority, or replay source execution. |

Use the existing administrator-scoped move-admission request identity as the target key. Fingerprint source deployment, backup identity, manifest digest, resolved target owner, and canonical source-account-sorted member map. Before placement, bind candidate ownership to that key/fingerprint through existing request/provenance owners.

1. Under current authority, check an already committed same-request result FIRST. An identical fingerprint returns that result; changed inputs conflict. Otherwise verify the sealed move bundle/source graph and target owner/member inputs. Share restore integrity/staging checks, not its same-deployment selector. Unrelated collisions refuse admission.
2. Stage the verified bytes privately and apply target-specific current bindings through ordinary control transactions. Preserve original immutable evidence/digests; do not run the clone/remint transformer. Interpret source-server IDs and receipts as historical provenance, not live target foreign keys or duplicate-admission authority. Record source deployment, backup identity, manifest digest, and predecessor lineage in the target's existing import provenance.
3. Synchronize and place the complete staged Workspace while it remains unpublished. In one target server transaction, register it with the admitted owner/members and import result. Product admission requires both committed registration and a valid final Workspace. Directory discovery MUST NOT fabricate missing registration or ownership.
4. Activate only the registered, validated Workspace. Missing Vault, optional external data, or Agent supply blocks the dependent effect truthfully. Imported automation and executable bindings remain disabled.

A pre-publication failure changes no live Workspace or membership. Placement without registration remains quarantined. An exact owned unregistered staged/final candidate may be reverified and finished under current authority using the same key/fingerprint; changed-input or unrelated candidates conflict. An administrator may explicitly discard an abandoned owned candidate under its operation/writer fence: durably close the request's finish right before retiring its candidate, respect holds, and report the next permitted action. Registered authority cannot be discarded this way. Unreadable/missing registered authority remains quarantined. Retry never remints or replays execution.

### Generative App And Presentation Coverage

The initial Kernel and native UI extend the existing Workspace V3 record graph; they do not create a binary database export or an app-package transport. Exports containing them declare `workspace.generative-kernel.v1` and/or `workspace.generative-ui.native-v1` and are rejected by readers that do not implement those features. These identifiers must be registered in the existing shared registry before implementation emits them. The following paths are relative to the existing export root and all files use the existing record-envelope, manifest inventory and digest rules.

| Portable path/family | Contents and coverage |
| --- | --- |
| `records/light-apps.jsonl` / `light-app` | Every app's identity, Workspace, lifecycle, app/schema revisions and necessary attributed lineage. The derived catalog is excluded. |
| `records/light-app-definitions.jsonl` / `light-app-definition` | Every retained admitted schema revision, parent relation, exact UTF-8 schema text and SHA-256 digest, with app/revision identity and admission lineage. This carries the definition bytes; no server file path is portable. |
| `records/light-app-records.jsonl` / `light-app-record` | Complete native-table inventory projected as app/collection/record identity, revisions/timestamps/lineage and typed values keyed by stable field ID. No raw SQL, DDL or database file. |
| Existing portable AuditEvent family | Includes app-local AuditEvents with app/record lineage; physical database partitioning does not exclude them. |
| `records/generative-presentations.jsonl` / `generative-presentation` | Every retained immutable native presentation, including request-owned unpublished ones, and its exact messages, source/action bindings, digests, lineage and intended Item identity. |
| Existing Item-log family | `generative-ui-reference` Items with exact presentation references and text fallback. All references require matching presentation authority. |

Initial source export holds the existing exclusive Workspace mutation fence through snapshot capture of the app inventory, each app database and Workspace presentation graph. It then serializes those captured bytes with the existing exporter. This is a bounded local consistent capture using the existing fence, not a transaction spanning SQLite files or external systems. New app creation and schema/data/UI admission must use that same mutation admission. Do not obtain portable data by paging the public records API. Unknown native tables/columns, missing definitions, unresolved app authority, or dangling presentation/Item references fail export instead of silently dropping data. The existing archive size and verification limits still apply.

On import, verify the complete source graph and exact digests before rewriting any identity. Use the existing staged import/new-identity mapping for Workspace, app, presentation, Item, Turn and AuditEvent identities. Collection, field, schema-revision numbers and record IDs are app-local and remain stable inside the reminted app; all references carrying an app ID are rewritten. Native tables and indexes are reconstructed only from the admitted typed schema, never from source SQL. Load definition revisions before data, enforce all constraints and relation integrity, and validate complete counts/inventory before publication. Each app database is part of the existing staged Workspace directory and becomes visible only with that Workspace's coordinated publication; it needs no separate installer or import lifecycle.

Recompute admitted definition digests after rewriting the schema's app identity. Rewrite only schema-defined internal references in presentation `source`, `actions`, and the retained data-model's record metadata/relation fields, then recompute presentation content digests. Never search-and-replace arbitrary text, external IDs, or user-authored field values. Retained component IDs and surface IDs are local to a presentation and remain unchanged. Preserve source identity/digest under existing imported-history lineage; imported historical content never supplies current execution grants. The imported native form may execute only after normal target authorization, exact schema/record binding, and source checks succeed. Unsupported bindings remain unavailable.

Presentation graph validation preserves interrupted publication: a presentation with an absent reserved Item is valid `unpublished` history and its reserved Item ID is reminted consistently; it is not a dangling-reference failure. An Item pointing to a missing/wrong presentation, a mismatched reference or duplicate publication is `inconsistent` and fails complete export/import/restore. Capture and restore preserve this derived condition without publishing or repairing it.

App-local and Workspace command receipts remain non-portable under the existing idempotency classification. Creator/request lineage and AuditEvents are history, not target replay authority. Imported presentations set their active `requestId` to null, retaining source `originRequestId ?? requestId` as non-authorizing `originRequestId` with the existing Workspace imported-history provenance; they do not participate in target duplicate-admission lookup. Credentials, active grants, selected MCP execution bindings and deployment handles are excluded. Preserve external system/instance identities as data without inventing account access. No new saved-view, Plugin byte, MCP declaration or Skill package family is admitted by this native profile. App-scoped schema/resource package export/import remains deferred to this owner's later explicit package contract.

The following capture rules apply to existing whole-server recovery; Workspace bundles instead use Backup And Restore's complete snapshot closure. Cold backup includes every app directory and Workspace presentation store under the existing full-data-root contract. Hot backup inventories all app databases, including apps created after startup, captures each with an SQLite-consistent snapshot, and reads every required definition revision/digest from that captured database, not from the live current pointer. If the earlier file-tree copy lacks matching immutable definition bytes, copy those exact digest-addressed bytes into the capture and verify them there. Missing/corrupt bytes fail capture before success; restore validation independently repeats the check. Capture inventories app directories before and after database capture; an app created or an unavailable authority discovered during capture makes that attempt fail explicitly rather than claim completeness. The unchanged individual-snapshot qualification applies: hot backup is not one cross-store point-in-time transaction. App-local receipts and audits are preserved in full deployment backup.

Restore checks app/Workspace identity, SQLite integrity, schema/data/native-table inventory, each referenced definition digest, and every retained presentation/Item reference. Missing authority is preserved for inspection and is never reconstructed from a view or empty default database. The current exporter/backup/import runtime does not yet implement these families; its implementation must extend the existing inventory, required-feature registry, identity rewriting and coverage checks before publishing these capabilities.

### Data-Root Migration

- Every newly initialized data root MUST mint and persist a unique deployment id before producing deployment-scoped records. A marker that predates deployment identity MUST receive one unique id exactly once during layout normalization; subsequent boots MUST preserve it.
- Moving a data root to a new path or host MUST be supported by pointing server config at the moved tree. Product records MUST NOT embed absolute data-root paths.
- The Workspace host repository resource is retired, including host `localPath` and any Turn binding of `workspaceCwd` or `workspaceRoots` to that path. This specification does not validate, import, or preserve that resource. The decision and its reason are recorded in [a decision record](../decisions/20261002-hosting_through_gateway_mcp.md).
- Boot layout verification validates the moved tree before the server serves traffic.
- When a move changes the deployment id, the new deployment MUST preserve the predecessor id so future exports carry truthful lineage.

### Retention And Deletion Interaction

- Workspace deletion MUST produce the sealed audit closure export defined in `docs/specs/20260703-audit_usage_evidence_records.md` before removal.
- Records under `legal-hold` retention block deletion until the hold is released. This spec adds no retention semantics.

### Compaction

The only permitted compaction is the item-log snapshot compaction already allowed by `docs/core/storage.md`: completed-item snapshots that change no item ids, causation links, or final meaning.

A compacted export MAY omit item-log segments superseded by such snapshots only when replay equivalence is preserved and the manifest records the compaction and elided segments. Deep compaction remains deferred.

## Accepted Design

The exporter reads canonical source records, validates the complete workspace graph, writes the portable V3 tree into a newly owned root, computes the exact content inventory, writes the manifest last, and immediately verifies the result. Material canonical content remains inline in its revision rows, and Artifact Review remains keyed to the exact exported Artifact version. The importer verifies once, parses the verified bytes, validates the source and target graphs, remints only identities that require target ownership, rewrites every Material, Review, and Context Package reference, writes target files and the workspace database through same-filesystem staging, and coordinates publication with transactional Core replay and synchronous compensation. Derived indexes stay absent until their boot or on-demand owner rebuilds them. Workspace recovery uses consistent static snapshots, protected immutable closure, and staged existing-only opens under the control-store design. Offline move adds source-local sealing/tombstone publication and explicit target admission, not a cross-server protocol. Whole-server recovery and data-root migration remain separate thin procedures.

## File Payload And Representation Coverage

Portable export/import includes each admitted Artifact version's exact original payload and digest under [Storage Layout](20260703-storage_layout_record_ownership.md#artifact-file-payloads-and-derived-media). Validate inventory, size, and digest before target publication. Preserve original and delivered Context Package digests separately, including excerpt/descriptor bytes and immutable replay proof. No UTF-8 conversion, base64 model round trip, or current-source reconstruction may replace binary originals or missing historical package bytes.

V2 classifies every retained Turn input as portable Turn-owned file state, including Assistant inputs with no Artifact or Worker Context Package. Include the ordered input inventory and each exact `threads/<threadId>/turns/<turnId>/inputs/<ordinal>/payload` file. Verify name/media metadata, ordinal uniqueness, complete payload inventory, size, and original digest before target publication. Client drafts, private staging, and live transfer authority remain excluded. Apply this owner's Workspace preservation/collision rule and invocation-local Thread and Turn maps consistently to ownership and to every `input/turn/<workspaceId>/<threadId>/<turnId>` reference. Preserve ordinals and exact payload bytes/digests; never search-and-replace binary contents. Recompute dependent descriptor, Context Package, inventory, and export-manifest digests after reference reminting. Missing, extra, duplicate, corrupt, unauthorized, or contradictory input entries fail import. Existing portable file/state coverage guards must classify these paths when implementation lands.

Current source and destination-audience checks cover payloads, names, digests, previews, snippets, counts, and diagnostics. Derived sidecars retain original/processor/locator/coverage provenance when included; omitted rebuildable caches are declared and never claimed as original evidence. Source deletion, suppression, holds, and private-origin export rules remain binding. This adds no archive handle or restore workflow. The ZIP source-extraction limits in Work Resource Interaction do not replace this owner's separate portable archive transport limits.

## Current Implementation Projection

Per-Workspace operational backup, restore, and identity-preserving offline move are design requirements, not implemented capabilities. The following descriptions concern the existing analytical transfer and whole-data-root tooling. They do not establish the new operational acceptance predicates.

The recurring projection uses the three required JSONL families and the deployment-safe whitelist. Its native accepted occurrence must resolve the exact current canonical Turn before portable export. A missing or contradictory Turn refuses export for inspection: current file absence cannot prove that no Turn ever existed, and the accepted no-repair lifecycle retains no durable publication-phase field that could prove that historical absence. The conditional unmaterialized-Turn allowance therefore supplies no exception for current native accepted occurrences. Complete same-deployment backup and restricted deletion closure retain their exact damaged Core history under their separate recovery owners. Inert recurring import uses the shared identifier producers and invocation-local remap maps for definitions, occurrences, ranges and exact recurring Audit subjects. It preserves source origins and creates no live schedule, queue, AutomationIdentity or absent Turn.

The definition-owned archive projection through Web and the administrator CLI, with the remote MCP disposition owned by Operation Definition, is implemented through the retained streaming bindings. Administrator CLI local-file sinks preserve exclusive creation, fixed private modes and no-overwrite behavior. Remote MCP discovery omits all three archives and call refuses them before staging, export or import processing.

`backup.create` and `backup.verify` are declared in the browser-safe data-root administration family and joined to the existing storage owners in `apps/nanocore/src/storage/data-root-admin-operations.ts`. HTTP uses `POST /api/app/operations/<id>`, Core Client uses `client.operations[id]`, and CLI, OpenAPI and remote MCP derive from the same definitions. Archive, inventory, SQLite capture, and canonical publication code are candidates, not ready operational APIs. Use the backup verifier and staged registration/quarantine, not global pause, whole-root replacement, or analytical compensation/remint. Preserve existing analytical/whole-server behavior/tests.

## Alternatives Considered

- SQLite-only analytical export. Rejected because external consumers need inspectable records without a binary database dependency. Operational recovery deliberately carries consistent SQLite snapshots and their content closure.
- A V1 compatibility reader or V1-to-V3 upgrader. Rejected because the project is internal, V1 omitted authoritative state, and accepting it would falsely imply a complete portable workspace.
- Incremental remote backup. Deferred because the first release needs one local verified bundle, not another change-tracking or synchronization service. Immutable content and sealed inventories preserve later incremental feasibility.
- Live replication between deployments. Deferred because continuous synchronization needs a separate consistency model.

## Consequences

- A workspace export is inspectable with standard tools and verifiable without the source deployment, at the cost of serializing portable database rows instead of copying a database file.
- V1 exports are intentionally unusable and must be recreated as V3 from the source workspace.
- A caught synchronous analytical import failure leaves no partial Workspace through same-filesystem staging, one Core transaction, and compensating cleanup. Its process-crash publication window remains.
- Derived state stays disposable, so restore boot and on-demand index reads rebuild it; live import does not rebuild it immediately.
- Vault and repository re-binding after import is explicit; imported workspaces do not silently inherit source-host credentials or paths.
- User-authored portable content remains user content rather than becoming secret-scanned or sanitized merely because it passed through export.

## Rollout / Migration Plan

Local Workspace backup/restore, offline MOVE, and their acceptance fixture MUST ship before `v0.1.0`. Prerequisites are implemented and fault-tested common-cut/GC protection, staged existing-only opens, scoped quarantine, and source/target request fences under the layout and existing request owners. Extend existing operator/native owners; add no transfer daemon, acknowledgement protocol, generic runner, or COPY surface. Same-release mismatch refuses admission; no pre-`v0.1.0` converter is provided. Analytical export remains independently usable.

V3 replaces V1 without compatibility obligations. Existing V1 exports and internal V3 exports carrying the removed `workspace.json` path MUST be rejected and regenerated from their source workspaces. Future workspace-owned authoritative families MUST join export and import coverage in the same change that introduces their storage ownership; derived or server-local families MUST be explicitly classified non-portable.

The completed Material and Artifact Review portability implementation adds the three Material JSONL families, replaces the Artifact-id-only Review portable schema with the version-keyed row, extends the Workspace SQLite coverage guard, and validates both the source graph and reminted target graph in the same change. Context Package and workspace-handoff references are rewritten in that implementation; no later repair pass or compatibility reader exists.

The multi-user implementation change MUST update V3 coverage and import tests in the same slice that moves Workspaces to the owner-independent root. It MUST prove that deployment-local membership, invitation and credential records never travel in a portable export and that ordinary portable import creates membership only for the importing user. Workspace-authored resource privacy restrictions travel under Named Resource Privacy Restrictions above; they do not create membership. Deleted-Workspace recovery grants the reminted membership to the tombstone's original owner and records the actual recovery caller as actor. No second export version is required unless the portable byte contract itself changes.

### Operational Recovery Before v0.1.0

The [test strategy](20260529-test_strategy.md) owns test layers. Unit and boundary tests prove snapshot/GC ordering, exact seal publication, identity preservation, request idempotence, and staged admission. One process-level fixture proves the complete operator path below. A mechanical transfer is L3 coverage, not agent-first L6 acceptance.

Create a realistic Workspace on one deployment with shared/private Threads, multiple Turns/Items, binary Artifacts, Materials/Reviews, Knowledge pages/Notebook history, local and unavailable external Sources, Light App rows/definitions/presentations, retained Skill payloads, work observations, model I/O message blobs, native transcripts, restricted bodies, capture gaps, and Pending Requests. Record the exact object/file counts, identities, local content digests, scope restrictions, and external omissions before capture. Do not compare mutable deployment bindings as immutable evidence.

Include a mutable MCP root with an active writer; refuse capture without freeze/flush proof. Exercise an in-flight app effect across the common-cut gate. Race mutation, GC, and Notebook pruning/repack against protected closure; unrelated work remains usable. Restore under the same-deployment fence; verify the cut, current safety, and truthful interruption. Quiesce MOVE, withdraw Pending Requests, seal bundle/tombstone, and transfer to ONE fresh same-release destination.

Supply an active owner and an explicit partial member map. Compare every retained identity, immutable digest, and family count against the sealed source inventory. Verify dropped members, unavailable unmapped private audiences, preserved restrictions/coverage, complete Light App state, and recorded lineage. New target-specific bindings may differ only as declared in Target Admission And Rebinding.

Boot the target, inspect history, re-provide required Vault material, admit current target Agent/configuration, and execute one new authorized Turn. Prove that no source execution, schedule, request, trigger, or channel reconnect ran automatically. The source must show its read-only moved-out tombstone and the same lineage/manifest digest. For an abandoned transfer, prove explicit source reactivation only after the operator prerequisite and current fence checks.

The bounded negative set includes corrupt/missing/extra bytes, release/feature mismatch, unrelated identity collision, absent/disabled owner, seal/import interruption, and restart. Exercise both source-fence interleavings: finalization first holds reactivation until marker publication/return completes; reactivation first prevents a paused or later finalizer from publishing/returning anything, including after restart. Later retries report abandoned/reactivated. Assert no seal before moved-out commit and no target admission before complete registration.

Lose the current Workspace database after post-B safety changes: without acknowledgement, quarantine; with explicit restricted recovery, open with all required bindings disabled. Assert the Audit/report window from B capture to detected loss, the possible loss disclosure, unchanged current server membership/grants, and explicit re-admission. Crash after target placement but before registration; exact same-key/fingerprint retry reverifies and finishes, then returns its committed result on replay. Changed-input/unrelated candidates conflict; fenced discard retires only its owned unregistered candidate. Preserve prior readable authority before publication and inspectable bytes after uncertainty. Healthy Workspaces remain usable; captured/external work never replays.

## Risks & Mitigations

- Risk: portable dumps drift from live storage ownership. Mitigation: shared record schemas, the workspace SQLite table coverage guard, explicit Core-family tests, app-local state coverage, and round-trip tests.
- Risk: a new source-of-truth file family is omitted. Mitigation: storage ownership changes must classify it as portable or non-portable and add coverage in the same change.
- Risk: reminting changes a stable identity or leaves a target-owned source identity or stale digest. Mitigation: validate source and target graphs, preserve explicitly stable workspace-scoped identities, and recompute identity-dependent context and manifest digests.
- Risk: import fails after writing one storage surface. Mitigation: same-filesystem staging, one Core transaction, and synchronous rollback tests across staged, published, live-store, and Core state. A process crash inside the cross-resource publication window remains a separate recovery gap.
- Risk: users treat an export as a secret-complete or secret-sanitized clone. Mitigation: exclude system-managed secrets and host bindings, import Vault references as `unbound`, expose explicit re-binding, and state that user-authored portable content is not DLP-scanned.
- Risk: Workspace capture races mutation or garbage collection. Mitigation: snapshot every mutable authority under its owner's consistent boundary, protect transitive roots before selection, and verify the complete closure before sealing.
- Risk: existing whole-server hot backup captures a torn append or a newer database snapshot than its copied files. Its crash-consistent label and boot checks retain their current limits; boot can reject that restored root. Canonical Item/event readers may discard an incomplete final fragment; other authoritative ledgers fail closed. This is not the new Workspace guarantee.

## Resolved Decisions

The accepted workspace export version is V3. The canonical archived extension remains `.openkit-workspace.tar.zst` with a product-registered OpenKit workspace export media type. Existing server-managed-tree dry-run performs exact-byte verification and collision preview without additional staging or target mutation; archive dry-run performs the same preview from non-authoritative request-local staging and removes that staging without target mutation.

## Deferred / Future Work

- Operational COPY with reminting. Reuse the existing exact owner/reference maps, verify before reminting, and recompute affected proofs. Never turn a colliding MOVE into COPY or change the sealed original evidence.
- Remote incremental/differential synchronization to S3-compatible storage or cloud drives. Synchronize immutable objects and publish a verified seal last; preserve snapshot protection, required features, retention, confidentiality, and incomplete-upload refusal. No backend or Litestream dependency is adopted now.
- Optional native-volume continuity. Require explicitly authorized whole-volume coverage, quiescent fenced writers, exact inventories/digests, preserved audience, checked target storage association, compatible runtime/layout, fresh credentials, and independent native-resume proof. Missing proof preserves bytes and refuses resume; no live process transfers.
- Whole-server hot-backup changes. Preserve its current limitations until a separate accepted design covers all server/user/Workspace authorities; per-Workspace consistency implies no whole-server transaction.
- Live replication and multi-deployment synchronization.
- Deep compaction beyond item-log snapshot elision.
- User- and server-scope export units, including whole-deployment archival export.
- Web UI surfaces for export and import progress.
- Durable recovery for a process crash inside the existing analytical import's filesystem-to-Core publication window. New operational restore/move already require interruption containment and complete publication before admission.
- Browser-level portability acceptance and optional agent-first L6 continuation beyond the fixed two-runner mechanical proof.
