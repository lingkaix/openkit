# Generative Kernel Data And Operations

This specification owns the realization of each Light App's schema and data.

## Scope

It owns file-authored definitions, the app database, semantic discovery, general data operations, the fixed operation's execution classes, schema evolution, mutation integrity, retirement, and portability.

It does not own:

- Presentation and interaction. [Generative UI Interaction](20260908-generative_ui_interaction.md) owns them.
- Identity, Policy, Vault, and Audit. [Policy](../core/policy.md) owns authorization.
- Work scheduling and Agent Runtime execution. [Runtime Model](../core/runtime-model.md) owns them.
- Workspace recovery, backup, restore, MOVE, and export. [Workspace Backup, Export, And Import](20260704-workspace_backup_export_import.md) owns them.
- Reserved admission of a data-defined operation. [Operation Definition](20261002-operation_definition.md) owns that admission.

It does not supply a visual app builder, a universal business ontology, a full CRM or CMS, a general workflow engine, a public SQL service, or arbitrary code execution inside NanoCore.

Core: [Generative Apps](../core/generative-apps.md).

## Contract

### Authority And Scope

Every Light App (called a module in the logical records below), definition revision, business record, and operation belongs to one selected Workspace. NanoCore alone validates and commits them. Current-User identity determines the caller; browser state and deployment administration do not grant Workspace data access. External source references include the configured system/account scope and external object identity so identical customer IDs in different accounts cannot collide. These references are locators and lineage, never credentials or proof of current external access.

Kernel owns preservation of the source reference's observed external instance/tenant discriminator independently of a mutable connection handle. The capability binding must prove that its current external instance still matches before resolving or invoking a referenced object. Re-pointing a connection invalidates affected bindings until explicitly reconciled; it cannot reinterpret existing IDs. If the upstream supplies no verifiable instance identity, the binding contract must provide an immutable instance discriminator and invalidate it on target/account changes. That binding/version check is part of the required capability-owner extension below, not a new connection registry.

The following are logical ownership requirements, not a physical table prescription. The first implementation must satisfy them without duplicating an existing command receipt, work record, or execution log.

| Truth | Unique owner | Required content |
| --- | --- | --- |
| Module identity and current definition | Workspace module record | Stable module ID, title, current definition revision, active or retired state, creator and mutation lineage |
| Structural schema and meaning references | Immutable app definition revision | Parent revision, digest, stable collection/field IDs, constraints, relationships, operational labels, external identifier namespaces, one exact Knowledge/Skill reference list, and author/request lineage |
| Optional fixed behavior | Existing Plugin component/catalog version owners | Exact selected Skill/MCP component versions and published operation bindings; app association references them without copying their version authority |
| Current business data | Module records | Collection and stable record IDs, record revision, definition revision used for validation, typed values, source references when applicable, creation and mutation lineage |
| Command deduplication and result reference | Existing Core completed-receipt owner for Kernel commands | Only the protocol baseline metadata: command, request ID, non-secret scope, semantic-input hash, authoritative response resource kind/ID, creation and expiry timestamps |
| Long-running or external execution | Existing work or CapabilityCall owner | Exact operation revision, resolved implementation and input lineage, authoritative status and effect evidence |

Display names are mutable labels. Renaming a field, collection, module, or operation does not change its identity or silently retarget a saved reference. Business records do not become Core Customer or Member entities. Types, explicit nullability, uniqueness, relationships, and indexes are declared by the schema. Files use existing governed Artifact/source references rather than inline bulk storage. The initial app transaction boundary excludes cross-app joins and transactions. In-app query expressions and, when admitted, aggregations should use SQLite capabilities instead of requiring a saved business function. Database internals and extension loading are not public data capabilities. Record the app, affected collection identities, effect kind, schema revision, bounded admitted statement or transaction identity or digest, actor and request lineage, and outcome through the existing audit owner. Do not log raw sensitive values. A single generic Tool name is not sufficient evidence of the admitted effects. Routine access does not create a decision ledger or a conversation Item for every query. [Agent Operator Skill](20260910-agent_operator_skill.md) requires catalog mapping or a checked exclusion. Public data, query, and schema commands use the operation registry. There is no per-app ACL.

### Agent-Led Catalog And Schema Import/Export

The primary creation and management path is an agent acting on user intent through the existing Workspace Resource Catalog and Kernel commands. The Resource Catalog owns reusable definition templates, their immutable versions, parent history, default selection and pins. The live app index remains a projection of actual per-app SQLite metadata; it cannot activate a candidate or reconstruct a missing database. A definition entry and a live app instance have different identities and responsibilities. Several app instances may explicitly use the same retained template version.

A template uses the existing strict PocketBase-inspired LightAppSchemaInput collections and fields. It contains no app instance identity, business rows, script, execution hook or copied permission. Its existing Resource Catalog group is lightApps with entries, versions and pins. An entry retains its catalog ID, display name, availability and current digest. A version retains entryId, digest, parentDigest, producer, createdAt and exact canonical definitionJson. The digest binds those declarative definition bytes; provenance is historical context, not authority. Initial parent is null; a later version names a retained parent. Identical bytes in one entry keep the original immutable version facts. A pin names one retained entry/digest pair. All mutations use the existing catalog revision and publication boundary, and ordinary errors leave unrelated catalog content intact.

Definition import validates the complete bounded schema and history before publication. Definition export carries one entry and its retained version/parent history and pin metadata; it excludes business data and executable resources. Import into a new target retains historical facts but does not activate source defaults or pins. Explicit target selection uses current authority. Stale revisions, unknown versions, missing parents or a digest mismatch produce a clear refusal without inferred repair. Workspace portability carries this definition group through the existing resource-catalog representation. Associated Skill, MCP or Plugin resources retain their separate owners and are not installed or executed by definition import.

Explicit app instantiation or schema activation resolves an exact definition version, preferring an explicit version, then the current pin, then the entry default. It passes the verified schema through the same native Kernel admission used by direct authoring. The live app records its source entry/digest as provenance and its actual admitted definition digest as authority. Changing a template default or pin never migrates live data. Selecting a previous template version is a catalog rollback only; restoring prior app data is the separate snapshot restore described below.

### Semantic Discovery

An agent first discovers a compact app index containing identity, purpose, active revision, availability, and selected behavior resources. It can then retrieve the exact relevant schema: collection and field identities, types, constraints, relationships, query capabilities, and the single exact meaning-reference list. Operational metadata explains external ID namespaces, units, valid categories, authoritative source, observation time, and provenance where applicable. Reusable domain context resolves through its exact Knowledge/Skill reference under current access. Missing context is reported as missing; generated explanation and prose labels are not verified business truth.

The `references` list contains only canonical [scope-qualified object-reference URIs](../core/protocol.md#scope-qualified-object-references) for Knowledge pages, raw Knowledge content and Skill versions. These versioned targets carry their exact content pin. Authoring may omit an empty list; admission writes an explicit list into every live or reusable definition. Retained admitted schemas and catalog version bytes require that list and do not acquire it through a legacy reader. Admission preserves the exact URI and list order without classifying labels, copying target content, resolving a current default or granting access. Knowledge owns page/raw resolution; Skill catalog owners resolve their retained version. Missing or inaccessible meaning does not block ordinary access to the app's own valid records.

App get returns a request-local `meaning` result for each admitted reference, in list order. Each result identifies the exact `reference` and its `status`. An `available` result includes the selected page text or the exact Skill version's `SKILL.md` text as `content`. An `unavailable` result includes no target content or private metadata. Current actor and destination-audience checks apply on every read. The projection never enters a definition, catalog, snapshot or export. Empty reference lists and unavailable app schemas omit it.

The response names the active schema revision and supported operation/limit vocabulary so the caller can bind later requests to what it inspected. Schema structure and meaning evolve together. Queries can select only relevant metadata and data, rather than injecting every app, Plugin, or record into context. Skill prose and stored descriptions are untrusted context, not a means to change internal prompts, authorization, or available Tools.

### Per-App Storage And File Definitions

App SQL uses the existing DatabaseOwner physical scope and lifecycle. The SQLite lock wait is the current default of 1,000 ms. It is not a query-cancellation deadline. Closed typed commands move complete atomic tuples. Definition, snapshot, format-journal, and final-receipt commits remain ordered awaited stages. Current admission is rechecked after native open and before later effects. No Main SQL transaction spans an await. The app database is not a second storage plane and not a separate database service. The Material slice in [Work Resource Interaction](20260713-work_resource_interaction_model.md) remains Markdown and plain text. It is not a general module store.

Each app has one SQLite database containing its active definition identity, schema metadata, native business tables, and local mutation receipts under the existing protocol owner. App identity and Workspace scope must be checked when opening it. A small Workspace app index is a discovery projection; it cannot override the app's admitted schema/data or become a second current-definition pointer. Core alone opens and mutates authoritative storage. Agents use APIs/MCP/CLI, not filesystem paths or direct database handles.

Schema is authored in a reviewable file. Admission validates the complete candidate, writes an immutable content-addressed definition file durably, and then atomically commits its verified digest/revision, DDL, data transformations, and completed receipt in the app database. The authoritative active definition is the committed database revision and its matching schema metadata. An unreferenced candidate file after failure is inert; a missing or mismatched referenced definition is an explicit recovery condition. Editing a working schema file does not change live data. There is no claimed atomic transaction spanning filesystem files and SQLite.

The concrete directory, schema-file grammar, stable field identifiers, app metadata inventory, and receipt storage-scope extension are fixed below and in [Storage Layout And Record Ownership](20260703-storage_layout_record_ownership.md). One app database is a transaction and portability boundary, not a second storage plane. SQLite WAL sidecars are live storage state; copying a live main file alone is not a valid backup. Use the existing backup owner with SQLite-consistent snapshotting, exact definition bytes, and verified attachment/reference coverage.

### Definition Authoring And Activation

An authorized user or agent may propose a complete module definition through an owning Core command. Proposal authority is distinct from permission to activate a schema or run its operations. An unaccepted proposal is ordinary work output, not an installed module or a second module lifecycle. Core checks the entire candidate, current Policy, identities, types, constraints and data dependencies before activation. Optional Plugin availability is reported separately; an unavailable Plugin does not prevent ordinary Kernel data access unless a specific admitted data invariant depends on it. Creating a UI form never implicitly creates a module or schema.

Initial activation creates the module and first immutable definition together. Updates name the expected current definition revision; a stale base returns a conflict and does not overwrite another author's changes. Activating a revision atomically changes the local schema, semantic context, any required local record transformation, and the current pointer, or leaves the previous state intact. A partially applied definition must never become visible to readers or commands.

The admitted evolution permits new collections with their supported fields and indexes, new optional fields in existing collections, collection/field renames with stable identities, and field removal. Populated-field removal is subject to the exact prior-value recovery proof in [Acceptance Predicates](#acceptance-predicates). Types, requiredness, field options, collection removal and unrelated index/relationship changes remain unsupported. Removing a field may remove its dependent index; it cannot leave a dangling constraint. There is no coercion, truncation, external effect, script or generated migration program.

[Generative Apps](../core/generative-apps.md#durable-authority-and-lifecycle) owns the one SQLite file, the automatic snapshot, the one-way migration, and the explicit rollback. The snapshot includes committed WAL data and the pre-migration schema and markers. Copying a live main file alone is invalid. Snapshot publication completes before DDL or marker changes. Normal record commands do not create snapshots. Kernel-format DDL and its format marker commit under the native migration journal. The command revision and receipt follow through the current command owner. An interruption after the native journal commits returns no success. Retry inspects that journal and does not repeat a completed migration effect. No cross-owner atomicity or additional receipt is claimed. Refusal, snapshot failure, or a failed DDL transaction leaves the prior live data usable. An unused snapshot or an immutable candidate definition after failure is inert. It is not a second active state and not a repair trigger.

The current Kernel database format is 2. Authoring `schemaVersion` 1 and recovery-copy `schemaVersion` 1 are separate markers. The app SQLite metadata has two version markers: kernel format version and exact admitted definition version, with schema_digest serving the latter. Template source entry/digest is separate provenance. Unknown or contradictory format/definition authority fails explicitly. Supported pending app-format migration uses the existing native app journal after the same automatic snapshot boundary. Ordinary reads and restart do not silently re-upgrade a restored older-format snapshot; that app stays visibly unavailable until the caller explicitly requests its supported format upgrade. Fresh app creation initializes the current format directly. There is no additional migration registry, legacy reader, runner or conversion path.

Snapshot listing exposes only the selected app's retained recovery copies and their original markers and lineage. Rollback requires its exact snapshot identity and expected current app revision. Core validates app/Workspace identity and SQLite integrity, prepares the restored copy with the existing rollback command receipt and Audit, closes its live handles, then atomically places the restored file and synchronizes its parent directory. It restores the selected data and version markers, advances the app revision and never generates down DDL. Later data is intentionally discarded by the explicit restore. A failure before placement preserves the current file; after an unknown placement result, inspection or ordinary exact-request retry uses the existing receipt owner. No recovery worker, replay ledger or Workspace-lifetime lock is introduced. Restart reads the actual committed file; missing or corrupt snapshots produce a local error and never a replacement identity.

### Record Commands And Concurrency

The admitted interface includes schema discovery, selection, filtering, ordering, pagination, and create, update, and bounded batch submission. Relationship traversal, joins, aggregation, delete, upsert, and bulk mutations are not in that set. Set-based requests avoid one agent round trip per row once those extensions are admitted. The first projection should follow PostgREST-style typed data semantics while using native SQLite statements internally; it is not a requirement to embed PostgREST or deploy PostgreSQL. Do not require a new named business operation for each valid query or combination. The [2026-10-31 rulings](../decisions/20261031-reserved_audit_question_rulings.md) record this narrower acceptance.

Choose one bounded query representation, with parameterized values and schema-resolved identifiers. The initial public projection does not expose unrestricted SQL, `ATTACH`, filesystem access, extension loading, PRAGMA mutation, administrative tables, or arbitrary URLs. A later lower-level database-language projection must demonstrate the same app isolation, statement admission, resource limits, constraints, concurrency, and receipt semantics before admission; it is not a second unguarded path. The initial contract below defines the supported PocketBase-style subset. Joins and aggregates remain explicit extensions rather than implicitly supported syntax.

Core enforces type, required-field, nullability, uniqueness, and referential constraints. A batch specifies its transaction boundary; within one atomic app transaction, any validation or precondition failure changes nothing. Bounded execution and result limits fail explicitly; truncating a displayed result cannot silently truncate a requested mutation. Deferred set updates, deletes, and bulk mutations must define the exact affected-set or predicate precondition and conflict semantics, including concurrent inserts. Deferred dependent deletes require an admitted effect and recovery contract, never an implicit cascade.

Single-record updates require the expected record revision and the expected definition revision. Deferred single-record deletes require the same revisions. Deferred bulk mutations carry the equivalent admitted set precondition plus expected definition revision. Core resolves authorization and validates within the mutation boundary; a stale schema, conflicting record revision, denied operation, or missing dependency produces a typed refusal without mutation. Creation uses a request ID and a stable server-issued record identity. Repeating the same request and fingerprint uses a valid completed receipt to project current state from the authoritative result owner; it does not reconstruct an old response body. Reuse with different arguments is rejected. Receipts contain no business content, use the current default seven-day replay window, and introduce no new command lifecycle. Existing request-owned effects without a valid receipt return `recovery_required` rather than replaying the effect or synthesizing a receipt. Missing result owners return their explicit missing/recovery condition.

The initial contract retains current records and immutable definition revisions, with audit and command lineage. It does not promise a full per-record version history or undo log. Destructive data removal therefore requires the accepted command-specific recovery contract above and current authorization; a UI confirmation alone is not authorization or a backup. Storage limits must fail before mutation, never silently discard fields or records.

### Optional Fixed Operations And Agent Plugins

The fixed operation is the first reserved data-defined operation under [Operation Definition](20261002-operation_definition.md). This specification keeps its proposal, validation, activation, retirement, immutable versions, and execution classes. That specification owns the reserved admission rules and does not replace those classes. No data-defined source is built by this link.

A fixed operation is packaged and selected through [Agent Plugin Packaging And Worker Supply](20260907-agent_plugin_packaging_and_worker_supply.md) and its existing component owners. Prefer one cohesive MCP server for an app's tool surface, plus Skills and any required CLI assets, rather than a server or runtime per function. A data-only app does not need its own Plugin. Agents can create, inspect, update, select, and remove these resources through admitted catalog operations; component installation is never automatic code execution or an authorization grant. Generic data commands remain available independently. A fixed operation has a stable ID and an exact component/implementation revision containing its input schema, output schema, effect class, exact implementation binding/version, required resource scope, and owner-defined failure and cancellation semantics. Labels and generated explanations do not determine effects. The server resolves the binding; callers cannot substitute executable code, credentials, targets, or actor identity through ordinary arguments. Publishing an operation requires validation of that exact binding. Revising its implementation uses the existing immutable component-version owner, and a stale caller must refresh rather than silently execute replacement code.

| Effect class | Invocation and result | Failure, retry, and cancellation |
| --- | --- | --- |
| Local data command | Core executes a general or specialized bounded command over schema-admitted records; mutation and the existing metadata-only receipt share one app database transaction. | Validation or conflict changes nothing. Same-request replay uses the receipt. Cancellation after commit cannot undo the transaction. |
| Pinned custom computation | An exact retained implementation revision is handed to an existing governed execution path; inputs and outputs are validated, and writes return through Core commands. | It cannot execute in the Core process or commit storage directly. Result availability is distinct from successful application. The executable admission and recovery seam must be accepted before that deferred class is enabled. |
| Agent work | An explicit operation requests existing Task/Goal work with exact module, operation revision, input, and actor lineage; it returns the owning work reference. | Admission is not completion. Existing work owners govern cancellation, retries, review, restart, and outcome; Kernel creates no scheduler or second run record. |
| External capability | An admitted existing capability route resolves current Policy, target, and Vault references and returns its owning call reference/result. | The external effect and local data commit are separate. Unknown results require inspection; no blind retry or fabricated cross-system rollback is permitted. |

Operation availability requires both its installed definition and a supported executable binding. A defined but unsupported fixed-operation binding is visibly unavailable; it must not fall through to a generic agent prompt or shell command. External calls and custom computation may only be published once their exact execution contracts are accepted and implemented. An operation does not become a model-visible Tool merely because it exists: existing entry-path admission selects exact Tools, binds authority in trusted code, and reauthorizes each call. A general data Tool can accept schema-admitted collection, query, and transaction arguments without registering each business action as an internal Tool. This is bounded data expressiveness, not a namespace-derived authorization grant.

CRM writeback followed by a local annotation comprises two separately receipted operations: the external capability call and the local data command. Existing request/Item lineage relates them; there is no composite Kernel receipt or new execution state. The caller may perform the second operation after inspecting the first result, or existing admitted Agent work may coordinate them. An automatic single-click composite is unsupported until an existing execution owner has a concrete accepted binding for that composition. External success followed by local persistence failure remains external success with unresolved local state. Inspection or a fresh authorized local repair can reconcile the record; the system must not rerun the CRM write to hide the failure. User-visible operation outcomes are item-backed through existing owners, while routine data access uses existing audit policy without creating conversation noise.

### Retirement, Missing Dependencies, And Recovery

Workspace close first drains only its already-open dependent Apps under the same exact bound root. The close proof grants no publication authority. A failed or unknown child close prevents Workspace database close. Rollback is one ordered owner publication: verify immutable candidate bytes before admission, then recheck path, inode, size, and receipt before rename, directory fsync, and reopen.

Retirement disables new mutations and effect invocation while retaining authorized reads, exact definition history, export, and evidence. Fresh snapshot restore and kernel-format upgrade require an active app and cannot reactivate a retired app. Reactivation requires current definition/dependency validation and authorization; it is not a bypass for a revoked capability. Initial scope has no physical module purge command. Workspace deletion remains owned by the existing Workspace lifecycle, and future module purge requires explicit reference, retention, and data-loss semantics.

A missing record or module, unsupported definition version, retired operation, unavailable implementation, revoked source, or disconnected external system returns its owning typed condition. No fallback changes the target, expands scope, creates replacement records, or infers success. Local restart loads the authoritative definition and records; query caches and UI projections are rebuilt. Missing or corrupt app authority marks that app unavailable, preserves original bytes, and uses explicit storage inspection/recovery; unrelated apps remain usable when their own authorities are sound. It is not reconstructed from an old generated view.

All new canonical record families require an explicit portable classification and strict export representation under [Workspace Backup, Export, And Import](20260704-workspace_backup_export_import.md). Export includes definitions, current business data, reference identity, and required lineage. Credentials and active grants are not copied.  Unbound external references remain visible but cannot execute until correctly rebound under current authority.

Per-app copying and export must inventory runtime-created tables and preserve schema, constraints, references, values, and required local metadata. Copying creates a new app identity and consistently rewrites app-local references; it cannot reactivate source command receipts, grants, credentials, or external capabilities. Use the existing portable owner's logical record projection for Workspace export, with explicit app/schema/collection metadata and typed record families plus native-table inventory coverage. Consistent SQLite snapshots serve backup and controlled same-deployment copying, not a new binary Workspace export format; new-identity copies still rewrite identities and clear execution authority. Backup consistency and cross-file failure limits remain those of that owner; Kernel adds no cross-store atomicity promise.

## Acceptance Predicates

These predicates cover the admitted contract. An extension predicate applies before that extension is enabled. Live Worker-process, provider, host, and abrupt-crash proof is outside this slice. Partial implementation must not be reported as full conformance.

- Agent-created and schema-imported apps appear in the same Workspace catalog and obey identical admission/evolution rules. A schema-only Light App catalog export/import creates a valid empty app; explicit data/resource selection round-trips its declared closure without silently installing capabilities or overwriting an existing app. Ordinary portable Workspace import is absent and is not that catalog path.
- An agent can discover an unfamiliar app's schema and contextual meaning and perform bounded list, create, update, and batch mutation without a custom business operation. Invalid fields, ambiguous identifiers, unsupported operators, and resource limits produce precise bounded feedback. Joins, aggregation, delete, upsert, and bulk mutation are not in the admitted operation set.
- An app database and its admitted schema survive restart, consistent backup, and restore. A new-identity copy, when that command is admitted, rewrites app-local references and clears execution authority. A candidate-file write or activation failure cannot publish a mixed schema/data revision.
- Two external accounts with the same customer ID remain distinct; a module can link their IDs without claiming ownership of either customer record.
- An authorized user and an authorized Worker obtain equivalent command semantics; a denied caller cannot read or mutate through an alternative UI, CLI, or capability path.
- Concurrent record and schema edits produce one valid commit or a typed conflict; invalid, oversized, or failed migrations preserve prior data and definition identity. Before supporting a populated-field drop, destructive narrowing, or physical deletion, its owning contract must prove recovery of exact prior values; missing proof keeps the operation unavailable. If recovery uses a pre-change snapshot, the proof must cover the complete affected set, including concurrent inserts, rather than only unchanged revisions of previously observed rows.
- Re-pointing a CRM connection to another tenant cannot reinterpret stored mappings or execute an old reference; mismatched or unprovable external instance identity requires explicit reconciliation.
- The same local request cannot duplicate a mutation; a stale operation revision cannot execute a newly rebound implementation without refresh.
- Native app, schema, record, batch and lifecycle mutations retain the actual executing Worker or internal Turn and its Thread in the existing app Audit event when trusted invocation assembly supplies them. The Turn must belong to the selected Workspace and Thread. Public arguments cannot select this execution lineage. A later human presentation action retains its Item link with no executing Turn unless a trusted invocation independently supplies one; the presentation producer is not the executor. Missing historical execution links stay unknown, and replay neither adds an event nor changes the original attribution.
- Every supported operation class demonstrates its exact dispatch, validated result, cancellation boundary, and restart behavior. An unavailable class is explicit and cannot silently invoke a model or code runner.
- A lost external response remains unknown and cannot automatically repeat the effect; a subsequent local failure does not erase evidence of external success.
- Retired modules remain readable/exportable where authorized and cannot execute actions. Reopening UI does not reactivate them.
- Verified Workspace export covers records created after startup and preserves external identity. Light App catalog import remains its separate definition owner. Ordinary portable Workspace import is absent and does not remint those records or rebind execution. Current access remains mandatory before execution.
- The membership-to-CRM mapping works headlessly; a separate CRM enrichment operation proves local-only dimensions can remain in Kernel without moving the entire CRM into OpenKit.

## Initial Contract: PocketBase-Inspired Collections And Records

This section fixes the initial supported contract. The wider operation, Plugin, and package directions elsewhere in this specification remain extension requirements, not enabled MVP surfaces. [PocketBase collections](https://pocketbase.io/docs/api-collections/) and [records](https://pocketbase.io/docs/api-records/) supply the collection/field model, familiar list/filter/sort/fields vocabulary, and transactional batch pattern. OpenKit does not embed PocketBase or claim API compatibility: Workspace identity/Policy, explicit nulls, revision preconditions, receipts, file admission, and per-app databases retain their OpenKit semantics.

Recovery-copy metadata carries independent `schemaVersion: 1`; its native reader checks that marker before decoding the fixed v1 metadata and ignores descriptive additions. The copied SQLite bytes, their digest and the recorded Kernel format stay unchanged. Missing or unsupported metadata versions are unavailable and are not converted or replaced.

### Schema Document And Native Mapping

The definition has one `references` list of exact Knowledge/Skill references in the shared Core reference form, pinned where the target is versioned. Admission removes repeated exact URI strings and preserves the first occurrence order; different content pins remain different references. An empty admitted list explicitly states that the definition has no external meaning dependencies; it is never a fallback for unavailable resolution. Authoring omission declares that same no-dependencies fact. Live schema admission and catalog templates retain the same list in immutable definition bytes. Structural constraints, labels, units and external identifier namespaces remain here; reusable domain meaning and solidified procedures stay with the referenced Knowledge or Skill owner. Purpose and description prose is structural, never meaning or permission authority. Authorized discovery resolves each exact target or states that it is unavailable; missing associated content does not move or block ordinary record data. Changing this list follows ordinary definition version admission and never rewrites an immutable version. No prose classifier, converter or separate context store is introduced.

A schema input is `LightAppSchemaInputSchema` in `packages/app-api-schemas/src/light-apps.ts`. A collection is `LightAppCollectionInputSchema`. A field is `LightAppFieldInputSchema`. An index is `LightAppIndexInputSchema`; each selector is a field ID or current name. The admitted document is `LightAppAdmittedSchemaSchema`. Unknown keys, duplicate JSON keys, duplicate names/IDs, empty identifiers, and unknown versions are rejected. Names match `[a-z][a-z0-9_]{0,62}`; user field names `id`, `created`, `updated`, and `revision` are reserved to keep query metadata unambiguous; descriptions and purpose are untrusted business context, not instructions or verified facts. `namespace` explains an external identifier's immutable system/tenant domain; it never stores a credential or authorizes external resolution.

New collection IDs are `col_` plus a UUIDv7. New field IDs are `fld_` plus a UUIDv7. App IDs and record IDs stay raw UUIDv5. [Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md#ids) owns the tagged form. Core assigns those collection and field IDs and returns them in the admitted schema. IDs are omitted for new entities and required unchanged for existing entities during updates. Relation collection selectors and index field selectors accept IDs or current names and resolve after allocating all new IDs; the admitted document returns those selectors as stable IDs. Schema update accepts the admitted schema with its read-only `appId` and `schemaRevision` removed, using the separate expected-revision arguments. The admitted document also contains Core-assigned `appId` and positive `schemaRevision`; these returned fields are not caller-controlled on create/update. Immutable definition files retain that exact admitted document. The admitted definition bytes are `JSON.stringify` of the admitted object, then one LF. SHA-256 covers those exact bytes. This is not RFC 8785 JSON. [Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md) owns the shared canonical digest. This definition digest is a named exception. An input file is a proposal; neither its filename nor editing its bytes activates a schema.

| Field type | Options and JSON value | SQLite value/constraint |
| --- | --- | --- |
| `text` | String. `LightAppTextFieldOptionsSchema` bounds the configurable maximum length from 1 to 4,096 UTF-8 bytes; the current default is 4,096. | TEXT, binary case-sensitive comparison; no trim or coercion. |
| `number` | Finite JSON number. `LightAppNumberFieldOptionsSchema` admits optional integer-only and range bounds. Integer-only defaults to false. Integer-only values must be safe JSON integers. | REAL or INTEGER with type/range checks; no decimal-exact arithmetic guarantee. |
| `bool` | JSON boolean; no options. | INTEGER restricted to 0 or 1, decoded to boolean. |
| `date` | `LightAppDateValueSchema`: a valid canonical UTC RFC3339 string `YYYY-MM-DDTHH:mm:ss.sssZ`; no options. | TEXT with validated calendar value and canonical lexical order. |
| `select` | One string. `LightAppSelectFieldOptionsSchema` admits 1–100 distinct nonempty strings; no multiple selection. | TEXT with membership check. |
| `relation` | One existing record UUID. `LightAppRelationFieldOptionsSchema` names the target collection on input and resolves to its stable ID. Same app only. | TEXT foreign key with `ON DELETE RESTRICT`; no implicit cascade. |

`required:true` means non-null. It does not prohibit empty text; use a business decision to reject or flag such values. Omitted nullable values become JSON/SQL null; omitted required values fail. A PATCH leaves omitted fields unchanged; explicit null is allowed only for nullable fields. No PocketBase zero-value substitution, string-to-number conversion, default scripting, JSON/blob field, auth collection, computed view, file upload, or executable hook is admitted. An external ID whose digits are significant is text. Cross-system mappings declare the instance discriminator and external ID as separate fields, normally covered by a composite unique index. Unique indexes use native SQLite semantics: two rows conflict only when every indexed value is non-null and equal under the field comparison rules; multiple rows containing a null indexed value are permitted. Required fields must be used where unknown identifiers must not bypass uniqueness.

Native table names are generated from stable collection IDs and columns from stable field IDs; user names never become SQL identifiers. Fixed record metadata contains `id`, `revision`, `created`, `updated`, creator/last-mutator `ActorRef`, and creation/last-mutation request lineage. Wire records are `LightAppRecordSchema`; placing user fields in `data` avoids collisions with metadata. All field values are present unless a read explicitly projects `fields`; record metadata remains present. Returned `schemaRevision` identifies the current interpretation, while stored mutation lineage records the schema used at the last write.

An app has an `appRevision` starting at 1 and incremented by schema activation or retirement; ordinary record writes do not change it. `schemaRevision` starts at 1 and advances on schema activation. After a restore, the next schema revision is one above every verified retained definition revision for that app. It is not the restored revision plus one. A missing digest, a bad digest, or definition history for another app refuses the app as unavailable. Snapshot restore must keep revision preconditions unambiguous: a revision must not identify a different schema. The snapshot recovery contract above owns that requirement. Each record revision starts at 1 and advances on every accepted update, including a same-value update. Schema changes require both expected app and schema revisions. Retire requires expected app revision. Initial evolution permits new collections, stable-identity renames, semantic/label changes, new optional fields and field removal through the automatic snapshot boundary above. Populated-field removal rebuilds the table after a complete snapshot. The native barrier waits for earlier app requests before snapshot preparation and covers the committed set before DDL. It is not a per-row certificate. The proof required by [Acceptance Predicates](#acceptance-predicates) still covers concurrent inserts. Snapshot presence does not discharge that proof. Missing proof keeps the operation unavailable. Types, requiredness, field options, collection removal and unrelated index or relationship changes are refused as `unsupported_operation`; surviving existing IDs cannot be omitted to simulate replacement. Retire preserves reads and disables writes. Reactivation, physical deletion, and purge are unavailable initially.

### General Query, Mutation, And Limits

Collection selectors accept an ID or current name, following PocketBase's discovery pattern; every record query and mutation carries the inspected `schemaRevision`, so stale names cannot silently resolve against a changed schema. The catalog returns `ListLightAppsResponseSchema`, including the active, retired, or unavailable condition. App get returns this metadata, its complete admitted schema, and supported types/operators/limits. Catalog pages use the current default of page 1 and perPage 30. perPage is at most 100. They are ordered by app ID ascending. They are a live inventory, not an export snapshot. An app ID that was never created returns `not_found`. An existing app whose retained state is missing or unreadable has an explicit unavailable entry. The response does not fabricate unknown schema, revision or digest values.

Record list accepts `page` (current default 1), `perPage` (current default 30, maximum 100), `filter`, `sort`, and `fields`, and returns `ListLightAppRecordsResponseSchema`. `completeResult` is true only for page 1 when the entire matching set fits in that response; a bounded whole-result read therefore needs no second endpoint. Agents must check it before treating results as a complete set and must not infer completeness by combining changing pages. Count and selected rows use one SQLite read transaction. `sort` is a comma-separated list of at most three field names with optional `-`/`+`; `id ASC` is the final unique tiebreaker. `fields` selects comma-separated user field names; omitted means all. IDs and metadata `id`, `created`, `updated`, and `revision` are also valid filter/sort operands. Page and per-page values must be positive integers and their offset cannot exceed 10,000. Pagination is a live query per request, not a multi-request snapshot or export mechanism; concurrent edits can move rows between pages. Writes always use record/schema preconditions, never a page position. Portable export uses the owning snapshot procedure instead of paginating this API.

Use a strict PocketBase-style filter subset: `field operator literal`, operators `=`, `!=`, `>`, `>=`, `<`, `<=`, grouping parentheses, `&&`, and `||` (`&&` binds more tightly). Literals are JSON double-quoted strings, finite numbers, booleans, or null; no field-to-field operands. Null equality/inequality compile to `IS NULL`/`IS NOT NULL`; other comparisons to null are rejected. Null field values do not match ordered comparisons or `!=` against a non-null literal; use an explicit `field = null || field != value` when nulls should be included. Ordering operators apply only to text, number, or date. Identifiers resolve against admitted metadata and values are bound parameters. Reject unsupported syntax, single-quoted strings, comments, `@` variables, nested paths, functions, relation expansion, wildcards, SQL fragments, and unknown fields; do not pass an expression string to SQLite. Same-app relations can be read as IDs, but joins and expansion are unavailable initially.

Create takes `CreateLightAppRecordRequestSchema`. Update takes `UpdateLightAppRecordRequestSchema` and an exact record ID. Batch takes `LightAppBatchRequestSchema` using PocketBase's request-list pattern; only `POST /api/collections/{selector}/records` and `PATCH /api/collections/{selector}/records/{id}` are accepted virtual paths inside the already-bound app. No host, query string, per-entry header, alternate app, delete, upsert, or arbitrary endpoint is accepted. Bodies use those create and update requests except the shared schema revision. Duplicate update targets and references to records being created in that batch are refused. Each update checks its explicit expected revision; any failure rolls back every record, audit event, and receipt in the batch.

Fixed initial admission limits are 128 app directories/Workspace (including retired, unavailable and interrupted creations), 256 KiB/schema, 16 collections/app, 64 fields/collection, eight indexes/collection with at most four fields/index, 10,000 records/app, 16 KiB/data object, 4 KiB/text value, 1 MiB/mutation request, 50 batch entries, 2 KiB/filter, 32 predicates and grouping depth four, and 2 MiB/read response. Limits count UTF-8 bytes of `JSON.stringify` where JSON is bounded. That encoding is not RFC 8785 JSON. A successful response never silently drops requested fields or rows. Inputs and projected response size are validated before mutation commits. SQLite lock waiting uses the current default of 1,000 ms. failure is `unavailable` with a retryable busy reason and no commit. The bounded grammar and row ceiling bound statement work; the synchronous driver does not promise a wall-clock query interrupt. Adding unbounded scans or a different execution strategy requires changing that admitted limit contract first, not pretending lock timeout is query cancellation.

Errors use the existing Core error envelope: `validation_failed` (field/path and reason), `conflict` (record/app expected and current revisions), `schema_stale`, `not_found`, `access_denied`, `limit_exceeded` (limit and maximum), `unsupported_operation`, `unavailable`, `idempotency_key_conflict`, and `recovery_required`. Denied access remains non-enumerating. SQLite messages, physical paths, credentials, and raw sensitive values are not error details. No failed validation/conflict/busy/limit result commits part of a requested mutation.

### Transaction, Initial Creation, And Receipt Contract

All commands pass current Workspace mutation admission, current authorization and lifecycle checks before opening authoritative writes. Within one app write transaction, recheck app/schema/record preconditions, validate all values/references, apply DDL or data, write the existing attributed AuditEvent, and complete the existing metadata-only receipt. A failed audit insert or receipt insert rolls back the business change. There is no Workspace-to-app database transaction. Reads and mutations cannot open a different app through a schema, path, SQL function, or MCP argument.

Core deterministically allocates an app UUID using UUIDv5 with the standard URL namespace over `openkit:kernel.apps.create:{workspaceId}:{requestId}`. This is a server allocation rule, not a client right to choose the app or infer authority. It lets a duplicate create find its app-local receipt without a second creation registry. New app allocation checks the directory ceiling and exclusively creates the app directory under the existing exclusive Workspace mutation fence; receipt inspection for an existing request precedes this new-allocation check. Core persists and fsyncs the immutable schema file and containing directories, and commits initial metadata, native DDL, audit, and receipt in the new app database. Existing app directories are inspected, never overwritten. A directory without a committed valid app is unavailable; an interrupted create returns `recovery_required`, not a new app or automatic activation. After commit, catalog rebuild discovers the app even if projection update or response delivery failed. A catalog entry whose authority is missing never causes recreation.

The receipt key is command + request ID + Workspace/app scope, with the app omitted from the logical create scope before allocation. Semantic fingerprints include normalized admitted input and authenticated actor/request lineage; current token/Policy is always rechecked on replay. Definition candidate files are written before the schema transaction; unreferenced candidates are inert. Missing/mismatched committed definition bytes make the app unavailable and preserve its original bytes.

Single-record receipts reference the authoritative record; schema/lifecycle/create receipts reference the app. Batch receipts reference the app; their verified original request identifies updated records, and Core allocates each created record as UUIDv5 using app ID as namespace and `kernel.records.batch:{requestId}:{entryIndex}` as name. A standalone create uses `kernel.records.create:{requestId}:0`. Initial and replay results read the current named records, in request order, with current schema identity; they do not recreate an earlier response snapshot. Missing result authority returns its missing/recovery condition. The body is never retained in the receipt.

Replay authority expires at the current default of seven days. An expired ID still fences reuse. For these app-local commands, retain expired receipt metadata until the app's owning retention ends, solely to detect reused request IDs and return `recovery_required`; do not replay from it, synthesize a new receipt, or treat it as an operation log. This is an explicit no-pruning choice for existing receipt rows, not extended replay authority or a new record family. Whole-deployment backup preserves them. Ordinary portable import is removed and does not transfer them.

Mutations carry the existing `x-openkit-request-id` UUID header; the CLI and Worker adapter generate or carry the same caller request identity. Shared schemas define one contract across Web, CLI and Worker.

[Internal Agent Resource Integration](20260909-internal_agent_resource_integration.md#native-kernel-and-ui-tools) owns that entry. It adds no general internal-agent role. [Policy Enforcement Mapping](20260703-policy_enforcement_mapping.md) owns the operation-to-right registry. [Worker Agent Capability](20260703-worker_agent_capability.md) owns the governed MCP route. Kernel uses that route. It does not add a typed-tool family only to reach the Kernel.

Selected Workers see the definition-derived `openkit-generative` MCP descriptor. Tool spelling and model input views derive from the definitions. Authenticated package lineage supplies bound Workspace, actor, and request identity. Native invocation supplies the primary operation admission. The Worker capability owner retains selected supply, Tool admission, and capability evidence.

That dispatch never forwards the built-in target to the gateway itself and never exposes raw SQLite. No plugin install or per-app MCP server is needed. Only implemented selected tools are advertised. The internal caller uses no synthetic Worker session and no recursive MCP call. Public Kernel semantics are the same on MCP, administrator CLI, Worker, and Web. No frontend or Plugin gets a privileged alternative. The Assistant tools keep their Core operation meanings, current admission, and command receipts. The selected-Worker surface remains an independent caller.

[Operation Definition](20261002-operation_definition.md) owns this family's definition table. HTTP placement, client typing, Worker tools, and internal tools derive from that table. A hand-maintained schema for the same operation is not a second contract. Model-facing schemas omit bound fields. A conflicting argument is rejected before any effect. Operation semantics, scope selectors, and the request-id rule stay in this specification. Replay stays with Transaction, Initial Creation, And Receipt Contract.
