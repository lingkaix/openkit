# Generative Kernel Data And Operations

## Owns

This specification owns each Light App's stable schema and data implementation: file-authored definitions, one app SQLite database, semantic discovery, general data operations, optional Agent Plugin behavior, schema evolution, mutation integrity, retirement, and portability. Its initial contract is implementation guidance; the broader optional extensions remain unavailable until their contracts are admitted. It is not evidence that the backend exists.

## Does Not Own

Generative UI presentation and interaction belong to [Generative UI Interaction](20260908-generative_ui_interaction.md). Existing owners retain identity, Policy, Vault, Audit, work scheduling, Agent Runtime execution, capability access, Workspace recovery, and backup/export/import. Kernel adds no parallel authority in these domains. It does not supply a visual app builder, universal business ontology, full CRM/CMS platform, general workflow engine, public SQL service, or arbitrary code execution inside NanoCore.

## Summary And Intent

[Generative Apps](../core/generative-apps.md) owns the concepts and their composition. This implementation treats each Light App as one Workspace-owned data boundary containing one or several related collections. Agent is the primary consumer: it must discover the exact schema and relevant business meaning, then perform general data operations without a bespoke tool for every business action. Generative authoring does not make the data store or deterministic execution depend on a model call.

The motivating examples are a membership-platform ID mapped to a CRM customer ID, and analytical dimensions retained beside a CRM record because that system has no suitable fields. External systems keep their domain authority. Data is bounded glue with explicit source identity and observation provenance, not an implicit replica of a SaaS system or data warehouse. An app can work headlessly, and a UI can exist without an app.

## Decision

Use a file-authored schema and one SQLite database per Light App, managed by NanoCore under the existing Workspace storage owner. Prefer native tables, constraints, indexes, and transactions for the app's collections. Do not create a separate database service or a second fixed-document storage strategy. File authoring represents desired definitions; the database's admitted revision and matching schema/data determine active state.

Expose semantic discovery and expressive general query/mutation interfaces first. Optional fixed functions use the existing Agent Plugin, Skill/MCP, and execution owners. This replaces the earlier fixed-business-operation-first proposal. The initial contract below fixes the protocol and storage projections; implemented support remains a separate acceptance obligation.

## Contract

### Authority And Scope

Every Light App (called a module in the logical records below), definition revision, business record, and operation belongs to one selected Workspace. NanoCore alone validates and commits them. Current-User identity determines the caller; browser state and deployment administration do not grant Workspace data access. External source references include the configured system/account scope and external object identity so identical customer IDs in different accounts cannot collide. These references are locators and lineage, never credentials or proof of current external access.

Kernel owns preservation of the source reference's observed external instance/tenant discriminator independently of a mutable connection handle. The capability binding must prove that its current external instance still matches before resolving or invoking a referenced object. Re-pointing a connection invalidates affected bindings until explicitly reconciled; it cannot reinterpret existing IDs. If the upstream supplies no verifiable instance identity, the binding contract must provide an immutable instance discriminator and invalidate it on target/account changes. That binding/version check is part of the required capability-owner extension below, not a new connection registry.

The following are logical ownership requirements, not a physical table prescription. The first implementation must satisfy them without duplicating an existing command receipt, work record, or execution log.

| Truth | Unique owner | Required content |
| --- | --- | --- |
| Module identity and current definition | Workspace module record | Stable module ID, title, current definition revision, active or retired state, creator and mutation lineage |
| Schema and semantic context | Immutable app definition revision | Parent revision, digest, stable collection/field IDs, constraints, relationships, business meaning, external source semantics, and author/request lineage |
| Optional fixed behavior | Existing Plugin component/catalog version owners | Exact selected Skill/MCP component versions and published operation bindings; app association references them without copying their version authority |
| Current business data | Module records | Collection and stable record IDs, record revision, definition revision used for validation, typed values, source references when applicable, creation and mutation lineage |
| Command deduplication and result reference | Existing Core completed-receipt owner for Kernel commands | Only the protocol baseline metadata: command, request ID, non-secret scope, semantic-input hash, authoritative response resource kind/ID, creation and expiry timestamps |
| Long-running or external execution | Existing work or CapabilityCall owner | Exact operation revision, resolved implementation and input lineage, authoritative status and effect evidence |

Display names are mutable labels. Renaming a field, collection, module, or operation does not change its identity or silently retarget a saved reference. Business records do not become Core Customer or Member entities. Types, explicit nullability, uniqueness, relationships, and indexes are declared by the schema. Files use existing governed Artifact/source references rather than inline bulk storage. The initial app transaction boundary excludes cross-app joins and transactions; query expressions and aggregations within an app should use SQLite capabilities instead of requiring a saved business function. Database internals and extension loading are not public data capabilities.

### Agent-Led Catalog And Schema Import/Export

The primary creation and management path is an agent acting on user intent, using the same governed app-definition, data, and lifecycle commands exposed through the Light App Catalog. The catalog belongs to the selected Workspace and projects app identity, purpose, active schema revision, provenance, active/retired/unavailable state, and associated UI/behavior references. Its discover/list/read/create/update/retire/copy/import/export projections do not add an independent installation or version lifecycle. A derived catalog index can be rebuilt from admitted app records; it cannot activate a candidate schema or repair a missing database.

Schema import is an alternative app-creation path, not the primary product workflow. A schema-only import creates an empty data kernel after normal validation. A Light App export may include associated Generative UI definitions, MCP declarations, Skills, or an Agent Plugin according to an explicit selection; data is a separate explicit optional selection. Import resolves exact resource identities and dependencies through existing component owners. It may create a new app but cannot overwrite an existing app solely because its display name matches; an explicit update names the existing identity and expected revision and uses ordinary schema evolution.

Use a bounded app-scoped package projection with the existing manifest, digest, staged verification, and identity-rewriting machinery, rather than exporting an entire Workspace to move one schema or creating another package installer. The exact app package feature/schema and selected-resource closure require an explicit [portability owner](20260704-workspace_backup_export_import.md) extension; the current Workspace archive does not already implement this scope. Preserve schema meaning and exact selected references; declare omitted/unavailable dependencies. Reuse the existing Agent Plugin/Skill/MCP package formats for included resources. No credentials, active grants, deployment bindings, or automatic executable installation travel with a schema. Optional resource failure leaves valid headless data usable; a required data dependency failing validation prevents activation without modifying the existing target.

### Semantic Discovery

An agent first discovers a compact app index containing identity, purpose, active revision, availability, and selected behavior resources. It can then retrieve the exact relevant schema: collection and field identities, types, constraints, relationships, query capabilities, and business context. Semantic fields explain external ID namespaces, units, valid categories, authoritative source, observation time, and provenance where applicable. Missing context is reported as missing; generated explanation is not verified business truth.

The response names the active schema revision and supported operation/limit vocabulary so the caller can bind later requests to what it inspected. Schema structure and meaning evolve together. Queries can select only relevant metadata and data, rather than injecting every app, Plugin, or record into context. Skill prose and stored descriptions are untrusted context, not a means to change internal prompts, authorization, or available Tools.

### Per-App Storage And File Definitions

Each app has one SQLite database containing its active definition identity, schema metadata, native business tables, and local mutation receipts under the existing protocol owner. App identity and Workspace scope must be checked when opening it. A small Workspace app index is a discovery projection; it cannot override the app's admitted schema/data or become a second current-definition pointer. Core alone opens and mutates authoritative storage. Agents use APIs/MCP/CLI, not filesystem paths or direct database handles.

Schema is authored in a reviewable file. Admission validates the complete candidate, writes an immutable content-addressed definition file durably, and then atomically commits its verified digest/revision, DDL, data transformations, and completed receipt in the app database. The authoritative active definition is the committed database revision and its matching schema metadata. An unreferenced candidate file after failure is inert; a missing or mismatched referenced definition is an explicit recovery condition. Editing a working schema file does not change live data. There is no claimed atomic transaction spanning filesystem files and SQLite.

The concrete directory, schema-file grammar, stable field identifiers, app metadata inventory, and receipt storage-scope extension are fixed below and in [Storage Layout And Record Ownership](20260703-storage_layout_record_ownership.md). One app database is a transaction and portability boundary, not a second storage plane. SQLite WAL sidecars are live storage state; copying a live main file alone is not a valid backup. Use the existing backup owner with SQLite-consistent snapshotting, exact definition bytes, and verified attachment/reference coverage.

### Definition Authoring And Activation

An authorized user or agent may propose a complete module definition through an owning Core command. Proposal authority is distinct from permission to activate a schema or run its operations. An unaccepted proposal is ordinary work output, not an installed module or a second module lifecycle. Core checks the entire candidate, current Policy, identities, types, constraints and data dependencies before activation. Optional Plugin availability is reported separately; an unavailable Plugin does not prevent ordinary Kernel data access unless a specific admitted data invariant depends on it. Creating a UI form never implicitly creates a module or schema.

Initial activation creates the module and first immutable definition together. Updates name the expected current definition revision; a stale base returns a conflict and does not overwrite another author's changes. Activating a revision atomically changes the local schema, semantic context, any required local record transformation, and the current pointer, or leaves the previous state intact. A partially applied definition must never become visible to readers or commands.

Adding a nullable field or changing a display label still requires validation. Subject to the availability rule below, tightening a constraint, changing a type, dropping a field, or changing a relationship requires a preview of affected records and an explicit authorized transformation. The default is refusal when the transformation cannot preserve valid existing data safely. No implicit coercion, truncation, cascading deletion, or repair by an LLM is permitted. Constraints are checked against all affected records and enforced on subsequent writes, including concurrent calls.

Removing or irreversibly narrowing populated values, and physical record deletion, remain unavailable until the owning command has an accepted data-loss and recovery contract. Schema history alone cannot recover removed values. The storage decision below must settle which destructive operations are supported and how their exact prior data remains recoverable, or keep those operations unavailable. This contract does not impose a new export before every CRUD mutation, define a scoped-export operation, or claim that current Workspace export already proves a per-command recovery point.

The initial migration scope is bounded local deterministic transformations. It excludes external calls and arbitrary migration scripts inside Core. A failed transaction preserves the previous definition and records. A crash exposes either committed new state or unchanged old state according to the database transaction, with the command receipt committed in that same transaction. Recovery must not rerun an unknown external effect because schema changes have no external effects. Large migrations that cannot satisfy this bounded atomic contract remain unsupported rather than introducing a background migration engine.

### Record Commands And Concurrency

The general interface includes schema discovery; selection, filtering, ordering and pagination; relationship traversal and joins within the app; aggregation; create, update, delete and upsert; and bounded batch/transaction submission. Set-based requests avoid one agent round trip per row. The first projection should follow PostgREST-style typed data semantics while using native SQLite statements internally; it is not a requirement to embed PostgREST or deploy PostgreSQL. Do not require a new named business operation for each valid query or combination.

Choose one bounded query representation, with parameterized values and schema-resolved identifiers. The initial public projection does not expose unrestricted SQL, `ATTACH`, filesystem access, extension loading, PRAGMA mutation, administrative tables, or arbitrary URLs. A later lower-level database-language projection must demonstrate the same app isolation, statement admission, resource limits, constraints, concurrency, and receipt semantics before admission; it is not a second unguarded path. The initial contract below defines the supported PocketBase-style subset. Joins and aggregates remain explicit extensions rather than implicitly supported syntax.

Core enforces type, required-field, nullability, uniqueness, and referential constraints. A batch specifies its transaction boundary; within one atomic app transaction, any validation or precondition failure changes nothing. Set updates/deletes must define the exact affected-set or predicate precondition and conflict semantics, including concurrent inserts. Bounded execution and result limits fail explicitly; truncating a displayed result cannot silently truncate a requested mutation. Dependent deletes require an admitted effect and recovery contract, never an implicit cascade.

Single-record updates and deletes require the expected record revision and the expected definition revision. Bulk mutations carry the equivalent admitted set precondition plus expected definition revision. Core resolves authorization and validates within the mutation boundary; a stale schema, conflicting record revision, denied operation, or missing dependency produces a typed refusal without mutation. Creation uses a request ID and a stable server-issued record identity. Repeating the same request and fingerprint uses a valid completed receipt to project current state from the authoritative result owner; it does not reconstruct an old response body. Reuse with different arguments is rejected. Receipts contain no business content, retain the Core default seven-day lifetime, and introduce no new command lifecycle. Existing request-owned effects without a valid receipt return `recovery_required` rather than replaying the effect or synthesizing a receipt. Missing result owners return their explicit missing/recovery condition.

The initial contract retains current records and immutable definition revisions, with audit and command lineage. It does not promise a full per-record version history or undo log. Destructive data removal therefore requires the accepted command-specific recovery contract above and current authorization; a UI confirmation alone is not authorization or a backup. Storage limits must fail before mutation, never silently discard fields or records.

### Optional Fixed Operations And Agent Plugins

A fixed operation is packaged and selected through [Agent Plugin Packaging And Worker Supply](20260907-agent_plugin_packaging_and_worker_supply.md) and its existing component owners. Prefer one cohesive MCP server for an app's tool surface, plus Skills and any required CLI assets, rather than a server or runtime per function. A data-only app does not need its own Plugin. Agents can create, inspect, update, select, and remove these resources through admitted catalog operations; component installation is never automatic code execution or an authorization grant. Generic data commands remain available independently. A fixed operation has a stable ID and an exact component/implementation revision containing its input schema, output schema, effect class, exact implementation binding/version, required resource scope, and owner-defined failure and cancellation semantics. Labels and generated explanations do not determine effects. The server resolves the binding; callers cannot substitute executable code, credentials, targets, or actor identity through ordinary arguments. Publishing an operation requires validation of that exact binding. Revising its implementation uses the existing immutable component-version owner, and a stale caller must refresh rather than silently execute replacement code.

| Effect class | Invocation and result | Failure, retry, and cancellation |
| --- | --- | --- |
| Local data command | Core executes a general or specialized bounded command over schema-admitted records; mutation and the existing metadata-only receipt share one app database transaction. | Validation or conflict changes nothing. Same-request replay uses the receipt. Cancellation after commit cannot undo the transaction. |
| Pinned custom computation | An exact retained implementation revision is handed to an existing governed execution path; inputs and outputs are validated, and writes return through Core commands. | It cannot execute in the Core process or commit storage directly. Result availability is distinct from successful application. The executable admission and recovery seam must be accepted before that deferred class is enabled. |
| Agent work | An explicit operation requests existing Task/Goal work with exact module, operation revision, input, and actor lineage; it returns the owning work reference. | Admission is not completion. Existing work owners govern cancellation, retries, review, restart, and outcome; Kernel creates no scheduler or second run record. |
| External capability | An admitted existing capability route resolves current Policy, target, and Vault references and returns its owning call reference/result. | The external effect and local data commit are separate. Unknown results require inspection; no blind retry or fabricated cross-system rollback is permitted. |

Operation availability requires both its installed definition and a supported executable binding. A defined but unsupported fixed-operation binding is visibly unavailable; it must not fall through to a generic agent prompt or shell command. External calls and custom computation may only be published once their exact execution contracts are accepted and implemented. An operation does not become a model-visible Tool merely because it exists: existing entry-path admission selects exact Tools, binds authority in trusted code, and reauthorizes each call. A general data Tool can accept schema-admitted collection, query, and transaction arguments without registering each business action as an internal Tool. This is bounded data expressiveness, not a namespace-derived authorization grant.

CRM writeback followed by a local annotation comprises two separately receipted operations: the external capability call and the local data command. Existing request/Item lineage relates them; there is no composite Kernel receipt or new execution state. The caller may perform the second operation after inspecting the first result, or existing admitted Agent work may coordinate them. An automatic single-click composite is unsupported until an existing execution owner has a concrete accepted binding for that composition. External success followed by local persistence failure remains external success with unresolved local state. Inspection or a fresh authorized local repair can reconcile the record; the system must not rerun the CRM write to hide the failure. User-visible operation outcomes are item-backed through existing owners, while routine data access uses existing audit policy without creating conversation noise.

### Retirement, Missing Dependencies, And Recovery

Retirement disables new mutations and effect invocation while retaining authorized reads, exact definition history, export, and evidence. Reactivation requires current definition/dependency validation and authorization; it is not a bypass for a revoked capability. Initial scope has no physical module purge command. Workspace deletion remains owned by the existing Workspace lifecycle, and future module purge requires explicit reference, retention, and data-loss semantics.

A missing record or module, unsupported definition version, retired operation, unavailable implementation, revoked source, or disconnected external system returns its owning typed condition. No fallback changes the target, expands scope, creates replacement records, or infers success. Local restart loads the authoritative definition and records; query caches and UI projections are rebuilt. Missing or corrupt app authority marks that app unavailable, preserves original bytes, and uses explicit storage inspection/recovery; unrelated apps remain usable when their own authorities are sound. It is not reconstructed from an old generated view.

All new canonical record families require an explicit portable classification and strict export/import representation under [Workspace Backup, Export, And Import](20260704-workspace_backup_export_import.md). Export includes definitions, current business data, reference identity, and required lineage; import validates before activation, rewrites internal IDs consistently, and preserves external identities without inventing account access. Credentials and active grants are not copied. Unbound external references remain visible but cannot execute until correctly rebound under current authority.

Per-app copying and export must inventory runtime-created tables and preserve schema, constraints, references, values, and required local metadata. Copying creates a new app identity and consistently rewrites app-local references; it cannot reactivate source command receipts, grants, credentials, or external capabilities. Use the existing portable owner's logical record projection for Workspace export/import, with explicit app/schema/collection metadata and typed record families plus native-table inventory coverage. Consistent SQLite snapshots serve backup and controlled same-deployment copying, not a new binary Workspace export format; new-identity copies still rewrite identities and clear execution authority. Backup consistency and cross-file failure limits remain those of that owner; Kernel adds no cross-store atomicity promise.

## Proposed Design And Existing Seams

Reuse the existing SQLite, command, Policy, identity, Vault, Audit, catalog, work/capability, and portability facilities, extended to the app storage scope. Keep public Kernel semantics common across MCP, Skill/CLI, Worker, and Web projections; no frontend or Plugin gets a privileged alternative. A general governed Kernel MCP surface is a valid agent-native projection, not direct database access and not a separate MCP runtime per app.

[Policy Enforcement Mapping](20260703-policy_enforcement_mapping.md) retains the unique operation/access-right registry. [Core Permissions](../core/permissions.md) owns equal-member eligibility; [Multi-User Workspace System](20260715-multi_user_workspace_system.md) owns its concrete membership/right projection and lifecycle; there is no per-app ACL. [OpenKit Agent Skill Interface](20260713-openkit_agent_skill_interface.md) requires catalog mapping or checked exclusion. Public data/query/schema commands require those mappings before publication, including sensitive schema and bulk operations' attributed audit evidence. Record the app, affected collection identities, effect kind, schema revision, bounded admitted statement/transaction identity or digest, actor/request lineage, and outcome through the existing audit owner. Do not log raw sensitive values or treat a single generic Tool name as sufficient evidence of its admitted effects. Existing routine access audit policy avoids a new decision ledger or conversation Item for every query.

[Worker Agent Capability](20260703-worker_agent_capability.md) owns the governed MCP route and any required non-MCP command projection. Expose Kernel through the existing governed MCP mechanism where it covers the contract, extending its target/actor binding explicitly; do not require the previously proposed new typed-tool capability family merely to reach R097. Gateway routing must not recursively route the built-in Kernel endpoint through itself, and published operations must retain exact Workspace/app scope and current caller identity.

For NanoCore-internal use, propose a distinct server-resolved generative-app entry path, reusing the Core Assistant role assembly where appropriate, as the first consumer of Kernel discovery/data Tools and a selected progressively disclosed Skill index. Do not widen the ordinary Chat Mode Assistant entry path or add a new general internal-agent role solely for this feature. [Internal Agent Runtime](20260813-internal_agent_runtime.md) already allows optional Skill context but does not supply arbitrary Plugin tools. Its trusted assembler and the capability owner must define the exact selected MCP bridge, admitted operation schemas, result sanitization, identity, limits, and version resolution before such invocation exists. General data Tools are fixed per entry path; their schema-admitted query arguments remain flexible. Resource changes take effect only at the owning admission boundary, not by mutating a running Tool set. Script/CLI execution and heavy work use existing Worker/runtime paths. This is a proposed integration, not proof that catalog installation currently supplies internal agents.

The SQLite and backup owners must name the complete app record graph, dynamic-table inventory, local receipt placement, schema-file durability, and restore validation before activation. Existing Core/User/Workspace receipt storage does not automatically supply an app transaction; collocation is a required extension of that same owner, not a new receipt lifecycle.

The first probes are independent: a headless cross-system ID mapping with create/update/conflict/export/import, and an existing-result Generative UI that requires no Kernel. Compose them only after their respective command and interaction contracts work. This preserves the smallest useful path and avoids making a UI demo evidence of a durable backend.

## Acceptance Predicates

These predicates cover the full design. The initial-delivery boundary selects the first supported data subset; deferred operation and package predicates apply before those capabilities are enabled, not as prerequisites for the MVP. Partial implementation must not be reported as full conformance.

- Agent-created and schema-imported apps appear in the same Workspace catalog and obey identical admission/evolution rules. A schema-only export/import creates a valid empty app; explicit data/resource selection round-trips its declared closure without silently installing capabilities or overwriting an existing app.
- An agent can discover an unfamiliar app's schema and contextual meaning and perform a joined query, aggregation, and conditional bulk mutation without a custom business operation. Invalid fields, ambiguous identifiers, unsupported operators, and resource limits produce precise bounded feedback.
- An app database and its admitted schema survive restart, consistent backup, restore, and a new-identity copy; a candidate-file write or activation failure cannot publish a mixed schema/data revision.
- Two external accounts with the same customer ID remain distinct; a module can link their IDs without claiming ownership of either customer record.
- An authorized user and an authorized Worker obtain equivalent command semantics; a denied caller cannot read or mutate through an alternative UI, CLI, or capability path.
- Concurrent record and schema edits produce one valid commit or a typed conflict; invalid, oversized, or failed migrations preserve prior data and definition identity. Before supporting a populated-field drop, destructive narrowing, or physical deletion, its owning contract must prove recovery of exact prior values; missing proof keeps the operation unavailable. If recovery uses a pre-change snapshot, the proof must cover the complete affected set, including concurrent inserts, rather than only unchanged revisions of previously observed rows.
- Re-pointing a CRM connection to another tenant cannot reinterpret stored mappings or execute an old reference; mismatched or unprovable external instance identity requires explicit reconciliation.
- The same local request cannot duplicate a mutation; a stale operation revision cannot execute a newly rebound implementation without refresh.
- Every supported operation class demonstrates its exact dispatch, validated result, cancellation boundary, and restart behavior. An unavailable class is explicit and cannot silently invoke a model or code runner.
- A lost external response remains unknown and cannot automatically repeat the effect; a subsequent local failure does not erase evidence of external success.
- Retired modules remain readable/exportable where authorized and cannot execute actions. Reopening UI does not reactivate them.
- Export/import covers records created after startup, restores exact data and definition relationships, preserves external identity, and requires current access/rebinding before execution.
- The membership-to-CRM mapping works headlessly; a separate CRM enrichment operation proves local-only dimensions can remain in Kernel without moving the entire CRM into OpenKit.

## Initial Contract: PocketBase-Inspired Collections And Records

This section fixes the initial supported contract. The wider operation, Plugin, and package directions elsewhere in this specification remain extension requirements, not enabled MVP surfaces. [PocketBase collections](https://pocketbase.io/docs/api-collections/) and [records](https://pocketbase.io/docs/api-records/) supply the collection/field model, familiar list/filter/sort/fields vocabulary, and transactional batch pattern. OpenKit does not embed PocketBase or claim API compatibility: Workspace identity/Policy, explicit nulls, revision preconditions, receipts, file admission, and per-app databases retain their OpenKit semantics.

### Schema Document And Native Mapping

A schema input is a strict UTF-8 JSON object `{format:"openkit.light-app", schemaVersion:1, title, purpose, collections}`. A collection is `{id?, name, type:"base", description, fields, indexes}`. A field is `{id?, name, type, required, description, unit?, namespace?, options?}`. An index is `{fields:[fieldSelector,...], unique:boolean}`; each selector is a field ID or current name. Unknown keys, duplicate JSON keys, duplicate names/IDs, empty identifiers, and unknown versions are rejected. Names match `[a-z][a-z0-9_]{0,62}`; user field names `id`, `created`, `updated`, and `revision` are reserved to keep query metadata unambiguous; descriptions and purpose are untrusted business context, not instructions or verified facts. `namespace` explains an external identifier's immutable system/tenant domain; it never stores a credential or authorizes external resolution.

Core assigns opaque UUIDs to new collections and fields and returns them in the admitted schema. IDs are omitted for new entities and required unchanged for existing entities during updates. Relation collection selectors and index field selectors accept IDs or current names and resolve after allocating all new IDs; the admitted document returns those selectors as stable IDs. Schema update accepts the admitted schema with its read-only `appId` and `schemaRevision` removed, using the separate expected-revision arguments. The admitted document also contains Core-assigned `appId` and positive `schemaRevision`; these returned fields are not caller-controlled on create/update. Immutable definition files retain that exact admitted document, and SHA-256 identifies its exact UTF-8 bytes. An input file is a proposal; neither its filename nor editing its bytes activates a schema.

| Field type | Options and JSON value | SQLite value/constraint |
| --- | --- | --- |
| `text` | String; optional `max` from 1 to 4,096 UTF-8 bytes, default 4,096. | TEXT, binary case-sensitive comparison; no trim or coercion. |
| `number` | Finite JSON number; optional `onlyInt` (default false), `min`, `max`. Integer-only values must be safe JSON integers. | REAL or INTEGER with type/range checks; no decimal-exact arithmetic guarantee. |
| `bool` | JSON boolean; no options. | INTEGER restricted to 0 or 1, decoded to boolean. |
| `date` | Valid canonical UTC RFC3339 string `YYYY-MM-DDTHH:mm:ss.sssZ`; no options. | TEXT with validated calendar value and canonical lexical order. |
| `select` | One string from `options.values`, 1–100 distinct nonempty strings; no multiple selection. | TEXT with membership check. |
| `relation` | One existing record UUID; `options.collection` names the target collection on input and resolves to its stable ID. Same app only. | TEXT foreign key with `ON DELETE RESTRICT`; no implicit cascade. |

`required:true` means non-null. It does not prohibit empty text; use a business decision to reject or flag such values. Omitted nullable values become JSON/SQL null; omitted required values fail. A PATCH leaves omitted fields unchanged; explicit null is allowed only for nullable fields. No PocketBase zero-value substitution, string-to-number conversion, default scripting, JSON/blob field, auth collection, computed view, file upload, or executable hook is admitted. An external ID whose digits are significant is text. Cross-system mappings declare the instance discriminator and external ID as separate fields, normally covered by a composite unique index. Unique indexes use native SQLite semantics: two rows conflict only when every indexed value is non-null and equal under the field comparison rules; multiple rows containing a null indexed value are permitted. Required fields must be used where unknown identifiers must not bypass uniqueness.

Native table names are generated from stable collection IDs and columns from stable field IDs; user names never become SQL identifiers. Fixed record metadata contains `id`, `revision`, `created`, `updated`, creator/last-mutator `ActorRef`, and creation/last-mutation request lineage. Wire records are `{id, collectionId, collectionName, revision, schemaRevision, created, updated, data:{fieldName:value,...}}`; placing user fields in `data` avoids collisions with metadata. All field values are present unless a read explicitly projects `fields`; record metadata remains present. Returned `schemaRevision` identifies the current interpretation, while stored mutation lineage records the schema used at the last write.

An app has an `appRevision` starting at 1 and incremented by schema activation or retirement; ordinary record writes do not change it. `schemaRevision` starts at 1 and advances on schema activation only. Each record revision starts at 1 and advances on every accepted update, including a same-value update. Schema changes require both expected app and schema revisions. Retire requires expected app revision. Initial evolution permits renaming, semantic/label changes, and adding nullable scalar fields without a default, new index, or new relation. Types, requiredness, existing indexes, relation targets, collection sets, field removal, and other changes are refused as `unsupported_operation`; existing IDs cannot be omitted to simulate drop-and-add. Retire preserves reads and disables writes. Reactivation, physical deletion, and purge are unavailable initially.

### General Query, Mutation, And Limits

Collection selectors accept an ID or current name, following PocketBase's discovery pattern; every record query and mutation carries the inspected `schemaRevision`, so stale names cannot silently resolve against a changed schema. The catalog returns `{page,perPage,totalItems,totalPages,items}` with app ID, title, purpose, app/schema revisions, schema digest, and active/retired/unavailable condition. App get returns this metadata, its complete admitted schema, and supported types/operators/limits. Catalog pages default to page 1/perPage 30, with perPage at most 100, ordered by app ID ascending; they are a live inventory, not an export snapshot. A missing or corrupt app has an explicit unavailable entry, not a fabricated empty schema.

Record list accepts `page` (default 1), `perPage` (default 30, maximum 100), `filter`, `sort`, and `fields`, and returns `{page,perPage,totalItems,totalPages,schemaRevision,completeResult,items}`. `completeResult` is true only for page 1 when the entire matching set fits in that response; a bounded whole-result read therefore needs no second endpoint. Agents must check it before treating results as a complete set and must not infer completeness by combining changing pages. Count and selected rows use one SQLite read transaction. `sort` is a comma-separated list of at most three field names with optional `-`/`+`; `id ASC` is the final unique tiebreaker. `fields` selects comma-separated user field names; omitted means all. IDs and metadata `id`, `created`, `updated`, and `revision` are also valid filter/sort operands. Page and per-page values must be positive integers and their offset cannot exceed 10,000. Pagination is a live query per request, not a multi-request snapshot or export mechanism; concurrent edits can move rows between pages. Writes always use record/schema preconditions, never a page position. Portable export uses the owning snapshot procedure instead of paginating this API.

Use a strict PocketBase-style filter subset: `field operator literal`, operators `=`, `!=`, `>`, `>=`, `<`, `<=`, grouping parentheses, `&&`, and `||` (`&&` binds more tightly). Literals are JSON double-quoted strings, finite numbers, booleans, or null; no field-to-field operands. Null equality/inequality compile to `IS NULL`/`IS NOT NULL`; other comparisons to null are rejected. Null field values do not match ordered comparisons or `!=` against a non-null literal; use an explicit `field = null || field != value` when nulls should be included. Ordering operators apply only to text, number, or date. Identifiers resolve against admitted metadata and values are bound parameters. Reject unsupported syntax, single-quoted strings, comments, `@` variables, nested paths, functions, relation expansion, wildcards, SQL fragments, and unknown fields; do not pass an expression string to SQLite. Same-app relations can be read as IDs, but joins and expansion are unavailable initially.

Create takes `{schemaRevision,data}`. Update takes `{schemaRevision,expectedRecordRevision,data}` and an exact record ID. Batch takes `{schemaRevision,requests:[{method,url,body},...]}` using PocketBase's request-list pattern; only `POST /api/collections/{selector}/records` and `PATCH /api/collections/{selector}/records/{id}` are accepted virtual paths inside the already-bound app. No host, query string, per-entry header, alternate app, delete, upsert, or arbitrary endpoint is accepted. Bodies use the same create/update shapes except the shared schema revision. Duplicate update targets and references to records being created in that batch are refused. Each update checks its explicit expected revision; any failure rolls back every record, audit event, and receipt in the batch.

Fixed initial admission limits are 128 app directories/Workspace (including retired, unavailable and interrupted creations), 256 KiB/schema, 16 collections/app, 64 fields/collection, eight indexes/collection with at most four fields/index, 10,000 records/app, 16 KiB/data object, 4 KiB/text value, 1 MiB/mutation request, 50 batch entries, 2 KiB/filter, 32 predicates and grouping depth four, and 2 MiB/read response. Limits count UTF-8 bytes after canonical JSON encoding where JSON is bounded. A successful response never silently drops requested fields or rows. Inputs and projected response size are validated before mutation commits. SQLite lock waiting is bounded to 1,000 ms; failure is `unavailable` with a retryable busy reason and no commit. The bounded grammar and row ceiling bound statement work; the synchronous driver does not promise a wall-clock query interrupt. Adding unbounded scans or a different execution strategy requires changing that admitted limit contract first, not pretending lock timeout is query cancellation.

Errors use the existing Core error envelope: `validation_failed` (field/path and reason), `conflict` (record/app expected and current revisions), `schema_stale`, `not_found`, `access_denied`, `limit_exceeded` (limit and maximum), `unsupported_operation`, `unavailable`, `idempotency_key_conflict`, and `recovery_required`. Denied access remains non-enumerating. SQLite messages, physical paths, credentials, and raw sensitive values are not error details. No failed validation/conflict/busy/limit result commits part of a requested mutation.

### Transaction, Initial Creation, And Receipt Contract

All commands pass current Workspace mutation admission, current authorization and lifecycle checks before opening authoritative writes. Within one app write transaction, recheck app/schema/record preconditions, validate all values/references, apply DDL or data, write the existing attributed AuditEvent, and complete the existing metadata-only receipt. A failed audit insert or receipt insert rolls back the business change. There is no Workspace-to-app database transaction. Reads and mutations cannot open a different app through a schema, path, SQL function, or MCP argument.

Core deterministically allocates an app UUID using UUIDv5 with the standard URL namespace over `openkit:kernel.apps.create:{workspaceId}:{requestId}`. This is a server allocation rule, not a client right to choose the app or infer authority. It lets a duplicate create find its app-local receipt without a second creation registry. New app allocation checks the directory ceiling and exclusively creates the app directory under the existing exclusive Workspace mutation fence; receipt inspection for an existing request precedes this new-allocation check. Core persists and fsyncs the immutable schema file and containing directories, and commits initial metadata, native DDL, audit, and receipt in the new app database. Existing app directories are inspected, never overwritten. A directory without a committed valid app is unavailable; an interrupted create returns `recovery_required`, not a new app or automatic activation. After commit, catalog rebuild discovers the app even if projection update or response delivery failed. A catalog entry whose authority is missing never causes recreation.

The receipt key is command + request ID + Workspace/app scope, with the app omitted from the logical create scope before allocation. Semantic fingerprints include normalized admitted input and authenticated actor/request lineage; current token/Policy is always rechecked on replay. Definition candidate files are written before the schema transaction; unreferenced candidates are inert. Missing/mismatched committed definition bytes make the app unavailable and preserve its original bytes.

Single-record receipts reference the authoritative record; schema/lifecycle/create receipts reference the app. Batch receipts reference the app; their verified original request identifies updated records, and Core allocates each created record as UUIDv5 using app ID as namespace and `kernel.records.batch:{requestId}:{entryIndex}` as name. A standalone create uses `kernel.records.create:{requestId}:0`. Initial and replay results read the current named records, in request order, with current schema identity; they do not recreate an earlier response snapshot. Missing result authority returns its missing/recovery condition. The body is never retained in the receipt.

Replay authority expires at the existing seven-day boundary. For these app-local commands, retain expired receipt metadata until the app's owning retention ends, solely to detect reused request IDs and return `recovery_required`; do not replay from it, synthesize a new receipt, or treat it as an operation log. This is an explicit no-pruning choice for existing receipt rows, not extended replay authority or a new record family. Whole-deployment backup preserves them; portable import does not transfer them.

### Public And Agent Projections

The App API paths below are relative to `/api/app/workspaces/:workspaceId`. Mutations require the existing `x-openkit-request-id` UUID header; the CLI/Worker adapter generates or carries the same caller request identity. GET inputs are query parameters, including `schemaRevision`; POST/PATCH/PUT inputs are strict JSON bodies. The shared schemas define one contract across Web, CLI and Worker, not transport-specific business behavior.

| Operation ID | Method/path | Result owner |
| --- | --- | --- |
| `kernel.apps.list` | `GET /light-apps` | Derived catalog over app authority. |
| `kernel.apps.create` | `POST /light-apps` with schema input | Created app and admitted schema. |
| `kernel.apps.get` | `GET /light-apps/:appId` | App metadata/schema/capabilities. |
| `kernel.schema.update` | `PUT /light-apps/:appId/schema` with `{expectedAppRevision,expectedSchemaRevision,schema}` | Current app/schema. |
| `kernel.apps.retire` | `POST /light-apps/:appId/retire` with `{expectedAppRevision}` | Current app lifecycle. |
| `kernel.records.list` | `GET /light-apps/:appId/collections/:collection/records` | Current paged records. |
| `kernel.records.get` | `GET /light-apps/:appId/collections/:collection/records/:recordId` | Current record. |
| `kernel.records.create` | `POST /light-apps/:appId/collections/:collection/records` | Current created record. |
| `kernel.records.update` | `PATCH /light-apps/:appId/collections/:collection/records/:recordId` | Current updated record. |
| `kernel.records.batch` | `POST /light-apps/:appId/batch` | Current app and ordered current record results. |

Use the existing operation catalog and one end-user `openkit` Skill/CLI. Selected Workers see one built-in `openkit-generative` MCP descriptor; tool names replace operation-ID dots with underscores and their strict argument schemas carry the same inputs plus scope selectors and request ID. The gateway derives the actual Workspace, actor, Thread/Turn/AgentSession and allowed target from its authenticated selected session; arguments must agree and cannot override them. Dispatch directly to the owning command handler through the existing capability owner, never by forwarding the built-in target to the gateway itself or exposing raw SQLite. No plugin install or per-app MCP server is needed. Only implemented selected tools are advertised. Internal-agent Plugin/MCP loading remains unavailable under this initial contract.

## Initial Delivery Boundary

The first delivery is a working Agent-to-Kernel-to-native-UI loop, not completion of every capability in this specification. It needs file-authored schema, per-app SQLite authority, semantic discovery and a small Workspace catalog, general bounded reads and conditional writes, safe additive schema changes, transaction/receipt integrity, attributed effects, and recovery/portability coverage for the records actually introduced. The initial query vocabulary must be explicit and discoverable; unsupported operators must fail clearly. A mapping-specific Tool is not a substitute for general data access.

Fixed operations, internal-agent MCP loading, advanced relational queries, destructive changes, and app-scoped packages containing optional UI/Plugin resources can follow independently. Their design direction remains as described above, but their implementation and detailed extension contracts do not block the initial data slice. This does not waive backup, restore, or Workspace export/import coverage for any canonical data admitted by that slice. Acceptance of a bounded implementation contract requires its scope and deferred extension boundaries to be explicit here and in the affected existing owners; a change plan cannot supply missing design authority.

## Open Questions And Deferred Extensions

No blocking initial-contract question remains. The initial contract fixes supported schema, data, lifecycle, request/result, concurrency, storage, portability, Policy and selected Worker behavior; the initial-delivery implementation is in progress on `feat/generative-apps-mvp` and live product proofs remain deferred.

- [Non-blocking] Richer queries, upsert/predicate-wide mutations, destructive changes and recovery, and app-scoped schema/resource packages require their own accepted extension contracts before enablement.
- [Non-blocking] Fixed operations and internal-agent MCP/Skill invocation require exact selected component and runtime bindings; they remain unavailable and do not block the general Worker data surface.

## Alternatives And Sources

[Airtable](https://airtable.com/developers/web/api/model) informs stable data identity and typed metadata; [PostgREST](https://docs.postgrest.org/en/stable/references/api.html) informs discoverable general relational data access and optional functions; [PocketBase](https://pocketbase.io/docs/collections/) and its [migrations](https://pocketbase.io/docs/js-migrations/) inform schema metadata, native tables, stable field identity, and file-based evolution. PocketBase itself keeps live collection authority in its database; its migration files are not proof of atomic filesystem/database publication. OpenKit chooses per-app SQLite scope rather than copying an entire PocketBase instance per app. These references do not select a bundled service, authentication layer, database engine, dashboard, or business model. Reuse versus a small native implementation must be judged against the concrete seams above, not a blanket preference for building everything ourselves.
