# Scheduler Recurring Triggers

This specification is the single owner of durable fixed-interval and bounded monthly UTC recurring schedule definitions, occurrence and expired-range admission history, scheduled-pull external-event admission joins, the daily Knowledge Manager maintenance trigger, the closed Server security trigger, and the serialized NanoCore scan and bounded pre-admission retry lifecycle.

## Scope

### Owns

- Durable fixed-interval and bounded monthly UTC schedule definitions (`RecurringSchedule`), occurrence history (`RecurringOccurrence`), and lossless expired ranges (`ExpiredOccurrenceRange`) for requesting the existing worker Turn admission operation in [Durable Scheduler Design](20260703-durable_scheduler_design.md).
- Bounded external-event admission (`ExternalTriggerAdmission`) requested by a scheduled poll Worker through the existing Worker admission boundary.
- The closed daily Knowledge Manager maintenance trigger and the closed Server security trigger on the same recurring interface using existing work records.
- The single NanoCore-local `5 s` (current default) serialized scan, `3`-outcome (current default) bounded admission retry, `10-minute` (`600,000 ms` current default) occurrence admission deadline, restart, `1`-waiting-slot overlap, clock-change, and missed-occurrence rules.
- The boundary between occurrence admission history and the existing scheduler, Turn, worker-runtime, permission, Audit, storage, backup, and product-surface owners.

### Does Not Own

- Scope-local Workspace recurring schedule, occurrence, expired-range, and event-admission storage and unified reconciler execution in [Durable Execution And Control Store](20261019-durable_execution_and_control_store.md) ([decision](../decisions/20261019-durable_execution_and_control_store.md)); cadence, trigger identity, overlap, missed occurrences, bounded admission-only retry, current authority, and the prohibition on replaying accepted execution remain binding across that replacement.
- Scheduler queue ordering, placement, execution attempts, dispatch, Turn execution, worker-effect recovery, or Task and Goal workflow progression ([Durable Scheduler Design](20260703-durable_scheduler_design.md), [Goal](20261002-goal.md), [Task Mode Worker Delegation](20260704-task_mode_worker_delegation.md)).
- A second executor, event bus, cron parser, general calendar system, general workflow engine, generic job registry, or recovery coordinator.
- Push subscriptions, webhooks, arbitrary operations, schedule dependencies, approval decisions, or actor substitution.
- Physical table DDL, retention-class vocabulary, `AuditEvent` schema, backup archive layout, or Web presentation ([Storage Layout And Record Ownership](20260703-storage_layout_record_ownership.md), [Audit, Usage, And Evidence Records](20260703-audit_usage_evidence_records.md), [Workspace Backup, Export, Import, And Data-Root Migration](20260704-workspace_backup_export_import.md), [Web Product Surface Projection](20260628-web_product_surface_projection.md)).

## Decision

### Supported operation and cadence

The recurring operation is one direct worker Turn admission using the durable scheduler primitive in [Durable Scheduler Design](20260703-durable_scheduler_design.md). A definition retains one Workspace, one existing Thread, one worker input, optional requested Agent/profile/model/reasoning-effort selections, and the concrete `AutomationIdentity` for this schedule (`ActorRef` `{ kind: 'automation', id: scheduleId, responsibleUserId: creatorUserId }`). It does not invoke the Task or Goal coordinator, create a new Thread, or generalize arbitrary Core operations. Cron expressions, time zones other than literal UTC, calendar rules outside the monthly UTC variant below (including days `29..31` and last-day rules), recurring Goal creation, one-shot schedules, push event subscriptions, arbitrary operation families, schedule dependencies, configurable overlap policy, catch-up coalescing, user-configurable retry counts or deadlines, multi-process timer ownership, and distributed takeover are excluded (`apps/nanocore/src/storage/recurring-retained-v1.ts`, `apps/nanocore/src/lib/recurring-cadence.ts`).

The target Thread remains single-flight. At most `1` `admission-accepted` occurrence for a schedule may link to a scheduler row whose current status is `queued`; an earlier occurrence may already be `admitted` or running. Distinct schedules targeting the same Thread may each have `1` queued occurrence, while scheduler admission and execution-attempt exclusion prevent two Turns in that Thread from executing concurrently. This bounded waiting rule is the sole trigger-specific overlap behavior; there is no skip policy or parallel execution mode.

The fixed-interval public cadence is `intervalSeconds` (an integer `>= 5`) plus the next exact UTC `scheduledAt` instant supplied on resume. Absolute UTC instants keep recurrence independent of local time zones and daylight-saving changes, and the `5 s` (current default) soft scanner grants no exact due-time precision guarantee. Creating a schedule creates it `paused`. Resuming requires a `scheduledAt` not earlier than the current Core clock and sets the first due instant. For a fixed interval, the next nominal instant is always `scheduledAt + intervalSeconds`; scan delay never shifts the nominal cadence.

New fixed-interval definitions and edits must have a representable four-digit UTC timestamp successor from the current Core instant, and resume checks the actual selected nominal instant (`apps/nanocore/src/lib/recurring-cadence.ts`). When an already retained cadence reaches an unrepresentable successor while the current occurrence and its `10-minute` (`600,000 ms` current default) deadline remain representable, the scanner accounts that exact final occurrence or expired range, records no further occurrence using the `null` cursor, and emits a bounded diagnostic without stopping other schedules or rolling back their work. Pause and delete still seal that schedule's exact accounted history; invalid or contradictory retained core values and deadline-range refusals fail closed.

### Monthly UTC cadence

Monthly UTC ([decision](../decisions/20261017-monthly_utc_recurring_work.md)) is the second closed timing variant of `StoredAutomationCadenceV1Schema` in `apps/nanocore/src/storage/recurring-retained-v1.ts`, used for direct Worker admission. The zone is literal UTC. `dayOfMonth` is an integer `1..28`, `hour` is `0..23`, `minute` and `second` are `0..59`, and milliseconds are `0`. Exactly one of `intervalSeconds` and `monthlyUtc` is present; existing fixed-interval shapes and retained bytes remain usable without migration, dual write, or artificial intervals, while unknown variants, non-UTC zones, contradictory shapes, or invalid values fail closed.

Each calendar month has one nominal instant with that Gregorian UTC day and time, and the successor uses the following nominal calendar month rather than a fixed elapsed duration, callback, attempt, acceptance, or completion time. Resume supplies a current-or-future exact UTC instant matching the complete rule with zero milliseconds and strictly after the greatest nominal instant already accounted for (mismatch or calendar/timestamp overflow is refused without normalization or wraparound; days `29..31`, last-day rules, ordinal weekdays, local/browser time, numeric offsets, IANA zones, DST conversion, holidays, cron, and RRULE are excluded).

Creation is `paused`. A paused edit supplies either complete timing shape and atomically replaces the previous shape (supplying both is invalid). Pause and delete seal the old rule and revision through their mutation time before future edits; monthly occurrence snapshots and expired ranges retain that old monthly rule, revision, and immutable request snapshot, while accepted work and its original snapshot are never altered by pause, edit, or delete (and the queued-admission cancellation owner may release the waiting slot without reopening an occurrence or changing future month boundaries).

A missed monthly prefix is located directly by integer Gregorian month indices: its count is the inclusive month-index difference plus `1` between its exact first and last matching instants (never elapsed duration divided by an assumed month length), and range readers validate rule matching, order, exact count, and snapshot consistency without enumerating an unbounded outage. Candidate selection compares the actual first live nominal instant across both timing variants under the shared per-scan bounds (`128` live candidates, `128` expired ranges, and `128` already-pending expirations, current defaults), advancing cursor and greatest-accounted instants in the same transaction as the occurrence or range coverage. Recurring Goal creation remains outside this contract: monthly UTC creates no Goal or Coordinator Turn, carries no Plan approval, changes no Goal wake marker, and grants no Goal progression or completion authority.

### External events through scheduled pull

A scheduled Worker may read an already selected MCP source and request bounded Worker work for each observed event using an ordinary fixed-interval schedule, its existing `AutomationIdentity`, and the MCP Gateway, with no source field, target Thread field, second scanner, MCP producer, push subscription service, or event queue (`apps/nanocore/src/external-trigger-operations.ts`, `apps/nanocore/src/runtime/external-trigger-service.ts`). The poll Skill supplies a non-empty opaque stable `eventKey` of at most `1,024` characters scoped by `scheduleId` (including the source name when reading multiple sources).

The built-in Worker projection of the event-admit operation binds `scheduleId`, Workspace, `sourceTurnId`, and exact actor from the authenticated live poll execution (never caller-selected); only a live Worker Turn admitted by that schedule's retained accepted occurrence may request admission, and each request rechecks the `active` definition, responsible user, membership, source audience, current Policy, and ordinary Worker admission (a `paused` or `deleted` definition permits no new event admission, and poll input or external content grants no permission or approval). Each new event receives its own Workspace-visible Worker Thread linked to the poll Thread through the new-Task-Worker isolation path ([Task Mode Worker Delegation](20260704-task_mode_worker_delegation.md)), receiving only the explicit bounded handling input and fresh Task storage defaults without copying poll history, work slots, or native continuation (a busy case Thread never blocks another case, and multiple events from one poll may create separate cases).

One immutable `ExternalTriggerAdmission` (`ExternalTriggerAdmissionSchema` in `apps/nanocore/src/storage/external-trigger-admissions.ts`) is the read projection of a permanent non-expiring `scheduler.external-trigger.admit` Core command receipt (`expiresAt: null`). The unique key is `(scheduleId, eventKey)`. `sourceTurnId` is lineage, not uniqueness. The join copies no payload, status, attempt count, deadline, or cursor. The join and ordinary scheduler queue insertion commit in the same Core transaction under the Workspace mutation fence; a duplicate `(scheduleId, eventKey)` returns the existing linked work without changing accepted input, `sourceTurnId`, or allocation, and missing or contradictory accepted work requires inspection rather than replacement work. Source publication attempts the initial pending Turn once; interrupted publication, unknown acceptance, or missing canonical Turns follow scheduler inspection and no-repair rules, proved pre-acceptance refusals retain no event join, and once accepted, later failure, interruption, approval wait, or unknown outcome never causes another event admission. Selected source reads, capability usage, and captured effect approvals stay with the Gateway and Pending Request owners, and backup, same-deployment restore, and inert portable export preserve `ExternalTriggerAdmission` under `workspace-audit` retention with no pruning.

### Knowledge Manager daily maintenance

The same recurring interface admits a bounded Knowledge Manager maintenance Turn for one Server, User, or Workspace notebook scope (`apps/nanocore/src/knowledge/knowledge-maintenance-schedule.ts`, `user-memory-schedule.ts`, `apps/nanocore/src/app.ts:1625,1821`). Each scope has one independent `knowledgeMaintenance.schedule.enabled` boolean switch, default `false`, on a fixed daily cadence with no additional schedule knobs, second timer, or occurrence family (explicit run requests remain available through [Knowledge Manager Internal Agent Runtime](20260704-knowledge_manager_internal_agent_runtime.md#query-and-maintenance-execution), which owns fresh input assembly, single-writer admission, instructions, and fixed-base publication).

The scan invokes the closed Knowledge Manager callback after finite Worker admission preparation without waiting for detached model execution. The Workspace callback retains a maintenance Turn before Provider work and deduplicates by the retained scheduled Turn's UTC calendar day (never rolling 24-hour elapsed time). User and Server scopes join the same scan without fabricating a Worker identity or Workspace membership: scheduled User maintenance admits only the local User (retaining the maintenance Thread in that User's personal Workspace) and records a visible skipped outcome for any other User without advertising unattended multi-user User maintenance, while the Server scope selects the current Server notebook and general Server-owned maintenance Thread without a Workspace anchor and takes its responsible User from a current local administrator in local mode or a current usable Server administration Token owner in multi-user mode. Missing authority, active writers, or failed dependencies record visible failed or skipped outcomes without a Provider call, never mark inputs processed, and are never replayed on boot.

### Durable definition

One definition record, `StoredRecurringScheduleV1Schema` in `apps/nanocore/src/storage/recurring-retained-v1.ts`, is the unique definition authority. Its `AutomationIdentity` is Workspace-scoped and adds no automation Token or Workspace membership. Exactly one timing shape is present.

Trigger permissions are derived on each attempt from current Policy rather than stored grants, and last-trigger time is a read projection over occurrence history. `active` permits due attempts, `paused` disables triggering while preserving identity and history, and `deleted` is a terminal read-only tombstone that stops future materialization without cancelling an already accepted scheduler admission or rewriting its Turn. The actor and responsible user cannot be edited or inferred; editing cadence, target, or worker input is allowed only while `paused` after pause has sealed all nominal instants through its mutation time using the old definition snapshot (marking unresolved in-window instants and `pending` occurrences `cancelled`, and older instants as lossless `ExpiredOccurrenceRange` rows, without altering `admission-accepted`, `admission-failed`, or `expired` history, under a compare-and-set `revision` guard). Resume sets a future-or-current `nextScheduledAt` strictly greater than `greatestAccountedScheduledAt` so pause, resume, or backward clock jumps never reuse an occurrence identity, and intentionally paused intervals are not missed work.

### Durable occurrence

One occurrence record, `StoredRecurringOccurrenceV1Schema` in `apps/nanocore/src/storage/recurring-retained-v1.ts`, represents one nominal scheduled instant `(scheduleId, scheduledAt)`. It keeps an immutable request snapshot, a `10-minute` (`600,000 ms` current default) deadline, and at most `3` (current default) committed admission-attempt summaries. A lossless expired range is `StoredRecurringExpiredRangeV1Schema` in the same module.

Authentication, authorization, lineage, bounded pre-admission preparation, input validation, selection resolution, and scheduler admission failures consume `1` committed attempt (up to `3` committed outcomes: initial attempt plus `2` retries on later scans). On first resolution the work owner durably stages the original occurrence’s exact input and preparation choices. The kernel commits their identity and digest with the admission result. A proved database rollback with no queue or launch effect leaves the attempt uncounted before the deadline, whereas an unknown commit result blocks retry until durable inspection and contradictory durable state fences the occurrence as `recovery_required`. Nominal instants already past their deadline before materialization use one lossless `StoredRecurringExpiredRangeV1Schema` row. Ranges for different revisions never merge, and no read expands an unbounded range.

#### Occurrence Input On Restart

Keep occurrence, applicable Audit and ordinary queue admission in one kernel transaction. The Turn binds exact committed input bytes and preparation choices to this occurrence. A schedule edit or clock replay cannot substitute current text for the original payload or change an admitted batch. Queue rows carry identity and digest. If the work owner is missing or original bytes cannot be proved, hold dispatch and preserve the occurrence and cursor. Historical import stays inert. The [work-data owner](20260921-work_data_retention_format.md#work-owned-input-and-proof) owns retention, and the [scheduler](20260703-durable_scheduler_design.md#retained-admission-and-attempt) owns queued recovery.

### Identifier producers

Under [Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md#ids) ([Identifier Owner Declarations](../decisions/20261015-identifier_owner_declarations.md), [Identifier Derivation And Import Allocations](../decisions/20261016-identifier_derivation_and_import_allocations.md)), `apps/nanocore/src/lib/automation-store.ts` and `apps/nanocore/src/storage/recurring-records.ts` allocate schedule IDs via `allocateEntityId('auto')` (UUIDv7) and expired-range IDs via `allocateEntityId('range')` (UUIDv7), derive occurrence IDs (`occ`) via UUIDv5 over the UTF-8 JSON array `[scheduleId, scheduledAt]` (`scheduledAt` normalized to canonical UTC milliseconds), derive fixed source Turn IDs (`tu`) via UUIDv5 over `["recurring", scheduleId, scheduledAt]`, and derive opaque scheduler request UUIDs via UUIDv5 using the RFC 4122 URL namespace (`6ba7b811-9dad-11d1-80b4-00c04fd430c8`) over the UTF-8 JSON pair `[scheduleId, scheduledAt]`.

### Scan and retry lifecycle

The `5 s` scan interval, `10-minute` (`600,000 ms`) admission deadline, and `3` committed admission-attempt outcomes are current empirical defaults ([Schedule Admission Numbers Are Empirical Defaults](../decisions/20260924-schedule_admission_numbers_are_empirical.md)). NanoCore starts `1` serialized recurring scanner owner per Core data root (`apps/nanocore/src/runtime/recurring-schedule-service.ts`) after critical storage and scheduler boot recovery complete; scans never overlap, missed timer callbacks are not replayed, and stopping the service retains scanner ownership until any in-flight preparation finishes while preventing that pending pass from committing after stop. Each scan reads a Core-owned UTC wall-clock instant to select candidates and re-reads the clock immediately before each admission transaction:

1. If selection time is `>= scheduledAt + 10 minutes`, commit `expired` without an admission attempt.
2. Otherwise re-resolve the stored Workspace, Thread, active `AutomationIdentity`, active responsible user and Workspace membership (`workspace.read` for reads; `workspace.configure` for create/edit/pause/resume/delete; `turn.run` and `runtime.launch` for due attempts, with no substitute actor or approval bypass), resolve any still-`null` admission payload in memory, and run only proved idempotent Core-local setup (an unknown setup effect fences the occurrence `recovery_required`).
3. Re-read the clock immediately before the Core transaction: if `< scheduledAt`, leave `pending` without recording an attempt; if `>= scheduledAt + 10 minutes`, commit `expired` with no queue row.
4. Within `[scheduledAt, scheduledAt + 10 minutes)` and in the same `core.sqlite` transaction, first reconcile the occurrence's own deterministic queue row (if present with matching original identity and input digest, reconcile to `admission-accepted`; if conflicting, fence `recovery_required`). If no row exists for this occurrence and another accepted occurrence of this schedule links to a currently `queued` scheduler row (`admitted`/running/terminal rows do not block the waiting slot), commit typed failure `queue_backlog_full` with no queue row. Otherwise commit the reference and digest with the scheduler admission or typed failure. Dispatch requires verified publication at the original work owner.
5. If the scheduler queue row and occurrence acceptance commit, mark `admission-accepted` and never select the occurrence again; if admission fails before commit, append `1` typed attempt summary, keeping `pending` after attempt `1` or `2` for a later `5 s` scan or committing terminal `admission-failed` after attempt `3` (even if the waiting slot later opens within the `10-minute` window).

### Core transaction and unknown effects

Definitions and occurrences are Workspace-attributed product records physically stored in `server/db/core.sqlite` so occurrence acceptance, `scheduler_admission_entries` insertion, and the required Workspace-attributed `AuditEvent` share one SQLite transaction (`apps/nanocore/src/storage/recurring-attempt-native.ts`). The recurring service never calls the combined `startProductTurn` inline-dispatch path and performs no external runtime, provider, repository, or Sandbox effect in that transaction. Source admission attempts initial fixed pending Turn file publication once under the Workspace mutation fence ([Interrupted Recurring Publication](../decisions/20261016-recurring_publication_inspection.md)); an interrupted publication never reopens acceptance, a missing or contradictory fixed Turn remains non-dispatchable `recovery_required` (while queue cancel can release the series waiting slot without fabricating a Turn), and once the queue row commits, every later unknown effect follows [Durable Scheduler Design](20260703-durable_scheduler_design.md) without recurring scanner replay. To prevent a busy Thread from stranding its accepted occurrence, the existing scanner may use optional proof of a definite native `thread_busy` rollback to publish the original missing Turn after fresh active schedule ownership, authority, and Thread idle checks before consuming the proof and again before publishing. A revoked schedule keeps its accepted queue entry for queue cancellation and bars publication of its missing Turn. Each definition change serializes with that schedule’s final deferred publication check and commit in the Data Root owner process. The first write completes before the second proceeds. A definition change that waits three seconds withdraws with `409 schedule_publication_in_progress` and can be retried. The exact deferred Workspace publication has one 30-second deadline from publication ownership through proof consumption, the final schedule check, and native posting. After the deadline, exact Core readback of consumed proof releases the queue cancellation lock, and exact readback of restored proof releases the schedule definition lock, even while their receipts are pending. A posted Workspace write keeps its schedule section until exact committed Turn readback or writer settlement. An occurrence history request with `includePublicationDiagnostics: true` exposes `publicationUncertainSince` while delivery is unproved. Other schedules can continue. Worker preparation after publication has the existing attempt deadline. The proof may be restored when the Thread becomes busy before the write or when the native writer again proves a `thread_busy` rollback.

### Restart, clock changes, and missed history

Schedule and occurrence truth survives restart, resuming from durable cursors and `pending` occurrences with deadlines always derived from original nominal `scheduledAt`. Forward clock jumps make nominal instants due or expired under the same comparisons; backward clock jumps never undo terminal history, reduce attempt counts, or duplicate occurrence IDs. The transaction that inserts due occurrences or an `ExpiredOccurrenceRange` atomically advances `nextScheduledAt` and `greatestAccountedScheduledAt` (reconciling from deterministic durable coverage after an unknown commit). Each scan independently bounds work to at most `128` live admission candidates (in earliest-deadline order), at most `128` expired ranges (including prefixes materialized with live candidates, then earliest nominal instant), and at most `128` already-materialized pending expirations (current defaults; `apps/nanocore/src/lib/automation-store.ts`, `apps/nanocore/src/storage/automation-scanner-selection.ts`, `automation-scanner-native.ts`).

### Closed Security Trigger

The Server security trigger is a closed Core-local workflow on this recurring interface (`apps/nanocore/src/security/watch.ts`, `apps/nanocore/src/security/trigger.ts`, [Runtime Security](20261109-runtime_security.md#deception-and-a1-containment-e12)): off by default, with daily (`86,400,000 ms`) advisory matching, exploitation polling at most `3,600 s` (`3,600,000 ms`) apart while healthy, and a `300 s` (`300,000 ms`) Audit watch (anchored to original start timestamps rather than completion times, checking due sources on enable/boot, making no Provider call, and creating no second scheduler or executor). Trusted deception and containment sensors start observation-only; only after a current administrator reviews false trips, static/cumulative caps, and reserved recovery/alarm capacity may the fixed template enable the deterministic `containment` consumer ([Worker Runtime Communication Model](20260629-worker_runtime_communication_model.md#containment-consumer), invoked directly on sensor events outside notification Turns).

The trigger state is `securityTriggerState` in `apps/nanocore/src/storage/schema/security-trigger.ts`. Its lifecycle moves from off to on, then to stopping, then to off. Detection advances the cursor and inserts outbox rows atomically in `core.sqlite`. Raising request tuples and marking delivery are separate idempotent steps that fence partial tuples as `recovery_required`. An authorized stop or loss of the enabling administrator's authority enters `stopping` and durably inserts a fixed-grant administrator alarm before detection stops; `stopping`, `off`, and delegation loss refuse new autonomous containment while keeping already applied quarantines for their admitted Policy lifetime until authorized human widening. Outstanding notices drain at boot and every `300 s` independently of detection (including after `off`, delegation loss, and restart), acknowledged only by the recipient's recorded answer, using deterministic UUIDv5 request names, `deriveEntityId` security Thread/Turn/Item IDs, and serialized triage revisions in [Runtime Security](20261109-runtime_security.md).

## Storage, audit, backup, and portability dependencies

Workspace-attributed definitions, occurrences, expired ranges, and `ExternalTriggerAdmission` joins reside in `server/db/core.sqlite` under the `workspace-audit` retention class ([Storage Layout And Record Ownership](20260703-storage_layout_record_ownership.md), [Audit, Usage, And Evidence Records](20260703-audit_usage_evidence_records.md)) with no credentials, provider responses, transcripts, secrets, or automatic pruning. User create/edit/pause/resume/delete mutations and scanner materialization/admission share the Workspace mutation fence; every definition mutation and every terminal occurrence or expired-range transition commits its Workspace-attributed `AuditEvent` in the same `core.sqlite` transaction (rolling back on Audit failure, with one range `AuditEvent` per `ExpiredOccurrenceRange`). Same-deployment backup and restore preserve active definitions, pending attempts, accepted links, terminal history, expired ranges, cursors, and event joins, while portable Workspace export (`workspace.recurring-triggers.v1` in [Workspace Backup, Export, Import, And Data-Root Migration](20260704-workspace_backup_export_import.md)) carries definitions, history, and event joins as inert data (excluding deployment-local Workspace root and working-directory paths from portable admission payloads and never activating a schedule or replaying work).

## Acceptance

- **Deterministic timer, cadence, retry, and clock-change conformance**: under [Test Strategy](20260529-test_strategy.md), verify with deterministic clock-injected unit and Core/Store integration checks that schedules create `paused`, obey revision and mutation-fence rules, never admit before `scheduledAt` (including across backward clock jumps), interrupt between work-owner staging, kernel commit and work publication, recover each by original identity, and verify that a missing payload holds the original occurrence without copying input text into the queue, enforce the `3`-committed-outcome and `10-minute` expiry bounds (leaving proved rollbacks uncounted and unknown commits fenced), enforce the `1`-queued-occurrence waiting slot per schedule (`queue_backlog_full`, reconciling own replay first and refusing explicit denied-entry scheduler retry while the waiting slot is occupied), advance cursors and `ExpiredOccurrenceRange` rows atomically within the three `128`-per-scan phase bounds, and preserve inert portable export versus same-deployment backup/restore.
- **Monthly UTC unequal-month reopen conformance**: verify `January 28`, `February 28`, and `March 28` at one explicit UTC time through the native admission service over the same retained definition and Thread with a Core/Store reopen before February and no duplicate after repeated scans or reopen, plus leap-year, year-boundary, invalid day/zone, resume-mismatch, overflow, old-revision sealing, and SQL live-frontier ordering checks.
- **Scheduled-pull external-event conformance**: verify one event admission across repeated source reads and Core/Store reopen (including after ordinary command-receipt expiry), distinct Worker Threads for distinct `eventKey` values while an earlier case runs, current-authority refusal, immutable duplicate `(scheduleId, eventKey)` lineage/input, atomic join/queue rollback, no automatic relaunch after failure or unknown outcome, and end-to-end synthetic inbound-message polling, isolated case Thread creation, draft generation, human approval, and captured effect Audit.
