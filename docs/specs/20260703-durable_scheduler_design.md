# Durable Scheduler Design

This specification is the single owner of NanoCore's single-writer Worker Turn admission queue, private execution-attempt grant, small-deployment runtime scheduling and scale limits, attempt exclusion, bounded same-worker reconnect, terminal handoff, cleanup fencing, and missing-Turn checkpoint maintenance.

## Scope

### Owns

- The single-writer NanoCore admission queue (`scheduler_admission_entries`) for one configured execution backend, idempotent exact admission, bounded FIFO dispatch, and one private execution attempt (`scheduler_execution_attempts`) replacing `SessionLease` as the sole active-Turn execution grant.
- The separation between Core mode and worker backend deployment and the small-deployment scheduling and scale profile, including proved bounded native residency and execution.
- The split between Core admission/attempt grants and backend-private Harness/Sandbox limits, occupancy, Worker Shim cold-start staging, and release barriers.
- The generic absolute execution-attempt deadline, attempt exclusion, operation-acceptance uncertainty, exact same-worker reconnect, terminal handoff, cleanup fencing, and missing-Turn checkpoint maintenance.
- The Goal-to-Sandbox pin boundary.

### Does Not Own

- Scope-local Workspace execution and step-journal persistence, rebuilt in-memory ready dispatch indexing, server-owned keyed physical reservations, and reservation commit-gap dispositions in [Durable Execution And Control Store](20261019-durable_execution_and_control_store.md#global-dispatch-and-physical-capacity) ([decision](../decisions/20261019-durable_execution_and_control_store.md)). Until that full index, reservation, and normal/restart engine convergence lands, dispatch, the queue, and the attempt grant use this specification's mechanisms without a parallel scheduler or dual-write transition; exact request identity, bounded FIFO ordering, one writer, current authorization, single-flight exclusion, truthful uncertainty, terminal evidence, and cleanup fences remain binding until individual named fault ablations remove them.
- Product workflow progression, Task or Goal lifecycle, Coordinator wakes, review gates, Items, Artifacts, or Workspace-apply decisions ([Goal](20261002-goal.md), [Task Mode Worker Delegation](20260704-task_mode_worker_delegation.md)); the scheduler admits Worker Turns only and never wakes the Coordinator or reconstructs incomplete cross-store product owners.
- Worker-control wire schemas, process-key transport, message sequencing, reconnect authentication, or `final_status` schema ([Worker Control Protocol](20260703-worker_control_protocol.md), [Worker Runtime Communication Model](20260629-worker_runtime_communication_model.md)); physical storage layout or DDL ([Storage Layout And Record Ownership](20260703-storage_layout_record_ownership.md)); AEP resolution ([Agent Manifest And AEP Resolution](20260703-agent_manifest_aep_resolution.md)); Workspace synchronization ([Workspace Synchronization](20260703-workspace_synchronization.md)); provider usage and billing ([Audit, Usage, And Evidence Records](20260703-audit_usage_evidence_records.md)); sandbox containment ([Runtime Security](20261109-runtime_security.md)); or recurring definition, cadence, occurrence, retry, expiry, and history semantics ([Scheduler Recurring Triggers](20260711-scheduler_recurring_event_triggers.md)).
- NanoHost identity, transport, Runtime Epoch composition/lifecycle, OpenShell operations, Sandbox create/delete, OS supervision, fresh-empty readiness proof, or on-demand incompatible-idle Sandbox retirement triggers and fences ([NanoHost Runtime And Transport](20260802-nanohost_runtime_and_transport.md)). The NanoHost profile retains its attempt-held process-key hash, credentials, worker-control verification, reconnect, and cleanup ownership unchanged; any different backend or proof contract requires explicit acceptance in the affected owners.
- Dynamic multi-target selection, second backends, mixed placement, fleet worker-pool policy, generic warm pools, cross-Workspace fairness, aging, weighted selection, affinity, per-scope or per-user quotas, autoscaling, high availability, hot failover, multi-process Core writers, and distributed takeover. Core admission does not manufacture physical capacity, select fleet placement, or add a settlement workflow, recovery runner, or acceptance platform, and unadmitted scale follow-ups authorize no current records, schemas, options, runners, harnesses, or tests.

## Components

- **Single-process Core writer and configured execution backend**: the deployment profile runs `1` NanoCore process per data root (data-root lock owned by [NanoCore Bootstrap Readiness](20260704-nanocore_bootstrap_readiness.md)), `1` logical SQLite writer per owned row family in scope-owned local databases under the write and space budget of [Durable Execution And Control Store](20261019-durable_execution_and_control_store.md#write-and-space-budget), and `1` configured execution backend ID (`NanoHost` in the current slice). Core mode is separate from worker placement: the same configured backend ID is used whether NanoHost is local or remote, remote execution never creates a multi-node Core, shared database, or cluster scheduler, and Runtime Epoch, Gateway, container-runtime identity, host paths, and inventory remain NanoHost-private without leaking into the product model.
- **Core scheduler vs NanoCore-process backend adapter**: Core owns the bounded FIFO admission queue (`scheduler_admission_entries`), the private execution-attempt grant (`scheduler_execution_attempts`), exact attempt exclusion, unknown-acceptance handling, reconnect verification, and product evidence/outcomes; SQLite transactions coordinate Core state while external backend effects remain a separate effect domain. The NanoHost backend adapter is a NanoCore-process module implementing the four-verb `submit`/`inspect`/`cancel`/`release` port in [Worker Runtime Communication Model](20260629-worker_runtime_communication_model.md#execution-backend-port) ([decision](../decisions/20261006-execution_backend_port_in_nanocore.md)) that owns `SandboxRuntimeRecord`, `HarnessInstanceRecord`, and `AgentSessionRuntimeBinding` residency in its own tables and enforces proved bounds, while NanoHost Rust retains its Runtime Epoch, stock OpenShell, process, and physical fencing responsibilities with no new Rust admission API or second lifecycle owner. One Runtime Epoch may contain zero or more Sandboxes, and a compatible Sandbox may host distinct compatibility-keyed Harnesses and multiple Thread-bound AgentSessions within proved bounds, with no per-AgentSession Epoch.
- **Private execution attempt (`scheduler_execution_attempts`)**: an execution attempt (`apps/nanocore/src/storage/schema/scheduler-execution-attempts.ts`, `apps/nanocore/src/runtime/execution-attempt-records.ts`) is private Server-scope coordination for one admitted Turn (never a product run, public navigation object, or workflow) replacing `SessionLease` as the sole active-Turn execution grant (`RuntimeTarget` `active_lease_id`, mutable `capacity_state`, and test-only claim/settle helpers are deleted, and backend residency/occupancy rows are placement and cleanup projections rather than a second Core capacity grant). The attempt record is `SchedulerExecutionAttemptRecord` in `apps/nanocore/src/runtime/execution-attempt-records.ts`. Its phase set is `SchedulerExecutionAttemptPhase` and its disposition set is `SchedulerExecutionDisposition`, both in `apps/nanocore/src/storage/schema/scheduler-execution-attempts.ts`. Protocol and evidence owners retain payloads and fingerprints. A NanoHost attempt retains the Core-held worker process-key SHA-256 hash, exact reconnect lineage, and references to the three distinct control, inference, and capability credential bindings and their original SHA-256 hash evidence. Only the attempt holds execution outcome and fence facts (never duplicated on admissions); conditional attempt updates reject stale or conflicting ownership and exclude every non-closed predecessor, and connection generations and predecessor-fence facts serve only as correlation and cleanup proof rather than scheduling capacity keys. Backend readiness and native progress are observations, not attempt phases.
- **Generic scheduler predicates vs NanoHost proof mechanisms**: generic admission, attempt, route, restart, and release coordination require exact operation and execution correlation, current authority, duplicate exclusion, authoritative stop or fence proof, and complete terminal handoff, output, evidence, outside collection, drain, and route-revocation barriers without branching on backend family or requiring NanoHost-specific mechanisms from every backend ([decision](../decisions/20261006-nanohost_profile_scoping_in_generic_owners.md)). Heartbeat sequence, exact worker process-key adoption, authoritative NanoHost readiness and predecessor connections, Harness inventory, Integration loopback drain, and worker-control `final_status` are the current NanoHost profile's proof mechanisms behind the backend port with unchanged obligations.
- **Native Core publisher, recurring scanner, containment consumer, and read/control projections**:
  - The native Core owner publishes scheduler admission, retry, cancellation, and denial tuples, recurring occurrence acceptance with its queue and Audit row, and external-event acceptance with its queue and permanent join (replaying exact originals while Main prepares immutable inputs, checks early policy refusal, and runs Workspace callbacks, and the native owner rechecks current database facts).
  - One serialized Core-local recurring scan (current default `5 s`, [Scheduler Recurring Triggers](20260711-scheduler_recurring_event_triggers.md)) writes ordinary admissions only and grants no execution authority or second scheduler.
  - The deterministic Core `containment` consumer ([Worker Runtime Communication Model](20260629-worker_runtime_communication_model.md#containment-consumer), [Runtime Security](20261109-runtime_security.md)) operates outside notification Turns with its Server control journal owning bounded intent/progress and Policy/native owners holding effect truth, receiving no Worker queue slot, fabricated launch package, Turn, or AgentSession.
  - Public operations `scheduler.list`, `scheduler.retry`, and `scheduler.cancel` (`apps/nanocore/src/runtime/scheduler-admission-operations.ts`) and `recovery.worker-list` and `recovery.checkpoint-retry` (`apps/nanocore/src/runtime/worker-recovery-operations.ts`) are definition-derived projections preserving queue status transitions, Workspace Audit placement, exact request receipts, original Turn/checkpoint lineage, minimum canonical child-audience selectors, current administrator eligibility, and terminal cleanup without creating a lease, launch, recovery runner, or second durable state.

## Queue And Bounds

- **Admission record**: an admission entry is `CoreSchedulerQueueEntry` in `apps/nanocore/src/scheduler-records.ts`. Credential provenance is `SchedulerCredentialRefSchema` in `apps/nanocore/src/storage/control-store-admission-codecs.ts`. `schedulerAdmissionInputHash` in `apps/nanocore/src/scheduler-records.ts` is the admission input projection. It includes backend, request, Workspace, Thread, Turn, input, storage and Agent, profile, model, and effort selections, actor, credential provenance, cwd, and roots. It omits queue identity and mutable status. [Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md) owns the shared digest form. `commandInputHash` in `apps/nanocore/src/storage/control-store-input.ts` is the current command-hash encoding: its local stable JSON plus SHA-256, including undefined-object omission and ordered arrays. That encoding is the named current exception. It is not an RFC 8785 conversion, and this specification does not rehash history or add a migration. Optional `reasoningEffort` stays with the requested Agent, profile, model, and storage selection. Credential provenance stays non-secret. Worker pools, placement plans, capacity records, target health/probation, orphan-capacity accounting, unused supply-refresh scheduling gates, and stepped lease-renewal/cap machinery are deleted.
- **Product acceptance, fixed queue bound `20`, and FIFO order**: product acceptance validates command identity, immutable input, product lineage, selected Agent readiness and setup constraints, and at most `1` nonterminal Turn per Thread (a pending worker Turn may lack an AgentSession before dispatch, and queueing grants no inference, capability, Vault, or native execution authority). Exact insertion under an existing command identity is idempotent and returns the original row before capacity checks; changed input or contradictory provenance conflicts (`409`). Both new queue insertion and explicit retry of a `denied` entry transactionally count rows with `status = 'queued'` and enforce the **fixed contract constant of `20` queued entries** (`apps/nanocore/src/scheduler-records.ts:307,423`); a full queue is a definite refusal (`queue-full`) with no hidden later execution. Eligible queued work dispatches in original insertion FIFO order without priority aging or pool policy (explicit retry of a denied entry updates its status in place without moving its FIFO position).
- **Queued `202` receipts and capacity deferral**: a second independent Task on its own Thread while active capacity is occupied receives HTTP `202` and reads as `queued` before dispatch; exact replay validates original owners and projects current state without another admission. Capacity deferral is accepted queued work rather than a caller failure or deferred cancellation; the release-triggered wake or bounded retry pass rechecks current authority and dispatches FIFO-eligible work with no durable retry job or automatic queue expiry.
- **Single-flight exclusion (`1` non-closed attempt)**: the private execution attempt grants one bounded Turn. Its phase and disposition sets are the types named under Components, and their transition meaning is the table under [Attempt, Reconnect, And Cleanup](#attempt-reconnect-and-cleanup). An idle resident binding holds no open or closing attempt and grants no right to begin work. At most `1` non-closed (`open` or `closing`, including `unknown`) attempt may exist per Turn, per Thread, and per assigned AgentSession (`apps/nanocore/src/storage/schema/scheduler-execution-attempts.ts:69,75`); a second live attempt for that Turn, Thread, or AgentSession is refused, and neither backend refusal bypasses Core authority nor Core admission manufactures physical capacity.
- **Recurring per-schedule waiting bound (`1` queued occurrence)**: each recurring schedule may retain at most `1` accepted occurrence whose linked scheduler entry is currently `queued` (`apps/nanocore/src/storage/recurring-attempt-native.ts:206`, `scheduler-records.ts:405,415`); an earlier occurrence of the same schedule may already be `admitted`/running, and distinct schedules targeting the same Thread may each hold `1` queued row while Thread single-flight serializes execution. A recurring occurrence's `10-minute` (`600,000 ms` current default) admission deadline bounds only pre-admission retry: once its scheduler queue row commits, it remains accepted even if not executed within `10 minutes`, and later queue denial, dispatch delay, Turn failure, interruption, or unknown worker effect never cancels accepted queue work or authorizes recurring resubmission.

## Scheduling Rules

- **Durable intent before external effects and owner tuples**: durable accepted work and exact attempt intent MUST commit in SQLite before any external execution effect; admission stores only the queued request (never an outcome, fence, or capacity grant), SQLite transactions cannot atomically commit external processes, provider calls, repository effects, or Sandbox outputs, and unknown acceptance is inspected rather than resubmitted or replaced. Before returning a response or becoming eligible for dispatch, acceptance publishes the complete request-bound pending Turn, exact admission, and entry-owned checkpoint/context facts together with the initiating owner's receipt (for a direct or outer command) or exact receipt-free source tuple (for an outcome-initiated Assistant handoff under [Task Mode Worker Delegation](20260704-task_mode_worker_delegation.md#entry-points) and [Chat Mode Assistant](20260704-chat_mode_assistant.md); Pending Request outcome and recurring admissions use their existing entry owners without inventing HTTP receipts, and SQLite and files are not cross-store atomic). A recurring occurrence is accepted when its scheduler queue row commits in the shared `core.sqlite` transaction under one deterministic request ID (replay returns the same row, conflict returns `recovery_required`, and committed occurrences never resubmit after later denial, delay, failure, interruption, unknown effect, or approval wait).
- **Admission Turn identifier derivation**: an accepted upper-level `reservedTurnId` passes through unchanged without deriving another Turn ID; when `reservedTurnId` is absent, the fallback Turn ID uses `tu` UUIDv5 over the exact JSON array `[canonicalActorRefJson, workspaceId, threadId, requestId, null]` where `canonicalActorRefJson` remains the serialized canonical Trigger `ActorRef` string passed to admission (`apps/nanocore/src/runtime/product-turn-start.ts:184`, [Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md#ids), [decision](../decisions/20261015-identifier_owner_declarations.md)).
- **Actor, administrator credential provenance, and live policy revalidation**:
  - Admission resolves the immutable Turn/AEP `triggerActor` from product lineage and checks `runtime.launch` current authority before writing an admission, linking Turn, AgentSession, and package snapshot without copying another runtime `ActorRef` or using derived `responsibleUserId` as storage or capacity scope.
  - For an interactive human request authenticated by a currently usable administrator credential (Web session or bearer token under [Core Policy](../core/policy.md)), admission retains only the non-secret credential reference (`SchedulerCredentialRefSchema`) bound to the immutable human `triggerActor` and admission (never a grant, `ActorRef` extension, AEP field, or raw secret); `null` provenance uses the normal member/responsible-user path, internal/automated/recurring triggers never inherit an unpresented administrator credential, and replay preserves exact provenance.
  - Dispatch and subsequent Worker launch, inference, tool calls, credential use, and content publication resolve that same admission through Turn/attempt/package lineage and revalidate the credential's current owner, scope, usability, and active canonical User (denying without membership fallback when invalid, revoked, expired, rebound, or conflicting; restart reloads the reference and re-runs live checks without reconstructing an admin grant from actor identity alone, preserving Audit and private-audience rules with no new token/recovery owner).
  - Dispatch re-evaluates `runtime.launch` current authority, the current activated `RuntimeConfig` policy (including the original source Thread of an external-trigger admission; admission-time policy checks are early refusal only, and the native owner checks current database facts without receiving a carried allow or policy snapshot), and any requested retained-storage selection ([Persistent Worker Volumes](20260910-persistent_worker_volumes.md), [User-Selected Workspace-Shared Sandboxes](../decisions/20261008-user_selected_workspace_shared_sandboxes.md): rechecking live membership, protected-source destination admission, and actor/credential policy before preparation effects, token minting, and native submission; busy capacity leaves the pending Turn queued while a stale explicit storage selection conflicts without silent rebasing or substitution).
- **In-process preparation claim, submission, and caller error isolation**:
  - Synchronous and background dispatch share one in-process preparation claim set per Core data root ([decision](../decisions/20261002-scheduler_in_process_preparation_claim.md), `apps/nanocore/src/runtime/scheduler-dispatch-loop.ts:138`): at most `1` dispatcher prepares a queued admission at a time, a synchronous caller joins its own in-flight attempt while background dispatch skips a claimed row, the claim ends on dispatch, deferral, cancellation, or failure and is never persisted or recovered across restart (the durable attempt persisted before preparation prevents duplicate launch across restart), and command receipts do not wait on preparation or submit.
  - A synchronous caller receives only its own admission outcome (unrelated shared dispatch/acquisition failures stay with their affected owners); a caller told of a real failure has its still-queued admission cancelled and receives the original failure unchanged, whereas background transient preparation failures may retain queued retry and any preparation failure after an accepted queued receipt lands on that same Turn ([decision](../decisions/20261006-execution_backend_port_in_nanocore.md)).
  - Before calling `submit`, Core persists the attempt and immutable finalized launch package, accepts the Workspace baseline, binds `1` AgentSession, validates `SandboxCompatibilityKey`, `HarnessCompatibilityKey` (selecting/creating a Harness from runtime, adapter, governed image, and static process setup while excluding Thread, Turn, logical-model route, and transient credentials), and `AgentSessionCompatibilityKey` ([NanoHost Runtime And Transport](20260802-nanohost_runtime_and_transport.md)), and rechecks launch authority while the adapter enforces Harness/Sandbox bounds and current authoritative predecessor-fenced NanoHost readiness.
  - A backend `busy` refusal is `not_accepted` only when zero capacity or submission was reserved; Core closes that no-effect attempt and keeps the same admission and pending Turn queued so a later eligible pass allocates a fresh attempt identity after the predecessor closes.
- **Bounded Turn step, `7,200 s` absolute deadline, and ordinary Turn release**:
  - A bounded step is one Turn on a resident binding with fresh authority, AEP, Context Package, and attempt checks every Turn (never native process lifetime; Goal-dispatched Tasks are ordinary worker work with no Goal pin, Coordinator wake, or warm-state authority, and lost warm Sandbox state costs latency only).
  - At submit, Core fixes one absolute attempt deadline with a current default of `7,200 s` (`7,200,000 ms`, `apps/nanocore/src/runtime/execution-attempt-records.ts:29`). Every Core-mediated route checks the attempt, its credential family, current Policy, explicit revocation, and that absolute deadline; no runtime, heartbeat, reconnect, human wait, or adapter observation extends or pauses it, and stepped renewal is removed.
  - Ordinary Turn completion releases attempt exclusion only after complete terminal handoff, output, evidence, outside Workspace collection, Integration loopback drain ([Worker Agent Capability](20260703-worker_agent_capability.md)), Turn upstream route revocation, and proof that the binding is a safe open resident or locally cleaned (only facts affecting authorization, duplicate external work, data loss, product outcome, or physical cleanup block release; Audit rows, read models, responses, and events are projections). Ordinary Turn release preserves the shared Sandbox, resident binding, session loopback credentials, retained resume references, and working volumes without requiring `session.close`, `bridge.close`, or Sandbox deletion. An idle AgentSession retains native continuity and open-session occupancy (`maxOpenSessions`) with no Turn, inference, capability, provider, Vault, or execution grant; ordinary Turn release does not decrement open-session occupancy, which returns only after `session.close` proves exact native-context and local cleanup while preserving compatible siblings.

### Containment Control Admission

Under [Worker Runtime Communication Model](20260629-worker_runtime_communication_model.md#containment-consumer) and [Runtime Security](20261109-runtime_security.md), the deterministic Core `containment` consumer may `inspect`, `cancel`, and `release` only the exact suspect's existing backend attempt under current authority and static/cumulative E12 caps, and MUST NOT `submit` new execution; it commits bounded intent in the Server control journal before effects and inspects original Policy and native receipts after crash or connection loss.

## Scale Limits

The single-process, single-logical-writer, single-configured-backend counts and bounds below define the design and verification profile ([Specification Numeric Values Are Defaults](../decisions/20261002-specification_numeric_values_are_defaults.md)), not a user, team, or licensing authorization limit:

| Domain | Bound / Value | Classification & Owner Rule |
| --- | --- | --- |
| Core processes / logical writers per data root | The deployment counts in [Components](#components) | [Components](#components) owns that deployment profile. |
| Core admission queue (`status = 'queued'`) | The fixed queued-entry bound in [Queue And Bounds](#queue-and-bounds) | [Queue And Bounds](#queue-and-bounds) owns that fixed contract constant. |
| Active Turns per Thread and per AgentSession | The nonterminal-Turn and non-closed-attempt exclusion predicates in [Queue And Bounds](#queue-and-bounds) | [Queue And Bounds](#queue-and-bounds) owns those predicates. |
| Authored aggregate active Turns per Sandbox (`maxActiveTurnsPerSandbox`) | Current default `20` | Authored deployment configuration (`packages/config-schema/src/server.ts:197`). |
| Harness `maxActiveTurns` and `maxOpenSessions` | `maxActiveTurns` current default `20`; `maxOpenSessions = max(8, maxActiveTurns)` | Active-Turn capacity is the authored default in `packages/worker-protocol/src/harness-control.ts`. Open-session capacity is the derived equality. Core produces it when creating the Harness in `apps/nanocore/src/runtime/nanohost-harness-records.ts` and rejects a resident whose value differs in `apps/nanocore/src/runtime/turn-executor-factory.ts`. |
| Worker Shim cold-start FIFO stage | Current default `max(1, min(2, affinity, floor(quota / period)))` | Resource-derived startup concurrency bound (`packages/worker-shim/src/lifecycle-deadline.ts:23,37`). |
| Absolute execution-attempt deadline | The absolute deadline in [Scheduling Rules](#scheduling-rules) | That section states the current default. |
| Recurring scanner cadence & per-schedule queue bound | The scanner cadence in [Scheduler Recurring Triggers](20260711-scheduler_recurring_event_triggers.md) and the waiting bound in [Queue And Bounds](#queue-and-bounds) | Those owners state the current default and the queued-occurrence bound. |

- **Harness and Sandbox occupancy vs Core grants**: a compatible Sandbox may host multiple runtime families or differently configured instances through distinct compatibility-keyed Harnesses (`maxHarnesses`) and retain multiple open native AgentSession contexts (`maxOpenSessions`, including idle contexts), while authorizing bounded concurrent active Turns across distinct Threads and AgentSessions (`maxActiveTurns`, current default `20`, and authored `maxActiveTurnsPerSandbox`, current default `20`) only when the adapter and runtime prove independent state roots, routes, interruption, output, credential binding, cleanup, and declared bounds (queueing or multiple residency alone proves no native concurrency, each Thread and AgentSession remains single-flight, queued/dispatched starts reserve capacity before native acceptance while `unknown`/`closing` retain exclusion, and no lower convenience active-Turn cap may be introduced). Aggregate Sandbox bounds limit simultaneous work without replacing CPU, memory, disk, process, or network limits; a capacity refusal names the exhausted bound (`harness.activeTurns`, `harness.openSessions`, `agentSession.activeTurn`, `harness.draining`, `sandbox.activeTurns`, or `adapter.isolationProof`) without borrowing a sibling slot or inferring capacity from count or process idleness.
- **Shared-Sandbox file confidentiality boundary**: Thread-level filesystem confidentiality is NOT provided inside a shared Sandbox; Threads sharing a Sandbox can read each other's files, Thread/runtime directory separation prevents accidental path collisions rather than acting as a security boundary, and successful concurrency probes never prove security or adjudication isolation.
- **Worker Shim FIFO cold-start stage (`packages/worker-shim/src/native-startup.ts`)**: the Worker Shim admits native cold starts—including `session.open` and deferred first-Turn native service initialization—through `1` shared bounded FIFO stage across all runtime adapters. At shim startup, it reads `/sys/fs/cgroup/cpu.max` once and sets concurrency to `max(1, min(2, affinity, floor(quota / period)))` (using scheduler affinity alone when quota is `max`/absent, rounding fractional quota down before applying the minimum of `1`, and selecting `1` when `cpu.max` is unreadable or malformed), independent of the `20` active-Turn bound. Waiting in the startup stage does not consume native preparation or per-request RPC deadlines (which start after stage admission), but never pauses or extends the absolute Turn attempt deadline (`7,200 s`) or NanoHost liveness gates; a cancelled, interrupted, or authority-lost queued Turn exits the stage without launching, startup capacity returns after native acceptance or failed-start cleanup (running Turns and warm reuse do not hold a startup slot), unknown native cleanup retains its fence, and the stage has no durable records, restart recovery, or automatic retry.
- **End-to-end deadline convergence vs adapter liveness**: Core-mediated routes enforce the `7,200 s` current default total submit-to-expiry cap while the NanoHost adapter enforces its heartbeat (`30 s` current default), startup, stale-classification, and bounded reconnect rules in [Worker Runtime Communication Model](20260629-worker_runtime_communication_model.md#nanohost-adapter-liveness). Under [Durable Execution And Control Store](20261019-durable_execution_and_control_store.md), independent nested acceptance budgets give way to the propagated Core end-to-end deadline while retaining individual liveness, pacing, and fencing checks until fault-based ablation proves them unnecessary (`#535`).

## Failure Scope And Recovery

### Attempt, Reconnect, And Cleanup

Phase and disposition membership are `SchedulerExecutionAttemptPhase` and `SchedulerExecutionDisposition`. This table is their transition meaning.

| Phase | Meaning and legal progress |
| --- | --- |
| `open` | Holds exclusion during preparation, submission, execution, and observation, recording the outstanding backend operation identity and `SchedulerExecutionDisposition`. Definite no-effect refusal can close it; terminal handoff, cancellation, authority loss, or cleanup ownership moves it to `closing`. |
| `closing` | Revokes new execution authority while resolving required handoff and fencing. Accounts for outstanding effects and retains exclusion even when the product outcome is already known. |
| `closed` | Releases exclusion only after definite non-acceptance with no possible outstanding effects, or proved execution fencing plus required handoff/output/evidence/collection/loopback-drain/route-revocation barriers. Preserves first terminal cause, actual outcome, and any unknown prior effects; a fence never proves success or absence of prior effects. |

- **Before-call operation recording, no replay of unknown effects, and cancellation races**: Core persists the outstanding operation identity before calling the backend port so its disposition is `unknown` until definite acceptance or non-acceptance is proved (a crash never makes a possible call look unsent); definite pre-effect non-acceptance may requeue the same admission only after its attempt closes, whereas once any operation may have occurred Core observes and inspects that same attempt and identity without resubmitting from the ready queue or replaying on lost reply, timeout, or missing observation (new user or workflow retry is new authorized work preserving the original Turn and evidence). Queued cancellation prevents dispatch; cancellation after a possible effect moves the attempt to `closing` and invokes `cancel` on that same attempt (acknowledgement is not fencing proof, exact late evidence cannot undo cancellation, reopen a closed attempt, or authorize execution, conflicting/stale responses retain the fence, known outcome with unknown cleanup stays `closing`, and proved fencing with unknown prior effects closes truthfully as `interrupted` or `unknown`). Queued denial uses the admission owner while authority lost after attempt creation uses attempt close and Turn failure without launching or inferring retry/replacement.
- **Exact same-worker reconnect and pre-listen vs post-listen recovery**: durable attempt identity and reconnect fences (never process-local state alone) reject stale or duplicate workers after restart, and the scheduler promises no continuous availability or automatic repair at every admission-to-launch crash boundary (while deleting obsolete scheduling mechanisms does not remove Core retained-data continuity). Pre-listen boot recovery (`apps/nanocore/src/runtime/scheduler-restart-recovery.ts`) runs one effect-free ownership scan that classifies durable attempts, applies conditional fences, reconstructs open-session occupancy from persisted bindings plus Harness inventory and execution exclusion from non-closed attempts (fencing any mismatch), performs read-only restoration, and re-derives bounded result-only expectations solely from complete immutable owners, without adopting a worker before process presentation or awaiting NanoHost effects or `final_status` closeout. Core refuses mediated routes while awaiting adoption even when the `7,200 s` deadline has not expired; only the exact Core-held worker process-key SHA-256 hash, resident host proof, product/backend/binding/package lineage, next sequence, unexpired deadline, predecessor-fenced authoritative NanoHost connection, and conditional attempt CAS may adopt that same worker. A wrong reconnect request or missed heartbeat never shortens an armed reconnect window or proves Turn success/failure by itself; successful adoption continues the same attempt, AgentSession, Turn, checkpoint, Sandbox, binding, package, process key, and sequence without Epoch/Sandbox creation or native submission, whereas failed proof closes or fences the binding through its cleanup owner so a native successor runs only for new authorized work. After the listener admits the authoritative NanoHost connection, the post-listen single-flight maintenance service (`apps/nanocore/src/runtime/scheduler-attempt-maintenance-service.ts`) serially inspects unresolved original operations (at most `1` process-local cleanup attempt per affected boundary at a time) and continues owned cancellation, cleanup, and accepted-`final_status` closeout; a retained successor result settles only its exact expectation without replaying effects. After that post-listen cleanup, definite physical cleanup is recorded separately for each exact existing session with its existing Server Audit. Unrelated rows and versions stay untouched. Recorded cleanup may satisfy the reliability envelope's failed-start predicate. Product closeout stays with the product lifecycle owner. A missing row or unknown cleanup stays fenced. Outcomes stay independent. Cleanup does not synthesize a grant or receipt. An Audit projection alone does not release authority. This adds no journal.
- **Residency without live attempt, wider cleanup fences, and terminal handoff**: a disconnected healthy NanoHost is not recreated or invalidated merely because Core restarted or transport was lost; unknown local cleanup, uncertain create/delete, or NanoHost/Gateway/backend/server failure widens the Harness/Sandbox/Runtime Epoch fence until definite physical cleanup or predecessor-domain fencing plus fresh readiness is proved, interrupting each attached AgentSession independently with no shared outcome or automatic replacement. Backend residency without a live attempt is not an adoptable Turn and an idle binding is not an orphan execution; unproved idle contexts close or fence without deleting retained resume references, scanning native files for replacements, synthesizing attempts/receipts/outcomes, or reconstructing orphan counters, while on-demand incompatible-idle Sandbox retirement and its no-inactivity-timer rule are owned by [NanoHost Runtime And Transport](20260802-nanohost_runtime_and_transport.md#sandbox-and-session-lifecycle). Missing/unready backend dependencies or missing/conflicting/overcommitted capacity refuse launch with a typed diagnostic without borrowing sibling slots, lost warm Sandbox state costs latency only (and a missing Goal pin is never a failure), missed-heartbeat stale classification holds `needs-evidence` exclusion, and Action Center is a projection owning no scheduler state. Worker-control `final_status` is transport evidence rather than completion authority: when its accepted record and safety-critical Turn, checkpoint, evidence, Workspace, backend, and attempt lineage agree, the attempt moves to `closing` and finishes through the owning transaction, whereas any partial or contradictory owner/terminal tuple (including Turn-ID derivation or acceptance mismatches) remains inspectable and non-dispatchable as `recovery_required` with no synthetic winner, receipt, effect repeat, or repair state.

### Missing-Turn Checkpoint Maintenance

- **Boot fail-closed rule**: boot classification stays fail-closed when a Task checkpoint's product Turn cannot be read (`getTurn` returns the same error whether the Turn is absent or owned by another Workspace/Thread), and restart recovery MUST NOT treat that error, a `null` `workerSessionId`, a `failed` checkpoint, or an attempt with first terminal cause `turn-start-failed` as proof that no Worker ran and MUST NOT delete the checkpoint.
- **Live synchronous cancelled-first-admission exception ([decision](../decisions/20261006-live_cancelled_task_checkpoint_removal.md))**: a live synchronous Task invocation (ordinary, selected-Worker, or Goal-dispatched) that cancels its own deferred or refused first admission MUST remove its own still-preparing checkpoint before returning the refusal only when complete local proof holds: the checkpoint was created by this invocation for the same Workspace, Thread, reserved Turn, request ID, and canonical input hash, remains `preparing` with `workerSessionId: null` and `stopReason: null`, was not admitted to the caller, matches exactly `1` durably `cancelled` admission, and has no attempt opened, no submit accepted or unknown, no durable product Turn under any owner, no accepted worker input, no AgentSession execution association, no backend session, no worker-control record, and no terminal or non-invocation preparation evidence (the invocation's own pre-admission context digest, context-selection diagnostics, and preparation authorization do not disqualify it, whereas an already accepted queued Task has a durable Turn/receipt and closes through its mode owner). After durable Core cancellation, the mode rechecks the proof and deletes only the checkpoint in the Workspace refusal transaction while retaining the cancelled admission and preparation/auth/evidence records (releasing no capacity, retiring no runtime, creating no nested receipt, and never allowing the cancelled request ID to relaunch; unproved cancellation, missing/changed/contradictory owners, removal failure, or a crash between the separate Core and Workspace commits preserves the checkpoint fail-closed, with no boot, replay, historical, or bulk deletion authority).
- **Stopped-server `task-checkpoint:clean` operator command (`apps/nanocore/src/runtime/cancelled-admission-checkpoint-cleanup.ts`)**: outside the live exception above, only the stopped-NanoCore operator command may delete a missing-Turn leftover. It requires the exclusive data-root lock, explicit checkpoint IDs, and a backup destination argument (defaulting to dry-run; on apply, writing a consistent external backup of each affected Workspace database before rechecking the row and deleting only that checkpoint through the terminal-checkpoint clearer; classification/dry-run never prune receipts, migrate Threads, repair approvals, or create databases, and any matching command receipt—even expired—contradicts deletion). The command admits a checkpoint only when all of the following hold:
  1. Stage is `failed`, `stopReason` is `error`, `workerSessionId: null`, `goalId: null`, `taskId: null`, and `iteration: 0` (excluding nonterminal, durable-Turn, boot, and Goal-affiliated checkpoints).
  2. The Turn has no context digest, context-assembly diagnostics (which count as execution evidence even if a summary parser is incomplete), Items, Artifacts, runtime-evidence rows, evidence bundles, AEPs, worker-control records, backend sessions, or AgentSessions.
  3. The Turn ID is globally absent across all Workspace and Thread owners (any present Turn, lineage mismatch, or unreadable/corrupt history—including malformed checkpoint diagnostics—refuses the entire invocation and deletes nothing), and the Workspace and Thread records match the selected identity.
  4. No attempt for the Turn is `open` or `closing`, at most `1` attempt exists, and the checkpoint matches **exactly one** of two no-effect proof tuples:
     - **Tuple A**: `1` matching `cancelled` admission for that Workspace, Thread, Turn, and request ID, and `0` attempts.
     - **Tuple B**: `1` `closed` attempt for that Workspace, Thread, and Turn with first terminal cause `turn-start-failed`, definite pre-effect `not_accepted` disposition, no backend ownership/heartbeat/sequence/process-key/route-token hash, and `1` matching `admitted` admission whose retained input, package, and operation facts prove no backend effect was possible.
  Deletion removes only the proved checkpoint (repeated apply on an absent row is a no-op, a changed row is left in place, lock/backup/read failure refuses before deletion, and no Turn, receipt, attempt, admission, residency, retry, or capacity release is created or mutated).

Also verify own-failure cancellation that keeps the original failure, background transient retry, the L1 subjects in [Scheduling Rules](#scheduling-rules) before `submit` (the immutable finalized launch package, the accepted Workspace baseline, exact compatibility, and launch authority) and the L1 subjects in [Attempt, Reconnect, And Cleanup](#attempt-reconnect-and-cleanup) (Core-held process-key adoption and reconnect refusal), per-Turn, per-Thread, and per-AgentSession exclusion while unknown or closing, stale-response rejection, cancellation-versus-dispatch ownership, backend bounds, deadline, revocation, and liveness refusal, release fencing, one configured backend identity, a running occurrence plus one waiting occurrence, distinct schedules under single-flight, no post-acceptance expiry cancellation, fresh per-Turn checks, and no Goal-pin writer.
