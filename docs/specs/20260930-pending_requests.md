# Pending Requests

This specification owns the Pending Request lifecycle, captured-call execution, and Discord attention responses.

## Decision

A pending request is the durable record of one approval request or one user-input request. It is raised by a governed call or command, resolved or ended by a person or an invalidating event, and delivered to its requester by a later Turn on the same Thread. Raising it never changes the status of the Turn that raised it. The record is the source of the request's state and of the Approval status, and Items remain its communication record. A producer that used to pause a Turn in `awaiting_human` raises a pending request instead. No agent approver is activated. The approver field exists. Native MCP Tasks are not on the wire. Link-back uses the Item `id`. It may fail to resolve and must never point at the wrong record. `seq` is only a per-file truncation counter. A configuration apply writes its marker Item on the Turn that executes the apply, with link-back to the proposing Item. It is never written onto an already terminal proposing Turn. Evidence that a request ended carries the request identity, the reason, the deciding actor, the time, and a link back to the initiating Item. `StatusItemSchema` has no structured slots for those facts. This record holds them. The Item carries a readable summary. No new retention container is added.

## Contract / Expected Behavior

### Definition And Exclusions

A pending request has one kind, `approval` or `user-input`, and one requester:
- **A worker agent**, which raises it through a governed MCP call: an approval-required external tool or the built-in `work_input_request` tool.
- **The internal Assistant**, which raises a clarification question in Chat Mode, and later an approval-required MCP call when its internal branch is implemented.
- **The Coordinator**, an internal agent bound to one Goal. It is its own requester and is not a person. A rule for the Coordinator applies to that requester without treating the Coordinator as a person. Propose Plan raises an approval whose exact intent is one exact Plan version. The Coordinator's call to accept completion has no authority to accept, so that call becomes an approval whose exact intent is the captured call, in the same pattern as an approval-required tool call. After a person or a currently usable administrator grants it, the captured call executes when the Goal owner consumes the grant, and that execution records the granting actor as the decider. The grant does not by itself execute the call. It is not an MCP binding, it is not a new request kind, and it adds no operation. The decision is recorded in [Goal Contract Gap Rulings](../decisions/20261002-goal_contract_gap_rulings.md).
- **A person**, whose own governed command requires another decision. A grant for a person's request executes nothing by itself; the person or external coordinator performs the governed command afterward through its owner. Command-intent approvals use the command-intent grant and consumption rules whether the requester is a person or the Coordinator; requester identity selects the delivery executor, not whether the approval governs a captured call. The Coordinator's Turn is the delivery opportunity for a Plan activation or completion grant, and delivery is not itself proof of consumption. The Goal owner consumes that grant through the Main effect-submission authority check and complete native claim-and-effect transaction; invalidation that wins before the claim prevents the effect. Consumption of a Plan grant activates the exact Plan version. Consumption of a completion grant executes the captured accept-completion call, records the granting actor as the decider, and writes the completion disposition. The resolve command records the grant and executes no worker work. A granted but unconsumed Plan approval or completion grant of a cancelled Goal is refused with a conflict when consumption is attempted, and that attempt does not execute. The decision is recorded in [Goal Contract Gap Rulings](../decisions/20261002-goal_contract_gap_rulings.md). A note that changes the commitment is a new Plan version and a new request, not a grant of the open one. An effect-specific approval stays with its effect owner.

- **Automation**, closed requester value `automation`, raises deterministic security requests through a Core-local Turn. A later Core-local Turn publishes its outcomes, without an agent or AgentSession. [Runtime Security](20261109-runtime_security.md) E4 and E6 own its producer and recipient workflow.


Exclusions:
- In-Sandbox tool use never raises an approval.
- A native runtime permission prompt never becomes a request; it receives the pinned runtime's shortest-lived allow by default without interrupting the Turn, and a user's explicit native deny rule stays ([decision](../decisions/20261001-sandbox_full_capability_rulings.md)).
- A review verdict is not a request here. Artifact Review, Workspace Sync Review, and Knowledge Review keep their own durable identity and may accept a response after their source Turn is terminal.
- A native effect that has no gateway operation cannot be approved.

### The Record

The workspace record `PendingRequest` holds:
- identity: the request id, which is the `approvalRequestId` or `userInputRequestId` already used by Items, plus the Workspace, the Thread, the raising Turn, and the request Item;
- `kind` and the requester, with its Agent identity where applicable and its AgentSession only when the requester executes through an AgentSession;
- the responsible user, who may resolve or withdraw it, as may a currently usable administrator credential under the administrator eligibility rule in `docs/core/policy.md`; the recorded deciding or ending actor is the actor who acted, and an administrator is recorded as that administrator;
- `state`: `pending`, `resolved`, or `ended`;
- for a resolved request: the resolution (`granted`, `denied`, or `answered`), the deciding actor, the decision time, and, for an answer, the answer map;
- for an ended request: `withdrawn` or `invalidated`, the invalidating event, the ending actor, and the time;
- for an approval that governs an agent's captured call, the captured call binding: server id, catalog revision, schema snapshot, tool, the full canonical arguments and their digest, and the originating authorization context, which is the Thread, Turn, AgentSession, Agent, responsible user, package digest, and policy decision;
- for a command-intent approval, whether the requester is a person or the Coordinator, the exact intent of the governed command it authorizes, one exact Plan version, or the captured accept-completion call that names one exact completion candidate. The Coordinator requester is not a person;
- for either kind of approval, the claim (`unclaimed`, `claimed`, or `finished`), the execution `CapabilityCall` id derived from the request id, the disposition (`approved-executed`, `denied-not-executed`, `execution-error`, or `outcome-unknown`) with its reason, and the bounded normalized result held for delivery;
- the publication Turn: the one Turn on which the outcome's Items are written, set once and never moved, and, for a command-intent grant invalidated after its decision, the separate invalidation Turn of that invalidation's `status` Item, which is absent until its publication is admitted and is then set once before the Item is written, while the recorded `denied-not-executed` stays durable as it waits;
- the delivery state: `undelivered`, `frozen` with the delivering Turn id, `delivered` with that Turn id, `delivery-unknown` with that Turn id, or `closed-out`, which states that no delivery to the requester followed and none will, and asserts nothing about what the requester saw.

The ApprovalRequest projection reads its status from this record; approval state is never derived from Items. Arguments and results are sensitive work data: they are never copied into usage or audit rows, and the held result is cleared once its delivery is proved. The record is a Workspace SQLite family under the storage layout owner's schema rule.

### Assistant Work Selection

An Assistant `user-input` request may retain one optional typed `assistantHandoff` descriptor. Its closed kind is `task` or `goal`; it retains the receiving Workspace, exact Task input and optional Agent/model selection, or exact Goal intent. The canonical request Item projects the same descriptor and questions. The record is the unique decision owner; the Item is communication. Duplicate raise compares the descriptor and question digest, canonical-load validation checks their exact equality, and the frozen outcome source hash includes the descriptor and recorded human answer. An unknown kind, malformed descriptor or mismatched projection fails closed. Retained ordinary requests have no descriptor and keep their current lifecycle.

The inline question displays every byte selected for shared execution. Only its exact affirmative answer selects that payload. A negative, other, withdrawn or invalidated outcome does not start work. This is elicitation, not a permission Approval or an authorization grant. The native Assistant outcome handler rechecks the original deciding credential as its recorded deciding user, separately from the responsible user's current execution, source and disclosure authority through the receiving owner. An administrator's confirmation does not supply the responsible user's execution credential or context. A revoked deciding credential still refuses the handoff. It uses the exact frozen payload without another model or keyword vote. Task and Goal keep their existing business records, and no nested command receipt, new store or new runner is added. A partial downstream tuple is inspect-only recovery; restart never infers or repeats an uncertain effect. The Assistant owner defines the resulting handoff Item and linked Thread tuple.

### Captured Execution Call Identifier

The existing execution CapabilityCall derived from a Pending Request uses `cap` UUIDv5 with exact JSON name `["pending", requestId]`. `requestId` is that exact durable Pending Request. [Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md#derived-entity-kinds-and-namespaces) supplies the kind namespace and canonical name bytes under the [accepted owner-declaration condition](../decisions/20261015-identifier_owner_declarations.md). The existing request-derived identity remains stable across the native reservation and Main effect-submission boundaries defined below. The name admits no second contact after a completed or uncertain claim. Existing call attribution, disposition, retention and failure rules remain binding. Acceptance requires stable request-derived identity after reopen and unchanged contact counts under exact replay.

### Exact Effect Disclosure

An approval's exact effect detail is a read-only projection of its immutable captured binding. For a captured MCP call it contains the server id, tool name, argument digest and the complete canonical arguments. It never contains a resolved credential, a private endpoint or runtime internals.

Cards, Items and attention lists carry a summary of at most 2,048 UTF-8 bytes and never the raw captured arguments. The request's responsible user, with current access to its Thread, can read the complete detail, as can a currently usable administrator credential under the administrator eligibility rule in `docs/core/policy.md`. The detail is at most 524,288 bytes of compact canonical UTF-8 JSON. Detail is unavailable if it exceeds that limit, cannot be loaded completely, or cannot be shown without omitting an effect-bearing value. Truncated or redacted content is never presented as exact.

Grant requires available exact detail. The response command checks this before it records a grant. When detail is unavailable, the command returns `409 approval_preview_unavailable` with no grant, no claim and no upstream contact, and the request stays open. Deny and withdraw remain available. No preview-read record is created. The decision is recorded in [a decision record](../decisions/20261001-approval_exact_effect_disclosure.md).

### Raise

Raising runs inside the governed call or command, in this order:
1. The caller's current authorization is evaluated, and the Thread must not be archived. A call that is not requestable fails as `capability_denied` and records nothing.
2. **Deduplication.** A repeated call matches a `pending` request on the same Thread when it has the same qualified binding: server id, catalog revision, schema snapshot, tool, canonical arguments, Agent, and responsible user. A repeated `work_input_request` matches when it has the same Agent and the same canonical question payload. A repeated command-intent approval matches a `pending` request on the same Thread when it has the same requester and the same exact intent, whether the requester is a person or the Coordinator. A match returns the existing request's pending result and records nothing new. It never substitutes an earlier effect for a different one, and it does not decide whether two calls after a terminal outcome are the same occurrence.
3. **Bound.** A Thread holds at most 16 `pending` requests. A raise over the bound fails as `request_limit_reached` before any write.
4. **Recording.** The request, the ApprovalRequest projection for an approval, and the request Item on the raising Turn are written together. The raising `CapabilityCall` is recorded as `denied` with no upstream contact for an approval, and as `succeeded` for `work_input_request`, whose function is to record the question.
5. **Pending result.** The call returns at once with the same pending fields in its structured and text content: `status` (`pending-approval` or `pending-input`), the request id, and a next-step sentence telling the agent that the outcome will arrive on a later Turn and that it must not call again to claim it. An approval's result is `isError: true`, because the tool has not executed. A `work_input_request` result is `isError: false`, because recording the question is the tool's function.

A call that policy allows without approval is not a pending request. A policy grant is never presented as a human decision and is not an agent approver.

### Resolve

- **Approval.** The existing approval response command, `POST /api/app/operations/approval.respond`, carries `approvalRequestId`, `workspaceId`, `threadId`, the raising `turnId`, command `requestId`, and `decision` (`granted` or `denied`). It is accepted while the request is `pending`, whatever the status of the raising Turn. Target selectors must match the retained request lineage; an admitted request with mismatched approval scope returns `400 invalid_request`.
- **Answer.** The command `user_input.answer`, projected as `POST /api/app/operations/question.answer` with `userInputRequestId`, `workspaceId`, `threadId`, command `requestId`, and `answers`, is accepted while the request is `pending`. The answer rules are unchanged: `answers` is `{ [questionId]: [string] }` with exactly one non-empty value per question, the keys equal every and only the request's question ids, a missing or extra key or a duplicate question id is `400 invalid_request`, and a request containing a secret question returns `400 secret_input_not_supported` before any write. It replaces the answer branch of `turn.input.submit`.

Rules shared by both commands:
- **Actor.** The responsible user may resolve, with current Workspace membership and authority. A currently usable administrator credential may resolve under the administrator eligibility rule in `docs/core/policy.md`, without that membership. The command records that actual deciding actor. The approval record is still checked. Any other actor gets `workspace_access_denied`.
- **Replay and conflict.** One response wins. An exact replay returns the recorded outcome through the command receipt. A different decision or answer map for the same request is `409 idempotency_key_conflict`. A response to a request that is already resolved or ended returns `409 request_not_pending` with the recorded state, before any write.
- **Missing owner.** A request whose record, Item, or projection is missing or contradictory returns `409 recovery_required` without writes. A slow answer is never that case.

Recording a denial or an answer sets `state=resolved` with the resolution, the actor, and the time; a denial moves the Approval to `denied`, and a denial of an approval that governs a call records `denied-not-executed` in the same write. A grant of an approval that governs an agent's captured call is recorded only together with its execution decision, as the next section defines, so such a grant is never published unclaimed. A command-intent grant, whether the requester is a person or the Coordinator, is recorded as `resolved` and `granted` with its claim `unclaimed`, and its effect owner later consumes it through the effect-submission authority check and native claim-and-effect transaction defined below. Invalidation that wins before the claim prevents the effect. The person's own governed command remains the command that claims a person's grant. The Approval moves to `granted` with the grant. The command's receipt is published after any disposition is recorded.

### Execute A Granted Call

Execution after a grant, for an approval that governs an agent's captured call, runs inside the approval response command and never in a background process:
1. **Resolution of asynchronous inputs.** A value that needs asynchronous resolution, such as a credential read from the Vault, is resolved first.
2. **Native reservation.** The native writer checks that the request is `pending`, the Thread is not archived or deleted, and the native-owned withdrawal and business comparisons still permit the operation. Its compare-and-set records the grant, actor, time and `claimed` state with the request-derived execution `CapabilityCall` identity. The claim is an at-most-once reservation, not Main-owned authority. A native invalidation that wins before this compare-and-set prevents the effect. The response waits for FULL acknowledgement of the claim.
3. **Main submission and execution.** After asynchronous input preparation and the claim acknowledgement, the existing Main effect owner synchronously checks current identity, Workspace membership, responsible-user and Agent authority, Thread supply, schema, Policy and Vault grants immediately before contact. The database worker records the original execution `CapabilityCall`, `PermissionDecision` and required Audit as one local tuple, correlated by the request-derived execution call identity, under the [native writer boundary](20261019-durable_execution_and_control_store.md#write-and-space-budget). Main awaits FULL acknowledgement before contact and rechecks current authority after awaited commits. If the authority check fails, the native writer commits the failed execution call and its existing submission-refusal PermissionDecision with `upstreamContacted=false`, required Audit and no usage, then Main posts the native `execution-error` disposition without contact. A later submission refusal preserves the earlier Approval winner and links the request through its existing context rather than claiming a second winner. Otherwise the gateway executes the exact captured call with the ordinary timeout and result bounds.
4. **Disposition.** The claim moves to `finished` with `approved-executed` (the call succeeded), `execution-error` (it failed and its outcome is known), or `outcome-unknown` (contact may have happened and the outcome cannot be established). The execution `CapabilityCall` is recorded as `succeeded`, `failed`, or `unknown`, with its upstream-contact knowledge. Usage follows the ordinary rule: none when upstream is proved not contacted.

The contacted execution's tool-call measurement uses the [Capability Usage recorder](20260703-audit_usage_evidence_records.md#call-and-usage-identity)'s independent `use` UUIDv7 default. Keep its `capabilityCallId` and complete measurement-equivalence facts separate from identity. An equivalent stored measurement returns its retained ID after replay or reopen; only a new measurement allocates. The same claim permits at most one contact, an uncontacted call creates no usage, and unknown claims never execute again. This declares no request-derived or call-derived usage identity. Allocation triggers, measurement semantics, retention and recovery remain unchanged.

For MCP schema re-evaluation at Main submission, a `tracking` entry compares the requested tool name and complete retained `inputSchema` between the captured and current snapshots. A missing tool or changed input schema yields `execution-error` after the claim, without upstream contact. A retained captured call whose tool left the supply keeps the decision `granted` and ends after the claim as `execution-error` with reason `tool-left-supply`, with no contact and no usage. Compare the complete schema by canonical JSON equality, including nested descriptions and annotations. Other-tool changes and top-level tool metadata changes outside `inputSchema` do not refuse the call. A `pinned` entry retains whole-snapshot refusal. The catalog revision, eligibility, authority, Policy, credential and native claim checks still apply at their owned boundaries. This uses the retained snapshots without a new durable field ([accepted #117 decision](../decisions/20261012-requested_mcp_tool_schema_at_grant.md)); [Worker MCP Tool Supply](20260704-worker_mcp_tool_supply.md) owns upstream execution.

The synchronous Main submission check is the linearization point for Main-owned authority. Revocation before this check prevents contact even when the native claim is already acknowledged. The native compare-and-set separately orders withdrawal, archive, competing responses and native-owned business mutations: one that wins before the claim prevents the effect, and a claimed request can no longer end. There is no lock, lease, snapshot, global gate or cross-owner atomicity claim. An ended request can no longer be claimed.

A command-intent grant, whether requested by a person or the Coordinator, is consumed by its existing effect owner after asynchronous preparation. For a native Goal Plan or completion operation, Main checks its current authority synchronously immediately before posting the complete native claim-and-effect transaction. The operation linearizes at that check; authority changes after the post do not revoke that admitted operation. A withdrawal or conflicting business mutation that wins before the native compare-and-set still prevents the effect. The Goal claim, exact Plan activation or completion mutation, owned disposition and original receipt commit in one native transaction. Each later effect passes its own effect-submission authority check. Consumption of a completion grant executes the captured accept-completion call and records the granting actor as the decider; consumption of a Plan grant activates the exact Plan version. A granted but unconsumed Plan approval or completion grant of a cancelled Goal is refused with a conflict, does not execute and records `denied-not-executed` with cancellation as the reason. A person's grant still waits for the person's own governed command. Invalidation applicable before the native claim preserves the recorded grant and prevents a later effect; End defines its scope. Plan supersession applies only to older pending Plan requests, not to already granted requests. Other command-intent consumers apply the same authority rule at their existing effect-submission owner. The [authority decision](../decisions/20261021-pending_authority_at_effect_submission.md) records this boundary.

A denial records `denied-not-executed` without re-evaluation. A crash before the native claim leaves the request `pending`, and the command's incomplete receipt returns `recovery_required` to a replay of the same command without any execution. After a restart, a claim that is `claimed` and not `finished` becomes `outcome-unknown` and is never executed again, even when no contact was made. A crash or lost acknowledgement between the claim and the Main submission step never permits a second execution. Recovery records truthful contact knowledge: the execution call row precedes contact, so its absence proves no contact; its presence alone does not prove contact.

### End

A pending request ends without resolution:
- **Withdrawal.** The command `pending_request.withdraw`, projected as `POST /api/app/operations/pending-request.withdraw` with `pendingRequestId`, `workspaceId`, `threadId`, and command `requestId`, lets the responsible user, or a currently usable administrator credential under the administrator eligibility rule in `docs/core/policy.md`, withdraw a `pending` request. The recorded ending actor is the actor who withdrew. The Approval becomes `withdrawn`. Agent withdrawal is defined with the same effect and is not enabled. The Approval status values this owner writes are `granted`, `denied`, `withdrawn`, and `expired`. `superseded` stays reserved and has no writer.
- **Invalidating events.** Archive of the Thread, deletion of the Workspace, loss of the responsible user's membership or authority, and removal of the requesting Agent or loss of its authority. Cancellation of a Goal and supersession of an open Plan proposal are the invalidating events the following bullets define, and they end only the open requests those bullets name. The Approval becomes `expired` for a request one of these events ends. The command that archives a Thread or deletes a Workspace, ends that scope's pending requests in its own write, and archive closes out the Thread's outcomes as Closeout defines. Loss of membership or authority is detected and written at the next response, withdrawal, execution, or delivery attempt; no process scans for it.
- **Goal cancellation.** Cancellation of a Goal ends every open Plan approval and every open completion request of that Goal in the cancellation's own write. Open means the request is still pending. Each ends as invalidated, with the reason that the Goal was cancelled. The person sees that reason where the request is shown, including the `status` Item summary Deliver requires for an ended request. A granted but unconsumed Plan approval or completion grant of that Goal is not ended by this write. Its consumption attempt is refused with a conflict, does not execute, and records `denied-not-executed` with the reason that the Goal was cancelled under the existing command-intent invalidation rules. The decision is recorded in [Goal Contract Gap Rulings](../decisions/20261002-goal_contract_gap_rulings.md).
- **Plan supersession.** A new Plan proposal ends every older open Plan proposal of the same Goal in that proposal's own write. Open means the request is still pending. Each ends as invalidated, with the reason that a newer Plan proposal superseded it, by the same immediate invalidation as Goal cancellation of an open request. The person sees that reason where the request is shown, including the `status` Item summary. This does not end the active Plan version, a completion request, or a granted but unconsumed Plan grant. The decision is recorded in [Goal Contract Gap Rulings](../decisions/20261002-goal_contract_gap_rulings.md).

Ending sets `state=ended` with the reason, actor and time through the native request compare-and-set that Execute A Granted Call defines.

Release, replacement, or failure of the requesting AgentSession does not end a request; neither does the end of the raising Turn, a restart, or elapsed time.

### Deliver

An outcome is a resolution with its disposition, where there is one, or an ending. It is ready when it is final: an answer, a denial, an ending, a grant of an agent's captured call whose disposition is recorded, or a command-intent grant, whether the requester is a person or the Coordinator, which is ready at once as a decision because its owner consumes it afterward. Requester identity selects the delivery executor, not whether the approval governs a captured call. A granted approval whose execution is still running is not ready. Every ready outcome is delivered to its requester, including a withdrawal, so that the agent does not wait for an answer that will not come; an outcome that no requester can receive is closed out instead.

Matching an outcome to a Turn:
- An outcome is delivered only by a Turn whose executor is its requester: a worker outcome by a worker Turn on that Thread, an Assistant outcome by an Assistant Turn, a Coordinator outcome by a Coordinator Turn on that Goal's Thread, and a person's or `automation` outcome by a Core-local Turn.
- A Turn admitted for any cause, such as a user message or a retry, freezes into its input the ready, `undelivered` outcomes that match its executor, in readiness order, up to 16 per Turn, and keeps its own trigger. Freezing sets `delivery=frozen` with that Turn id in the same write as the Turn's admission. The rest wait for the next Turn.
- When matching outcomes are ready and no Turn is being admitted, Core admits an outcome-initiated Turn for them. Executor precedence stays unchanged. An autonomous Worker or Assistant Turn continues the first readiness-selected outcome's responsible user P; the Worker also keeps that outcome's Agent. Its batch contains only the same executor, Worker Agent and responsible user P. This principal filter applies before the 16-outcome bound. Other users' outcomes remain undelivered for a later Turn; they are not consumed or refused.
- An autonomous Worker or Assistant Turn has `triggerActor = { kind: 'user', id: P }`, the accountable execution principal defined by the [multi-user Workspace contract](20260715-multi_user_workspace_system.md). Current authority is rechecked at the existing admission and effect boundaries; a retained User id supplies provenance, not a grant. Decision and ending attribution stays on the Pending Request and its existing communication Items, never in the execution principal. Independently admitted Turns carrying outcomes keep their admitted authority, and the Coordinator keeps its Goal principal.
- The outcome Turn's trigger is `approval-resolution` when its actual frozen batch contains an approval outcome and `user-input` otherwise, with a summary naming that batch's counts. Preparation, native admission and freezing use the same readiness selection, including the request-id tie-break. Canonical association validation refuses an autonomous Worker or Assistant batch whose responsible user differs from its admitted Turn, before dispatch or reopen; this refusal does not cause an immediate retry.

The 16-outcome limit bounds how many outcomes a Turn carries, not their bytes. There is no aggregate input byte budget. Delivery carries every selected value completely and never truncates, drops or summarizes one. Each producer and transport keeps its own limits and typed refusals. A large input can therefore be refused downstream by an executor. That refusal is handled by the existing delivery rules. The decision is recorded in [a decision record](../decisions/20261001-pending_delivery_count_bound.md).

When admission is attempted, with no polling process:
- when an outcome becomes ready while the Thread has no non-terminal Turn, which is inside the response, answer, or withdraw command, after any execution;
- at the terminal barrier of every Turn on the Thread, except the barrier of an outcome-initiated worker Turn refused before native submission, whose released outcomes wait for the next other trigger so that a Thread whose agent cannot start does not loop;
- at boot, after scheduler fencing, for each Thread with ready `undelivered` outcomes and no non-terminal Turn.

Only one outcome-initiated Turn is admitted at a time. When several executors have waiting outcomes, the worker, Assistant, or Coordinator Turn goes first and person or `automation` outcomes follow at the next idle point.

Execution and the proof that ends delivery, per executor:
- **Worker requester.** The Thread's worker Agent runs the Turn, which is created `pending`, is admitted under current authority, and waits for worker scheduler capacity. The frozen outcomes enter its worker input as structured context: each request, its resolution or ending, and, for every approval that governs a call, the disposition with its reason and any bounded result. The Turn runs on the current AgentSession, or on a successor that resumes the native conversation when that binding has ended. Delivery requires exact receiver read-back that identifies the frozen input in processing on that Turn. A native submission acknowledgement establishes intake only.
- **Assistant requester.** The Chat Mode owner runs the Turn with the answer as the clarified input, with no AgentSession and no worker scheduler capacity. Delivery is proved when the Assistant service durably accepts the Turn input.
- **Coordinator requester.** The Goal owner runs the Turn with the granted or refused intent as input, with no AgentSession and no worker scheduler capacity. Delivery is proved when that owner durably accepts the Turn input. The grant does not admit a worker Turn.
- **Person requester.** A Core-local Turn records the Items and completes, runs no agent, and needs no scheduler capacity. Delivery is proved by that Turn's completion, written together with its Items.

The derived Item identifiers published by this owner retain their request-id and role inputs. The output uses `it_` plus canonical lowercase UUIDv5 text in the fixed Item namespace from [Protocol Identifiers And Enums](20261021-protocol_identifiers_and_enums.md#derived-entity-kinds-and-namespaces). Its exact name bytes are the UTF-8 RFC 8785 JSON Canonicalization Scheme output for `[requestId, role]`, in that order. `requestId` is the exact durable pending-request identifier. For a `user-input-request` Item, it is the recorded `userInputRequestId`; for an approval-request Item, it is the recorded `approvalRequestId`. Both request Items use exactly the role `request`, including when either is a Chat result. Their name is `[requestId, "request"]`, not a Turn-based Chat result name. `role` is exactly `request`, `decision`, `answer`, `disposition`, `disposition-status`, `ending`, or `invalidation`. The distinct `disposition-status` role names a status companion to the disposition Item. This fixes name bytes without changing publication or restart-completion predicates. [One Identifier Mechanism](../decisions/20261014-one_identifier_mechanism.md) records the output-encoding decision.

**Outcome and closeout Turn identity.** Core-assigned outcome or closeout Turns whose former names included a fresh clock use independent `tu` UUIDv7. Allocate once at existing first admission before that Turn's first effect, and retain its exact ID in the existing canonical Turn and publication/delivery association. A clock is not deterministic retry identity. A complete existing association reuses its exact `publicationTurnId`, `deliveryTurnId` and separate `invalidationTurnId` according to their existing meanings. It never moves publication or allocates a replacement Turn ([accepted conditional D2 realization](../decisions/20261015-identifier_association_and_import_boundaries.md)).

Required association and canonical Turn validation precede success on retry or boot completion. An identifiable partial owner with a missing required counterpart remains `recovery_required`, including a publication pointer without its required Turn or an outcome Turn without its required association. Preserve the existing record and effect uncertainty. Do not infer association from time, title, an ID suffix, readiness order or the current pending list. Do not create the missing counterpart as repair, repeat an effect, or report success merely because an invalid row was skipped. Initial admission without effects may allocate once; an unproved partial state is not empty authority.

SQLite association and file-backed Turn publication remain separate effect domains. Admission and closeout triggers, outcome bounds, freeze ordering, late-answer behavior, one nonterminal Turn and source authority remain unchanged. Existing stable invalidation Turn naming uses `tu` UUIDv5 over `["invalidation", requestId]`, with the same first selected durable request as its current owner. Retry follows recorded `invalidationTurnId`; it does not select a new first request. No closeout registry, timestamp field, alternate UUIDv5 tuple or repair path is added. Existing Item-completion, receipt, claim, retention and deletion rules remain binding.

Acceptance covers complete-association reopen and crashes after Turn persistence before association, after SQLite closeout before Turn publication, after association before Items, and after Items before terminal proof. Complete tuples retain their Turn; partial tuples refuse replacement allocation and extra effects. If first-admission proof needs a new durable field or cross-store transaction, that dependent implementation requires separate acceptance.

**Publication.** An outcome's Items are written once, on its publication Turn, which is the first Turn that freezes it or its closeout Turn. The record names the publication Turn in the same write that freezes the outcome, before the Items are written. Each Item's id is derived from the request id and the Item's role (request, decision, answer, disposition, disposition-status, ending, or invalidation), so a publication is identified exactly. Restart completes an incomplete publication on its named Turn, after scheduler fencing and before any command is admitted, by writing only the missing Items of that already-decided outcome, which Core admits as completion of an already-decided publication; it never publishes the outcome elsewhere. A later Turn that delivers the same outcome, after a refusal proved before delivery, carries it as structured input that references those Items, and writes none. The Items, written as input before any agent output:
- an `approval-decision` Item for a resolved approval, with its actor, decision, `decidedAt`, and causation to the request Item;
- a `user-input-response` Item for an answer, with its actor, answer map, `answeredAt`, and causation to the request Item;
- for every granted approval that governs an agent's captured call, its disposition: a `tool-call` Item authored by Core when the call was claimed, with `approved-executed`, `execution-error`, or `outcome-unknown` and a bounded, redacted result summary where one exists, or a `status` Item stating that the call was not executed and why, for `denied-not-executed`;
- a `status` Item for an ended request, whose summary states the reason and whose causation is the request Item.

`decidedAt` and `answeredAt` are required on those Items. No Item is ever back-filled onto the raising Turn.

**Discord group publication fallback.** The Core producer prepares the closed `channel.publish` governed intent on the existing Pending Request: `originId`, `botUserId`, `guildId`, `channelId`, `audienceRef`, `authorityRevisionRefs`, `influenceDigest`, `renderedBodyRef`, and `actionDigest`. The digest binds the exact rendered answer, citations, authority references, destination and mention/embed suppression. This intent is App-only. The card retains no copy of the answer. Approval remains unavailable until the App can resolve and verify the exact current dispatch from its retained body owner; a truncated summary never serves as the preview. A changed answer, authority revision or destination needs a fresh intent. Oversize E9 evidence is not clipped. A human decision does not send, establish a delivery claim, or prove acknowledgement. The writer remains disconnected from production until exact App approval and the native single-claim release are wired. Existing intents and DM requests retain their previous meaning.

A person's grant is delivered as a decision only: its Core-local Turn writes the `approval-decision` Item. The effect and result of the person's later governed command are published by that command's owner and never by redelivering the request. A `denied-not-executed` that an invalidating event records later for a command-intent grant, regardless of requester, is a separate fact, published once on its own Core-local invalidation Turn that the record names separately. That publication is admitted by the invalidating command when the Thread is idle, at the Thread's next terminal barrier when a Turn is running, or at boot after scheduler fencing when no non-terminal Turn remains; its admission does not depend on the decision being undelivered. It has the same three phases as any publication: while it waits there is no invalidation Turn and no invalidation Item; a named invalidation Turn with its Item missing is an in-progress publication; and a completed one has exactly one matching invalidation `status` Item on that Turn. Its Item id is derived from the request id and the invalidation role, and the same id, content, Thread-lineage, and restart-completion checks apply to it independently of the decision's publication, so a named incomplete invalidation publication is completed before ordinary command admission. Publishing the invalidation never moves or republishes the decision and does not itself change the decision's delivery state; archive closeout may independently change an undelivered decision to `closed-out`.

Outcome of delivery:
- The executor's proof sets `delivered` and clears any held result.
- Return the frozen outcomes to `undelivered` only on proof that the original delivery was refused before any effect. Preserve the original publication Turn. After possible contact, missing processing proof keeps the original delivery unknown and inspectable.
- When that proof is unknown, as when Worker processing or the Assistant's input acceptance cannot be established, the outcomes are set to `delivery-unknown`. They are never resubmitted automatically; the Turn follows ordinary recovery, and a later user message does not re-deliver them.

For Worker delivery, keep the complete, immutable frozen outcome batch with the Workspace Turn. Its order and digests make recovery resolve the original bytes after restart. Open the [kernel input obligation](20261019-durable_execution_and_control_store.md#retained-kernel-step-carriage) when delivery is selected. A transport ACK, repeated text or the Turn's later response cannot prove per-input processing. Missing evidence after possible contact stays unknown, with no automatic delivery to a successor. Release and restage only after definite refusal before effect or through governed resolution. The original publication Turn and request identity stay fixed.

### Closeout

An outcome is closed out rather than delivered when no requester can receive it: its Thread is archived, or its requesting Agent is removed from the Thread or loses its authority. Closeout never takes an outcome that is `frozen`, `delivered`, `delivery-unknown`, or already `closed-out`: a frozen outcome stays with its delivering Turn, whose proof decides it. Closeout Items, like delivered Items, are never written onto the Turn that raised the request or onto another run's Turn; they go on a Core-local service Turn with trigger `system-input` that runs no agent, needs no scheduler capacity, has no input bound, and completes in the command that writes it.

Archive closes out inside the archive command, in this order:
1. **Refusals.** Archive fails before any write with `409 request_executing` while the Thread holds a claimed, unfinished execution, and with `409 thread_busy` while the Thread has a non-terminal Turn and archive would end a pending request, select an outcome, including one frozen into that Turn, or publish an outstanding command-intent-grant invalidation, regardless of requester, even one recorded by an earlier command for a decision already delivered. The caller retries after the execution finishes, or after the Turn ends or is interrupted. Archive of a busy Thread with nothing to close out is not refused.
2. **Selection.** The pending requests the archive ends, the command-intent grants it turns into `denied-not-executed`, and every other final outcome of the Thread that is `undelivered`. Any already-recorded command-intent-grant invalidation, regardless of requester, whose status publication is outstanding is selected independently of the decision's delivery state.
3. **Publication.** A selected outcome that already has a publication Turn, because an earlier delivery attempt was refused, gets no new Item. Every other selected outcome gets its Items, as Deliver lists them, on one Core-local closeout Turn. For a command-intent grant turned into `denied-not-executed` by this archive, or a selected outstanding invalidation, Core writes the invalidation `status` Item on that closeout Turn; that Turn serves as the invalidation Turn defined in Deliver.
4. **Result.** Only selected original outcomes become `closed-out`. Publishing a separate invalidation leaves the decision's delivery state unchanged, so a decision already delivered remains `delivered`. All of this is written before the Thread's archived status, so no Turn is ever admitted to an archived Thread.

Loss of the requesting Agent's authority closes out that requester's final outcomes that are `undelivered` in the same way: in the command that detects the loss when the Thread has no non-terminal Turn, and otherwise at that Turn's terminal barrier, where admission finds that the requester can no longer execute and admits the Core-local closeout Turn instead of a delivering Turn. More than 16 outcomes waiting at archive are all published on that one closeout Turn. The delivery bound of 16 does not cap archive closeout.

A closed-out outcome is never delivered later, even when an archived Thread is restored, and an ended request is never reopened. Deleting a Workspace deletes its Threads' requests with their history under the deletion owner and writes no Item.

### Blocking And Presentation

A `pending` request is blocking when its raising Turn is terminal and no later Turn has started on its Thread. Blocking is computed from those facts, never stored, and changes presentation only. Action Center shows every `pending` request as decidable until it is resolved or ended, with its age, the number of Turns since it was raised, and whether it is blocking. A request remains decidable after its raising Turn completes.

### Conflict, Missing, Stale, Restart, And Dependency Failure

- **Stale facts.** Re-evaluation at execution time is the only defense against stale facts; staleness is shown to the approver, never enforced by a clock.
- **Dependency failure.** A dependency refusal before claim records `denied-not-executed`. A failed Main submission check after claim records `execution-error` without contact or usage. A failure after contact records `execution-error` or `outcome-unknown`. None is retried.
- **Restart.** Restart reads every state from this record, validated as below. It never denies, ends, or re-pauses a request because its raising Turn ended, never reopens a terminal Turn, never re-executes a claimed call, completes an incomplete publication only on its named publication or invalidation Turn, and admits a waiting command-intent-grant invalidation publication, regardless of requester, on a Core-local Turn once no non-terminal Turn remains.
- **Partial writes.** A partial write that leaves a request Item without a record, or a record without its Item, is `recovery_required` and inspect-only; no action is offered and nothing is synthesized.
- **Cross-domain truth.** Core storage and the upstream system are separate effect domains. No cross-domain atomicity is claimed, and an unknown effect stays unknown.

### Canonical Load Validation

The record is authoritative for request state, claim, disposition, and delivery; Items are its communication projection and never a source of authority. Command admission and canonical load check the same predicates for each record:
- **Lineage.** The request Item exists on the raising Turn, whose Thread and Workspace are the record's, and the Item's kind and request id match the record.
- **Parties.** The requester and responsible user match the request Item. A Policy-backed captured Worker approval retains the canonical agent's responsible human in the request and its captured authorization context; a later Task Turn's actual triggering administrator can be different. Canonical load checks the exact raising Worker and Session and captured context without requiring that trigger to be the agent's accountable human. Current response admission still checks the exact retained Policy source and subject before claim. Resolution admission permits the responsible user or a currently usable administrator credential under the administrator eligibility rule in `docs/core/policy.md` and records the actual deciding actor. For a retained completed policy grant, the accepted policy actor remains the recorded actor. This is retained-read validation, not authority to produce a new policy-grant decision. Canonical load preserves that recorded actor and validates its identity, lineage, legal state, and agreement with whatever retained command or audit evidence exists. Contradictory evidence fails closed. Receipt expiry or later credential revocation does not invalidate a completed decision and does not authorize command replay. The recorded actor is never rewritten to the responsible user.
- **One winner.** The record holds at most one resolution and at most one ending, and where the receipt of the command that resolved or ended the request is still retained, it matches the record; an expired receipt is not a conflict.
- **Publication phase.** An outcome with no publication Turn has no outcome Items, as when it is resolved and waits behind a busy Turn. An outcome whose publication Turn is named and whose Items are incomplete is an in-progress publication, which restart completes as Deliver defines; the Items present match it by id and content. A completed publication has exactly the outcome's Items, once, on that Turn, matching its resolution, disposition, or ending; a later delivery attempt's input references them and adds none. A command-intent grant invalidated after its decision, whether the requester is a person or the Coordinator, applies the same three phases to its separate invalidation publication: no invalidation Turn and no invalidation Item while it waits, a named invalidation Turn with its Item missing as an in-progress publication, and exactly one matching invalidation `status` Item on that Turn once complete.
- **Legal combinations.** `pending` has no resolution, ending, disposition, or claim other than `unclaimed`, and its delivery is `undelivered`. A denial or answer has claim `unclaimed`. An agent's captured-call grant has claim `claimed` or `finished`, or claim `unclaimed` with `denied-not-executed`. A command-intent grant, whether the requester is a person or the Coordinator, has claim `unclaimed` with no disposition while it waits for its owner, claim `unclaimed` with `denied-not-executed` after an invalidation, or claim `claimed` or `finished`. `finished` has one of the three post-claim dispositions. An ended request has no resolution and claim `unclaimed`. A request that is not ready has delivery `undelivered`.
- **Delivery association.** A `frozen`, `delivered`, or `delivery-unknown` record names a Turn on the same Thread that was admitted after the outcome was ready and whose executor is the requester. A published outcome names its publication Turn on the same Thread. A `closed-out` record names its publication Turn.

A record that fails a predicate, such as missing request lineage, conflicting Item content, or an outcome Item on a Turn the record does not name, is inspect-only and returns `recovery_required` to every command on it. Load never picks a winner, never reconstructs a resolution, grant, or claim from Items, and never repairs the record; the rest of the Thread stays usable. A `claimed` record without a disposition is the restart case above and is not a validation failure.

This version starts from a new data root and reads no data that an earlier version wrote, as [the engineer decided](../decisions/20260930-earlier_version_data_not_carried.md). ## External Attention And Discord Responses

### Authority And Scope

External attention is a delivery projection of an approval request, user-input request or durable security notice. Core retains one source reference per exact source and responsible recipient. Delivery records own only transport state. They never copy the request lifecycle or decide an outcome. Server control storage owns account bindings, inbound deduplication, attention references, and delivery attempts. Ordinary portable Workspace import is removed. Portable export does not carry these deployment-local account or transport authorities.

Discord is the first adapter. Its first direct-response allowlist is approval denials and answers to non-secret user-input requests. Approval grants return to the App, which owns their additional confirmation and irreversible-effect disclosure. All other interactions link to the App. A configured adapter requires a trusted public HTTPS App origin. Approval grant responses include an exact request link only when current source access permits it; otherwise they include the App home link. Email carries only digest or attention links. No adapter's implementation proves acceptance of another adapter.

All first-release Discord interactions occur in a private direct message to the bound account. Shared channels cannot receive request content or submit decisions. Current source access and destination audience admission precede every disclosure and send. Attention messages contain an App link, with no request arguments or protected summary. A link still requires App authentication and current source access.

### Security Notices And Recipient Copies

A security notice is a durable source independent of its request. Only an answer whose recorded actor is its recipient acknowledges that notice. Another administrator's answer or withdrawal MUST NOT end it; common answer and withdrawal authority is unchanged. The trigger raises at most one open `renotice` request per item and recipient when needed. Other recipients' copies stay open after triage; Core adds status Items naming the decider and outcome.

Every channel delivery, inspection and answer interaction for an `automation` request MUST return fixed deadline-and-App-link text only. It MUST issue no disclosure token, expose no report content and accept no channel answer. [Runtime Security](20261109-runtime_security.md) E4 and E6 own the notice drain, reminders and per-revision triage.

### Account Binding

A currently authenticated Core user starts a one-use, expiring pairing challenge. Only the authenticated Web pairing flow receives its plaintext. The CLI excludes pairing with this owning reason; its access-token sink must not store a channel challenge. MCP also excludes this one-time-secret result. Core stores only its digest. A verified Discord interaction consumes that challenge and binds the proven Discord account to that user. A challenge cannot replace another user's active binding. Revoke ends the binding and pending pairing challenges, including when the deployment removes Discord configuration. Rebinding never restores prior response authority or replays prior input.

The channel resolves a currently active ordinary Core actor for each input. It never inherits an administrator credential from pairing. The existing response owner checks responsible user, Workspace membership, Thread audience, exact request lineage, and current execution authority at response time.

### Delivery Lifecycle

An attention reference starts queued. A delivery attempt is recorded as sending before transport contact. A positive transport acknowledgement records sent, which proves neither reading nor a Core decision. A definite no-send refusal records failed-no-send. An ambiguous exception, lost acknowledgement, or interrupted sending attempt records delivery-unknown. An unsupported core value or contradictory record fails closed.

The first attempt fixes its channel. An unknown or sent delivery cannot be sent again through another channel or an automatic retry. A user may explicitly retry failed-no-send through the same channel after fresh authority and audience checks. A transport dependency failure before contact remains a definite no-send failure. Missing source, disabled actor, revoked binding or lost access refuses sending. An ended request refuses request-sourced sending. A security notice remains eligible while outstanding, independently of the linked request's state, under the same recipient, audience and channel-account checks. Notification creation and failure never block the request's Core lifecycle.

### Exact Responses And Recovery

Core verifies the Discord request signature, application identity, timestamp freshness, and private destination before reading account authority. It records the authenticated inbound event identity and exact input digest before dispatch. An identical duplicate returns a bounded acknowledgement of its retained state without dispatch. Duplicate inspection requires a fresh inspection before disclosure; receipts retain no effect or question text. A changed payload under that identity conflicts. An unfinished dispatch remains response-unknown after restart and is never automatically dispatched again. The Core request owner is the inspection authority when the channel result is unknown.

The inbound receipt retains the external actor from the signed envelope. Before native response invocation, it also retains the current admitted Core actor, binding revision, operation and exact Workspace, Thread, Pending Request and raising Turn references. Its existing native request identity joins that response; no second receipt family is created. These facts identify the actual responder, independently of the requester, responsible user or trigger actor. Required origin retention must succeed before invocation. Input rejected before native invocation claims no native acceptance. These origin facts prove neither native acceptance nor a Pending Request outcome. Duplicate input and restart do not rewrite origin or infer missing historical attribution from current bindings.

A private inspection discloses the complete exact approval effect and its digest before direct denial admission. Core binds the disclosure to the account, binding, and exact request. If the complete effect cannot be disclosed within the adapter limit, the user must respond in the App. A later response acknowledges that exact disclosure and rechecks current effect identity. A stale disclosure cannot retarget another request or effect. Secret questions, unavailable detail, unsupported kinds, and changed or terminal requests return a link or typed refusal without guessing a decision.

The channel invokes the existing approval or answer command with one stable command identity for the authenticated event. It preserves the actual actor and owner's result. Its acknowledgement says accepted only when that owner returns acceptance. A missing result stays unknown even when transport response publication fails. The existing Pending Request owner alone determines whether an effect was claimed, executed, denied, or unknown.

### Observable Acceptance

- A pairing challenge cannot bind twice, bind after expiry, or transfer another user's account.
- After an account transition, Web shows only the current actor's binding and delivery history, including cached data and pending query results.
- When Discord is configured and the user is paired, current notification cards show the exact private inspection command. Rendering the command makes no send or response call.
- Invalid signatures, shared-channel input, disabled actors, revoked bindings, changed duplicate input, and stale disclosures cause no command dispatch.
- Duplicate input and restart after incomplete dispatch cause no second dispatch or inferred decision.
- A response retains signed external identity and admitted native origin before dispatch; origin retention failure causes no dispatch.
- Duplicate input, restart, revocation and rebinding preserve response origin. Historical receipts keep unknown attribution.
- A response after membership or audience revocation fails under the current owner, even if pairing and disclosure succeeded earlier.
- Sending records the attempt before contact. A missing acknowledgement remains unknown after restart and cannot trigger automatic resend.
- An explicit retry after definite no-send failure repeats current source, recipient, and binding checks.
- Notification failures leave the exact Pending Request and any recorded Core outcome unchanged.
