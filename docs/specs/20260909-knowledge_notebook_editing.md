# Knowledge Notebook Editing And Publication

## Owns

The single fixed-base editing and publication contract for an owner-scoped OKF notebook: retained Git content revisions, bounded Knowledge Manager file editing, final-tree validation, exact authority and conflict checks, multi-page publication, history/diff/restore, and their publication command projections. This contract replaces the former single-page generated-change restriction and mandatory per-edit human Review for ordinary explicitly delegated maintenance.

## Does Not Own

Knowledge Core owns meaning and authority; S60 owns OKF profile and source governance; S61 owns parsing, storage encodings, retrieval and source records; the storage layout owns physical roots. The Knowledge Manager and shared internal runtime own invocations. Identity, Policy, Human Attention, command receipts, Audit, S39 delivery and backup retain their existing responsibilities. This is neither another Knowledge engine nor a persistent editing session, workflow runner, Git hosting service, general shell or real-time collaborative editor. Multi-modal extraction remains with existing Source/Artifact capability owners.

## Summary

One scoped notebook editor and publisher supports joint human/Agent maintenance, retained diff/history and current authorization. The implementation uses Git for content revisions and a bounded virtual filesystem for Agent edits; ordinary delegated edits and exact required human decisions share this owner.

## Decision

User Memory and Workspace/Server Knowledge are one jointly maintained notebook model with distinct ownership and source restrictions. User pages emphasize preference, background and intent; professional notebooks emphasize domain knowledge, working context and reusable findings. Retrieval indexes, summaries, embeddings and task-time context are projections, not separate knowledge authorities. The initial path remains text-first OKF with source/attachment references; no mandatory vector database or universal RAG framework is added.

An authorized user may delegate ordinary notebook maintenance. Such generated edits may publish after current authority and structural validation without a synthetic human Review. A model cannot grant itself that delegation, weaken its policy or attest that its own claims are true. Required human decisions remain for designated critical content, scope/authority changes and forgetting or destructive actions defined below. Explicit human editing uses the same data-preserving publisher.

## Scope And Maintenance Authorization

One notebook is addressed by the existing `ownerScope`: User, Workspace or current Server. No additional notebook catalog or notebook ID is needed in this slice. The initial authored `knowledgeMaintenance` setting is `{enabled:boolean,reviewRequiredPageIds:readonly string[]}` on the existing User, Workspace or Server settings owner, defaults to disabled and an empty list, and is written only by the current user for User scope, active Workspace members under current configuration Policy for Workspace scope, or deployment administrators for Server scope. Disabling it takes effect before the next publication. A one-off explicit user request may authorize one ordinary maintenance invocation; its trusted command admission records that bounded authority without changing settings. Enabling maintenance does not enable automatic source capture or a scheduler.

Background personal capture retains its separately opted-in source-intake boundary. Workspace/Server maintenance is explicitly invoked initially. Each invocation carries the requesting/responsible user's current identity; membership, source access and disclosure are rechecked before reads, proposal/review display and publication. A shared notebook must not receive information disclosable only to its requesting member. Server administration never grants access to another user's Memory. No model argument selects an actor, local root, authorization mode or approval identifier.

`reviewRequiredPageIds` names exact page IDs; deleting or changing the status of one is still a change to that protected page. A change intersecting that set uses the existing exact human Proposal/Review path. The set is outside editable notebook content, and a page's model-authored metadata cannot remove it. Existing authored required-assessment policies remain effective. Current Policy may impose a stricter exact confirmation; default ordinary text updates, new pages, reversible archival and multi-page organization need no extra per-edit gate once admitted. Changing source restrictions or scope is not an ordinary content edit.

## Content, Revisions And History

The storage owner assigns a bare `notebook.git` inside each existing notebook root. Its `refs/heads/published` identifies the sole current content tree. The tree contains only the OKF bundle under `pages/`; it contains no credentials, source originals, schema/configuration, Proposal/Review store, indexes, hooks, executable assets or Git submodules. The old `pages/` directory becomes an optional rebuildable materialization/export with a service-owned commit stamp outside its bundle. Build it completely before publishing its stamp; missing/mismatched stamp makes it unavailable. It is never a second live reader or writer of content authority. Product reads pin a commit at request start and read that immutable tree; checkout progress cannot expose a mixed revision.

For a fresh authorized User/Workspace/Server scope, the existing scope/store initialization creates the bare repository and a root commit containing the valid empty OKF bundle and versioned root index. It durably establishes `refs/heads/published` before exposing that notebook. This initial commit has no parent and records the existing creation/bootstrap command's trusted attribution. Failure leaves initialization unsuccessful under that owner's existing boundary; it never exposes a partly initialized notebook. An already initialized notebook with a missing ref/object is `recovery_required`, never silently recreated as empty. No separate initialization endpoint, lifecycle record or lazy recovery mechanism is added.

A revision is the full Git commit object ID, treated as opaque. Page identity remains its scope-qualified bundle-relative path without `.md`, with S61's existing safe grammar and reserved names. Exact content identity is `{ownerScope,notebookRevision,pageId,contentDigest}`; the existing SHA-256 digest covers exact page bytes. Git already supplies version history, so remove the unimplemented `openkit_revision` page counter and registered Source copies made only to retain an old page version. Original evidence Sources remain immutable and separately owned. Page revisions are not independent authorities. API projections that need `revision` use the pinned notebook commit, not another sequence number.

Each commit has one parent: the exact edited base, except the initial creation/import/migration commit. Git-native author/committer metadata records the responsible actor and time; its entire message is one service-serialized canonical JSON object `{summary,changeRequest:{requestId,inputDigest},producer,authority,sourceReferences}`. `summary` is bounded untrusted display text (at most 4 KiB UTF-8), JSON-escaped as a string, never concatenated with metadata or interpreted as instructions. Readers strictly parse the complete object with duplicate/unknown authority-key rejection; absent or malformed metadata returns `recovery_required`, never inferred authority. `producer` distinguishes human/Agent authorship with existing model/invocation lineage. Direct/delegated `authority` contains the trusted instruction reference or exact resolved maintenance setting value and its SHA-256 digest; record the same facts in Audit admission. No mutable setting pointer or nonexistent version primitive supplies evidence. Changed paths and old/new bytes derive from Git. These fields prove historical admission facts, never reusable grants.

A required-review candidate instead fixes `authority:{kind:proposal,proposalId}` before its commit is created; the Proposal ID is derived from the draft request independently of candidate bytes. This marker is not approval. The existing terminal Review later names that exact candidate commit, and publication verifies it without rewriting the candidate or injecting a future Review ID into it. The draft `changeRequest` is distinct from the deciding command's request ID; Audit and receipt bind the latter to the exact Proposal/Review/candidate. Published provenance resolves the existing accepted Review; missing or contradictory decision evidence fails closed. Imported history carries only provenance and supplies no live permission.

Commits used as saved review candidates are retained by the existing Proposal owner through the service-owned `refs/proposals/<proposalId>` ref defined by S61. Keep that ref while its Proposal/Review evidence is retained, including rejected candidates; terminal Review does not silently unpin historical evidence. Only the published ref determines current pages; a reachable candidate object alone is not active content. Service-owned Git configuration disables reflogs, automatic maintenance/collection, hooks, signing callbacks, external diff/textconv/filter drivers, remotes and submodule/network operations. The Agent never sees `.git`, chooses Git arguments, changes the published ref or edits commit metadata.

## One Editing Workspace

`knowledge.notebook_workspace.update` is a Knowledge Manager-only Tool taking `{script:string}`. Trusted invocation assembly binds one notebook, its fixed base commit, source audience and an in-memory just-bash filesystem populated from admitted files of that immutable revision. The same temporary filesystem persists across Tool calls in that bounded invocation. A separate read-only `/sources` tree may contain selected already-authorized Source material; `/notebook` contains editable OKF pages and reserved index/log files. Paths are virtual. Neither filesystem mounts live DATA_ROOT, another scope, mutable source originals, schema/settings, credentials or host Git metadata.

The editing result is `{exitCode,stdout,stderr,truncated}` with the combined output cap below; nonzero exit is visible and leaves only temporary edits, never implies publication. Invalid input, denied scope, exhausted bounds or runtime cancellation return the existing typed Tool failure. Scripts are at most 64 KiB UTF-8; no raw exception, host path or restricted source is copied into errors.

Use just-bash's built-in file/text/YAML/JSON commands and pipelines; no host shell/process spawning, network/fetch, Python, JS runtime, native SQLite or model-supplied custom commands. Disable symlinks, hardlinks and device/special-file creation for this notebook profile. The host supplies a fixed code-owned command set; unsupported commands return a bounded error. This is interpreted manipulation of admitted data, not a Worker working directory or permission to load plugins. A direct OverlayFs over live pages is insufficient because reads could change during the run; use an immutable materialization or in-memory snapshot.

Initial named bounds are 32 MiB admitted text per workspace, 2 MiB per file, 256 changed files and 64 KiB returned output per Tool call. Use the library's hardened execution limits, with each call's deadline no later than the remaining shared-runtime deadline; no independent unbounded retry. Bounds are implementation constants exposed in Tool metadata and errors, not a new configuration surface. Reject an oversized workspace before execution and direct the user to a narrower explicitly selected editing request; omitted files remain immutable members of the base tree and final validation still resolves links against the complete resulting tree. A request may select exact page IDs and selected Source IDs, never host paths. All writes must stay within that admitted editable set plus new pages under the notebook root.

Read/search/edit tools may observe draft or archived pages only when the user explicitly includes them in the editing or historical-inspection request; ordinary context retrieval stays active-only. Semantic merging, splitting and formatting are Agent work using these primitives. Temporary inconsistencies inside the editing workspace are allowed. `rm` removes a draft-workspace file only; it cannot erase retained history or bypass publication checks. Cancellation discards unpublished volatile edits unless an explicit existing Proposal save already retained a candidate; the UI must distinguish an unsaved edit from a published revision.

## Final-Tree Validation And Multi-Page Operations

`knowledge.notebook.update` takes `{summary:string}` and submits the current edit workspace; it accepts no actor, base, target scope or authorization fields from the model. The service computes one exact candidate tree and runs the existing OKF parser/profile/schema and source checks over all changed files plus affected references. User editor submissions take `{baseRevision,changes:[{path,content:string|null}],summary}` through the same publisher. `null` removes a path from the candidate; there is no separate merge/split/rename executor. Unchanged files retain their bytes and existing metadata.

Validate path grammar and require `openkit_entry_id`, when present, to equal the path-derived concept ID; no metadata alias can override identity. Validate case collisions, regular-file type, file/output bounds, YAML structure, required fields, exact scope, reserved index/log structure, status projection and current source disclosure. Preserve unknown OKF metadata and body bytes except where explicitly edited. Normalize only service-owned attribution fields before computing final digests. The ordinary Agent cannot edit schema, maintenance policy, assessment requirements or source permissions. A valid rough note may remain draft; malformed content is preserved only in an explicitly saved non-active proposal/draft artifact, never by replacing valid active content.

Concept links and local page/source references resolve against the entire resulting tree, not sequential intermediate writes. Published paths are stable identifiers in this slice: rename/move is not a notebook operation. Reorganize using titles, index links, new pages and archived/superseded originals; this preserves references and protected-page identity without a redirect mechanism. Agents may freely rearrange never-published scratch paths before publication. A confirmed deletion requires affected live Markdown links to be repaired in the same candidate or returns bounded diagnostics identifying admitted and outside-selection referrers. The caller can start a new broader bounded invocation, or use archive when the full repair exceeds the workspace bound. Every repaired page is an actual content edit: its prior content-bound Review/assessment is invalidated, protected-page rules apply, and confirmation displays the complete affected diff and attribution changes. No silent mechanical-repair exemption applies; the explicit forget path instead resolves affected links as redacted/unavailable from the existing suppression record, with no replacement page or prose tombstone, so referential cleanup cannot delay suppression. Links to intentionally retained archived/superseded pages remain resolvable but do not activate them. Historical citations continue to identify the original commit/path/digest and are not rewritten. Sources supporting substantive claims remain attributable; another generated page or repetition is not independent factual corroboration.

Ordinary maintenance uses archive/supersede for previously published pages. Removing a published page from the current tree or restoring a revision that removes one requires an exact human confirmation showing removed content/paths and retained history. A merge leaves its former pages as archived/superseded with links to the merged page, avoiding destructive deletion while retaining discoverability. This is one publication check on the final diff, not a merge workflow. Fresh uncommitted scratch files may be removed freely. An explicit forget command has stronger retrieval suppression semantics below.

## Publication, Failure And Restart

Prepare candidate objects without changing `published`. Within the existing scope mutation fence, recheck current scope/source authority, maintenance setting or exact human decision, current schema and assessment requirements, and equality of `published` with the fixed base. Human editors and Agent publishers share this fence. The fence covers only final validation/admission/publication, never the model run. Missing required approval saves one existing Proposal with exact base/candidate/input/source evidence and returns `review_required`; it does not publish or let a model answer the Review. Changed bytes/base or requirements need a new candidate/decision.

Persist the existing Audit admission evidence before updating the ref; inability to retain required evidence prevents publication. Publish by compare-and-set of the existing ref from exact base to prepared candidate, after all Git objects are durable under the supported filesystem/Git durability configuration. Ref update is the one content publication decision. Crash durability requires flushing objects and ref/directory updates; an ordinary unflushed Git command is not a durability proof. This is not atomic with SQLite Audit or command receipts. Keep the existing post-publication result/Audit/receipt sequence and return success only with its exact evidence. Derived index failure cannot roll back a published content revision or make a retry publish again.

If the base changed, return `409 conflict` with the current revision and retained candidate/diff when saved; perform no ref update, automatic merge, overwrite or model rerun. Missing/corrupt objects or contradictory owner/commit evidence return `recovery_required`, never an empty replacement notebook. Failure before ref publication leaves the old revision active. If publication occurred but its completed command evidence is missing, return `recovery_required` and expose the existing commit through authorized inspection, not fabricated success or automatic repair. A completed identical request replays its existing receipt and named commit; changed input under the same request ID returns `idempotency_key_conflict`. Existing request admission must serialize duplicate requests before preparing effects; commit metadata allows inspection of a prior publication and is not a second receipt.

Restart reads the published ref and immutable tree plus existing command/Proposal/Review/Audit owners. It does not resume an editing session, rerun dreaming or infer that an unpublished object became active. Published history, retained proposal candidates and backup roots must be protected from garbage collection. Git is local and shares the existing single-process data-root deployment constraint; no distributed Git writer or remote synchronization is introduced.

## Retrieval, Notebook UI And Restoration

S61 owns indexing, state-filtered search and deterministic ranking for these notebook revisions. The notebook requires active-only default retrieval and explicit authorized inspection of other supported states through that existing owner. Publication provenance replaces the former requirement to reconstruct a human Proposal/Review tuple for every Agent-edited page. Before returning content, recheck exact scope, source permissions, suppression, sensitivity, freshness and applicable policy at the pinned revision. A valid active page can carry unresolved uncertainty explicitly; the retrieval owner preserves its existing conflict exclusions and diagnostics and must not present uncertainty as settled truth. `review_state: delegated` records an ordinary authorized Agent edit; it does not mean human-reviewed or AI-proven. Exact human acceptance remains `accepted`, direct human editing remains `user-authored`; an edit cannot inherit old content-bound acceptance or assessment.

The default state filter admits only active pages. Explicit `states` selection or exact historical reads may include draft, archived or superseded material under current permission; pins cannot bypass the default filter. S61 owns commit-tagged index validation, mismatch failures and rebuild; this notebook consumes that owner without adding another index, ranker or repair path. Summaries and navigation are derived/read aids over admitted content, not trusted instructions or proof. Multimodal Source representations use exact source/digest lineage and current disclosure through the same retrieval boundary; adding a media reader does not change page version authority.

The Notebook UI provides page editing, state selection, source links, revision history, changed-file list and text diff with responsible human/Agent attribution. History defaults to the selected notebook and current permissions. It never exposes raw repository paths, Git configuration, unpublished candidates belonging to an unauthorized audience or data denied by current source restrictions. `index.md` and `log.md` may be edited with other pages, but the user-visible change history comes from Git and does not rely on an Agent's prose log.

Restore computes a candidate diff from selected historical paths into the current base and publishes it through the same validation and authority checks as any edit. It adds a new commit, never rewinds published history or undoes external effects. No generic cherry-pick/rebase/reset API is exposed. Missing historical bytes, revoked source access or now-invalid schema produces an explicit unavailable/conflict result, not a lossy restore.

## Forgetting And Portability

Archive keeps content and history. Explicit forget retains the scoped learning owner's exact human confirmation, suppression of the same source versions and current-authority rechecks. It removes the page from active content through one new revision and immediately makes affected historical page bodies, diffs, summaries and source-derived reads unavailable to normal retrieval and history endpoints, including cached results. Independently owned content is not deleted. Prior Git objects (including retained rejected candidates and unreachable prepared objects), Source/evidence/backup bytes remain under their existing retention authority and are explicitly disclosed; ordinary forget is not physical erasure. Reflogs are disabled; no automatic history rewrite, garbage collection or promise of backup erasure is introduced. Collection is never evidence of physical erasure. A physical purge requires a separate explicit operator/data-retention action. Restore and import cannot resurrect suppressed content merely by replaying history.

Backup under the same owner includes the retained Git object graph/ref and existing source, schema, policy, suppression, Proposal/Review and command/evidence records; validate content and references before recovery. Ordinary OKF export emits selected authorized pages from one published commit and their supported resource closure, without Git internals. Optional history export uses only validated published reachable history, excludes unpublished candidates/reflogs/config/hooks/credentials, and checks the entire requested historical disclosure closure. If that closure is not disclosable, fail that history request rather than silently exporting it or pretending a truncated graph is complete.

Workspace clone/remint rewrites scope and source IDs using existing portability rules; changed bytes require new commits/digests and original commit identities remain import provenance only. Import does not activate maintenance, human decisions, credentials or old grants. It stages and validates before publication, preserves explicit historical attribution and source restrictions, and cannot bypass forgetting suppression. Sources and large binary attachments remain in their existing stores; Git history is not a substitute for off-disk backup.

## Current Implementation Projection

The existing Knowledge Store has direct file-backed Workspace pages, create-only reviewed proposals, deterministic retrieval and bounded create reversal. Git content authority, scoped virtual editing, multi-page publication and history APIs are Not Started. No just-bash dependency is installed by this documentation change; runtime confinement and crash durability still require implementation evidence.

## Implementation Cutover And Acceptance

Migrate under the existing offline scope writer/backup boundary: preserve exact current page/source/Proposal/Review bytes and hashes, validate owner/profile, construct an initial Git tree, verify every admitted page and create the published ref before switching all readers/writers/indexes together, including index rebuild and worker-context canonical-byte readers. No reader falls back to an unversioned materialized directory. Retain the original backup until explicit cleanup. Existing immutable command/review evidence stays historical; it cannot authorize a new candidate. Invalid legacy pages are retained as non-active migration material with diagnostics, never dropped. No dual writable page directory, compatibility alias, duplicate full-page revision archive or counter is retained. Scope/revision envelope and S39 consumers change together. The new contracts remain Not Started until that cutover and the following checks pass.

- An authorized Agent uses file tools to merge/split/edit several pages and publishes one validated revision; no artificial human Review is created for ordinary delegated changes.
- With maintenance disabled and no exact user instruction, no autonomous publication occurs; protected-page, destructive-removal or required-assessment failures retain a candidate and require the actual authorized decision.
- Two writers starting from one revision cannot silently overwrite each other. Readers see a complete old or new tree; history/diff proves the exact changed bytes and attribution.
- Invalid YAML, source disclosure, path escape, special files, unauthorized paths and dangling affected references cannot change published content. Guest execution cannot read host/config/credential/Git state or access network.
- Failure before/after ref publication and receipt completion has the exact outcomes above; restart never regenerates content or claims missing evidence. Disk-durability verification exercises the publication boundary, not just a Git API mock.
- Active-only default retrieval, explicit archived reads and current source revocation apply equally to human and delegated content. S39 still alone proves delivered worker bytes.
- History restore creates a new validated revision; forget blocks normal current/historical retrieval and resurrection while accurately reporting retained backups. Backup/import verifies the complete admitted content/history/source graph.
