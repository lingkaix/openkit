# Personal Memory And Scoped Knowledge Learning

## Owns

This specification owns the User/Workspace/Server projections of the existing Knowledge Store, personal Memory retrieval, explicit conversation-source intake, Knowledge Manager integration, scoped notebook editing and forgetting. Bounded consolidation and learning from recent authorized scope Threads run through Knowledge Manager maintenance in v0.1.0, with daily scheduling default off. Usage aging and candidate-specific AI assessment remain deferred until after v0.1.0. It extends the existing Knowledge Page, Source, Proposal, Review and maintenance records; it creates no separate Memory engine or generic learning framework.

## Does Not Own

It does not own Thread history, permission policy, model transport, a new Agent runtime, background scheduler, Skill versions, A/B experiment orchestration, multi-page transactions, formal proof, or autonomous promotion. `docs/specs/20260711-skill_catalog_versioning_pinning.md` continues to own procedural Skill candidates, exact version selection, comparisons and rollback.

## Summary

Memory is personally owned reusable understanding; Knowledge is Workspace- or Server-owned reusable understanding. They are different object kinds with different semantics and privacy boundaries. They reuse the OKF-backed page, source, review and Retrieval Kernel mechanisms, but Memory recall and Knowledge retrieval are separate invocations. Skill stores reusable procedures and optional supporting code under its own catalog. Knowledge Manager retrieves and synthesizes answers, integrates supplied information and organizes notebooks under current scope authority. Facts and preferences grant no authority. Consolidation and bounded learning use the maintenance contract below. AI assessment and usage aging remain deferred.

## Goals / Non-goals

Give Personal Assistant continuity across private conversations and authorized project contexts; let users state intent, supply information, inspect, approve, correct and forget saved material; preserve provenance and current source restrictions; reuse bounded work and existing governance. Exclude personality inferred as a privileged system prompt, unconditional history ingestion, a second vector database, a new Dreaming service, cross-scope copying by default, automatic Skill promotion, and a universal evaluator.

## Decision

The existing Knowledge model is extended to one `ownerScope`: `{ kind: user, userId }`, `{ kind: workspace, workspaceId }`, or `{ kind: server }` for the current deployment. Scope-qualified identity, not title or page id alone, identifies a page and every associated record. There is one implementation parameterized by a trusted resolved owner, not three engines or a globally searchable shared corpus.

User ownership is independent of Quick Chat or a project Workspace. Personal Memory remains private when the user joins, leaves or changes Workspaces. A project-derived fact keeps its source restriction; private ownership never grants permission to import it into another Workspace or keep using a revoked source. Workspace Knowledge serves authorized work in that Workspace. Server Knowledge initially serves deployment administration; publishing any subset for ordinary member use requires an explicit authorized promotion into that member's Workspace, not a blanket Server read grant.

## Contract / Expected Behavior

### Scope, storage and API projection

The storage layout owner assigns the following roots; this is its projection, not a second path authority. Reuse the existing notebook tree, OKF v0.2 envelope and governed record families under these trusted storage roots: `users/<userId>/memory/`, `workspaces/<workspaceId>/knowledge/`, and `server/knowledge/`. Each root contains `notebook.git/`, optional materialized `pages/`, `schema/`, `proposals/`, `reviews/` and the existing maintenance families. Source material remains a separately owned sibling family: `users/<userId>/sources/`, `workspaces/<workspaceId>/sources/`, or `server/sources/`. Rebuildable indexes live in the same ownership scope. No new SQLite database is required and no Workspace tree moves under a user.

The existing Knowledge Store owns scope resolution, OKF parsing, Sources and deterministic retrieval. Profile/schema v4 records exact owner scope without a page counter; page `revision` projects the pinned notebook Git commit, with SHA-256 of exact page bytes as content digest. `20260909-knowledge_notebook_editing.md` owns fixed-base editing, publication and retained history. The applicable schema lives at `schema/scope-schema.yaml`; content edits cannot change it or another scope's authority.

OKF pages keep a closed core and open extension front matter under the notebook owner. Only required core semantics receive strict validation. Users and agents may add extension fields; readers ignore unknown optional additions and preserve them during normal rewrites. Unknown required or authority-bearing semantics fail closed. No page-level origin or trust field is required. Existing commit `producer`, `authority` and `sourceReferences` record each change's origin; an origin note may be an optional extension.

App API, Core Client and the agent-facing interface reuse the existing page/source/proposal/review operations. Workspace routes retain their existing scope. User management uses the `memory.*` App operation family at `/api/app/operations/<operationId>` and resolves its owner from current authentication; no payload selects another User. Server Knowledge retains its separate deployment-administrator admission. These operation paths follow the shared App API projection, not an alternate CRUD service. The existing Workspace operation suffixes and strict payload validation apply without a second CRUD implementation. Exact route schemas are projections of these scoped operations, not permission to accept arbitrary filesystem roots or user ids.

Page/source/candidate reads, writes, exports and derived retrieval require current scope authority. User Memory read and mutation eligibility follows [Core Permissions](../core/permissions.md), while ownership remains with the original User. Ordinary users cannot read another user's Memory. Workspace Knowledge requires active membership and existing operation checks. Server Knowledge requires deployment administration. Restricted source evidence adds its own current read/disclosure conditions. The Notebook UI labels User pages Memory and Workspace/Server pages Knowledge, shows source and applicable scope, and offers saved entries and pending changes separately.

The envelope owner must register `openkit.knowledge-owner-scope.v1` and `openkit.knowledge-git-notebook.v1` before this extension becomes writable/importable. Emit them in `requiredFeatures` on scoped pages, governed mutation records and export manifests carrying these semantics. Unsupported readers reject before retrieval, mutation or import; an omitted capability cannot downgrade User ownership or discard a replacement base assertion.

### History, explicit saving and personalization

Private Thread history remains history; a transient prompt, provider cache or inferred preference is not a saved Memory. An explicit instruction such as "remember that I prefer concise Chinese reports" passes supplied information to Knowledge Manager for integration. An exact saved expression may be user-authored through the current owner. Users may also make simple direct edits. A model's expanded interpretation is generated content and requires the notebook owner's current delegation or exact proposal approval; the model cannot label it user-authored. A one-task exception does not silently rewrite a standing preference.

Personal Assistant receives separate bounded Memory and Knowledge overviews from their admitted OKF root indexes. Knowledge Manager keeps each index current. Personal Assistant asks Knowledge Manager for relevant active Memory and separately for admitted Knowledge, using its trusted User, query context and current output audience. Assembly receives labelled Memory and Knowledge sections with separate limits fixed before retrieval, each 1 through 20 with default 5; neither section consumes the other's budget or participates in a shared score-ranked list. Entering a Workspace does not read every notebook. Personal preference can influence a private reply across Workspaces, but cannot override the current instruction, policy, tool admission, target schema or required decision. Workers cannot read Memory, including when they act for its owner; administrative Memory inspection remains a separate currently authorized operation under Core Permissions. A selected preference may cross into shared Task/Goal work only through the explicit handoff/promotion contract.

The private project Thread's physical placement does not transfer its extracted Memory to the Workspace notebook. A user may explicitly publish selected understanding as Workspace Knowledge, using destination validation and disclosure checks plus a new destination-owned candidate. The same rule applies to Workspace-to-Server promotion; generalization, paraphrase or generated Skill packaging is not declassification.

### Deterministic retrieval and conflicts

Every query runs in exactly one trusted `(Server, Workspace, Actor, Thread/Turn)` context. A Thread, when present, belongs to that Workspace; a Turn requires that Thread. Direct User App calls may have no Thread or Turn and then publish no trace or trace reference. They retain the same source and access checks. A caller cannot omit existing query lineage. Missing Server, Workspace or Actor and contradictory context fail before source inventory. The Assistant's current User and role come from this context, never request-supplied user ids. Memory recall also requires that User's private Assistant Timeline in this Workspace; a role label or User credential cannot make a shared Thread eligible. Context derives eligible Workspace Knowledge, current Server Knowledge under its existing administrator admission, and current User Memory for the Assistant only. A request may narrow those sources but cannot add another owner. This replaces the private User-plus-Workspace union under [Query Context, Sources, References And Acts](../decisions/20261015-context_sources_references_query_acts.md).

Memory recall addresses only that User's Memory. A Knowledge retrieval invocation addresses one admitted Knowledge base, with the current Workspace as its default; an admitted Server Knowledge query is a separate invocation. The caller can narrow to one admitted source, not provide an arbitrary scope union. Keep source-labelled Knowledge results separate when assembly makes more than one invocation. Scores rank candidates only within their index; they are not comparable across Memory and Knowledge or across Knowledge indexes. Within one source, preserve pinned-first order, descending local score, then bytewise page id and revision. Existing state, conflict, freshness and disposition rules remain. Current source and audience admission precede even candidate metadata.

Pins, trace entries and citations use the [Core Protocol reference](../core/protocol.md#scope-qualified-object-references) `(scope id, object id)`. The page object id remains its existing stable bundle-relative path without `.md`; revision and digest identify the observed bytes separately. The scope identifies the logical notebook page collection, including its User/Workspace/Server owner, not a kernel eligibility partition. No pin widens the admitted source or changes its score. Same context, source revisions, inputs and budgets reproduce the same source-local selection.

Each query with a Thread or Turn publishes one immutable selection trace file under that querying owner, at the paths and atomic publication boundary defined by Knowledge Store. A threadless direct User App call publishes none. The Assistant trace belongs to its one private Timeline per `(User, Workspace)`; a Worker trace belongs to the Task/Goal Thread and contains no Memory selection. The trace stores references and non-content selection metadata, not copied source bodies, snippets, query text or matched terms. Its audience and retention follow that Thread/Turn. A read, ordinary export or direct record projection checks both the containing record and each reference against current access; revoked content and restricted identity metadata stay unavailable. There is no User/Workspace combined-trace ledger and no source notebook owns the act.

Future sharing uses explicit source-owner-authorized, revocable bindings into the querying Workspace, with grantor, source scope and destination audience checked at every query and read. Cross-server bindings use a server connector; optional publish/copy retains provenance and destination validation. This is direction only, consistent with personal Workspaces not being able to add members and with a future Workspace data-view `sources/` mount. No binding, mount, connector or cross-user Memory permission is introduced here; their exact contracts wait for their owners.

Current explicit instructions govern the current task; a personal preference may override a broader presentation default. Contradictory factual pages remain source-attributed conflicts and cannot be resolved merely by choosing User over Workspace or Server. Existing conflict/freshness filters apply before selection; unresolved content returns uncertainty or is excluded under the current retrieval policy. Protected-source revocation invalidates the corresponding candidate even if a personally owned snapshot remains stored.

### Conversation-source intake

Selected completed Assistant or human conversation Items are captured through the existing Knowledge Source registration owner before drafting. The source stores exact Item identities/digests, cutoff, originating Thread/Workspace/user attribution, source audience, capture time and restrictions with the captured bytes. The proposal cites the existing `source:<sourceId>@<digest>` form. This is conversation evidence, not worker-output evidence, and it MUST NOT fabricate an AgentSession, S39 Context Package or completed Worker Turn.

At capture, draft, apply and later retrieval, reauthorize the source and destination. Deferred assessment must apply the same checks when admitted. An inaccessible private source must not appear in another scope's candidate title, rationale, preview, index or evaluation prompt. If an ordinary raw conversation is deleted, separately and explicitly saved user-authored Memory follows its own retention choice; the UI explains that deleting a chat does not itself forget saved entries. Revocation of a protected source prevents derived reuse regardless of whether a historical snapshot remains stored for evidence.

### Knowledge Manager integration and organization

Internal agents ask Knowledge Manager for details and tell it supplied information with admitted Sources. Worker ask/tell addresses only the current Task's Workspace Knowledge; it cannot read personal Memory. Each query is a bounded per-request run with no shared context across audiences. Answers cite scope-qualified `page@revision` and `source@digest`, report uncertainty and show the observed revision time. Agents verify volatile facts against current Sources before action.

One Knowledge Manager maintenance Thread records each notebook scope's work and required approvals; it is not resident. Explicit requests and the admitted daily trigger start fresh bounded Turns with one writer. Users inspect work and approve required candidates there. Knowledge Manager integrates new information, updates pages, merges, splits or archives material, and keeps the bounded root index current. It preserves source restrictions and the distinction between evidence and interpretation. Users give intent, information and approval; simple direct edits remain available.

Knowledge Manager remains the existing Internal Core Role, limited to querying and managing the admitted notebook scope. It has its own usage accounting and work record through existing owners; requesting calls supply lineage. It receives no network Tools or other external-effect Tools. Ordinary Provider transport belongs to the shared runtime. Its operations are trusted at this stage and require no second-model review or confidence mark.

Knowledge Manager uses the existing fixed-base publisher. Current scope maintenance delegation permits ordinary publication; otherwise the exact candidate requires proposal approval. Neither capture permission nor supplied facts grant publication authority. Source registration remains explicit and uses its existing owner. Worker-output provenance retains the exact completed Worker Turn and delivery requirements; a tell does not invent them.

[Knowledge Manager](20260704-knowledge_manager_internal_agent_runtime.md) owns the role integration with shared execution, existing role-profile resolution and OpenKit summary-checkpoint compaction near the model threshold. Maintenance never uses the durable rolling context window. Failure and restart reconstruct from current authorized notebook content and existing Thread/Turn/Item history; no model run or virtual editing session is replayed.

### Notebook editing and required review

Human and Agent changes share `20260909-knowledge_notebook_editing.md`: one fixed base, temporary scoped editing filesystem, complete candidate validation and one Git publication. Ordinary explicitly delegated changes publish without per-edit human Review; designated critical content and sensitive effects use the existing exact Proposal/Review/confirmation owners. The model cannot change its maintenance authority or required-assessment policy. Publication records human/Agent attribution and source lineage; active status is neither truth proof nor human approval.

History retains exact prior bytes and diffs in Git, not registered Sources copied solely as page revisions. Restoration publishes a new current-base change under current permissions and schema. Multi-page merge/split/archive and reference repair are permitted through this same mechanism. Skill versioning remains with its catalog. Optional assessment remains evidence and cannot supply missing publication authority.

### Forgetting and deletion

User `forget` is a direct authorized operation over an exact page revision, distinct from deleting its source chat. Before application, the existing Item-backed confirmation gate displays the exact owner/page/revision/digest, content being removed, suppression effect and separately retained source/evidence/backup scope. Confirmation binds that payload and request identity; the model cannot confirm it. Apply rechecks current authority and the exact revision/digest, rejects stale targets, and returns the same inspected outcome on identical replay rather than deleting a later page. The notebook publisher owns Git publication and historical-read suppression; ordinary forget retains Git/evidence/backup bytes under disclosed retention rules and is not physical erasure. Mark the page unavailable before derived index cleanup, remove its content from active pages and derived summaries/caches, and prevent pending candidates based on the forgotten material from applying. Retain only minimal scope/id/last-revision/digest and source-fingerprint suppression metadata in the existing maintenance records; a forgotten page id remains reserved and an explicit later save creates a new page id at the current notebook base, never revives the forgotten identity; do not retain forgotten prose as a tombstone. Existing Proposal, Source and evidence bytes containing that material follow the owning deletion/redaction rules and must be excluded from future model retrieval immediately. Physical evidence retention and backup retention remain separately disclosed; no promise is made to erase an already published external copy.

Suppression rejects automatic re-extraction from the same source versions. It is not a semantic ban on every future similar sentence. Only an explicit user save or user removal of the suppression can re-admit that material; an index rebuild, restart, repeated observation or generated paraphrase cannot. New observations with different source identity follow current maintenance authority; they cannot grant themselves permission or silently remove suppression. Forgetting personally saved material does not delete independently owned Workspace/Server Knowledge or shared work.

### Procedures and Skills

If learning produces a reusable procedure, submit an existing SkillCandidate with exact base/candidate digests and permitted source/work evidence. Do not store executable behavior as a privileged Memory page or introduce OKF as a substitute Skill package format. Skill comparison, A/B trials and rollback use existing version pins and attributable work outcomes; experiment scheduling/statistical evaluation remain separately scoped. A better-looking score is evidence for a decision, never automatic promotion or a claim that the A/B platform is already implemented.

### Portability and deletion of an owner

An ordinary Workspace bundle contains Workspace Knowledge and shared admissible sources, not User Memory or Server Knowledge. The current user may separately export their Memory as OKF pages; import binds to that importing user, validates content and source restrictions, and leaves unavailable references inactive. Server Knowledge export/import is administrator-scoped. Raw private conversations, credentials, prior users' review authority and automatic capture settings are not silently imported with pages. The existing User `disabled` state immediately blocks Memory reads, extraction and publication and invalidates in-flight admission; retained pages, Sources, candidates and reviews remain owned by that user and are not transferred to administrators or Workspace members. No re-enable transition is introduced; if Identity later owns one, Memory admission must reconstruct current source permissions rather than replay old grants. User hard deletion and account-closure export are excluded until Identity owns those transitions; they are not invented by this feature. Unavailable storage fails without creating an empty replacement store. Deleting Server Knowledge requires current administration and never deletes Workspace or User material; Workspace deletion cannot delete independent personal preferences. Restricted project-derived material remains unusable when its source permission is lost.

## Current Implementation Projection

Workspace Knowledge supports registered Sources, fixed-base human notebook publication, source-linked Proposal and Review, bounded reversal and confirmed removal, current authorized pinned retrieval, and history/diff/restore through the common Git publisher. Its current Workspace clone initializes a fresh target Notebook from the admitted published tree; same-deployment backup retains Git history and separate authority records. Explicit personally authored User Memory saves, lists, reads and edits pages with no Sources or current self literal document Sources through the existing scoped notebook publisher. Its bounded history and diff apply current self, schema, sensitivity, suppression and Source-version admission; restore appends a new fixed-base revision and refuses removal. Exact Item-backed forgetting uses the existing person command-intent approval, records the actual human grant without executing, and consumes it once through the common publisher. Minimal suppression rows immediately exclude the identity from current and normal historical disclosure, publication and confirmation previews; retained Git/evidence/backup bytes are not erased. User inspection by a separate administrator remains an internal read-only scoped seam.

Explicit User Source intake now registers, lists and reads literal documents under current self authority. Sources use the sibling Source registry and material store, without creating a Memory notebook. Each registry record uses one canonical envelope header for identity, User/request lineage, timestamps and the digest of the exact captured bytes. Its payload holds the document kind, title and null location, conversation and file provenance. The literal producer's creation event supplies its capture time. Registration retains exact UTF-8 bytes through existing User receipts and Audit; replay returns the original Source and changed input conflicts. Missing established storage or incomplete command evidence requires recovery instead of a replacement capture. Registration adds no conversation or Worker provenance and creates no Memory page or candidate.

Authored pages use the shared Source resolver: `source:<sourceId>` selects an owning-scope registered Source, and `source:<sourceId>@<contentDigest>` also requires its exact digest. Current self admission verifies the literal Source's exact UTF-8 bytes and SHA-256 digest before page metadata or body disclosure, publication and page receipt replay. Forget preparation, approval detail and grant recheck those Source versions; initial apply repeats the check before consuming the grant. Suppression writes sorted, unique `source:<sourceId>@sha256:<digest>` fingerprints from the actual admitted versions, without Source text or forgotten prose. Source, evidence, Git and backup bytes remain separately retained. Completed forget replay returns its original content-free outcome. An explicit later human save may use those Sources under a new page identity at the current base; it cannot restore the forgotten identity.

Explicit remote MCP Source inspection already delivers content to models. Its trusted invocation context fixes model delivery; requests cannot select human delivery. After forgetting, `memory.source.read` returns null for a matching Source-version fingerprint, and `memory.source.list` withholds that version's complete metadata, including its title. Authorized human Source inspection retains access to the stored bytes. A later explicit new-page save does not clear suppression of the raw Source version for model delivery. Knowledge Manager recall, ask/tell, internal semantic maintenance and its daily trigger remain unimplemented. Administrator inspection of another User's Sources remains unjoined.

Public Server Knowledge, User Source-backed Proposal/Review, private recall and the semantic maintenance entry remain unimplemented. Scheduled consolidation and learning are accepted v0.1.0 scope but are not implemented. Usage aging and AI assessment remain deferred until after v0.1.0. The independent Skill catalog retains its own candidate/version lifecycle. Old Workspace `memory` aliases remain retired; intentional User Memory does not restore them. This partial scoped implementation does not establish full Memory or learning acceptance.

## Rollout / Migration Plan

Implement personal scope, explicit save/read/edit/forget and visibility enforcement, then explicit Source intake and Knowledge Manager ask/tell, integration and organization. Use the same fixed-base publisher and required approvals. Initialize new notebooks directly in profile v4 with Git-owned history. Current prerelease data follows the accepted pre-stable reset boundary; add no predecessor reader or synthesized authority. Then add bounded consolidation and learning through daily maintenance, default off. Usage aging and AI assessment remain outside v0.1.0.

## Testing Strategy / Acceptance Criteria

- Memory recall and Knowledge retrieval use the same current query context but separate invocations, labelled sections and independently fixed budgets. No query request can choose another User, Workspace or Server. Workers receive no Memory even when acting for its owner; a shared Thread cannot be made Memory-eligible by a role label.
- Pins and citations qualify exact owner/path references; equal paths in two sources never alias. Assistant traces stay in the private Timeline and Worker traces in the Task/Goal Thread. Both trace audience and current source permission gate every read; revocation hides content and restricted identity metadata without altering the retained evidence or creating a combined ledger.
- Two users' Memory remains isolated across direct APIs, search, indexes, exports and model context for ordinary users. Ordinary users cannot read another user's Memory. A currently usable administrator credential is eligible under [Core Permissions](../core/permissions.md) without taking ownership. User preferences survive switching Workspace without importing business data from one Workspace into another.
- Exact explicit saving is user-authored; a model inference uses current maintenance authority or remains pending for required Review; a temporary instruction changes no standing Memory. Users can see source, edit a page and invalidate a prior assessment.
- Explicitly supplied private conversation material yields an admitted registered Source and either an authorized revision or a required-review candidate, without fabricated Worker/S39 evidence. Interactions do not trigger implicit maintenance; only explicit runs or an enabled daily schedule may do so. Usage aging and AI assessment remain deferred.
- Concurrent direct edit versus reviewed replacement preserves the winner and returns conflict for the stale base, including an ABA case with repeated body text but a later revision. Faults around Git publication and command evidence follow the notebook owner, with no inferred completion or repeated publication.
- Forget without exact target confirmation or with a stale revision changes nothing; identical replay cannot delete a later save. Unsupported required features reject reads/imports before exposing content or weakening base checks.
- Forget immediately stops retrieval and stale candidate application, survives restart/index rebuild, and suppresses re-extraction from the same sources without deleting independent shared resources.
- Optional extension front matter survives without a required page-level origin/trust field. Commit metadata retains change attribution.
- Ask queries remain separate across audiences. One nonresident maintenance Thread per notebook scope serializes fresh bounded runs and exposes required approval. Each run retains its fixed base, source range, trigger and instructions; human edits remain inputs, own run records are excluded, and failed or skipped schedules remain visible. A Skill candidate changes no current version until its catalog owner accepts promotion.

## Scheduled Maintenance

[Knowledge Manager Agent](20260704-knowledge_manager_internal_agent_runtime.md#query-and-maintenance-execution) owns the bounded run and publication contract. Server, User and Workspace scopes each have one independent on/off setting, default off. The cadence is fixed daily; enable scheduling only for acceptance, testing and evaluation. Explicit requests remain available. There are no cadence, source-count or candidate-count settings. Existing intake bounds remain at most eight eligible completed prior Turns and four candidate changes in one bounded notebook changeset. [Recurring Triggers](20260711-scheduler_recurring_event_triggers.md#knowledge-manager-daily-maintenance) owns trigger admission, not learning or notebook publication.

A run learns from recent eligible completed Threads within its current scope and consolidates the notebook. It starts with the notebook overview, its retained inputs and needed Thread records. Retain the notebook base revision, the exact processed source range since the last run, trigger (`schedule` or `request`) and instructions in the existing Turn and Item records. Reuse existing Observation and maintenance records for exact scope, selected Source versions, target revision/digest, producer, model/configuration identity, candidate IDs, usage/assessment references and outcome. Retain current audience restrictions and skip already recorded candidates. The notebook and its commit history provide cross-run memory; no model state is carried across runs.

Include human edits since the previous run as inputs. Never use Knowledge Manager run records as learning inputs. Exclude active, ephemeral/no-memory or inaccessible work, prior generated maintenance/assessment output, pending proposals and unreviewed generated text as factual evidence. Registered Sources preserve admitted evidence before candidate drafting. An incomplete or failed range is not silently marked processed; a later fresh run can select it again. This uses prior run records, not a separate cursor or ledger.

Produce candidate commits on the fixed base through the existing notebook publisher. Publish under current maintenance delegation or retain the exact candidate as a proposal for required approval. The diff is the review surface. Human edits are never overwritten; a newer published revision causes the existing stale-base conflict. Generated pages may be comparison targets, but a new claim requires admitted Source lineage or new authorized evidence. Repetition, frequency and model confidence grant neither truth nor publication authority.

Each invocation reauthorizes its reads and writes and stops on cancellation, Source loss or runtime limits. Existing work records distinguish no-op, skipped, failed, pending candidate and published revision. A failed or skipped scheduled run records a visible reason and cannot stop silently. An unchanged source range or no useful changes is a visible no-op. Retry starts a fresh Turn from current owners; it never replays a model or resumes a hidden editor. Capture permission never grants maintenance authority. Source removal makes affected output ineligible and triggers no compensating cross-scope operation. Forget suppression remains effective through restart, source reuse and index rebuild.

## Deferred / Future Work

Usage aging and candidate-specific AI assessment remain deferred until after v0.1.0. They reuse existing Sources, notebook publication and evidence owners; they create no separate learner, scheduler, evaluator or hidden session.

Future optional AI prove means candidate-specific evidence assessment, not formal proof, publication authority or approval. An authorized user may request assessment of an exact candidate/page revision; authored scope policy may require it for generated critical content. Default assessment remains optional. It must use independent admitted Sources or observed checks, an explicit rubric, bounded existing invocation and existing Observation evidence. Retain assessed digest, authorized Sources and observations, assessor/model identity, outcome `supported | contradicted | insufficient_evidence`, limitations and time. A source or candidate change invalidates it. An authored required assessment leaves a candidate pending on unavailable, failed or insufficient assessment; positive assessment never replaces human Review. Advisory assessment has no veto over a currently authorized human decision, whose disagreement remains evidence. Direct user edits remain possible under current policy and invalidate assessment. Changing a required-assessment policy is a separate authorized policy decision. Assessment cannot repair missing disclosure authority. Conflicting Sources remain uncertain; ordinary user-authored preferences record expressed preference and need no truth assessment.
