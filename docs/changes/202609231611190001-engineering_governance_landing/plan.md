## Accepted Decisions

The source is the discussion record `temp/quality-governance/discussion-log.md`, which retains each engineer ruling with its reason and revisit trigger. At landing, curated rationale moves into `proposal.md` in this bundle and into decision records; the temp record stays disposable.

- Decision records: one file per decision under `docs/decisions/`, a new documentation type with fields for date, decider, decision, reason, rejected alternatives, revisit trigger, supersession, and affected owners. Scope is engineer rulings, approved agent-initiated governing design changes, and decisions whose rejected alternatives are likely to return. Record new decisions going forward and backfill a selected first batch. Specification text links to the record instead of an inline ruling marker, which makes an unlinked Safety Kernel limitation a detectable finding.
- Specification writing: specification bodies stay living documents; decisions and reasons are append-only records outside them. Each specification declares its kind (concept contract, boundary contract, cross-cutting mechanism, realization topology, or process and verification). Cross-cutting mechanism specifications own the questions every member answers plus a member registry; concept-specific semantics stay in the concept's specification. Drafts may be organized by feature, and division happens at promotion to Accepted under independent criterion-preservation review.
- Documentation as single source of truth: the governing test is that an agent could rebuild a system meeting the design and behavior expectations from documents alone after all implementation is deleted. Normative text must not depend on implementation identifiers or line citations; boundary conformance tests are part of the executable specification; technology choices that are decisions state their reasons. The rebuild probe joins document mutation as a documentation-governance instrument; it is not run in this plan.
- Test strategy: L2 is redefined to require agreement across a boundary in shape and in behavior under failure. In-process composition of real producers and consumers, with no double at the crossing, fault injection at the boundary, and invariant assertions, is a core part of L2 rather than a variant. The primary names a seam in the plan when a change alters a representation crossing different owners; a test author reads both owning contracts.
- Review and verification: independent review at representation boundaries favors executable counterexamples against invariants. Reviewer and Auditor ask about caller obligations and report raw before and after observations without scores. Scoring frameworks do not become gates.
- Complexity: design-time questions ask whether a new concept can be an existing kind, can register into existing dispatch, and can derive its durable state from existing facts. The primary records a small set of raw numbers at material closeout; an Auditor compares trends at a release boundary or on request. Signals are explanatory, never builder targets; triage separates essential from accidental complexity and routes through existing findings and design-challenge paths.
- Roles and harnesses: harness-neutral role contracts under `docs/roles/`, abstract capability tiers (frontier, standard, fast), default role compositions per task class that remain starting points rather than pipelines, a platform reference that owns harness enforcement facts and dispatch methods so each model name appears in one place, and thin adapters for Codex, Claude Code, and Grok Build. Cursor CLI, PI through Herdr, and DeepSeek Harness use prompt dispatch naming the role file. OpenCode is not supported. The Consultant contract declares the gap it fills (freshness, independence, capability) and its stance; there is no separate advisor role. A writer role drafts and edits documentation text and must never change a criterion; another context verifies every rewrite.
- Vocabulary: an engineering-process glossary follows Ubiquitous Language within its bounded context and stays separate from the product vocabulary in Core Concepts. It lists classic terms with sources and project usage, which also act as trigger words; the few project-specific terms that remain, each with definition, scope, and owner; one fixed phrase per meaning for overloaded words; and an avoid list. Cross-context collisions such as Intent Epoch against runtime epoch are removed by renaming where possible. Root AGENTS.md gains a situation index or points to one, and fast-tier agents read a bounded task contract rather than the full governance corpus.
- Temporary material: temp stays disposable. Value is harvested at parking, checkpoint, closeout, and triage into existing committed homes, stripped of host details and unverified inference because the repository is public. Each temp work package carries a fixed status header.
