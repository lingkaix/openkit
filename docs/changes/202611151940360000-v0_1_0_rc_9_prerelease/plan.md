## Pre-Stable Deployment Reset

This release cannot read a Data Root written by `v0.1.0-rc.8`, an earlier prerelease or an unpublished development build. Core and Workspace each start from one current SQL baseline; startup refuses the retired journals and never resets data. User and App journals are unchanged, but no data is carried forward selectively.

| Data | Disposition |
| --- | --- |
| Data Root of every existing deployment (dev, `a1`, `a2`) | Reset. Rename the old Root aside on the same filesystem; physical deletion is a separate engineer-reserved step |
| Accounts the engineer names for each deployment | Re-registered with operator-held credentials and verified through public surfaces before ordinary use |
| Operator configuration | Copied and reviewed against this release; the manifest does not assert configuration compatibility |
| Workspaces, Threads, Turns, Artifacts, Knowledge, Memory, Vault material, Provider accounts and retained Worker sessions | Reset; regenerated by acceptance work. No export or import crosses the reset |

The reviewed manifest facts declare `migrationFree: false`, `configurationCompatible: false`, `retainedDataCompatible: false` and `recovery: "pre-stable-reset"`. `previousAppImageId` is the rc.8 App linux/amd64 image ID, `sha256:1ed39d334b281354662cf9fec7ab395b8c2bcfd649ea0a45de9fa70f63d6bfff`; the linux/arm64 image ID is `sha256:6662d610f158d7c1ec678ef3fba6516da47745f57584424f8c7104a284446094`. These facts authorize no reset. Each deployment reset follows the [operator procedure](../../../skills/openkit-ops/references/nanocore-operations.en.md#explicit-pre-stable-deployment-reset) under its own authority, one deployment at a time; `a2` needs a separate engineer GO.
