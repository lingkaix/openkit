# Work Data Capture And Turn Lifecycle

On 2026-09-21 the engineer authorized locking the work-data retention format in three steps: (1) what to retain; (2) storage form and file format; (3) architecture and technology stack. This plan holds only the implementation work that the settled decisions already determine. Indexing and search acceleration are out of scope by the engineer's ruling. Source: the engineer's instructions given in the 2026-09-21 working session; the reasoning, the rejected alternatives and the falsified claims behind those decisions are recorded in [`proposal.md`](proposal.md).

## Work Items

These items are not a schedule, queue, or package sequence. Each names a change, the owner that must decide it, and what is still missing before implementation may start. Each "Missing before start" clause below was written while that owner statement did not exist; every one of them was supplied by commit `f9f6e112` and the items are now implemented, so read those clauses as the contract each item had to satisfy rather than as work still outstanding. `Implementation` below records what actually landed against each one.

### 1. Turn terminal publication boundary

After a Turn is terminal, `updateTurn`, `createItem`, and `emitTurnEvent` admit only completion of an already-decided publication: the write is admitted when it carries the same identity and the same content as the decision already recorded, and time since terminalization is not the test. Two different behaviours hide under that description and must not be merged: exact repair of an already-decided publication, which worker transcript replay at `apps/nanocore/src/runtime/worker-transcript.ts:247-254` enforces by deep equality; and a named field-limited display refresh, which `apps/nanocore/src/mode-entry-routes.ts:269-280` performs by returning the Item unchanged when `level`, `title` and `summary` match and updating only those three fields when they differ. A single shared predicate would break one of them. The three guards are one rule applied three times. The existing shape is the presence-keyed idempotent repair at `apps/nanocore/src/runtime/worker-turn-failure.ts:115-152`. A sweep of ten call sites established that a blanket "no writes after terminal" rule would break legitimate paths that must be named here rather than left as a count: `terminalizeGovernedWorkerTurn` emitting its own terminal event and performing idempotent repair; the MCP boot backfill of missing Items; approval-projection repair; and the Task-to-Goal explanation Item. A fifth case, configuration apply, is coupled to the delayed-user-input rebinding line and MUST be resolved with that owner before any guard that would reject its present behaviour is enabled. The admitted exception therefore has to state, per path, what an identical outcome, a missing outcome and a conflicting outcome each do, and whether the rule covers events as well as Items; "judged by identity" alone is a slogan that has already been implemented wrongly once. [`docs/core/protocol.md`](../../core/protocol.md) owns terminal immutability and "MUST NOT be reopened or rewritten"; it does not yet state the identity-keyed publication exception. Missing before start: that exception admitted by the Turn-lifecycle owner, plus a focused regression covering legitimate post-terminal completion of already-decided publication versus rejected new writes.

### 2. Goal revision failure handling

The engineer ruled that a planner failure during plan revision preserves the scene and lets the user decide, keeping the Goal alive so work can continue on the same goal path. `reviseGoalPlan` currently sets the Goal to `planning` with a null `planItemId` (`apps/nanocore/src/runtime/goal-plan-approval.ts:292-299`), and `goal.plan` admits exactly that state (`apps/nanocore/src/goal-routes.ts:3162`), so after a failure the user can retry planning but cannot approve the old plan or issue a fresh revision instruction. [`docs/specs/20260704-goal_mode_coordination.md`](../../specs/20260704-goal_mode_coordination.md) owns Goal admission, plan approval, and the active-plan pointer. Missing before start: a coherent Goal admission and active-plan-pointer transition under that owner, plus a focused regression covering revise, planner failure, fresh planning retry, fresh revision instruction, and old-plan approval.

### 3. Measured harness identity

Stop treating the authored `runtimeVersion` on the Agent Environment Package as a measured harness version. Reference the measured `sandbox_runtime_records.image_digest` instead, captured at binding time for both new and reused bindings, because the row is deleted on cleanup. [`docs/specs/20260616-agent_environment_package.md`](../../specs/20260616-agent_environment_package.md) owns the authored package; [`docs/specs/20260802-nanohost_runtime_and_transport.md`](../../specs/20260802-nanohost_runtime_and_transport.md) owns sandbox runtime records and binding. Missing before start: those owners stating that measured harness identity is the binding-time digest rather than authored `runtimeVersion`, and capture on both new and reused bindings.

### 4. System prompt digest capture

Declare one semantic boundary — the prompt before adapter conversion — and account for the actual conversion paths rather than promising a single existing hook: Chat calls reach it through one converter while Codex and bridged Responses reach it through another (`apps/nanocore/src/llm/pi-ai-client.ts:284-300`). The grouping is not injective: an absent prompt and an explicit default literal produce different pre-adapter digests and identical outgoing instructions. [`docs/specs/20260921-work_data_retention_format.md`](../../specs/20260921-work_data_retention_format.md) owns the slot this digest occupies and the semantic boundary it must be taken at, and requires the slot to exist even when no producer does. What is still missing is the producer and its owner: no accepted owner states who computes the digest, on which conversion paths, and how the non-injective grouping is reported. The LLM conversion paths are implementation fact under the existing pi-ai client. Missing before start: an accepted owner for the producer, without requiring a single hook.

### 5. Coverage binding

The resolved effective retention setting is fixed at Turn admission and written into `turn.json`, which is already rewritten on every persist, so this adds no new file. A setting change takes effect at the next Turn; an already-started Turn is never interrupted. The switch defaults to off. [`docs/core/protocol.md`](../../core/protocol.md) owns Turn admission and when the effective setting is fixed; [`docs/specs/20260703-storage_layout_record_ownership.md`](../../specs/20260703-storage_layout_record_ownership.md) owns what `turn.json` carries. The engineer decided the binding point, the next-Turn effect and the default-off switch; [`docs/specs/20260921-work_data_retention_format.md`](../../specs/20260921-work_data_retention_format.md) holds the contract. Missing before start: the admission-time field on `turn.json` and the default-off switch under those owners, without a mid-Turn interrupt path.

### 6. Turn terminal predicates derived from one named set

Now that `cancelled` is a live Turn terminal in both the schema and production, the predicates that ask "is this Turn finished" are split. The waiter defect half is done: `isTerminalTurnStatus` at `apps/nanocore/src/goal-routes.ts:2326-2333` answers `completed`, `failed`, `interrupted`, `cancelled`, or `awaiting_human`, which is the settled-for-waiters set in [`docs/core/protocol.md`](../../core/protocol.md) (`:204-207`; terminal list `:191-196`). `waitForWorkerTurnTerminalState` (`:2269`, used at `:3972`) therefore settles a cancelled Turn instead of waiting out `WORKER_TURN_AWAIT_TIMEOUT_MS` (`:2259`). That restoration is what protocol already decided, so it needed no new owner under `[AUTH-001]`. `apps/nanocore/src/goal-worker-turn-wait.test.ts` is the regression: it covers the already-cancelled Turn, a Turn cancelled while the waiter is subscribed, and a still-running Turn that must not settle. Named execution output with the fix reverted: tests 1 and 2 fail with `expected Symbol(still-waiting) not to be Symbol(still-waiting)` and test 3 passes; with the fix applied all three pass, and `src/goal-plan-read.test.ts`, `src/goal-steering-authority.test.ts` and `src/thread-goal-summary.test.ts` run 53 tests with 0 failures alongside it. A second function of the same name at `apps/nanocore/src/runtime/worker-turn-failure.ts:319` answers `completed`, `failed`, `interrupted` or `cancelled` and omits `awaiting_human`, so the two same-named predicates still disagree; that is the refactor half, still blocked. The design the discussion settled on is four named sets rather than one: the sealed terminals `completed | interrupted | cancelled | failed`; settled-for-waiters, which adds `awaiting_human` because that state does not advance on its own but can still be moved by an outside actor and therefore must not be read as "the system guarantees no further writes"; checkpoint-collectable, which removes `interrupted` because the recovery path may still own those Turns; and recovery-rewritable, which is only `pending | running`. Deriving remaining predicates from the named set is the refactor. The derivation must be mechanically enforced: adding a value to `TurnStatusSchema` today fails nothing, because `['a','b'].includes(status)`, `new Set<Turn['status']>([...])` (the present shape at `apps/nanocore/src/app-dashboard.ts:38-39`) and `as const satisfies readonly TurnStatus[]` all accept a missing value silently. Only an exhaustive `Record<TurnStatus, …>` or a `switch` with a `never` default fails compilation. Product-side predicates that are allowed to differ from the sealed set must either import it or declare the difference explicitly and list it; the sites to reconcile include `apps/nanocore/src/runtime/stop-after-turn.ts`, `apps/web/src/screens/chat/ThreadStream.tsx` and `apps/web/src/screens/chat/ThreadScreen.tsx`. Missing before start of the refactor half: an accepted statement of where the single derivation lives and which product projections may diverge.

## Implementation

Every item below was produced by one agent and accepted by a different agent, under `[GOV-001]`. No producer adjudicated its own artifact. Four of the six packages were rejected on their first independent review and one was rejected twice; every rejection was on a lost bound or a moved defect rather than on a wrong fact, which is the same failure shape this work line saw during the documentation promotion.

Work item 1, the terminal publication boundary, is implemented as a terminal branch on the four canonical writers `updateTurn`, `createItem`, `emitTurnEvent`, and `updateItem` in `apps/nanocore/src/lib/store.ts`, with the per-path admission grid from [`docs/specs/20260703-storage_layout_record_ownership.md`](../../specs/20260703-storage_layout_record_ownership.md) and the two equality behaviours kept structurally separate as that owner and [`docs/core/protocol.md`](../../core/protocol.md) both require. Admission of an event is judged by the published outcome and the sealed Turn's decided content, not by an event-name allowlist; the first implementation used a name list, which rejected `turn.updated`, the terminal event of a Turn sealed as `cancelled`, and broke the committed regression from commit `79fb6778`. Configuration apply remains admitted and is marked pending [`docs/specs/20260921-delayed_user_input.md`](../../specs/20260921-delayed_user_input.md); no guard rejecting its present behaviour was enabled, because that admission was not granted.

Work item 2, Goal revision failure handling, changed the three planner-admission fences together so a revision planner Turn is admitted by the revision command and its durable revision-request Item against an intact pointer. A revision request no longer moves the Goal to `planning` or clears `planItemId`, and a planner failure leaves the Goal at `awaiting_plan_approval` so the previous Plan stays approvable. `assertApprovableGoalPlanRevision` was not withdrawn.

Work item 3, measured harness identity, copies the sandbox image digest as a value at binding time on both the new-binding and the reuse paths, and the physical Epoch cutover now carries that state so a binding keeps its digest across a rebuild. The first implementation refused a reuse whose digest differed, which forbade exactly the false-split the owner permits; it now splits.

Work item 4, the system-prompt digest, is produced at the Gateway entry above the provider split and keyed on the gateway-entry capability ids rather than on `family` alone. The first implementation added a Drizzle TypeScript member without a migration journal entry, so the column did not exist in any migrated database and every attributed public Gateway call returned 400; the column is now created by the committed workspace journal and a SQLite CHECK duplicates the persist fence.

Work item 5, coverage binding, writes the admission-time resolved `{scope, value}` pair onto the existing `turn.json` and now reads the operator's `server.jsonc` `policy.workDataCapture`. The first implementation left that switch unwired, so a configured value never reached Turn admission and the recorded pair was always the default; an independent reviewer caught it.

Work item 6 is complete on both halves. The defect half landed earlier as commit `79fb6778`. The refactor half derives the four named sets from one exhaustive `Record<TurnStatus, boolean>` per set in `packages/protocol/src/models/turn-status-sets.ts`, which satisfies the owner requirement that adding a Turn status value fails compilation; that property was verified by two agents independently adding a value and observing four `TS2741` errors.

One change outside the six items landed with them. `apps/nanocore/src/internal-agents/worker-coordinator.ts` scanned the whole prompt for review and audit keywords, so nouns in supplied context or inside negated constraints selected a routing kind and Chat Mode refused a request that only asked the Assistant to summarise. Routing now reads the request the prompt makes and falls back to scanning the whole prompt when no clause is identified as the request, so it is never narrower than the previous behaviour. This is an implementation choice inside an internal agent and changes no accepted contract, so it required no specification under `[DOC-002]`; the precedent is commit `5edc6a02`.

## Remaining Turn-status restatements

[`docs/core/protocol.md`](../../core/protocol.md) assigns this inventory to the change record: "The inventory of projections that still need reconciling belongs to the change record." The first inventory written here listed eighteen predicates and was wrong twice: it searched only for array literals, so it missed every predicate written as a chain of `===` comparisons, and it included one entry that is not a Turn-status projection at all. An independent review found the misses. The corrected sweep looks for any window mentioning three or more status literals next to `.status`, excluding exhaustive `switch` statements and `z.enum` declarations, which are already compile-safe or are wire contracts rather than predicates.

**Twenty-two behaviour-preserving imports.** Eight negated the sealed four as an array, in [`worker-governance-turn-executor.ts`](../../../apps/nanocore/src/runtime/worker-governance-turn-executor.ts) twice, [`worker-environment-preparation.ts`](../../../apps/nanocore/src/worker-environments/worker-environment-preparation.ts) twice, [`worker-environment-activation.ts`](../../../apps/nanocore/src/worker-environments/worker-environment-activation.ts) once, and [`simulator.ts`](../../../apps/nanocore/src/lib/simulator.ts) three times. Eight wrote the identical predicate as the positive complement `pending`, `running`, `awaiting_human`, in [`store.ts`](../../../apps/nanocore/src/lib/store.ts), [`app.ts`](../../../apps/nanocore/src/app.ts), [`artifact-routes.ts`](../../../apps/nanocore/src/artifact-routes.ts), [`worker-context-projection.ts`](../../../apps/nanocore/src/context/worker-context-projection.ts), [`worker-environment-operations.ts`](../../../apps/nanocore/src/worker-environments/worker-environment-operations.ts), the removed `WRITABLE_TURN_STATUSES` in [`generative-ui/commands.ts`](../../../apps/nanocore/src/generative-ui/commands.ts), [`turn-routes.ts`](../../../apps/nanocore/src/turn-routes.ts), and [`repository-routes.ts`](../../../apps/nanocore/src/repository-routes.ts). Five spelled the sealed four out positively, two in `store.ts` and one each in `turn-routes.ts`, `worker-governance-turn-executor.ts`, and [`packages/core-client/src/events.ts`](../../../packages/core-client/src/events.ts). One was the checkpoint-collectable set in [`mode-entry-routes.ts`](../../../apps/nanocore/src/mode-entry-routes.ts), whose own comment gives the reason interrupted stays fail-closed; it imports that set and keeps the reason as a comment at the use. All twenty-two are truth-table identical to the named predicate they now import.

**Two defects of one family, both fixed.** Each omitted `cancelled` from a finishedness test, so a sealed Turn was treated as live. `app.ts` required the awaited Worker Turn to be `completed`, `failed`, or `interrupted`, so a cancelled Turn reached `throw new Error('Worker still requires human intervention.')` and failed the resident replacement. `repository-routes.ts` hung the Git push approval gate on the source Turn unless it was `completed`, `failed`, or `interrupted`, so a cancelled source Turn received a gate on a sealed Turn instead of the separate publication Turn. Both now test the sealed set, which admits `cancelled` and still rejects `awaiting_human`, the one settled status that does mean a human is required. Both waiters have settled on a cancelled Turn since `79fb6778`, which predates this bundle, so these were standing defects of that family rather than permitted differences.

**One entry withdrawn.** `packages/app-api-schemas/src/dashboard.ts` was listed in error. `WorkspaceAttentionSchema.kind` is an attention-kind wire enum whose members are not `TurnStatus` values, so the clause does not reach it.

**What the sweep deliberately leaves alone.** Exhaustive `switch` statements over `TurnStatus`, such as `stopReasonForTurnStatus` and the dashboard attention mapping, already fail compilation when a status is added. `z.enum` declarations are wire contracts, not predicates. Several nearby closed lists belong to other unions, including `RecoveredTurnStatus` in `index.ts` and the restart recovery path, Goal Task status in `goal-routes.ts` and `workspace-import.ts`, and worker stop reasons in `worker-control-records.ts`. The status-to-stage chain in `artifact-routes.ts` maps each status individually rather than testing a set.

**Coverage, stated plainly.** The full suite passes before and after, which proves the conversions broke nothing. It does not prove each converted predicate is exercised. Spot checks found `store.ts` thread-busy covered by a test that fails if the predicate is inverted, and the Generative UI writability fence not covered by any such test. No new regression is owed for a behaviour-preserving substitution, but the coverage of these fences is uneven and that is a known state, not a claim of proof.
