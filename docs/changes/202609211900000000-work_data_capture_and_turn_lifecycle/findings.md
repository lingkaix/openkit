## [open] WDC-FND-001 — Two denial paths produce different Turn terminal statuses

- **Observation:** A denied policy-local approval writes Turn `cancelled` in `finishPolicyApprovalProjection` at `apps/nanocore/src/approval-routes.ts:601`; a denied worker gate writes Turn `interrupted` at `apps/nanocore/src/approval-routes.ts:873-874`, and the worker-control `aborted` overload at `apps/nanocore/src/runtime/worker-control-records.ts:80` also maps to Turn `interrupted`.
- **Impact:** Each path is self-consistent under its own owner, but a user sees two terminal statuses for the same product fact that an approval was denied. Unifying them would change a live mapping; leaving them split leaves the product presentation inconsistent.
- **Evidence:** Direct read of `apps/nanocore/src/approval-routes.ts:600-601` (`terminalStatus = input.decision === 'denied' ? 'cancelled' : 'completed'`) and `:868-874` (denied worker-gate closeout writes AgentSession `interrupted` and Turn `interrupted`); `apps/nanocore/src/runtime/worker-control-records.ts:80-96` (`aborted` overload returns `'interrupted'`). Source: R51.7 item 1.
- **Owner:** None is accepted.
- **Next action:** Obtain an accepted owner for whether the two denial paths should unify Turn terminal status. Do not implement unification in this plan.

## [closed] WDC-FND-003 — removeStaleDirectories is a capture-point directory constraint

- **Observation:** `removeStaleDirectories` at `apps/nanocore/src/storage/workspace-file-records.ts:2653-2658` runs `rmSync(..., { recursive: true, force: true })` on child directories absent from an in-memory expected set; `writeThreads` invokes it twice on the ordinary persist path at `:2001` with `expectedThreadIds` and at `:2014` with `expectedTurnIds`; the expected turn set is projected from `this.turns` in `FsStore.writeWorkspaceFileRecordsToRoot` at `apps/nanocore/src/lib/store.ts:1160-1164`; the trigger is private `persist` at `store.ts:1083-1098`, which public mutators such as `updateTurn` (`:2478`) call; `loadWorkspace` at `workspace-file-records.ts:918` walks every thread and turn directory and throws on missing `thread.json` (`:962-964`), missing `turn.json` (`:989-991`), embedded items (`:994-998`), or lineage mismatch (`:1002-1008`); `listThreads` at `store.ts:2225-2227` returns every thread for the workspace including archived; after a successful load the in-memory expected names are a superset of on-disk directories, so those two `rmSync` calls are empty; a capture point that creates a thread or turn directory NanoCore has not admitted into `this.turns` loses that directory on the next `persist()`; a `turn.reap` observation therefore has to be written only after recovery has re-admitted the crashed Turn into `this.turns`; `observations.jsonl` and `blobs/` living inside an already-admitted turn directory sit outside this `rmSync`; this is consistent with the import-and-verify rule for canonical product records at `docs/specs/20260703-storage_layout_record_ownership.md:439`, under `OpenShell And Worker Output Ingestion`, which states that canonical product records are created only when NanoCore imports and verifies the output.
- **Impact:** Capture-point topology is constrained: writers may only append inside directories NanoCore already holds in memory. Violating write order for crash evidence (`turn.reap`) would delete the directory that holds the crash record. Re-probing this path as a data-loss defect would repeat a closed result.
- **Evidence:** Direct read of the cited lines at HEAD `968f5a4e`. Source: R34.0, originally marked verified at `c1a8b6ad`; current lines match, with `persist` private at `store.ts:1083`.
- **Owner:** `docs/specs/20260703-storage_layout_record_ownership.md`
- **Next action:** No further probe of `removeStaleDirectories` as a data-loss defect is owed. Capture-point writers remain bound by the directory-existence constraint in Observation.
- **Closing verdict:** The path is a hard constraint on where a capture point may write; under ordinary load-then-persist operation it deletes no admitted history.
- **Closure evidence:** `loadWorkspace` fail-closed at `workspace-file-records.ts:918-1008` plus expected-set projection from `this.turns` at `store.ts:1160-1164` on the persist path at `store.ts:1083`.

## [open] WDC-FND-004 — Terminal immutability is stated in Core twice and unenforced in storage

- **Observation:** Core states terminal immutability twice: `docs/core/core-concepts.md:97` ("A terminal Turn is immutable and never reopened") and `docs/core/protocol.md:214` ("A terminal Turn is never reopened or rewritten"; survey cited `:213`, now `:214`). A literal "reject every write after terminal" reading would break the legitimate post-terminal paths named in `plan.md` work item 1; "identity-and-content consistency" as one universal rule is what an earlier implementation already got wrong, so the allowed identical / missing / conflicting outcomes and event coverage live as a compact table in `proposal.md`, including an admitted conversation-result refresh limited to `level` / `title` / `summary` at `apps/nanocore/src/mode-entry-routes.ts:269-279` and worker-transcript replay that requires full deep equality at `apps/nanocore/src/runtime/worker-transcript.ts:247-254`. Current Core terminal states are `completed|interrupted|cancelled|failed` (`protocol.md:191-196`); `unknown` is not a Turn status, so the survey's `unknown`-rewrite example is historical while the missing storage guard remains.
- **Impact:** The storage layer will accept a status patch that reopens or retargets a terminal Turn, and will append Items and events after terminalization, unless a caller applies a private predicate. This finding overlaps work item 1 in `plan.md`; that item names the paths, and `proposal.md` records per-path identical / missing / conflicting behaviour.
- **Evidence:** Direct read of the cited lines at HEAD `968f5a4e`. Source: R34.1 as corrected by R45.5. Presence-keyed idempotent repair remains at `terminalizeGovernedWorkerTurn` in `apps/nanocore/src/runtime/worker-turn-failure.ts:115-152`.
- **Owner:** `docs/core/protocol.md`
- **Next action:** Keep this finding open with work item 1 until that owner states the publication exception with the per-path bounds in `proposal.md`. Do not implement a time-based reject or a generic post-terminal exception from this finding.

## [open] WDC-FND-006 — Four definitions of incomplete after a crash

- **Observation:** Restart recovery `scheduler-restart-recovery` at `apps/nanocore/src/index.ts:302-348` calls `terminalizeGovernedWorkerTurn` at `:337`; incomplete there means the Turn is outside `isTerminalTurnStatus` at `apps/nanocore/src/runtime/worker-turn-failure.ts:319-320` (`completed|failed|interrupted|cancelled`). `listRecoverableWorkerCheckpoints` at `apps/nanocore/src/runtime/worker-checkpoints.ts:504-516` keeps every checkpoint whose `stage !== 'completed'`; `RecoverableWorkerTurnStage` at `apps/nanocore/src/runtime/worker-recovery.ts:42` is `Exclude<WorkerTurnStage, 'completed'>`, so `failed` and `aborted` are recoverable, while `isTerminalWorkerTurnStage` at `apps/nanocore/src/runtime/worker-stage.ts:31-34` treats `completed|failed|aborted` as terminal. `isClosedProductTurnStatusForStaleCheckpoint` at `apps/nanocore/src/mode-entry-routes.ts:1231-1232` treats only `completed|failed|cancelled` as closed. `recoverRunningCapabilityCalls` at `apps/nanocore/src/capability/usage-ledger.ts:533-547` recovers only `status = 'running'`; `startCapabilityCall` at `:227` always writes `running`, so a `queued` row allowed by `CapabilityCallStatusSchema` at `packages/protocol/src/models/capability.ts:18-28` would never close on this path.
- **Impact:** Editing one incomplete-predicate leaves the others in place. Restart recovery can terminalize an `awaiting_human` Turn to `interrupted` while stale-checkpoint cleanup leaves the checkpoint because that Turn is outside `completed|failed|cancelled`. The predicates answer different questions and must stay named and distinct: sealed terminals `completed | interrupted | cancelled | failed`; settled-for-waiters, which adds `awaiting_human`; checkpoint-collectable, which removes `interrupted` because recovery may still own those Turns; recovery-rewritable `pending | running`; and CapabilityCall running-recovery, which is a different owner's running-status sweeper.
- **Evidence:** Direct read of the cited lines at HEAD `968f5a4e`. Source: R34.3 row 3, as later named in R37.4 and `plan.md` work item 6 without the withdrawn Turn `unknown`.
- **Owner:** None is accepted.
- **Next action:** Obtain accepted owners for the named, deliberately different sets above and keep them distinct. Do not seek one shared incomplete-after-crash predicate covering Turn, checkpoint, and CapabilityCall recovery, and do not implement unification from this finding.
