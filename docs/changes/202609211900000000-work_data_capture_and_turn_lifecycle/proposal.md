# Work Data Capture And Turn Lifecycle — Scheme Rationale

This file is a work-proposal rationale record under `docs/change-execution.md`. It has no independent design authority. Lasting design belongs to accepted Core and specifications. Execution lives in `plan.md`. Open findings live in `findings.md`. The discussion that produced this rationale is the gitignored record `temp/work-data-retention/proposals/format-proposal-v2.md`, whose banner states that only R39–R51 are current decisions and that overturned passages are retained under `⚠` rather than deleted.

This file carries only `date` because the closed change-record `type` vocabulary has no proposal value, the validator classifies a bundle `proposal.md` as a findings-type document whose permitted fields are `date` and `status` only, and adding `type: proposal` fails validation.

## The question and the three-step framing

On 2026-09-21 the engineer split the work into three steps: (1) what to retain, and for which later uses; (2) storage form and file format; (3) architecture and technology stack. Step 1 is settled in `temp/work-data-retention/proposals/note.md`. Step 2 is settled in the discussion record, with current decisions in Parts 12–24 (R39–R51). Step 3 has not started. Indexing and search acceleration were put out of scope by the engineer at the opening of step 1 (`note.md` §〇).

The question that step 2 had to answer is the launch criterion already stated in `note.md` §1.7: for every class of information that will only be collected later, can the first-shipped format distinguish “not collected then” from “did not happen then”? A format that can distinguish those two cases lets collectors arrive later; a format that cannot makes old data claim completeness, and that lie cannot be repaired after production data exists.

`plan.md` holds the implementation work that step 2 already determines. This file does not restate those work items. It records why the scheme was chosen, which alternatives died, which probes changed a decision, which rulings were the engineer’s, which objections moved the authors, and which once-verified claims were later falsified.

## Why the chosen scheme

The decisive constraints are the engineer’s, recorded in `note.md` and in the later rulings E1–E5, R42, R46, and R48. Each constraint ruled something out.

**Agent is model plus runtime.** What must be retained is Gateway-mediated model interaction plus the runtime’s kind, version, and environment. External intervention — user input, interruption, approval, product acceptance — is a third class, neither model nor runtime. That formula ruled out a producer-by-producer inclusion debate: a unified model takes all three classes, and “should this producer be in?” is a false question (`note.md` §1.1–1.2, §八).

**An agent is a cheap scheduling unit.** Tasks that run on agents are valuable; the agent instance is not. Exact resume of an interrupted execution is neither possible nor worth building in a multi-agent orchestration system. Enough retained data lets a new Thread continue the work. That ruled out resume as the design floor, a second work state machine, continuation serialization, effect-intent/settlement protocols, and a generic recovery engine (`note.md` §1.3, §二).

**There is no perfect environment.** Even complete and correct capture cannot guarantee that an agent will not err, because the world it talks to is unstable. Network reordering of two tool calls is acceptable. That ruled out mechanical guarantees aimed at eliminating that class of uncertainty, and it ruled out treating missing data as a format failure (`note.md` §1.4).

**The world can be re-read.** Capture is complete on the agent’s own loop — model I/O, tool I/O, Core decisions, user intervention — and is not a photograph of world state. File contents, repository state, and the live environment remain in the world. That ruled out digesting every related file, CRDTs, a full working-directory VCS, and keyboard recording (`note.md` §1.5, §1.8, §二).

**Capture trends and regularities, not a controlled experiment.** The engineer’s later wording of the same constraint is E4: keep the principal information, trends, and laws; for external associated files, do our best; it is allowed that a file cannot be found, and it is not allowed that a reference is wrong. That ruled out a row that promises never to be deleted, a tombstone ledger for every legal deletion, and any reference that can silently resolve to a different object after import reminting.

**The design floor is fine-tuning, audit, and multi-dimension eval, not resume.** Resume needs are a subset of those three. Eval needs a resolved configuration fingerprint, a task-instance identity orthogonal to Thread/Turn, and outcome labels with provenance. Fine-tuning needs faithful model I/O with “what the model saw” separable from “what actually happened.” E1 then accepted that full I/O is too expensive to implement in this round, while requiring the architecture to cover it and a future switch at task / workspace / server grain. That ruled out shipping a first version whose format cannot later hold full I/O, and it also ruled out pretending that digest-only first ship already satisfies the fine-tuning floor (`note.md` §三, E1 at discussion-record R40.0).

**Missing data and wrong data are different.** An agent can work around absence. It cannot work around a confident falsehood. Combined with E4, that ruled out silent drops, default-complete coverage claims, and join keys that remint to the wrong object.

**Pointers run from owner back to Thread, not the reverse.** World-change logs, coverage policy, and environment bindings live with their owners. A Thread records which binding it used. That ruled out copying server changelogs into every Thread, and it ruled out a per-Thread `capture.coverage` replica that would drift from the global policy table.

**Grep-first storage.** Retrieval preference is search over files, then reconstruction. That ruled out a highly normalized SQLite journal as the online authority whose payloads sit in BLOBs that cannot be grepped, and it ruled out adopting OpenTelemetry GenAI conventions as the storage format (those conventions are sampled telemetry; span status is Unset/Ok/Error with no unknown; content is not collected by default; a full queue drops).

**Use an already-authorized family rather than reopen Item.** Round-1 review showed that stuffing observations into `items.jsonl` either opens the protocol Item union (crash records and `env.bound` would enter App API / SSE / Web) or filters on write-time audience (product Item becomes a projection again). `docs/specs/20260703-schema_evolution_record_envelope.md` already names observation ledgers as a line-oriented family beside item logs. Dual family — naked protocol Item as the narrative, observation ledger as the annotation — is the scheme that satisfies `docs/core/work-model.md`’s rule that ordered Item history remains the user-visible source of truth, without a Core doctrine change to Item.

**Bind coverage at Turn admission, in a file already rewritten on every persist.** Independent review of E3 showed that a Thread-creation epoch cannot answer whether a later Turn ran under a later switch setting, and that the cheapest carrier is `turn.json`, which the discussion record reports is already rewritten on every persist. The engineer then ruled that a coverage-setting change does not interrupt an already-started Turn, and that the switch defaults to off. Default-off raises the binding’s necessity: almost every first-ship Turn will carry `off`, and without that field later readers cannot separate “was off,” “was broken,” and “did not happen.”

**Turn terminals follow the running system.** Under [PRECEDENCE-002], Git and the running system decide implementation fact. Production already writes Turn `cancelled`. Core and thirteen specifications still described a three-value terminal set. The scheme therefore corrects documents to the four terminals `completed` / `interrupted` / `cancelled` / `failed`, and does not add `unknown` to Turn. Effect uncertainty stays on `CapabilityCall`. Which denial path produces which terminal is left to the owning specification.

Those constraints, taken together, are why the scheme is dual-family JSONL with self-describing `refs`, B′ retention (rows carry long-retention principal facts and minimum references; time-bounded diagnostics and restricted raw stay with their owners; no independent row-level TTL; no new tombstone ledger), Turn-admission coverage in `turn.json`, placement by content kind rather than size, `parent` for join, `corr` only as a request/response pair, `ret` as the Core closed five retention classes, and UUIDv7 Thread/Turn identifiers without calendar sharding.

## Engineer rulings

Choices below are the engineer’s. Surrounding derivation is the authors’ unless marked otherwise.

**E1 (fidelity floor), recorded at discussion-record R40.0.** Full retention of model I/O is too expensive to process and store. The architecture and model must fully consider and cover that case, and this round does not implement it. Future implementation gives the user a switch at the grain of one task / one workspace / the whole server. Author derivation that went beyond the ruling — “therefore v1 must freeze the digest byte boundary now,” “therefore v1 leaves every digest slot empty including metadata” — was later defeated or narrowed (R41.1, R43.3, R44.1).

**E2 (export), recorded at R40.0.** Make the simplest design. Export does only very simple necessary processing, then exports completely. Do not over-consider security and privacy: exported data is not expected to be published or reused elsewhere; its uses are internal team backup or use outside the system. Author derivation that the portable-import `requiredFeatures` gate still applies was upheld for portable import and judged excessive for cold backup (R41.1). Author derivation that the backup spec’s private-thread exclusion and exact inventory must be rewritten wholesale was judged excessive; only whether observation is blocked by directory membership needs the owner (R41.1).

**E4 (references and retention), recorded at R40.0.** The principle is to keep the principal information, trends, and laws in the data. For externally associated files, do our best: let the user find as many related files as possible when using history, without guaranteeing that all can be found. The hard constraint: it is allowed that something cannot be found; it is not allowed that a reference is wrong. Same as E1, leave an architecture that can cover full file retention, later turned on by the user for cost reasons. Independent review replaced the author’s “rows never delete” (B) with B′ (R41.2). Independent review also replaced “legal deletion leaves a tombstone row” and “envelope `:148-155` already covers this” (R40.3, defeated in R41.1).

**E3 (coverage binding).** The original question was how coverage binds in time and across portable export. E1 rewrote it into a three-level runtime switch. The author recommended a Thread-level append-only changelog on cost grounds, and the engineer had agreed. Two independent reviewers both bound the resolved setting per execution. The author then withdrew the Thread-level recommendation after noticing `turn.json` is already rewritten (R41.3). The remaining product question — whether a mid-Turn switch change interrupts capture — went to the engineer as R41.7 and was ruled in R42.

**E5 (cancelled versus unknown).** The original question was priority when authorization-withdrawal and effect-uncertainty are both true, plus a conflict between R38.2’s same-identity retry language and “retry opens a new Turn.” Independent Codex chose scheme 2: do not add `unknown` to Turn. The engineer’s `cancelled` ruling was left unchanged. Author language that called `Turn.status` a pure authorization state was withdrawn; it is execution lifecycle and terminal reason (R41.4).

**R42, three rulings on the leftovers of R41.7.** (1) Do not interrupt an already-started Turn. Reason, in the engineer’s terms: Turn execution is relatively short, so cutting capture mid-Turn does not lose much data. Authors merged R41.3 rules 3 and 4 into one: every capture-setting change takes effect at the next new Turn; a sealed Turn’s new attempt uses the new setting. Authors noted, as a reminder rather than an objection, that session-continuity still requires immediate interruption on security revocation; R42 answers the capture-switch question and does not amend that other owner. (2) The switch remains off by default. Authors recorded two consequences: off is the main first-ship path, so the binding is required on almost every Turn; under default configuration the fine-tuning floor in `note.md` is never met until a user turns the switch on and the collector exists. (3) Agree to change Core wording. The C1–C6 list at R42.4 was an author inventory; later review expanded and then re-scoped it. ## What was deliberately not done in this round, and why

**AgentSession uncertainty.** E5 scheme 2 is a Turn decision. `AgentSessionStatus` also lacks `unknown`, and several documents write `unknown` as an AgentSession result. Independent review treated that as a new design decision on another axis, with no owner ruling. [SCOPE-012] keeps the correction local. Sites whose subject is AgentSession were left untouched in the documentation correction (`968f5a4e`) and are not implementation work in `plan.md`.

**Unifying the two denial paths.** Policy-local deny writes Turn `cancelled` (`approval-routes.ts:601`). Worker-gate deny writes Turn `interrupted` (`approval-routes.ts:873-874`; `worker-control-records.ts:80-96`). Each path is self-consistent under its own owner. Unifying them would change a live mapping. R51.1 requires Core to state that `cancelled` is a lawful terminal and that which path writes which terminal belongs to the owning specification. The split is `findings.md` `WDC-FND-001`, with no accepted owner.

**Expiry producers.** Approval already declares `expired` / `superseded` / `withdrawn` (`packages/protocol/src/models/approval.ts:14-21`) and production does not write them as Approval statuses. R48.1(2) meaning — owning workflow may withdraw authorization; reasons live on an Item — is recorded. Installing timers, implicit transitions, or a closeout producer would collide with the current worker-gate owner rule that those protocol statuses have no accepted closeout producer and return `recovery_required`. That work belongs to the delayed-user-input line.

**`docs/product-vision.md`.** [DOC-018] requires the engineer to name that document. R42 and R49 authorized Core and specification changes, including creating a specification if needed, and did not name `product-vision.md`. Fail-closed: if a matching stale assertion is found there, it is a finding, not an edit.

**Step 3, indexing, and search acceleration.** Architecture and technology stack have not started. Indexing and search acceleration were out of scope from step 1. A rebuilt collector topology is an entrance to step 3, not a hidden first-ship collector.

**Full model I/O, `context.evicted` collection, and a ninth pending-request owner.** E1 defers full I/O behind a default-off switch. `context.evicted` has no producer; the slot stays and must not be described as collected. A ninth queue table would duplicate truth; delayed input extends existing owners and the existing Action Center projection.
