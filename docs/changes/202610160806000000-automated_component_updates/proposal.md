# Bounded Operator Component Driver

## Question And Sources

The coordinator requests the whole P29 feature. The existing Worker stage consumes separate successful NanoHost replacement evidence, but that producer is missing. The existing App composition's CLI also refuses without a concrete live identity adapter. A function that accepts asserted success records would leave the requested update path incomplete. The governing tension is between Release Management's accepted automated component stages and the earlier installed-replacement decision's explicit external-Agent procedure, unchanged installer and exclusion of a new updater or product update record.

## Proposed Boundary

Independent Astra scrutiny accepted this mechanical boundary with revisions recorded in the plan and external evidence. The supported path is one Linux/systemd posture and the fixed App-first sequence. Its protected current grant must bind a positive exact transitional-pair assessment; no alternate order is selected automatically. Reconcile the existing raw App machine binding and digest-based host binding through a fresh actual observation, without a new durable deployment registry. Successful NanoHost evidence requires final restored supervision and a new inspection of the same process; temporary Restart=no is never the accepted Worker baseline.

Implement an optional, explicitly invoked operator CLI and exported composition under `scripts/host-worker-update/`. It selects one retained authorized staging binding and immutable release, reads the current grant independently, reuses the App update composition and actual Worker prepare/activate owner, and supplies the missing stopped NanoHost replacement stage through the user's authorized host tools. The privileged host adapter executes a fixed bounded program through that operator transport; the request cannot choose commands, service names or destinations. It is not a NanoCore runtime SSH path, host daemon, fleet selector, installer mode or product update lifecycle.

The NanoHost stage verifies old and target archives through the existing attribution/verifier, runs the fresh target host check, observes exact identity and current impact, and takes exclusive maintenance ownership. Before vacating any fixed destination, it stops and proves the complete failure group absent and establishes the activation prevention required by the observed posture. It retains only differing old payloads with verified bytes and metadata, calls the unchanged target installer, verifies all target destinations and retained input observations, reloads a changed unit while inhibited, and starts once. A fresh nonce-bound inspection plus the public readiness bracket binds the running target executables, unit and fresh successor before a successful component record can admit Worker preparation. No epoch root is retired by ordinary replacement.

Where activation sources require persistent inhibition, use an operation-owned persistent drop-in outside the three installer destinations. The drop-in blocks activation until the complete verified set is established and disables automatic restart for the controlled start. Its removal restores only this operation's changes. A pre-existing or conflicting path refuses. The exact mechanism must pass an isolated systemd gate, including manager restart with a partial destination set, preservation of unrelated overrides, and changed-unit reload, before the CLI admits that posture. It is temporary maintenance custody already required by the owner, not a reusable product marker or automatic recovery authority.

Retain private evidence before each effect and separate App, NanoHost and Worker results. Recheck current grant, deployment binding, idle impact and the preceding component evidence at effect boundaries. A transport loss, contradiction, unknown operation or partial result stops dependent stages with fixed non-secret diagnostics. No automatic restore, data rollback, blind retry, reset, reenrollment or inferred success is provided. Recovery remains explicit inspection under the existing owners. Actual a1/a2 effects are excluded from this implementation task.

## Alternatives And Trade-Off

Keep the current function-only prototypes: less privileged code, but no executable whole feature and no NanoHost evidence producer. Automate only deployments with no activation source: smaller initial implementation, but the checker must positively establish that posture and refuse ordinary enabled deployments; it must not infer safety from a missing Install section. Build a persistent updater or installer replacement mode: rejected by the accepted owners and unnecessary for this bounded operator invocation.

The proposed driver has the largest safety burden at filesystem custody, activation prevention and unknown handoffs. It must reuse existing public schemas and verification helpers, not grow a second update authority or manufacture assessment from the release manifest. Qualification after carry-forward remains separately authorized retained-work execution, not a prerequisite that can be simulated by orchestration fixtures.

## Decisive Checks Before Production

Independent scrutiny must settle whether this mechanical operator adapter fits the existing accepted design or needs an owner decision. It must identify a smaller coherent path if one exists. Independent tests then derive old/target identity, drain/fence, grant revocation, partial install, inherited activation, changed-unit reload, unknown start and component-stop counterexamples from the owners. Real systemd proof runs only in an isolated test environment, never against the retained dev service or a1/a2. If that proof cannot be supplied, that activation posture remains unavailable; a mock cannot certify it.
