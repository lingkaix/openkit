# NanoCore Restart Reconnection Contraction

Type: change-plan

Status: verified

Started: 2026-07-16

Completed: 2026-07-16

Branch: `codex/self-improvement-loop-foundations`

## Intent

Allow the original surviving worker shim and task in an independently surviving stock OpenShell sandbox to reconnect after a NanoCore restart, continue the same durable lease and turn without duplicate launch, and close through the records and code paths that already own final status, evidence, workspace synchronization, backend cleanup, product turn state, lease state, and capacity.

## Landing Decision

Reset the slice to a deletion-first design. The restart requirement needs one bounded lease state and one exact adoption compare-and-set, not three recovery state machines.

The accepted minimum is:

- one random 32-byte process key generated by each shim process and retained only in that process's memory
- only the SHA-256 key hash bound to the lease by the sequence-zero heartbeat
- at least one accepted post-launch heartbeat before a lease is eligible for restart adoption
- exact durable lineage, exact next sequence, the raw reconnect key, and the unexpired lease deadline required for adoption
- one `awaiting-reconnect` recovery state with one preserved deadline
- one timeout compare-and-set that transfers the exact lease from awaiting adoption to cleanup ownership
- direct closeout through accepted final-status, backend-session, checkpoint, Agent Session, workspace, evidence, turn, lease, and capacity records
- the ordinary worker-control heartbeat route and the ordinary NanoCore listener
- stock OpenShell only, with no fork, patch, replacement Gateway, or private protocol

The Ed25519 challenge exchange, restart settlement workflow, settlement table, recovery-serving subsystem, boot-time recovery admission index, phase coordinator, and dedicated large test platform are rejected and removed. There is no compatibility path for those abandoned internal designs.

## Scope

- Replace the signed challenge contract with the per-process random key and durable key hash.
- Arm only eligible post-launch heartbeat-live leases for one bounded reconnect window during the normal pre-listen boot scan; a sequence-zero-only supervisor has not proved that child work launched and uses existing cleanup.
- Preserve the original lease, worker process, sandbox, backend session, Agent Session, checkpoint, materialization, workspace handoff, and capacity.
- Restore the exact existing OpenShell backend session as read-only for collection and cleanup; never prepare, create, upload, mutate provider state, launch, or register through a restored handle.
- Resume an already accepted `final_status` through the existing closeout path without another heartbeat.
- Fence timeout cleanup with one compare-and-set so adoption and cleanup cannot both win.
- Keep one deterministic NanoCore kill/restart L3 scenario and one thin A1 acceptance runner.
- Update every owning specification and the roadmap to this smaller contract.

## Non-Goals

- No second workflow engine, restart settlement record, phase ledger, generalized recovery framework, or recovery-specific HTTP application.
- No active-active NanoCore, distributed consensus, session migration, worker-process restart, inference-stream resumption, or multi-target failover.
- No protocol-version negotiation, compatibility registry, legacy adapter, or rollback path.
- No OpenShell fork, patch, private build, replacement Gateway, custom Gateway protocol, or TLS-verification bypass.
- No claim that a worker survives Cell recycle, sandbox destruction, host reboot, or an unverified network topology.
- No durable exactly-once guarantee for the ephemeral app-local turn event projection.

## Minimal Runtime Contract

1. Before readiness, the shim generates a random process key. Sequence zero sends only its hash. NanoCore binds the hash to the exact lease before worker-child launch; the first accepted post-launch heartbeat advances the durable sequence to at least one.
2. On boot, NanoCore creates the durable worker-control and backend runtime, then scans non-terminal leases. An accepted final status closes directly. An eligible survivor must have `lastWorkerSequence >= 1` and is compare-and-set to `awaiting-reconnect` with one deadline. A sequence-zero-only supervisor and every other ineligible case use existing cleanup.
3. NanoCore binds the ordinary listener once. The shim's existing bounded retry loop reaches the ordinary heartbeat route.
4. A reconnect heartbeat includes the raw memory-only key outside the canonical heartbeat fingerprint. NanoCore verifies its hash, complete lineage, exact next sequence, awaiting state, and deadline, then claims reconnect and applies the ordinary exact-next heartbeat update inside one database transaction.
5. At expiry, the existing scheduler lease-maintenance loop invokes cleanup; no reconnect-specific timer exists. Cleanup first compare-and-sets the exact awaiting lease to `needs-evidence` and clears the reconnect deadline. The loser of the adoption-versus-cleanup race performs no effect. Physical cleanup failure stays fenced with capacity held until the next boot.
6. The shim sends terminal status only after sealing runtime provenance and workspace-change publication, so it is the last durable-output barrier. Accepted status re-enters the existing executor closeout functions using the durable accepted timestamp. Matching durable writes replay as no-ops; conflicting identity or digest fails closed.
7. Capacity releases only after exact backend cleanup succeeds. Failure retains the physical owner identity and capacity.

## Explicit Compromises

The reconnect request relies on the trusted TLS or operator-managed SSH transport already required to protect the sandbox bearer token. There is no server-fresh application challenge or asymmetric signature. A transport observer who obtains both the bearer token and process key could race the original worker. If the deployment trust boundary later requires defense from that observer, add mTLS or another transport identity mechanism; do not recreate an OpenKit-specific challenge protocol by default.

Durable final-status, checkpoint, workspace, evidence, cleanup, lease, capacity, and read-model writes replay exactly. App-local turn events are an ephemeral projection and may be delivered at least once if NanoCore crashes a second time after durable closeout but before event projection finishes. Consumers must tolerate equivalent duplicate events. This compromise is preferable to a settlement workflow.

A final status accepted after reconnect triggers one asynchronous process-local closeout attempt. If that attempt fails and the worker does not replay, the accepted record and lease remain `releasing` with capacity held until the next boot retries the existing closeout path. Timeout cleanup similarly moves the lease to `needs-evidence` before physical effect; cleanup failure stays fenced until the next boot. These fail-closed gaps are accepted instead of adding durable retry stages or a settlement loop.

## Deletion Plan

- Delete `worker-control-recovery.ts`, `restart-settlement-flight.ts`, `worker-turn-settlements.ts`, the settlement schema, and every migration or export that exists only for them.
- Delete Ed25519 public-key, signature, challenge, signing-byte, current-boot challenge, and challenge-response schemas and handlers.
- Delete the dedicated startup module seam created only for restart tests.
- Delete the large NanoCore restart harness and replace it with one small deterministic process test.
- Delete the reconnect-specific recursive timeout and reuse the existing scheduler lease-maintenance interval as the single lease time owner.
- Reduce the A1 runner to environment preflight, start, one read-only post-launch heartbeat barrier with the sequence-zero key hash already bound, NanoCore kill/restart, same-lease completion checks, and exact Cell cleanup checks.
- Reuse the existing backend restore, final-status reader, turn executor closeout, workspace records, and scheduler lease helpers instead of adding wrapper owners.

The production-code review target is approximately one thousand net new lines for this requirement. It is a review budget, not a reason to remove trust-boundary validation or cleanup fencing. Any material excess must identify a required behavior that cannot reuse an existing owner.

## Execution Plan

2. Shim: land failing bounded-reconnect tests, then collapse heartbeat, poll, and final-status retry into one small shared outage loop.
3. NanoCore lease path: land failing exact adoption and timeout race tests, then add only the lease fields, scan, and CAS operations.
4. Direct closeout: land failing completed and non-completed final-status replay tests, then route both through existing executor and cleanup owners.
5. OpenShell: land failing exact read-only restore tests, then restore the existing session without launch capability and preserve official stock CLI/Gateway behavior.
6. Test contraction: delete the dedicated harness, retain one deterministic L3 and one thin A1 runner.
7. Documentation: align the owning specs, roadmap, package READMEs, test READMEs, and this record.
8. Verification: run L0-L3 locally, build the worker image directly on A1, reinstall the test server freely, run the real remote-Gateway acceptance, review the final diff for further deletion, and push the current branch.

## Risks And Stop Rules

- Stop if adoption can commit without the bound key hash, raw in-memory key, exact lineage, exact next sequence, unexpired deadline, or exact awaiting-state CAS.
- Stop if cleanup can race adoption without first moving the same lease to `needs-evidence` through compare-and-set.
- Stop if restart closeout requires copied domain state, a phase ledger, or a new workflow table.
- Stop if read-only restoration can prepare, create, upload, mutate provider state, launch, or register control.
- Stop if capacity can release before exact physical cleanup succeeds.
- Stop if implementation requires an OpenShell fork, patch, replacement artifact, private Gateway protocol, or compatibility branch.
- Stop and delete again if the deterministic L3 or A1 runner starts rebuilding a general-purpose test platform.
