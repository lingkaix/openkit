# CI Acceleration

## Intent Revision 1 — 2026-10-16

The engineer requested a complete full gate below ten minutes without reducing coverage. The coordinator assigned L-OPS to split the long NanoCore and Worker Shim Vitest executions, run independent static checks in parallel, preserve the required L0-L2, L3 and L4 aggregate names, retain exact-head reuse and every-main-push gating, and prove complete execution with two full branch runs. No publication or deployment is in scope. Landing uses the shared v2 protocol: review and full CI before the short guarded main window.

## Intent Revision 2 — 2026-10-16

The coordinator confirmed the account's 20-job concurrent limit and changed the priority to total runner job-minutes first, wall time second. Keep exact-commit reuse unchanged; the fast main-push gate reuses the exact tested commit after land.sh fast-forwards main. Do not permit reuse across commits or amend that reuse rule. Optimize repeated setup and caches, group short suites, split only the long NanoCore and Worker Shim suites, and do not execute product tests twice. Landing is accepted when the comparison shows lower total job-minutes and no coverage loss, even if wall time improves less than the original ten-minute goal. Retain the two full branch runs, all required aggregate names, exact-head semantics, and the every-main-push gate.

## Intent Revision 3 — 2026-10-16

The engineer approved express landing for ordinary changes while the shared hosted pool is saturated. The coordinator requires every main push to run complete verification, including L4 Web e2e. Keep the existing one-pending-head concurrency group and never cancel an in-progress main run. Release candidates and changes to workflows or release scripts still require exact-head full CI before landing. The release admission job set and registry dependency now require L4 as well; a missing, skipped, failed or duplicate L4 observation cannot admit a release.

## Checkpoint

The earlier merged-source trial 38907234062 failed `native_tls_handshake_progresses_after_partial_record_write` at the unchanged 15-second Node TLS peer startup bound, before production transport construction. Its unit summary was 379 passed, one failed and three declared ignores. The same NanoHost source passed the original-layout main run 38904580499. Main now owns this setting in the NanoHost package test command, so the workflow drops its redundant override. A shell-level regression proves that shard setup preserves inherited settings while the package still selects sequential harness execution. Every test, explicit in-case concurrency and all fixture/product deadlines remain unchanged. No retry or pass is inferred from the failed run.

Independent review found that the observer labels a complete main run `full`, while the original admission predicate allowed only `release-gate` on push. A composed observation-to-admission regression reproduced the refusal before correction. Admission now consumes the actual `full` label without relabeling evidence; required L4, exact source, attempt and job predicates remain mandatory.

NanoCore had 366 files and 6,823 cases; Worker Shim had 30 files and 1,093 cases. The later root Node suite had 1,344 passing cases and its separate Python suite had 88. Eight Worker Shim partitions keep its three long adapter files separate. Four NanoCore partitions cover its complete suite; their largest historical file-work sum is about 474 seconds. The coordinator's runner-minute priority supersedes that unmeasured 20-job method. The next trial uses two NanoCore partitions and two Worker Shim partitions, with the same grouped short suites and required whole-owner coverage merges. It has twelve execution jobs and two merges. Compared with the 20-job plan, it removes eight more execution environments and their repeated prerequisite builds; compared with the original implementation it also removes synchronous build-cache uploads. Longer individual execution is an accepted trade for less total runner work under the shared limit. Keep this method only if two full measurements show lower summed runner minutes and unchanged complete test inventories. The reuse rule remains exact-commit only.

The completed measurements reject the twelve-job method despite its first lower total. In run 38903387211, separate static jobs cost 854 seconds versus the classic same-source 347 seconds. The later failed trial cost 137.93 runner minutes even without its skipped coverage merges, so it establishes no repeatable cost reduction. Do not count that failure as a second successful trial.

The corrected method uses nine execution jobs and one required Worker Shim coverage merge. Static check, lint, typecheck and build share one environment and prepared outputs. NanoCore returns to the existing admitted complete-suite coverage command, with its original thresholds applied in that execution; no partial NanoCore coverage is admitted. Worker Shim retains its two partitions and mandatory original-threshold merge. Web, the seven smaller complete owners, both native groups and root/Python retain every previous test. This removes repeated setup and collection demonstrated by the named measurements. It is a scheduling correction within the unchanged complete-coverage owner, not a cross-commit reuse or threshold exception. Two complete successful final-method branch measurements and the exact-head gate remain required before landing.
