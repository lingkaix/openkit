# Persistent Live Acceptance

Use this recipe for ordinary L6 and Agent task/benchmark work against an explicitly authorized persistent internal deployment. [Persistent Deployment Acceptance](../specs/20260909-persistent_deployment_acceptance.md) owns the contract; [L6](../specs/20260529-l6_story_acceptance.md) owns Actor isolation and adjudication. Installation, cold-start, destructive recovery and containment qualification use their own recipes.

## Prepare Once, Observe Each Attempt

Choose the deployment through operator-supplied connection information. Use its normal installation procedure and current protected Provider configuration; do not invoke a fixture bring-up or teardown against it. For an initial source installation, use the existing toolchain and build commands; for an initial App-image installation, follow [Docker App Image](docker-app.md). Update a persistent deployment only to a published release. Record the actual checked-out commit plus dirty state or deployed image digest, not only a version label. Coordinate an upgrade with ongoing work and hold the selected build fixed during the attempt.

Use HTTPS or an explicitly authorized SSH loopback tunnel when remote access otherwise lacks a protected transport. The SSH alias comes from local operator configuration; keep ordinary host-key verification. A typical tunnel shape is `ssh -N -L <local-port>:127.0.0.1:<service-port> <alias>`; resolve the actual service port from the deployment rather than copying a fixture port. The tunnel is an operator tool, not a Skill capability or new service.

Connect the external Actor's MCP client to the deployment's configured HTTPS origin plus `/mcp` with its protected per-user static bearer header. Use [MCP connection guidance](../../skills/openkit-ops/references/nanocore-deployment-modes.en.md#administrator-cli-and-remote-mcp-access). An authorized administrator provisions the scenario credential through the existing Web or secret-safe operator procedure; never put it in prompts, argv, reports or committed files. Browser OAuth and refresh tokens are unavailable; clients without static-header support cannot run this release's external-agent path.

Read guide and discover the relevant contracts through search and describe. With appropriate authority, read diagnostics, NanoHost runtime-target and the required Workspace/Worker records. A reachable API, configured Provider or ready target is a precondition observation, not completed Worker evidence. Do not create a fresh Provider subscription merely to run another attempt. Administrator diagnosis and secret/archive delivery use the complete operations package and its CLI; they are separate from the ordinary user's MCP flow.

### Initial NanoHost Provisioning

The current pinned stock OpenShell Gateway may contact GHCR to obtain its Supervisor during startup, before Gateway health and NanoCore readiness. This accepted upstream dependency is separate from OpenKit's Worker-image provisioning; an already prepared Worker image does not prove that NanoHost can start offline. Diagnose the exact bootstrap failure and authorized host network access without bypassing TLS or changing the pinned release.

Install the configured binary/unit and enroll the configured identity/deployment pair into its safe credential sink before the first NanoHost service start. Then start the service and observe the normal authoritative connection, predecessor fence, readiness and fresh-empty gates; an empty Worker Image Store is valid. Supply the workload image before admitting work, using the local `nanohost image import <archive> <expected-digest>` command or the authorized connected image preparation operation. After local import, use the administrator CLI operations `worker-environment.prepare` and `worker-environment.activate` to admit the image and update the targeted Agent before submitting work; do not point Agents at the new image by editing their files directly. A bare `sha256:` reference reuses verified retained content without registry or build fallback. Local import and image maintenance do not start or restart NanoHost. A Core test-data reset invalidates old transport credentials even when their sink files remain; reenroll before starting NanoHost against the fresh Core.

The [NanoHost owner](../specs/20260802-nanohost_runtime_and_transport.md) preserves the first timestamp across an unresolved fence-to-ready interval. An expired interval remains failed through process restart; removing its marker is not a recovery operation. Preserve its bounded non-secret evidence and diagnose the original pre-expiry failure rather than repeatedly restarting the service.

When a complete installation retirement is explicitly authorized, use the owner's terminal decommission and exact-pair reinstall lifecycle. Stop the whole service group and prove the old Gateway, backend, sandboxes, networks and sockets absent before invoking Core decommission, because that API also removes raw credential slots. Verify revocation of every identity-owned token and the fenced connection. Import any non-secret failure evidence required after decommission into its existing durable owner before removing or archiving the retained NanoHost evidence location. Then dispose the entire retired installation's mutable roots, both credential slots and metadata, image store and evidence location. Check actual deployed paths and group ownership; service inactivity alone is not effect-absence proof. For the standard Linux layout the mutable roots include `/var/lib/openkit/nanohost`, `/run/openkit/nanohost`, and the configured image and evidence roots. Credential disposal removes both slot files and their companion metadata; a proven-empty configured credential directory may retain its inode, non-symlink placement, ownership and permissions. In particular, preserve that directory when a live NanoCore container bind-mounts it, because replacing its host path would strand the existing mount and redirect safe-sink writes into the old directory. Prove all four slot paths and any temporary entries absent before re-enrollment. A composed operator procedure is sufficient; the installer is not a complete uninstall command.

Reinstall only the exact retained identity/deployment pair, obtain a fresh safe-sink token, and then start once through ordinary readiness. Supply and verify the selected Worker image before admitting its workload. Keep the retired interval's failure separate from the new installation's observation. This is an authorized initial restoration or terminal maintenance operation, never ordinary per-story setup; App data, unrelated services and scenario evidence retain their own ownership.

## Pre-Release Execution Authority Cutover

This procedure requires the engineer’s explicit authorization for the selected fresh-root deployment and its protected enrollment handoff. Preserve the old Core root, configuration, credentials and non-secret evidence under their existing custody. Prevent new admission and stop old NanoCore and every starter. Stop the selected NanoHost effect domain, including Gateway, backend descendants and sibling Sandbox scopes, and prove actual process, cgroup, namespace, network and socket absence through the existing [administrator stop procedure](../../skills/openkit-ops/references/nanocore-operations.en.md). Service inactivity or a Core disconnect is insufficient; unrelated services and system Docker keep their owners.

Deploy the matched candidate against the selected fresh root through ordinary installation. Do not adopt the old execution baseline or restore old execution sessions. An old named-slot credential cannot authenticate without its old Core token records; enroll fresh credentials through the authorized safe-sink procedure while preserving protected old custody. Start once, verify predecessor fencing and fresh readiness, and retain exact source/artifact attribution before workload acceptance. This documentation authorizes no deployment, destruction, credential disposal or publication.

## Maintained Round Kit

For a catalog story run or a Worker-qualification case, use one fixed, parameterized public runner, `tests/support/release-round.mjs`, rather than copying or editing scripts per run. The maintained round kit refers to that runner with its private parameters and evidence. [Tests support guidance](../../tests/README.md) documents its exact subcommands and parameter fields. Follow that single entry point and its subcommands. Do not maintain a second interface here. The runner is a live-acceptance instrument under `tests/**`. [Verification Instruments](../verification-instruments.md#harness-admission) still governs admission before it decides a result. The repeatable runner and cookbook fulfill the persistent-acceptance requirement to repeat the procedure without reconstructing deployment scripts. The runner does not build an image or replace a container. Shared support is parameters, the evidence directory, story-owned browser preflight, actor provisioning, evidence collection, and cleanup.

Use a private parameter file per round, kept outside the repository or under ignored `temp/`. It holds every deployment-specific value and no secret value; secret values remain in the existing protected stores and channels. Validate parameters and current effect authority before acting. Create one new private evidence directory per round and never reuse it. Record UTC start/end and component attribution, and pin the runner's commit and digest and the private parameter-file digest in both evidence and the compact release row. Use only synthetic placeholders in examples; never publish a staging parameter file, host name, private path, Thread id or transcript.

The execution subcommands use protected operator channels and public product operations. Its summarize mode regenerates verdicts and the compact row solely from retained evidence without product effects, preserving incomplete coverage and original failures. No subcommand automatically retries a story, repairs the product or deployment, grants an approval, or publishes a release. An ambiguous mutation result stops dependent work for inspection. It is not submitted again to obtain a result. The stage manager never retries, repairs, or approves on the actor's behalf. An approval in a story is the actor's user action through a public surface. Keep the actor's persona and goal separate from outcome predicates and judge inputs.

Run four runtime groups concurrently within admitted capacity, with A to D sequential in each group's Thread, as described by [Worker qualification scheduling](release.md#scheduling-worker-qualification). Worker qualification is not a story and not a pre-tag round. Runner-generated verdicts use retained product records, with independent checks for every non-pass or undecidable row and any story-owned independent proof still required. Retain complete evidence privately and publish only neutral aliases, digests, and the [compact projection](../specs/20260829-release_management.md#compact-release-record). Correcting an evidence tool can permit re-adjudication of complete retained observations under the owner. It cannot create missing observations or turn a repair into the original run's pass.

## Release Update Projection

Use the release owner's [bounded deployment procedure](../specs/20260829-release_management.md#bounded-test-deployment-update). Supply one explicit authorized SSH alias or URL target; automation excludes production. Retain App, NanoHost, Worker, and qualification results independently. Verify exact identities and selected existing Workspace content with public reads. A failed, missing, or unknown component observation stops its dependent stage. Do not treat a warm image as fresh-epoch Worker acquisition evidence.

Stories 1 and 2 retain cycle/change cadence; stable promotion still needs story 2 on its exact prerelease. Mechanical update and Worker qualification do not supply an L6 verdict. Worker-only preparation has no browser prerequisite; browser stories retain theirs.

## Mode One: Work Inside OpenKit

Choose a small real user task with an output that can be checked independently, or a small task set with declared inputs and outcome checks. Create identifiable scenario state through public operations. Submit it through normal Task/Goal Mode to a real Worker; preserve returned Workspace/Thread/Turn ids and follow durable progress through public reads. A request accepted by the scheduler is not a completed workload.

Inspect the actual terminal result and meaningful output, then retrieve only the relevant Artifacts, Evidence, Audit and Usage. Store the report as ordinary evidence or an Artifact. Benchmark reports additionally identify input/check revisions, model/configuration, budget and sample count; do not claim improvement from a single noisy sample. An unavailable Worker remains an unmet mode-one observation, even if an internal chat reply works.

## Mode Two: External Agent Uses The Product

Start a fresh MCP-capable AgentSession outside the source checkout with the secure remote connection already available. Provide only the user persona and goal. Do not provide the outcome predicates, implementation guidance, the expected answer, or a fixed sequence of operations. Normal host instructions and public documentation are allowed. Keep engineering SSH tools out of the Actor's product flow; the Agent in a separate authorized operator phase, or another operator, can use them for diagnosis after the attempt.

For L6, select an admitted story under `tests/stories/`, preserve the prompt and relevant redacted observations, and have an independent Judge inspect the story and evidence. The Judge recomputes a deciding public fact. Apply the existing repeated-run admission rule when admitting or materially revising a story. Reuse the same deployment between repetitions; vary only scenario-owned names/inputs where necessary.

### Cursor CLI Host

The verified Cursor CLI entrypoint is `agent` (also installed as `cursor-agent`); the desktop `cursor` binary is a different entrypoint. Configure the host's supported Streamable HTTP MCP connection and protected per-user static header in a fresh directory. Start a new process with `--workspace <fresh-directory> --trust --model <model-id>` and supply only the persona and user goal. Do not resume a development session or add the source checkout. Select an available real model through the installed CLI; record its exact model id and CLI version with the attempt.

Supply the configured public origin plus `/mcp` and the protected bearer header through the actual Actor host's MCP configuration. A variable in a coordinator shell does not prove that a child inherited its credential configuration. Do not put a Token in launch arguments or the task prompt. Verify an actual authorized public read; credential configuration alone proves no usable connection.

Match the credential to the scenario. Ordinary Thread or Task work uses a Workspace-bound token with the necessary mutation posture; a normal user session provisions the Workspace and issues that token through supported APIs when needed. A currently usable presented `server-admin` bearer may also initiate Tasks across Workspaces; later governed effects revalidate that exact originating credential. A currently usable administrator credential is eligible under the administrator eligibility rule in [Core Permissions](../core/permissions.md). Preserve the operator endpoint store and configure the scenario credential separately in the Actor MCP host's protected per-user header setting. Retain only non-secret scope and binding metadata. Do not overwrite the admin store or broaden product authorization to repair a test precondition.

Record the exact MCP client/version, endpoint identity, served guide/build identity and protected configuration provenance without header values, alongside the exact deployment identity. Keep the story and judge inputs outside the Actor directory. Interactive terminal capture is sufficient when the host's headless print entrypoint stalls; that stall is a host/tool observation and supplies no product verdict. Apply the same prompt isolation and retain the actual interaction transcript. The independent Judge uses a different fresh process and receives the story plus the sealed observed evidence, then re-reads the deciding public record.

## Observe, Repair, Repeat

Use current public records first. Inspect optional telemetry only for the missing diagnostic question; telemetry absence does not override a proved product result. Preserve a collector or judge error and its inputs before correction. Complete retained evidence may be re-adjudicated without rerunning the product; missing observations cannot be reconstructed into a pass.

For a stock file Collector, inspect the configured rotation files as well as the current output file when correlating an earlier request. Retain only the deciding safe span fields and matching request-log identity in the attempt evidence before rotation expires them; the live file is not a full-boot archive.

If authorized SSH diagnosis identifies a repair, record the failure and perform the repair through the existing owner. A product upgrade or state repair starts a new attempt. Reduce a deterministic defect into its lowest sufficient regression rather than repeatedly expanding L6. Leave the deployment, Provider account and unrelated resources in place. Remove only attempt-owned temporary resources, and report cleanup failures separately.

Map the retained observations to the acceptance conditions of each relevant change plan. One run may support several conditions, but a successful deployment or unrelated workload cannot close an untested plan. Keep a short record of build, input/story, times, public ids, observed outcome, deciding evidence and remaining limitations; no new execution database is needed.
