# Identifier Cutover And Protected Accounts

Use this recipe for the explicit pre-stable identifier reset. [Core Protocol](../core/protocol.md#ids) owns the new identifier format. [Release Management](../specs/20260829-release_management.md#pre-stable-deployment-reset-and-protected-accounts) owns reset disclosure, exact scope, fencing and protected-account proof. [Pre-Stable Data Continuity](../decisions/20261014-pre_stable_data_continuity.md) sets the stable-release boundary. This recipe adds no reset service, compatibility reader, account conversion or automatic startup reset.

The engineer's P14 grant covers the development machine, staging and production for this one cutover. Do not request that same grant again. A live operator dispatch still identifies one exact deployment and its current OpenKit scope. The identifier lane performs only a synthetic dry run; it does not contact deployments, inspect real accounts, reset data or switch live ingress. A synthetic pass is not live account or release evidence.

## Inventory The Selected Scope

Keep the complete engineer-named account list and credentials in existing private operator custody. Repository and release evidence contains only designated and verified counts, pass/fail, exact non-secret artifact identities, evidence aliases and digests. Never copy personal identifiers, account addresses, secrets or credential locations into reports.

The private inventory binds the deployment, current and candidate published identities, the service and ingress owners, each retained data and runtime scope, protected accounts, current writer owners and excluded services. Resolve actual commands from that inventory and the existing installation and operator guides. No target default, guessed path, wildcard cleanup or host teardown is part of this recipe.

| Selected deployment | P14 boundary | Exclusions |
| --- | --- | --- |
| Development machine | Its explicitly selected OpenKit installation and runtime scope. | Source worktrees, other applications, system container services and unrelated data. |
| Staging | The selected OpenKit staging installation and its exact writer, data and runtime owners. | Navidrome, Blinko, Memos, Dokploy and every other non-OpenKit service. |
| Production | The selected OpenKit production installation under this one P14 grant. | Every non-OpenKit service. This grant does not extend ordinary automated updates or authorize future production resets. |

Before any source mutation, prove that every protected account is registered, active and usable through fresh public sign-in and its required current authority. Missing or contradictory inventory stops the selected deployment. Keep the working source available while preparing its replacement.

## Stage A Clean Candidate

1. Publish the incompatible-data disclosure before switch. Name the affected entity data, the reset disposition and the exact candidate release. State that predecessor IDs are not migrated, account rows are not converted, and predecessor Workspace continuity and rollback compatibility are not claimed.
2. Prepare a fresh isolated candidate OpenKit data and runtime scope with private pre-switch ingress. Do not mount a predecessor writable root or adopt a predecessor execution session. Retain authored configuration and secret custody under their existing owners; recreate typed bindings against new canonical owners instead of copying obsolete identity rows or making an alias reader.
3. Initialize the canonical local User only at a proved fresh local initialization boundary. Server mode creates no implicit local User. An initialized scope with missing or ambiguous User authority requires inspection, without a replacement allocation or reset inferred from startup failure.
4. Re-register the same protected login identities through existing public registration, bootstrap and administration surfaces, with operator-held credentials. New `usr`, `acct` and authentication record IDs are expected. Reissue the required administrator access records into existing private operator configuration. Do not copy, convert or directly import old account rows.
5. Through fresh public sign-in, verify each protected account against the candidate, including its required administrator operation and bounded new product work. Observe completed work and a successful public read of the new result. Sign-out, sign-in and candidate reopen must retain the newly registered canonical identity and access. Registration rows and health alone are insufficient.

If any candidate account or work check fails, retain the working source and candidate evidence. Do not switch, convert accounts, retry unknown effects or turn an administrative report into product success.

## Fence Writers And Switch

1. Complete candidate qualification and prove it idle. Close source admission through its existing maintenance owner and obtain current idle or closeout evidence. Account for ingress mutations, scheduler admissions, active and closing Turns, pending claims and captured calls, Gateway contacts, imports and exports, update work, Workers, NanoHost current and predecessor epochs, retained storage bindings and file writers.
2. Drain or fence each writer through its accepted owner. Service inactivity, a Core disconnect or a storage lock alone does not prove native predecessor absence. Unknown external effects, incomplete closeout, unproved fencing and retention or hold conflicts stop the selected deployment. Never replay an uncertain call to obtain a cleaner result.
3. Recheck the candidate identity, all protected-account observations and the excluded-service inventory. Candidate and predecessor must never share a writable retained root. Switch only the selected OpenKit service or ingress binding through its existing deployment owner to the already verified candidate. Keep predecessor data intact until post-switch qualification succeeds.
4. After switch, repeat every protected account's fresh sign-in, required administrator operation and bounded successful new work. Prove the active published candidate, canonical IDs, completed qualification closeout, no resumed predecessor writers and unchanged excluded services. Missing evidence prevents returning that deployment to ordinary use.
5. An unknown switch result requires inspection of that exact target and retained operation result. Do not repeat it blindly, move to another deployment or claim automatic rollback safety. The retained predecessor is an inspection and separately assessed recovery option; the new code does not read its discarded identifier format.

## Cleanup And Evidence

Only after successful switch and account proof may the scoped operator dispose of the inventoried predecessor OpenKit entity data and runtime leftovers, through their stopped and fenced owners. Proximity does not make authored secrets, unrelated data, held records or Worker evidence disposable. Retain current deployment data, designated access, protected secret custody and complete evidence. Cleanup failure leaves an explicit residual; it does not permit broader deletion or another reset.

Record an independent result for each deployment: exact installed candidate, public reset disclosure, designated and verified account counts, public access and new-work results, writer fences, exclusions, cleanup disposition and retained evidence digest. Close that result before moving to another deployment. Story 2 uses the published release and independent Actor and Judge rules; this procedure and its rehearsal replace no story verdict.

## Synthetic Dry Run

Use fresh local scratch scopes and invented account identities only. Exercise the real public registration and sign-in owners for an old synthetic installation and a clean candidate. Keep the old scope readable, register the same synthetic identities in the candidate under distinct canonical IDs, verify required access and new work, reopen the candidate and verify access again. Model source writer fencing and the selected ingress switch only within the scratch fixture. Never contact a deployment or reuse real account material.

The deciding observations are successful sign-in and product work for every synthetic account, stable candidate identities after reopen, distinct predecessor and candidate canonical IDs, unchanged predecessor observations after a deliberately failed candidate verification, no predecessor writable root in the candidate, and no modeled switch before complete candidate proof. Keep the source scope and evidence. Record synthetic counts, exact tested head, commands, results and limits in the lane evidence. This proves the procedure's local account and ordering seams; it proves no actual host fence, live account preservation, deployed image, release disclosure or production switch.
