# Identifier Derivation And Import Allocations

## Decision

Accept the P14 wave-2 allocating-owner declarations for boot AuditEvents, captured-execution PermissionDecisions, Task retrieval traces, and MCP, terminal-checkpoint and export CapabilityCalls. Admit their UUIDv5 kinds only with those exact producer declarations. Usage measurements retain independent UUIDv7 allocation and complete stored-measurement equivalence. No AgentSession, Knowledge source, VaultReference or VaultGrant UUIDv5 producer is accepted.

Accept independent UUIDv7 reminting for the ten ordinary portable import families under S51's existing invocation-local maps. Preserve every previously accepted derivation, graph-closure requirement, historical-authority boundary and filesystem/SQLite crash gap. Accept required immutable VaultGrant issuance provenance within the canonical grant. This field replaces grant-prefix origin inference without adding authority or a permission lifecycle. Preserve the separate Approval identity rule and Vault's existing use-time lineage predicate. Conversation-to-Task handoff retains its separate receiving Thread and sole outer command receipt. Imported history uses the remapped graph and imported-history verifier, not live command replay.

## Reason

Source: P14/wave2-derivation-packet.md, the independent Astra Consultant's AGREED WITH CONDITIONS verdict in P14/consultant-wave2.md, and the coordinator's Wave-2 derivation packet decision in P14/coordinator-decisions.md, all dated 2026-10-16 in the backlog-20261015 working record. The coordinator accepted all twelve conditions and the final item table under engineer delegation. These are new bounded owner decisions where the earlier identifier decisions required separate acceptance; deterministic code alone did not authorize them.

Exact existing run, request, package, checkpoint and export scope supplies stable call or evidence identity without a second association owner. Usage already has a separate equivalence lookup. The ten import families need consistent target owners within one verified graph, not ordinal reproduction between invocations. Canonical grant identifiers remove the old imported-origin prefix, so the existing grant must retain that denial fact explicitly. A UUID never proves current authority, publication success or permission to repeat an effect.

## Rejected Alternatives

- Adding usage derivations would duplicate the accepted measurement-equivalence mechanism.
- Blanket derived-kind admission would authorize producers without an allocating-owner declaration.
- Ordinal import names would add source-order identity constraints without an accepted need.
- Grant provenance inferred from UUID shape or defaulted when missing would lose the imported-grant denial.
- Re-running Approval at grant use would add a second use-time authority contrary to the Vault owner.
- Crash-atomic import and same-Thread handoff would change governing decisions; neither was accepted.

## Revisit When

Revisit if an accepted producer needs different immutable inputs, another family needs derivation, or the import owner needs durable replay. A new authority, recovery owner, crash-atomic promise or handoff topology requires separate acceptance. This decision authorizes no data reset, migration, old-ID reader, account conversion or loss of unreset data. Existing pre-stable reset authorization and later retained-data continuity remain separate.
