# Independent Control-Store Workers And Committed Load References

## Decision

Amend the [mixed-writer decision](20261020-control_store_mixed_writer_exception.md) only for worker placement, load references and measured-need qualification. Replace the single shared worker with a bounded pool: pin each Workspace database's worker-owned families to one worker, and give the server database's worker-owned families a separate worker. Main retains its other families, each family has one logical writer, Main busy wait is bounded at 5 ms, and there is no automatic retry. This is not one exclusive writer for every family in a database. The [Durable Execution And Control Store](../specs/20261019-durable_execution_and_control_store.md#write-and-space-budget) specification owns the rules.

Different Workspaces need no joint commit. Independent Sandboxes, AgentSessions and Threads within one Workspace need no common logical order. Shared invariants retain deciding SQL revision checks, and server-owned facts commit before dependent references. Group commit stays database-local. Use natural batching: at most one commit is in flight per Turn; arrivals enter the existing count/byte-bounded FIFO or receive explicit refusal. The next commit takes queued Items in order, one savepoint each. A failed Item refuses its Turn successors; acknowledgements follow outer FULL COMMIT in order. Execution single-flight and expected-revision checks remain unchanged. No K-deep commit pipeline is adopted.

Each durable content byte has one publishing owner and exactly one successful first-publication synchronization. For new native bodies first referenced by a worker batch, that database worker owns publication: synchronize the file cohort in parallel, synchronize each distinct changed directory once, then FULL COMMIT the references. Already durable objects are not re-synchronized. Existing unchanged ancestors and removal of private staging names add no sync. Creating a new directory still requires its changed parent entry to become durable. Extend the existing startup cleanup owner to abandoned native publication names; do not add a service or a durability ledger. This does not move unrelated file authorities or cold SQL families.

For high-frequency progress, commit the first change after idle immediately; subsequent progress commits are at least 100 ms apart, coalescing intervening changes without discarding retained records or bytes. Barriers flush their causal prefix and bypass this throttle. The existing 32-transition/5-ms group limit applies once work is eligible for writer batching; the progress throttle is an explicit upstream eligibility delay, not a hidden enlargement of that writer window. Every producer, including worker shim, NanoHost and Sandbox-side owners, retains data in its existing owner until NanoCore's durable acknowledgement and resends unacknowledged sequences idempotently. Existing NanoHost collection pending pairs and worker-volume transcripts are source retention, not new user-data authorities. No new NanoHost buffer, ledger or state family is introduced. Visible canonical progress means committed progress; there is no volatile publication path.

These changes are Level A: unchanged FULL-before-acknowledgement. A separate consent-gated STREAM early-acknowledgement option is not adopted and cannot qualify the reference profiles.

Keep activated admission/product families and the measured Artifact/Review/Material switch on their existing worker paths. Evaluation candidate sets remain a Main cold family. Their use as a qualification proxy does not justify migration. Authentication/Tokens, Vault, registry/membership, Channels, Knowledge/configuration/catalog and the other unmeasured cold families retain the exception.

Mixed qualification must exercise real effect submission, including CapabilityCall, PermissionDecision and required Audit through the actual effect-submission owner. Use a provisional ratio of one effect lifecycle per ten scheduled native transitions: 20 effect submissions/s at the 200/s native reference. A normal Worker MCP call publishes one terminal tool-call Item; ten percent effect-associated native traffic is a provisional workload choice, not measured production prevalence. The ratio also makes the Main effect dose four times the former 5/s proxy. Preserve required usage, completion and publication work. Count ledger mutations separately from native product progress, and do not count the same terminal Item twice. A missing or refused in-envelope effect dose cannot qualify a vacuous mixed arm.

Any Main family whose actual reference-profile write path causes main-loop p99 above 25 ms, fails the existing 10-ms Main BEGIN criterion, or breaks sibling isolation must move to its owning database worker as a measured need. Move the whole family with its original receipt and required Audit partitions, not only a convenient tested operation. CapabilityCall and PermissionDecision, with their required Audit, are the expected first candidates; the proxy measurements are not proof that those real families already failed. Audit partitions do not authorize moving unrelated Audit producers. Current authority must be rechecked at effect submission after awaited commits, and the call row must precede contact. The reference effect workload remains after migration, through the same domain owner, with actual writer placement verified.

The provisional profiles remain 200 committed native transitions/s in one Workspace using 40 Turns at 5/s, and 200/s per instance across four Workspaces at 50/s each. These are alternative distributions, not an 800/s entitlement. One Turn demonstrates 20 committed transitions/s through natural batching, with at most one commit in flight; queued Items are not concurrent commits. Each sibling must achieve 99% success during the specified saturation run. The twofold headroom requirement and safety criteria remain firm. This partially replaces the earlier single-worker arrangement and inherited 640-offered/s reference, not the mixed-writer decision as a whole. Its rejection of compulsory cold-family migration remains binding.

**Compatibility with future replication.** No replication implementation is proposed for v0.1.0. Asynchronous database/blob replication may be scoped per instance or per Workspace, including a future Turso/libSQL or Litestream-style backend. A replica must durably receive and verify a blob before exposing a referencing row; replication cannot invert the local content-before-reference rule. Checkpoint ownership must accommodate an external replicator's read position without exceeding the existing 32-MiB WAL bound. A lagging replica must catch up, resnapshot, or trigger bounded admission refusal rather than pin an unbounded WAL or silently lose required frames. Restore means exact reopen at an explicitly declared replicated durable cut, plus a missing-blob report and refusal of affected references; replica lag must not masquerade as the latest locally acknowledged state. Local acknowledgements remain after native-content durability and local FULL COMMIT, never after a remote round trip. Replication changes neither effect write-ahead nor producer retention until the local durable acknowledgement.

## Reason

Source: the engineer's 2026-10-23 direction, translated from Chinese, the adopted coordinator model, and the coordinator's scope and qualification corrections. Writes in different Workspaces, Sandboxes and AgentSessions have no strict general relationship and need not be synchronized together. State reference performance separately per NanoCore instance and per Workspace. Never relax durability. Independence does not authorize a NanoCore-wide writer migration, and a synthetic contender cannot decide which product family is hot.

R1160 reports final R1155 hot rates of 49.790, 44.380, 44.810 and 43.333/s, with exact reopen, no accepted loss and WAL bounds passing. The harness's `cold()` runs candidate-set creation in the primary Workspace, with its original receipt and an explicit qualification Audit dose. It is not a cold-sibling workload. The hot stream rotates through eleven actors: eight primary Turns and three sibling Turns. Those results establish neither per-sibling success nor an eight-Turn mean latency.

Final mixed cells have 1116/1080 Main commits from 1500 BEGIN attempts each, with 384/420 BUSY refusals. Their only Main mutation families are candidate sets, receipts and Audit. Main COMMIT maxima are 607.353/634.308 ms; mixed-1 BEGIN reaches 26.973 ms. The 654.833-ms maximum belongs to earlier R1069/R1074, whose mixed-1 BEGIN maximum is 7.417 ms. These observations demonstrate synchronous Main durability stalls, not a measured-need mandate to migrate the proxy. Main-loop p99 passed; the earlier mixed loop failures were p999 failures.

The actual Worker MCP submission path starts a durable CapabilityCall before contact, records policy decisions, checks current authority before dispatch, and records usage and terminal Audit through ordinary owners. Its ledger methods execute synchronous SQLite transactions; an `await` at a caller does not move synchronous work off Main. Therefore qualification must measure those owners rather than direct SQL or candidate-set stand-ins. Removing the only proxy writer from Main would otherwise produce a misleading pass without testing this product path.

R1070 describes the full immutable-publication and terminal-preparation path. R1087 warns that native-only synchronization arithmetic omits Main publication and SQL. The estimated 1060 syncs/s at 200 transitions/s would consume about 95% of the benchmark's 1121 fsync/s parallel capacity: there is no useful margin for effects, checkpoints or variability. Target an average of at most three sync operations per committed native transition, including the actual effect dose and all owners' synchronization. At 200/s that is 600 syncs/s, not proof of feasibility. The measured breakdown is a required reported observation; the numerical target is not another pass/fail gate. The existing committed-throughput and safety gates decide qualification.

The coordinator's `fsync-bench-dev-20261023.md` measured 11.7 ms per serial fsync, 1121 fsync/s at 16-way concurrency, 1129 objects/s for 32-file cohorts and 88 serial WAL-like commits/s on the reference btrfs/LUKS SSD. None certifies the augmented real-effect workload. Existing failed qualifications remain failed. A 100-ms progress cadence needs at least two Items per commit to sustain 20 Items/s; natural batching supplies that amortization without multiple in-flight commits for one Turn. K-deep pipelining cannot make one SQLite writer commit concurrently. MAIN should consider it only if a measured preparation bottleneck survives cohort publication and natural batching, and must justify the smallest necessary overlap.

At the checked revision, `ensureCanonicalDirectoryAsync` synchronizes the parent even when the directory already exists; `immutable-content.ts:161–162` calls it for both the mount and staging roots. The publisher also synchronizes after unlinking its temporary name. `discardAbandonedWorkspaceStaging`, called from startup, removes only Workspace `.staging`, not the publisher's hidden `.tmp` names. Extending that existing startup owner under writer exclusion is required work, not an already-implemented cleanup guarantee. Directory existence alone is not proof of a completed first publication after interruption.

The corrected static SQL count is 7 + 2 + 1 = 10 write sites in the capability ledger, permission decisions and Audit modules, not an implementation-line estimate or a mandate to migrate all three modules. Existing NanoHost pending-pair retention is a building block, not proof that every producer already satisfies the unified rule; baseline replacement and transcript cleanup/reconnection must preserve unacknowledged data.

The untrusted, read-only `earendil-works/pi` reference at `be14d9732` supplies structure only: [durable README](https://github.com/earendil-works/pi/blob/be14d9732/packages/durable/README.md) and [specification](https://github.com/earendil-works/pi/blob/be14d9732/packages/durable/docs/spec.md), invariants 2–3, effect sandwich at lines 2044–2052, and throttled coalescing at 3310–3325 and 3966–3972. Borrow committed visibility and intent–effect–outcome boundaries, not its SQLite WAL `synchronous=NORMAL`, truncation policy or effect retry policy. NORMAL may lose a committed intent on power loss after its external effect ran, violating OpenKit's write-ahead requirement.

Evidence: the R1160 report, R1074 summary, retained harness/instrument and per-cell JSON, R1070, R1087 and the benchmark in the redesign evidence directory; effect-submission, capability-ledger, permission-decision and Audit owners at origin/main c4cec848. These observations support the decision, not the public contract's operation.

## Rejected Alternatives

- Move candidate sets because the harness uses them. This teaches to the proxy and can remove all measured Main writes without correcting the real effect path.
- Compulsory migration of all cold families. No measured product path justifies that scope.
- Move only one operation or only an insert in a failing family. Other mutation paths would retain a second writer or the same blocking path.
- Move every receipt or Audit producer. Only the owning family's operation/scope partitions follow its complete tuple.
- Reduce the effect dose after refusal or migration. This makes qualification depend on the bottleneck it must detect.
- Keep the shared worker, use offers as committed capacity, weaken durability, acknowledge early, or add unbounded queues. These preserve coupling or remove headroom and safety.
- Add a thread per stored Workspace, a database per Thread, a durable pipeline ledger or a new effect scheduler. Existing owners, bounded workers, revisions and receipts suffice.
- Require four-deep/K-deep pipelining before natural batching is measured. Multiple queued Items do not require multiple in-flight commits; compare both mechanisms without treating the more complex one as the default.
- Add a NanoHost buffer to repair source retention, or make transport acceptance authorize producer deletion. Preserve existing source owners until the Core durable acknowledgement instead.
- Copy SQLite NORMAL or adopt STREAM early acknowledgement as a performance fix. Neither is part of Level A; the separate Level B option requires an explicit contract change and consent.

## Revisit When

Use the first real-effect native measurement and release-candidate deployment-host measurements to validate the provisional profiles and effect ratio. Attribute failures to actual Main families before a whole-family switch; preserve the same workload after it. Measure all synchronous writes in that owner, including required usage, rather than omit them. Unmeasured frequency, module co-location or a planned engine increment does not justify migration. A miss cannot waive the 200/s headroom floor, loop/BEGIN/isolation criteria, authority recheck, ordering or durability. Report synchronization counts and natural-batching versus pipelining ablations; a miss of the three-sync design target must be explained, not hidden by weakening a durability barrier.
