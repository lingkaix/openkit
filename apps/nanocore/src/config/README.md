# Configuration

This directory owns NanoCore-specific configuration discovery, loading, precedence, runtime snapshots, reload behavior, and configuration routes.

## Boundaries

- Keep environment, mode, bind-host, data-root, server, workspace, agent, and provider configuration loading here.
- Load Server resources and fallbacks, shared Workspace composition, and User preferences as distinct owners; resolve explicit selection, User, Workspace, then Server without treating Server supply as a Workspace ceiling.
- Keep `gateway.jsonc`, `internal-role-profiles.jsonc`, `providers/*.provider.jsonc`, `agents/*.agent.jsonc`, `workspaces/*/config/workspace.jsonc`, `workspaces/*/config/data-sources.jsonc`, `workspaces/*/catalog/catalog.json`, and `users/*/config/user.jsonc` distinct in snapshots and diagnostics.
- Workspace Agent pinning uses the registered Workspace file through `runtime.file-list`, `runtime.file-read`, `runtime.validate`, `runtime.file-update` and `runtime.reload`. Preserve unrelated bindings and update against the exact read revision. Persistence and loaded target availability are separate facts; a failed reload retains the prior target catalog. See the [pin prerequisite](../../../../docs/specs/20260831-unified_conversation_composer.md#workspace-pin-prerequisite); no separate pin store or dedicated Web control is implied.
- Accept only configuration that has a current runtime consumer; bind, CORS, public URL, sign-up, and gateway policy are startup-owned. Ignored optional Server, User, Workspace preference, data-source, Gateway, Provider, model-catalog, internal-role and Agent descriptive envelope keys produce located warnings through the existing loader, snapshot and file-validation diagnostics; environment variable names remain consumed settings; unknown authority-section keys and unsupported required features still fail closed.
- Cross-package contract schemas remain in their owning packages; this directory performs NanoCore-specific file I/O and runtime projection.
- Workspace snapshots preserve optional `assistant.resources.skillIds` without changing authored bytes. Selection changes use the existing Workspace reload classification for later runs; omission selects no installed Skills. The shared schema checks shape and duplicate IDs, while the configuration command and Assistant owners retain catalog-reference validation and exact per-run admission. Producer preparation must merge with those consumers before the selection is offered for use.
- `../agents/` and `../providers/` own resolved runtime concepts after loading, so configuration code must not introduce parallel registries.
- Secret values must remain behind explicit references or backend-private state and must not enter snapshots, diagnostics, or generated configuration.
- New Agent config templates must name the immutable image-owned Python environment under `/opt/openkit/venv`; writable user-created environments remain runtime data and are not default template authority.
- New Agent files created without supplied content select `openkit/worker-runtimes:dev` with the Codex adapter and its image pin `0.160.0`, prefer the `smart` logical tier, and allow `all` configured logical models; creation does not rewrite existing authored files.
- MCP catalog changes are session-scoped; stdio enablement requires deployment-admin. Catalog App API mutations reload the runtime snapshot and close Gateway sessions for that Workspace.
- A failed reload must not publish a partially updated runtime snapshot.
- `knowledge-base.ts` reads the immutable `defaultKnowledgeBaseId` from the existing Server, User or Workspace configuration. Explicit fresh Knowledge-scope initialization records it once; reads never allocate or repair a missing binding. Ordinary configuration edits cannot add, replace or remove it. Existing Notebook or Source storage with no binding requires recovery, not another ID.
- Reload failure diagnostics must redact the concrete data root. Accepted Workspace-name changes refresh the joined store projection immediately; session-scoped Agent changes apply to later composition, while startup-captured Provider changes remain restart-required.

## Verification

Run the focused loader, precedence, runtime snapshot, reload, file, and route tests affected by the change, followed by the package gates in the [NanoCore source guide](../README.md).

`administration-configuration.ts` projects existing Provider catalog metadata and Gateway logical-model bindings into immutable private candidate Artifacts. It preserves credential/endpoint/extension fields, validates source revisions and dependencies, and reuses the file service for application. Human application records a start Item before effects and an immutable outcome plus command receipt afterward; interrupted effects require inspection rather than automatic retry. Provider changes may remain restart-required. Policy candidate previews retain optional server-computed unobserved-Tool warnings in the digest-bound Artifact. Preparation adds the same text to its native validation plan and returns that transient plan with the proposal; apply preserves the proposal-time warning bytes even when observations change. Warning metadata is not part of the agent's Policy proposal input.

The administration schema advertises only editable fields and omits excluded credential carrier names, including impossible properties inherited from shared metadata validators. Admission still rejects those carriers. The general runtime-config editor catalog retains the complete authored contract, including explicit impossible exclusions; it is distinct from the narrowed administration schema.

`model-catalog.ts` validates known metadata in `config/model-catalog.jsonc`, strips descriptive additions with located warnings, and projects its exact vendor/native-ID entries beneath profile overlays, leaving both authored files unchanged. The runtime snapshot tracks the complete catalog, including unused entries, and retains active catalog and Provider metadata until restart. Generic file operations expose the `model-catalog` kind under the existing deployment-admin boundary.

The inert `server.jsonc.policy.workspaceApprovalModes` field is removed and refused. Workspace Assistant inspection settings remain inert after host retirement. Policy statements use their current owner and cannot reactivate host publication.

`server.jsonc.policy.workDataCapture` is the default-off work-data capture switch. Its resolved value is fixed at Turn admission, so a change is applied at the next Turn and never interrupts a running Turn; it does not require restart. Its positive-safe-integer `nativeLogMaxBytes` defaults to a combined 16 MiB per Turn for actual stderr/log sources. The AEP constructor selects that bound into `observability.evidence.nativeLogMaxBytes`; reload changes later selection, not an existing package. Native admission reads the exact named AEP, never live configuration or an invented historical default. No budget is added to the Turn capture binding, and transcript bytes are not charged to the log bound. The receiver/contract prerequisite leaves capture OFF and activates no producer.

## Public Native Environment

`agent-native-environment.ts` derives the administrator view from confirmed image settlements, the existing Agent file revision, the live configuration snapshot and audience-checked AgentSession bindings. Updates use `RuntimeConfigFileService.updateFile` CAS and safe reload; failed reload keeps the previous snapshot. Native application is pending until exact native-start acknowledgement, and uncertain or cleanup-unproved bindings expose unknown state without applied values.

Gateway reload warns for unavailable authored members without rejecting their logical IDs. Invalid thresholds remain blocking. Account integrity failures make only the bound members unavailable, while the account owner retains strict integrity errors. Pre-owner boot snapshots do not evaluate subscription availability. Unknown additive keys inside `logicalModels[*].routing` are stripped and receive located warnings through snapshot and file validation; `autoFailover` must be a boolean when routing is present.

Provider and extension `reasoning_options` use the shared strict metadata schema. The existing leaf overlay replaces option arrays, preserving explicit empty arrays and restoring extension inheritance when a profile leaf is removed. Safe reload retains active options until restart; invalid candidates retain the last-known-good metadata.

`RuntimeConfigFileService.deleteFile` removes only an exact Provider profile under the same containment and revision checks as writes. Its deployment-admin DELETE command requires a non-null existing revision. Key profiles revoke their exact server Vault key through the provider credential owner before unlinking; subscription profiles leave shared account slots untouched. Failed effects are reported without rollback or replay. References remain authored, safe reload retains the active registry with pending restart, and strict reload rejects the restart-required candidate.

`runtime-config-operation-implementations.ts` exports the dependency-built exact implementation map for the ten runtime operations. Native file, environment and reload owners retain their lifecycle and effect checks; the family classifies known file failures as transport-neutral `OperationError`. Shared operation composition supplies the same map to JSON and remote MCP.

Provider and model-catalog loaders accept the existing unknown-key warning sink so runtime composition records source locations before metadata inheritance. These warnings are configuration diagnostics rather than blocked Provider readiness. File validation reuses the same key collector, strips additions from effective values, and preserves authored bytes through existing revision-checked editing. Agent workspace, Sandbox, MCP and credential authority remain closed; the complete owner classification is linked from the shared config package guide.

The generated Agent example opts only its npm read-only REST grant into `allowEncodedSlash: true`, matching the copy-on-init templates. Shared manifest validation owns eligibility; creating or reloading configuration does not edit existing manifests.

`RuntimeConfigFileService.createFile` and `updateFile` refuse unsupported work-slot source selections before atomic storage with `workspace_data_source_blocked`. An Agent write checks only its own selections against current authored catalogs; a catalog write checks every Agent's selections against prospective catalogs, including edits awaiting reload: matching references require at least one credential-free HTTPS Git entry, while missing references keep their late resolution refusal. The candidate replaces its current version. Inline inputs without a reference are refused only on Agent writes. Unselected catalog registration remains available. Load and reload preserve authored non-Git inputs and roots; their use keeps the late guard with the same supported-source explanation. Empty inputs remain valid. Run `runtime-config-materialization.test.ts`, `turn-workspace-context.test.ts`, `agent-environment.test.ts`, and `turn-routes.test.ts` for this boundary.

`server.jsonc.channels.discord` is startup-owned. Its public application identity and verification key authenticate the private interaction entry. Optional bot credential references use the existing environment resolver at message preparation; snapshots retain references only. Reload marks channel changes restart-required and retains the active values.

The default Provider file template allocates a canonical `vault` UUIDv7 candidate through Protocol and writes it into `secretRef`. Existing file reads, reload and rotation retain the complete recorded reference and do not derive it from the profile name.

`worker-git-read-correction.ts` resolves registered Server Agent sources without caller paths, preserves raw authored siblings and verifies the audience-checked terminal Git failure against its exact retained AgentSession/AEP and unique Git input. It admits only the existing explicit REST grant and repository Git-read baseline, preserving unrelated rules. `administration-configuration.ts` shares immutable candidates, command receipts and the sole CAS file writer between human application and finite private delegated application; the latter records a current loaded-Policy PermissionDecision and never fabricates human confirmation. Saved revisions and reload results remain separate. Successful reload of finite permissions in `policy.mediation` changes subsequent effects; invalid reload retains the prior loaded statements and validity.

NanoHost bind, identity, deployment, rendezvous and credential references are restart-required. Dry-run reports startup differences without changing transport authority. A real safe or strict reload that observes a changed startup field permanently fences the predecessor and rejects new NanoHost admission until App restart, including after a later file revert; strict rejection still preserves the loaded snapshot. Safe reload preserves the prior complete NanoHost stanza across addition or removal, and preserves changed startup children for an existing stanza. A capacity-only change keeps its existing live behavior. This rule does not rebind a listener, rotate a Token or restart a Runtime Epoch.

Authored Server, Workspace and Provider files require `schemaVersion: 1`. Native file boundaries check the shared retained-format header before decoding. The absent Server file still yields empty resolved settings without writing a file; logical Provider registry values omit the authored-file header. Fresh templates write v1 explicitly, and unmarked retained files are refused.

The typed `policy` administration target retains the shared collection under `server.jsonc.policy.mediation`. Proposal and apply use the existing private candidate Artifact, current deployment-admin admission, exact base revision, human confirmation and CAS writer. The native Policy owner derives statement versions and distinguishes saved content from the actual loaded admitted revision. Proposal and apply recheck current input Workspace authority for added or changed noninactive bindings. The candidate distinguishes supported passive observation narrowing from widening, while every change still requires human confirmation. Generic file updates refuse changes to this collection with `policy_write_required`; unrelated Server configuration keeps its existing path. Unsupported retained forms remain inactive. See the [Policy guide](../policy/README.md).

`runtime-config-operation-implementations.ts` requires the resource Policy Pending Request and distinct confirmation when the authored Workspace Policy subtree changes. Generic file create/update cannot remove or widen a managed boundary. An unchanged Policy subtree permits ordinary sibling edits; the confirmed command retains the existing CAS writer and validated reload lifecycle. Current audience checks and portable owner remint consume the same loaded common statement document.

Server finite Git maintenance constraints now live in permission statements at policy.mediation. Workspace Thread restrictions use workspace.policy.mediation with explicit managed-boundary statements and the existing required feature. Reload publishes the complete current document; removing the final permission leaves its boundary active. The retired workerGitReadMaintenance, resourceAccess and workspaceApprovalModes configuration fields have no reader. Native projections recheck current authors and recipients before effects; a saved document alone is not credential admission.

Local-mode App binds must remain loopback even when TLS material is configured. Bind resolution refuses a non-loopback environment or authored host before listener creation.
