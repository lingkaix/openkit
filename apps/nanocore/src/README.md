# NanoCore Source

This directory contains NanoCore's composition root and feature owners. `app.ts` mounts middleware and concrete feature registrars; complete product behavior belongs in the nearest cohesive route, runtime, storage, provider, policy, or workspace owner.

## Boundaries

`operation-invocation.ts` shares handler execution and logical output validation between public definitions and release-authored internal-only definitions. Private command bindings use the canonical `AssistantOperationInvocationContext`, current primary admission and a static exact-key retained handler join in `operation-composition.ts`. `skill.read` is omitted from every public table and projection. Its resource owner supplies the single schema/definition and model Tool projection; the engine contains no Skill dispatch. No binding is persisted or registered at runtime.

- Keep authentication and middleware order in `app.ts`; do not move product handlers back into the composition root.
- Keep one complete route lifecycle in one feature module when practical, and pass only concrete dependencies that the module cannot import from its real owner.
- `catalog/catalog-operations.ts` carries optional Vault credential bindings through the existing MCP update-binding operation, preserving them on omission and replacing them when supplied. The catalog owner validates the proposed effective entry before publication; malformed request bodies and invalid proposed bindings return JSON 400 `invalid_request`. Retained-record decoding failures keep the catalog operation's former 404 code and the phase-neutral fixed message "The record could not be processed." Output-schema validation belongs to `operation-invocation.ts` and returns HTTP 500 `invalid_operation_output`; validation does not undo committed effects.
- `api-errors.ts` owns `publishedErrorMessage` at the existing response and durable failure publishers. It bounds `SyntaxError` and Zod errors recursively through causes and cleanup aggregates before their retained input can enter public messages, while keeping authored errors and caller fallbacks. Request-body validation, sharing request detail, authored configuration warnings and operator process logs keep their existing diagnostics. Historical records are not rewritten.
- Keep protocol and App API schemas in their owning packages; NanoCore validates and executes those contracts rather than defining parallel DTOs.
- Keep runtime execution under `runtime/`, persistence and recovery under `storage/`, provider configuration under `providers/`, authentication under `auth/`, and secret material mechanics under `vault/`.
- Reuse `auth/thread-visibility.ts` after Workspace eligibility for Thread-derived reads and effects. A current usable administrator Web session or bearer receives administrator eligibility on active Workspaces without a manufactured membership; migrated private reads pass that eligibility into `isThreadVisible` through `isThreadIdVisible`. Read-only credentials stay read-only. Retained route guards and the Turn event stream keep the ordinary audience check until those routes are cut over. Conversation counts, attention, recovery lists, and generated presentations admit their current audience before dependent projection; generated presentations also preserve their source Item's audience by requiring a private destination with the same private owner for private Item sources, even for eligible administrators.
- Do not add controller, service, repository, façade, dependency-container, or compatibility layers unless they remove demonstrated complexity across multiple real consumers.

## Entry Points

- `app.ts` composes middleware, authentication, shared process state, and feature registrars.
- `remote-mcp-routes.ts` serves `openkit_search`, `openkit_describe`, `openkit_guide` and `openkit_call`, the supplied names for canonical `openkit.*` Operation Definition tools, through per-request stock Streamable HTTP transports after bearer admission in the existing auth middleware. Discovery and schemas derive from the composed tables, and `openkit_call` passes the canonical operation id into `operation-invocation.ts` directly. Closed binding and one-time-secret facts derive MCP result eligibility before dispatch; trusted entry assembly and immutable Worker supply still own authority. Request audit uses the existing server audit owner, keeps the Token id and `remote-mcp` channel in its redacted summary, and stores no arguments or results. The plain guide preserves product workflow and explicit human-decision guidance; the public Skill package is retired, and administrator operations use the generated `skills/openkit-ops/scripts/openkit` executable inside the operations Skill.
- `index.ts` owns process boot and shutdown.
- `http-server-options.ts` owns the shared App HTTP/HTTPS receive deadlines and advertised/physical idle timeout margin; the private native HTTP/2 listener has no idle-close timer. `http-server-options.test.ts` checks both listener families and reproduces an unread reused request during a blocked server event loop.
- `telemetry.ts` owns optional stock-SDK request spans and bounded exporter lifecycle; canonical work, audit and evidence remain with their existing owners.
- `openapi.ts` owns the explicit App API operation catalog and generated projection.
- `mode-entry-routes.ts` returns direct `task.start` and automatic Assistant Task handoffs at validated durable Turn admission, publishes the original receipt before responding, and retains worker database and scheduler ownership through independently observed completion. The worker invocation binds its checkpoint to the exact lease session before admission acknowledgement or executor entry. Live replay validates checkpoint context and scheduler input before the later initiating Item exists; terminal replay and receipt-first checkpoint deletion keep their full closeout proof. An App-local owner retains each original Task closeout promise through settlement, so terminal replay joins that same closeout before validating durable Task and cleanup evidence. A rejected execution observer permits failed-Turn replay only with the existing never-submitted proof and a checkpoint whose closeout has not started; a started closeout keeps its failure. Settlement removes the owner and leaves ordinary receipt-based recovery available. Existing `turn.read`, `thread.items`, dashboards, attention and exact replay expose completion.
- Direct `task.start` accepts optional exact `agentId`, narrows the existing eligible Coordinator candidates to that Agent, and refuses an unavailable selection before Knowledge preparation or admission effects. Candidates combine manifest readiness with the existing setup resolver using current Server, Workspace and initiating User configuration plus live Provider supply and the explicit requested model. The requested model takes precedence over configured preferences; an unavailable requested model, missing control binary or unsupported resources cannot appear ready. An incompatible exact-Agent model override retains its typed refusal. The canonical caller input is shared by checkpoint and command receipt hashing; an omitted selector preserves the existing hash. Replay returns the original admitted Agent before current selection or readiness is resolved.
- Task checkpoint maintenance classifies an exact sessionless queued admission as live waiting, without requiring an attempt or worker input Item. A preparation failure before AgentSession assignment closes only after its original initiating receipt, scheduler input/context, definite no-effect attempt and canonical failed Turn/event agree; the existing terminal checkpoint owner collects it. Exact `task.start` replay shares this proof before and after collection and returns HTTP 202 with the original failed Turn, without requiring an absent worker input Item or launching another worker. The shared proof rechecks the immutable admission input hash through `scheduler-records.ts` and consumes the native recovery owner's pre-effect predicate, so retained heartbeat, sequence, process or credential evidence prevents collection and replay. Missing or contradictory proof remains `recovery_required`. Run `pnpm --filter @openkit/nanocore exec vitest run src/mode-entry-routes.test.ts src/runtime/worker-turn-loop.test.ts src/runtime/scheduler-restart-recovery.test.ts --maxWorkers=2` for waiting, no-effect failure, replay and fail-closed recovery regressions.
- An assigned-Session checkpoint can finish the narrow never-submitted failed-start alternative after its original command and complete retained tuple agree and the adapter proves its exact cleaned anchor was unused. Maintenance and exact replay invoke the existing terminal owner, preserve terminal `failed` Session mapping and decided history, apply the original conversation status projection or direct Task receipt rule, and then collect the failed checkpoint. Execution-generated provenance is inapplicable only with that same proof. See the [runtime guide](runtime/README.md) and `src/runtime/worker-checkpoint-failed-start.test.ts`; Native maintenance keeps its checkpoint exclusion and D8 diagnostic.
- `mode-entry-routes.ts` keeps ordinary Assistant answers on current input and admitted context without ambient Workspace Knowledge pre-reads. Follow-up answers reconstruct ordered user and Assistant messages from the current Thread's canonical Items, including after restart; the current input is appended once. The explicitly selected Knowledge Manager target retains source-traceable retrieval and replay. Provider answers retain Turn-bound model capture. See [the Chat owner](../../../docs/specs/20260704-chat_mode_assistant.md) for the information-source contract.
- Active internal Chat provider work exposes explicit interrupt control to `turn-routes.ts`; HTTP disconnect does not stop that server work. Stop races the provider, persists the same Turn as `interrupted` with `provider_call_aborted`, and retains a submit receipt containing only its Turn pointer. Replay verifies the original actor and narrative lineage without redispatch. Request-derived provider Turn ids prevent redispatch when a required write fails; the existing-attempt check runs before target selection or result creation, so changed input cannot bypass it. Terminalization or receipt refusal returns `recovery_required`. Once both exact-Turn receipts prove complete publication, a fresh Stop retains the ordinary `turn_not_interruptible` conflict; the accepted Stop request still replays. Late provider results cannot publish an answer. Worker interruption retains its existing runtime admission and control checks.
- `*-routes.ts` files own cohesive public feature paths. Host repository routes and execution owners are removed; hosted writes use selected vendor MCP through the Gateway.
- `worker-mcp-routes.ts` dispatches the always-supplied `openkit-work` tools through its existing package admission and capability ledger. Its ledger-owned Item reconstruction is shared by boot backfill and read-only proof of already-decided additions during failed-start settlement. Selected MCP servers keep one Worker-visible schema per Turn through existing capability-call snapshot references, including after reconnect or restart. New Turns refresh tracking schemas; ordinary calls retain each live observation for approval re-evaluation while keeping the Worker's Turn selection, current credential checks and pinned drift refusal. Approval raising uses the Turn's retained schema without upstream contact. The [runtime guide](runtime/README.md) describes recovery, pending input requests and read-only same-Sandbox peer projections.
- `lib/store.ts` exposes the app-local product store while `storage/` owns durable record placement. After a Turn is a sealed terminal, `updateTurn`, `createItem`, `emitTurnEvent`, and `updateItem` admit only completion of an already-decided publication or a named field-limited display-projection refresh, judged by identity and content.
- A failed new Turn file operation drops only its invocation-created cache candidate and restores the prior Thread projection. It keeps source files and leaves the Workspace writable. An unrelated aggregate write does not delete retained Turn directories merely because the cache does not list them; explicit Thread and Workspace deletion still own history removal.

`operation-invocation.ts` is the transport-free engine for the shared operation-definition slice. `operation-composition.ts` explicitly composes inferred exact-key family maps and rejects duplicate ids; `operation-contract.ts` carries parsed/admitted context separately from stable dependencies. `operation-resolvers.ts` dispatches closed declared strategies with family-owned minimum-lineage readers; `operation-error.ts` supplies the sole classified error and safe field projector consumed by HTTP and both MCP framers. Unknown HTTP exceptions reach the app error handler. The shared JSON route sets `Cache-Control: no-store` for every response, including typed refusals, unclassified HTTP errors and bodyless 204 successes. Complete inputs are validated before request-store selection and independently at native admission through the same parser; failures expose only declared field names, never submitted values or unknown keys. The exact-key handler join adds executable bindings only; existing authorizers, mutation admission and domain effects remain their current owners. The Kernel owner resolves children inside the authorized Workspace and preserves its unavailable read entry or unavailable mutation error for missing authority; invocation does not preclassify child availability. `operation-json-routes.ts` and `openapi.ts` derive canonical JSON bindings for that slice, while the remaining operations retain their current projections. `operation-projections.test.ts` checks one invariant across HTTP, typed client, actual selected Worker MCP and CLI catalog execution, including wrong-child and missing-app owner outcomes and admitted Worker credential revocation.

The private administration entry provisions a current administrator bearer's own personal Workspace through `workspace-membership.ts`. A retained removed owner membership raises a nominal owner error and becomes the common HTTP 403 `workspace_access_denied` refusal with fixed `Workspace access denied.` text; remote MCP preserves the same semantic status and safe fields. The tombstone is never revived, and refusal precedes family execution, Thread creation and command receipts. First-use provisioning remains available, while unexpected provisioning failures escape unchanged to the shared error boundary.

## Supporting Directories

Native Light App mutations preserve actual executing Worker, Coordinator or trusted Assistant Thread/Turn identity in the existing app-local Audit fields. Direct human calls leave execution unknown; a presentation Item links the viewed content and does not identify the executor of a later click. The Kernel command assembler reads only trusted invocation lineage and checks the retained Workspace/Thread/Turn before mutation; caller payloads cannot supply this evidence.

Light App definitions carry one explicit `references` list for reusable meaning in exact pinned Knowledge page/raw or Skill targets. The shared Protocol URI codec validates identity; Kernel admission preserves it without granting access or copying target bodies. Authored omission becomes an empty list in canonical writer output, while retained definitions require the list. Purpose and descriptions remain labels. Native record operations do not depend on target availability. Knowledge resolution stays in the Knowledge owner, separate from app storage and current record authority.

- `capability/` owns capability-call and usage-ledger operations.
- `context/` owns LLM context projection and its projection policy.
- `diagnostics/` owns product-safe setup and runtime diagnostic projections.
- `knowledge-operations.ts` joins the two Knowledge definition tables to the existing domain owners without HTTP context. `createTaskKnowledgePreparation` owns the private Task entry and trace-only output; it shares public definition admission and retrieval without a private branch in the common engine. `knowledge-operation-projections.test.ts` exercises all 23 operations through real HTTP, client and CLI projections, readonly refusal, eligible administration, Source lineage, restricted content, retired routes and trusted Task preparation.
- `retrieval-knowledge-adapter.ts` admits current readable Knowledge pages, declares only title/description/tags/body as lexical fields, and verifies current source/audience facts. Knowledge Manager answer/preparation, direct Task selection and App Knowledge search share `index-rebuild.ts`'s asynchronous governed kernel pipeline. `knowledge-source-authority.ts` resolves existing publication and completed-work evidence; it grants no read authority. The Rust analyzer also owns deterministic answer sufficiency. Trusted operation assembly carries existing Thread/Turn context; direct User App calls without it publish no trace. Qualified pins and source-local results use the Core reference grammar. `storage/retrieval-traces.ts` is the sole live writer of immutable query-owned evidence, and current audience/source checks guard reads and export. Notebook editing, Git history and portable historical closure remain separate unimplemented requirements.
- `knowledge/` owns OKF validation, the Git notebook publisher and bounded Knowledge Manager query and maintenance adapters. Native `knowledge.ask` and Worker `knowledge_ask` use one model-backed role and retain the asker's query context. The separate role Turn owns model usage; the asking capability call retains delivered answer bytes. Fixed-base virtual editing uses the existing Proposal and Review owners. The existing recurring scanner supplies the daily trigger; `knowledgeMaintenance.schedule.enabled` defaults to false and grants no publication delegation.
- `policy/` adapts product approval gates and permission decisions while canonical authorization semantics remain in `@openkit/policy-kernel`.
- `docker/` contains source-adjacent contract tests for application and worker container assets.
- `test-support/` contains shared test fixtures only.
- `lib/` contains the existing app-local stores and simulator; do not expand it with new general helpers, and place new behavior with its concrete owner.

Setup composition in `app.ts`, conversation targets, and setup diagnostics forwards the existing credential-presence predicate and subscription-account owner to the Agent setup resolver. Public Turn operations, both direct App worker admissions and the boot scheduler retry service pass the same live owners through product admission and dispatch. These live references stay separate from configuration snapshots and public responses; setup adds no Provider probe, Vault material resolution, quota gate, or cached availability state. Managed Vault presence uses Core reference metadata; injected credential-material resolvers remain dispatch-only for Vault references. Non-Vault references retain the existing configured-supply fallback.
