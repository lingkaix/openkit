# External Channels

The Discord adapter projects the existing Pending Request response operations. It does not own requests, approval claims, effect execution, or outbound delivery records. Core composition supplies current actor, exact request, source, audience and native operation admission. A configured adapter requires a trusted public HTTPS App origin; an exact request link is returned only after current source admission. The owning rules are [Communication](../../../../docs/core/communication.md) and [Pending Requests](../../../../docs/specs/20260930-pending_requests.md).

`discord.ts` verifies Ed25519 signatures over the timestamp and raw body, checks a five-minute freshness window and application identity, and accepts commands only in a private bot DM. Pairing consumes a five-minute Core-issued challenge atomically and stores only its digest. Account revocation invalidates unused pairing challenges and remains available when the adapter is not configured. Pairing never retains administrator credentials. Core migrations create the four `discord_*` tables; constructing an adapter does not create tables.

An inspection returns the complete admitted effect or non-secret questions, their digest, and an expiring disclosure token. A direct answer or denial requires that token and the same current account binding, exact request lineage, content and authority. Content that cannot fit in one 2,000-character response requires the App. The adapter stores no captured arguments or answer content in inbound receipts. Identical duplicate events receive a bounded acknowledgement without dispatch or protected-content replay. Changed duplicate events conflict. Unfinished dispatch remains unknown after restart and is never automatically retried.

`discord_inbound_receipts` also owns capture origin. `discord_user_id` comes from the signed command envelope. An admitted denial or answer stamps `core_user_id`, `binding_revision`, `operation_id`, `workspace_id`, `thread_id`, `pending_request_id` and `turn_id` before `invoke`. The existing `request_id` joins the native command. A failed origin write prevents invocation. Input rejected before origin stamping retains only its signed external identity. Historical nulls stay unknown. A stamped origin proves no native acceptance or outcome. Duplicate input, restart, revocation and re-pairing do not relabel earlier responses. These facts identify the responder without changing requester or trigger attribution.

`discord-command.ts` exports `DISCORD_OPENKIT_COMMAND`, the global slash-command registration body for an existing guild-installed Discord bot. It restricts commands to bot DMs. Registration and endpoint configuration are operator actions outside this module. The supported commands are `/openkit pair challenge:<challenge>`, `/openkit inspect workspace:<id> thread:<id> request:<id>`, `/openkit answer workspace:<id> thread:<id> request:<id> disclosure:<token> answers:<JSON>`, and `/openkit deny` with the same selectors and disclosure. `/openkit approve` takes the request selectors and returns an authenticated request link, or the App home link when source access is unavailable. Grants require the complete App confirmation; the first direct allowlist contains only non-secret answers and approval denials. Answers use the existing Core map shape, for example `{"color":["blue"]}`. Obtain the challenge from the authenticated App and inspect the exact request before responding. The HTTP entry must return its truthful private in-progress message before Discord's three-second deadline if Core invocation is still running; it does not cancel or retry that invocation.

`discord-rest.ts` opens and verifies a private DM, checks current recipient eligibility again after credential and DM preparation, and sends fixed attention text containing only an absolute HTTPS App link. It suppresses mentions and link embeds. Token resolution is injected; raw credentials, transport errors and upstream bodies do not escape. A message acknowledgement must name the expected channel. Loss, timeout, a server failure or an invalid acknowledgement remains delivery-unknown. No automatic retry is implemented.

Run `pnpm --filter @openkit/nanocore exec vitest run src/channels src/storage/migrate.test.ts` for signature, pairing, revocation, disclosure, native operation projection, duplicate/restart and REST boundary coverage. Tests use generated keys, isolated real SQLite and fake fetch only. They make no Discord contact and prove no real-account or deployment acceptance.
