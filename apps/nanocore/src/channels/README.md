# External Channels

The App selects the admitted Communication owner and Kernel receipt adapter. A missing owner returns typed unavailability. Core credential operations remain available through their own owners.

Discord pairing bind/unbind writes the original channel, User, binding revision, actor and administrator-at-event facts under an IMMEDIATE communication-service transaction with the binding change. Unbind revokes the active binding and outstanding challenges. Relay the local immutable Audit fact to the kernel with the same event ID and full content. Repeat relay as exact read-back and expose relay lag. For an automation Pending Request, delivery, inspect and answer return only `OpenKit security: action needed within 24 hours.` and the App link. They create no disclosure and execute no channel answer.

Communication owns binding, challenge and disclosure stages. It commits the signed envelope before Kernel reservation. Denials and answers commit the full original Pending Request origin and hash of the exact native input before asking the Kernel to bind the effect. Each stage joins its covering FULL acknowledgment. A repeat can inspect the original outcome after restart. Neither an unresolved write nor a lost acknowledgment authorizes another dispatch. The private worker codec carries IDs, digests and receipt facts. Challenge secrets, disclosed content and answers stay out of the Communication journal and its worker frames.

The Discord adapter projects the existing Pending Request response operations. It does not own requests, approval claims, effect execution, or outbound delivery records. Core composition supplies current actor, exact request, source, audience and native operation admission. A configured adapter requires a trusted public HTTPS App origin; an exact request link is returned only after current source admission. The owning rules are [Communication](../../../../docs/core/communication.md) and [Pending Requests](../../../../docs/specs/20260930-pending_requests.md).

`discord-interaction.ts` verifies Ed25519 signatures over the timestamp and raw body, checks a five-minute freshness window and application identity, and accepts commands only in a private bot DM. Pairing consumes a five-minute challenge from the communication owner atomically and stores only its digest. Account revocation invalidates unused pairing challenges and remains available when the adapter is not configured. Pairing never retains administrator credentials. The communication journal owns `channel_account_bindings`, `channel_pairing_challenges` and `channel_disclosures`. The kernel owns the permanent `channel.inbound` command receipt in `idempotency_requests`. Constructing an adapter does not create tables.

An inspection returns the complete admitted effect or non-secret questions, their digest, and an expiring disclosure token. Automation security requests are App-only: delivery, inspect and refused answers use fixed deadline text and the App link, with no question disclosure token or response submission. A direct answer or denial requires that token and the same current account binding, exact request lineage, content and authority. Content that cannot fit in one 2,000-character response requires the App. The adapter stores no captured arguments or answer content in inbound events. Identical duplicate events receive a bounded acknowledgement without dispatch or protected-content replay. Changed duplicate events conflict. Unfinished dispatch remains unknown after restart and is never automatically retried.

Each inbound event has one permanent Kernel `channel.inbound` key. The original request ID derives from the deployment, source owner, verb and authenticated event coordinates. The Kernel compares the signed payload digest across principals. The Communication owner retains the signed Discord account reference and original envelope before resolving any binding. The account reference grants no authority. For a denial or answer, replay compares the complete retained origin and native input hash with the original Workspace decision. A conflicting event, changed origin or missing decision proof cannot dispatch again. A proved refusal remains definite after reopen. Discord data is retained by default. Governed deletion can remove the account reference while keeping the minimum replay proof, and expiry is opt-in.

`discord-command.ts` exports `DISCORD_OPENKIT_COMMAND`, the global slash-command registration body for an existing guild-installed Discord bot. It restricts commands to bot DMs. Registration and endpoint configuration are operator actions outside this module. The supported commands are `/openkit pair challenge:<challenge>`, `/openkit inspect workspace:<id> thread:<id> request:<id>`, `/openkit answer workspace:<id> thread:<id> request:<id> disclosure:<token> answers:<JSON>`, and `/openkit deny` with the same selectors and disclosure. `/openkit approve` takes the request selectors and returns an authenticated request link, or the App home link when source access is unavailable. Grants require the complete App confirmation; the first direct allowlist contains only non-secret answers and approval denials. Answers use the existing Core map shape, for example `{"color":["blue"]}`. Obtain the challenge from the authenticated App and inspect the exact request before responding. The HTTP entry must return its truthful private in-progress message before Discord's three-second deadline if Core invocation is still running; it does not cancel or retry that invocation.

`discord-rest.ts` opens and verifies a private DM, checks current recipient eligibility again after credential and DM preparation, and sends fixed attention text containing only an absolute HTTPS App link. It suppresses mentions and link embeds. Token resolution is injected; raw credentials, transport errors and upstream bodies do not escape. A message acknowledgement must name the expected channel. Loss, timeout, a server failure or an invalid acknowledgement remains delivery-unknown. No automatic retry is implemented.

Run `pnpm --filter @openkit/nanocore exec vitest run src/channels src/storage/migrate.test.ts` for signature, pairing, revocation, disclosure, native operation projection, duplicate/restart and REST boundary coverage. Tests use generated keys, isolated real SQLite and fake fetch only. They make no Discord contact and prove no real-account or deployment acceptance.

`discord-guild-gateway.ts` opens one Reports connection with `GUILDS` and `GUILD_MESSAGES`. It verifies the bot on `READY`, keeps Resume state in memory, and projects only eligible `MESSAGE_CREATE` events. `discord-group-mention.ts` preserves the exact addressed text and derives a receipt key and digest independent of the connection. The native receipt owner must recheck current binding and authority, resolve replays before rejecting stale unseen messages, and reserve before invoking work. These boundaries are fixture-tested and not wired into server startup.

Discord account pairing resolves an ordinary session-shaped actor without administrator credential projection, including in local mode. Recheck the current actor and the scope required by the operation. Match the exact current Pending Request for an operation acting on it, and verify disclosure digest and expiry when disclosure applies. Pairing never inherits an unpresented administrator Token.

## v0.2.0 Readiness And Acceptance

Bindings, Attention and retained delivery facts live at `server/services/communication/state.sqlite`. Stateful native route, cursor and message facts live at `server/extensions/discord/state.sqlite` when provisioned. Account pairing and unbind are in the reinstall acceptance. Reports and unfinished channel routes await qualification before enablement.

Attention starts after original Workspace publication acknowledgement, deduplicates by source and recipient, and takes its durable communication send claim before transport. Inspect the original receipt after restart. A lost acknowledgement stays unknown and grants no second send. Inject unavailable communication, lost Audit and send ACKs, stale restored binding behind kernel Audit, changed duplicate content and revoked disclosure. Verify kernel sign-in and token revocation, original event replay without a second effect, typed channel refusal and no protected response. See [Communication](../../../../docs/core/communication.md) and [Bootstrap And Readiness](../../../../docs/specs/20260704-nanocore_bootstrap_readiness.md).
