# Product Policy Bridge

This directory owns NanoCore's product Policy projection, authored Policy admission, I16 mediation and pending-request admission.

## Boundaries

- `permission-decisions.ts` maps policy-kernel outcomes into redacted, scope-owned decision and audit records.
- Configuration reload policy belongs in `packages/config-schema`; boot policy-kernel loading belongs in `../bootstrap/`.
- Keep subject, resource, and context summaries redacted and write them only to the database for their declared owner scope.

## Verification

Run `pnpm --filter @openkit/nanocore exec vitest run src/policy` and the affected route or workflow tests, then the NanoCore package gates.

See [Policy Enforcement Mapping](../../../../docs/specs/20260703-policy_enforcement_mapping.md).


The accepted design replaces the Turn-pausing approval gate and the closed-source-AgentSession actionability rule with a pending request whose captured call executes after grant; [Policy Enforcement Mapping](../../../../docs/specs/20260703-policy_enforcement_mapping.md) and [Pending Requests](../../../../docs/specs/20260930-pending_requests.md) own that rule.

Boot self-check decisions use independent canonical `pd` UUIDv7 identities. Their separate immutable boot/action correlation retains existing decisions and Audit across exact reopen/retry; ambiguity or missing linked evidence fails closed. Both decisions and their Audit publish within one Core SQLite transaction, without an external effect or a new boot lifecycle.

`worker-git-read-maintenance.ts` maps one loaded finite Server assignment and immutable effect facts into the existing NGAC evaluator. It owns no storage or identity lifecycle. Missing, invalid, duplicate, inactive, expired or out-of-scope assignments supply no association; Workspace fixed roles cannot grant this Server operation. The configuration command records the resulting immutable Server PermissionDecision and linked initiating-human Audit before dispatch.

`workspace-access.ts` projects one active-member association through the Policy Kernel for the closed Workspace operation set. Ownership, administrator eligibility, credential intersection, private audiences and owner-specific effects remain separate checks. No membership tier or access-changing command remains.

## Primary Admission

`server-access.ts` projects already-established User, Server and administrator Workspace eligibility into the existing NGAC evaluator using the current actor, exact admitted scope and registered operation/right mapping. `operation-resolvers.ts` consumes the User and Server decisions; the shared `auth/operation-authorizer.ts` consumes the Workspace decision after current credential and membership or administrator eligibility. Denials and evaluation failures stop the handler through the existing access-denial result. Ordinary admission remains transient; it adds no decision ledger or workflow. The exclusive actorless bootstrap-secret entry and finite delegated-maintenance assignment keep their existing owners. Named Workspace resource restrictions use the Workspace configuration owner described below.

Server targets may declare `family: administration | mcp | knowledge`; omission selects administration and unknown families deny. The current administrator maps to `ua:server-administrator`, and each selected family has its own object and object attribute under `pc:server`. Administration retains existing registered rights; MCP uses `api.call`; Knowledge uses its existing read, write, Review and Thread/Turn rights. These transient associations reuse `PolicyState`, `evaluateAccess` and `PolicyDecision`, with no saved assignment or operator setup. Native invocation performs the current credential read before the Kernel call: unexpected storage errors propagate to the error handler, while a Kernel deny or evaluation failure refuses admission. Server MCP operations declare their family in the shared table; prepared Server Knowledge registration remains with its operation owner.

## Unified Policy Slice

`statements.ts` validates the native subset, stamps real candidate authorship and derives exact content revisions. `configuration.ts` admits the typed Policy target through the existing human candidate, confirmation and sole file writer. The collection lives at `server.jsonc.policy.mediation`; its content digest is the Policy revision. Saved bytes, admitted bytes and the current loaded revision remain separate observations. Generic file updates cannot change the collection.

`interception.ts` runs bounded deterministic participation for I16 before credential preparation. Advice feeds gates and the actual mandatory Kernel. Current membership, Token lineage, binding author, audience, anchor and Policy changes invalidate the attempt. The existing captured Pending owner handles human escalation and re-evaluates the same logical proposal at response time. An allowing decision permits an attempt; it is not a Tool outcome. Completion observers cannot veto or replay the settled call.

`retained-records-v1.ts` owns frozen family decoders for PermissionDecision and Audit. SQL readers check `schema_version` with the shared Protocol helper before JSON decoding. Portable records carry `schemaVersion`. Unknown optional additions are ignored; required authority values fail closed. All native writers stamp version one explicitly; there is no default, converter or predecessor reader. Gate evidence shares the existing decision/Audit transaction. Only final combined allows consume finite statement uses in that Workspace transaction.

Bindings and invocation evidence retain operation/stage once. PermissionDecision owns its Policy revision in policySnapshotId, derives enforcementPoint from operation/stage and derives subjectSummary from mediation.subject. SQL stores no repeated point or subject summary for mediated rows, and portable records omit those projections. Policy candidate diff and classification are computed rather than retained. The Protocol v1 mode mapping fixes input/output contracts; independent selectors and replacement-v1 are absent. Active advice and transform require a future safe-output owner/reference and are refused now.

Goal-domain, agent-principal and storage-lease declarations follow the reset slice as additive behavior increments. The I16 agent gate subset below is the only active agent-principal consumer. The joined implementations below define their actual supported activation; the reset slice alone supplies none of those effects or automatic narrowing review.

`goal-domains.ts` exports `createGoalDomainPolicyService`, `GoalDomainPolicyService` and `GoalDomainStatement` for the Goal owner. Activation reads the jointly approved typed declaration from the existing Pending Request after the Goal transaction commits. It checks the actual deciding credential, current exact Plan, scope and lifetime, then publishes through existing Policy decision/Audit, configuration CAS and reload owners. Read rechecks that authority on each use; close withdraws the Goal's current statement without depending on the old credential or Plan. The current inactive statement prevents its old approval from reactivating it; no separate revocation ledger exists. Generic Server Policy candidates preserve these Goal-owned statements. The Goal producer, joint preview and Task admission joins must land with this additive family before it supplies product authority.

`goal-task-access.ts` exports `evaluateGoalTaskAccess` for the existing mandatory Kernel callback. Its native caller must first read the current admitted domain and restore the exact Task resources and actual agent subject from the scheduler/Worker lineage, plus the current Goal responsible human from the Goal owner. The approving statement author remains separate from that accountability identity. It projects Goal and Task scope into two policy classes and calls the existing Kernel; both associations and the existing current human/credential Kernel admission are required. Empty typed resources grant nothing. Its envelope flag is scope metadata, not permission or proof that no prohibition exists. Its authorization digest belongs in the existing currentness check. Current delegated permissions can add only the existing Task association. The approved Goal association and current human Kernel remain mandatory; this does not replace human approval or claim that runtime callers are joined.

`goal-task-policy.ts` joins the canonical native Task reader to current Goal-domain admission. Its `evaluateAdmission` takes the prepared Worker, Goal/Plan, responsible human and typed resources before a Worker Session exists. This checks selection bounds through the existing Kernel, grants no Tool effect and spends no use. `evaluateTask` instead restores the retained execution context and verifies the actual agent subject/process; null means an ordinary unlinked Task, while a linked missing domain denies. The caller keeps its live or captured-source guard and combines the returned revision with its existing credential/lineage revision.

The existing `PolicyInterception.finalKernel` callback accepts that current Goal/Task evaluation directly, or a plain Kernel decision for other callers. Only the missing Task association inside the admitted Goal with current human allow supplies a transient `escalation` destination for the domain's Coordinator. Human-only approval and participant failures keep their existing destinations. The final PermissionDecision retains the real Kernel deny, and blocked evaluations consume no uses. The Goal owner supplies routing and wake-up; the destination itself grants nothing and adds no retained format.

`GoalDomainPolicyService.administer` restores the live Coordinator separately from the affected canonical Task. It writes an ordinary permission through the same Policy CAS/reload and decision/Audit owners, with the Coordinator author and exact approved delegation reference. Scope and lifetime remain inside that domain, and the Coordinator cannot grant itself rights. `readPermissions` supplies only current native exceptions to the existing Task Policy class; the original Task request remains unchanged. Root replacement, closure and revoked credentials end child authority without deleting its evidence. The existing proposal shape retains the rationale and validation in the decision context; saved configuration and admitted authority remain distinct. No new retained field or store is added.

For finite Goal domains and selected delegated permissions, `evaluateTask.authorizationUses` feeds `PolicyInterception.decide` and its existing final PermissionDecision/Audit transaction. Denied or approval-required decisions consume nothing. The recorder checks the current limit atomically. After that same effect's last allowing use, `readTaskDecision` and the domain service's `readForDecision` recognize only its matching final decision, proposal/revisions and linked Audit; they recheck current Policy, Plan, credential and lifecycle facts without spending or granting another use. This is dispatch currentness, not a new-call authorization or replay mechanism. Runtime callers remain unjoined until their owner wires and verifies those boundaries.
## Named Workspace Resource Access

`workspace-resource-access.ts` projects current Workspace eligibility and exact resource allocations into the existing Kernel. A managed Thread adds a resource Policy class, including when its last positive association is gone; explicit prohibitions retain deny precedence. Agent invocation maps the actual process to its responsible User and receives only its exact Agent allocation, not another Agent or human allocation for that User. The current caller still owns credentials, membership, private audiences and trusted lineage.

`resource-policy-requests.ts` captures terms in existing Pending Requests without resolving the proposed target at creation. It checks current `workspace.configure` authority, requester responsibility, shared Thread identity, allocation targets and configuration revision before confirmed application through `RuntimeConfigFileService`. Approval alone changes no assignment; saved configuration and validated reload remain distinct. The shared authored-right vocabulary is `@openkit/config-schema` product-policy metadata; the Kernel remains product-independent.

The prepared R033 bridge now joins exact admission, current discovery and source audiences, existing human request review, and portable export/import. `resource-policy-operations.ts` supplies request and distinct confirmed apply handlers; the public operation table and native composition register both handlers together. Current requester revalidation uses the captured credential or exact Worker responsibility and current request-Thread rights, including Policy activation without a file revision change. The existing Pending Request closeout consumes that same current requester predicate. Runtime source and retained-storage joins use the live Policy and exact admitted Agent/process; they retain their existing lease and contributor checks. The public definitions derive the HTTP, CLI and eligible Agent Tool projections.

The generic runtime configuration operations refuse changes to the authored Workspace Policy subtree. Unchanged Policy survives ordinary sibling edits. The confirmed resource request calls the same CAS file owner directly; missing request lineage remains inspect-only on retry.

## Storage Lease Admission

`configuration.ts.readStorageLeaseAccess` projects a current admitted human-root permission into the existing `@openkit/storage` StorageAccess. The grant retains only Knowledge Base, mount, normalized relative prefix and mode. Subject stays in the statement scope; required lifetime.notAfter is the only stored expiry. Native configuration candidate/confirmation/CAS/reload and existing PermissionDecision/Audit own admission and withdrawal. No lease store or second evaluator exists.

The caller supplies current credential/Kernel admission, actual human subject, owner/Knowledge Base binding, loaded Policy and container currentness on every byte, scan or staging request. Absent, expired, withdrawn, out-of-scope or denied authority returns null; invalid Policy and dependency errors remain explicit. Current author authority comes from the actual local User or existing administrator Token resolution, never a fabricated local Actor for an arbitrary human. The first active subset uses exact Server/User/Workspace containers and no finite uses; agent and delegated leases stay inactive. Storage enforces its existing mount/prefix/mode/expiry boundary, and staged writes cannot read or overwrite originals or publish them. Source/runtime adoption remains a separate consumer join.

Native Server Git maintenance and Workspace Thread restrictions use the same Protocol Policy document. The finite maintenance bridge preserves the human, exact Agent, grant, endpoint, repository, binary and time tuple and rereads current Server author authority. Workspace restrictions use explicit managed-boundary statements and ordinary or exact Agent-process permissions; an empty permission set remains restricted. The native Thread subset activates only allow and prohibit; an active approval-condition permission is refused. The current Workspace reader fails closed if an active author loses authority. Confirmed Pending apply stamps the authenticated human author through the existing configuration CAS writer. Portable import remints Workspace and Thread containers and validates permission recipients without granting imported boundary authors rights. No legacy configuration reader or second grant store exists.

Kernel-backed permission records retain their matched association and prohibition IDs in the existing `contextSummary.kernelTrace`; existing decision readers and exports preserve that structural explanation. Their `policySnapshotId` identifies the actual evaluated Policy/configuration version; boot self-checks use the evaluated PolicyState digest. Gate records without a Kernel and unavailable evaluations omit the trace. This evidence changes no admission result, credential, Approval or Audit linkage. [Policy Enforcement Mapping](../../../../docs/specs/20260703-policy_enforcement_mapping.md#permissiondecision) owns the contract.

`agent-gate.ts` runs only an explicitly declared I16 agent gate through the existing bounded internal-agent loop, with the safe summary and one typed result Tool. `agent-gate-provider.ts` joins the existing logical Gateway, model capture and capability/usage owner within the actual admitted Turn; it creates no execution store or investigative Tool. `statements.ts` resolves the current finite responsibility chain and explicit agent domain through the existing Kernel before disclosure and before release. Human candidate preparation preserves creation attribution and requires exact completed shadow evidence before active publication. Agent gate decisions retain the actual approver and resolved human; final decisions retain the caller. Empty and deterministic paths preserve their exact SQL bytes and effects. Transform, advise and automatic Policy review remain unavailable. Goal delegation administration uses only the bounded native subset above.
