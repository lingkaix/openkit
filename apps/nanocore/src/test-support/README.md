# Test Support

This directory owns explicit reusable NanoCore test fixtures and no production behavior.

## Boundaries

- `store.ts` initializes the native Core schema before constructing a Store in an explicit fixture data root. Existing databases remain unchanged. The caller owns root cleanup and must close the native writer before removing or replacing database files.

- `native-task-admission.ts` shares one deterministic NanoHost peer over the configured native Task lifecycle. It retains separate gates and transcripts for actual Turns, serves the existing runtime between executions and observes original effect requests. The caller supplies Core and Demo owners, joins each entered execution and outer product closeout, restores the peer, and stops the native writer before disposing roots. Its optional configuration reader, acknowledged capability token, failed-final and required-export-loss controls use that same runtime; none grants Core completion or release. Tokens are never printed or persisted. The peer models one physical Sandbox slot and outside effects; it supplies no physical process or cleanup proof. Its `waitForStartup` join observes the original executor delivery-prove acknowledgement after peer acceptance; live MCP fixtures use it before assertions so setup does not race that native write. The shared `observeNativeTaskStartup` pass-through observer provides the same join to hand-driven native peers without admitting new work. Its `admitTurn` method joins real scheduler launch and acknowledged package readback after the caller publishes its pending Turn and receipt through the existing owner. It returns the actual attempt/package/execution and explicit completion/cleanup joins; callers retain scenario oracles and call cleanup before restore. The method requires the existing explicit runtime configuration reader and adds no phase control or default behavior. Native observation follows accepted `turn.start`; a definite pre-acceptance busy refusal retains unentered gates for a distinct attempt. Cleanup joins the entered invocation even when native acceptance was refused. For a Core-only restart, join all work, await the old fixture's `restore()`, stop its native writer, reopen Core and Store, and pass the same opaque `outside` value as the next fixture's fourth argument; this preserves peer facts without a second live controller or a new physical Epoch. Its optional `workspaceGitBaseline` constructor option carries a test-authored outside checkout HEAD/tree through the existing `session.open` result; Core still compares the report with the admitted AEP source before accepting a baseline. Its optional `peerFaults.closeRefusal` returns `cleanup_required` or `conflict` through the existing native result path and keeps its outside Session live; callers can clear the control after observing refusal for later cleanup.
- `execution-attempt.ts` establishes exact prepared Native attempt authority below the dispatcher from a caller-supplied authorized admission. It records an optional submission intent without inventing acceptance, a cleanup fence, or Workspace membership.
- `demo-store.ts` asynchronously creates an isolated `FsStore`, initializes absent fixture Core storage, and awaits Quick Chat and Demo Workspace publication. Callers await setup and close the native worker before deleting or replacing a persistent root. Its retained-personal fixture stops that writer and imports historical private Thread rows into a supplied unpublished project Workspace or the default Quick Chat Workspace through the canonical snapshot owner; it accepts explicit earlier private Thread names with the Timeline first, returns their exact identities and grants no current duplicate admission or historical command acknowledgement. Its default retains two Threads; callers which need only the Timeline supply that single name. An explicit `knowledge` collection selects authored Demo pages; omission retains the default page, while `[]` initializes an empty canonical Notebook through the same native import owner. Existing Workspace roots reopen without reseeding, and the fixture data input is not passed to the Store.
- `createRetainedDemoStore` in `demo-store.ts` builds explicit earlier Worker history in memory and cold-imports it through the real snapshot owner into a fresh unpublished Demo Workspace. Completed Turns with idle Sessions remain the default; callers can supply an explicit failed Turn/error and failed Session. It refuses an existing Workspace, grants no current execution, receipt or release authority, and retains exact Session/Thread/Turn/capture lineage. Callers record their original AEP and CapabilityCall through those owners before deliberate recovery faults.
- `workspace-source.ts` captures exact supplied fixture bytes through the actual shared Source publisher and current Notebook admission. The caller supplies an existing real User and Core/Workspace authority; the helper seeds no identity, membership, digest or malformed-input normalization.
- `notebook-import.ts` creates current canonical page bytes and explicit User attribution for synthetic Workspace import fixtures. Retained archive bytes still use the verified import owner; this fixture supplies no current authorization or Review decision.
- `git-repository.ts` seeds a writable Git repository with one resolvable HEAD commit.
- `agent-environment.ts` records deterministic production-shaped AEP snapshots for scheduler recovery fixtures. Requested workspace input ids use pinned, credential-free remote Git catalog sources supported by NanoHost; the fixture creates no host repository.
- `goal-intent.ts` creates a completed user Turn and initial objective Item so Goal fixtures bind a real `createdByItemId` and `currentIntentItemId` lineage.
- `goal-domain.ts` supplies an explicit synthetic typed domain for Plan proposal fixtures, without admitting Policy authority or replacing human approval.
- `app.ts` creates an app with an explicit Core-backed simulated executor and its same execution backend unless a test supplies another executor. Its explicit `createAppWithWorkspaceAuthority` fixture creates real temporary local identity and Workspace membership records for storage-only HTTP fixtures that exercise definition-derived operations, and closes those fixture databases after each test. Explicit databases and server authority remain caller-owned.
- Both app fixtures accept omitted options. Tests whose subject is file-backed configuration loading or reload supply an explicit `runtimeConfigManager` so synthetic Gateway and Provider defaults do not replace the authored initial snapshot.
- `workspace-sync.ts` records deterministic trusted input and materialization lineage for review fixtures.
- `mcp-stdio-stub.mjs` publishes a descendant-written PID, supervisor PID, and credential digest receipt so MCP process cleanup tests verify inherited credentials on supported POSIX hosts without external process-inspection tools. The server's parent is the gateway's detached supervisor and the inherited process-group leader.
- Its initialization-hang mode keeps stdin open while withholding protocol replies; an unresolved top-level Promise alone makes Node exit rather than simulate a live unresponsive server.
- `mcp-http-stub.ts` can hold its `delayed` tool response on a test-owned Promise; the test observes request ingress and releases the gate during cleanup to establish concurrency without a guessed delay.
- `knowledge-operation.ts` projects explicit test selectors and supplied request bytes to definition-derived routes. It supplies no Workspace authority, request identity, data or admission default; malformed bodies stay malformed.
- Fixtures must use production public paths where practical, stay deterministic, and avoid silently changing production defaults.
- Add shared helpers only when multiple tests repeat the same fixture knowledge.

## Verification

Before direct NanoCore runs, build its workspace dependencies, NanoCore itself, and `@openkit/retrieval-kernel`. CLI fixtures load compiled NanoCore modules, and retrieval fixtures spawn the local kernel binary.

Publish a canonical AgentSession before a native Turn names its id. Await dependent fixture writes and serialize writes to the same retained record. A native Pending Request publication already owns its supplied request Item; pass that Item to the owner instead of publishing it again.

`nanohost-native-tls-peer.ts` is the isolated peer for NanoHost's real TLS regression. It uses the native secure HTTP/2 factory from `src/index.ts`, production Token verification, admission, and durable readiness routes. It generates its own temporary CA, server key, and Token, and sends the credential only through the captured child pipe. The Rust caller owns process and temporary-file cleanup. Run `cargo test native_tls_` from `apps/nanohost` with the repository's pinned Node and OpenSSL available after installing workspace dependencies and building NanoCore's dependency packages.

Its CA-as-leaf mode reproduces a server certificate that Rustls rejects although some other TLS clients accept it. A bounded pipe query observes HTTP requests, Token presentation and durable target absence after certificate rejection. These observations remain fixture-local and supply no runtime authority.

Run the tests that consume the changed fixture and the NanoCore package test suite.

See [NanoCore README](../../README.md) for the package test model.

## Confirmed Synthetic Images

`recordTestNativeRuntimeTarget` records explicitly requested fresh Native target evidence for simulated consumer fixtures and leaves an existing target untouched. It grants no execution, cleanup or admission authority.

`native-environment.ts` explicitly confirms synthetic image defaults through the production settlement path for fixtures whose subject is another contract. `prepared-agent-environment.ts` resolves production AEP/metadata/compatibility against that fixture evidence and supplies explicit server-scoped default-off capture when unrelated consumer fixtures omit it. Explicit capture values remain unchanged. Missing/stale image and capture admission regressions call the production resolver directly. Historical image-effect fixtures may retain a package without the optional environment record; newly resolved packages always require confirmed evidence.

Simulated and metadata-only consumers may explicitly install `withTestPreparedNativeEnvironment` in their test module. It runs the production resolver with fixture-owned confirmed evidence and preserves capture, credential and scheduler checks. Fixture-only databases are removed after the test module; real production paths retain no automatic admission or empty-default fallback.

`operation-request.ts` exports `operationRequest`, the generic request helper, reused for Artifact, Task, conversation, attention and Pending Request, NanoHost and data-root administration selectors and caller-supplied request bytes on the derived HTTP path. It adds no authority, fixture data, request identity or admission default and leaves malformed bodies malformed.

The HTTP MCP fixture exposes server-observed header snapshots for exact bearer and raw-header replacement assertions. These observations contain only synthetic test canaries and stay fixture-local.

`recordTestAgentEnvironmentPackage` accepts an explicit Core database when the test exercises a storage or physical runtime consumer. Use the same Core owner as the Workspace and executor so the package retains that data root's deployment and admission facts; its standalone default remains for package-only fixtures.

`local-user.ts` explicitly seeds a canonical fixture User for tests that assert exact identity bytes, then invokes the production recorded-User owner. Local identity lifecycle tests use the production initializer directly. The fixture supplies no production default or alternate identifier mechanism.

`createAppWithLocalIdentity` supplies only the explicit local fixture identity when a test has no Core database. Tests of production runtime or configuration defaults use it without simulated-provider or environment injection. Existing Core and server authority remain caller-owned.

`entity-ids.ts` allocates shared-codec IDs once for process-local fixture keys. Setup and assertions share those exact allocations. It declares no owner derivation and supplies no cross-process replay authority; process-boundary tests pass the recorded IDs explicitly.

`mcp-tool-policy.ts` constructs explicit synthetic human Tool conditions for tests of the common Policy/Goal/agent pipeline. It neither admits production authority nor reads retired catalog permission lists.

`resource-policy.ts` builds explicit managed Thread Policy inputs. `writeManagedThreadPolicyFixture` authors that fixture in the existing Workspace configuration, preserves required features and authored siblings, and returns the original bytes for optional fixture restoration. Callers provide the current User, Workspace and Thread; the fixture grants no runtime admission or human confirmation.
