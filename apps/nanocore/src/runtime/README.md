# Runtime

Harness result acknowledgement retries retain the exact prior receipt while a successor operation is queued. An identical replay only returns the acknowledgement; it neither mutates the successor nor notifies its producer. Dispatching the successor clears the prior receipt, after which stale or changed results remain conflicts.

This directory owns accepted-turn execution, scheduler dispatch integration, worker lifecycle, runtime recovery, worker-control transport, context preparation, and runtime-specific App API feature paths.

## Boundaries

- Scheduler records and capacity transitions live in `../scheduler-records.ts`; runtime code consumes that owner instead of duplicating lease state.
- Product turn HTTP ownership lives in `../turn-routes.ts`; `product-turn-start.ts` owns scheduler admission and dispatch after route validation.
- `goal-planning.ts` retains immutable Plan authority and serializes draft requests per Goal. An explicit pre-approval revision uses `goal-plan-propose-tool.ts` and the existing Goal Orchestrator profile with only `goal.plan.propose`; a revision request does not change Goal status or clear the active-plan pointer, and a failed, cancelled, unchanged, or invalid proposal leaves the Goal at `awaiting_plan_approval` with that pointer intact, so the previous Plan is still approvable and a further revision instruction is still accepted. The propose Tool and durable Plan owner share the same approvability checks so rejected candidates receive model-visible correction feedback within the existing loop. Tool success validates a candidate only; it does not attest persistence or human approval.
- Workspace-root preparation lives in `turn-workspace-context.ts`; after Agent selection it resolves one credential-free HTTPS Git source and exact commit before scheduler admission. `scheduler-dispatch-loop.ts` selects the data-source and MCP catalogs by the dequeued entry's Workspace, derives its authored source references, projects no NanoCore host path or MCP topology into the AEP, and binds that exact context through preparation and launch.
- `agent-environment.ts` owns NanoCore-to-AEP projection. NanoHost is the sole production runtime target and consumes that immutable package through the fixed image, sandbox, bridge, import, and export effect vocabulary instead of a direct OpenShell CLI path. NanoCore strictly reparses and canonically serializes the AEP; after bridge readiness and exact AgentSession admission, it imports that package at `/openkit/sessions/<agent-session-id>/config/package.json`, then serially imports the sorted generated Context Package under `/openkit/sessions/<agent-session-id>/context/` before `turn.start`. AEP `agent.runtimeVersion` remains the unverified authored AgentManifest label, including the missing-value label `unversioned`; measured harness identity is the sandbox image digest copied as a value onto `agent_session_runtime_bindings` at new-binding and reuse time.
- Worker credential materialization in `agent-environment.ts` verifies available Vault health and exact Core/backend reference scope and version before writing injection records or sending material to a backend-private sink.
- `openshell-policy.ts` validates OpenKit-authored filesystem and network intent and projects one structured sandbox policy. The fixed baseline disables implicit WorkingDir access, grants the persistent `/workspace` and `/sandbox` data roots plus ephemeral `/openkit` and `/tmp/openkit-bootstrap` write access explicitly, and keeps immutable `/opt` read-only; NanoHost strictly parses that object into its current OpenShell SDK type before requesting the sandbox effect.
- Explicit `worker.runtime-provenance.v1` requirements project bounded raw-stream, manifest, and native-origin-index transcript outputs. NanoCore requests declared path-only exports only after accepted terminal status; NanoHost independently proves process-group absence before returning verified staged bytes to the existing canonical storage owners.
- Worker backends must make their declared `TurnExecutor.capabilities` truthful and reject unsupported operations before store mutation.
- Terminal Harness inspection waits for any admitted Codex stop operation, whether public interruption or an MCP human Gate, to settle before queuing `session.inspect`; an earlier accepted terminal status does not release that operation slot.
- Runtime-private sessions, host paths, credentials, raw worker payloads, and backend handles must not enter protocol events or public responses.
- Worker-control, inference, and selected-MCP capability traffic authenticate through three distinct live-memory route tokens. The scheduler lease stores only their separate lowercase SHA-256 projections, while the non-secret sandbox binding remains lineage rather than a credential; restart rebuilds hash-bound serving state without restoring a raw token.
- `nanohost-session-dispatch.ts` binds fixed session readiness, the eight runtime effects, and worker-control, inference, and selected-MCP capability HTTP semantics to one authoritative physical HTTP/2 connection. Private `POST /api/nanohost/transport/session/readiness` accepts exactly `{ "physicalEpoch": "<64 lowercase hexadecimal characters>" }` and returns empty `204` after projecting the authenticated coordinator witness and current readiness through the RuntimeTarget owner; admission remains `{}` and solely allocates connection generations. The same coordinator retains its witness across reconnects. Boot, allocation, close, revocation, and readiness loss clear current readiness and witness without erasing immutable backend-attempt or Sandbox origins. Unknown cleanup requires the recorded origin and a different fresh coordinator's authenticated readiness after complete predecessor fencing; timestamps and healthy reconnects do not prove physical absence. Restored result-only cleanup expectations carry the actual durable Sandbox origin, or the backend origin when no Sandbox exists; a different authenticated fresh Epoch retires those expectations as unknown without closing its connection or replaying cleanup. Same-Epoch expectations and origin-less Image Store settlements keep their existing unknown-outcome fence. Boot restoration may reconstruct inert Sandbox/Harness projections from their durable origins while readiness is absent, allowing the existing bounded Worker reconnect path to run after the listener starts. A known different current Epoch still refuses restoration; reconstruction grants no execution or reuse authority. Reconnect adoption also requires a live backend with completed workspace handoff and an exact origin match to the current ready, fresh and fenced RuntimeTarget before accepting the existing process-key and next-sequence proof; absent readiness keeps the existing reconnect requirement, while cleanup-owned backends remain refused. Effect polling and Sandbox publication recheck the originating witness, and the Harness timeout starts at enqueue without resetting on delivery. Bridge launch evidence is published only after the authenticated sequence-zero `starting` heartbeat, and an accepted bridge is monitored across connection successors without relaunch. See the owning [physical Epoch contract](../../../../docs/specs/20260802-nanohost_runtime_and_transport.md#physical-epoch-identity-and-recovery).
- `nanohost-runtime-target.ts` owns the durable configured target row and the redacted public readiness projection (`readConfiguredNanoHostRuntimeTargetStatus`) used by GET `/api/app/nanohost/runtime-target` and the administration `nanohost.runtime-target` Tool. The projection returns only identity, deployment, connection generation, predecessor-fenced, ready, fresh-empty, and observed-at; it never exposes physical Epoch, credentials, or host paths.
- `nanohost-session-dispatch.ts` retains the validated inline Dockerfile bytes, projects byte-free `image.build` metadata below the unchanged 512-KiB control ceiling, serves them once on private same-authoritative-ready-connection `POST /api/nanohost/transport/effects/image.build/input` through the existing single file-data reservation, removes them on settlement, and never refetches them for a successor.
- Workspace materialization records and backend handles bind the AEP package snapshot separately from the backend worker session id; terminal events, teardown, and stale-lease recovery correlate by package lineage, and review persistence rejects missing materialization lineage instead of inferring it from a change set.
- Accepted Worker `aborted` outcomes use the shared canonical mapping to Turn `interrupted` in live closeout and restart recovery; Task Mode separately projects that intentional stop as Task `cancelled`.
- Restart fencing permits a backend session with no nonterminal scheduler lease to pass the pre-listen scan. Ordinary scheduler recovery maintenance verifies lease-plan lineage before physical cleanup, retains shared capacity while any orphan in its pool is dirty, then atomically retires and audits every physically cleaned member and releases only their proved target and pool surplus; an unproved or separate fence remains intact.
- Recovery code must preserve workspace, thread, turn, request, package, and scheduler lineage before changing terminal state. The post-migration phase-8 checkpoint scan reopens only the existing Workspace database because the same boot already verified its complete layout.

`turn-executor-factory.ts` copies the measured sandbox image digest onto each AgentSession binding when it creates a Harness and again when it reuses an existing Sandbox, Harness, or binding. Surviving copies are keyed by binding id plus digest so a later new base image records a second identity instead of refusing the rebind. `turn-executor-factory.ts` retains process-local evidence when image acquisition, build, result validation or inspection fails, or a storage reservation transaction fully rolls back before Sandbox creation. Its live cleanup then completes without bridge/delete effects or result-only recovery expectations, preserving the ready NanoHost connection. The evidence is consumed by cleanup and cleared before a new materialization; it is never reconstructed after restart or used after a reservation commits, Sandbox creation is attempted, or a resident Sandbox is reused. Tag-only image references, including the authored `openkit/worker-codex:dev` template value, are rejected by NanoHost's immutable-reference validation. A usable image must be selected as a verified installed local digest with `pullPolicy: never`, an allowed exact registry digest, or an authorized bounded build; cleanup cannot invent a replacement image or retry the failed effect.

After proved whole-Sandbox writer cleanup, `turn-executor-factory.ts` retires stale runtime projections even if their storage association is missing. It reports the missing association without reconstructing or purging retained storage; fresh admission still inspects the image and reserves and attaches its own storage. Unknown cleanup continues to require the existing different fresh physical Epoch proof. Idle replacement also accepts coherently failed/draining/unknown residents after that proof, including converted `pre-witness` rows with no Harness or storage binding. Pins, active leases, busy Harnesses, and unsettled AgentSession bindings remain admission fences; replacement retires the exact old runtime projection before ordinary image inspection and storage attachment.

A live attempt that receives a successful `sandbox.create` result and then fails local validation or storage activation before the in-memory session is published keeps process-local proof of that create. Cleanup of that attempt sends the first `sandbox.delete` on the original physical Epoch and, only after that deletion is proved, releases the exact reserved association to idle. It does not register result-only expectations for a command this process never dispatched. A failed or unknown deletion, a changed reservation revision or generation, or a physical Epoch that is no longer current leaves the reservation in place and does not replay the delete. Restart drops the process-local proof and continues to use result-only recovery.

Result-only cleanup of an exact `cleanup-pending` backend with no in-memory session or durable Sandbox also releases its sole matching Worker storage reservation after definite writer cleanup. A non-null current Sandbox binding must match the durable backend Sandbox binding; a null pre-Sandbox reservation remains valid. The association keeps its identity, targets, attachment generation and contributor history while clearing the current attachment. The reservation is captured before awaiting cleanup, so ambiguous lineage, contradictory Sandbox ownership, failed or unknown cleanup, and a changed revision or generation cannot release it; sibling reservations and retained bytes remain untouched. The existing different fresh physical Epoch cleanup branch is unchanged.

## File Groups

- `worker-*-executor.ts`, `worker-*-backend.ts`, and `worker-*-gateway.ts` own governed worker execution and transport.
- `git-push-repository.ts` inspects only the authorized linked checkout with a scrubbed Git environment and command-scoped `safe.directory` for its canonical path; push execution uses an isolated temporary bare view and does not change linked checkout ownership or host Git configuration. An approved push to a missing target verifies the remote symbolic default HEAD as its outgoing-range base and uses an exact absence lease to create the branch.
- `workspace-review-git.ts` stages and applies approved changes with command-scoped trust of the canonical linked repository and its exact operation-owned detached worktree. Different container and checkout owners do not require `chown` or global Git trust; sibling repositories, hooks, filters and path escapes remain excluded.
- `nanohost-session-dispatch.ts` owns fixed-effect correlation, sensitive bridge-command disposal after acceptance, present raw file transfer validation, exact optional-absence JSON validation for the Workspace change manifest, and the two private semantic route projections on the authoritative NanoHost connection.
- `worker-runtime-provenance.ts` owns bounded capture verification, product-safe normalization, package-scoped gateway reconciliation, and portable index ref reminting.
- `nanohost-epoch-audit.ts` rejects private or secret-shaped references before projecting redacted epoch invalidation and readiness boundaries directly into the existing server-owned audit event store.
- `scheduler-*.ts` files coordinate dispatch and lease maintenance without owning scheduler persistence.
- `goal-*.ts` and `worker-recovery*.ts` own long-running work and recovery lifecycles.
- `idempotent-command.ts` owns process-local duplicate collapse and delegates durable command records to storage.
- `agent-environment.ts` owns the metadata-only pre-lease AEP and SessionCompatibilityKey projection and the full effect-owning AEP construction; scheduler and runtime owners use that projection for compatibility and one-Sandbox capacity admission, then revalidate before launch. Incompatible idle retirement drains existing bindings before exact private closure and physical deletion; cached reuse cannot bypass the durable drain state. Before classifying an idle binding missing from process-local inventory, exact current package keys and a ready same physical Epoch may rehydrate its existing Sandbox, Harness and attached storage. The ordinary native-handle, hygiene, lease and binding checks still decide reuse; missing or fenced storage remains an error. Bindings without that exact restoration proof require whole-Sandbox closure and deletion under the successor's admitted lease before Core predecessor retirement, unless a valid immutable origin and the accepted different-Epoch absence proof establish that the old physical Sandbox is gone. That proof retires only its exact old bindings and live references; it does not bypass durable cleanup ownership or retained-storage release. Same-process reuse and exact active-attempt restoration remain separate from this idle cleanup path. Explicit storage selection is authorized at its supplied revision before cleanup. Only the exact cleanup-owned release advances the immediate successor selection by one revision; dispatch carries that choice in memory without rewriting durable admission, and a competing storage change still fails compare-and-swap before Sandbox creation.
- MCP catalog supply remains non-executable metadata; exact selected supply enables only the fixed governed MCP route, while transport topology and Vault grant bindings never enter the AEP.
- `worker-mcp-gateway.ts` rejects entire upstream results containing resolved credential values or the URL-encoded query values it sends, before returning them to a Worker.
- MCP stdio sessions use Node's detached process groups; a private supervisor IPC channel reaps credential-bearing descendants if NanoCore dies, while explicit cleanup proves process-group absence before releasing session ownership.

`openkit-repository-mcp.ts` owns the two fixed repository MCP descriptors and dispatches to the existing in-process owners in `../repository-routes.ts`. The AEP carries explicit selected supply and its digest; current effective manifest selection and current `repo.push` authority are rechecked at the relay boundary. Domain failures return matching JSON text and structured content with `isError: true`; only unavailable host source commits use `git_push_source_unavailable` and review/apply guidance. Other inspection failures remain bounded repository errors.

`git-push-linkage.ts` collects known applied and staged review ids for every requested commit, including host-exempt pushes and repositories with linkage enforcement disabled. Exemption changes the missing-link refusal only; publication authority and durable audit ownership remain with the existing push executor.

## Verification

Run the nearest focused tests first, followed by NanoCore typecheck, lint, build, and the complete NanoCore test suite for runtime behavior changes. Governed-worker changes should also run worker-control, recovery, scheduler, and Server route coverage relevant to the changed lifecycle.

Environment preparation binds private authored-candidate lineage to image effects before dispatch. Preparation and ordinary Worker materialization make every reference available through `image.acquire` before `image.inspect`; canonical lowercase `sha256:` references with `pullPolicy: never` use that same effect for verified local-store import with no registry or build fallback. `worker-image-settlements.ts` owns the immutable Server SQLite outcome written before acknowledgment, independent of candidate visibility and current user credentials. Local persistence failure returns exact empty `503` and `recovery_required` to the caller while retaining result correlation; later explicit recovery reads the durable outcome without rebuilding or repeating local acquisition. These records grant no activation or readiness authority. Package planning and attachment reservation share the binding owner's work-slot resolver so sequential handoff retains the selected work directory.

Explicit selected storage is checked at the caller's revision before native AgentSession closure or resident Sandbox eviction, including when the selected ref differs from the resident ref. Compatible resident reuse still validates the chosen work slot against the planned package. An explicit fresh choice creates a separate retained association; an explicit handoff to another slot fences the old resident before reattachment. Only omitted choices continue the Thread's resident slot automatically. Shared contributor admission never substitutes a current revision for the caller's selection.

Independent-review admission conservatively rejects storage with ordinary-work contributors until adjudication targets can be proven by their server owner; caller-supplied exclusions cannot waive this guard. Goal child admissions refresh a retained-storage revision only when every contributor in the current attachment generation belongs to that same Goal and Thread.

Harness `turn.start` dependency refusals may include a closed `startupFailure` stage/reason pair. The runtime validates that pair before settlement and includes it in the existing error message, without accepting raw worker exception text. Only a validated `turn.start` refusal with `dependency_failed` and `workspace_materialization: retained_baseline_conflict` appends this guidance: “The retained checkout and requested commit differ; choose a fresh work environment for the requested commit, or restore the source configuration to the retained checkout’s original commit before reusing it.” This shared NanoCore Turn error reaches Web and Skill/API unchanged; the refusal and retained bytes remain intact, with no automatic reset, clean or reconciliation.

Failed worker closeout adds a fixed inference-stream diagnostic when the latest Gateway call for the exact Workspace, Thread, Turn, AgentSession and package snapshot failed with a known stream code. It reads the existing capability ledger, including during restored closeout, and does not project raw worker output or arbitrary error strings. A later successful inference call supersedes an earlier stream failure for this diagnostic; reconciliation of provenance bytes alone does not prove inference success.

A transcript or Workspace-change handoff failure before backend cleanup explicitly forbids retaining an otherwise reusable native AgentSession. Cleanup uses the same exact Harness `session.close` operation and requires closed state, absent child and absent private state before retiring its binding; successful closeout retains the existing reuse behavior. Failed or unknown close results keep the existing cleanup failure boundary.

A later separately authorized Task may retire one failed, interrupted, or closed Thread-affine predecessor identified by the exact Workspace and Thread native binding selector. Preview remains read-only; Core terminal history is not reopened. Fresh admission proceeds when that Thread currently has no native binding. A native inspect that labels the binding failed or closed without verified `session.close` does not free uniqueness. Active, foreign, unknown, and contradictory Thread bindings stay admission fences.
