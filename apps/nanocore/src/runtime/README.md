# Runtime

Ordinary post-listener `scheduler-restart-recovery.ts` maintenance finishes the [Worker Turn Reliability Envelope](../../../../docs/specs/20260531-worker_turn_reliability_envelope.md)'s terminal failed-start recovery predicate through `terminalizeGovernedWorkerTurn`. It requires the sole exact failed lease, matching product, admission, placement and package lineage, no checkpoint or accepted final status, no competing execution or contradictory runtime binding, and definite exact cleanup or positive unanchored pre-effect proof. Unknown outcome delivery remains `delivery-unknown` without resubmission; the Turn fails with `delivery_unknown`, or `worker_governance_turn_failed` otherwise. An existing typed failure and delivery proof remain authoritative. Later passes finish missing AgentSession and terminal events without rewriting the decided Turn. Missing or contradictory proof reports `recovery_required`; live and reconnecting attempts retain their owners. This does not change native `turn.interrupt` admission or release unrelated capacity fences.

`pending-request-flow.ts` contains initial Turn lookup, native delivery, and recovery bookkeeping failures for both detached outcome admission paths. Diagnostics name the Turn. A refusal whose bookkeeping fails is retried as a release and recorded with its refusal code; writable recovery of an unknown submission records `delivery-unknown` and a failed `delivery_unknown` Turn. A failure before submission leaves the frozen outcome and pending Turn for boot resume; unavailable storage leaves existing authority for ordinary recovery. Unknown submissions are never automatically retried.

`pending-requests.ts` owns one Workspace SQLite pending-request record for an approval or a user-input question. Raising a request does not change the raising Turn. A grant of a captured call re-evaluates, claims, and executes inside the approval response, and the outcome is published once on a later Turn of the same requester or on one Core-local closeout Turn written before archive.

`openkit-work-mcp.ts` supplies `work_request_input`, `work_list_peers`, and `work_read_peer` through the existing in-process MCP dispatcher and capability ledger. Peer handles are stateless HMACs scoped to the calling Turn and current runtime binding; no handle or peer map is retained. Each read resolves current same-Sandbox bindings and the responsible user's current Workspace and Thread access, preserving the originating admission's administrator bearer context through the existing authority owner. Recent Turns use the Thread dashboard's product schema and Items use the existing item-history schema, restricted to messages, plans, tool-call summaries, and status. Both lists page newest first with an offset cursor, default 20 and maximum 50 records per list, and the complete tool result retains the 512 KiB MCP limit. These tools read only Core product records and never invoke peer control or read native state. [Worker Agent Capability](../../../../docs/specs/20260703-worker_agent_capability.md#built-in-work-target) owns the contract.

Harness result acknowledgement retries retain the exact prior receipt while a successor operation is queued. An identical replay only returns the acknowledgement; it neither mutates the successor nor notifies its producer. Dispatching the successor clears the prior receipt, after which stale or changed results remain conflicts.

Successful Harness `session.close` proves the binding closed and its disposable private state absent. Host liveness is not the close proof: a shared host may remain running for siblings. The same transaction deletes the binding and releases that binding's open-session occupancy and, if it still names a current Turn, one active-Turn slot. Closing an idle sibling preserves another binding's active occupancy; a refused close other than `cleanup_required`, and an unknown close, release nothing. `cleanup_required` drains the Harness and, while the cleanup owner is still live, issues the first `bridge.close` and `sandbox.delete` when neither was dispatched; those successes release the binding's capacity, and a failure keeps the admission fence. Result-only recovery stays limited to a genuinely uncertain earlier dispatch. A binding whose terminal inspection reported `failed` without clean state keeps its Turn slot until that close, under the [shared-Sandbox lifecycle owner](../../../../docs/specs/20260802-nanohost_runtime_and_transport.md#shared-sandbox-harness-topology).

This directory owns accepted-turn execution, scheduler dispatch integration, worker lifecycle, runtime recovery, worker-control transport, context preparation, and runtime-specific App API feature paths.

`worker-mcp-gateway.ts` and `openkit-work-mcp.ts` share the oversized-result refusal message, which directs Workers to route bulk output through artifacts or the data plane. Upstream tool results retain the 512 KiB semantic limit and 1 MiB protocol envelope allowance; refused results are never truncated, as [Worker MCP Tool Supply](../../../../docs/specs/20260704-worker_mcp_tool_supply.md#routes-on-capabilitylocal) requires.

## Boundaries

- AEP LLM routes preserve optional complete effective `modelParameters` from the admitted setup. The producer copies no private Provider identity or current configuration lookup into this projection; incomplete or conflicting authored-route metadata stays absent, and the native adapter owns whether that absence prevents launch.
- Scheduler records and capacity transitions live in `../scheduler-records.ts`; runtime code consumes that owner instead of duplicating lease state.
- Scheduler recovery maintenance consults the shared worker executor's process-local lifecycle ownership before taking over a Turn. Ordinary execution and restored accepted-final-status closeout retain that ownership through cleanup and terminal publication, including failure handling, then release it on settlement. Cleanup state alone does not prove that the live owner has exited; after process loss the existing durable recovery rules still apply.
- Product turn HTTP ownership lives in `../turn-routes.ts`; `product-turn-start.ts` owns scheduler admission and dispatch after route validation.
- `goal-owner.ts` owns the ten Goal operations and their current intent, cards, immutable Plan versions, Task citations, shared decision consumption and dispositions.
- `goal-coordinator.ts` admits ordinary internal-agent Turns from the two-revision marker and derives its Goal Tools from the operation table; the existing `goal-orchestrator` configuration selects its model profile. A public Plan proposal captures its approval on a short ordinary Coordinator Turn without a model call; admission and terminal publication happen outside the Goal SQL transaction. Both approval surfaces call the Goal owner to check exact Plan eligibility before granting, and consumption rechecks it before claiming.
- `goal-task-admission.ts`, `task-admission.ts` and `task-terminal-fact.ts` retain ordinary Task ownership while reserving Goal citations and committing a minimal Task terminal fact with the Goal wake marker. Boot republishes committed terminal facts before considering open Goals.
- Workspace-root preparation lives in `turn-workspace-context.ts`; after Agent selection it resolves one credential-free HTTPS Git source and exact commit before scheduler admission. `scheduler-dispatch-loop.ts` selects the data-source and MCP catalogs by the dequeued entry's Workspace, derives its authored source references, projects no NanoCore host path or MCP topology into the AEP, and binds that exact context through preparation and launch.
- `agent-environment.ts` owns NanoCore-to-AEP projection. NanoHost is the sole production runtime target and consumes that immutable package through the fixed image, sandbox, bridge, import, and export effect vocabulary instead of a direct OpenShell CLI path. NanoCore strictly reparses and canonically serializes the AEP; after bridge readiness and exact AgentSession admission, it imports that package at `/openkit/sessions/<agent-session-id>/config/package.json`, then serially imports the sorted generated Context Package under `/openkit/sessions/<agent-session-id>/context/` before `turn.start`. AEP `agent.runtimeVersion` remains the unverified authored AgentManifest label, including the missing-value label `unversioned`; measured harness identity is the sandbox image digest copied as a value onto `agent_session_runtime_bindings` at new-binding and reuse time.
- Worker credential materialization in `agent-environment.ts` verifies available Vault health and exact Core/backend reference scope and version before writing injection records or sending material to a backend-private sink.
- `openshell-policy.ts` validates OpenKit-authored filesystem and network intent and projects one structured sandbox policy. The fixed baseline disables implicit WorkingDir access, grants the persistent `/workspace` and `/sandbox` data roots plus ephemeral `/openkit` and `/tmp/openkit-bootstrap` write access explicitly, and keeps immutable `/opt` read-only; NanoHost strictly parses that object into its current OpenShell SDK type before requesting the sandbox effect.
- The shipped Codex template requires trusted inference without the optional unsupported provenance extension. `worker-governance-turn-executor.ts` validates the complete AEP against backend capabilities before AgentSession creation, materialization, or launch; unsupported authored requirements raise `DeterministicAgentPreparationError` and are never silently removed. Explicit `worker.runtime-provenance.v1` requirements project bounded raw-stream, manifest, and native-origin-index transcript outputs. NanoCore requests declared path-only exports only after accepted terminal status; NanoHost independently proves process-group absence before returning verified staged bytes to the existing canonical storage owners.
- Worker backends must make their declared `TurnExecutor.capabilities` truthful and reject unsupported operations before store mutation.
- Terminal Harness inspection waits for an admitted private `turn.interrupt` to settle before queuing `session.inspect`; an earlier accepted terminal status does not release that operation slot. A successful interrupt records cancellation only: the Turn keeps its slot until a terminal inspection proves the clean barrier, or `session.close` proves release.
- The NanoHost backend requires the AgentSession recorder before it dispatches terminal `session.inspect`, and hands each agreeing ready proof it accepts, including a failed non-reusable binding, at `session.open` or at that inspection, to the recorder before any later import, native work, export, or close. A recording failure keeps the binding row. A crash between the SQLite binding commit and the AgentSession write can leave the proof only on that row until the exact binding is restored and its recorder is bound before cleanup; a restored binding hands over the proof its durable row holds when the recorder is bound. A successor resumes the pair of the Thread's latest-created other AgentSession, walking back past predecessors without proof to the pair they would have resumed, and equal creation times fail closed.
- A supply change, including an MCP-only change, stays outside SessionCompatibilityKey. No adapter declares that it lists its tools again at the next Turn, so every such change is a successor: when the admitted package's Harness compatibility key differs from the idle resident binding's key, the existing continuity close retires that binding and the successor AgentSession opens with the predecessor's recorded resume pair. Reuse of an existing binding requires the current desired package; a package-free inspection cannot prove unchanged supply. An unchanged supply reuses the same binding. The supply change is never applied by opening a second current binding on the Thread.
- Runtime-private sessions, host paths, credentials, raw worker payloads, and backend handles must not enter protocol events or public responses.
- Worker-control, inference, and selected-MCP capability traffic authenticate through three distinct live-memory route tokens. The scheduler lease stores only their separate lowercase SHA-256 projections, while the non-secret sandbox binding remains lineage rather than a credential; restart rebuilds hash-bound serving state without restoring a raw token.
- `nanohost-session-dispatch.ts` binds fixed session readiness, the eight runtime effects, and worker-control, inference, and selected-MCP capability HTTP semantics to one authoritative physical HTTP/2 connection. Private `POST /api/nanohost/transport/session/readiness` accepts exactly `{ "physicalEpoch": "<64 lowercase hexadecimal characters>" }` and returns empty `204` after projecting the authenticated coordinator witness and current readiness through the RuntimeTarget owner; admission remains `{}` and solely allocates connection generations. The same coordinator retains its witness across reconnects. Boot, allocation, close, revocation, and readiness loss clear current readiness and witness without erasing immutable backend-attempt or Sandbox origins. Unknown cleanup requires the recorded origin and a different fresh coordinator's authenticated readiness after complete predecessor fencing; timestamps and healthy reconnects do not prove physical absence. Restored result-only cleanup expectations carry the actual durable Sandbox origin, or the backend origin when no Sandbox exists; a different authenticated fresh Epoch retires those expectations as unknown without closing its connection or replaying cleanup. Same-Epoch expectations and origin-less Image Store settlements keep their existing unknown-outcome fence. Boot restoration may reconstruct inert Sandbox/Harness projections from their durable origins while readiness is absent, allowing the existing bounded Worker reconnect path to run after the listener starts. A known different current Epoch still refuses restoration; reconstruction grants no execution or reuse authority. Reconnect adoption also requires a live backend with completed workspace handoff and an exact origin match to the current ready, fresh and fenced RuntimeTarget before accepting the existing process-key and next-sequence proof; absent readiness keeps the existing reconnect requirement, while cleanup-owned backends remain refused. Effect polling and Sandbox publication recheck the originating witness, and the Harness timeout starts at enqueue without resetting on delivery. Bridge launch evidence is published only after the authenticated sequence-zero `starting` heartbeat, and an accepted bridge is monitored across connection successors without relaunch. See the owning [physical Epoch contract](../../../../docs/specs/20260802-nanohost_runtime_and_transport.md#physical-epoch-identity-and-recovery).
- `nanohost-runtime-target.ts` owns the durable configured target row and the redacted public readiness projection (`readConfiguredNanoHostRuntimeTargetStatus`) used by GET `/api/app/nanohost/runtime-target` and the administration `nanohost.runtime-target` Tool. The projection returns only identity, deployment, connection generation, predecessor-fenced, ready, fresh-empty, and observed-at; it never exposes physical Epoch, credentials, or host paths.
- `nanohost-session-dispatch.ts` retains the validated inline Dockerfile bytes, projects byte-free `image.build` metadata below the unchanged 512-KiB control ceiling, serves them once on private same-authoritative-ready-connection `POST /api/nanohost/transport/effects/image.build/input` through the existing single file-data reservation, removes them on settlement, and never refetches them for a successor.
- Workspace materialization records and backend handles bind the AEP package snapshot separately from the backend worker session id; terminal events, teardown, and stale-lease recovery correlate by package lineage, and review persistence rejects missing materialization lineage instead of inferring it from a change set.
- Accepted Worker `aborted` outcomes use the shared canonical mapping to Turn `interrupted` in live closeout and restart recovery; Task Mode separately projects that intentional stop as Task `cancelled`.
- Restart fencing permits a backend session with no nonterminal scheduler lease to pass the pre-listen scan. Ordinary scheduler recovery maintenance verifies lease-plan lineage before physical cleanup, retains shared capacity while any orphan in its pool is dirty, then atomically retires and audits every physically cleaned member and releases only their proved target and pool surplus; an unproved or separate fence remains intact.
- Recovery code must preserve workspace, thread, turn, request, package, and scheduler lineage before changing terminal state. The post-migration phase-8 checkpoint scan reopens only the existing Workspace database because the same boot already verified its complete layout.
- Failed Worker closeout preserves the latest exact inference call's `unsupported_gateway_feature` category in the Turn error, with fixed compatible-model guidance. A later successful call or a different package cannot supply that failure; raw provider and bridge text remain private.

`turn-executor-factory.ts` copies the measured sandbox image digest onto each AgentSession binding when it creates a Harness and again when it reuses an existing Sandbox, Harness, or binding. Surviving copies are keyed by binding id plus digest so a later new base image records a second identity instead of refusing the rebind. `turn-executor-factory.ts` retains process-local evidence when image acquisition, build, result validation or inspection fails, or a storage reservation transaction fully rolls back before Sandbox creation. Its live cleanup then completes without bridge/delete effects or result-only recovery expectations, preserving the ready NanoHost connection. The evidence is consumed by cleanup and cleared before a new materialization; it is never reconstructed after restart or used after a reservation commits, Sandbox creation is attempted, or a resident Sandbox is reused. Tag-only image references, including the authored `openkit/worker-codex:dev` template value, are rejected by NanoHost's immutable-reference validation. A usable image must be selected as a verified installed local digest with `pullPolicy: never`, an allowed exact registry digest, or an authorized bounded build; cleanup cannot invent a replacement image or retry the failed effect.

After proved whole-Sandbox writer cleanup, `turn-executor-factory.ts` retires stale runtime projections even if their storage association is missing. It reports the missing association without reconstructing or purging retained storage; fresh admission still inspects the image and reserves and attaches its own storage. Unknown cleanup continues to require the existing different fresh physical Epoch proof. Replacement retires old-Epoch residents regardless of their stale Sandbox, Harness or idle binding lifecycle and cleanup projections, including converted `pre-witness` rows with no Harness or storage binding. Queued and dispatched old Harness operations settle as unknown before their rows retire; absence never asserts that they succeeded. Pins, active-Turn occupancy, current Turn or lease references, and nonterminal scheduler leases remain admission fences for their existing owners to settle; same-Epoch admission checks remain strict. Replacement releases the exact retained-storage attachment through its existing revision and generation checks before ordinary image inspection and storage attachment.

A live attempt that receives a successful `sandbox.create` result and then fails local validation or storage activation before the in-memory session is published keeps process-local proof of that create. Cleanup of that attempt sends the first `sandbox.delete` on the original physical Epoch and, only after that deletion is proved, releases the exact reserved association to idle. It does not register result-only expectations for a command this process never dispatched. A failed or unknown deletion, a changed reservation revision or generation, or a physical Epoch that is no longer current leaves the reservation in place and does not replay the delete. Restart drops the process-local proof and continues to use result-only recovery. When that same process later proves a different fresh physical Epoch and releases the reservation, it drops the process-local proof only after that release; an unresolved deletion keeps the proof.

Result-only cleanup of an exact `cleanup-pending` backend with no in-memory session or durable Sandbox also releases its sole matching Worker storage reservation after definite writer cleanup. A non-null current Sandbox binding must match the durable backend Sandbox binding; a null pre-Sandbox reservation remains valid. The association keeps its identity, targets, attachment generation and contributor history while clearing the current attachment. The reservation is captured before awaiting cleanup, so ambiguous lineage, contradictory Sandbox ownership, failed or unknown cleanup, and a changed revision or generation cannot release it; sibling reservations and retained bytes remain untouched. The existing different fresh physical Epoch cleanup branch is unchanged.

## Verification

Run the nearest focused tests first, followed by NanoCore typecheck, lint, build, and the complete NanoCore test suite for runtime behavior changes. Governed-worker changes should also run worker-control, recovery, scheduler, and Server route coverage relevant to the changed lifecycle.

The MCP concurrent credential-rejection regression holds the real upstream delayed response on an explicit fixture gate and observes tool-call ingress before triggering rejection. It preserves the call rejection, unknown-effect and degraded-health assertions without relying on wall-clock scheduling.

The MCP Gateway's existing teardown-required fence refuses late tool and listing results and prevents health probes from restoring ready state while cleanup owns the cached session. A separate regression holds HTTP termination pending while another real response completes, proving typed rejection with known upstream contact and degraded health; failed cleanup retains its existing exact-retry ownership.
