# Authentication And Authorization

`capture-retry-context.ts` binds a definite pre-effect capture refusal to its current Actor and authenticated session. Only the authorized admission gate advertises `Retry-After: 1`; unbound sessions, recovery closures and later domain errors do not. Definition-derived JSON routes compare the retained binding before dispatch and repeat ordinary authorization, so replay never carries authority into another session. Core-client owns the single bounded wait and cancellation policy.

Operation admission awaits administrator-bearer Quick Chat provisioning before it checks the resulting Workspace authority and audience. Better Auth session creation awaits the existing active-user provisioning hook before session recording. Both paths keep their current active-user, owner and membership checks.

This directory owns NanoCore authentication middleware, Better Auth browser sessions, actor resolution, server access-token authentication, bootstrap credential flow, and request-scope authorization helpers.

## Boundaries

- Presented bearer verification remains on Main. Its exact identity/hash proof enters the existing native Core owner, which rereads the current Token and active User, checks expiry, rotation grace and revocation, and publishes last-use before returning the existing redacted identity. No bearer, precomputed authority grant or secret returns through that internal command; other credential writers retain their existing ownership.

- Browser and product requests use Better Auth session cookies; remote requests from the `openkit-ops` administrator CLI, remote MCP, other non-browser clients, and administration clients use explicit `okt_` bearer credentials.
- Authentication establishes the actor; workspace membership and token scope still require authorization before any workspace database, store, or mutation is opened.
- `/mcp` reuses this middleware's bearer verifier and socket-derived transport admission in both modes. It accepts no implicit local actor or browser session, returns the same uniform authentication body plus `WWW-Authenticate: Bearer`, and installs only the presented Token's actor. Native operation invocation retains scope and permission admission; the endpoint adds no second authorizer. The App composition forces `remote-mcp` last-use attribution regardless of caller-supplied channel headers.
- A current usable administrator Web session or presented administrator bearer receives administrator eligibility on active Workspaces without a manufactured membership, including the derived Workspace list. Session eligibility is resolved from the active canonical User's currently usable `server-admin` Token. Workspace-scoped tokens keep their bindings, and read-only credentials stay read-only. Administrator projections retain the actual membership status and revision, including null when no membership exists; isOwner reports only registry identity.
- Personal admin-token list/default operations accept the implicit local canonical user, a Better Auth session, or a currently usable administrator bearer and return only owned redacted records and the effective default token ID. Ordinary Workspace bearer actors remain rejected; token create/rotate/list-all administration retains its server-mode boundary. Default selection sends only the admitted User and Token ids to the existing native Core owner, which rechecks current User activity and the original token/retained-setting conditions in its savepoint, then awaits covering FULL acknowledgement before the handler reads the original list projection. Failure or a lost acknowledgement never reports success or automatically reposts the setting change; canonical token mutations and later lifecycle Audits remain separate.
- Global administration routes require the documented deployment-admin capability and must not be reachable merely because a browser session is valid.
- Server startup must supply a deployment-specific `BETTER_AUTH_SECRET` with at least 32 characters; the local development fallback is never valid for server mode.
- Better Auth public URL and sign-up policy use the startup `server.jsonc` snapshot; `BETTER_AUTH_URL` may override the public URL. Browser origins use validated `server.cors.origins` plus the auth server's own origin. The SDK context projects that fixed snapshot during initialization and concurrent HTTP requests; environment origin values cannot alter admission.
- Browser requests with an `Origin` header must match the exact startup allowlist before route work begins; requests without `Origin` remain valid for non-browser clients.
- Remote bearer requests and bootstrap-token consumption must use an actually encrypted Node transport; only a real loopback peer may use plaintext, and request URL or Host text never substitutes for socket state.
- When admission requires membership, missing, removed, inactive, or cross-user membership must fail closed before resource existence is revealed.
- After current Workspace eligibility, addressed existing Threads reuse `isThreadVisible` / `isThreadIdVisible`. Missing, corrupt, Workspace-mismatched, and inaccessible Threads fail as the same 404 before disclosure or effect. Migrated private reads pass current Administrator Eligibility into `isThreadVisible` through `isThreadIdVisible`. Retained route guards and the Turn event stream keep the ordinary audience check. Core Thread list filters before projection. SSE rechecks current Workspace permission, presented Token usability, and ordinary audience before each publication and closes on revocation or expiry.
- Tokens, cookies, password material, OAuth material, and full unique credential identifiers must never enter logs, diagnostics, events, or test output.
- NanoHost transport Tokens reuse the same `okt_` create/hash/verify primitives as human access tokens, but they are a separate Core Token class with closed type and scope `nanohost-transport`. Product App API paths and `server-admin` actor installation MUST reject presented `nanohost-transport` material. Human `OpenKitAccessTokenScope` and `openkit_access_tokens` are not extended.
- NanoHost transport session authority is process-local connection-generation fencing for one configured NanoHost identity: at most one authoritative generation, descending and replayed generations rejected, successor work blocked until the predecessor is fenced, and non-loopback TLS policy consumed by the dedicated native HTTP/2 listener in `index.ts`. Production admission in `nanohost-transport-admission.ts` verifies the dedicated `nanohost-transport` Token and completes a configured-slot rotation only after the successor wins. It reuses the `nanohost-transport` Token class and does not invent a second token table, secret prefix, or actor path.
- NanoHost transport lifecycle helpers in `nanohost-transport-lifecycle.ts` compose store, named-slot clear, and session authority for rotation cutover/abort (exactly one usable slot at steady state), revoke/expiry/decommission fencing of live authoritative work, and truthful restart re-admit (process-local authority resets; durable Tokens require re-admit). Live Runtime Epoch/AgentSession topology remains WP-6.

## File Map

- `middleware.ts` owns actor authentication and request variables, including fail-closed rejection of `nanohost-transport` on product App API paths.
- `loopback-host.ts` supplies the pure loopback hostname predicate to authentication, NanoHost transport sessions, App composition and bind-host resolution. Each caller retains its transport, peer and admission checks.
- `thread-visibility.ts` owns the unique Thread audience predicate (`isThreadVisible`) applied after current Workspace eligibility, and `isThreadIdVisible` for id-only callers that must fail closed on a missing or corrupt owner. Private Threads require exact private ownership or the current Administrator Eligibility supplied by migrated reads; workspace-shared Threads use current Workspace eligibility.
- `operation-access.ts` projects migrated operation access metadata from `OPERATION_DEFINITIONS` and classifies retained public routes; Goal intent revision derives its mutating body-Workspace `workspace.write` posture from the Goal definition.
- `operation-authorizer.ts` resolves retained route bindings from the checked source catalog without reading or building the generated OpenAPI document. It excludes canonical JSON and raw Artifact operation bindings from retained route guards so native invocation supplies their single parsed-selector admission. Retained Workspace archive paths keep catalog-driven canonical-user or Workspace guards and closed-Workspace admission; server-scoped routes keep their existing route-owned authentication. It owns catalog-driven Workspace guards for retained routes and requires the shared Thread-constraint Kernel after primary Workspace admission for every addressed existing Thread: retained path `threadId` and native definition-derived addressed Thread selectors; `turn.feedback` resolves only opaque Turn-map lineage in native invocation before child content. The constraint request carries the concrete catalog policy operation; it cannot skip permission evaluation. Presented workspace bearers recheck current Token usability on each Workspace authorization. Current usable administrator sessions and bearers receive administrator eligibility on active Workspaces without membership; retained guards project current administrator eligibility into the same mandatory audience constraints.
- `better-auth.ts` and `server-flow.ts` own browser authentication and server-mode flows. The active-session hook awaits personal Workspace acknowledgement and owner membership before the new session is recorded; a provisioning failure rejects the session.
- `access-token-lifecycle-codecs.ts` / `access-token-lifecycle-native.ts` move only public canonical Token revoke/rotate to the existing Core writer. Main prepares rotation id/secret/hash and sends no raw secret; native rereads current target eligibility and keeps the original predecessor-update/successor-insert tuple atomic, inheriting owner/scope/bindings/expiry from that predecessor. Original mutation-time non-secret snapshots return only after FULL acknowledgement. The handler then awaits its separate original lifecycle Audit before publishing success or its one-time secret. A lost canonical acknowledgement never reports success, starts that later Audit or automatically reposts. Legacy synchronous rotation still generates its secret inside its original transaction; issue/create and bootstrap retain their separate original owners.
- `access-token.ts` / `access-token-store.ts` / `access-token-operations.ts` own human bearer credential lifecycle and validation. Current presented-Token checks reuse the exact redacted store lookup and fixed retained decoder; unrelated Token history is not materialized. Management listing keeps its separate complete-list contract.
- `user-disable-native.ts` applies the complete canonical User-disable tuple through the existing closed Core-sharing command. It reuses the original User status/session deletion/Token revocation primitive, lifecycle Audit helpers and Core receipt owner in one native savepoint. Public Kernel admission remains separate; native rechecks current durable administrator identity facts and exact target/receipt lineage. The covering FULL acknowledgement precedes the original per-invocation `afterUserDisabled` hook and public output; Main verifies but never rewrites that receipt. A lost acknowledgement reports no success, calls no later hook and does not repost. A later hook failure does not roll back the committed tuple. Token create and Bootstrap consume remain separate families.
- `admin-recovery.ts` owns the stopped-server active-User discovery and file-first administrator credential recovery command while reusing the existing data-root lock, Token store, and Audit owner.
- `nanohost-transport-token.ts` / `nanohost-transport-token-store.ts` / `nanohost-operations.ts` own the dedicated NanoHost transport Token class, hash-only Core store, native server-admin enrollment/lifecycle operation joins, and the configured RuntimeTarget readiness observation. Definition-derived HTTP, client, CLI and remote MCP projections use the shared current deployment-administrator admission. The runtime-target operation and private administration `nanohost.runtime-target` Tool share `readConfiguredNanoHostRuntimeTargetStatus`; they do not infer health from configuration or gain host lifecycle authority. Issuance and verification require the Token's exact active identity/deployment owner, so orphan or decommissioned material cannot authenticate, update last-use metadata, rotate, or produce another Token. Enrollment inserts only a lineage-free configured identity or reactivates the exact retained decommissioned identity/deployment pair with one fresh Token; retained Token history without its identity row and every active, missing, duplicate, or cross-bound lineage fail closed.
- `nanohost-transport-codecs.ts` and `nanohost-transport-native.ts` move the complete NanoHost credential tuples and the two existing separate Audit forms through the existing Core native writer. Main retains one-time secrets, constant-time presented-secret proof, named-slot files and process authority. Callers await each covering FULL acknowledgement before its later file, generation, fencing or success stage; native SQL repeats current administrator and credential predicates. Open refusal remains distinct from an uncertain submitted write: only definite enrollment rollback permits exact-owned slot cleanup, while uncertain revocation/decommission fences the exact known identity without claiming SQL completion or clearing files. Abort retires the successor atomically and restores only a still-rotated, non-revoked predecessor. A revoked predecessor remains revoked; this failed restoration uses the existing failed rotation Audit after mandatory cleanup is attempted and leaves the original typed outcome visible. The same current-administrator implementation and Error constructor live in `access-token-store.ts` and remain re-exported by `operation-authorizer.ts`.
- `nanohost-transport-sink.ts` owns NanoCore-side safe-sink delivery to the configured A/B credential files (raw `okt_` + companion metadata at mode `0600`), including direct rejection of relative, aliased, or symlinked targets. Enrollment exclusively creates one empty slot without overwrite and conditionally clears only the exact attempted Token after a later transaction failure; issue and opposite-slot rotation explicitly replace their named slot without exposing raw `okt_`; unconditional slot clear remains limited to cutover, abort, and decommission cleanup.
- `nanohost-transport-session.ts` owns process-local NanoHost transport session authority (connection-generation admission, predecessor fencing, `mayCarryWork`, authoritative fence, pending-successor discard) and resolves the configured dedicated listener with its non-loopback TLS requirement. `createApp` installs the store; `index.ts` starts that listener separately from the App HTTP/1.1 listener.
- `nanohost-transport-admission.ts` owns the production NanoHost→NanoCore admission path: hash-only secret verification plus exact active identity/deployment ownership through `verifyNanoHostTransportTokenRecord`, session `admit` / `fencePredecessor` / `mayCarryWork`, and HTTP admit/fence routes under `/api/nanohost/transport/session/*` that verify `nanohost-transport` Tokens themselves (not product App API actor paths).
- `nanohost-transport-lifecycle.ts` owns focused rotation cutover/abort, revoke/expiry/decommission fencing, and restart-readmit composition over store + sink + session authority.
- `bootstrap-ensure.ts` joins only server startup ENSURE to the existing Core native writer. Main retains the new Bootstrap secret; native reuses the original all-User count, retained pending/expiry guards and setting upsert, returning only issue timestamps after FULL acknowledgement. `index.ts` awaits that join before its original separate emission file. A lost ACK does not emit, return a secret or repost; an acknowledged setting remains durable if later emission fails. The synchronous primitive keeps its original secret generation and clock/TTL options. Consume's original User/account/Token/setting transaction, file cleanup and separate later Audit are unchanged.
- `bootstrap.ts` owns the one-time server owner bootstrap path.
- `actor-store-manager.ts` owns actor-scoped store selection.

The stopped-server operator keeps its exclusive data-root lock across native preparation and FULL acknowledgement. Its file-first recovery envelope and fsync precede the existing atomic hash-only Token plus Audit tuple; the original file identity and exact-retry checks remain. Native and Main database handles close before standard output and root-lock release. A failed native close joins the existing worker shutdown before releasing that lock and cannot report completion. Recovery opens only the already existing Core scope without migration. Other authentication writers remain separate pending their complete-family native cuts.

## Verification

Run authentication middleware, server flow, access-token, bootstrap, administrator-recovery, membership, and Server route tests relevant to the change, followed by NanoCore typecheck, lint, and build. Administrator-recovery tests use only temporary data roots and process-local lock probes; they must not start, stop, or restart NanoCore. Server-mode tests must cover unauthenticated, wrong-scope, removed-membership, read-only, and server-admin cases where applicable.
