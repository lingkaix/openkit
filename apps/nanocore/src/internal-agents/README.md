# Internal Core Roles

This directory owns the deterministic Workflow Coordinator, Internal Role Execution Profile resolution, the bounded shared Internal Agent Loop, structured worker delegation payloads, and shared redaction helpers used by NanoCore services.

## Boundaries

- `assistant-timeline.ts` derives the current user's ordinary private Timeline from canonical Threads. Private `thread.create` opens the earliest conversation by creation time and exact id, excluding administration and shared work. Fresh command identities reuse it without renaming or reopening; archived state requires an explicit update. Retained earlier extra conversations remain readable history. The existing Thread command owner preserves replay and conflicts; no pointer, second history or identifier format is added.

- Keep Coordinator decisions request-scoped and deterministic; mode services own persistence and effects. Mode entries supply required trusted `entryIntent: explicit_task`, which selects eligible worker supply and composes the exact instruction without semantic reclassification. Direct `task.start` derives it from the operation; confirmed Assistant handoff derives it from the existing Pending Request's exact human selection. Ordinary conversation reaches the Assistant model and fixed Tools. The retired English keyword classifier has no remaining production consumer and is removed.
- Assemble a fixed ordered Tool set before each Internal Agent Loop run. The loop validates Tool arguments, executes only its injected closures, preserves correlated transcript order, and terminates through explicit model-turn, Tool-call, cancellation, or deadline fuses. Each admitted closure receives the one-based toolOccurrence from the existing Tool touch counter; model call IDs stay correlation only and remain unique across the run. Unknown Tools and invalid arguments do not consume that counter.
- The loop preserves the first cancellation cause, discards Provider and Tool results that settle after cancellation, clears its deadline timer on every exit, and stops text observation when the run ends. A cancelled Tool still owns its admitted effects and evidence; the loop does not retry it.
- Preserve original Tool schemas with provider constrained sampling disabled; the loop owns exact argument validation before each closure, including tuple schemas and omitted optional fields.
- Trusted role owners reconstruct the rolling window as ordered `messages` from current authorized records through an exact committed input boundary. The loop appends observations only for that bounded run; it neither persists a transcript nor selects or replaces canonical history. A new run rebuilds its window and Tools from the existing owners, and does not replay settled Tool history.
- `assistant-skill-resources.ts` owns the selected Skill definition, logical schemas, retained native handler and definition-derived model Tool under [Resource Integration](../../../../docs/specs/20260909-internal_agent_resource_integration.md) and [Operation Definition](../../../../docs/specs/20261002-operation_definition.md). New command assembly supplies explicit `assistant.resources.skillIds` and the real admitted `requestId` once. It resolves pins before current digests, freezes the sorted metadata-only index and minimal admission, and retains the original exact version inventory. `AssistantSkillResources.read` returns only the five-field logical success and throws safe resource failures; it exposes no direct model Tool. Before content access it matches the retained actor, Workspace, Thread, Turn, `assistant-command` kind, `conversation.submit` entry and command request, then rechecks current catalog-read authority, Thread audience, nonterminal Turn, catalog availability and original retained inventory. The existing tree verifier checks exact immutable bytes and containment. Reads return sanitized UTF-8 text and source provenance, bounded at 64 KiB for the complete serialized output; the sanitizer fixed-point check prevents later loop sanitization from corrupting provenance or expanding that bound. `ASSISTANT_SKILL_OPERATION_DEFINITIONS` owns the strict logical input/output schemas, description, read-only posture and `workspace.read` admission. `createAssistantSkillReadTool` derives its name, description and JSON input schema from that table and calls only P12's supplied native invoker. P12 binds the original `read` handler through the shared private invocation engine, which parses input, applies primary admission and validates logical output. The Tool validates the same output schema and model envelope, emits bounded safe failures without exception text and preserves cancellation. No public operation projection, registration API or binding store is added. Tests use explicit local fake invokers to preserve handler/projection coverage while P12 supplies the real engine; these cannot reach production or prove invocation cutover. The separate administration entry receives no Skill from this module.
- Bind the loop to logical-model dispatch through `gateway-provider.ts`; role entry owners retain authorization, durable Item production, usage attribution, and product-success interpretation. Each route attempt checks prompt, Tool schemas, and messages against the admitted logical-model context ceiling and current effective member capacity. The known admitted output ceiling, or current member output limit when it is unknown, is reserved and sent as the ordinary model-request output cap. The shared local text estimate uses UTF-8 request bytes divided by three plus a fixed margin. It checks the complete stock payload after native overlays and includes native continuity and the serialized output cap. It does not require an exact tokenizer or contact a count endpoint. This estimate is not a proved token bound; upstream overflow remains explicit. The adapter fails safely on missing physical bounds or an oversized request. Role-owned rolling or compaction assembly runs before this dispatch check; the adapter does not compact or truncate its input. Public Gateway and Worker policy retain their own contracts. Carry private session scope through dispatch context rather than provider payload metadata, including Codex Responses calls.
- Project Tool IDs to Responses function names only at that Gateway seam with `operationToolName`, rejecting invalid names and collisions before dispatch. Project canonical history through the same request-local map and restore response calls by exact alias lookup only; loop closures, retained Items, capability evidence and diagnostics retain canonical IDs. Unadmitted complete calls use the loop's existing unavailable correction: keep safe unknown spellings, replace unadmitted canonical or pattern-invalid spellings with reserved `openkit_unavailable_tool`, and carry those pattern-valid names through correction history. Reject any canonical ID or alias that equals the sentinel before dispatch; malformed calls remain fatal. No alias or sentinel is durable authority.
- Keep every NanoCore-owned model-using built-in Agent's fixed System Prompt in `builtin-prompts.ts`, including Assistant and Goal Coordinator callers. Its assembler checks non-empty fixed text and the 3000 Unicode-codepoint ceiling before dispatch; current private administration identifiers are appended from server-owned context at admission, while current Tool definitions and work messages stay with their entry owners.
- Resolve internal-role profile preference User first, then Workspace, then Server, and admit only logical models whose derived capabilities satisfy the profile. Production callers pass the Gateway's live subscription and API-key presence dependencies for current route availability. Each Provider invocation resolves that pinned logical ID again from the current runtime snapshot and live dependencies, then restarts logical dispatch from the first available member that satisfies the admitted capabilities and known coherent context/output minimums. Required capabilities and known coherent limits stay pinned; current known member limits below those minimums are skipped through the existing pinned-capability selection path. Physical input admission still requires a known usable context limit from effective member metadata. An unavailable route is skipped, and an ID that no longer resolves returns the existing unavailable outcome.
- Keep worker delegation schemas here because they are the concrete handoff from mode decisions to worker execution.
- Configured product and worker agents belong to `../agents/`; governed worker execution and recovery belong to `../runtime/`.
- `assistant-command-run.ts` prepares the shared-loop adapter for command-initiated Assistant Turns admitted by `conversation.submit`. The entry passes the original selected resources, canonical window and complete ordinary Tool array, including the definition-derived `skill.read` Tool bound to native invocation of the retained logical handler. The adapter freezes messages and Tool definitions, places a bounded sanitized Skill index inside escaped `assistant_skill_index` delimiters as untrusted user context, and keeps the built-in System Prompt separate. It passes the exact minimal shared `AssistantSkillAdmission` tuple with that prompt and Tool set to `withTurnModelCapture` with `requireAssistantSkillAdmission: true`, so immutable `env.bound` retention succeeds before Provider dispatch even when capture is off. Empty selection is explicit. Current lineage, audience, catalog availability and retained inventory are checked before each logical invocation without selecting replacement pins. The adapter also uses the same-data-root Core database to recheck the existing `llm.gateway.use` authority before each call; resource-read access alone cannot authorize inference. Authorized re-entry must reuse the original assembly and matching closure; capture deduplication permits no replay or recovery by itself. The Gateway tags invalid response content with its private `provider_response_invalid` failure; the adapter maps only that projection failure to the ordinary typed invalid-response error and preserves original upstream exceptions. The adapter preserves the ordinary answer, Provider identity, usage and error types; cancellation, deadline and invalid final answers use the existing entry errors. The command entry still owns admission, receipt and unknown-effect decisions, Operation Invocation, pending-outcome continuations, publication authorization, Items and Turn completion. The stateless entry is retired; ordinary Assistant requests use Timeline admission. The command entry wires this adapter through the shared private invocation engine for the complete selected-Skill family. This family does not establish specification completion.
- Command-initiated Assistant assembly appends the fixed eleven native Kernel/UI Tools after skill.read. Their definition-derived strict schemas omit bound identity fields; the trusted closure binds only declared Workspace, Thread, Turn and command inputs and calls createOperationInvocation with the original authenticated actor and current query lineage. Opaque command UUIDs use the exact resource-owner conversation/accepted-occurrence tuple, never model correlation IDs. The retained command resources recheck current source/Thread/Turn admission before native dispatch and result delivery, while native admission retains operation access and read-only checks; renderer payload stays private, and a non-published result is not a successful Tool publication.
- Assistant entry and publication remain in `../mode-entry-routes.ts`; do not introduce a registry, hook system, private event protocol, or streaming facade here.
- Keep shared redaction helpers free of workflow or diagnostics ownership. Sanitize decoded JSON string values and property names while preserving valid structure and unchanged safe bytes; opaque text retains its existing credential filters.

## Verification

Run `internal-agent-loop.test.ts`, `gateway-provider.test.ts`, `profile-resolver.test.ts`, and the focused entry or Coordinator tests affected by the change, followed by the package gates in the [NanoCore source guide](../README.md).

Production administration and Goal consumers supply their existing capability context to the Gateway provider. It opens one call before route planning, associates reported usage with reached attempts, and finishes once on success or no-supply failure. Capture retains the actual admitted Turn and the logical call reference. For the #144 command-initiated Assistant adapter, each inference invocation uses a null per-invocation request ID and a fresh call; the real validated command request travels separately as the shared `CapabilityAuditLineage` option. Gateway admission, both finish paths and both usage paths forward it to the existing recorder, including an earlier `usage_record_failed` closeout. The admission Audit retains the known command identity and available credential summary with the actor; terminal and restart-unknown Audit reuse that same captured attribution when the call request is null. It supplies the existing AuditEvent request field without changing call or usage request IDs. Other callers can omit this option. Null provides no request-key replay protection: P12 must return the original exact command result and prevent extra invocation for replay, concurrent duplicates, missing receipts after dispatch and uncertain-effect recovery. Retaining the original Skill admission preserves selection only and never reopens a closed call or authorizes another inference effect.

The internal Gateway producer settles callback ownership at logical closeout on both success and failure. Later usage callbacks are ignored before any ledger access, including after the capture database closes. Its transport carries the executor’s unchanged absolute deadline through retry and failover; no deadline consumer is added here.

Failed logical closeout emits the best-effort `internal_gateway_call_failed` process log under [Operational Telemetry Standardization](../../../../docs/specs/20260731-operational_telemetry_standardization.md#failed-internal-gateway-logical-calls). Diagnostic state resets before each member's resolution, and stock completion establishes output-projection evidence before adapter conversion. A selected-model Codex SSE HTTP rejection supplies an attempt-local diagnostic status only when validated routing-bearing failure status is absent; it changes no failure kind, retry or replay rule. The unsupported-feature error class alone does not prove pre-transport rejection, and the fixed local `prefixItems` rejection takes precedence over HTTP evidence. `gateway-provider.test.ts` exercises the real stock required-sampling `prefixItems` rejection and undeclared Tool output, mixed HTTP/local-resolution failover, safe phase/status/correlation projection, and a throwing log sink. `gateway-provider-http-rejection.test.ts` composes the stock Codex producer and internal consumer with intercepted HTTP 401 and tests diagnostic precedence, attempt isolation and privacy. Public failure and durable CapabilityCall metadata keep their existing projections.

The deterministic Workflow Coordinator routes user requests; the model-using Goal Coordinator is a separate consumer in `../runtime/goal-coordinator.ts`. It uses this existing loop on ordinary Goal Thread Turns without an AgentSession and the configured `goal-orchestrator` role identity. `task-shapes.ts` retains ordinary Task handoff shapes independently of the removed Goal stores.

`rolling-context.ts` assembles internal-role history from ordered canonical Turns and first-seen Item order. It uses the Gateway's local text request estimate and source-bound `context-summary` Items. Pressure-driven summary batches use the caller's captured Provider path and consume the same model-turn and absolute deadline budget. Assistant command and pending continuation, private administration and Goal Coordinator use rolling context.

`knowledge-manager-agent.ts` executes one fresh Knowledge Manager Turn through the existing role-profile resolver, model capture, Gateway and bounded loop. The Turn retains role, logical model, context strategy, threshold, selected profile ID, effective initial limits and admitted inputs before inference. Assistant, Coordinator and administration retain the same profile/limit metadata through the existing rolling-context admission; configured defaults use a null profile ID. Existing metadata is preserved when configuration later changes. Canonical user, assistant and completed Tool-call Items retain the actual transcript; model call IDs correlate results and grant no effect. `compacting-context.ts` summarizes only accepted Items from this run through the same Provider. Summary and ordinary calls share the model-call ceiling and deadline and reserve one answer call. A rejected result permits one bounded repair turn within the same model, Tool and deadline limits. Safe role feedback names missing prerequisites; repair may read evidence or supply a missing notebook submission, but cannot repeat editing or an attempted submission. Live KM runs use the existing Turn interruption hook; Stop aborts Provider and Tool work and waits for the ordinary terminal Turn. Process-local cancellation handles are discarded when the run ends.
