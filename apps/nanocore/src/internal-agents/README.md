# Internal Core Roles

This directory owns the deterministic Workflow Coordinator, Internal Role Execution Profile resolution, the bounded shared Internal Agent Loop, structured worker delegation payloads, and shared redaction helpers used by NanoCore services.

## Boundaries

- Keep Coordinator decisions request-scoped and deterministic; mode services own persistence and effects. Mode entries supply required trusted `entryIntent`: `explicit_task` selects eligible worker supply and composes the exact instruction without semantic reclassification; `conversation` retains the classifier below. Direct `task.start` derives that intent from the operation, never prose, and creates no Goal from keywords. An explicit Assistant Task Tool integration remains incomplete; current automatic project Chat and pending-outcome routing use `conversation`. Goal routing requires an explicit planning request or actionable multi-step work; mentioning Goal, roadmap, or strategy as a topic does not request a handoff. Review, audit, handoff, retry, and refinement still match their keywords anywhere in the remaining request text after unambiguous supplied-context and negated-constraint clauses are dropped; when no clause is recognised as an ask the original prompt is scanned; a leading summarize, explain, or describe verb keeps that text in Quick Chat even when a later noun repeats those keywords. The inference remains a bounded English heuristic.
- Assemble a fixed ordered Tool set before each Internal Agent Loop run. The loop validates Tool arguments, executes only its injected closures, preserves correlated transcript order, and terminates through explicit model-turn, Tool-call, cancellation, or deadline fuses.
- The loop preserves the first cancellation cause, discards Provider and Tool results that settle after cancellation, clears its deadline timer on every exit, and stops text observation when the run ends. A cancelled Tool still owns its admitted effects and evidence; the loop does not retry it.
- Preserve original Tool schemas with provider constrained sampling disabled; the loop owns exact argument validation before each closure, including tuple schemas and omitted optional fields.
- Trusted role owners reconstruct the rolling window as ordered `messages` from current authorized records through an exact committed input boundary. The loop appends observations only for that bounded run; it neither persists a transcript nor selects or replaces canonical history. A new run rebuilds its window and Tools from the existing owners, and does not replay settled Tool history.
- `assistant-skill-resources.ts` prepares ordinary Assistant resources from the Workspace's explicit `assistant.resources.skillIds` selection under the [resource integration owner](../../../../docs/specs/20260909-internal_agent_resource_integration.md). It resolves pins before current catalog digests, freezes a metadata-only index sorted by Skill ID, and supplies one fixed `skill.read` Tool for exact retained versions. The catalog's digest identity is also the private `versionId`; no version or run record is added. Current Workspace read Policy, Thread audience, nonterminal Turn admission and catalog availability guard assembly and every read. The existing catalog tree verifier checks immutable bytes; only sanitized UTF-8 text and exact provenance enter the model, with a 64 KiB ceiling on the complete JSON response after sanitization and on the metadata index. A read refuses a projection that the loop sanitizer would change again, so it cannot substitute provenance, corrupt JSON or exceed that response ceiling. Skill text executes no code and cannot enlarge the Tool set. The ordinary entry owns assembly, delimited metadata projection, existing Turn/capability evidence and publication reauthorization; this module is preparation until that wiring ships with resource-selection schema and reference validation. The separate administration entry uses no Skill body or Tool from this module.
- Bind the loop to logical-model dispatch through `gateway-provider.ts`; role entry owners retain authorization, durable Item production, usage attribution, and product-success interpretation. Each route attempt checks prompt, Tool schemas, and messages against the admitted logical-model context ceiling and current effective member capacity. The known admitted output ceiling, or current member output limit when it is unknown, is reserved and sent as the ordinary model-request output cap. The existing conservative UTF-8 serialization allowance is an admission bound, not exact Provider token usage; upstream overflow remains explicit. Missing physical bounds or an oversized appended observation fails safely without truncating history or calling a compactor. Internal input has no compaction policy or Gateway checkpoint; public Gateway and Worker policy retain their own contracts. Carry private session scope through dispatch context rather than provider payload metadata, including Codex Responses calls.
- Project Tool IDs to Responses function names only at that Gateway seam with `operationToolName`, rejecting invalid names and collisions before dispatch. Project canonical history through the same request-local map and restore response calls by exact alias lookup only; loop closures, retained Items, capability evidence and diagnostics retain canonical IDs. Unadmitted complete calls use the loop's existing unavailable correction: keep safe unknown spellings, replace unadmitted canonical or pattern-invalid spellings with reserved `openkit_unavailable_tool`, and carry those pattern-valid names through correction history. Reject any canonical ID or alias that equals the sentinel before dispatch; malformed calls remain fatal. No alias or sentinel is durable authority.
- Keep every NanoCore-owned model-using built-in Agent's fixed System Prompt in `builtin-prompts.ts`, including direct Quick Chat and Goal Coordinator callers. Its assembler checks non-empty fixed text and the 3000 Unicode-codepoint ceiling before dispatch; current private administration identifiers are appended from server-owned context at admission, while current Tool definitions and work messages stay with their entry owners.
- Resolve internal-role profile preference User first, then Workspace, then Server, and admit only logical models whose derived capabilities satisfy the profile. Production callers pass the Gateway's live subscription and API-key presence dependencies for current route availability. Each Provider invocation resolves that pinned logical ID again from the current runtime snapshot and live dependencies, then restarts logical dispatch from the first available member that satisfies the admitted capabilities and known coherent context/output minimums. Required capabilities and known coherent limits stay pinned; current known member limits below those minimums are skipped through the existing pinned-capability selection path. Physical input admission still requires a known usable context limit from effective member metadata. An unavailable route is skipped, and an ID that no longer resolves returns the existing unavailable outcome.
- Keep worker delegation schemas here because they are the concrete handoff from mode decisions to worker execution.
- Configured product and worker agents belong to `../agents/`; governed worker execution and recovery belong to `../runtime/`.
- `assistant-command-run.ts` prepares the shared-loop adapter for command-initiated Assistant Turns admitted by `conversation.submit`. The entry passes the original selected resources, canonical window and complete ordinary Tool array, including its trusted invocation wrapper around the retained `skill.read` closure. The adapter freezes messages and Tool definitions, places a bounded sanitized Skill index inside escaped `assistant_skill_index` delimiters as untrusted user context, and keeps the built-in System Prompt separate. It passes the exact minimal shared `AssistantSkillAdmission` tuple with that prompt and Tool set to `withTurnModelCapture` with `requireAssistantSkillAdmission: true`, so immutable `env.bound` retention succeeds before Provider dispatch even when capture is off. Empty selection is explicit. Current lineage, audience, catalog availability and retained inventory are checked before each logical invocation without selecting replacement pins. The adapter also uses the same-data-root Core database to recheck the existing `llm.gateway.use` authority before each call; resource-read access alone cannot authorize inference. Authorized re-entry must reuse the original assembly and matching closure; capture deduplication permits no replay or recovery by itself. The Gateway tags invalid response content with its private `provider_response_invalid` failure; the adapter maps only that projection failure to the ordinary typed invalid-response error and preserves original upstream exceptions. The adapter preserves the ordinary answer, Provider identity, usage and error types; cancellation, deadline and invalid final answers use the existing entry errors. The command entry still owns admission, receipt and unknown-effect decisions, Operation Invocation, pending-outcome continuations, publication authorization, Items and Turn completion. Standalone `chat.quick` stays in `../mode-entry-routes.ts` and receives no resources or synthetic Turn. This module remains preparation until P12 wires it in the complete held #144 delivery unit; it does not establish specification completion.
- Keep shared redaction helpers free of workflow or diagnostics ownership.

## Verification

Run `internal-agent-loop.test.ts`, `gateway-provider.test.ts`, `profile-resolver.test.ts`, and the focused entry or Coordinator tests affected by the change, followed by the package gates in the [NanoCore source guide](../README.md).

Production administration and Goal consumers supply their existing capability context to the Gateway provider. It opens one call before route planning, associates reported usage with reached attempts, and finishes once on success or no-supply failure. Capture retains the actual admitted Turn and the logical call reference. For the #144 command-initiated Assistant adapter, each inference invocation uses a null per-invocation request ID and a fresh call; the real validated command request travels separately as the shared `CapabilityAuditLineage` option. Both Gateway finish paths and both usage paths forward it to the existing recorder, including an earlier `usage_record_failed` closeout. It supplies the existing AuditEvent request field without changing call or usage request IDs. Other callers can omit this option. Null provides no request-key replay protection: P12 must return the original exact command result and prevent extra invocation for replay, concurrent duplicates, missing receipts after dispatch and uncertain-effect recovery. Retaining the original Skill admission preserves selection only and never reopens a closed call or authorizes another inference effect.

The internal Gateway producer settles callback ownership at logical closeout on both success and failure. Later usage callbacks are ignored before any ledger access, including after the capture database closes. Its transport carries the executor’s unchanged absolute deadline through retry and failover; no deadline consumer is added here.

Failed logical closeout emits the best-effort `internal_gateway_call_failed` process log under [Operational Telemetry Standardization](../../../../docs/specs/20260731-operational_telemetry_standardization.md#failed-internal-gateway-logical-calls). Diagnostic state resets before each member's resolution, and stock completion establishes output-projection evidence before adapter conversion. A selected-model Codex SSE HTTP rejection supplies an attempt-local diagnostic status only when validated routing-bearing failure status is absent; it changes no failure kind, retry or replay rule. The unsupported-feature error class alone does not prove pre-transport rejection, and the fixed local `prefixItems` rejection takes precedence over HTTP evidence. `gateway-provider.test.ts` exercises the real stock required-sampling `prefixItems` rejection and undeclared Tool output, mixed HTTP/local-resolution failover, safe phase/status/correlation projection, and a throwing log sink. `gateway-provider-http-rejection.test.ts` composes the stock Codex producer and internal consumer with intercepted HTTP 401 and tests diagnostic precedence, attempt isolation and privacy. Public failure and durable CapabilityCall metadata keep their existing projections.

The deterministic Workflow Coordinator routes user requests; the model-using Goal Coordinator is a separate consumer in `../runtime/goal-coordinator.ts`. It uses this existing loop on ordinary Goal Thread Turns without an AgentSession and the configured `goal-orchestrator` role identity. `task-shapes.ts` retains ordinary Task handoff shapes independently of the removed Goal stores.
