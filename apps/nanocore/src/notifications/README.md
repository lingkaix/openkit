# Attention Notifications

This module owns durable attention references and external delivery attempts in the Core SQLite database. It implements the [communication owner](../../../../docs/core/communication.md) and the external attention criteria in [Pending Requests](../../../../docs/specs/20260930-pending_requests.md). It does not resolve a request, execute its captured call, publish an Item, or infer that a person read a message.

## Composition

The composition root supplies an already migrated raw `better-sqlite3` database. `schema.ts` exports `ATTENTION_SCHEMA_SQL` for the Core migration owner and isolated tests. The constructor never creates tables or runs migrations. Its optional `buildAppPath(source)` callback selects the current authorized App route; the default points to `/tasks/:workspaceId/:threadId` with an exact request query. The composition root supplies the conversation route for a private conversation source. The composition root calls `reconcileIncompleteAttempts()` once at startup before it admits commands or starts sends. Calling it while sends run would classify those sends as unknown.

`enqueue({ source, recipientUserId })` records only the exact Workspace, Thread, Pending Request kind, request id and responsible recipient. Repeating that complete identity returns the existing reference, including its delivery outcome. The composition root admits the source and recipient before enqueue. There is one reference per source and recipient, and one retained attempt history under that reference. The latest attempt is the current delivery projection; no second delivery-state field exists.

`get(id)` is an internal owner read. It grants no permission to expose its result. `getForActor(id, userId, isEligible)` and `listForActor(userId, { limit }, isEligible)` expose only the exact recipient with current admission. List reads inspect at most 100 database rows, default 50, before source/audience filtering, so a filtered list can contain fewer rows than the requested limit. Lists order by creation time and then id. No cursor or total count is claimed.

`deliver({ deliveryId, recipientUserId, channel, retry, expectedAttemptId }, { isEligible, transport })` durably claims one attempt before it checks current authority and calls the transport. The synchronous `isEligible` callback must check the current actor, source, Pending Request state, responsible recipient, destination audience and channel-account binding. It receives the selected channel. It must return exactly `true`; an unavailable check prevents contact and records `failed-no-send`. No asynchronous step separates a successful eligibility check from transport invocation. The callback is a trusted Core boundary, not caller input. The transport closure owns destination resolution and current account credentials; no address, credential or captured argument is retained here.

## Delivery Outcomes

A queued reference has no attempt. The first attempt freezes its channel. A concurrent send observes `sending` and cannot contact the transport. A successful transport acknowledgement records `sent`, which proves only delivery acknowledgement. A definite refusal before any send effect records `failed-no-send`. Every send supplies `expectedAttemptId`: null for a first send or the last observed attempt id for a retry. The durable claim checks that exact attempt id, so a duplicate retry cannot send again when its first execution also failed before sending. Only an explicit call with `retry: true` can retry that state, on the same channel and with a fresh eligibility check. A throw, malformed result, explicit uncertain result, or unfinished attempt after restart records `delivery-unknown`. Unknown, sending and sent outcomes cannot be retried, and changing the channel cannot bypass that fence. There is no background sender or automatic retry.

The transport must report `failed-no-send` only when it proves that no send effect occurred. Every adapter exception is uncertain because this module cannot know where contact happened. If transport acknowledgement succeeds but SQLite settlement fails, the durable attempt remains `sending`; startup makes it unknown. No cross-system atomicity or automatic repair is claimed. Retained unknown core values and invalid record combinations fail with `attention_recovery_required`; optional additive SQL columns do not change admission.

`AttentionLink` contains only `kind: 'attention-link'`, the delivery id, and an encoded App path with the exact Workspace, Thread and request ids. The composition root owns that App route and the transport adds only its configured App origin. Email uses this same attention-link payload; this module provides no Email adapter or Email decision surface. No vendor operation runs in these tests.

## Verification

With the pinned Node and pnpm on `PATH`, run `pnpm --filter @openkit/nanocore exec vitest run src/notifications/attention.test.ts --maxWorkers=1 --no-file-parallelism --no-coverage`. The tests inspect real SQLite rows, prove exact deduplication and claim visibility, use injected transports to observe no-contact fences, and close/reopen a file-backed fixture to prove restart handling. Temporary fixture directories and all database handles are removed after each test.
