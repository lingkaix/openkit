# Administration

Load this reference for runtime configuration, access administration, NanoHost execution-host credentials, vault operations, audit, usage, automations, backup, export, import, or workspace portability. The Workspace host repository resource, its diagnostics, and its write settings are a legacy surface retiring under the hosting decision. This reference gives no instruction to create, correct, or rely on one. Hosted writes are selected vendor MCP effects under their own current authority and approval, and this reference does not describe that default path as currently working.

## Confirm authority and scope

Identify the deployment, workspace, target resource, requested effect, and acting user before selecting an operation. Use `ops search` and `ops describe` to inspect the operation's mutation status, sensitivity, and required access.

Use existing explicit user direction, or obtain it when absent, before changing runtime configuration, invalidating sessions, revoking access, unlocking or rebinding a vault, changing grants, scheduling an automation, requesting a selected vendor MCP hosted write, exporting data, importing data, restoring data, or creating another external effect. The Workspace host repository resource, its diagnostics, and its write settings are a legacy surface retiring under the hosting decision. This reference gives no instruction to create, correct, or rely on one, and it gives no instruction to write or push through that surface. A selected vendor MCP hosted write stays under its own current authority and approval, and this reference does not describe that default path as currently working.

Invoke one bounded administration operation at a time. Re-read the owning status, audit, usage, repository, automation, vault, or portability record before reporting success.

## Manage shared Workspace access

For owner-directed sharing, list the current members or invitations before creating or revoking an invitation, changing member access, removing a member, or transferring ownership. Pass an invitee email only through stdin, confirm the exact target and expected revision before each mutation, and re-read the owning collection afterward.

For the current canonical user's invitations, use `workspace.my-invitation-list`, `workspace.my-invitation-accept`, and `workspace.my-invitation-decline` through implicit local identity. The list takes `{}`; accept and decline take `invitationId`, `expectedRevision`, and an optional `requestId` through stdin. List first, confirm the exact pending invitation and revision, submit the chosen response, and re-list afterward. Preserve the same request ID and payload for an exact retry; do not silently retry a revision conflict with a newer revision.

These three bundled CLI operations are local-mode only. Ordinary server-mode bearer credentials, including `workspace` and `workspace-readonly`, do not authorize current-user invitation operations. Current CLI admission also rejects an administrator bearer. That running rejection is not the rule. A currently usable administrator credential is eligible under the administrator eligibility rule in [Core Permissions](https://github.com/lingkaix/openkit/blob/main/docs/core/permissions.md#administrator-eligibility), and the recorded actor is that administrator. The CLI neither acquires nor persists Better Auth cookies. Use the Web Account Invitations panel for the ordinary session path. Report the CLI limitation rather than bypassing it through raw HTTP, cookie persistence, invitation secrets, or another token mechanism.

For the current canonical user's non-owner membership, use local-mode `workspace.leave` with `workspaceId`, `expectedRevision`, and an optional `requestId` through stdin. List Workspaces with `workspace.list` or members with `workspace.member-list` first; use the caller's `membershipRevision` from the Workspace list or `revision` from their member record as `expectedRevision`. For example, pass `{"workspaceId":"ws_demo","expectedRevision":1}` to `ops call workspace.leave --input -`. Preserve the returned request ID and the same payload for an exact retry, supplying that ID as `requestId`; never silently refresh a conflicting revision. Re-list Workspaces after success to confirm the membership is no longer accessible. Ordinary server-mode bearer tokens remain unsupported for leave. Current CLI admission also rejects an administrator bearer for leave. That running rejection is not the rule. A currently usable administrator credential is eligible under the administrator eligibility rule in [Core Permissions](https://github.com/lingkaix/openkit/blob/main/docs/core/permissions.md#administrator-eligibility). Use Web Account for the ordinary session path.

Use Workspace access recovery or user disable only with explicit deployment-administrator direction. Recovery exposes no Workspace content and supports only the actions described by the selected operation; user disable preserves durable identity and history.

## Protect access and vault material

Pass secret input through stdin or a platform credential mechanism, and keep it out of arguments and agent-visible output. Never request raw provider credentials, vault contents, injection payloads, process handles, or private runtime records through the operation catalog.

For a locked-out or stopped server, this Skill cannot stop NanoCore or replace a Data Root. After an authorized operator produces a protected recovery envelope, pass the complete envelope directly through stdin to `credential.store`; the operation stores only its token field. Never copy the envelope into conversation or inspect its token. Complete same-deployment restore is the App image `openkit-restore` command (`docker run --rm --entrypoint openkit-restore`), not a live catalog mutation. Stop NanoCore first. Persist live `backup.create` output from the sibling `<data-root>.backups` host path. Bind a writable host parent at `/restore` and restore its child (for example `--data-root /restore/data`); do not bind the Data Root itself as `/data/openkit`, because restore `rename`s that path and a mountpoint fails with `EBUSY`. Mount the backup subtree read-only at `/backup` and pass `--backup-root /backup`. The parent must be writable on the same filesystem as the child so `<data-root>.restore-staging` can be renamed onto it.

A full same-deployment Data Root restore retains Core NanoHost identity and transport Token records, so matching, unexpired and unrevoked named-slot credentials can continue to admit. Restoring only runtime configuration and host named-slot files onto a fresh Core without those records yields NanoHost admission 401; that is expected missing trust, not a slot-format bug. Fresh enrollment needs separately authorized host stop and archival of the old slot pair, an empty target slot, public `nanohost.enroll` with server-admin authority, then start of the execution host. Do not bypass exclusive-create, copy stale Token records, or reveal slot material. On a fresh Core, complete `nanohost.enroll` before the first execution-host start; a premature start can leave the create-once fence-to-ready interval expired and non-ready across restart. Never delete or reset that marker. This Skill has no SSH or service-stop authority. Public `nanohost.decommission` and `nanohost.enroll` run only under an authorized host handoff. Authorized recovery is the operator cookbook's terminal decommission and exact-pair reinstall path, preserving prior non-secret failure evidence.

For the current canonical user’s admin tokens, call local-mode `token.my-admin-list` with `{}` through stdin. Select an owned usable token with `token.my-admin-default` and exactly `{ "tokenId": "tok_admin" }`; re-list to confirm the effective `defaultTokenId`. Responses contain only redacted `items` and `defaultTokenId`. An ordinary server-mode bearer remains unsupported for these personal admin-token operations. Current CLI admission also rejects an administrator bearer. That running rejection is not the rule. A currently usable administrator credential is eligible for them under the administrator eligibility rule in [Core Permissions](https://github.com/lingkaix/openkit/blob/main/docs/core/permissions.md#administrator-eligibility). Use Web **My admin access** for the ordinary session path. The CLI does not acquire or persist Better Auth cookies and does not provide a cookie jar for an ordinary caller.

Use `token.list` and `token.revoke` to inspect and administer existing tokens. With explicit administrator direction, describe `token.create` or `token.rotate`, supply the shared request fields through stdin, and include a safe named local `destination`; rotation also requires `tokenId`. Both require server-admin bearer authority in server mode. The named destination receives the secret directly, while the CLI returns redacted records and storage metadata. Reusing a name deliberately replaces only that slot; it never replaces or selects the endpoint administration credential. Inspect inventory after mutations, delivery failures or unknown results before making another request. Issuance and local delivery are separate effects: storage failure does not undo issuance or rotation, and the secret cannot be retrieved from NanoCore.

Ask for explicit deployment-administrator direction before enrolling, issuing, rotating, aborting rotation, revoking, or decommissioning NanoHost transport credentials. Those operations write secrets only to the named execution-host slot and return redacted inventory; they do not return raw tokens through the CLI. Re-read the token list after each mutation and do not invent a second delivery path.

Use vault status, bootstrap, unlock, lock, grant, injection-record, use-record, and rebind capabilities only through their public operations. Treat a successful local schema check as neither vault authorization nor evidence that a secret was injected or used.

## Inspect database migrations

Use the public `storage.layout-report` operation to inspect applied migrations for Core, User, and Workspace databases; Web and Skill/API report the same scope-owned facts. NanoCore executes pending packaged SQL through Drizzle during the owning database startup/open path. Missing SQL or journals and failed pending migrations are failures, not an empty or successfully upgraded database. Drizzle does not validate historical SQL hashes; its ledger is not proof that a rewritten unpublished baseline matches existing tables. Do not infer rollback safety from a healthy fresh database or from an unchanged initial migration name.

Before the first release, developers may consolidate schema changes into `0000`; an older deployed test baseline may therefore need an explicitly authorized stopped-process cutover or recreation. Startup never resets it automatically. After release, schema-changing releases append migrations instead of rewriting applied SQL. A previous App image does not undo committed database changes. Respect the App update helper's current compatibility assessment and supported recovery boundary; this Skill does not perform host-side database edits, service stops, or automatic restores.

## Operate runtime and scheduled work

Read current runtime configuration and stale-session state before changing it. Report any restart, stale-session, or reconnect consequence returned by NanoCore without inventing a compatibility or hot-reload guarantee.

Read an automation's current definition and status before creating, changing, or deleting it. Confirm external effects and provider spending separately from schedule configuration.

For retained Worker environments, discover `worker-environment` and describe the exact operation before calling it. Technical preparation, activation and storage maintenance require current deployment-administrator authority plus independent access to the Agent configuration and every affected Workspace and source audience. Listing or selecting an environment is not attachment authority. Selection requires access to the exact target Thread as well as every contributing source. A currently usable administrator credential has that access under the administrator eligibility rule in [Core Permissions](https://github.com/lingkaix/openkit/blob/main/docs/core/permissions.md#administrator-eligibility). A status response contains separate Core association and host storage observations. Retain both when they differ: host availability or no observed host attachment does not clear a Core reservation, authorize reuse, or prove completed work. Preserve the exact prepared candidate, observed revisions and affected group; human activation confirms that complete payload. A stale or unknown result requires status inspection, not a new blind activation. Whole-storage purge is separate from normal Worker close and image replacement.

Preparation and activation are global operations for one exact Server Agent manifest; do not add a Workspace path or profile target. Initial preparation uses `mode: "prepare"`, target `{ "kind": "agent", "agentId": "..." }`, an authored runtime image declaration, and configuration `{ "fileId": "agents/...agent.jsonc", "expectedRevision": "<sha256>" }`. Use `replaceNow` only for immediate replacement of current resident work. Its nonempty `prompt` is the actual successor Turn input and must come from the administrator's words or explicit adoption; never synthesize hidden user speech. Without `replaceNow`, the change applies only to later admissions. Preserve the separate immutable version-1 authored and resolved candidate Artifact references. Result-only recovery uses `mode: "recover"`, a fresh request id, and the exact authored candidate reference; it resolves the original result without rebasing or repeating image effects.

Activation sends the exact resolved candidate, Agent target, configuration revision, affected storage revisions, optional `replaceNow`, and the payload-bound confirmation. Display and review the complete prepared response first. After the human approves that exact payload, copy its `activationConfirmation` preview unchanged into the activation request; the preview is not approval or authorization. A changed field requires a new preparation and review. List, select, status, and purge remain Workspace-scoped.

Use `administration.conversation-submit` for the private built-in administration Assistant. On the first request omit `threadId`; NanoCore establishes the validated administrator’s own private Quick Chat home if absent, including for a server-admin bearer that has never signed in through the Web. Retain its returned Thread identity for subsequent administration submissions. Do not substitute a project Task Thread or another user’s private Thread. Ordinary conversation and administration are separate entry paths; the Assistant may inspect and prepare, while activation and purge remain human-confirmed public commands. It never needs an administrator token in its prompt. The separately installed `openkit-ops` Skill explains image changes, whole-volume retention, backups and authorized host recovery without adding host privileges to this client.

The private administration Assistant can inspect NanoHost through its read-only `nanohost.runtime-target` Tool, using the same configured-target observation as Web and public Skill `nanohost.runtime-target` with `{}`. Current deployment-administrator authority is required on each call. NanoHost is an execution host, not an LLM Provider; an absent Provider entry or empty Worker-environment list does not establish its state. Read the readiness flags and observation timestamp together: this is Core's stored observation, not a fresh host probe or a promise that the next Task will launch. Missing or unavailable observations must be reported explicitly. This Tool cannot select another host, enroll credentials, restart, activate an image or repair the host.

For App-update connection diagnosis, search `app-update` and describe `app-update.status`. Read a known receipt by `requestId` without starting replacement; a missing receipt is distinct from an unusable SSH identity. For an `app_update_unavailable` identity or known-hosts error, an operator checks the configured paths, file type, ownership, permissions and App mounts. Restore missing existing read-only file binds at `/run/openkit/app-update/id_ed25519` and `/run/openkit/app-update/known_hosts` while preserving every other current mount. Do not mint keys, copy key material, bypass SSH host-key checks, or escalate tokens. This Skill has no Docker or SSH authority. `app-update.prepare` is not activation and does not replace the App; `app-update.start` remains the replacement after explicit maintenance consent.

A host helper can remain reachable while its separate `adminTokenFile` is stale after a server rebuild; failed authenticated diagnostics are not proof that the public Skill credential is invalid. An authorized host operator refreshes that existing credential and rechecks the helper. For repository-backed deployments, the operator declares the existing read/write `/srv/repos` mount with the helper’s protected `repositoryDirectory`; the update preserves the exact configured source and refuses undeclared or mismatched mounts before interruption. Neither Web nor this Skill can add mount paths to an update request.

If the configured NanoHost reports `ready: false`, App update refuses before acquiring the candidate or stopping the current App. Inspect `nanohost.runtime-target` and arrange separately authorized execution-host recovery before preparing another update. A healthy App or reachable helper does not establish NanoHost readiness. A deployment with no configured NanoHost remains supported; do not remove a configured target to bypass its readiness check.

For remote-commit updates, the host helper initializes its configured source cache when missing or empty. A nonempty non-Git directory or a symbolic link at the cache or its `.git` entry is refused before fetch and before stopping the App. Inspect the saved update receipt and ask an authorized host operator to correct that cache configuration; do not delete existing contents or retry an unknown update. Operator-staged source archives remain a separate path.

An accepted administration command can still return `outcome: refused` and a failed Turn. `administration_execution_failed` may identify missing admitted model selection or responses/tool-calling support; inspect the explanation and authoritative model metadata. `context_compaction_unavailable` identifies a missing context policy after capability admission. Neither refusal proves an inference ran.

## Diagnose a missing repository or stale Worker source

A Worker Git data source remains a catalog input and is not the Workspace host repository resource. That host repository resource, its `repository.list` and `repository.diagnostics` surfaces, and its write settings are a legacy surface retiring under the hosting decision. This reference gives no instruction to create, correct, or rely on that resource. A ready App does not prove a host checkout is present, and a missing container bind is not authority to add one. A server-admin token or the built-in administration Assistant does not grant Docker or SSH authority. Hosted writes are selected vendor MCP effects under their own current authority and approval, and this reference does not describe that default path as currently working.

A legacy `git_repository_missing` failure identifies an incomplete host-repository cutover, not authority to create a new host apply target. Preserve the failed Turn, exact input identity, and available review/recovery evidence. Do not substitute another repository, modify session records, or replay the failure. A separately authorized recovery Task must inspect any retained changes under the existing storage and audience rules.

A Worker Git source intentionally selects an immutable commit. Updating the App or the host checkout does not advance that source. With deployment-admin authority, read the Workspace data-source configuration using `runtime.file-read`, retain its exact revision, and change only the intended locator commit to an obtainable revision through `runtime.file-update`. Inspect the write result and re-read the file. Run `runtime.reload` with `dryRun: true` first, then apply the supported safe reload and inspect its result. Workspace data sources are session-scoped: the updated source applies to future sessions, while accepted existing session snapshots retain their original source. Verify a new Worker's reported checkout revision before claiming the repair complete. The Web Configuration editor uses the same configuration and reload boundary. The administration Assistant may diagnose or prepare supported changes, but never bypasses payload-bound human confirmation.

## Operate repositories and portable data

The Workspace host repository resource, its diagnostics, and its write settings are a legacy surface retiring under the hosting decision. This reference gives no instruction to confirm a host repository identity, create or correct that resource, write or push through it, or re-read a Git push record. Hosted writes are selected vendor MCP effects under their own current authority and approval. A legacy host missing-review exemption does not waive that authority or approval, and this reference does not describe the default vendor path as currently working.

Host repository commit-on-apply belongs to the retired Git apply path. Do not enable it as a step toward the accepted hosting workflow. Non-Git review/apply retains its own acceptance and result checks; selected vendor hosting calls require their separate current authority and approval.

For backup, export, import, or workspace portability, confirm the source, destination, workspace scope, overwrite behavior, and sensitive-data handling described by the operation. Verify the durable result after completion and report partial, rejected, or recovery-required outcomes without local repair.

In server mode, portable archive download and import through Web **Settings → Portability** use the signed-in canonical Better Auth user session. The bundled CLI `workspace.archive-download`, `workspace.archive-import-dry-run`, and `workspace.archive-import` operations are local-mode only: they use the implicit local actor and do not store cookies. That local-mode limit and the absence of a cookie jar are current ordinary-caller CLI behavior. That running rejection of a server-admin bearer is not the rule. A currently usable administrator credential is eligible for archive export and import of any Workspace under the administrator eligibility rule in [Core Permissions](https://github.com/lingkaix/openkit/blob/main/docs/core/permissions.md#administrator-eligibility).

On Web Portability, **Export workspace** (`exportWorkspace`) then **Download archive** (`downloadWorkspaceExportArchive`) for a current-format `.openkit-workspace.tar.zst` file. To import, choose that exact portable tar archive in **Portable archive**, **Review import** (`dryRunWorkspaceArchiveImport`), and only then **Import workspace** for the same selected file (`importWorkspaceArchive`). Do not import a different file than the one reviewed.

Use `workspace.archive-download`, `workspace.archive-import-dry-run`, and `workspace.archive-import` for the supported local-mode portable archive path. Download writes only a new exact destination and never overwrites a file or link; a failed transfer leaves that partial destination for explicit inspection or removal rather than racing pathname cleanup. Dry-run and import read one exact regular non-link source as a one-shot stream, so preserve the original archive and invoke a new operation for each retry.

Use audit and usage reads to explain recorded effects and consumption. Audit event time is `occurredAt` when present, otherwise `createdAt`; permission decisions use `createdAt`. Keep missing time unknown. The Web audit rows display those same timestamps in the browser's local timezone. Do not treat those projections as permission to repeat an operation or as a substitute for the owning durable record.

For existing Provider model catalogs and Gateway logical-model bindings, ask `administration.conversation-submit` to inspect the target and propose the update. Review the exact before/after candidate Artifact with the user, including its source revision and restart impact. Only after the human confirms that exact digest, invoke `administration.configuration-apply` with the returned candidate and confirmation plus a fresh request ID. A broad setup request does not confirm an unseen candidate. Exact request replay reads the saved outcome; stale candidates need a new proposal and confirmation. If application reports recovery required, inspect configuration and audit before any new request. Persistence does not establish Provider readiness, and restart-required configuration does not restart the App automatically. Credential bindings and endpoint changes remain on the existing setup forms.

Web **Settings → Administration** presents the same private catalog candidate under the administration conversation. **Review configuration** shows its target, before/after values, source revision and restart impact; **Apply configuration** confirms that exact candidate through the same public operation. Web derives one stable request ID from the complete private candidate identity, so confirming that same candidate after a reload reuses the original command. A failed or unknown application is not a retry instruction: inspect the configuration and audit before requesting a fresh candidate.

## Hosting credentials

Platform-managed hosting credentials stay in the Gateway. A runtime-env `github-token` is the separate user-space read or native-push path, not the default hosting route. The current default gateway-only grant still targets the legacy host-push capability; it is not evidence that the selected vendor MCP credential flow is ready. OpenKit adds no native-push mechanism. Native Git push remains optional user-space configuration requiring a user-injected credential and admitted git-receive-pack egress.

Use `question.answer` to answer a pending user-input request and `pending-request.withdraw` to withdraw a pending request, only from explicit user direction. The responsible user, or the user of a currently usable administrator credential under the administrator eligibility rule in [Core Permissions](https://github.com/lingkaix/openkit/blob/main/docs/core/permissions.md#administrator-eligibility), may do either. The recorded actor is the person who decided. Ordinary Workspace membership remains the ordinary caller's authority. A secret question cannot be answered. These commands target the exact pending request, whatever the status of the raising Turn; they do not resubmit that Turn.

Read `vault.reference-list` and `vault.grant-list` after each mutation. Replace material with `vault.secret-rotate` using `{ workspaceId, referenceId, material }` on stdin. `vault.grant-revoke` removes one grant's authority; `vault.secret-revoke` destroys all stored versions and revokes dependent grants. Both retain non-secret history. For a replacement after revocation, create a fresh reference and grant. On an unknown or failed write, inspect inventory before a new request; do not infer completion or repair storage.

Web administrators can use **Settings → Vault backend**, unlock if needed, select the Workspace, and add or rotate a secret through its password field. **Revoke** destroys material; **Revoke grant** invalidates one grant. Secret values are never displayed after submission.

## Consolidate deployment model metadata

Keep upstream facts in the vendored models.dev snapshot and deployment policy or missing-model metadata in `model-catalog.jsonc`. Its outer key is the exact Provider vendor (or profile ID when vendor is absent), and its inner key is the exact native model ID listed by that Provider. Effective leaves compose snapshot, extension, then profile; remove superseded profile leaves when centralizing limits, or they will continue to override the extension. No subscription-family cap overrides the composed context. Preserve subscription slot bindings and API-key references. Validate the complete candidate, inspect revision-checked writes, and honor the returned restart requirement; a stored file alone is not evidence of active metadata. Check that logical-model compaction threshold plus its output reserve fits the effective context, then verify a bounded real request and its recorded route.

Explicitly configured Codex and xAI subscription models may be newer than the bundled model inventory. Supply the exact model ID and effective context limit in the existing Provider/catalog configuration; dispatch keeps the selected account slot and its authenticated transport, and unknown pricing remains unknown. Catalog presence alone does not prove inference.

Internal Chat and administration or Goal planning calls use the selected subscription model through the same Gateway. A connected account or a successful quota read alone does not prove inference: confirm a completed answer and its actual Gateway usage. Private session attribution belongs to OpenKit dispatch context, not an extra provider-native request field.

## Remove a Provider profile or subscription account

With explicit administrator direction, read the exact Provider file through `runtime.file-read`, then call `runtime.file-delete` with its `id`, `kind: "provider"` and current `expectedRevision`. References do not block removal. Key profiles revoke their Vault API-key reference before file removal; unsupported external references and Vault failures require inspection rather than a claimed success. Deleting a subscription-backed profile leaves its shared account slot untouched. Safe reload reports pending restart and retains the active Provider registry; strict reload rejects the restart-required candidate. Restart through the deployment's existing authorized procedure, then inspect reload warnings for unavailable authored routes. Removal preserves route order and does not promote a backup.

Use `provider-subscription.account-delete` to remove the exact subscription Provider and account-slot pair independently. This operation cancels and settles pending login, revokes local credential material and its Core authority, and then removes account metadata. Referencing profiles and routes stay unchanged. Inspect a reported partial failure through the existing account and Vault owners before a new request; do not restore credentials or replay effects automatically.

## Inspect subscription quota and costs

Subscription accounts belong to the deployment, not the selected Workspace. Use `provider-subscription.account-quota` with `{ "subscriptionProviderId": "xai", "accountSlotId": "xai-plus-k" }` through stdin after selecting an existing account slot. Both xAI and OpenAI Codex support this read. An available result includes `observedAt`, optional `planType`, and `windows` with only supplied percentages and period fields. `startsAt` and `resetsAt` are period boundaries; `observedAt` is the read time. Format times in the user's local timezone, with full instants and timezone inspectable. Do not invent periods or reset times. Codex reports primary and secondary windows when supplied, with optional positive `limitWindowSeconds` from the provider. Label a reported 604,800-second window Weekly; otherwise use an exact duration such as 5-hour for 18,000 seconds. Without duration retain Primary/Secondary, and keep the exact reset time. Zero or negative private durations do not create a public duration or guessed period. xAI reports only its actual included period, with `periodType` weekly/monthly when supplied; absence does not justify a second window.

Missing percentages are unknown, never zero used or full remaining quota. Explicit zero is zero used and 100 percent remaining. A valid period without usage stays visible without a meter. Display one percentage per window: remaining when supplied, otherwise used. `temporarily_unavailable` means the current billing query failed, distinct from a successful observation missing its usage field, and is neither zero remaining nor an authentication verdict. Codex `authentication_required` means its quota request returned 401 and the rejected credential was still selected at recheck. Offer the existing login operation for that exact pair; do not claim permanent refresh-token expiry, remove credentials, or infer this state from a timeout, 403, 429, 5xx or malformed quota response. Fresh xAI discovery metadata can survive a billing failure: `accountObservedAt` timestamps that same request's account observation, and `subscriptionActive` records the official Build subscription-eligibility check, not effective coding permission or guaranteed inference. Never reuse an earlier observation as current after a failed refresh.

The optional xAI `billing` object reports `currency: USD`, `prepaidBalanceCents`, `onDemandUsedCents`, `onDemandCapCents`, and `sharedAllowance` only when provided. Amounts are signed integer cents. A returned zero is known zero; omitted fields are unknown. Zero prepaid balance does not mean the included subscription allowance is exhausted. The adapter handles the vendor protocol's zero-valued amount object without collapsing a missing amount to zero.

Read auto-top-up only when the user requests or expands costs: `provider-subscription.account-auto-topup` with the same xAI pair. This separate read returns its own `availability` and `observedAt`, optional `enabled`, and USD-cent `thresholdCents`, `amountCents`, and `monthlyCapCents`. Missing enabled state is unknown; explicit false is disabled. Never infer enabled state from a saved payment method, balance, or extra spending. A rule query failure does not discard the separate quota observation. The operation neither changes rules nor triggers payments.

Web **Settings → Gateway** uses the same fields, an account-scoped Refresh action, and collapsed Balance and costs and Account settings. Refresh only the selected account; no background polling or automatic account switching is needed. Account management is separate from observation: never log out, rebind credentials, or alter billing merely to refresh. No provider-private identity, raw billing payload, or credential is returned.

## Pi Task readiness

Pi Task execution requires a Worker image that implements the controlled internal-Gateway route and a newly resolved package with complete effective model parameters. A connected Grok subscription or a successful Assistant answer alone does not prove Pi readiness. Keep upstream credentials in NanoCore; never copy them into a Worker or provide a user-authored models.json. The adapter generates its own temporary native descriptor from the admitted logical model. Missing parameters on older packages mean not recorded, not a zero context window; inspect current model configuration and request a fresh Task after correcting missing metadata. Pi reuses its exact native conversation only through an admitted AgentSession binding: each Turn starts a fresh process with that binding’s validated session file and the current model descriptor. Retained workspace files alone do not authorize selecting another conversation or loading native configuration. Missing or mismatched bound session state is an error, not permission to silently start a replacement; inspect the failed Turn and request a fresh Task when a new conversation is intended. Closing a binding preserves retained native files but does not let its successor resume them automatically. Selected MCP execution remains unsupported. Verify real tools, consecutive Turns and the existing review/apply result before treating a deployment as usable.
