# Storage (`@openkit/storage`)

Storage locates bytes and enforces the caller's current admitted access. It does not own Sources, Artifact versions, Knowledge, Policy, publication, retrieval or media processing. The accepted owner is [File Storage And Knowledge Packages](../../docs/specs/20261018-file_storage_and_knowledge_packages.md).

## Contract

`StorageService` uses asynchronous JSON requests and responses. Byte chunks use base64; temporary staging uses opaque handles. No native file handle, callback or shared mutable object crosses the service contract. `ContentReference` comes from `@openkit/protocol`; do not create another descriptor or URI codec.

`LocalStorage` accepts configured mount roots and a staging root. The trusted NanoCore caller supplies a fresh `StorageAccess` on every operation. Its `basis` distinguishes an explicit current `lease` (actual grant ID, expiry and revocation), request-local `knowledge` authority and native `work-capture` admission (both without grant ID or expiry). Knowledge authority is restricted to a declared managed raw root and its exact `sources/` prefix; external/host mounts and Worker exposure require leases. Native Knowledge admission owns current membership and publisher checks; Storage cannot turn metadata into permission. This projection is not a new grant, grant issuer or retained lease store. Do not expose the backend directly to an untrusted client. Roots, grants and owner publication remain outside this package. Configure physical roots without symlink components. The local backend pins directory traversal through an OS descriptor namespace; platforms without that primitive return unavailable/unsupported instead of falling back to mutable pathname traversal.

`work-capture` uses explicit `knowledgeBaseId: null` only for a configured Server or Workspace `backend-evidence` mount. The native owner supplies the existing scope's `evidence/backend/` root, authorizes current record access before each operation and confines digest objects to `sha256/<digest>`. This basis cannot borrow Knowledge, User, external or host mounts. Native references support whole-source or byte ranges; scans are confined to the digest directory. Equal digests grant no read permission. The shared Knowledge case still requires its exact real Knowledge Base ID.

`stat` observes original identity and sniffed media. `read` verifies the entire original against captured digest and size with bounded memory before returning a bounded requested byte chunk; it does not retain an original for replay. Missing or changed originals return unavailable. Only whole-source and byte-coordinate references support raw reads; page conversion belongs to Derivation; time and frame references are deferred.

`scan` examines at most the requested number of directory entries per call. A name filter can therefore return an empty page with a continuation. A changed directory or unusable cursor requires a new scan. Stateless continuation seeks at most 65,536 prior entries; a cursor beyond that capacity explicitly requires a rescan and cannot establish complete discovery of a larger directory. This is shallow metadata discovery, not a recursive index or durable change feed.

Staging uses `beginStage`, repeated bounded `writeStage` calls and `finishStage`. The owner consumes sealed bytes through `readStage`, performs its own Source or Artifact publication, then calls `discardStage`. Storage never writes the destination original. Handles are temporary and bound to their admitted basis and exact owner/mount/prefix. Lease handles expire with that lease; Knowledge and work-capture handles have no invented expiry and are closed by their owning native request. A process restart invalidates them. The caller owns cleanup of its dedicated staging directory after restart, when no live process uses it. `close` removes this instance's remaining temporary stages.

## Commands

`ensureCanonicalDirectoryAsync` and `syncCanonicalDirectoryAsync` alias the existing internal `ensureTreeDirectory` and `syncTreeDirectory` functions. Storage exports these canonical names directly, so callers share one implementation. Recursive creation commits each parent before creating its child; path and descriptor checks reject final links and non-directories, and descriptors close on success or failure. The caller retains publication authority.

Internal trusted Node tree helpers in `local.ts` move the existing ZIP physical staging, streamed writes, directory moves/syncs and recursive cleanup into Storage. They are in-repository helpers, outside `StorageService`; the ZIP caller retains exact source identity, caps, capacity accounting, manifest, authorization, publication ordering and in-flight joins. Private member bytes keep close-only completion and inventory-based crash rejection; metadata is synchronized after its accounting callback. Directory move and sync remain separate so the owner preserves its current acknowledgement and uncertain-outcome boundaries. No tree handle registry or publication authority is introduced.

Trusted Node owners can use `createDirectoryExclusive` for a synchronous single-directory create with caller-selected mode. It creates no parents and preserves `EEXIST`; the caller owns current admission, directory identity and any cleanup. This primitive alone makes no durable-publication claim. They can use `copyVerifiedFile` for bounded independent copies or digest verification, and `publishDurableFile` for create-only private metadata publication. Both pin directory traversal, reject links and source changes, and synchronize output bytes before acknowledgement. Publication also synchronizes its parent entry. `removeDurableFile` retires one caller-owned regular-file entry through the same pinned parent and acknowledges only after parent synchronization; an absent-entry retry still synchronizes that parent. It does not select content, revoke publication authority or remove a directory. `copyFileForCut` uses the same confined independent-copy mechanics but returns explicitly unverified private bytes without a digest or payload sync. It preserves inode, link, size and binding checks. Its caller must verify and synchronize durable destination objects before publishing any seal; a completed cut copy alone is not durable publication. NanoCore's snapshot owner selects paths, reserves capacity, protects source lifetimes and decides when a seal can become visible; these helpers add no Storage service request or retained authority.

`syncVerifiedFile` synchronizes an exact caller-owned regular file by inode and byte length. `changeVerifiedFileMode` changes only that verified file's mode. `publishVerifiedFileReplacement` replaces an exact same-directory destination inode with the caller-verified candidate, then synchronizes the parent before return. These operations do not inspect domain receipts, hash whole candidates, choose authority, or provide rollback after a rename. The caller retains its existing admission and lifecycle fence; a failure after replacement remains an uncertain publication outcome.

Trusted Node callers also share the synchronous canonical directory and tree primitives (`assertCanonicalRegularFile`, `assertCanonicalDirectory`, `ensureCanonicalDirectory`, `syncCanonicalDirectory`, and `syncCanonicalTree`). These preserve link refusal, recursive parent publication, child-before-parent synchronization and descriptor cleanup; NanoCore retains domain admission, capacity and publication decisions.

Trusted canonical staging-tree publication also uses Storage through `syncCanonicalTreeAsync`, `publishCanonicalPath` and `publishCanonicalPathAsync`. The same tree synchronization precedes rename, followed by destination and any distinct source parent synchronization. Synchronous post-rename acknowledgement failures retain `CanonicalPublicationError` and its cause; asynchronous failures retain their original error. A renamed destination is not rolled back after acknowledgement failure. These helpers select no domain authority or capacity admission.

Trusted canonical byte reads and integrity measurement also use the shared local owner (`readCanonicalTextFile`, `readCanonicalFile`, `measureCanonicalFile` and `measureCanonicalFileDescriptor`). The original no-follow regular-file checks, link-race error conversion, positional digest reads, concurrent-change refusal and descriptor ownership remain unchanged. The caller retains domain admission; measurement grants no read or publication authority. An optional exact byte length on `readCanonicalFile` requires a complete immutable read of precisely that size and refuses file changes; calls without that argument keep their original behavior.

Trusted catalog callers share `materializeSnapshot` and `directoryContainsFiles` for physical snapshot staging, publication acknowledgement and non-staging file observation. These internal Node helpers preserve the admitted entry bytes, executable modes, existing-target synchronization, failure cleanup and `.staging` directory exclusion. Their structural entry input matches the existing caller-owned tree entries; catalog validation, hashing, revision checks and retention decisions remain with NanoCore. They add no StorageService operation.

Trusted Artifact byte staging uses `stagePrivateFile` for the existing durable pipeline and request-local file lifetime. The caller supplies its concrete byte counter, integrity and cleanup error constructors, reservation and original source-inspection inputs; their calls keep the original order. Partial writes update actual capacity before completion, cancellation joins an in-flight write before close/removal, and successful capture synchronizes the file and request directory before return. The existing ZIP member writer remains close-only. `createPrivateTreeSync` and `removePrivateTreeSync` preserve synchronous version staging and handled caller-selected compensation. Artifact identity, admitted metadata, current authority, publication, Audit and receipts remain with NanoCore. No StorageService operation or retained staging authority is added.

Trusted PDF and vision callers use the internal `withStagedMediaSource` for the complete private input lifetime. It preserves bounded copies, exact digest verification, private-directory and read-only-file modes, cancellation of a stalled iterator, consumption before cleanup and capacity retention when cleanup is uncertain. The caller supplies its existing reservation and actual failure constructor; source metadata validation, processor limits and supervision, current authority and disclosure remain with NanoCore. Private input completion remains close-only. This helper adds no StorageService operation or retained authority.

NanoHost export and collection callers reuse `createPrivateTree`, `movePrivateTree` and `removePrivateTree` for their private staging lifetime. NanoCore retains byte verification, descriptor synchronization, capacity, cancellation, current authority and original consumer and receipt ordering. These internal helpers add no publication acknowledgement or retry.

Trusted retrieval adapters use `writeVerifiedRepresentation` for their existing complete private copy, close and current-source digest proof, with the original input, source and reservation objects. Their authority methods retain their receivers and call positions; the helper selects no authority. `removePrivateTreeStrict` preserves recursive cleanup without force, including absent-path failure, before caller-owned capacity release. `measureDerivedTreeBytes` preserves recursive no-link/non-regular refusal and the caller's fixed per-recursion stopping ceiling through its actual failure constructor. NanoCore retains eligibility, configured publication capacity, derived index placement and Kernel request supervision. These are internal Node helpers, outside StorageService, with no new state or preparation cache.

Internal physical helpers have package-local behavioral tests over private temporary files. NanoCore composition tests do not contribute to Storage's package coverage. A body MOVE into this package must carry its package-local checks and pass the unchanged Storage coverage thresholds through the CI owner recipe; caller integration tests remain separate evidence. The tests cover byte identity, private lifetime, cancellation, cleanup, publication acknowledgement and refusal behavior rather than invoking helpers only to count lines.

Trusted filesystem rollback cleanup uses `removePrivateTreeInventory` for the complete caller-validated removal batch. It removes selected files, then empty directories from children to parents, then the marker and root; only absent directories are ignored. NanoCore retains root confinement, marker validation, inventory selection, current admission and observation ordering. Unknown residue is not recursively removed. This internal helper adds no StorageService operation.

Internal telemetry helpers in `local.ts` perform the existing checked directory inventory, current filesystem headroom observation and segment descriptor effects. The trusted NanoCore caller retains queue and retention policy, current reserve authority, serialization, names, rotation and shutdown. Segment completion is close-only and disposable; these helpers add no StorageService operation, durable delivery acknowledgement or retained state. Package-local real-filesystem tests cover confinement, capacity, exact writes, partial-write refusal and descriptor cleanup.

The internal `materializePrivateTreeSync` helper resets a caller-owned private root and writes its already-validated tree with the original recursive directories, exclusive file creation and executable modes.
