## Changes since the previous candidate

- When a Workspace index set is missing or invalid, NanoCore rebuilds it at boot. NanoCore reports a completed rebuild as information. A healthy deployment can become ready (#217).
- NanoHost's member-exit report names the first failing member or watched task when known. It distinguishes an observed exit, task completion, and unavailable proof (#181).
- When an App container lacks a required log setting, the App update helper refuses it at prepare time. The refusal names that setting (#215).
- NanoCore writes the resource catalog and the thread-visibility file through a durable atomic write. A crash leaves the previous file or the complete next file.
- Release notes come from a reviewed input file. The notes list the image digest of each platform (#216, part of #206).
- NanoCore publishes a new Thread, Turn, Artifact, or AgentSession directory by one rename. A crash during creation leaves no partial directory that stops the next start.
- Registry preparation and `nanohost image import` accept the image index digest from these release notes. NanoHost selects the manifest for the host platform (#206). The operations Skill removes the manual platform selection.

### Release process and documentation

- Release validation now uses outcome stories on the published prerelease.

## Known issues

These known issues do not block this pre-release and are tracked in #177.

### Work and replies

- You cannot yet redirect a task while it is running (#121).
- You cannot yet choose or create a shared Workspace sandbox for a task (#122).
- A task ending normally does not prove its objective is complete; inspect its output and request another step if work remains (#128).
- A reported Pi stop before finishing has not been reproduced, and the available records do not establish its cause or timing (#130).
- Interrupting a reply can delay its final status by about 30 seconds and leave its final evidence incomplete (#179).
- Some streamed replies fail without enough diagnostic detail to identify the cause (#180).
- A model call can fail before any output with only a generic provider error, and a Pi task then reports a correlation failure instead of naming the failed call; the cause is not recorded. Work done before the failed call can still have succeeded, so inspect the Task's Artifacts and completed effects before asking, in a new message, for only the work that remains (#186).
- A failure message can still mention the first cleanup failure after later cleanup succeeds (#182).
- After a Goal's Plan is approved, its Coordinator may not start any Task: in recent acceptance runs the Goal kept its card with no Task, and in one recorded case the Coordinator could not choose a verified Worker Agent until the work card supplied its id; the cause is not yet established (#142).
- Worker runtime identities across the four current versions have not yet been qualified for general work, and an audited older Pi fallback frames non-software work as coding (#191).
- Chat can answer an execution request, such as comparing contracts, instead of handing off the work; start execution work as a Task (#192).
- The ordinary Assistant's planned Core Tool and Skill resource integration remains deferred (#144).
- Internal Agent runs, including Goal coordination, cannot shorten their context and continue once they reach the configured context limit (#125).
- After an unsupported Gateway feature error, choose a compatible route and start the Task in a new Thread if you need a fresh native conversation (#129).
- An older recovery checkpoint can remain marked as requiring recovery after later work reuses the same AgentSession and changes its current environment package (#132).
- Starting a Task selects the first ready Worker Agent; naming an Agent in the prompt or choosing a model does not select that Agent (#133).
- The conversation target catalog lists only Workspace-pinned Agents, so a globally configured Agent can be absent from the starter choices (#134).
- A Worker can write a report outside its permitted output folder and then be unable to publish it; use the eligible folders listed in the Artifact submission tool's description (#140).
- A review Worker cannot yet receive selected Artifacts from a prior Task through a general cross-Task delivery path (#141).
- A Worker can read permitted peers in the same Sandbox but cannot yet send a peer a question (#150).
- Worker peer reads are limited to peers in the same Sandbox, with no general permission-based read path across Sandboxes (#151).
- Streamed activity still uses synchronous storage writes that can delay processing; the recorded cost was measured locally and has not been qualified on deployment storage (#163).
- Failed-start maintenance can take longer as retained work history grows; the measured scaling cost does not establish the cause of earlier outages (#164).
- Large streamed tool arguments can incur repeated parsing cost; the local measurement still needs qualification against the current Gateway version (#167).
- If the first native conversation's resume proof is not retained, later work can start a new native conversation (#168).
- After the system clock moves backward, continuation can consider successor session history in the wrong order (#169).
- A Goal that asks for monthly work does not run automatically each month; initiate each cycle manually until calendar recurrence is supported (#194).
- Only one Worker Turn runs at a time across the deployment, so work in unrelated Threads and Workspaces waits in the queue (#204).
- Some internal model calls fail before output with only an unknown transport failure in the log. The retained evidence lacks the provider status and cause (#207).
- Knowledge search misses a Chinese or Japanese word that appears inside a sentence (#222).
- Each Workspace save rewrites every Thread file, including a Thread that did not change. The cost grows with the number of Threads (#224).

### Tools and GitHub

- When NanoCore observes another tool's description change on the same MCP server, it can refuse a pending approval although the requested tool is unchanged. Request the operation again. The old approval cannot run it (#117).
- When Codex must shorten a conversation to fit the context limit, a failure may be reported without identifying that step as the cause (#123).
- Provider acceptance of past tool calls during conversation shortening remains unproved; successful ordinary continuation does not verify it (#124).
- New tool calls in Chat Completions requests are not checked against the request's listed tools as they are in Responses requests (#127).
- Upstream MCP integrations that require NanoCore-managed OAuth are not yet supported; current credential delivery uses static raw or bearer credentials (#146).
- MCP server configuration does not yet support an explicit map of ordinary non-secret HTTP query parameters (#147).
- Agents cannot yet withdraw a pending tool request themselves (#149).
- Available vendor MCP tools do not prove that access is limited to the intended repository; acting identity and repository restrictions still need qualification (#170).
- Shared server-scoped MCP entries and their Vault credentials cannot yet be created or used; configure the MCP binding and credential separately for each Workspace (#203).
- The packaged App proxy returns the Web page with HTTP 200 for agent-facing `/v1` Gateway requests at the public origin, so remote agents and SDKs cannot parse them as API responses (#209).

### Host and deployment

- The installable NanoHost archives do not yet establish supported Worker Agent execution readiness while the R001 runtime gate remains open (#120).
- Package downloads can be refused when processes sharing one socket have different policy identities; the recorded denial does not establish which identity was wrong or whether it caused the reported download failure (#135).
- A package download can fail before an HTTP event without diagnostics that connect the failure to the affected request, leaving its cause unproved (#136).
- Idle backend bindings are not automatically evicted to make room for other work (#157).
- Workspace exports are for outside analysis and cannot be used for lossless re-import; a recoverable Workspace and whole-server backup mechanism still needs a design (#158).
- This release supports one execution backend and cannot place work across mixed backends (#171).
- Execution capacity is not a per-user quota system, and execution quotas are not yet implemented (#172).
- Queued work uses first-in-first-out admission, with fairness and aging policies beyond that order still deferred (#173).
- Dynamic fleet selection and placement affinity are not yet supported (#175).
- Multi-process NanoCore scheduling, high availability and hot failover are not supported in this release (#176).
- An App update receipt's status can be blocked by an outdated compatibility assessment, while a helper that exits before reporting its result exposes only a missing-observation error; re-author the assessment for a release candidate before preparing or starting another update (#197).
- An App update does not replace the installed App update helper, and the release does not publish the helper as an asset. An existing deployment keeps its earlier helper, including its refusal behavior, until an operator installs this release's `scripts/docker/app-update-helper.py` from the tagged source revision (#230).
- Worker checkpoint maintenance can log `recovery_required` while a new Workspace's database is still being created; the observed warnings stopped once the database existed and showed no data loss or damage (#208).
- NanoCore records HTTP request spans only. Those spans do not show where a failed Turn stopped (#219).
- NanoHost has no trace for epoch start, sandbox start, member start, or member exit (#220).
- An operating-system crash or power loss can leave some records empty, truncated, or missing after publication without disk synchronization. Affected records include Vault files, backup manifests, Turn feedback, provider accounts, authored configuration, catalog snapshots, Workspace sync data, Worker evidence, and new Workspace directories. A process kill after the rename does not cause this power-loss failure (#223).
- An operator cannot see cleanup work that is waiting, retrying, or failed (#226).
- `nanohost image import` of a multi-platform image index writes a projection in the system temporary directory. A small temporary disk can reject a large image. The projection does not count against Image Store capacity. `nanohost image list` omits an interrupted projection, so `nanohost image remove` cannot delete it. A per-platform archive imports directly. Registry preparation does not use this staging (#227).

### Setup

- Existing npm access rules need the documented administrator update for scoped package downloads; shipped template fixes do not update existing configurations (#126).
- Repository tool setup may be blocked by download permissions even when npm access is allowed; use approved preinstalled tools or administrator-reviewed download permissions (#131).
- This release accepts only credential-free remote Git sources as Worker input from a Workspace; saving a configuration that selects a folder or another source kind is refused with an error that names the supported kind, and work without a source input still runs. Workers can submit only text Artifacts: Markdown, plain text, or JSON (#190).
- The release installation guide is incomplete: it does not yet walk you through downloading and verifying the release, starting the App, and setting up a persistent NanoHost with Worker images. Some examples require a source checkout or assume an existing installation (#195).
- A Codex subscription can appear connected despite rejected credentials, and a stuck login can block login or deletion; administrator API logout recovered the observed rejected-credential case (#108).
- MCP catalog setup requires a tool allowlist before it can preview an unconfigured server's tools; use the vendor's documented tool names (#143).
- Remote MCP does not yet provide browser OAuth login; use the supported static bearer route (#145).
- External Agent clients use the user's authorization rather than independent Agent identities with fine-grained permissions (#152).
- Permission-based blocking of selected operations through the Policy Kernel is not yet implemented (#153).
- Workspace deletion and recovery still apply owner-only checks, so other active members can be refused (#159).
- The Web interface does not yet provide the complete Workspace membership, invitation and lifecycle experience (#160).

### Documentation

- The Core Client Boundary specification still lists Workspace repository routes and `client.repositories` methods that this release no longer provides. Repositories are Workspace data sources, and repository writes go through the Gateway-mediated vendor tools (#189).
- The Worker reliability specification names a recovery command that the operation catalog does not expose; discover and use `recovery.checkpoint-retry` (#137).
- Worker reliability documentation still describes unimplemented NanoHost transport and retired session and Goal paths, although the current implementation has replaced those paths (#162).
