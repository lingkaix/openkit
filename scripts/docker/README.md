# Docker Commands

These helpers read the single image catalog at `containers/images.json`. `build-image.sh <image-id> [tag]` passes its Dockerfile and target to Docker; `smoke-image.sh <image-id> [tag]` runs its installed smoke command. For App images it supplies build-time source and optional release-tag arguments. With no explicit source input, a clean checkout supplies its exact commit; a dirty checkout stays unknown. No runtime Git or environment fallback is used. Unknown ids fail. Worker artifacts are the empty extension base `worker-common` and the four-runtime deployment image `worker-runtimes`. Worker smoke containers, including the base derivation, use `--network=none`; synthetic loopback services remain available. Other image kinds retain their existing smoke networking.

Build and smoke the worker artifacts with `bash scripts/docker/build-image.sh worker-common`, `bash scripts/docker/build-image.sh worker-runtimes`, and their matching `smoke-image.sh` commands. Use the optional tag for isolated verification. Base smoke also builds a network-free throwaway derivation, adds one executable as root, returns to sandbox, checks the inherited baseline, and removes the temporary image.

The test-image helpers own content-addressed `test-env` identification and anonymous inspection; `run-app.sh`, `e2e-app.sh`, and app smoke helpers own the app image. The release preflight consumes the same catalog and rejects singular runtime metadata and retired worker leaf ids. Installed binaries and catalog metadata grant no endpoint or credential authority.

The persistence smoke reads the post-restart Workspace collection through the definition-derived `workspace.list` JSON binding and checks the nested Workspace record. Its pre/post-restart persistence observation is unchanged.

The App-update helper observes configured NanoHost readiness through `POST /api/app/operations/nanohost.runtime-target` with an empty JSON object, preserving bounded JSON HTTP error handling and configured identity checks. Its host fixtures use the canonical `workspace.list` binding for forbidden Workspace discovery, and its assertions retain the requirement that update admission never reads Workspace content.

The App-update helper observes retained authentication through `POST /api/app/operations/token.list` with an empty JSON object. Its before/after fixed-key token comparison and last-use exclusions remain unchanged.

The App-update helper compares staged and live Web digests before stopping the App when the candidate directory is already the live target. Matching trees reuse the live directory and pointer and remain subject to post-publication and post-boot digest verification; different trees refuse before interruption. Compatible recovery skips candidate stop and rename only when a successful all-container listing shows the active name is absent; a nonzero listing exit keeps the existing candidate path. Command timeouts require explicit host recovery, as elsewhere in the helper. Before starting the retained App, recovery checks running-container mount observations for writable Data Root users and refuses failed inspections or invalid JSON.

Run the helper's local filesystem and fake-host regressions with `python3 -I -B scripts/docker/app-update-helper.test.py` after resolving the repository's pinned Node and pnpm on `PATH` and installing dependencies. The suite builds the App API schemas and checks helper output against their real parser. The L0-L2 CI job invokes that exact command on release-tag pushes and the `l0-l2`, `release-gate`, and `full` workflow-dispatch gates, subject to its exact-commit reuse condition; pull requests run `pr-check` and do not run this suite; its Docker doubles prove helper decisions and filesystem effects, while selected-host verification remains separate.

App updates pull published release digests only. Before pulling, the helper checks Docker data-root and receipt filesystem capacity against its current 3 GiB default; shortages return `app_update_capacity` with measured and required bytes before App effects. A failure-receipt I/O error preserves the original coded cause in stdout and leaves the last durable stage authoritative. Retained release sources ignore additive fields; commit-only receipts require recovery for their own IDs, remain counted for capacity and do not block later valid receipts. The opt-in live fixture builds isolated images before launch and doubles acquisition only; it preserves host job/concurrency/restoration coverage without claiming release attribution or registry pull proof.

Receipt status validates safe deployment configuration and the receipt location independently of the compatibility assessment. A valid retained release receipt remains readable with a stale, absent, or malformed assessment. A pre-removal commit-only receipt returns `app_update_recovery_required` for that ID. Prepare, start, and supervised apply still require an assessment re-authored for the exact release candidate; status grants no execution or recovery authority.

NanoCore classifies a non-zero or signal helper exit with empty stdout as `app_update_helper_exit_before_envelope` in the server log, retaining only exit code and termination signal. It drains stderr without retaining its contents. The public result remains `app_update_unavailable`. A non-empty helper envelope remains the observation even on a non-zero exit. Use the saved request ID and separately authorized host inspection for unknown effects; do not infer success or submit another start from an absent envelope.

The deployment-admin `app-update.preflight` read aggregates running and pending Turns, queued admissions, open and closing attempts, and in-flight commands without product content. Prepare requires idle evidence. Apply rechecks under its update lock immediately before stop and persists a named refusal when work appeared. That refusal preserves existing container names and the live Web pointer and tree, and removes the staged partial Web directory. Older Apps without the operation refuse with `app_update_preflight_unsupported`; no fallback or override exists. The update lock is not a product admission barrier, so the owner states the residual window before shutdown closes admission.

Run the real-container environment regression explicitly with `OPENKIT_TEST_APP_UPDATE_ENV_HOST=1 python3 -I -B scripts/docker/app-update-helper.env-host.test.py` on a disposable Docker-capable developer host. It creates unique scratch images and stopped containers, observes Docker's merged environment after applying the helper options, and removes those fixtures. It proves candidate defaults replace old defaults while operator overrides survive. The regression passed on this host against commit `444fb18c` with Docker 29.7.2: one test, exit 0. In-process argument coverage does not replace that host-domain proof.

The App launcher leaves User directory allocation to NanoCore's recorded local User owner. Persistence smoke reads that unique User from the read-only Core database, verifies its exact directory tree and checks that the identity survives restart. It does not select an identity from a directory name.
