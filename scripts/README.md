# Repository Scripts

Root `package.json` owns the command surface and `docs/toolchain.md` owns setup and execution placement. These scripts implement those commands; they do not supply design authority.

`validate-test-governance.mjs --run -- <command>` retains command failures and rejects undeclared TAP skips. It also rejects positive unnamed skipped counts from Vitest and Node's default and spec reporters because those summaries cannot prove file-bound skip authorization. It removes ANSI decoration for skip parsing and retains the original output for display.

## Release Inputs And Verification

`release-ci-reuse.mjs --repository <owner/repo> --workflow ci.yml --sha <full sha> --job <exact job name>` reads GitHub Actions with the job-scoped `GITHUB_TOKEN` and reports the run, latest attempt, and successful job identity for one completed exact-commit workflow-dispatch run or main-push release-gate run. Reuse remains per job, never across commits or from another branch. It paginates runs and attempt jobs, rechecks the selected attempt, and exits 1 when no job qualifies or 2 on usage/API errors. Complete L0-L2 shard steps can reuse exact-source evidence on main and tag pushes; NanoCore e2e reuses it on tag pushes. Either failure result runs the normal tests, and the host aggregate requires every successful shard. Fixtures inject HTTP responses without network access. See the [release cookbook](../docs/cookbooks/release.md#cadence-commands) for preparation, admission, pre-merge and local smoke commands.

`release-notes.mjs` checks `release-notes/<tag>.md` and the tag workflow fails before image promotion when that file is missing or malformed. The verify job compares the published release body through `--compare-body`.

`release-preflight.mjs` validates the selected release inputs and the schema-version-2 NanoHost capability profile. `package-release-assets.mjs` reads checkout-owned inputs from the selected Git revision and produces the controlled release archives. The operations envelope includes `release-identity.json` with the archived commit and release tag; the NanoHost manifests retain their existing source provenance. NanoHost packaging selects `linux/amd64` and `linux/arm64` from the distribution table in `lib/nanohost-elf.mjs`; it bundles exact `host-manifest.json` bytes, profile id and digest, product commit, and libc symbol-version requirements derived from both ELF executables. `verify-nanohost-release.mjs` checks the archive tree, checksums, checkout-owned bytes, provenance, ELF and derived requirements, then performs a contained staging install.

Run `pnpm release:preflight -- --tag <tag>` and `pnpm release:package -- --tag <tag>` through the release cookbook. Release and pre-release tag CI runs target-native real-host qualification before publication under the release and NanoHost specifications; pull-request and manual gates do not run it.

For a complete NanoHost release, supply `--nanohost-amd64-binary`, `--nanohost-arm64-binary`, `--openshell-amd64-gateway-archive`, `--openshell-arm64-gateway-archive`, `--openshell-license`, and `--openshell-notices` to the existing packager. Gateway archive and extracted executable identities come from `gateway.targets["linux/<architecture>"]` in the schema-version-2 OpenShell release pin. The shared checksum covers the operations Skill and both NanoHost archives. Tag packaging installs checkout dependencies before invoking the packager and downloads the accepted inputs with the test image's built-in Node fetch. Post-publication asset inspection also installs checkout dependencies inside that image; its Node 24 verifier runs operations discovery from the extracted envelope outside the checkout while Docker and GitHub Release access remain on the host.

## Upgrade From The Previous Release Candidate

`upgrade-from-previous-guest.py run PRIVATE_INPUT.json` operates only the already prepared `lrt-p14-rehearsal` guest, its `lrt-p14-network` carrier and the `lrt-p14-upgrade` App container. It does not provision a guest, change capabilities, install host prerequisites or touch a retained deployment. The private input pins previous/candidate artifacts and their prepared private payload bindings. Both App and Worker OCI identities must already be loaded in the local Engine; OCI manifest digests remain distinct from Docker configuration IDs. The operator installs and configures the previous published release with synthetic accounts and an admitted provider/Agent before this command. Use the immediately previous published RC; the current baseline is rc.8 for the rc.9 pre-reset candidate. A reset cannot qualify as a continuity upgrade. [Release Management](../docs/specs/20260829-release_management.md#upgrade-from-the-previous-release-candidate) owns the requirement from rc.13.

The driver stops the complete fixture Host domain and App, seeds the corpus with the previous image's own production writers, activates the matching old Worker image and runs a baseline Turn, then stops writers and retains complete previous state. It replaces matching components against that same state, checks login, administrator access and readiness, compares candidate reader results, activates the matching candidate Worker image and runs one fresh Turn on the retained B01 Workspace. It stops only its owned fixture processes on completion. Failure leaves the normal private result and any known request/Turn selectors for inspection. There is no submission retry or automatic rollback. Preserve the stopped previous container, complete retained state and previous payloads for operator recovery.

`upgrade-from-previous.mjs` exposes the individual fixture phases used by that driver: `fixtures`, `seed`, `activate-before`, `worker-before`, `operator-read-before`, `snapshot`, `operator-read`, `compare`, `activate`, `worker` and `retirement`. It reads the current register instead of silently accepting a fixed family count. The file and SQL corpus modules use the selected image's `/app/nanocore/dist` owners. SQL rows compare through their native readers; originals and opaque files compare by exact digest. The Artifact sample uses the current-head, immutable-version and original-payload families from the register. Both text and binary versions are read through the existing exact native reader; missing descriptors or originals fail without reconstruction. The SQL sample creates and reopens an Artifact judgement and an exact candidate selection through their existing native owners, and retains the selected source descriptors and original bytes. Snapshot freezes selected old external paths, so an additive candidate image or file does not change the comparison subject. The two operator-format samples use existing no-effect App-helper fixtures and a genuine admission-refused component outcome; they do not claim an actual component update. The stopped Host's own Image Store reader must still admit the old image, and candidate startup admits retained Host identity metadata. A fresh Worker Turn proves work after upgrade, not native-session resume. The baseline Worker also freezes its actual idle binding, accepted AgentSession digest, retained-storage attachment, snapshot identity and exact AEP bytes. The candidate Worker must retire that old binding in a fresh, ready and predecessor-fenced Epoch while preserving the historical proof and AEP bytes, including a pre-naming package that current execution admission rejects. The live Worker check proves readiness before stopping; the final offline retirement check joins its exact Turn to the retained backend origin, compares that Epoch with the previous binding and checks byte preservation without reading cleared live-readiness flags.

Private input credentials are supplied only in `OPENKIT_UPGRADE_ADMIN_TOKEN` and `OPENKIT_UPGRADE_LOGIN_PASSWORD`; never print them or put their values in arguments, input JSON or reports. Keep the prepared layout, source checkouts, synthetic inputs and result below the existing private L-RT temporary root. The helper containers mount only that private layout and read-only source checkouts. Their Data Root and retained paths keep the same absolute names across both revisions. The input's `externalSelections` names actual previous Host metadata, opaque/native files and image entries; the `fixtures` phase supplies the App-helper and component selections. The driver verifies complete custody before changing payloads. An existing report is an inspection boundary, not permission to resume a failed invocation.

Run the complete offline instrument suite after building NanoCore and its dependencies, with the pinned toolchain and the normal CPU slot. This runs no guest, service, image build, upstream request or real Worker Turn:

```bash
pnpm exec turbo run build --filter=@openkit/nanocore...
node scripts/validate-test-governance.mjs --run -- node --test --test-concurrency=1 tests/upgrade-from-previous*.test.mjs
```

The private operator recipe belongs to the existing operations handoff. Real qualification also requires the prepared previous release, its admitted provider and matching images; these offline checks cannot substitute for that run. No extra CI dispatch is required.

## NanoHost Static Checks

After checking the outer archive checksum, extract the NanoHost archive beside its original `.tar.gz`, then run the bundled `./install.sh --check-host`. The checker reads only bundled checksum-verified inputs and verifies that the adjacent archive contains those exact bytes. Checking and installation, including staging verification, require Python 3.8 or later with its standard library at `/usr/bin/python3`, with isolated imports and bytecode writes disabled. It is not a NanoHost service runtime dependency; missing or unusable inspection returns one bounded `cannot-check` result and blocks installation. Every static probe has a deadline, and no checker mode provisions packages or invokes a service lifecycle command.

Each installer invocation bounds interpreter execution and result collection together in the existing POSIX shell and verifies bundled inputs once through that path; no shell checksum prepass runs before it. The checker emits one JSON object and a newline with a hard verdict and separate combined-deployment resource recommendation. `./install.sh --check` and live installation consume the same result while retaining their installation-disposition output. `DESTDIR=/new/canonical/path ./install.sh` verifies bundled inputs and stages only the three fixed payloads, with the existing host-check exemption.

See [Deployment Host Requirements](../docs/specs/20260909-deployment_host_requirements.md), [NanoHost Runtime And Transport](../docs/specs/20260802-nanohost_runtime_and_transport.md), and the [Release Cookbook](../docs/cookbooks/release.md) for the owners and qualification boundary.

`release-record.mjs` generates offline manifests, reviewed drafts and private compact closeout projections. It imports the existing exported notes functions; `release-notes.mjs` remains byte-identical to the proved publication baseline. `tests/release-manifest.test.mjs` checks its raw bytes against the pinned SHA-256 from baseline commit `23f3e2dc`, without requiring Git history in CI. `release-safety.mjs` owns shared credential-safe evidence, canonical identities and single-shot effect retention for the scripts and qualification kit. The kit pins that script-side dependency as part of its instrument digest.

`release-publication-check.mjs EVIDENCE.json` reads immutable Git objects at exact P and `baseline.sha`. Its proof includes publication jobs, moved candidate jobs, the matrix and read-only registry admission. Native App publication also includes its index loader, both native smoke legs and promotion. It follows invoked scripts and their static relative-import and literal-file dependencies, including the native missing-setter fixture. Trailing-slash directory URLs locate a working directory and are not file inputs. Missing or changed file inputs refuse even if supplied hashes agree. The proof retains each input blob identity and the aggregate fingerprint.

`release-observe.mjs` collects baseline workflow, tag-push and job provenance from current GitHub API responses. It resolves lightweight or annotated tags to the actual commit and rechecks the tag and completed run after job collection. Missing or mismatched job run, attempt or source identities refuse collection; authored baseline fields cannot fill them.

## Retrieval Build Supply

`retrieval-cargo.sh` verifies the repository's pinned IPADIC archive with `retrieval-dictionary.py` before Cargo uses its fixed build cache. It forwards the requested Cargo operation without another build runner. `retrieval-notices.py` retains SPDX metadata and notices supplied by the locked Cargo packages, verifies the vendored missing-crate notice provenance, and includes explicit unresolved gaps. The App image copies this output beside the target-native executable; the CI development image seeds the same archive. `release-tests.mjs` builds NanoCore and its dependency graph, including the kernel, before NanoCore tests are collected because CLI-backed tests import compiled Skill helpers. Its root suite inlines the existing CLI build and bundle steps, including NanoCore helpers, so the placed test command enters the test environment only once. These scripts add no publication effect or Sandbox installation.

`release-record.mjs --publication-assets DIR` joins the committed `release-notes/<tag>.manifest.json` compatibility facts with the exact source and image records, writes the fifth attachment and appends its checksum. `--verify-publication-assets DIR` independently reconstructs the manifest and checks the downloaded archive bytes. The authored assessment cannot override source or App identity. Missing, negative or unassessed facts refuse.

`release-promotion.mjs` supplies the bounded tag-only synthetic stable rehearsal in `notrucked/openkit`. It verifies the current successful source attempt, notes, indexes, manifest and archive bytes before assigning scratch stable tags, then repeats published verification and anonymous worker-base inspection. It contains no build or package operation. Stable assets keep their prerelease names, provenance and bytes. `--check-only` reads and verifies without publishing; an existing stable identity requires complete matching version tags and Latest. The CLI refuses production, and no synthetic result grants production stable eligibility.

`ci-l0-l2.mjs --matrix` derives all deterministic execution partitions, and `--coverage-matrix` derives the required whole-owner coverage merges. Worker Shim uses two Vitest file partitions. NanoCore and Web each run as a complete owner, and seven other complete coverage owners share one job with separate execution reports. Every partition compares unit and covered case inventories and retains its execution report, inventory and blob. `--merge-coverage <owner>` refuses incomplete or overlapping file and case unions, then merges coverage under the unchanged package configuration. `--join <directory>` requires all execution and merged-coverage observations, including the existing exactly-once root inventory. One shared static job and two native/catalog groups retain every previous command. Static commands share prepared build outputs; measured NanoCore partition and collection costs did not justify splitting that owner. Exact-commit reuse must download the cited run-attempt artifact; an absent artifact fails closed.
